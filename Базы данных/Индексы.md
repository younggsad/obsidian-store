### Общее понятие

> **Индекс** — вспомогательная структура данных, ускоряющая **поиск** по столбцу (или выражению), ценой места на диске и небольшого замедления записи (`INSERT`/`UPDATE`/`DELETE` теперь должны обновлять ещё и индекс).

> **Без индекса:** поиск требует **полного перебора** (full table scan). **С индексом:** поиск примерно за логарифмическое время, как в оглавлении книги.

```sql
CREATE INDEX idx_users_email ON users(email);
```

PK автоматически получает уникальный индекс. `UNIQUE`-ограничения тоже создают индекс.

### B-tree — самый распространённый тип

> Сбалансированное дерево, данные отсортированы. Спроектирован с учётом чтения данных **блоками с диска** — минимизирует количество обращений к диску за счёт широких узлов (B-tree, а не бинарное дерево).

**Подходит для:** точного поиска (`=`), диапазонного поиска (`BETWEEN`, `>`, `<`), сортировки (`ORDER BY`), поиска по префиксу (`LIKE 'abc%'`). Индекс по умолчанию в большинстве СУБД.

### Hash-индекс

> Хэш-функция → мгновенный доступ к "корзине" данных, O(1) в среднем.

**Подходит только для точного совпадения** (`WHERE email = ...`). **Не подходит** для диапазонов — хэш "перемешивает" значения, соседние по значению числа оказываются в разных корзинах. В PostgreSQL долгое время hash-индексы не были WAL-логируемыми (не переживали restore из бэкапа) — с версии 10 это исправлено, но B-tree всё равно остаётся дефолтным выбором почти всегда.

### GIN / GiST (специализированные индексы, PostgreSQL)

> **GIN (Generalized Inverted Index)** — для составных значений, где нужно искать "элемент внутри": полнотекстовый поиск (`tsvector`), массивы, `JSONB` (`WHERE data @> '{"key": "value"}'`).

> **GiST (Generalized Search Tree)** — для геометрических данных, диапазонов, поиска "ближайшего соседа", полнотекстового поиска с ранжированием.

### Clustered index

> Определяет **физический порядок хранения** данных на диске. У таблицы может быть **только один** (обычно это PK, как в MySQL/InnoDB — там таблица физически и есть clustered index по PK). Быстрый для диапазонных запросов — данные физически лежат рядом.

Важный нюанс: в PostgreSQL нет "истинного" постоянно поддерживаемого clustered index — там команда `CLUSTER` физически переупорядочивает таблицу по индексу **один раз**, но новые вставки снова идут в произвольном порядке (в отличие от InnoDB в MySQL, где кластеризация поддерживается постоянно).

### Non-clustered index

> **Отдельная** структура с указателями на реальные строки, физический порядок данных не меняет. Таблица может иметь **много** таких индексов. Требует дополнительного шага — **bookmark/key lookup** (перейти от указателя к реальной строке), поэтому чуть медленнее clustered.

### Составные (композитные) индексы

> Индекс по нескольким столбцам, **порядок важен** (правило "leftmost prefix"):

```sql
CREATE INDEX idx_users_country_city ON users(country, city);
-- ускорит: WHERE country = ...
-- ускорит: WHERE country = ... AND city = ...
-- НЕ ускорит: WHERE city = ... (без условия на country — ведущий столбец не задействован)
```

### Покрывающий индекс (covering index)

> Индекс, который содержит **все** столбцы, нужные запросу — тогда база вообще не обращается к самой таблице (не делает "key lookup"), а берёт всё прямо из индекса. Это называется **index-only scan**.

```sql
CREATE INDEX idx_orders_covering ON orders(user_id) INCLUDE (total, created_at); -- PostgreSQL
-- запрос ниже полностью обслуживается индексом, без обращения к таблице:
SELECT total, created_at FROM orders WHERE user_id = 5;
```

### Селективность

> Отношение уникальных значений к общему числу строк.

```
Высокая (email) → индекс эффективен

Низкая (is_active: true/false)
→ индекс малополезен, оптимизатор может проигнорировать и сделать full scan
```

> Формула: `селективность = уникальные значения / всего строк`. Ближе к 1 — эффективнее.

### Когда индекс НЕ используется

1. **Низкая селективность** — оптимизатор предпочтёт full scan (например, столбец `is_deleted` с двумя значениями на миллион строк).
2. **Функция применена к столбцу в запросе:**

```sql
SELECT * FROM users WHERE LOWER(email) = 'alice@mail.com';
-- обычный индекс на email не сработает

CREATE INDEX idx_email_lower ON users(LOWER(email));
-- нужен функциональный индекс (expression index)
```

3. **Не используется ведущий столбец составного индекса** (см. пример выше — только `city` без `country`).
4. **`LIKE` с ведущим `%`:**

```sql
WHERE name LIKE '%son'
-- индекс НЕ работает эффективно (нужен полный обход или специальный триграммный индекс pg_trgm)

WHERE name LIKE 'John%'
-- индекс МОЖЕТ работать, т.к. B-tree отсортирован по префиксу
```

5. **Маленькая таблица** — full scan может быть быстрее накладных расходов на использование индекса.
6. **`OR` между разными столбцами** без покрывающего составного/битмап индекса — оптимизатор часто не может эффективно объединить два разных индекса.
7. **Неявное приведение типов** — сравнение `INTEGER`-столбца со строкой может помешать использовать индекс в некоторых СУБД.
8. **Таблица недавно сильно изменилась, а статистика устарела** — планировщик принимает решения на основе статистики (`ANALYZE` в PostgreSQL); устаревшая статистика может привести к неверному выбору плана.

> **Инструмент проверки:** `EXPLAIN ANALYZE` (PostgreSQL) / `EXPLAIN` (MySQL) — показывает реальный план выполнения запроса, использовался ли индекс, сколько строк было просканировано, сколько времени заняла каждая операция.
