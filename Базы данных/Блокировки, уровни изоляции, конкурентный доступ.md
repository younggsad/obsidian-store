### Уровни изоляции

> Определяются тем, какие **аномалии параллельного выполнения** допускаются.

- **Dirty Read** — чтение **незафиксированных** изменений другой транзакции (которая может ещё откатиться).
- **Non-Repeatable Read** — повторное чтение одной и той же строки даёт разные результаты (другая транзакция изменила и зафиксировала её между чтениями).
- **Phantom Read** — повторный запрос с условием возвращает разное **количество** строк (другая транзакция вставила новую подходящую строку между запросами).

|Уровень|Dirty Read|Non-Repeatable Read|Phantom Read|
|---|---|---|---|
|**Read Uncommitted**|Возможен|Возможен|Возможен|
|**Read Committed** (default в PostgreSQL, Oracle, SQL Server)|Предотвращён|Возможен|Возможен|
|**Repeatable Read** (default в MySQL/InnoDB)|Предотвращён|Предотвращён|Возможен (в PostgreSQL — тоже предотвращён благодаря snapshot-модели MVCC)|
|**Serializable**|Предотвращён|Предотвращён|Предотвращён|

**Практический вывод:** выше изоляция → больше гарантий, но больше блокировок/конфликтов и ниже производительность (или больше retry на `Serializable`). `Read Committed` — разумный баланс по умолчанию. `Serializable` — для критичных операций (финансы, где недопустима любая аномалия).

```sql
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
-- ...
COMMIT;
```

### MVCC (Multi-Version Concurrency Control)

> Механизм, которым PostgreSQL (и во многом MySQL/InnoDB) реализуют изоляцию **без блокирования читателей писателями**: вместо блокировки строки при чтении, каждая транзакция видит **свою версию (snapshot)** данных на момент начала (или начала запроса). Пишущие транзакции создают новую версию строки, не трогая старую, пока она может быть нужна другим читателям. Отсюда правило: **читатели не блокируют писателей, и наоборот** — это ключевое отличие от систем с чисто блокировочной моделью.

### Блокировки (locks)

> **Пессимистичная блокировка (pessimistic locking)** — заранее блокируем строку перед изменением, предполагая, что конфликт вероятен:

```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- блокирует строку до конца транзакции
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

> **Оптимистичная блокировка (optimistic locking)** — не блокируем ничего заранее, а проверяем на момент записи, что данные не были изменены кем-то другим (обычно через версию/timestamp столбец):

```sql
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5; -- если version уже не 5 — кто-то опередил, 0 строк обновлено, приложение делает retry
```

Оптимистичная блокировка лучше подходит при **редких** конфликтах (мало параллельной записи в одну строку) — меньше накладных расходов на блокировки. Пессимистичная — лучше при **частых** конфликтах, чтобы не тратить время на неудачные retry.

### Deadlock (взаимная блокировка)

> Ситуация, когда транзакция A ждёт блокировку, удерживаемую транзакцией B, а B в это же время ждёт блокировку, удерживаемую A — circular wait, ни одна не может продолжиться.

```
Транзакция A:                    Транзакция B:
UPDATE accounts WHERE id=1       UPDATE accounts WHERE id=2
-- ждёт --                       -- ждёт --
UPDATE accounts WHERE id=2       UPDATE accounts WHERE id=1
```

СУБД обычно детектирует deadlock автоматически и принудительно откатывает одну из транзакций с ошибкой, чтобы разорвать цикл. **Практическое правило для избежания deadlock:** всегда блокировать/изменять строки в одном и том же согласованном порядке (например, всегда по возрастанию `id`) во всех местах кода.
