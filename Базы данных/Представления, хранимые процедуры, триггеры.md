### VIEW (представление)

> Сохранённый именованный SQL-запрос, который можно использовать как обычную таблицу для чтения. Не хранит данные физически (обычное представление) — просто разворачивается в исходный запрос при каждом обращении.

```sql
CREATE VIEW active_users AS
SELECT id, name, email FROM users WHERE is_active = true;

SELECT * FROM active_users WHERE name LIKE 'A%';
```

Плюсы: упрощает часто используемые сложные запросы, скрывает сложность, может ограничивать доступ (пользователю дают права только на view, не на исходные таблицы).

> **Materialized View (материализованное представление)** — в отличие от обычного view, **физически хранит** результат запроса на диске. Быстрее читать (не нужно пересчитывать каждый раз), но данные могут устареть — нужно периодически обновлять (`REFRESH MATERIALIZED VIEW`).

```sql
CREATE MATERIALIZED VIEW daily_sales AS
SELECT DATE(created_at) AS day, SUM(total) AS total_sales
FROM orders
GROUP BY DATE(created_at);

REFRESH MATERIALIZED VIEW daily_sales;
```

### Хранимые процедуры и функции

> Код (обычно на процедурном расширении SQL — PL/pgSQL в PostgreSQL, T-SQL в MS SQL Server), сохранённый и выполняемый на стороне базы данных.

```sql
CREATE OR REPLACE FUNCTION get_user_total(p_user_id INTEGER)
RETURNS NUMERIC AS $$
DECLARE
  result NUMERIC;
BEGIN
  SELECT COALESCE(SUM(total), 0) INTO result FROM orders WHERE user_id = p_user_id;
  RETURN result;
END;
$$ LANGUAGE plpgsql;

SELECT get_user_total(5);
```

Плюсы: меньше сетевых обращений (логика выполняется рядом с данными), инкапсуляция сложной логики. Минусы: сложнее версионировать/тестировать по сравнению с кодом приложения, привязка к конкретной СУБД, размывание бизнес-логики между приложением и базой.

### Триггеры

> Код, который автоматически выполняется в ответ на событие (`INSERT`/`UPDATE`/`DELETE`) над таблицей.

```sql
CREATE OR REPLACE FUNCTION update_timestamp() RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_update_timestamp
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION update_timestamp();
```

Типичное применение: автоматическое обновление `updated_at`, ведение audit log, поддержание денормализованных агрегатов в актуальном состоянии, валидация сложных бизнес-правил. Минус — "невидимая" для разработчика логика, которая срабатывает неявно, что усложняет отладку.
