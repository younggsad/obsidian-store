### EXPLAIN / EXPLAIN ANALYZE

> `EXPLAIN` показывает **план выполнения** запроса, который построил оптимизатор — какие индексы/сканирования будут использованы и в каком порядке. `EXPLAIN ANALYZE` **реально выполняет** запрос и добавляет фактические цифры (время, количество строк) — точнее, но выполняет запрос по-настоящему (осторожно с `EXPLAIN ANALYZE` на `DELETE`/`UPDATE` в проде без `ROLLBACK`).

```sql
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 5;
```

Ключевые вещи, на которые смотрят в плане: `Seq Scan` (полное сканирование таблицы — плохо для больших таблиц с избирательным условием) против `Index Scan`/`Index Only Scan` (использование индекса), оценочное (`estimated`) число строк против фактического (`actual`) — большое расхождение сигнализирует об устаревшей статистике.

### Проблема N+1

> Классическая проблема производительности в коде приложения (особенно с ORM): вместо одного запроса, объединяющего данные, приложение делает **1 запрос**, чтобы получить список сущностей, а затем **N дополнительных запросов** — по одному на каждую сущность, чтобы получить связанные данные.

```
-- Плохо (N+1):
SELECT * FROM users;                          -- 1 запрос
SELECT * FROM orders WHERE user_id = 1;       -- N запросов, по одному на пользователя
SELECT * FROM orders WHERE user_id = 2;
...

-- Хорошо: один JOIN или один запрос с IN
SELECT * FROM orders WHERE user_id IN (1, 2, 3, ...);
-- либо
SELECT u.*, o.* FROM users u LEFT JOIN orders o ON o.user_id = u.id;
```

Решается через **eager loading** в ORM (например, `select_related`/`prefetch_related` в Django, `.includes` в Rails, `JOIN FETCH` в JPA/Hibernate) — заранее подгрузить связанные данные одним/двумя запросами вместо множества.

### Пул соединений (connection pool)

> Установка соединения с БД — дорогая операция (TCP-хендшейк, аутентификация, выделение ресурсов на стороне сервера). **Пул соединений** держит заранее открытый набор соединений и переиспользует их между запросами приложения, вместо того чтобы открывать/закрывать соединение на каждый запрос.

Примеры инструментов: PgBouncer/Pgpool для PostgreSQL, встроенные пулы в ORM/драйверах (HikariCP для Java, встроенный пул в `pg`/`node-postgres` и т.д.). Важно правильно подобрать размер пула — слишком маленький создаёт очередь ожидания, слишком большой может перегрузить сервер БД избыточным количеством параллельных активных соединений.
