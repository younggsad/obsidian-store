### Primary Key (PK)

> Столбец (или комбинация столбцов), **однозначно** идентифицирующий строку. Требования: уникальность, не-`NULL`, неизменность (в идеале никогда не меняется после создания).

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name TEXT
);
```

**Natural key vs surrogate key:**

> **Естественный ключ (natural key)** — уже существующий в предметной области уникальный атрибут (email, номер паспорта, ISBN). **Суррогатный ключ (surrogate key)** — искусственно сгенерированный идентификатор без бизнес-смысла (`SERIAL`, `UUID`, `AUTO_INCREMENT`).

На практике почти всегда предпочитают суррогатный ключ: естественные ключи могут меняться (email пользователь может сменить), могут быть составными и громоздкими для FK-ссылок, могут содержать чувствительные данные.

```sql
-- surrogate key через UUID (полезно при распределённых системах —
-- можно генерировать id на клиенте до записи в базу, без риска коллизий между узлами)
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT UNIQUE NOT NULL
);
```

### Foreign Key (FK)

> Столбец, ссылающийся на PK (или UNIQUE-столбец) другой таблицы — реализует связь между таблицами и обеспечивает **ссылочную целостность (referential integrity)**.

```sql
CREATE TABLE orders (
  id SERIAL PRIMARY KEY,
  user_id INTEGER REFERENCES users(id),
  total NUMERIC
);
```

**Зачем именно FK:** база данных **обеспечивает целостность автоматически** — нельзя вставить `user_id`, которого нет в `users`, и нельзя случайно "осиротить" заказы, беспорядочно удаляя пользователей.

**Поведение при удалении/обновлении родительской строки (`ON DELETE` / `ON UPDATE`):**

```sql
user_id INTEGER REFERENCES users(id) ON DELETE CASCADE   -- удалить заказы вместе с пользователем
user_id INTEGER REFERENCES users(id) ON DELETE RESTRICT  -- запретить удаление, если есть заказы (по умолчанию похожее поведение)
user_id INTEGER REFERENCES users(id) ON DELETE SET NULL  -- обнулить ссылку, заказ остаётся "ничей"
user_id INTEGER REFERENCES users(id) ON DELETE SET DEFAULT -- поставить значение по умолчанию
```

`RESTRICT`/`NO ACTION` — безопасный выбор по умолчанию для большинства бизнес-данных (не терять данные молча). `CASCADE` уместен для по-настоящему зависимых сущностей (например, `order_items`, которые не имеют смысла без `order`).

### Типы связей

> **One-to-Many (1:N)** — один пользователь → много заказов, каждый заказ принадлежит одному пользователю. FK лежит в таблице "многих" (`orders.user_id`). Это самый распространённый тип связи в реляционных схемах.

> **Many-to-Many (N:M)** — статья может иметь много тегов, тег — принадлежать многим статьям. Реализуется через **промежуточную (junction / associative) таблицу**:

```sql
CREATE TABLE article_tags (
  article_id INTEGER REFERENCES articles(id),
  tag_id INTEGER REFERENCES tags(id),
  PRIMARY KEY (article_id, tag_id)
);
```

Без промежуточной таблицы связь many-to-many не выразить, не нарушив нормализацию (нельзя хранить "список id" в одной ячейке — это нарушение 1NF). Составной `PRIMARY KEY (article_id, tag_id)` заодно не даёт вставить дублирующую пару.

> **One-to-One (1:1)** — например, пользователь и его расширенный профиль в отдельной таблице. Причины так делать:
> 
> - разделение часто запрашиваемых и редко запрашиваемых данных (сама таблица `users` компактнее и быстрее сканируется);
> - разделение чувствительных данных (например, паспортные данные в отдельной таблице с более строгими правами доступа);
> - опциональные данные, которые есть не у каждой строки.

```sql
CREATE TABLE user_profiles (
  user_id INTEGER PRIMARY KEY REFERENCES users(id),
  bio TEXT,
  avatar_url TEXT
);
```

Ключевой признак 1:1 в схеме — `user_id` одновременно и PK, и FK (то есть на одного пользователя может быть максимум одна строка профиля).

### Составные ключи (Composite key)

> PK, состоящий из нескольких столбцов. Типичный случай — junction-таблицы many-to-many (см. выше), где сама пара `(article_id, tag_id)` уникально идентифицирует строку связи.
