> **SQL (реляционные базы данных)** — данные организованы в **таблицы** со строго заданной схемой (**schema-on-write**), связанные между собой через ключи. Примеры: PostgreSQL, MySQL, SQLite, Oracle, MS SQL Server.

```
Таблица users:

| id | name  | email           |
|----|-------|-----------------|
| 1  | Alice | alice@mail.com  |
| 2  | Bob   | bob@mail.com    |

Таблица orders:

| id | user_id | total |
|----|---------|-------|
| 1  | 1       | 99.90 |
```

`user_id` в `orders` — внешний ключ, ссылающийся на `id` в `users` — это и есть "реляционность".

> **NoSQL** — базы данных, не использующие табличную реляционную модель (**schema-on-read** или гибкая схема):

- **Документные** (MongoDB, CouchDB) — гибкие JSON/BSON-подобные документы, разная структура в одной коллекции. Удобны, когда сущность естественно представляется целиком одним объектом (профиль пользователя со всеми вложенными данными).
- **Ключ-значение** (Redis, Memcached, DynamoDB) — простейшая модель "ключ → значение", очень быстрый доступ, часто хранится в памяти. Используется для кэша, сессий, счётчиков, очередей.
- **Колоночные** (Cassandra, HBase, ClickHouse) — данные хранятся по столбцам, а не по строкам, оптимизированы для аналитики и больших объёмов записи (пишущая нагрузка, временные ряды, логи).
- **Графовые** (Neo4j, ArangoDB) — узлы и рёбра, оптимизированы для данных со сложными связями (соцсети, рекомендации, маршруты).

**Когда SQL:**

- данные хорошо структурированы и структура стабильна;
- важна целостность связей между сущностями (внешние ключи, ограничения);
- нужны сложные запросы с объединением множества таблиц, агрегацией, отчётностью;
- важны строгие транзакционные гарантии (деньги, бронирования, бухгалтерия).

**Когда NoSQL:**

- структура данных часто меняется или неоднородна между записями;
- нужна очень высокая скорость записи или чтения при простом доступе по ключу;
- данные естественно организованы как самодостаточные документы;
- нужно простое горизонтальное масштабирование "из коробки" на много серверов;
- временные ряды, логи, большие объёмы неструктурированных данных.

### CAP-теорема (часто спрашивают вместе с SQL vs NoSQL)

> В распределённой системе одновременно можно гарантировать **не более двух** из трёх свойств:

- **Consistency (согласованность)** — все узлы видят одинаковые (актуальные) данные в любой момент времени.
- **Availability (доступность)** — каждый запрос получает ответ (не ошибку), даже если часть узлов недоступна.
- **Partition tolerance (устойчивость к разделению сети)** — система продолжает работать при разрыве связи между узлами.

На практике partition tolerance в распределённых системах обязательна (сеть может разорваться всегда), поэтому реальный выбор — между **CP** (согласованность важнее доступности, например MongoDB в дефолтных настройках, HBase) и **AP** (доступность важнее мгновенной согласованности, например Cassandra, DynamoDB — там используется **eventual consistency**, "согласованность в конечном счёте").

Классические реляционные СУБД (PostgreSQL, MySQL) на одном узле не подпадают под CAP напрямую (там нет разделения сети), но в кластерных/реплицированных конфигурациях выбор та же — обычно тяготеют к CP.
