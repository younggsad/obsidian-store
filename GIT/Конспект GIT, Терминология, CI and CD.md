# ЧАСТЬ 1. ТЕРМИНОЛОГИЯ

|Термин|Значение|
|---|---|
|**Repository (репозиторий)**|папка проекта, за изменениями которой следит Git|
|**Commit (коммит)**|"снимок" состояния файлов в определённый момент времени, с уникальным хэшем-идентификатором|
|**Branch (ветка)**|independent линия разработки — указатель на конкретный коммит, позволяющий вести параллельную работу|
|**HEAD**|указатель на текущий коммит/ветку, с которой сейчас работаешь|
|**Working directory (рабочая директория)**|файлы на диске в их текущем состоянии, как ты их видишь и редактируешь|
|**Staging area / Index (индекс)**|промежуточная зона — сюда добавляют файлы командой `git add` перед тем, как закоммитить|
|**Remote (удалённый репозиторий)**|версия репозитория, расположенная на сервере (GitHub, GitLab и т.д.)|
|**Origin**|стандартное имя для основного удалённого репозитория (просто соглашение, можно назвать иначе)|
|**Merge (слияние)**|объединение изменений из одной ветки в другую|
|**Rebase (перебазирование)**|перенос коммитов одной ветки поверх другой, с переписыванием истории|
|**Conflict (конфликт)**|ситуация, когда Git не может автоматически объединить изменения (правки в одних и тех же строках)|
|**Clone (клонирование)**|создание локальной копии удалённого репозитория|
|**Fork**|создание собственной копии чужого репозитория на сервере (GitHub и т.д.), независимой от оригинала|
|**Pull Request / Merge Request (PR/MR)**|запрос на слияние своей ветки в основную, с возможностью code review перед этим|
|**Tag (тег)**|метка на конкретном коммите, обычно используется для версий релизов (`v1.0.0`)|
|**Stash**|временное "отложенное" сохранение незакоммиченных изменений, без создания коммита|
|**Upstream**|ветка на удалённом репозитории, с которой связана локальная ветка (для `push`/`pull` без явного указания)|
|**Detached HEAD**|состояние, когда `HEAD` указывает напрямую на коммит, а не на ветку (например, после `checkout` конкретного хэша коммита)|

# ЧАСТЬ 2. БАЗОВЫЕ КОМАНДЫ

## 2.1 Настройка и создание репозитория

```bash
# создать новый репозиторий в текущей папке
git init                   

# склонировать удалённый репозиторий
git clone <url>             

# склонировать в папку с конкретным именем
git clone <url> <папка>     

# настроить имя для коммитов
git config --global user.name "Имя"      

# настроить email 
git config --global user.email "email"   
```

## 2.2 Отслеживание изменений

```bash
# показать текущее состояние (что изменено, что готово к коммиту)
git status   

# показать построчные различия в НЕзастейдженных изменениях             
git diff               

# показать различия в уже застейдженных изменениях (то, что готово к коммиту)  
git diff --staged     

# история коммитов  
git log       

# компактная история — по одной строке на коммит            
git log --oneline  

# визуальный граф веток и коммитов       
git log --graph --oneline --all  
```

## 2.3 Добавление и коммит

```bash
# добавить конкретный файл в staging area
git add file.js          

# добавить ВСЕ изменённые/новые файлы в текущей папке
git add .
   
# добавить все изменения во всём репозитории (включая удаления)              
git add -A   

# зафиксировать изменения из staging area с сообщением             
git commit -m "Сообщение" 

# сократить add + commit ЗА ОДИН ШАГ — но только для файлов, которые Git уже отслеживает (новые файлы так не добавятся!)
git commit -am "Сообщение" 

# изменить ПОСЛЕДНИЙ коммит (сообщение и/или содержимое)
git commit --amend        
```

⚠️ `git commit -am` не сработает для новых, ещё не отслеживаемых файлов — только `git add` явно добавит их впервые.

# ЧАСТЬ 3. РАБОТА С ВЕТКАМИ

## 3.1 Создание, переключение, удаление

```bash
# список локальных веток (текущая отмечена *)
git branch                    

# список ВСЕХ веток, включая удалённые
git branch -a

# создать новую ветку (без переключения на неё!)  
git branch <имя>

# переключиться на существующую ветку              
git checkout <имя>

# современный аналог checkout для переключения веток            
git switch <имя>              
```

### ⭐ Создание ветки с одновременным переключением

```bash
# СОЗДАТЬ и СРАЗУ переключиться — классический способ
git checkout -b <имя-ветки>    

# то же самое, современный синтаксис (-c = create)   
git switch -c <имя-ветки>         
```

Можно сразу указать, от какой точки создавать ветку:

```bash
# создать от ветки main
git checkout -b feature/login main    

# создать от конкретного коммита (по хэшу)     
git checkout -b hotfix/bug-123 a1b2c3d

# создать от удалённой ветки     
git switch -c release/2.0 origin/develop   
```

### Удаление веток

```bash
# удалить ветку (безопасно — откажет, если есть неслитые изменения)
git branch -d <имя>  

# удалить ветку ПРИНУДИТЕЛЬНО, даже если изменения не слиты     
git branch -D <имя>  

# удалить ветку на удалённом репозитории     
git push origin --delete <имя> 
```

### Переименование

```bash
# переименовать ТЕКУЩУЮ ветку
git branch -m <новое-имя> 

# переименовать конкретную ветку, не переключаясь на неё         
git branch -m <старое> <новое>     
```

## 3.2 Слияние веток — `merge`

```bash
# сначала переключаемся на ветку, КУДА хотим влить изменения
git checkout main   

# вливаем ветку feature/login в main       
git merge feature/login    
```

**Два основных сценария:**

**Fast-forward merge** — если в `main` не было новых коммитов с момента создания `feature/login`, Git просто "передвигает" указатель `main` вперёд, без создания отдельного merge-коммита.

**Three-way merge (с merge-коммитом)** — если в обеих ветках были отдельные изменения, Git создаёт специальный **merge-коммит** с двумя родителями, объединяющий историю обеих веток.

```bash
# ПРИНУДИТЕЛЬНО создать merge-коммит, даже если возможен fast-forward
git merge --no-ff feature/login   
# (часто используется в команде — сохраняет явную "точку слияния" в истории)
```

## 3.3 Перебазирование — `rebase`

```bash
git checkout feature/login

# переносим коммиты feature/login поверх последнего состояния main
git rebase main
```

**Отличие от merge:** `rebase` не создаёт merge-коммит — он **переписывает историю**, как будто твои коммиты изначально были сделаны поверх актуального `main`, история становится линейной, без "развилок".

```bash
git rebase -i HEAD~3   
# интерактивный rebase — позволяет объединить (squash),
# переписать сообщения, удалить или переставить местами
# последние 3 коммита
```

⚠️ **Важное правило:** никогда не делай `rebase` для веток, которые уже запушены и которые могут использовать другие люди — переписывание истории "ломает" её для всех, у кого уже есть старая версия этих коммитов (придётся делать `git push --force`, что может привести к потере чужих изменений).

**Когда что использовать:**

- `merge` — для слияния готовой feature-ветки в основную (сохраняет полную историю, безопасен для командной работы)
- `rebase` — для "причёсывания" **своей собственной**, ещё не запушенной (или запушенной только тобой) ветки, перед тем как предложить её к слиянию — для чистой, линейной истории

## 3.4 Разрешение конфликтов

Конфликт возникает, когда Git не может автоматически определить, какую версию строк оставить (обе ветки изменили одни и те же строки по-разному).

```bash
git merge feature/login
# CONFLICT (content): Merge conflict in file.js
```

Git помечает конфликтующие места прямо в файле:

```javascript
<<<<<<< HEAD
const price = 100;
=======
const price = 150;
>>>>>>> feature/login
```

**Шаги разрешения:**

1. Открыть файл, вручную выбрать/объединить нужную версию, убрать спецсимволы (`<<<<<<<`, `=======`, `>>>>>>>`)
2. `git add <файл>` — пометить конфликт как решённый
3. `git commit` (для merge) или `git rebase --continue` (для rebase) — завершить процесс

```bash
# полностью отменить слияние, вернуться к состоянию до начала merge
git merge --abort  

# аналогично для rebase
git rebase --abort     
```

# ЧАСТЬ 4. РАБОТА С УДАЛЁННЫМ РЕПОЗИТОРИЕМ

```bash
# показать список подключённых удалённых репозиториев
git remote -v                  

# подключить удалённый репозиторий под именем origin      
git remote add origin <url>          

# скачать изменения с сервера, БЕЗ слияния с текущей веткой
git fetch                      

# то же самое, явно указав remote      
git fetch origin                     

# fetch + merge ЗА ОДИН ШАГ (скачать и сразу влить)
git pull               

# fetch + rebase вместо merge (более чистая история)             
git pull --rebase   

# отправить локальные коммиты на сервер
git push              

# отправить конкретную ветку               
git push origin <ветка>              

# отправить И связать локальную ветку с удалённой (upstream) — после этого достаточно просто git push
git push -u origin <ветка>   

# ПЕРЕЗАПИСАТЬ историю на сервере (опасно — используется после rebase)        
git push --force      

# более безопасный force — откажет, если на сервере есть чужие изменения, о которых ты не знаешь               
git push --force-with-lease          
```

# ЧАСТЬ 5. ОТМЕНА И ВОССТАНОВЛЕНИЕ ИЗМЕНЕНИЙ

```bash
# отменить незакоммиченные изменения в файле (вернуть к последнему коммиту)
git restore <файл>   

# убрать файл из staging area (отменить git add), не трогая сами изменения
git restore --staged <файл>    

# отменить последний коммит, но оставить изменения в staging area
git reset --soft HEAD~1   

# отменить коммит И staging area, но оставить изменения в рабочей директории (по умолчанию)
git reset --mixed HEAD~1   

# ПОЛНОСТЬЮ отменить коммит и все изменения — опасно, теряются безвозвратно
git reset --hard HEAD~1       

# создать НОВЫЙ коммит, отменяющий изменения указанного коммита
# (безопасно для истории, которая уже опубликована — в отличие от reset)
git revert <хэш-коммита>             
```

**Ключевое различие `reset` vs `revert`:**

- `reset` — переписывает историю, двигает указатель ветки назад (опасно для публичной истории)
- `revert` — не трогает старые коммиты, а добавляет новый, который "отменяет" эффект старого (безопасно, сохраняет полную историю)

```bash
# временно "отложить" незакоммиченные изменения, вернуть чистую рабочую директорию
git stash           

# посмотреть список отложенных изменений         
git stash list 

# вернуть последний отложенный набор изменений и удалить его из списка stash  
git stash pop   

# вернуть изменения, но НЕ удалять их из списка stash              
git stash apply                

# удалить конкретный stash без применения
git stash drop                 
```

# ЧАСТЬ 7. КАК ПРАВИЛЬНО РАБОТАТЬ С GIT В КОМАНДЕ

## 7.1 Стратегии ветвления (branching strategies)

### Git Flow — классическая, "тяжёлая" модель

Строгая структура веток:

- `main`/`master` — только стабильные релизы
- `develop` — основная ветка разработки, куда сливаются фичи
- `feature/*` — отдельная ветка на каждую фичу, создаётся от `develop`
- `release/*` — подготовка к релизу (финальное тестирование, багфиксы)
- `hotfix/*` — срочные исправления прямо в продакшене, создаются от `main`

```bash
git checkout -b feature/user-auth develop
# ... работа над фичей ...
git checkout develop
git merge --no-ff feature/user-auth
```

Подходит для проектов с редкими, крупными релизами (например, десктопный софт с версиями).

### GitHub Flow — упрощённая модель (популярна сегодня)

Всего одна долгоживущая ветка (`main`), всё остальное — короткоживущие feature-ветки:

1. Создать ветку от `main` под конкретную задачу: `git checkout -b feature/login`
2. Делать коммиты, регулярно пушить
3. Открыть Pull Request для code review
4. После одобрения — слить в `main`
5. Удалить feature-ветку

Подходит для проектов с непрерывным деплоем (CI/CD), веб-сервисов, где релизы происходят часто (несколько раз в день/неделю).

### Trunk-Based Development

Ещё более радикальный подход: все разработчики коммитят напрямую в `main` (или очень короткоживущие ветки, живущие часы, не дни), с активным использованием feature flags (переключателей функциональности), чтобы незавершённый код не мешал остальным. Требует зрелой культуры тестирования и CI.

## 7.2 Соглашения по именованию веток

```
feature/short-description     — новая функциональность
bugfix/short-description       — исправление бага
hotfix/short-description       — срочное исправление в продакшене
release/1.2.0                  — подготовка релиза
chore/short-description        — рутинные задачи (обновление зависимостей и т.д.)
```

## 7.3 Соглашения по коммитам — Conventional Commits

Популярный стандарт формата сообщений коммитов, чтобы историю можно было легко читать и даже автоматически генерировать changelog:

```
feat: добавлена авторизация через Google
fix: исправлена ошибка расчёта скидки при пустой корзине
docs: обновлена документация по API
refactor: вынесена логика валидации в отдельный модуль
test: добавлены тесты для UserService
chore: обновлены зависимости
```

Формат: `<тип>(<опциональная область>): <краткое описание>`.

## 7.4 Pull Request / Code Review — типичный процесс

1. Создать ветку от актуального `main`
2. Сделать изменения, регулярно коммитить с понятными сообщениями
3. Запушить ветку: `git push -u origin feature/my-feature`
4. Открыть Pull Request на GitHub/GitLab с описанием, что и зачем сделано
5. Настроить автоматические проверки (CI) — линтер, тесты, сборка — должны пройти **до** ревью
6. Коллеги оставляют комментарии, запрашивают изменения (Request Changes) или одобряют (Approve)
7. После одобрения и прохождения всех проверок — слияние (Merge/Squash Merge/Rebase Merge, в зависимости от принятой в команде стратегии)
8. Удаление отработавшей feature-ветки

### Squash Merge — частый выбор для чистой истории `main`

При слиянии PR все коммиты фичи объединяются в **один** коммит в `main` — история основной ветки остаётся линейной и читаемой, даже если в самой feature-ветке было 20 "промежуточных" коммитов вроде `fix typo`, `wip`, `try again`.

## 7.5 Практические правила для командной работы

- **Никогда не коммитить напрямую в `main`/`develop`** — только через Pull Request с ревью.
- **Регулярно подтягивать актуальные изменения** (`git pull`/`git fetch` + `rebase`) в свою feature-ветку, чтобы избежать больших, болезненных конфликтов в конце.
- **Маленькие, частые коммиты с понятными сообщениями** — легче ревьюить, легче откатить конкретное изменение при необходимости (`git revert`).
- **`.gitignore`** — обязательно исключать файлы окружения, зависимости (`node_modules`), временные файлы, секреты (`.env`) из репозитория.
- **Не коммитить закомментированный "мёртвый" код и секреты** (пароли, API-ключи) — для секретов используются переменные окружения и специальные хранилища (Vault, Secrets Manager и т.д.).

# ЧАСТЬ 8. CI/CD

## 8.1 Общее определение

**CI/CD** — набор практик автоматизации процесса от написания кода до его развёртывания (деплоя) в продакшен.

- **CI (Continuous Integration, непрерывная интеграция)** — практика частого (несколько раз в день) слияния изменений в общую ветку, с автоматической проверкой (сборка, тесты, линтинг) при каждом изменении — чтобы обнаруживать проблемы как можно раньше, а не в конце большого цикла разработки.
- **CD (Continuous Delivery / Continuous Deployment, непрерывная доставка/развёртывание)**:
    - **Delivery** — код всегда находится в состоянии, готовом к развёртыванию, но финальный деплой в продакшен запускается **вручную**.
    - **Deployment** — деплой происходит **полностью автоматически**, как только код прошёл все проверки — без ручного вмешательства.

## 8.2 Зачем это нужно

- Раннее обнаружение багов (тесты запускаются автоматически при каждом изменении, а не раз в неделю вручную)
- Уверенность в качестве кода перед слиянием (PR не смержат, пока не пройдут проверки)
- Быстрая обратная связь для разработчика
- Уменьшение "ручной" рутины — не нужно вручную собирать, тестировать и разворачивать проект каждый раз

## 8.3 Типичный CI/CD-пайплайн для веб-проекта

```
1. Разработчик пушит код / открывает Pull Request
        ↓
2. CI автоматически запускает:
   - Установку зависимостей (npm install)
   - Линтер (проверка стиля кода, ESLint)
   - Юнит-тесты (Jest, Vitest и т.д.)
   - Сборку проекта (build)
   - Возможно — end-to-end тесты (Cypress, Playwright)
        ↓
1. Если что-то упало — PR блокируется, разработчик получает уведомление, должен исправить и запушить снова
        ↓
2. Если всё прошло успешно — PR можно смержить (часто требуется ещё и code review)
        ↓
3. После слияния в main — CD автоматически (или по кнопке) разворачивает новую версию на сервер (staging → потом production, либо сразу в production)
```

## 8.4 Пример конфигурации CI (GitHub Actions)

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4         # скачать код репозитория

      - name: Установить Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Установить зависимости
        run: npm install

      - name: Запустить линтер
        run: npm run lint

      - name: Запустить тесты
        run: npm test

      - name: Собрать проект
        run: npm run build
```

**Разбор:**

- `on:` — при каких событиях запускать пайплайн (пуш или PR в `main`)
- `jobs:` — набор задач, которые нужно выполнить (могут выполняться параллельно или последовательно)
- `steps:` — последовательные шаги внутри одной задачи
- Если хотя бы один шаг завершится с ошибкой — весь пайплайн помечается как "упавший", и (при правильной настройке) PR нельзя будет смержить

## 8.5 Стадии окружений (environments)

Типичная последовательность окружений, через которые проходит код перед попаданием к реальным пользователям:

```
Local (у разработчика) → CI (проверки) → Staging (тестовое, максимально похожее на прод) → Production (реальные пользователи)
```

**Staging** — важное промежуточное звено: позволяет протестировать изменения в условиях, близких к боевым, прежде чем показать их реальным пользователям.

## 8.6 Стратегии деплоя (кратко, для общего понимания)

- **Rolling deployment** — постепенная замена старых версий сервиса новыми, по одному серверу за раз, без простоя.
- **Blue-Green deployment** — два идентичных окружения ("синее" — текущее, "зелёное" — новое); трафик переключается на "зелёное" разом, при проблемах — мгновенный откат обратно на "синее".
- **Canary deployment** — новая версия сначала выкатывается на небольшой процент пользователей, и только при отсутствии проблем — постепенно на всех.

## 8.7 Как это связано с Git-практиками из предыдущей части

CI/CD особенно хорошо сочетается с моделью **GitHub Flow** (короткоживущие ветки, частые PR) — именно частая интеграция небольших изменений и есть суть "Continuous Integration". При Git Flow с редкими крупными релизами CI тоже применяется, но реже задействуется полноценный Continuous **Deployment** (обычно ограничиваются Continuous Delivery, с ручным решением о релизе).
