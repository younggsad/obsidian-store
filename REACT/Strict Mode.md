## 💡 Определение

**`<StrictMode>`** — это служебный компонент-обёртка, который не рендерит собственный DOM-узел, а включает набор дополнительных проверок и предупреждений **только в режиме разработки (development)**, помогая заранее выявить потенциально небезопасный код до того, как он проявится в проде в виде трудноуловимого бага.

> [!info] Формулировка для собеседования 
> "StrictMode — это инструмент статической диагностики на этапе разработки: он не добавляет новый функционал в приложение, а намеренно делает побочные эффекты небезопасного кода видимыми раньше, за счёт двойного вызова определённых функций. В production-сборке все дополнительные проверки StrictMode полностью отключены и не влияют на производительность или поведение приложения."

## 🏗️ Синтаксис

```jsx
import { StrictMode } from 'react';

root.render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

Может оборачивать как всё приложение, так и отдельное поддерево — проверки применяются только к обёрнутой части дерева.

## 🔬 Что именно проверяет и делает StrictMode

### 1. Двойной вызов функций компонентов и некоторых хуков (React 18+)

В dev-режиме React намеренно вызывает **дважды**:

- тело функционального компонента (render-фазу)
- функции, переданные в `useState`, `useMemo`, `useReducer` (initializer-функции)
- эффекты: `useEffect`/`useLayoutEffect` — монтирует, сразу размонтирует, и монтирует снова

```jsx
useEffect(() => {
  console.log('Подписка создана');
  const subscription = subscribeToStore();

  return () => {
    console.log('Подписка отменена');
    subscription.unsubscribe();
  };
}, []);

// В dev-режиме под StrictMode консоль выведет:
// "Подписка создана"
// "Подписка отменена"
// "Подписка создана"
```

> [!info] Цель этого поведения 
> Такой двойной цикл монтирование → размонтирование → монтирование эмулирует ситуацию, в которой компонент **переиспользует своё состояние** после временного размонтирования — сценарий, важный для будущей возможности React сохранять state скрытых частей UI (offscreen rendering). Если эффект не содержит корректной функции очистки (cleanup) или полагается на то, что выполнится **строго один раз за всё время жизни приложения**, повторный вызов сразу обнажит эту проблему в dev-режиме, а не спустя месяцы в проде.

> [!warning] Частое заблуждение 
> Двойной вызов **не означает**, что компонент рендерится дважды в production. Это исключительно dev-механизм диагностики. В production-сборке (`NODE_ENV=production`) двойных вызовов нет.

### 2. Выявление небезопасных побочных эффектов в render-фазе

React ожидает, что тело компонента (render) — **чистая функция**: без мутации внешних переменных, без побочных запросов, без работы с DOM напрямую. Двойной вызов функции компонента в dev-режиме помогает выявить такие нарушения — если побочный эффект (например, инкремент внешнего счётчика) выполняется прямо в теле компонента, он выполнится дважды, что сделает баг заметным сразу.

```jsx
let renderCount = 0; // антипаттерн: мутация внешней переменной в render

function Component() {
  renderCount++; // будет увеличиваться на 2 при каждом рендере в dev под StrictMode
  return <div>{renderCount}</div>;
}
```

### 3. Предупреждение об устаревших (legacy) API

StrictMode выводит warning при использовании:

- **Legacy String Refs** (`ref="myRef"` вместо callback-рефов или `useRef`)
- **Legacy Context API** (`contextTypes`, `getChildContext`)
- **`findDOMNode()`** — устаревший императивный способ доступа к DOM-узлу
- Неопознанных побочных эффектов при использовании устаревших методов жизненного цикла классовых компонентов (`componentWillMount`, `componentWillReceiveProps`, `componentWillUpdate` без префикса `UNSAFE_`)

### 4. Проверка совместимости со Concurrent-фичами

StrictMode помогает выявить компоненты, которые не готовы к работе в конкурентном режиме рендеринга (Concurrent Rendering) — например, если компонент полагается на строго последовательный, ровно однократный вызов рендера без прерываний.

## 🆚 StrictMode: dev vs production

|Аспект|Development|Production|
|---|---|---|
|Двойной вызов render/эффектов|да|нет|
|Warning об устаревших API|да|нет|
|Влияние на производительность|дополнительные вызовы (только dev)|нулевое — StrictMode полностью не активен|
|Наличие в итоговом бандле|код диагностики удаляется|—|

> [!tip] Практический вывод 
> Совершенно нормально и ожидаемо, что в dev-режиме под StrictMode видно "лишние" вызовы `console.log` внутри эффектов или конструкторов — это не баг React и не повод убирать StrictMode, а сигнал, что стоит убедиться в идемпотентности эффекта и корректности функции очистки.

## ⚠️ Частые вопросы на собеседовании

> [!example] "Почему после добавления StrictMode эффект стал вызываться дважды — это баг?" 
> Нет, это ожидаемое поведение React 18+ в dev-режиме, введённое для заблаговременного выявления эффектов, не имеющих корректной функции очистки или не готовых к повторному монтированию. В production такого удвоения не происходит.

> [!example] "Меняет ли StrictMode поведение приложения в production?" 
> Нет — все проверки и двойные вызовы, вводимые StrictMode, активны исключительно в dev-сборке. В production-бандле соответствующий код не выполняется, StrictMode не оказывает влияния ни на производительность, ни на функциональность.

> [!example] "Как правильно исправить эффект, который ломается при двойном вызове под StrictMode?" 
> Убедиться, что эффект возвращает корректную функцию очистки, полностью откатывающую то, что было сделано при монтировании (отписка от подписки, отмена таймера, закрытие соединения), и что повторное выполнение эффекта после cleanup приводит систему в то же валидное состояние — то есть эффект должен быть идемпотентным относительно цикла "монтирование → размонтирование → монтирование".
