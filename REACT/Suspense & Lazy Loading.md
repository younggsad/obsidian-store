## 💡 Определение

**Suspense** — это механизм React, позволяющий компоненту декларативно "приостановить" рендер до тех пор, пока не будет готов необходимый ему асинхронный ресурс (код компонента, данные), и показать fallback-интерфейс на время ожидания — без ручного управления состояниями `isLoading` в каждом компоненте по отдельности.

**`React.lazy`** — функция, позволяющая объявить компонент, код которого физически загружается **по требованию** (через динамический `import()`), а не включается в основной бандл при первой загрузке страницы. `React.lazy` — один из немногих встроенных источников, умеющих "приостанавливать" рендер, который `Suspense` умеет перехватывать.

> [!info] Формулировка для собеседования 
> "Suspense инвертирует привычную модель обработки асинхронности: вместо того чтобы компонент сам отслеживал состояние загрузки через `useState`/`isLoading` и условно рендерил спиннер, компонент 'бросает' (throws) промис во время рендера, а ближайший родительский `<Suspense>` перехватывает этот промис и показывает fallback до его разрешения. Это концептуально похоже на Error Boundary, только вместо перехвата ошибок перехватывается состояние 'ещё не готово'."

## 🏗️ React.lazy + Suspense: код-сплиттинг

```jsx
import { lazy, Suspense } from 'react';

const HeavyChart = lazy(() => import('./HeavyChart'));

function Dashboard() {
  return (
    <Suspense fallback={<Spinner />}>
      <HeavyChart />
    </Suspense>
  );
}
```

Что происходит технически:

1. При первом рендере `Dashboard` React обнаруживает, что `HeavyChart` — lazy-компонент, код которого ещё не загружен
2. Динамический `import('./HeavyChart')` инициирует загрузку отдельного JS-чанка (браузер делает сетевой запрос за файлом)
3. Пока промис загрузки не разрешён, React рендерит `fallback` из ближайшего родительского `<Suspense>`
4. После загрузки чанка React автоматически перерендеривает поддерево, теперь уже с реальным `HeavyChart`

> [!info] Связь с код-сплиттингом 
> Это основной встроенный механизм **code splitting** в React без привязки к конкретному бандлеру (Webpack, Vite, и т.д. — все они поддерживают синтаксис динамического `import()` на уровне сборки). Практический эффект — уменьшение размера начального JS-бандла и более быстрая первая отрисовка (First Contentful Paint), за счёт переноса загрузки редко используемого либо "тяжёлого" кода (графики, редакторы, модалки) на момент, когда он реально понадобится.

## 🔬 Как Suspense перехватывает "незавершённость" — throw promise

Механизм, лежащий в основе Suspense, — компонент (или, в случае `lazy`, сам React) **выбрасывает промис** во время рендера вместо выброса ошибки:

```jsx
// Упрощённая иллюстрация внутреннего механизма (не то, как пишут в прикладном коде)
function readData(promise) {
  if (promise.status === 'fulfilled') return promise.value;
  if (promise.status === 'rejected') throw promise.reason;
  throw promise; // React перехватывает именно это выброшенное значение
}
```

React, встретив выброшенный промис во время рендера, приостанавливает рендеринг данного поддерева, находит ближайший родительский `<Suspense>` и рендерит его `fallback`. Когда промис разрешается, React инициирует повторный рендер поддерева.

> [!warning] Почему нельзя просто использовать это с любым `useEffect`-подходом 
> Классический паттерн "`fetch` в `useEffect` + `useState(isLoading)`" **не интегрируется** с Suspense напрямую — Suspense требует, чтобы источник данных сам был совместим с этим механизмом "выброса промиса" (так называемый "Suspense-совместимый" источник данных). Именно поэтому data fetching через Suspense на практике реализуется либо через специализированные библиотеки (React Query с суспенс-режимом, Relay), либо через `use()` в React 19 (см. [[Встроенные React Hooks]]), а не написанием "обычного" `useEffect` вручную.

## 🌳 Гранулярность и вложенность Suspense-границ

Аналогично Error Boundary (см. [[Error Boundaries]]), `<Suspense>` можно и нужно располагать на разных уровнях дерева в зависимости от требуемой детализации состояний загрузки:

```jsx
function ProfilePage() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <ProfileHeader />
      <Suspense fallback={<PostsSkeleton />}>
        <ProfilePosts />
      </Suspense>
    </Suspense>
  );
}
```

Здесь `ProfileHeader` и `ProfilePosts` могут загружаться независимо: пока `ProfilePosts` ещё не готов, `ProfileHeader` уже отображается, а на месте постов показывается собственный, более узкий fallback — вместо блокировки всей страницы одним общим спиннером.

> [!info] Приоритет ближайшей границы 
> Если у компонента, выбросившего промис, есть несколько `<Suspense>` выше по дереву — сработает **ближайшая** родительская граница, аналогично тому, как работает всплытие к ближайшему Error Boundary.

## 🆚 Suspense vs классический подход с isLoading

|Критерий|`useState(isLoading)` вручную|Suspense|
|---|---|---|
|Место логики "загрузки"|размазана по каждому компоненту|централизована на уровне границы `<Suspense>`|
|Вложенные независимые загрузки|требует ручной координации нескольких флагов|естественная вложенность границ|
|Совместимость с кодом "из коробки"|работает с любым `fetch`/`useEffect`|требует Suspense-совместимого источника данных|
|Интеграция с код-сплиттингом|отдельная логика (например, `React.lazy` без Suspense невозможен)|встроена нативно|

## ⚠️ Частые ошибки

> [!danger] Отсутствие Suspense вокруг lazy-компонента 
> `React.lazy` **обязательно** требует родительский `<Suspense>` где-то выше по дереву — без него React выбросит ошибку в момент, когда встретит незагруженный lazy-компонент, поскольку "приостановленный" рендер некому перехватить.

> [!tip] Suspense не заменяет Error Boundary 
> Если загрузка чанка (или данных) завершается **ошибкой** (например, сетевой сбой), `<Suspense>` эту ошибку не перехватывает — для этого нужен отдельный [[Error Boundaries|Error Boundary]] выше по дереву. На практике `Suspense` и `ErrorBoundary` почти всегда комбинируют вместе:

```jsx
<ErrorBoundary fallback={<ErrorMessage />}>
  <Suspense fallback={<Spinner />}>
    <HeavyChart />
  </Suspense>
</ErrorBoundary>
```

## ⚠️ Частые вопросы на собеседовании

> [!example] "Что происходит внутри React, когда компонент 'приостанавливается' под Suspense?" 
> Компонент (или сам механизм `lazy`) выбрасывает промис во время рендер-фазы вместо возврата JSX. React перехватывает это выброшенное значение аналогично тому, как Error Boundary перехватывает ошибку, находит ближайшую родительскую Suspense-границу и рендерит её `fallback`, пока промис не разрешится, после чего инициирует повторный рендер поддерева.

> [!example] "Можно ли использовать Suspense с обычным fetch в useEffect?" 
> Не напрямую — обычный `fetch` внутри `useEffect` не выбрасывает промис во время рендера, поэтому Suspense не может его перехватить. Для интеграции с Suspense нужен источник данных, явно поддерживающий этот контракт (специализированные библиотеки данных, либо хук `use()` в React 19).

> [!example] "Зачем нужна вложенность нескольких границ Suspense вместо одной общей?" 
> Одна общая граница на всё приложение блокирует отображение **всей** страницы, пока не готов самый медленный ресурс — даже если остальной контент давно готов. Вложенные границы позволяют показывать уже готовые части интерфейса немедленно, откладывая fallback только для тех частей, что реально ещё загружаются — это называется паттерном "progressively revealing content".
