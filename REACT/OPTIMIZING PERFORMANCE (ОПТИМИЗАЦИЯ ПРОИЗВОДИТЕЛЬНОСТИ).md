# ЧАСТЬ 6. OPTIMIZING PERFORMANCE (ОПТИМИЗАЦИЯ ПРОИЗВОДИТЕЛЬНОСТИ)

## 6.1 Общий принцип — сначала измерить, потом оптимизировать

>**React DevTools Profiler** — встроенный инструмент для записи и визуализации того, какие компоненты рендерились, сколько это заняло времени, и почему (какая причина вызвала рендер). Оптимизация "вслепую", без профилирования — частая ошибка, приводящая к усложнению кода без реального выигрыша.

## 6.2 `React.memo` — предотвращение лишнего рендера компонента

```jsx
const ExpensiveComponent = React.memo(function ExpensiveComponent({ data }) {
  console.log("Рендерюсь");
  return <div>{data}</div>;
});
```

`React.memo` оборачивает компонент так, что React **пропускает** повторный рендер, если `props` не изменились (по умолчанию — поверхностное сравнение, shallow comparison, каждого пропа). Полезен для компонентов, которые часто получают **одни и те же** пропсы от родителя, перерендеривающегося по другим причинам.

⚠️ **Ловушка:** если среди пропсов передаётся объект/массив/функция, создаваемые заново на каждом рендере родителя (как в примере с Context выше) — поверхностное сравнение всегда будет находить "различие" (новая ссылка), и `React.memo` не даст никакого эффекта, пока эти пропсы тоже не мемоизированы через `useMemo`/`useCallback`.

## 6.3 `useMemo`/`useCallback` — разобрали в Части 5, здесь — про их роль именно в оптимизации

**Важное предостережение:** `useMemo`/`useCallback` — **не бесплатны**. Сама мемоизация тоже требует памяти (хранение предыдущих значений/зависимостей) и вычислительных затрат на сравнение зависимостей при каждом рендере. Использовать их **везде подряд** "на всякий случай" (что прямо нарушает принцип YAGNI, который разбирали ранее) может даже **замедлить** приложение, а не ускорить — они оправданы конкретно там, где: 1) вычисление реально тяжёлое, или 2) нужна именно ссылочная стабильность для дочернего `React.memo`/зависимостей других хуков.

## 6.4 Виртуализация списков (windowing)

Для очень длинных списков (тысячи элементов) рендер **всех** DOM-узлов сразу — дорогая операция, даже если пользователь видит на экране только 10-20 элементов одновременно. **Виртуализация** — рендеринг только тех элементов, которые реально попадают в видимую область (viewport), с "подменой" остальных пустым пространством нужной высоты.

```jsx
import { FixedSizeList } from 'react-window';

function BigList({ items }) {
  return (
    <FixedSizeList height={600} itemCount={items.length} itemSize={35} width="100%">
      {({ index, style }) => <div style={style}>{items[index].name}</div>}
    </FixedSizeList>
  );
}
```

Библиотеки: `react-window`, `react-virtualized`, `@tanstack/react-virtual`.

## 6.5 Ленивая загрузка компонентов — `React.lazy` + `Suspense`

```jsx
import { lazy, Suspense } from 'react';

const HeavyChart = lazy(() => import('./HeavyChart')); // код-сплиттинг — отдельный бандл, грузится по требованию

function Dashboard() {
  return (
    <Suspense fallback={<Spinner />}>
      <HeavyChart />
    </Suspense>
  );
}
```

Компонент (и весь его "тяжёлый" код, например, библиотека графиков) загружается только тогда, когда он реально нужен на экране, а не входит в основной bundle сразу — уменьшает первоначальное время загрузки приложения (Time to Interactive).

## 6.6 Правильное разбиение состояния (state colocation)

```jsx
// ❌ Плохо — состояние поля ввода живёт в самом верху,
// каждое нажатие клавиши перерендеривает ВЕСЬ большой App
function App() {
  const [searchText, setSearchText] = useState("");
  return (
    <div>
      <SearchInput value={searchText} onChange={setSearchText} />
      <HugeUnrelatedContent /> {/* тоже перерендеривается зря */}
    </div>
  );
}

// ✅ Лучше — состояние живёт максимально близко к тому, кто его реально использует
function App() {
  return (
    <div>
      <SearchBox /> {/* useState внутри самого SearchBox */}
      <HugeUnrelatedContent /> {/* не затрагивается вообще */}
    </div>
  );
}
```

Принцип "state colocation" — держать состояние на максимально низком, локальном уровне дерева компонентов, поднимая его выше только когда это реально необходимо для совместного использования несколькими компонентами (принцип "lifting state up" в обратную сторону — не поднимай состояние выше, чем нужно).
