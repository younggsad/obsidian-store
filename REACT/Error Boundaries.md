## 💡 Определение

**Error Boundary** — это React-компонент, который перехватывает JavaScript-ошибки, возникшие **при рендеринге**, **в методах жизненного цикла** и **в конструкторах** компонентов, находящихся ниже него по дереву, логирует их и отображает fallback-интерфейс вместо аварийно упавшего дерева компонентов.

Механизм появился в React 16 как замена прежнему поведению, при котором необработанная ошибка в рендере приводила к полному размонтированию всего приложения.

> [!info] Формулировка для собеседования 
> "Error Boundary — это компонент, реализующий один из двух специальных методов жизненного цикла — `static getDerivedStateFromError()` или `componentDidCatch()` — который перехватывает ошибки в поддереве и позволяет отрендерить fallback UI вместо падения всего приложения."

## 🏗️ Реализация

Error Boundary может быть реализован **только как классовый компонент** — на момент актуальной версии React эквивалента через хуки не существует.

```jsx
class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError(error) {
    // Вызывается во время рендера — используется для обновления state,
    // чтобы следующий рендер показал fallback UI
    return { hasError: true };
  }

  componentDidCatch(error, errorInfo) {
    // Вызывается после рендера — используется для побочных эффектов:
    // логирование в Sentry, отправка на сервер и т.д.
    logErrorToService(error, errorInfo.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <FallbackUI />;
    }
    return this.props.children;
  }
}
```

Использование:

```jsx
<ErrorBoundary>
  <ProfilePage />
</ErrorBoundary>
```

> [!tip] Разделение ответственности между методами 
> `getDerivedStateFromError` — чистая функция, отвечает **только** за обновление state для рендера fallback UI, без побочных эффектов. 
> `componentDidCatch` — отвечает за побочные эффекты (логирование), не должен использоваться для обновления UI.

## 🚫 Что Error Boundary НЕ перехватывает

Это один из наиболее часто проверяемых на собеседовании нюансов. Error Boundary **не ловит**:

1. **Ошибки в обработчиках событий** (`onClick`, `onChange` и т.д.) — эти ошибки не связаны с рендерингом, для них применим обычный `try/catch`
2. **Ошибки в асинхронном коде** — `setTimeout`, `requestAnimationFrame`, промисы, `async/await` вне рендера
3. **Ошибки при серверном рендеринге (SSR)**
4. **Ошибки в самом Error Boundary** — компонент не может поймать собственную ошибку; для этого нужен родительский Error Boundary выше по дереву

> [!example] "Почему обработчики событий не перехватываются Error Boundary?" 
> Обработчики событий не участвуют в процессе рендеринга React — они выполняются вне цикла рендера, обычно в ответ на действия пользователя. Ошибка в них не оставляет дерево компонентов в неконсистентном состоянии, поэтому механизм, спроектированный для защиты целостности рендера, здесь не требуется — достаточно обычного `try/catch`.

## 🌳 Гранулярность и позиционирование в дереве

Error Boundary можно и нужно располагать на разных уровнях приложения в зависимости от требуемой изоляции сбоев:

- **На верхнем уровне** — одна общая граница вокруг всего приложения, чтобы избежать полного "белого экрана"
- **Вокруг отдельных виджетов/секций** — чтобы падение одного виджета (например, блока рекомендаций) не разрушало остальную страницу

```jsx
function Dashboard() {
  return (
    <>
      <ErrorBoundary fallback={<WidgetError />}>
        <StatsWidget />
      </ErrorBoundary>
      <ErrorBoundary fallback={<WidgetError />}>
        <RecommendationsWidget />
      </ErrorBoundary>
    </>
  );
}
```

Каждая граница действует независимо — падение внутри `RecommendationsWidget` не затронет `StatsWidget`.

## 🔬 Почему нет хука-аналога

Часто задаваемый на собеседовании вопрос. Формальная причина: концептуально `getDerivedStateFromError` и `componentDidCatch` семантически завязаны на жизненный цикл класса и обработку ошибок именно **во время commit/render фазы**. Явного хук-API (`useErrorBoundary` или аналога) команда React официально не представила; библиотека `react-error-boundary` реализует обёртку поверх классового компонента, предоставляя удобный декларативный интерфейс, но не заменяет базовый механизм.

> [!info] Практический вывод 
> На практике Error Boundary почти всегда либо пишется один раз как классовый компонент-обёртка и переиспользуется, либо берётся готовым из библиотеки `react-error-boundary` — писать его вручную под каждый проект нет необходимости.

## 🆚 Сравнение с try/catch

|Критерий|try/catch|Error Boundary|
|---|---|---|
|Область действия|конкретный блок кода|поддерево компонентов|
|Перехватывает ошибки рендера|нет|да|
|Перехватывает ошибки в обработчиках событий|да|нет|
|Декларативность|императивный|декларативный (JSX-обёртка)|

## ⚠️ Частые вопросы на собеседовании

> [!example] "Что произойдёт, если ошибка возникла внутри Error Boundary, а не в его children?" 
> Сам Error Boundary не может перехватить собственную ошибку — она "всплывёт" к ближайшему **родительскому** Error Boundary. Если такового нет, всё дерево размонтируется, как и до появления этого механизма.

> [!example] "Чем отличается getDerivedStateFromError от componentDidCatch по времени вызова?" 
> `getDerivedStateFromError` вызывается на фазе рендера (render phase), до коммита изменений в DOM — здесь недопустимы побочные эффекты. `componentDidCatch` вызывается на фазе коммита (commit phase), после того как fallback UI уже применён — здесь безопасно выполнять побочные эффекты вроде сетевого запроса для логирования.
