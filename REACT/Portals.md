## 💡 Определение

**Portal** — это механизм, позволяющий отрендерить дочерние React-элементы в DOM-узел, находящийся **за пределами иерархии родительского DOM-контейнера**, при этом сохраняя компонент на своём месте в **дереве React-компонентов**.

Формально: Portal разрывает связь между иерархией React-компонентов и физической иерархией DOM-узлов, оставляя первую нетронутой.

> [!info] Формулировка для собеседования 
> "createPortal позволяет отрендерить поддерево в произвольный DOM-узел вне родительского контейнера, при этом с точки зрения React-дерева (контекст, порядок событий, реконсиляция) компонент остаётся дочерним по отношению к месту вызова — меняется только физическое расположение в DOM."

## 🏗️ Синтаксис

```jsx
import { createPortal } from 'react-dom';

function Modal({ children }) {
  return createPortal(
    <div className="modal-overlay">{children}</div>,
    document.getElementById('modal-root')
  );
}
```

Требуется отдельный DOM-узел за пределами основного `#root`, заранее объявленный в HTML:

```html
<body>
  <div id="root"></div>
  <div id="modal-root"></div>
</body>
```

## 🎯 Зачем это нужно

Основная мотивация — визуальные компоненты, для которых важно **физическое расположение в DOM**, но логически они принадлежат глубоко вложенному компоненту:

- **Модальные окна** — должны рендериться поверх всего интерфейса, без влияния родительских `overflow: hidden`, `z-index`, `position: relative`
- **Тултипы и поповеры** — то же ограничение по позиционированию
- **Дропдауны и меню** — во избежание обрезания контейнером с `overflow: hidden`

> [!example] "Почему нельзя просто использовать `position: fixed` без Portal?" 
> `position: fixed` не решает проблему, если у любого предка в цепочке задан `transform`, `filter`, `perspective` или `will-change` — эти свойства создают новый **containing block**, и `fixed`-элемент позиционируется уже относительно него, а не относительно viewport. Portal физически выносит DOM-узел из этой иерархии, устраняя проблему на корню, а не полагаясь на CSS-хаки.

## 🔬 Что сохраняется, а что нет

Ключевой момент для собеседования — Portal влияет **только на физическое дерево DOM**, но не на архитектуру React:

|Аспект|Сохраняется как в обычном дереве|Комментарий|
|---|---|---|
|Иерархия React-компонентов|✅ да|Portal — обычный дочерний компонент в дереве React|
|React Context|✅ да|Providers выше по дереву React доступны внутри портала|
|Всплытие событий (event bubbling)|✅ да|событие всплывает по React-дереву, а не по DOM-дереву|
|Физическое положение в DOM|❌ нет|элемент рендерится в указанный узел, вне обычной иерархии|
|CSS-наследование от родителя|❌ нет|стили не наследуются из физического родителя в DOM|

> [!info] Всплытие событий через Portal — частый вопрос 
> Если внутри портала кликнуть по элементу, а у логического родителя (по React-дереву, не по DOM) навешан `onClick`, обработчик **сработает**, несмотря на то что физически в DOM элементы находятся в разных поддеревьях. Это прямое следствие того, что React реализует делегирование событий и всплытие поверх собственного (виртуального) дерева, а не поверх реального DOM (см. [[Synthetic Events]]).

## ⚠️ Частые ошибки и нюансы

> [!danger] Забытый DOM-узел назначения 
> Если целевой элемент (`document.getElementById('modal-root')`) отсутствует в момент вызова `createPortal`, произойдёт ошибка времени выполнения. Узел должен существовать в DOM до рендера портала — обычно его добавляют статически в `index.html`, либо создают динамически через `document.createElement` в `useEffect` при монтировании.

> [!tip] Портал и accessibility 
> Portal решает только визуальное позиционирование, но не решает автоматически проблемы доступности — управление фокусом (focus trap), `aria-modal`, возврат фокуса при закрытии модалки — всё это должно быть реализовано отдельно, Portal сам по себе этим не занимается.

## 🆚 Portal vs обычный рендер

|Критерий|Обычный рендер|Portal|
|---|---|---|
|Место в DOM|внутри родительского контейнера|произвольный DOM-узел|
|Место в дереве React|как обычно|как обычно, без изменений|
|Контекст (Context API)|доступен|доступен|
|Всплытие событий|по DOM = по React-дереву|по React-дереву, не по DOM|
|Типичное применение|обычные компоненты|модалки, тултипы, дропдауны|

## ⚠️ Частые вопросы на собеседовании

> [!example] "Может ли компонент внутри Portal получить доступ к Context, объявленному выше по дереву в точке вызова?" 
> Да — Context не зависит от физического расположения в DOM, он передаётся по дереву React-компонентов, а Portal не разрывает это дерево, только DOM-структуру.

> [!example] "Как обработать клик вне модального окна (click outside), реализованного через Portal?" 
> Поскольку всплытие событий идёт по React-дереву, обработчик `onClick` на overlay-контейнере сработает штатно при клике по фону модалки, несмотря на физическое разделение в DOM — специальных обходных решений для самого факта всплытия не требуется. Однако стоит учитывать `event.stopPropagation()` внутри содержимого модалки, чтобы клик по контенту не считался кликом по overlay.
