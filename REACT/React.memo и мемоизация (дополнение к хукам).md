## 🧠 React.memo

**`React.memo`** — это HOC (Higher-Order Component), а не хук: он оборачивает компонент и предотвращает его повторный рендер, если пропсы **поверхностно (shallow)** не изменились относительно предыдущего рендера.

```jsx
const ExpensiveChild = React.memo(function ExpensiveChild({ data, onSelect }) {
  console.log('Рендер ExpensiveChild');
  return <div onClick={onSelect}>{data.name}</div>;
});
```

По умолчанию сравнение пропсов происходит через `Object.is` для каждого ключа — то есть это **shallow comparison**, а не глубокое сравнение объектов. Можно передать собственную функцию сравнения вторым аргументом:

```jsx
const Component = React.memo(MyComponent, (prevProps, nextProps) => {
  // return true, если рендер НЕ нужен (пропсы "равны" с точки зрения компонента)
  return prevProps.id === nextProps.id;
});
```

> [!warning] Почему React.memo часто "не работает" 
> Самая частая причина, по которой `React.memo` не даёт эффекта на собеседовании спрашивают в первую очередь: если родитель на каждом рендере передаёт **новый объект, массив или функцию** как проп (например, инлайн-объект `style={{color: 'red'}}` или необёрнутый в `useCallback` обработчик), то с точки зрения `Object.is` это всегда "новое" значение — shallow comparison не спасёт, и дочерний компонент перерендерится, несмотря на `React.memo`. Именно поэтому `React.memo` на дочернем компоненте практически всегда должен идти в паре с `useCallback`/`useMemo` на пропсах, которые ему передаются из родителя.

## 🔗 Связка React.memo + useCallback + useMemo

Это триада, которую почти всегда спрашивают вместе — важно чётко разделять, что каждый из трёх инструментов **кэширует**:

|Инструмент|Что кэширует|Уровень применения|
|---|---|---|
|`useMemo`|результат **вычисления** (значение)|внутри компонента|
|`useCallback`|**ссылку на функцию** (по сути частный случай useMemo)|внутри компонента|
|`React.memo`|**сам рендер компонента** целиком|оборачивает компонент снаружи|

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  const [text, setText] = useState('');

  // Без useCallback handleSelect был бы новой функцией на каждом рендере Parent,
  // и React.memo на Child не спас бы от лишнего рендера
  const handleSelect = useCallback((id) => {
    console.log('selected', id);
  }, []);

  const data = useMemo(() => ({ id: count }), [count]);

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <Child data={data} onSelect={handleSelect} />
    </>
  );
}

const Child = React.memo(function Child({ data, onSelect }) {
  return <button onClick={() => onSelect(data.id)}>{data.id}</button>;
});
```

Здесь ввод текста в `input` меняет `text` и вызывает ре-рендер `Parent`, но `Child` **не перерендерится**, потому что и `data`, и `handleSelect` сохраняют стабильные ссылки между рендерами благодаря `useMemo`/`useCallback`, а `React.memo` видит "одинаковые" пропсы.

## ⚠️ Когда мемоизация вредна (частый "продвинутый" вопрос)

> [!danger] Мемоизация — не бесплатна 
> `useMemo`/`useCallback` сами по себе имеют цену: React должен хранить предыдущие зависимости и предыдущий результат в памяти и сравнивать массив зависимостей на каждом рендере. Для дешёвых вычислений (простое сложение, форматирование короткой строки) накладные расходы на саму мемоизацию могут быть **выше**, чем стоимость просто пересчитать значение заново. Правило: мемоизировать стоит либо действительно затратные вычисления (сортировка/фильтрация больших массивов, сложная агрегация), либо когда важна именно **ссылочная стабильность** значения (проп для `React.memo`-компонента, зависимость другого хука, значение для Context Provider — см. [[Context]]), а не сам факт "пересчёта".

> [!example] "Стоит ли оборачивать вообще все функции в useCallback по умолчанию?" 
> Нет — это частая ошибка "premature optimization". `useCallback` оправдан, когда функция передаётся мемоизированному дочернему компоненту, используется как зависимость другого хука (`useEffect`, `useMemo`), либо участвует в сравнении в кастомной `areEqual`-функции `React.memo`. Во всех остальных случаях оборачивание добавляет сложность кода без измеримой выгоды.

## 🎛️ useImperativeHandle

Позволяет **кастомизировать** значение, которое родительский компонент получает через `ref`, когда используется `forwardRef` — то есть скрыть часть внутреннего DOM/API компонента и явно решить, какой именно "императивный" интерфейс наружу предоставить.

```jsx
const FancyInput = forwardRef(function FancyInput(props, ref) {
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() {
      inputRef.current.focus();
    },
    clear() {
      inputRef.current.value = '';
    },
    // намеренно НЕ отдаём наружу весь DOM-узел целиком
  }));

  return <input ref={inputRef} {...props} />;
});
```

```jsx
function Parent() {
  const fancyInputRef = useRef(null);
  return (
    <>
      <FancyInput ref={fancyInputRef} />
      <button onClick={() => fancyInputRef.current.focus()}>Фокус</button>
    </>
  );
}
```

> [!info] Формулировка для собеседования 
> "`useImperativeHandle` реализует принцип инкапсуляции для рефов: вместо того чтобы отдавать родителю сырой DOM-узел (что размывает границу ответственности между родителем и дочерним компонентом), компонент явно определяет ограниченный набор методов, которые допустимо вызывать императивно снаружи."

Используется редко — в основном в переиспользуемых UI-библиотечных компонентах (кастомный инпут, модалка с методами `open()`/`close()`), не в обычном прикладном коде.

## 🐛 useDebugValue

Хук, который **не влияет на поведение приложения**, а лишь добавляет читаемую метку для custom hook в панели **React DevTools**, помогая отлаживать сложную композицию хуков.

```jsx
function useOnlineStatus() {
  const isOnline = useSyncExternalStore(subscribe, getSnapshot);

  useDebugValue(isOnline ? 'Online' : 'Offline'); // видно в DevTools рядом с хуком

  return isOnline;
}
```

Опциональный второй аргумент — функция форматирования, вызывается только при реальном открытии DevTools (чтобы не тратить ресурсы на форматирование, если его никто не смотрит):

```jsx
useDebugValue(date, (d) => d.toDateString());
```

## ⏱️ Дополнительный нюанс к useEffect: automatic batching (React 18)

> [!info] Про что часто забывают упомянуть, разбирая useState/useEffect 
> Начиная с React 18, React группирует (batching) несколько вызовов `setState`, произошедших в рамках одного события, в **один** ре-рендер — причём теперь это работает не только внутри React-обработчиков событий (как было раньше), но и внутри промисов, `setTimeout`, нативных event listeners.

```jsx
function handleClick() {
  setTimeout(() => {
    setCount(c => c + 1); // до React 18: вызвал бы отдельный ре-рендер
    setFlag(f => !f);     // до React 18: вызвал бы ещё один отдельный ре-рендер
    // React 18: оба обновления объединяются в один ре-рендер
  }, 1000);
}
```

Это напрямую связано с тем, зачем вообще нужна функциональная форма `setCount(prev => ...)`, которая уже отмечена в основном конспекте — при батчинге нескольких обновлений подряд именно функциональная форма гарантирует работу с актуальным, а не устаревшим значением.
