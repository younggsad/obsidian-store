## 💡 Контекст

React как библиотека **не предоставляет встроенного решения** для получения данных с сервера — это намеренное архитектурное решение: React отвечает за рендеринг UI, а не за сетевой слой. Однако наивная реализация загрузки данных через `useEffect` + `useState` регулярно приводит к одному и тому же набору проблем, ради решения которых и появились специализированные библиотеки (React Query, SWR, RTK Query).

## 🏗️ Наивный подход: fetch внутри useEffect

```jsx
function UserProfile({ userId }) {
  const [data, setData] = useState(null);
  const [isLoading, setIsLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setIsLoading(true);
    fetch(`/api/users/${userId}`)
      .then((res) => res.json())
      .then((data) => {
        setData(data);
        setIsLoading(false);
      })
      .catch((err) => {
        setError(err);
        setIsLoading(false);
      });
  }, [userId]);

  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <Profile data={data} />;
}
```

Этот паттерн формально работает, но содержит несколько системных проблем, которые проявляются по мере роста приложения — именно их разбор чаще всего и спрашивают на собеседовании.

## ⚠️ Проблема 1: Race Condition (состояние гонки)

Если `userId` меняется быстрее, чем успевает разрешиться предыдущий запрос, ответы могут прийти **не в том порядке**, в котором были отправлены запросы — и компонент отобразит устаревшие данные поверх актуальных.

```jsx
// userId: 1 → быстро меняется на 2
// Запрос за userId=1 отправлен первым, но по какой-то причине разрешился позже
// Запрос за userId=2 отправлен вторым, но разрешился раньше
// Итог без защиты: на экране показаны данные userId=1, хотя запрошен uderId=2
```

**Классическое решение** — флаг отмены (cancellation flag) в функции очистки эффекта:

```jsx
useEffect(() => {
  let isCancelled = false;

  fetch(`/api/users/${userId}`)
    .then((res) => res.json())
    .then((data) => {
      if (!isCancelled) setData(data); // игнорируем устаревший ответ
    });

  return () => {
    isCancelled = true; // помечаем предыдущий эффект как "устаревший" при смене userId
  };
}, [userId]);
```

> [!info] Формулировка для собеседования 
> "Race condition при data fetching в useEffect возникает из-за отсутствия гарантии порядка разрешения промисов относительно порядка их создания. Функция очистки эффекта — стандартный механизм React для отмены/игнорирования эффекта предыдущего рендера — используется здесь не для реальной отмены сетевого запроса (browser fetch не всегда отменяем без AbortController), а для игнорирования его результата, если пришёл 'устаревший' ответ."

Более технически корректное решение — `AbortController`, реально прерывающий сетевой запрос:

```jsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then((res) => res.json())
    .then(setData)
    .catch((err) => {
      if (err.name !== 'AbortError') setError(err);
    });

  return () => controller.abort();
}, [userId]);
```

## ⚠️ Проблема 2: Отсутствие кэширования

При наивном подходе каждый рендер компонента, монтирующего этот `useEffect`, инициирует **новый** сетевой запрос — даже если данные для этого `userId` уже были загружены секунду назад в другом месте приложения. Нет единого кэша между разными компонентами, использующими одни и те же данные.

## ⚠️ Проблема 3: Дублирование запросов (отсутствие дедупликации)

Если два компонента в дереве одновременно запрашивают одни и те же данные (например, `<UserAvatar userId={5} />` и `<UserName userId={5} />` в разных частях страницы), наивный подход отправит **два одинаковых** сетевых запроса вместо одного разделяемого.

## ⚠️ Проблема 4: Отсутствие ревалидации и синхронизации

Наивный подход не отвечает на вопросы: когда данные считать устаревшими? Нужно ли перезапрашивать их при возврате фокуса на вкладку браузера? Как обновить все места в приложении, где отображаются эти данные, после того как пользователь их изменил (мутация)?

## 🔬 Что решают специализированные библиотеки (React Query / SWR)

|Проблема наивного подхода|Как решает библиотека|
|---|---|
|Race conditions|встроенное отслеживание актуальности запроса из коробки|
|Отсутствие кэша|единый глобальный кэш по ключу запроса, разделяемый между всеми компонентами|
|Дублирование запросов|дедупликация — параллельные идентичные запросы автоматически схлопываются в один|
|Устаревание данных|понятия `staleTime` / `cacheTime`, фоновая ревалидация (refetch on window focus, refetch on reconnect)|
|Состояния загрузки/ошибки|стандартизированные `isLoading`, `isError`, `isFetching` без ручного дублирования в каждом компоненте|
|Мутации и синхронизация|инвалидация кэша по ключу после мутации — все подписанные компоненты автоматически получают свежие данные|

```jsx
// Пример с React Query — то же самое, что наивный пример выше, но с решением всех перечисленных проблем
import { useQuery } from '@tanstack/react-query';

function UserProfile({ userId }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ['user', userId], // ключ кэша — по нему определяется дедупликация и инвалидация
    queryFn: () => fetch(`/api/users/${userId}`).then((res) => res.json()),
  });

  if (isLoading) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <Profile data={data} />;
}
```

## 🕰️ staleTime vs cacheTime (gcTime) — частый вопрос на собеседовании

Эти два понятия систематически путают между собой:

- **`staleTime`** — сколько времени данные считаются **свежими (fresh)** после получения. Пока данные "свежие", повторный вызов `useQuery` с тем же ключом **не** инициирует новый сетевой запрос — просто отдаёт закэшированное значение.
- **`cacheTime`** (в новых версиях React Query переименован в `gcTime`) — сколько времени **неиспользуемые** (ни одним смонтированным компонентом) данные хранятся в памяти кэша, прежде чем будут удалены сборщиком мусора библиотеки.

```jsx
useQuery({
  queryKey: ['user', userId],
  queryFn: fetchUser,
  staleTime: 5 * 60 * 1000,  // 5 минут данные считаются свежими — фоновый рефетч не нужен
  gcTime: 30 * 60 * 1000,    // но хранить в памяти кэш можно ещё 30 минут после того, как все компоненты размонтированы
});
```

> [!info] Формулировка для собеседования 
> "`staleTime` определяет, когда данные считать устаревшими _с точки зрения необходимости повторного запроса_, а `cacheTime`/`gcTime` определяет, как долго данные вообще хранить в памяти после того, как последний подписанный компонент размонтировался. Данные могут быть 'stale', но всё ещё присутствовать в кэше — в этом случае они мгновенно отображаются из кэша (нет пустого состояния загрузки), а свежий запрос уходит в фоне (паттерн 'stale-while-revalidate', давший название и самой библиотеке SWR)."

## 🆚 useEffect vs специализированная библиотека — когда что уместно

> [!tip] Практическое правило 
> Ручной `useEffect` + `fetch` оправдан для одноразовых, изолированных запросов без необходимости кэша, синхронизации между компонентами или сложной инвалидации (например, простая форма, отправляющая данные один раз). Как только в приложении возникает **несколько мест**, использующих одни и те же серверные данные, либо требуется синхронизация после мутаций — специализированная библиотека решает эти задачи с кардинально меньшим объёмом кода и меньшим числом граничных случаев (edge cases), которые пришлось бы реализовывать вручную.

## ⚠️ Частые вопросы на собеседовании

> [!example] "Как возникает race condition при загрузке данных в useEffect и как его избежать?" 
> Возникает, когда зависимость эффекта (например, `userId`) меняется быстрее, чем разрешается предыдущий запрос, и ответы приходят в порядке, отличном от порядка отправки. Избежать можно через флаг отмены в cleanup-функции эффекта, либо технически корректнее — через `AbortController`, реально прерывающий устаревший запрос.

> [!example] "В чём разница между staleTime и cacheTime/gcTime в React Query?" 
> `staleTime` — время, в течение которого данные считаются актуальными и не требуют фонового рефетча при повторном обращении. `cacheTime`/`gcTime` — время хранения неиспользуемых данных в памяти после того, как последний подписчик отписался, прежде чем они будут удалены сборщиком мусора библиотеки.

> [!example] "Зачем вообще нужна дедупликация запросов, если можно просто поднять данные наверх (lift state up) и передавать пропсами?" 
> Поднятие состояния решает проблему дублирования запросов только в пределах заранее известного, статичного дерева компонентов и требует ручного прокидывания пропсов (см. [[Prop drilling]]). Библиотеки для data fetching решают это на уровне глобального кэша по ключу запроса, работая для любых компонентов в приложении вне зависимости от их взаимного расположения в дереве, без явной передачи данных через пропсы.
