## 💡 Общий контекст

Все три паттерна решают одну и ту же фундаментальную задачу React-экосистемы — **переиспользование логики и гибкую композицию** компонентов, но делают это разными архитектурными средствами и с разными компромиссами. Исторически они предшествуют Custom Hooks (см. [[Custom Hooks]]) и во многом были вытеснены ими для задач переиспользования _stateful-логики_, но остаются актуальными там, где решается задача переиспользования именно **компоновки UI** (composition), а не только логики.

> [!info] Формулировка для собеседования 
> "Render Props и HOC решают задачу переиспользования логики через оборачивание/параметризацию компонентов — но именно из-за них возникает проблема 'wrapper hell'. Custom Hooks решили эту задачу без обёрток. Однако Compound Components и Provider Pattern остаются актуальными и сегодня, поскольку решают другую задачу — гибкую, декларативную композицию **связанных между собой** компонентов UI, а не изолированную переиспользуемую логику."

## 🎭 Render Props

**Render Prop** — это проп компонента, значением которого является **функция**, возвращающая JSX; компонент вызывает эту функцию вместо того, чтобы рендерить фиксированную разметку самостоятельно, передавая ей своё внутреннее состояние или данные в качестве аргументов.

```jsx
class MouseTracker extends React.Component {
  state = { x: 0, y: 0 };

  handleMouseMove = (e) => {
    this.setState({ x: e.clientX, y: e.clientY });
  };

  render() {
    return (
      <div onMouseMove={this.handleMouseMove}>
        {this.props.render(this.state)}
      </div>
    );
  }
}

// Использование:
<MouseTracker render={({ x, y }) => (
  <p>Курсор находится в точке ({x}, {y})</p>
)} />
```

Часто используется вариант через `children` как функцию (**function as child / FaCC**):

```jsx
<MouseTracker>
  {({ x, y }) => <p>({x}, {y})</p>}
</MouseTracker>
```

### ✅ Плюсы

- Явный, декларативный способ "инъекции" данных в разметку без промежуточных пропсов
- Компонент-источник логики не диктует, **что именно** рендерить — только **что передать**

### ⚠️ Минусы

- Вложенность нескольких Render Props (несколько источников данных) приводит к глубокой вложенности JSX ("callback hell" в JSX-варианте — иногда называют "wrapper hell")
- Требует ре-рендера при каждом изменении state источника, так как функция-рендер вызывается заново
- В подавляющем большинстве случаев современного кода вытеснен Custom Hooks — переиспользование той же логики (`useMouseTracker()`) устраняет вложенность полностью

```jsx
// Эквивалент через Custom Hook — без вложенности
function useMousePosition() {
  const [position, setPosition] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const handler = (e) => setPosition({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', handler);
    return () => window.removeEventListener('mousemove', handler);
  }, []);
  return position;
}
```

## 🧩 Compound Components

**Compound Components** — паттерн, при котором несколько компонентов работают совместно как единая логическая единица, неявно разделяя общее состояние между собой (обычно через `React.Context` или `React.Children`/`cloneElement`), при этом предоставляя потребителю **декларативный и гибкий** API компоновки — сравнимый с тем, как HTML-теги `<select>` и `<option>` работают вместе.

```jsx
const ToggleContext = createContext();

function Toggle({ children }) {
  const [on, setOn] = useState(false);
  const toggle = () => setOn((prev) => !prev);

  return (
    <ToggleContext.Provider value={{ on, toggle }}>
      {children}
    </ToggleContext.Provider>
  );
}

function ToggleButton() {
  const { on, toggle } = useContext(ToggleContext);
  return <button onClick={toggle}>{on ? 'ВКЛ' : 'ВЫКЛ'}</button>;
}

function ToggleIndicator() {
  const { on } = useContext(ToggleContext);
  return <span>{on ? '🟢' : '🔴'}</span>;
}

Toggle.Button = ToggleButton;
Toggle.Indicator = ToggleIndicator;
```

Использование — потребитель сам решает порядок и состав дочерних элементов, не будучи ограничен фиксированной структурой пропсов:

```jsx
<Toggle>
  <Toggle.Indicator />
  <Toggle.Button />
</Toggle>
```

> [!info] Формулировка для собеседования 
> "Compound Components реализуют неявную коммуникацию между связанными компонентами через общий контекст, вместо явной передачи десятков пропсов через родителя. Ключевое архитектурное преимущество — гибкость композиции: потребитель компонента управляет структурой JSX (порядком, наличием опциональных частей), а не ограничен фиксированной формой, заданной автором компонента через пропсы вроде `renderHeader`, `renderFooter` и т.д."

### ✅ Плюсы

- Гибкая композиция — потребитель решает, какие части использовать и в каком порядке
- API читается декларативно, близко к семантике HTML
- Устраняет "проп-бурение" (prop drilling) между связанными частями UI (см. отдельную тему [[Prop drilling]])

### ⚠️ Минусы

- Дочерние компоненты неявно зависят от того, что они отрендерены **внутри** родительского компонента-обёртки — использование `Toggle.Button` вне `<Toggle>` приведёт к ошибке (контекст будет `undefined`)
- Сложнее типизировать в TypeScript, чем простую передачу пропсов
- Требует более сложной документации — неочевидно "снаружи", какие подкомпоненты обязательны, а какие опциональны

## 🏛️ Provider Pattern

**Provider Pattern** — использование `Context.Provider` для передачи данных и функций напрямую любому компоненту в поддереве, вне зависимости от глубины вложенности, без необходимости передавать их явно через пропсы на каждом промежуточном уровне.

```jsx
const AuthContext = createContext(null);

function AuthProvider({ children }) {
  const [user, setUser] = useState(null);

  const login = (credentials) => {/* ... */ setUser(/* ... */);};
  const logout = () => setUser(null);

  const value = useMemo(() => ({ user, login, logout }), [user]);

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  );
}

function useAuth() {
  const context = useContext(AuthContext);
  if (context === null) {
    throw new Error('useAuth должен использоваться внутри AuthProvider');
  }
  return context;
}
```

Использование — любой компонент внутри дерева, обёрнутого в `AuthProvider`, получает доступ без прокидывания пропсов:

jsx

```jsx
function App() {
  return (
    <AuthProvider>
      <Dashboard />
    </AuthProvider>
  );
}

function ProfileMenu() {
  const { user, logout } = useAuth(); // доступ на любой глубине
  return <button onClick={logout}>{user.name}</button>;
}
```

> [!warning] Частый вопрос на собеседовании: производительность Provider Pattern Все компоненты, вызывающие `useContext(SomeContext)`, перерендериваются при **любом** изменении значения `value` у `Provider` — вне зависимости от того, какая именно часть объекта `value` изменилась. Поэтому:
> 
> 1. Значение `value` рекомендуется мемоизировать через `useMemo`, чтобы не создавать новый объект на каждом рендере родителя без необходимости
> 2. При большом числе часто меняющихся значений стоит **разделять контексты** по смыслу (например, отдельно `UserContext` и `ThemeContext`), чтобы изменение одного не вызывало ре-рендер потребителей другого
> 3. Context не оптимизирован для очень частых, высокочастотных обновлений (например, позиции курсора 60 раз в секунду) — для таких случаев больше подходят внешние стор-библиотеки с точечной подпиской (Zustand, Redux с селекторами)

### ✅ Плюсы

- Устраняет prop drilling для глобальных/широко используемых данных (тема, авторизация, локализация)
- Явная граница ответственности — Provider инкапсулирует логику управления состоянием отдельно от компонентов-потребителей

### ⚠️ Минусы

- Не предназначен как замена полноценному стейт-менеджеру для часто меняющихся данных (см. предупреждение выше)
- Неаккуратное использование (немемоизированный `value`) — частый источник неочевидных лишних ре-рендеров всего поддерева

## 🆚 Сравнение трёх паттернов

|Критерий|Render Props|Compound Components|Provider Pattern|
|---|---|---|---|
|Что решает|переиспользование логики через функцию-рендер|гибкая композиция связанных UI-частей|доступ к данным на любой глубине дерева|
|Механизм связи|функция как проп|общий Context между подкомпонентами|Context.Provider / useContext|
|Добавляет вложенность в JSX|да (может быть глубокой)|нет|нет|
|Актуальность сегодня|в основном вытеснен хуками|остаётся актуальным|остаётся актуальным, широко используется|
|Типичный пример из практики|редко в новом коде|`<Tabs>`, `<Accordion>`, `<Select>` из UI-библиотек|тема оформления, авторизация, i18n|

## ⚠️ Частые вопросы на собеседовании

> [!example] "Почему Custom Hooks в основном вытеснили Render Props?" Render Props решают задачу переиспользования логики ценой дополнительной вложенности компонентов в дереве и в JSX-разметке ("wrapper hell"). Custom Hooks решают ровно ту же задачу — переиспользование stateful-логики — без создания дополнительных компонентов-обёрток вообще, так как хук — это просто функция, вызываемая внутри тела компонента.

> [!example] "В чём принципиальное отличие Compound Components от простой передачи render-пропсов вроде renderHeader?" При передаче `renderHeader`/`renderFooter` автор родительского компонента заранее фиксирует, какие "слоты" вообще существуют. Compound Components дают потребителю полный контроль над составом и порядком JSX-детей — можно не использовать часть подкомпонентов, менять их порядок, оборачивать во что-то ещё, что невозможно при фиксированном наборе render-пропсов.

> [!example] "Почему компонент, использующий Context, перерендеривается, даже если ему нужно только одно поле из объекта value?" `useContext` подписывается на **весь объект** `value`, переданный в `Provider`, а не на отдельные поля внутри него. React сравнивает ссылку на `value` целиком между рендерами: если родитель создаёт новый объект `{ user, login, logout }` на каждом рендере (без `useMemo`), это триггерит ре-рендер всех потребителей контекста, даже если изменилось лишь одно поле или не изменилось вообще ничего.
