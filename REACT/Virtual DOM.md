>**Virtual DOM** — это лёгкое, JS-объектное представление реального DOM-дерева (обычный JS-объект в памяти, никакого отношения к браузерному DOM API).

>Когда состояние компонента меняется, React:

1. Строит **новое** дерево Virtual DOM, отражающее обновлённое состояние.
2. Сравнивает его со **старым** деревом Virtual DOM через процесс, называемый **reconciliation** (алгоритм "diffing" — сравнение деревьев).
3. Вычисляет **минимальный набор изменений**, которые нужно применить к реальному DOM, чтобы привести его в соответствие с новым Virtual DOM.
4. Применяет только эти изменения к реальному DOM (это называется **commit phase**).

Cравниваются именно **два** Virtual DOM дерева (старое и новое) — а не Virtual DOM с реальным DOM напрямую. Реальный DOM в этом сравнении не участвует — он только **получает** финальные точечные изменения на последнем шаге.

### Заблуждение, которое стоит разобрать

>Частое заблуждение звучит так: **"Virtual DOM существует, потому что прямые манипуляции с реальным DOM — медленные, а работа с Virtual DOM — быстрая"**. Это не совсем точно, и вот почему:

Прямая, **точечная** манипуляция реальным DOM (например, `element.textContent = 'new value'` для одного конкретного узла) на самом деле **очень быстрая** — быстрее, чем цикл React (создать новое дерево → сравнить → применить изменения). Если бы ты точно знал, какой единственный узел нужно поменять, и делал это напрямую — это было бы эффективнее, чем через весь процесс Virtual DOM.

>**Настоящая причина, зачем нужен Virtual DOM** — не "скорость сама по себе", а **предсказуемость и удобство разработки** при частых, сложных обновлениях состояния:

Без Virtual DOM разработчику пришлось бы **вручную** отслеживать, какие именно части реального DOM нужно обновить при каждом изменении состояния — это быстро становится крайне сложно поддерживать в большом приложении с множеством взаимозависимых частей UI. Virtual DOM позволяет писать код в **декларативном** стиле — "вот как должен выглядеть UI при таком состоянии" — и React сам разбирается, **что именно** реально нужно поменять в DOM, избавляя разработчика от ручного отслеживания изменений.

>**В чём тогда практическая выгода в производительности** — она есть, но более тонкая: без Virtual DOM наивный подход "просто перерисовать всё" при каждом изменении состояния (то есть полностью **уничтожать и пересоздавать** весь DOM-дерево заново) был бы гораздо медленнее — потому что реальные DOM-операции (создание узлов, layout, reflow, repaint) дорогие именно при **больших объёмах**. Virtual DOM (сравнение JS-объектов в памяти) — дешёвая операция, и она позволяет **избежать** дорогих полных перерисовок реального DOM, сводя изменения к минимальному необходимому набору точечных правок.

**Итог, который стоит запомнить дословно для собеса:** Virtual DOM не быстрее прямых точечных манипуляций с реальным DOM в теории — но он даёт возможность писать декларативный код без ручного управления DOM, при этом **избегая наивной полной перерисовки**, что на практике оказывается быстрее и удобнее, чем если бы разработчик или наивный фреймворк перерисовывал весь DOM целиком при каждом изменении.
