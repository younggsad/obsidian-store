# ЧАСТЬ 3. RECONCILIATION (СОГЛАСОВАНИЕ)

## 3.1 Что это такое

>**Reconciliation** — алгоритм, с помощью которого React определяет, **какие именно изменения** нужно внести в реальный DOM после того, как состояние компонента изменилось и вызвало новый рендер. Это ядро того, что делает React эффективным — вместо полной пересборки DOM при каждом изменении, React вычисляет **минимальный набор изменений** и применяет только их.

## 3.2 Virtual DOM — база механизма

При каждом рендере компонент возвращает **описание** UI (JSX компилируется в вызовы `React.createElement`, создающие обычные JS-объекты) — это и есть **Virtual DOM**, лёгкое, "виртуальное" представление реального DOM в памяти.

```jsx
// JSX
<div className="box"><p>Текст</p></div>

// компилируется в (упрощённо)
React.createElement('div', { className: 'box' },
  React.createElement('p', null, 'Текст')
)
```

При обновлении состояния React строит **новое** дерево Virtual DOM, сравнивает его со **старым** (предыдущим) деревом — этот процесс сравнения и называется **diffing**, а результат применяется к реальному DOM минимальными точечными изменениями (**patch**).

## 3.3 Правила эвристического алгоритма Reconciliation

Полное сравнение двух произвольных деревьев в общем случае — алгоритмически дорогая задача (O(n³)). React использует **эвристический алгоритм** со сложностью O(n), основанный на двух допущениях:

**Правило 1 — разные типы элементов дают разные деревья**

```jsx
// Было:
<div><Counter /></div>
// Стало:
<span><Counter /></span>
```

При смене типа корневого элемента (`div` → `span`) React **полностью уничтожает** старое поддерево (включая состояние всех вложенных компонентов) и строит новое с нуля — даже если внутри логически "тот же" `Counter`, его состояние **сбрасывается**.

**Правило 2 — элементы одного типа сравниваются по их атрибутам/пропсам**

```jsx
// Было:
<div className="before" />
// Стало:
<div className="after" />
```

React сохраняет тот же реальный DOM-узел, только обновляет изменившийся атрибут (`className`) — не пересоздаёт узел целиком.

**Правило 3 — `key` в списках дочерних элементов**

```jsx
// Без key или с key={index} — при вставке элемента в НАЧАЛО списка
// React может решить, что ВСЕ элементы "изменились", и перерисовать/пересоздать состояние каждого

// С правильным стабильным key={item.id} —
// React понимает, что старые элементы просто "сдвинулись", а не пересозданы заново
```

`key` — единственный способ дать React "подсказку", какой конкретно элемент из старого дерева соответствует какому элементу нового дерева, при переупорядочивании списков.

## 3.4 Fiber — архитектура, лежащая в основе современного Reconciliation (с React 16)

**Fiber** — переписанная внутренняя архитектура механизма согласования (пришла на смену старому "Stack Reconciler"). Ключевая идея: работа по вычислению изменений разбивается на маленькие единицы ("fiber"-узлы), которые можно **приостанавливать, возобновлять, прерывать и назначать им разный приоритет** — вместо того чтобы выполнять весь процесс синхронно, одним блокирующим проходом.

Именно архитектура Fiber сделала возможным **Concurrent Rendering** — ключевую возможность React 18 (см. Часть 7): React может начать рендерить обновление низкого приоритета, прерваться, если пришло более срочное обновление (например, реакция на ввод пользователя), обработать срочное первым, а потом вернуться к прерванной работе.

## 3.5 Практический вывод — почему нужны `key` и стабильные типы компонентов

```jsx
// ❌ Плохо — при каждом рендере родителя создаётся НОВЫЙ компонент-тип
function Parent({ isEditing }) {
  const Component = isEditing ? EditForm : ViewForm; // компонент меняется на каждый рендер
  return <Component />; // React считает это РАЗНЫМИ типами → полный ремаунт, теряется состояние
}

// ✅ Лучше — стабильный тип, условие внутри JSX
function Parent({ isEditing }) {
  return isEditing ? <EditForm /> : <ViewForm />; // тоже разные типы, но осознанно и предсказуемо
}
```
