# ЧАСТЬ 1. BUNDLERS (СБОРЩИКИ МОДУЛЕЙ)

## 1.1 Зачем нужны бандлеры

>**Бандлер (module bundler)** — инструмент, который берёт множество отдельных файлов проекта (JS-модули, CSS, изображения, шрифты) со всеми их зависимостями друг от друга, и **объединяет** их в один или несколько оптимизированных файлов ("бандлов"), готовых к работе в браузере.

**Проблемы, которые решают бандлеры:**

1. **Модульность в браузере** — до появления бандлеров браузеры не умели нативно работать с системами модулей вроде CommonJS (`require`/`module.exports`, стандарт Node.js), а поддержка нативных ES-модулей (`import`/`export`) в браузерах пришла далеко не сразу и до сих пор имеет ограничения по производительности при большом количестве файлов.
2. **Количество HTTP-запросов** — без бандлинга каждый JS/CSS-файл проекта (а их могут быть сотни) загружался бы отдельным сетевым запросом — это медленно, особенно на HTTP/1.1.
3. **Оптимизация** — минификация (сжатие кода), удаление неиспользуемого кода (tree shaking), транспиляция современного синтаксиса под старые браузеры, оптимизация изображений.
4. **Управление зависимостями** — импорт npm-пакетов, CSS-файлов, изображений прямо в JS-код единым, согласованным образом.

## 1.2 Ключевые концепции бандлинга

### Entry point (точка входа)

Файл, с которого бандлер начинает строить **граф зависимостей** — анализирует все `import`/`require` внутри него, потом внутри их зависимостей, и так далее рекурсивно.

```javascript
// webpack.config.js
module.exports = {
  entry: './src/index.js',
};
```

### Граф зависимостей (dependency graph)

Внутреннее представление того, какой модуль от какого зависит — бандлер строит это дерево/граф, начиная от entry point, чтобы понять, какие файлы вообще нужно включить в сборку.

### Output (выходной файл)

```javascript
module.exports = {
  output: {
    filename: 'bundle.[contenthash].js', // hash в имени — для правильного кэширования браузером
    path: __dirname + '/dist',
  },
};
```

### Loaders / Transformers — обработка не-JS файлов

Бандлеры изначально понимают только JavaScript (и иногда JSON) — чтобы импортировать CSS, изображения, шрифты, TypeScript, JSX прямо из JS-кода, нужны специальные обработчики.

```javascript
// Webpack loaders
module.exports = {
  module: {
    rules: [
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
      { test: /\.(png|svg|jpg)$/, type: 'asset/resource' },
      { test: /\.tsx?$/, use: 'ts-loader' },
    ],
  },
};
```

### Plugins — расширение возможностей сборки

В отличие от loaders (обрабатывают отдельные файлы), плагины работают с процессом сборки **в целом** — генерация HTML-файла со вставленными тегами `<script>`, очистка выходной папки перед сборкой, извлечение CSS в отдельный файл и т.д.

## 1.3 Обзор популярных бандлеров

|Бандлер|Особенность|
|---|---|
|**Webpack**|самый функциональный и настраиваемый, но сложнее в конфигурации; долгое время индустриальный стандарт|
|**Vite**|использует нативные ES-модули в dev-режиме (мгновенный старт), Rollup для production-сборки; сегодня самый популярный выбор для новых проектов|
|**Rollup**|заточен под сборку библиотек (а не приложений), отличный tree shaking, простая конфигурация|
|**esbuild**|написан на Go, чрезвычайно быстрая компиляция (в десятки раз быстрее JS-based инструментов); часто используется как "движок" внутри других инструментов (Vite использует его в dev-режиме)|
|**Parcel**|"нулевая конфигурация" — работает из коробки почти без настройки|
|**Turbopack**|новый бандлер от Vercel (на Rust), используется в Next.js, ориентирован на инкрементальную сборку|

## 1.4 Webpack — базовая конфигурация

```javascript
// webpack.config.js
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  mode: 'production',              // 'development' | 'production' — включает разные наборы оптимизаций
  entry: './src/index.js',
  output: {
    filename: '[name].[contenthash].js',
    path: path.resolve(__dirname, 'dist'),
    clean: true,                      // очищать dist перед каждой сборкой
  },
  module: {
    rules: [
      { test: /\.jsx?$/, exclude: /node_modules/, use: 'babel-loader' },
      { test: /\.css$/, use: ['style-loader', 'css-loader'] },
    ],
  },
  plugins: [
    new HtmlWebpackPlugin({ template: './public/index.html' }),
  ],
  devServer: {
    port: 3000,
    hot: true,                          // Hot Module Replacement
  },
};
```

## 1.5 Vite — базовая конфигурация

```javascript
// vite.config.js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    port: 3000,
  },
  build: {
    outDir: 'dist',
    sourcemap: true,
  },
});
```

**Ключевое архитектурное отличие Vite от Webpack:**

- **Webpack (в dev-режиме)** — предварительно собирает **весь** бандл приложения при старте dev-сервера, прежде чем что-то показать в браузере — на больших проектах это может занимать десятки секунд.
- **Vite (в dev-режиме)** — не бандлит приложение целиком заранее. Использует **нативные ES-модули браузера**: браузер сам запрашивает файлы по мере навигации (`import`), Vite отдаёт их "на лету", трансформируя каждый файл индивидуально (через esbuild — очень быстро). Старт сервера практически мгновенный, независимо от размера проекта, потому что ничего заранее не собирается.

Для **production**-сборки Vite использует Rollup под капотом (не нативные ES-модули браузера — это уже полноценный оптимизированный бандл, как у традиционных инструментов).

## 1.6 Code Splitting (разделение кода)

Вместо одного огромного `bundle.js`, содержащего весь код приложения, код разбивается на несколько отдельных частей ("чанков"), загружаемых **по требованию**, а не всех сразу при первом заходе на сайт.

### Динамический импорт — основной механизм

```javascript
// Вместо статического импорта в начале файла:
import HeavyComponent from './HeavyComponent';

// Динамический импорт — создаёт ОТДЕЛЬНЫЙ чанк, загружаемый только при вызове:
button.addEventListener('click', async () => {
  const { default: HeavyComponent } = await import('./HeavyComponent');
  // используем HeavyComponent только теперь, когда он реально понадобился
});
```

В React это лежит в основе `React.lazy` (разбирали в конспекте по React):

```jsx
const HeavyChart = React.lazy(() => import('./HeavyChart'));
```

### Route-based splitting — самый частый практический паттерн

```jsx
const HomePage = lazy(() => import('./pages/HomePage'));
const AboutPage = lazy(() => import('./pages/AboutPage'));
// Каждая "страница" приложения — отдельный чанк, грузится только при переходе на неё
```

### Vendor splitting — отдельный чанк для сторонних библиотек

```javascript
// webpack.config.js
optimization: {
  splitChunks: {
    cacheGroups: {
      vendor: {
        test: /[\\/]node_modules[\\/]/,
        name: 'vendors',
        chunks: 'all',
      },
    },
  },
},
```

Библиотеки (React, lodash и т.д.) обычно меняются гораздо реже, чем код самого приложения — вынос их в отдельный чанк позволяет браузеру **кэшировать** этот файл надолго, даже когда обновляется сам код приложения (пользователю не нужно перекачивать библиотеки заново при каждом релизе).

## 1.7 Tree Shaking — удаление неиспользуемого кода

```javascript
// utils.js
export function usedFunction() { return "используется"; }
export function unusedFunction() { return "НЕ используется нигде в проекте"; }

// main.js
import { usedFunction } from './utils.js';
console.log(usedFunction());
```

При production-сборке бандлер анализирует, какие именно экспорты реально **используются** где-либо в проекте, и **исключает** из финального бандла всё остальное (`unusedFunction` не попадёт в итоговый файл).

**Важное условие для работы Tree Shaking:** требует использования **ES-модулей** (`import`/`export`), а не CommonJS (`require`/`module.exports`) — статический анализ зависимостей ES-модулей возможен **до** выполнения кода (на этапе сборки), тогда как `require()` может быть вызван условно, динамически, что делает статический анализ ненадёжным.

```javascript
// ❌ Плохо для tree shaking — импорт ВСЕЙ библиотеки целиком
import _ from 'lodash';
_.debounce(fn, 300);

// ✅ Хорошо — именованный импорт конкретной функции (если библиотека это поддерживает)
import { debounce } from 'lodash-es'; // ES-модульная версия lodash
debounce(fn, 300);
```

## 1.8 Минификация

Удаление пробелов, переносов строк, комментариев, сокращение имён переменных до минимально возможных — уменьшает размер файла без изменения поведения кода.

```javascript
// До минификации
function calculateTotal(price, quantity) {
  const total = price * quantity;
  return total;
}

// После минификации
function a(b,c){return b*c}
```

Инструменты: **Terser** (для JS, используется внутри Webpack/Rollup по умолчанию в production-режиме), **esbuild** (минификация как часть общей трансформации, очень быстро), **cssnano** (для CSS).

## 1.9 Транспиляция — Babel / SWC

Отдельная задача от бандлинга (хотя часто выполняется в связке): преобразование современного синтаксиса JS/TS/JSX в код, понятный **более старым** браузерам/окружениям, которые не поддерживают новые возможности языка нативно.

```javascript
// Babel config (.babelrc)
{
  "presets": [
    ["@babel/preset-env", { "targets": "> 0.25%, not dead" }],
    "@babel/preset-react"
  ]
}
```

**SWC** (используется в Next.js, Vite для некоторых задач) — аналог Babel, написанный на Rust, значительно быстрее.

## 1.10 Source Maps

```javascript
// webpack.config.js
devtool: 'source-map',
```

Файл-карта, связывающая **минифицированный/скомпилированный** код в production с **исходным** написанным кодом — позволяет видеть в DevTools браузера настоящие имена переменных, оригинальную структуру файлов, точные номера строк при отладке, даже когда реально выполняется совсем другой, преобразованный код.

## 1.11 HMR (Hot Module Replacement)

>Механизм, позволяющий **заменять** изменённые модули прямо в работающем приложении в браузере во время разработки, **без полной перезагрузки страницы** — сохраняется текущее состояние приложения (например, значения в формах, открытые модальные окна), пока меняется только конкретный отредактированный компонент/файл. Значительно ускоряет цикл разработки по сравнению с полным `location.reload()` при каждом изменении.

**Как это работает технически (кратко):**

1. Бандлер в dev-режиме держит **WebSocket-соединение** между сервером и открытой вкладкой браузера.
2. Когда файл меняется на диске, бандлер пересобирает **только этот модуль** (а не всё приложение), и отправляет обновлённый код через WebSocket в браузер.
3. Специальный runtime-код на странице (HMR runtime) получает новый модуль и **заменяет** старую версию в памяти — без перезагрузки страницы.
4. Дальше зависит от фреймворка — для React есть **React Fast Refresh** (современная замена старому React Hot Loader), который умеет заменять код компонента, сохраняя его `state` (например, значение `useState`), но при этом корректно применяя новый JSX/логику.

**Разница с live reload, если формализовать чётче:**

- **Live reload** — при любом изменении файла происходит полный `window.location.reload()` — вся страница перезагружается с нуля, весь JS-контекст стирается, приложение стартует заново.
- **HMR** — заменяется только изменённый модуль в уже работающем JS-контексте, состояние приложения (в идеале) сохраняется.

**Практический пример, почему это важно для разработчика:** если ты заполнил длинную многошаговую форму и поправил стиль одной кнопки — с live reload тебе придётся заново проходить всю форму, чтобы увидеть эффект. С HMR (и особенно с React Fast Refresh) — состояние формы сохранится, а изменение стиля применится мгновенно поверх текущего состояния приложения.

## 1.12 Сравнительная сводка

|Критерий|Webpack|Vite|
|---|---|---|
|Скорость dev-старта|медленнее на больших проектах (бандлит всё заранее)|почти мгновенная (нативные ES-модули + esbuild)|
|Гибкость конфигурации|максимальная, много готовых loaders/plugins под любую задачу|проще из коробки, меньше готовых плагинов под экзотические случаи|
|Production-сборка|Terser + собственный движок|Rollup под капотом|
|Порог входа|выше, конфиг может быть громоздким|ниже, разумные настройки по умолчанию|
|Экосистема|огромная, самая зрелая|быстро растёт, уже стандарт для новых React/Vue проектов|
