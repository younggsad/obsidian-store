>**Dependency Injection** — техника, при которой объект **получает** свои зависимости **извне** (через конструктор, метод или свойство), а не **создаёт их сам внутри себя**. Это практическая реализация принципа инверсии зависимостей (D из SOLID).

**Без DI:**

```js
class UserService {
  constructor() {
    this.database = new PostgresDatabase(); // создаёт зависимость сам, жёстко "вшито" внутри
  }
}
```

Проблема: `UserService` **невозможно протестировать изолированно** — при каждом тесте он будет пытаться подключиться к реальной PostgreSQL базе данных. Также невозможно легко подменить базу данных на другую реализацию, не переписывая сам `UserService`.

**С DI:**

```js
class UserService {
  constructor(database) { // зависимость передаётся ИЗВНЕ, "инъецируется"
    this.database = database;
  }
}

const service = new UserService(new PostgresDatabase()); // в реальном коде
const testService = new UserService(new MockDatabase());  // в тестах — легко подменить на "фейковую" БД
```

**Три основных способа внедрения зависимостей:**

1. **Через конструктор (constructor injection)** — как в примере выше, самый распространённый способ.
2. **Через сеттер/свойство (setter injection)** — зависимость устанавливается после создания объекта через отдельный метод/свойство.
3. **Через метод (method injection)** — зависимость передаётся прямо в конкретный метод, а не хранится во всём объекте.

## 1. Constructor Injection

Самый распространенный способ.

```TypeScript
class UserService {
  constructor(private email: EmailService) {}
}
```

### Преимущества

- зависимость обязательна;
- объект всегда находится в корректном состоянии;
- невозможно забыть передать зависимость;
- именно этот способ используется в большинстве современных backend-фреймворков (NestJS, Spring, ASP.NET Core).

---

## 2. Setter Injection

```TypeScript
class UserService {
  private email!: EmailService;

  setEmail(email: EmailService) {
    this.email = email;
  }
}
```

### Используется когда

Зависимость может меняться во время работы программы.

Недостаток — можно забыть вызвать сеттер.

---

## 3. Method Injection

```TypeScript
class UserService {
  register(email: EmailService) {
    email.send();
  }
}
```

Используется значительно реже.

Подходит тогда, когда зависимость нужна только одному конкретному методу.

## DI-Контейнеры

>**DI-контейнеры** — в более крупных приложениях (особенно на backend, например в NestJS — популярном Node.js-фреймворке) используют **DI-контейнер** — специальный механизм, который **автоматически** создаёт и внедряет нужные зависимости, отслеживая, что каждому классу требуется, без необходимости вручную писать `new UserService(new PostgresDatabase())` для каждого класса вручную.

```ts
// Пример синтаксиса NestJS (иллюстративно) — DI-контейнер сам разберётся,
// что UserService нужен DatabaseService, и создаст/подставит его автоматически
@Injectable()
class UserService {
  constructor(private database: DatabaseService) {}
}
```

Например:

```typescript
class C {}

class B {
  constructor(private c: C) {}
}

class A {
  constructor(private b: B) {}
}
```

Без контейнера:

```typescript
const c = new C();
const b = new B(c);
const a = new A(b);
```

С контейнером:

```typescript
const a = container.resolve(A);
```

Контейнер самостоятельно:

1. создает `C`;
2. передает его в `B`;
3. создает `B`;
4. передает его в `A`;
5. возвращает готовый объект `A`.

---

# Как это реализовано в NestJS

Когда разработчик пишет:

```typescript
@Injectable()
export class UserService {
  constructor(
    private readonly repo: UserRepository,
  ) {}
}
```

NestJS при запуске приложения:

1. Находит классы с `@Injectable()`.
2. Регистрирует их в DI-контейнере.
3. Строит граф зависимостей.
4. Создает объекты в правильном порядке.
5. Передает зависимости через конструктор.

Разработчику больше не нужно самостоятельно писать `new UserRepository()`.

**Практический вывод, зачем всё это нужно:** DI делает код **тестируемым** (можно подменять реальные зависимости на mock/fake-объекты в тестах), **гибким** (легко заменить одну реализацию на другую, не переписывая зависимый код) и **слабосвязанным** (loosely coupled) — классы не привязаны жёстко к конкретным реализациям друг друга, а работают через абстракции/интерфейсы.

# Inversion of Control (IoC)

>**IoC (Inversion of Control)** — архитектурный принцип, согласно которому управление созданием объектов передается внешнему механизму.

Без IoC:

```Typescript
const repo = new UserRepository();
const service = new UserService(repo);
```

Разработчик самостоятельно управляет созданием объектов.

С IoC:

```Typescript
@Injectable()
class UserService {
  constructor(private repo: UserRepository) {}
}
```

Разработчик лишь сообщает, какие зависимости необходимы.

Созданием объектов занимается специальный механизм — **DI-контейнер**.

---
# Почему это называется "Инверсия управления"

Раньше программист сам писал:

```typescript
new UserRepository()
```

Теперь он этого не делает.

Он лишь говорит:

> "Мне нужен объект `UserRepository`."

Кто и когда его создаст — решает контейнер.

---
# Dependency Inversion Principle (DIP) и Dependency Injection (DI)

Эти понятия часто путают.

## Dependency Inversion Principle (DIP)

Это **принцип проектирования** из SOLID.

Он говорит:

> **Модули верхнего уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.**

Пример плохой зависимости:

```Typescript
class UserService {
  private db = new MySQLDatabase();
}
```

`UserService` напрямую зависит от конкретной реализации базы данных.

---

## Dependency Injection (DI)

Это **техника**, которая позволяет реализовать принцип DIP.

Вместо создания объекта внутри класса зависимость передается извне.

Именно поэтому можно сказать:

> **DI — один из способов реализации DIP.**

---

# Почему лучше зависеть от абстракций

Вместо:

```Typescript
class UserService {
  constructor(private db: MySQLDatabase) {}
}
```

лучше:

```Typescript
interface Database {
  save(data: string): void;
}

class MySQLDatabase implements Database {}

class PostgreSQLDatabase implements Database {}

class UserService {
  constructor(private db: Database) {}
}
```

Теперь `UserService` вообще не знает, какая именно база данных используется.

Если завтра потребуется заменить MySQL на PostgreSQL или MongoDB, потребуется изменить только реализацию зависимости, а сам сервис останется неизменным.

---
# Преимущества Dependency Injection

- **Слабая связанность (Loose Coupling)** между классами.
- Простая замена реализаций (например, MySQL → PostgreSQL).
- Соблюдение принципа DIP.
- Удобное модульное тестирование (можно легко подменять зависимости моками).
- Высокая расширяемость приложения.
- Более чистая и поддерживаемая архитектура.

---
# Недостатки

- Увеличивается количество классов и интерфейсов.
- Появляется дополнительный уровень абстракции.
- В небольших проектах использование DI может быть избыточным.

---
# Что важно запомнить для собеседования

- **Dependency Injection** — техника передачи зависимостей извне.
- **DIP** — принцип SOLID, который рекомендует зависеть от абстракций.
- **DI** помогает реализовать **DIP**.
- Самый распространенный способ внедрения зависимостей — **Constructor Injection**.
- **IoC** означает передачу управления созданием объектов внешнему механизму.
- **DI-контейнер** автоматически создает объекты, управляет их жизненным циклом и внедряет зависимости.
- В **NestJS** DI и IoC реализованы встроенным DI-контейнером, поэтому разработчику не нужно вручную создавать зависимости через `new`.
