# ЧАСТЬ 4. YAGNI (You Aren't Gonna Need It)

**Формулировка:** "Тебе это не понадобится" — не добавляй функциональность заранее, "на будущее", если она не нужна прямо сейчас, для решения текущей задачи. Предположения о будущих потребностях часто не сбываются, а лишний код увеличивает сложность, время разработки и площадь для багов.

### ❌ Плохо — избыточная гибкость "про запас"

```javascript
class UserService {
  constructor(options = {}) {
    this.cacheEnabled = options.cacheEnabled ?? false;
    this.cacheStrategy = options.cacheStrategy ?? "lru";
    this.cacheSize = options.cacheSize ?? 100;
    this.retryEnabled = options.retryEnabled ?? false;
    this.retryCount = options.retryCount ?? 3;
    this.retryDelay = options.retryDelay ?? 1000;
    this.loggingEnabled = options.loggingEnabled ?? false;
    this.loggingLevel = options.loggingLevel ?? "info";
    this.pluginsEnabled = options.pluginsEnabled ?? false;
    this.plugins = options.plugins ?? [];
    // ни кэширование, ни retry, ни плагины сейчас реально НЕ используются
    // и не запрашивались — просто "на всякий случай, вдруг понадобится"
  }

  getUser(id) {
    console.log(`Получаем пользователя ${id}`);
  }
}
```

**Проблема:** вся эта конфигурация (кэш, повторы запросов, плагины, логирование) добавлена "на будущее", без реального текущего требования. Это увеличивает сложность класса, площадь для потенциальных багов, время, потраченное на разработку и тестирование функциональности, которая, возможно, никогда не понадобится — а если и понадобится, то, скорее всего, не в том виде, в котором её "предугадали" заранее.

### ✅ Хорошо — реализуем только то, что реально нужно сейчас

```javascript
class UserService {
  getUser(id) {
    console.log(`Получаем пользователя ${id}`);
  }
}

// Когда РЕАЛЬНО понадобится кэширование — добавим его тогда,
// с учётом актуальных на тот момент требований, а не гипотетических
```

**Важный нюанс YAGNI:** принцип не означает "не думай о будущем вообще" или "пиши код, который невозможно будет расширить". Он означает конкретно — **не пиши код для функциональности, которая ещё не запрошена и не нужна прямо сейчас**. Хорошая архитектура (разделение ответственности, слабая связанность — то, что как раз обеспечивают SOLID/DRY) сама по себе облегчает добавление нового функционала позже, когда он реально понадобится — не нужно заранее пытаться предугадать все возможные будущие требования и закладывать под них код już сейчас.
