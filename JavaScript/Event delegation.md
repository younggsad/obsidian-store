### Всплытие событий (event bubbling) — основа механизма

>Когда происходит событие на каком-то элементе (например, клик на `<li>`), оно **не останавливается** на этом элементе — оно "всплывает" вверх по дереву DOM: сначала срабатывает обработчик на самом элементе, потом на его родителе, потом на родителе родителя, и так далее вплоть до `document`.

```html
<ul id="list">
  <li>Item 1</li>
  <li>Item 2</li>
</ul>
```

```js
document.getElementById('list').addEventListener('click', () => {
  console.log('Клик где-то внутри списка!');
});
```

Если кликнуть по `<li>Item 1</li>` — событие клика произойдёт **сначала** на `<li>`, но так как у самого `<li>` обработчика нет, оно **всплывёт** до `<ul>`, где обработчик есть — и он сработает, даже несмотря на то, что клик был не по самому `<ul>`, а по его дочернему элементу.

### Что такое event delegation

>**Делегирование событий** — это техника, которая **использует** это всплытие: вместо того чтобы вешать отдельный обработчик на **каждый** дочерний элемент, вешают **один** обработчик на **общего родителя**, а внутри него определяют, на каком именно дочернем элементе произошло событие — через `event.target`.

```js
document.getElementById('list').addEventListener('click', (event) => {
  if (event.target.tagName === 'LI') {
    console.log('Кликнули по:', event.target.textContent);
  }
});
```

`event.target` — это **конкретный элемент**, по которому реально кликнули (в отличие от `event.currentTarget`, который всегда равен элементу, на котором **висит** обработчик — в данном случае всегда `<ul>`).

### Зачем это нужно — практические причины

**1. Производительность на больших/динамических списках.** Если у тебя список из 1000 элементов, вешать 1000 отдельных обработчиков — заметная нагрузка на память и инициализацию. Один обработчик на родителе — намного дешевле.

**2. Работа с динамически добавляемыми элементами** — это самая важная практическая причина. Представим:

```js
// Плохой подход — обработчики на каждый элемент отдельно
document.querySelectorAll('li').forEach(li => {
  li.addEventListener('click', () => console.log('clicked'));
});

// Проблема: если позже добавить новый <li> в список динамически —
// у него НЕ будет обработчика клика, потому что querySelectorAll
// прошёлся только по элементам, существовавшим на момент вызова
const newLi = document.createElement('li');
list.appendChild(newLi); // у этого элемента нет обработчика!
```

С делегированием эта проблема решается сама собой — обработчик висит на родителе, который существовал всегда, и работает для **любых** дочерних элементов, даже тех, что появились в DOM **после** того как обработчик был назначен:

```js
document.getElementById('list').addEventListener('click', (event) => {
  if (event.target.tagName === 'LI') {
    console.log('Клик сработает даже для новых элементов!');
  }
});

const newLi = document.createElement('li');
newLi.textContent = 'New Item';
list.appendChild(newLi);
// Клик по newLi всё равно сработает — обработчик на родителе видит всплытие от него
```

### Связь с React

Это, кстати, объясняет один из внутренних механизмов React (частично изменился в React 17+, но идея та же): React исторически вешал **один** обработчик событий на корень приложения (или на `document`), а не по одному на каждый элемент с `onClick` — именно ради производительности, используя тот же принцип делегирования "под капотом", хотя разработчик пишет `onClick` вроде бы на каждом отдельном элементе.

### Практический нюанс — `event.target` vs `event.currentTarget`

```js
parent.addEventListener('click', (event) => {
  console.log(event.target);        // конкретный элемент, по которому кликнули
  console.log(event.currentTarget); // всегда parent — элемент, на котором висит обработчик
});
```

Это часто путают на собесах — стоит запомнить чётко: `target` — "где реально кликнули", `currentTarget` — "где висит обработчик, который сейчас выполняется".
