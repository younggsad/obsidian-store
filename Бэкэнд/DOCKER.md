### Проблема, которую решает Docker

>Классическая проблема разработки: "у меня на компьютере работает, а на сервере — нет" — из-за разницы версий Node.js, операционных систем, установленных библиотек и системных зависимостей между машиной разработчика и сервером.

>**Docker** решает это через **контейнеризацию** — упаковку приложения **вместе со всем окружением**, необходимым для его работы (нужная версия Node.js, системные библиотеки, конфигурация) в единый переносимый пакет — **контейнер**, который будет работать **одинаково** на любой машине, где установлен Docker, независимо от того, что установлено на самой машине.

### Image vs Container — ключевое различие

>**Image (образ)** — это **шаблон, чертёж** — неизменяемый "снимок" файловой системы и настроек, из которого создаются контейнеры. Похоже на класс в ООП.

>**Container (контейнер)** — это **работающий экземпляр** образа — реально запущенный процесс со своим изолированным окружением. Похоже на объект (экземпляр класса) в ООП — из одного образа можно запустить сколько угодно независимых контейнеров.

```bash
docker build -t my-app .        # создать образ из Dockerfile
docker run my-app               # запустить контейнер из образа
docker run my-app      # запустить ЕЩЁ ОДИН независимый контейнер из того же образа
```

### Dockerfile — инструкция для сборки образа

```dockerfile
FROM node:20-alpine     # базовый образ — Node.js версии 20 на лёгкой Alpine Linux

WORKDIR /app                # рабочая директория внутри контейнера

COPY package*.json ./       # сначала копируем только файлы зависимостей
RUN npm install             # устанавливаем зависимости (кэшируется, если package.json не менялся)

COPY . .                    # копируем весь остальной код проекта

EXPOSE 3000                 # документирует, какой порт слушает приложение

CMD ["npm", "start"]        # команда, которая выполняется при запуске контейнера
```

**Важный практический приём** — копирование `package*.json` **до** копирования всего остального кода: Docker кэширует **каждый слой (layer)** сборки — если `package.json` не изменился с прошлой сборки, шаг `npm install` **не будет выполняться заново**, что сильно ускоряет пересборку образа при изменении только кода приложения (без изменения зависимостей).

### Docker Compose — управление несколькими контейнерами

Реальное приложение обычно состоит из **нескольких** сервисов — сам backend, база данных, возможно Redis для кэша. **Docker Compose** позволяет описать все эти сервисы в одном файле и запускать/останавливать их вместе одной командой.

```yaml
# docker-compose.yml
version: '3.8'

services:
  app:
    build: .
    ports:
      - "3000:3000"
    depends_on:
      - db
    environment:
      - DATABASE_URL=postgres://user:pass@db:5432/mydb

  db:
    image: postgres:16
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:
```

```bash
docker-compose up    # поднимает ВСЕ сервисы сразу, в правильном порядке (учитывая depends_on)
docker-compose down  # останавливает и удаляет все контейнеры
```

**Ключевые понятия из примера:**

- **`ports: "3000:3000"`** — проброс порта: "порт 3000 на хост-машине" → "порт 3000 внутри контейнера".
- **`volumes`** — постоянное хранилище данных, которое **не удаляется** при пересоздании контейнера (критично для баз данных — иначе все данные исчезали бы при каждом перезапуске контейнера).
- **`depends_on`** — указывает Docker Compose, в каком порядке запускать сервисы (сначала `db`, потом `app`).
- Сервисы внутри одной Compose-сети могут обращаться друг к другу **по имени сервиса** как по hostname (`db:5432`, а не `localhost:5432`) — Docker Compose автоматически настраивает внутреннюю сеть между контейнерами.
## Image (образ)

**Что это на самом деле:** образ — это **набор слоёв (layers)**, каждый из которых — это разница (diff) в файловой системе относительно предыдущего слоя. Каждая инструкция в `Dockerfile` (`FROM`, `RUN`, `COPY`) создаёт **новый слой**.

```dockerfile
FROM node:20-alpine   # слой 1 — базовая ОС + Node.js
COPY package*.json ./  # слой 2 — файлы зависимостей
RUN npm install         # слой 3 — установленные node_modules
COPY . .                # слой 4 — код приложения
```

**Слои кэшируются и переиспользуются** — если ты изменишь только код приложения (последний `COPY . .`), Docker **не** будет пересобирать слои 1-3 заново, используя закэшированную версию — именно поэтому важен **порядок** инструкций в Dockerfile: то, что меняется реже (установка зависимостей), должно идти **раньше** того, что меняется часто (код приложения) — это уже разбирали в backend-конспекте, здесь дополняем механикой послойного устройства.

Образы также могут **переиспользовать общие слои** между разными образами — если у тебя 10 разных Docker-образов, все основанные на `node:20-alpine`, этот базовый слой физически хранится на диске **один раз**, а не 10 раз.

## Container (контейнер)

**Что это на самом деле:** контейнер — это **работающий процесс**, использующий образ как read-only базу, плюс **тонкий, изменяемый слой поверх (writable layer)**, куда пишутся любые изменения, сделанные во время работы контейнера (новые/изменённые файлы).

**Технически контейнер строится на возможностях самого Linux-ядра:**

- **Namespaces** — изолируют то, что процесс **видит** (свою собственную файловую систему, сетевые интерфейсы, список процессов) — контейнер "думает", что он один в системе, хотя физически на хосте могут работать десятки контейнеров.
- **cgroups (control groups)** — ограничивают, **сколько** ресурсов (CPU, память) может использовать процесс.

**Важное отличие от виртуальных машин:** контейнеры **не эмулируют** отдельное "железо" и не запускают отдельное полноценное ядро ОС — все контейнеры на одной машине **используют одно и то же ядро хоста**, только изолированы друг от друга через namespaces/cgroups — поэтому контейнеры **гораздо легче и быстрее** запускаются, чем виртуальные машины (секунды против минут), но при этом менее изолированы на самом глубоком уровне (уязвимость в ядре хоста теоретически может повлиять на все контейнеры).

**Если удалить контейнер** — writable-слой (все изменения, сделанные во время работы) **теряется**, если данные не были явно вынесены в volume.

## Volume (том)

**Проблема, которую решает volume:** контейнеры **эфемерны** (ephemeral) — их пересоздают, обновляют, удаляют регулярно. Если данные (например, база данных) хранятся **внутри** writable-слоя контейнера — при пересоздании контейнера **все данные будут потеряны**.

**Volume** — механизм, который выносит данные **за пределы** жизненного цикла конкретного контейнера, в отдельное, постоянное хранилище на хост-машине (или в специальном управляемом Docker пространстве).

```bash
docker run -v pgdata:/var/lib/postgresql/data postgres
# "pgdata" — именованный volume, физически хранится Docker'ом отдельно от контейнера
# "/var/lib/postgresql/data" — путь ВНУТРИ контейнера, куда этот volume "примонтирован"
```

Даже если контейнер с PostgreSQL будет удалён и создан заново — если он снова подключит **тот же** volume `pgdata`, все данные окажутся на месте, потому что они физически хранились **отдельно** от самого контейнера.

**Bind mount** — альтернативный, более "прямой" способ: монтирование **конкретной папки хост-машины** напрямую внутрь контейнера (`-v /home/user/code:/app`) — часто используется в разработке, чтобы изменения кода на компьютере разработчика сразу отражались внутри работающего контейнера, без пересборки образа.

## Network (сеть)

По умолчанию Docker создаёт изолированную **виртуальную сеть** для контейнеров. Контейнеры в **одной** пользовательской сети (created network, например через `docker-compose`, который создаёт сеть автоматически) могут обращаться друг к другу **по имени контейнера/сервиса** как по hostname:

```yaml
services:
  app:
    # ...
  db:
    # ...
```

Внутри контейнера `app` можно обратиться к базе данных просто как `db:5432` — Docker сам настраивает внутренний DNS, разрешающий имена сервисов в их внутренние IP-адреса в пределах этой сети. Контейнеры в **разных**, не связанных сетях, по умолчанию **не видят** друг друга — это дополнительный уровень изоляции.

## Dockerfile — краткое напоминание ключевых инструкций

```dockerfile
FROM <base_image>     # базовый образ, с которого начинаем
WORKDIR <path>          # рабочая директория внутри контейнера для последующих команд
COPY <src> <dest>       # копирование файлов с хоста в образ
RUN <command>            # выполнение команды ВО ВРЕМЯ СБОРКИ образа (например, npm install)
ENV <key>=<value>        # переменная окружения, доступная во время сборки и в запущенном контейнере
EXPOSE <port>             # документирует, какой порт слушает приложение (не публикует его сам по себе!)
CMD ["executable", "arg"] # команда, выполняемая при ЗАПУСКЕ контейнера (можно переопределить при docker run)
ENTRYPOINT ["executable"] # похоже на CMD, но сложнее переопределить — обычно используют вместе:
                            # ENTRYPOINT задаёт "неизменную" команду, CMD — аргументы по умолчанию к ней
```

**`RUN` vs `CMD`/`ENTRYPOINT`** — частый вопрос: `RUN` выполняется **один раз, во время сборки образа**, результат "запекается" в сам образ (новый слой). `CMD`/`ENTRYPOINT` выполняются **каждый раз при запуске** контейнера из готового образа — это не часть сборки, а то, что происходит в момент `docker run`.

## Docker Compose — зачем нужен и как работает (расширенно)

_(Базовый пример уже приведён в backend-конспекте.)_ Дополнительно — ключевые практические возможности:

```yaml
services:
  app:
    build: .
    depends_on:
      db:
        condition: service_healthy # ждать не просто запуска db, а именно готовности принимать соединения
    restart: unless-stopped         # автоматически перезапускать контейнер при падении

  db:
    image: postgres:16
    healthcheck:                    # определяет, как проверить, что сервис действительно "готов"
      test: ["CMD", "pg_isready"]
      interval: 5s
      timeout: 3s
      retries: 5
```

**`healthcheck`** — важный практический момент: просто "контейнер запустился" (`docker start`) не значит, что **приложение внутри** уже готово принимать запросы (базе данных, например, нужно время на инициализацию). `depends_on` без `condition: service_healthy` гарантирует только **порядок запуска контейнеров**, но не "готовность" сервиса внутри — именно поэтому в реальных проектах часто настраивают `healthcheck`, чтобы зависимые сервисы действительно дожидались полной готовности, а не просто факта запуска процесса.
