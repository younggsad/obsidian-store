>**Аутентификация (authentication)** — проверка **личности**: "кто ты?" (логин/пароль, токен). 
>**Авторизация (authorization)** — проверка **прав**: "что тебе разрешено делать?" (может ли этот пользователь удалить чужой пост).

Это разные вещи, которые часто путают — аутентификация всегда идёт **до** авторизации: сначала система выясняет, кто ты, потом — что тебе можно.

### Сессии (session-based auth)

1. Пользователь логинится (отправляет логин/пароль).
2. Сервер проверяет данные, создаёт **сессию** — запись в своей базе данных/памяти (обычно Redis) с уникальным ID.
3. Сервер отправляет клиенту этот ID сессии через **cookie**.
4. При каждом следующем запросе браузер **автоматически** прикрепляет эту cookie.
5. Сервер смотрит на ID сессии, находит соответствующую запись в своём хранилище, узнаёт, кто это.

**Особенность:** состояние (кто залогинен) хранится **на сервере** — сервер должен где-то держать все активные сессии.

### JWT (JSON Web Token) — token-based auth

1. Пользователь логинится.
2. Сервер проверяет данные и генерирует **JWT-токен** — самодостаточную строку, содержащую закодированную информацию о пользователе (например, `{ userId: 42, role: "admin" }`), подписанную секретным ключом сервера.
3. Клиент сохраняет токен (обычно в `localStorage` или cookie) и отправляет его в заголовке `Authorization: Bearer <token>` при каждом запросе.
4. Сервер **проверяет подпись** токена (не обращаясь к базе данных или общему хранилищу) — если подпись верна, значит токен не подделан, и серверу можно доверять информации внутри него.

**Структура JWT** — три части, разделённые точками: `header.payload.signature`

```
eyJhbGciOiJIUzI1NiJ9.eyJ1c2VySWQiOjQyfQ.SflKxwRJSMeKKF2QT4fw...
```

- **Header** — метаданные (алгоритм подписи)
- **Payload** — сами данные (userId, роль, срок действия) — **не зашифрованы**, а просто закодированы в Base64 — это важно: любой может **прочитать** содержимое JWT, просто декодировав Base64, поэтому **нельзя** класть в payload секретные данные (пароли и подобное). Подпись защищает от **подделки**, а не от **чтения**.
- **Signature** — подпись, вычисленная сервером с использованием секретного ключа — именно она гарантирует, что токен не был изменён клиентом.

**Ключевое отличие JWT от сессий — stateless:** серверу **не нужно** хранить список активных токенов где-либо — вся необходимая информация уже находится внутри самого токена, проверка сводится к проверке подписи. Это упрощает горизонтальное масштабирование (любой из нескольких серверов может проверить токен, не обращаясь к общей базе сессий).

**Минус JWT** — токен нельзя "отозвать" (revoke) так же просто, как удалить запись сессии из базы — раз выданный токен остаётся валидным до истечения срока действия, даже если пользователя, например, заблокировали. Решают это через короткий срок жизни токена (`access token`, обычно 15 минут) + отдельный `refresh token` (более долгоживущий, для получения нового `access token` без повторного логина).

### OAuth — авторизация через сторонний сервис ("Войти через Google")

>**OAuth** — протокол, позволяющий приложению получить **ограниченный доступ** к данным пользователя на другом сервисе (Google, GitHub), **не получая его пароль**. Упрощённый поток (Authorization Code flow):

1. Пользователь нажимает "Войти через Google" на сайте.
2. Его перенаправляют на страницу Google, где он логинится **напрямую в Google**, не вводя пароль на сайте разработчика.
3. Google спрашивает пользователя: "Разрешить приложению X доступ к твоему имени и email?"
4. После согласия Google возвращает приложению **код авторизации**, который приложение обменивает на **токен доступа**, дающий право запрашивать разрешённые данные о пользователе у Google.

Ключевое преимущество: пароль пользователя от Google **никогда не попадает** на сервер стороннего приложения — снижается риск утечки паролей.
