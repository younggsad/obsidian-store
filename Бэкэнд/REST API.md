### Что такое REST

>**REST (Representational State Transfer)** — архитектурный стиль (не строгий протокол и не технология) для построения API, предложенный Роем Филдингом в 2000 году. Описывает набор принципов, при соблюдении которых API считается "RESTful".

### Основные принципы REST

**1. Клиент-серверная архитектура** — чёткое разделение: клиент отвечает за UI, сервер — за хранение данных и бизнес-логику, они независимы друг от друга и общаются только через API.

**2. Stateless (без состояния)** — сервер не хранит информацию о состоянии клиента между запросами. Каждый запрос должен содержать **всю** необходимую информацию для его обработки (например, токен авторизации в каждом запросе, а не "сервер помнит, что ты залогинен" из предыдущего запроса).

**3. Ресурсы и их представления** — всё в API — это **ресурс** (пользователь, заказ, товар), у каждого ресурса есть уникальный **URL** (`/users/42`), и клиент работает не с самим ресурсом напрямую, а с его **представлением** (обычно JSON).

**4. Единообразный интерфейс (Uniform Interface)** — использование стандартных HTTP-методов для стандартных операций (это и есть CRUD через HTTP-методы, см. таблицу выше).

**5. Кэшируемость** — ответы должны явно помечать себя как кэшируемые или нет (через заголовки типа `Cache-Control`), чтобы клиент мог переиспользовать данные без повторного запроса.

**6. Многослойная система (Layered System)** — клиент не обязан знать, общается ли он напрямую с сервером или через промежуточные слои (балансировщики нагрузки, прокси, кэширующие серверы) — это не должно влиять на то, как клиент работает с API.

### Проектирование REST URL — практические конвенции

```
GET    /users          → получить список всех пользователей
GET    /users/42       → получить конкретного пользователя с id=42
POST   /users          → создать нового пользователя
PUT    /users/42       → полностью заменить пользователя 42
PATCH  /users/42       → частично обновить пользователя 42
DELETE /users/42       → удалить пользователя 42

GET    /users/42/orders  → получить все заказы пользователя 42 (вложенный ресурс)
```

**Правила хорошего REST API:**

- URL называют **существительными во множественном числе** (`/users`, а не `/getUsers` или `/user`) — само действие уже выражено HTTP-методом, не нужно дублировать его в URL.
- Используют **вложенность** для связанных ресурсов (`/users/42/orders`), но не углубляются слишком сильно (`/users/42/orders/5/items/3/reviews` — уже избыточно, лучше сделать отдельный эндпоинт).
- **Пагинация** для списков: `/users?page=2&limit=20` или `/users?offset=20&limit=20` — чтобы не отдавать миллион записей одним ответом.
- **Фильтрация/сортировка** через query-параметры: `/users?role=admin&sort=createdAt`.
- **Версионирование API**: `/api/v1/users`, `/api/v2/users` — чтобы можно было менять API, не ломая клиентов, которые ещё используют старую версию.

### REST vs GraphQL (частый сравнительный вопрос)

>**REST** — множество отдельных эндпоинтов, каждый возвращает **фиксированную** структуру данных.

**Проблема REST — over-fetching и under-fetching:**

- **Over-fetching** — эндпоинт `/users/42` возвращает **все** поля пользователя, даже если клиенту нужно только имя — лишние данные передаются впустую.
- **Under-fetching** — чтобы получить пользователя **и** его заказы, нужно сделать **два** отдельных запроса (`/users/42` и `/users/42/orders`), потому что REST-эндпоинт возвращает только один тип ресурса.

>**GraphQL** — единый эндпоинт (`/graphql`), где клиент **сам описывает**, какие именно поля и связанные данные ему нужны, в одном запросе:

```graphql
query {
  user(id: 42) {
    name
    orders {
      id
      total
    }
  }
}
```

Сервер вернёт **ровно** те поля, что запрошены — ни больше, ни меньше, и заберёт связанные `orders` в том же запросе, без отдельного round-trip.

**Когда что выбирать (практическое правило):**

- **REST** — проще в реализации, лучше кэшируется на уровне HTTP (`GET`-запросы кэшируются браузерами/CDN "из коробки"), стандартизирован, большинство разработчиков с ним знакомы — хороший выбор для большинства обычных проектов.
- **GraphQL** — лучше для сложных, тесно связанных данных с множеством вложенных сущностей, особенно когда разные клиенты (веб/мобильный) нуждаются в разных наборах полей — но сложнее в реализации на сервере, сложнее кэшировать, требует больше инфраструктуры (резолверы, схема).
