# ЧАСТЬ 5. HTTP COOKIE

## 5.1 Зачем нужны cookie

>Так как HTTP — **stateless** протокол (не помнит ничего между запросами), нужен механизм, позволяющий серверу "узнавать" клиента при повторных запросах — например, чтобы не заставлять пользователя логиниться заново на каждой странице. 

>**Cookie** — один из основных механизмов решения этой проблемы.

>**Cookie** — небольшой фрагмент данных (обычно до 4КБ), который сервер просит браузер сохранить и **автоматически** отправлять обратно с каждым последующим запросом к этому же домену.

## 5.2 Установка cookie сервером

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Max-Age=3600; Path=/; HttpOnly; Secure; SameSite=Strict
```

Браузер сохраняет эту cookie и автоматически прикладывает её к последующим запросам к тому же домену:

```http
GET /api/profile HTTP/1.1
Cookie: sessionId=abc123
```

## 5.3 Атрибуты cookie

|Атрибут|Значение|
|---|---|
|`Max-Age` / `Expires`|время жизни cookie (в секундах / конкретная дата); без них — **session cookie**, удаляется при закрытии браузера|
|`Path`|путь, для которого cookie действительна (`/` — весь сайт, `/admin` — только под-раздел)|
|`Domain`|домен, для которого cookie действительна (можно расширить на поддомены)|
|`HttpOnly`|cookie **недоступна через JavaScript** (`document.cookie` её не увидит) — важнейшая защита от XSS-атак, крадущих cookie через внедрённый вредоносный скрипт|
|`Secure`|cookie передаётся **только по HTTPS**, никогда по незашифрованному HTTP|
|`SameSite`|контролирует отправку cookie при кросс-доменных запросах (защита от CSRF, см. ниже)|

### `SameSite` — три значения

```
— cookie НИКОГДА не отправляется при переходе с другого сайта (даже по клику на ссылку извне)
SameSite=Strict 

— cookie отправляется при обычной навигации (переход по ссылке), но НЕ при фоновых запросах с других сайтов (например, форма, автоматически отправляемая с чужого домена) — значение ПО УМОЛЧАНИЮ в современных браузерах
SameSite=Lax  

— cookie отправляется всегда, при любых кросс-доменных запросах (требует обязательного Secure)  
SameSite=None   
```

## 5.4 Виды cookie

- **Session cookie** — без `Max-Age`/`Expires`, удаляется автоматически при закрытии браузера.
- **Persistent cookie** — с заданным сроком жизни, сохраняется между сессиями браузера (например, "запомнить меня").
- **First-party cookie** — установлена доменом, который пользователь непосредственно посещает.
- **Third-party cookie** — установлена **другим** доменом, обычно встроенным в текущую страницу через iframe/скрипт (классический пример — рекламные/трекинговые cookie); современные браузеры всё активнее их ограничивают из соображений приватности.

## 5.5 Практический пример — аутентификация через cookie

```javascript
// Сервер (Node.js/Express) — установка cookie после успешного логина
app.post('/login', (req, res) => {
  // ...проверка логина/пароля...
  res.cookie('sessionId', 'abc123', {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    maxAge: 3600000, // 1 час в миллисекундах
  });
  res.json({ success: true });
});
```

```javascript
// Последующие запросы автоматически несут cookie — сервер может проверить сессию
app.get('/profile', (req, res) => {
  const sessionId = req.cookies.sessionId; // читаем cookie на сервере
  // ...найти сессию по sessionId, определить пользователя...
});
```

Клиентский JS **не может** прочитать эту cookie через `document.cookie`, если установлен `HttpOnly` — это специально сделано, чтобы вредоносный скрипт (например, внедрённый через XSS-уязвимость) не смог украсть токен сессии.

## 5.6 CSRF (Cross-Site Request Forgery) — атака, связанная с cookie

**Суть атаки:** пользователь залогинен на `bank.com` (у него есть валидная cookie сессии). Он заходит на вредоносный сайт `evil.com`, который автоматически отправляет запрос к `bank.com/transfer` (например, через скрытую форму) — браузер **автоматически** приложит cookie от `bank.com` к этому запросу (потому что cookie привязаны к домену, а не к тому, "откуда" пришёл запрос), и банк может выполнить перевод, думая, что запрос пришёл от легитимного пользователя.
