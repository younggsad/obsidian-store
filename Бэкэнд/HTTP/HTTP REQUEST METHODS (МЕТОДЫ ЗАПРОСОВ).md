# ЧАСТЬ 2. HTTP REQUEST METHODS (МЕТОДЫ ЗАПРОСОВ)

## 2.1 Общее понятие

>**Метод (method)** — указывает **действие**, которое клиент хочет выполнить над ресурсом на сервере. Является частью REST-архитектурного стиля, где методы соответствуют CRUD-операциям (Create, Read, Update, Delete).

## 2.2 Основные методы

### GET — получить данные

```http
GET /api/users/1 HTTP/1.1
```

- Используется для **чтения** данных, ничего не изменяет на сервере.
- Не должен иметь тела запроса (по стандарту — хотя технически некоторые серверы его допускают, это не рекомендуется).
- Параметры передаются через **query string** в URL: `/api/users?page=2&limit=10`.
- **Кэшируется** браузером по умолчанию.
- **Идемпотентен** (см. 2.5) и **безопасен** (safe — не изменяет состояние сервера).

### POST — создать новый ресурс / отправить данные

```http
POST /api/users HTTP/1.1
Content-Type: application/json

{"name": "Аня"}
```

- Используется для **создания** нового ресурса или отправки данных, которые должны быть обработаны сервером (форма, файл, произвольное действие).
- Данные передаются в **теле** запроса.
- **НЕ кэшируется** по умолчанию.
- **НЕ идемпотентен** — повторный одинаковый `POST` обычно создаёт **ещё один** ресурс (например, два одинаковых заказа при двойном клике на "Отправить").

### PUT — полностью заменить ресурс

```http
PUT /api/users/1 HTTP/1.1
Content-Type: application/json

{"name": "Аня", "email": "anna@new.com", "age": 21}
```

- Заменяет **весь** ресурс целиком переданными данными — если какое-то поле не передано, оно может быть затёрто/сброшено (зависит от реализации сервера, но по семантике HTTP — именно полная замена).
- **Идемпотентен** — повторная отправка одного и того же `PUT` приводит к одинаковому результату (ресурс просто будет заменён теми же данными ещё раз).

### PATCH — частично обновить ресурс

```http
PATCH /api/users/1 HTTP/1.1
Content-Type: application/json

{"email": "anna@new.com"}
```

- Обновляет **только указанные** поля, остальные поля ресурса остаются нетронутыми.
- По строгой семантике HTTP-стандарта не обязан быть идемпотентным (хотя на практике часто реализуется идемпотентно).

### DELETE — удалить ресурс

```http
DELETE /api/users/1 HTTP/1.1
```

- Удаляет указанный ресурс.
- **Идемпотентен** — повторное удаление уже удалённого ресурса обычно просто возвращает соответствующий статус (например, `404`), но не вызывает побочных эффектов повторно.

## 2.3 Менее часто используемые методы

```http
HEAD /api/users/1 HTTP/1.1
```

Идентичен `GET`, но сервер возвращает **только заголовки, без тела ответа** — используется, чтобы проверить существование ресурса, его размер, дату изменения, не скачивая сам контент.

```http
OPTIONS /api/users HTTP/1.1
```

Запрашивает, какие методы/заголовки поддерживает сервер для конкретного ресурса — **ключевой метод в механизме CORS** (браузер автоматически посылает "preflight"-запрос `OPTIONS` перед "небезопасными" кросс-доменными запросами, чтобы проверить разрешение сервера).

```http
TRACE   —  возвращает запрос обратно клиенту как есть, для диагностики (редко используется, часто отключён из соображений безопасности)

CONNECT — устанавливает туннель к серверу, используется для HTTPS через прокси
```

|Метод|Назначение|Тело запроса|Идемпотентен|Безопасен (safe)|Кэшируется|
|---|---|---|---|---|---|
|GET|получить|нет|✅|✅|✅|
|POST|создать/отправить|да|❌|❌|❌ (обычно)|
|PUT|заменить целиком|да|✅|❌|❌|
|PATCH|обновить частично|да|⚠️ (не гарантировано)|❌|❌|
|DELETE|удалить|обычно нет|✅|❌|❌|

|OPTIONS|узнать доступные методы|нет|✅|✅|❌|

## 2.5 Важные термины: идемпотентность и безопасность

- **Безопасный метод (safe)** — не изменяет состояние сервера (`GET`, `HEAD`, `OPTIONS`). Это не значит "защищённый от атак" — это значит "не имеющий побочных эффектов на сервере".
- **Идемпотентный метод** — повторный вызов с теми же параметрами приводит к **тому же результату** на сервере, что и первый вызов (хотя сам HTTP-ответ при этом может отличаться, например `404` при повторном `DELETE`). `GET`, `PUT`, `DELETE` идемпотентны; `POST` — нет.

**Практический смысл:** идемпотентные методы безопасно повторять при сетевых сбоях (например, автоматический ретрай запроса, если не пришёл ответ) — повтор не создаст дублирующих побочных эффектов. `POST` повторять автоматически нельзя без дополнительной защиты (например, idempotency key) — иначе можно случайно создать дубликат заказа/платежа.
