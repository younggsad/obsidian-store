## 1. Общая картина: путь запроса от браузера до сервера

Когда пользователь вводит `example.com` в адресную строку:

1. Браузер узнаёт **IP-адрес** сервера по доменному имени через **DNS**.
2. Устанавливается **TCP-соединение** с сервером по этому IP-адресу (three-way handshake).
3. Если сайт на HTTPS — устанавливается **TLS-соединение** поверх TCP (шифрование).
4. Браузер отправляет **HTTP-запрос**.
5. Сервер обрабатывает запрос и отправляет **HTTP-ответ**.
6. Браузер получает ответ (обычно HTML) и рендерит страницу, попутно запрашивая дополнительные ресурсы (CSS, JS, изображения) — каждый по такой же цепочке.

Дальше разберём каждый из этих шагов подробно.

## 2. DNS (Domain Name System)

>**Проблема, которую решает DNS:** компьютеры общаются через **IP-адреса** (числа вроде `192.0.2.1`), а человеку удобнее запоминать домены (`google.com`). DNS — распределённая система, "телефонная книга интернета": превращает доменные имена в IP-адреса.

**Как происходит DNS-резолвинг (по шагам):**

1. Браузер проверяет **свой локальный кэш** — не резолвил ли уже этот домен недавно.
2. Если нет — запрос идёт к **DNS-резолверу** (сервер провайдера или публичный, например `8.8.8.8`).
3. Резолвер обращается к **корневым серверам (root servers)** — они не знают конкретный IP, но знают, куда обратиться дальше (к серверам зоны `.com`).
4. **TLD-сервер** (зона `.com`) указывает на **авторитетный DNS-сервер**, ответственный конкретно за `example.com`.
5. Авторитетный сервер возвращает **IP-адрес**.
6. Результат **кэшируется** на время, заданное **TTL (Time To Live)** — чтобы не повторять процесс при каждом запросе.

**Основные типы DNS-записей:**

- **A** — домен → IPv4-адрес.
- **AAAA** — домен → IPv6-адрес.
- **CNAME** — домен → другой домен (алиас).
- **MX** — почтовый сервер домена.
- **TXT** — произвольный текст (верификация владения доменом, SPF/DKIM для email-безопасности).

**Практический вывод:** DNS-резолвинг добавляет задержку к первому обращению к домену — поэтому кэширование DNS важно для скорости загрузки (браузеры используют техники типа `dns-prefetch`, чтобы заранее резолвить домены, которые понадобятся).

## ## 3. Модели сети: OSI и TCP/IP

Есть две модели, описывающие "слои" сетевого взаимодействия — академическая **OSI** (7 уровней) и практическая **TCP/IP** (4 уровня, чаще используется в реальной разработке). 

Они описывают **одно и то же**, просто с разной степенью детализации: несколько верхних уровней OSI объединены в TCP/IP в один уровень. Разберём по уровням TCP/IP, снизу вверх, с указанием, какому уровню OSI это соответствует.

### 1. Канальный уровень (Link layer) — соответствует уровням 1-2 модели OSI (Физический + Канальный)

>Передача данных между устройствами в **одной** физической/локальной сети (Ethernet, Wi-Fi). 

Работает с **MAC-адресами**. Физический уровень OSI отвечает конкретно за передачу битов через физическую среду (кабели, радиоволны), канальный — за организацию их в кадры (frames) и коммутацию внутри локальной сети (switches).

### 2. Сетевой уровень (Internet layer) — соответствует уровню 3 модели OSI (Сетевой)

>Протокол **IP**, отвечает за **маршрутизацию** данных между разными сетями через интернет, используя **IP-адреса**.

IP разбивает данные на **пакеты (packets)** и обеспечивает их доставку от одного узла к другому, но **не гарантирует** ни порядок доставки, ни то, что пакет вообще дойдёт — эти гарантии добавляются уже на следующем уровне.

### 3. Транспортный уровень — соответствует уровню 4 модели OSI (Транспортный)

>Протоколы **TCP** и **UDP**, отвечают за доставку данных между конкретными приложениями (через порты) с разными гарантиями надёжности.

>**TCP (Transmission Control Protocol)** — обеспечивает **надёжную**, упорядоченную доставку:

- Устанавливает соединение перед передачей данных через **three-way handshake** (тройное рукопожатие):

```
Клиент → SYN → Сервер        
(клиент: "хочу подключиться")

Клиент ← SYN-ACK ← Сервер    
(сервер: "ок, готов, а ты?")

Клиент → ACK → Сервер        
(клиент: "да, начинаем")
```

- Гарантирует **правильный порядок** доставки и **повторно отправляет** потерянные пакеты.
- Используется там, где важна надёжность: загрузка веб-страниц (HTTP работает поверх TCP), передача файлов, email.

>**UDP (User Datagram Protocol)** — **не** устанавливает соединение, **не гарантирует** доставку и порядок — отправляет данные "как есть", быстро, без накладных расходов на подтверждения.

- Используется там, где скорость важнее надёжности: видеозвонки, онлайн-игры, стриминг (потерянный кадр видео лучше пропустить, чем ждать повторной отправки и тормозить весь поток).

**Частый вопрос на собесе:** 
_"Почему HTTP использует TCP, а не UDP?"_ 

— потому что для веб-страниц критично, чтобы **все** данные дошли и в правильном порядке (нельзя, чтобы часть HTML/JS-файла потерялась) 

— надёжность важнее минимальной задержки. 
Существует HTTP/3, работающий поверх **QUIC** — протокола, построенного на UDP, но с добавлением надёжности уже на уровне приложения (совмещает скорость UDP с гарантиями, похожими на TCP — более продвинутая тема).

### 4. Прикладной уровень (Application layer) — соответствует уровням 5-7 модели OSI (Сеансовый + Представления + Прикладной)

>Протоколы, с которыми напрямую работают приложения: **HTTP/HTTPS** (веб), **FTP** (передача файлов), **SMTP** (email), **WebSocket** (двусторонняя связь в реальном времени). 

Работают "поверх" TCP (или UDP), используя их для фактической передачи данных. В терминах OSI сюда же попадают: сеансовый уровень (установка/поддержание сеансов связи между приложениями) и уровень представления (форматирование и шифрование данных — например, TLS/SSL иногда относят именно сюда).

**Практический вывод:** OSI — скорее концептуальный, обучающий инструмент для понимания разделения ответственности в сети, чем то, что буквально реализовано "по слоям" в реальных системах. На практике (и на большинстве практических собеседований) чаще оперируют упрощённой 4-уровневой моделью TCP/IP, где верхние три уровня OSI объединены в один прикладной уровень.

## 4. IP-адреса, порты, NAT

### IP-адреса: IPv4 vs IPv6

>**IPv4** — привычный формат из четырёх чисел (`192.0.2.1`), всего около **4.3 миллиарда** уникальных адресов. Из-за роста числа устройств в интернете этого пространства уже **не хватает** — отсюда необходимость в NAT (ниже) и постепенном переходе на IPv6.

>**IPv6** — новый формат (`2001:0db8:85a3:0000:0000:8a2e:0370:7334`), пространство адресов астрономически больше (по факту — практически неисчерпаемо для обозримого будущего), что снимает необходимость в NAT в теории, хотя на практике IPv4+NAT всё ещё широко используется параллельно с постепенным внедрением IPv6.

### Порты

>IP-адрес указывает, **к какому устройству** обращаться, но одно устройство может одновременно работать с множеством разных сервисов (веб-сервер, почтовый сервер, база данных) — **порт** указывает, **к какому конкретно сервису/процессу** на этом устройстве обращаться.

```
192.0.2.1:443   → HTTPS-сервер на этом хосте
192.0.2.1:22    → SSH-сервер на этом же хосте
192.0.2.1:5432  → PostgreSQL на этом же хосте
```

**Стандартные порты, которые стоит помнить:** `80` (HTTP), `443` (HTTPS), `22` (SSH), `21` (FTP), `25` (SMTP), `5432` (PostgreSQL по умолчанию), `3306` (MySQL по умолчанию), `6379` (Redis по умолчанию), `27017` (MongoDB по умолчанию).

### NAT (Network Address Translation)

**Проблема:** IPv4-адресов ограниченное количество, а устройств в интернете больше. Большинство устройств в домашней/офисной сети имеют **приватные** IP-адреса (`192.168.x.x`, `10.x.x.x`), не видимые напрямую из интернета.

**Как работает:** роутер с **одним** публичным IP "транслирует" исходящие запросы всех устройств локальной сети через этот единственный адрес, запоминая, какое внутреннее устройство какой запрос отправило — чтобы правильно направить ответ обратно.

```
Компьютер (192.168.1.5) → Роутер (публичный IP: 203.0.113.5) → Интернет
```

**Побочный эффект:** устройства за NAT **не могут** напрямую принимать входящие соединения извне без дополнительной настройки (port forwarding) — попутно это даёт некоторый уровень защиты от прямого внешнего доступа к устройствам внутри локальной сети.

## 5. TCP vs UDP

>Оба — протоколы **транспортного уровня**, оба используют порты, но с принципиально разными гарантиями.

### TCP (Transmission Control Protocol)

>Обеспечивает **надёжную, упорядоченную** доставку данных.

>**Устанавливает соединение** перед передачей данных через **three-way handshake**:

```
Клиент → SYN → Сервер        
(клиент: "хочу подключиться")

Клиент ← SYN-ACK ← Сервер    
(сервер: "ок, готов, а ты?")

Клиент → ACK → Сервер        
(клиент: "да, начинаем")
```

>Гарантирует **правильный порядок** доставки и **повторно отправляет** потерянные пакеты (подтверждения доставки, нумерация пакетов).

**Используется там, где важна надёжность:** загрузка веб-страниц (HTTP работает поверх TCP), передача файлов, email — везде, где недопустима потеря или перепутанный порядок данных.

### UDP (User Datagram Protocol)

>**Не** устанавливает соединение, **не гарантирует** доставку и порядок — просто отправляет данные "как есть", быстро, без накладных расходов на подтверждения и повторные отправки.

**Используется там, где скорость важнее надёжности:** видеозвонки, онлайн-игры, стриминг (лучше пропустить потерянный кадр видео и показать следующий, чем ждать повторной отправки и тормозить весь поток), DNS-запросы (из-за их простоты и малого размера).

**Частый вопрос на собесе:** 
_"Почему HTTP использует TCP, а не UDP?"_

— потому что для веб-страниц критично, чтобы **все** данные дошли и в правильном порядке (нельзя, чтобы часть HTML/JS-файла потерялась). 

Существует HTTP/3, работающий поверх **QUIC** — протокола, построенного на UDP, но с добавлением надёжности уже на уровне приложения (совмещает скорость UDP с гарантиями, похожими на TCP — более продвинутая тема).

## 6. HTTP и HTTPS/TLS

_(Подробная структура HTTP-запроса/ответа, методы, статус-коды — разобраны в отдельном backend-конспекте; здесь фокус на TLS/шифровании.)_

>**HTTPS** = HTTP + **TLS/SSL** (шифрование). Решает проблему: обычный HTTP передаёт данные **в открытом виде** — перехвативший трафик (например, в общественном Wi-Fi) может прочитать пароли, номера карт и любые другие данные.

**Упрощённо, TLS handshake:**

1. Клиент и сервер согласовывают алгоритм шифрования.
2. Сервер предоставляет **сертификат** — доказательство подлинности, подписанное доверенным центром сертификации (Certificate Authority).
3. Стороны обмениваются ключами для **симметричного** шифрования (сама передача данных дальше идёт через быстрое симметричное шифрование, а не медленное асимметричное — асимметричное используется только на этапе обмена ключами).
4. Дальнейшая передача данных идёт в зашифрованном виде.

**Практический вывод:** TLS обеспечивает не только **конфиденциальность** (данные зашифрованы, третьи лица не могут прочитать), но и **целостность** (данные не были подменены при передаче) и **аутентификацию сервера** (сертификат подтверждает, что ты общаешься именно с тем сервером, за который он себя выдаёт, а не с злоумышленником посередине — защита от атак "человек посередине", man-in-the-middle).

## 7. Cookies

>**Cookie** — небольшой кусочек данных (до ~4КБ), который сервер просит браузер **сохранить** и **автоматически прикреплять** к каждому следующему запросу на этот же домен.

```
// Сервер отправляет в ответе:

Set-Cookie: sessionId=abc123; HttpOnly; Secure; SameSite=Strict; Max-Age=3600

// Браузер дальше сам добавляет в КАЖДЫЙ запрос к этому домену:

Cookie: sessionId=abc123
```

**Ключевые атрибуты:**

- **`HttpOnly`** — cookie недоступна для чтения через JS (`document.cookie`) — защита от кражи cookie через XSS.
- **`Secure`** — передаётся только по HTTPS.
- **`SameSite`** — контролирует отправку при переходе с другого сайта (защита от CSRF). `Strict` — не отправляется при переходе с другого сайта вообще. `Lax` — отправляется в некоторых "безопасных" случаях (обычный переход по ссылке). `None` — отправляется всегда (требует обязательного `Secure`).
- **`Max-Age`/`Expires`** — время жизни; без этого — "сессионная" cookie, удаляется при закрытии браузера.

**Практическое применение:** хранение ID сессии, запоминание предпочтений пользователя (язык, тема), аналитика/реклама (третьесторонние cookies).

## 8. Proxy и Reverse Proxy

>**Прокси-сервер** — посредник между клиентом и сервером: принимает запрос, пересылает дальше (возможно, изменяя), возвращает ответ клиенту.

### Forward proxy ("прямой" прокси)

>Работает **от имени клиента** — клиент настраивает своё приложение так, чтобы запросы шли через прокси, а не напрямую к целевому сайту.

**Применение:** обход географических ограничений, кэширование на уровне организации, фильтрация контента (корпоративный прокси), скрытие реального IP клиента от целевого сервера.

### Reverse Proxy (обратный прокси)

>Работает **от имени сервера** — клиент не знает, что за прокси может стоять несколько реальных серверов; для клиента обратный прокси выглядит как единственный конечный сервер.

```
Клиент → Reverse Proxy (nginx) → [Server 1, Server 2, Server 3]
```

**Применение:**

- **Балансировка нагрузки (load balancing)** — распределение запросов между несколькими серверами.
- **SSL termination** — прокси берёт на себя расшифровку HTTPS, внутренние серверы общаются с ним уже по обычному HTTP — упрощает управление сертификатами (в одном месте).
- **Кэширование** статичного контента близко к клиенту.
- **Скрытие внутренней структуры инфраструктуры**.
- Инструменты: **nginx**, **HAProxy**, **Traefik**.

**Частый вопрос на собесе — разница:** forward proxy представляет интересы **клиента** перед серверами (сервер не знает реального клиента). Reverse proxy представляет интересы **сервера** перед клиентами (клиент не знает реальный сервер).

## 9. Реалтайм-связь: WebSocket, SSE, Long Polling

>**Проблема:** обычный HTTP работает по модели "запрос-ответ" — **клиент всегда инициирует** взаимодействие, сервер не может сам, по своей инициативе, отправить что-то клиенту без предварительного запроса.

### Long Polling (историческое решение, до WebSocket/SSE)

Клиент отправляет запрос, сервер **намеренно не отвечает сразу**, а "держит" соединение открытым, пока не появятся новые данные (или не истечёт таймаут) — тогда отвечает, и клиент **сразу** отправляет новый такой же запрос. Работает поверх обычного HTTP, но создаёт много лишних соединений и задержку.

### WebSocket

>Протокол, обеспечивающий **постоянное, двустороннее (full-duplex)** соединение — после установки обе стороны могут отправлять сообщения друг другу в любой момент.

**Установка соединения** — начинается как обычный HTTP-запрос с заголовком `Upgrade: websocket`, сервер соглашается "перейти" на WebSocket-протокол в рамках уже установленного TCP-соединения:

```
Клиент → GET /chat HTTP/1.1
          Upgrade: websocket
          Connection: Upgrade
        → Сервер

Сервер → HTTP/1.1 101 Switching Protocols → Клиент
// Дальше соединение остаётся открытым, обе стороны шлют сообщения в любой момент
```

**Применение:** чаты, live-уведомления, совместное редактирование, онлайн-игры, живые финансовые котировки — везде, где нужны низкая задержка и **частый обмен в обе стороны**.

### SSE (Server-Sent Events)

>**Однонаправленный** канал — только **сервер → клиент**. Обычное HTTP-соединение, которое не закрывается сразу, сервер постепенно отправляет данные в формате `text/event-stream`:

```js
// Сервер
app.get('/events', (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  setInterval(() => {
    res.write(`data: ${JSON.stringify({ time: Date.now() })}\n\n`);
  }, 1000);
});

// Клиент
const eventSource = new EventSource('/events');
eventSource.onmessage = (event) => console.log(JSON.parse(event.data));
```

**Практический вывод:** SSE выбирают, если нужен **только** поток от сервера (уведомления, лента новостей, статус длительной операции) — он проще WebSocket и работает через обычный HTTP. WebSocket выбирают, когда нужна **двусторонняя** связь (чат, игры, совместное редактирование).

## 10. Частые вопросы на собеседовании

>**В: Что происходит быстрее — DNS-резолвинг или сам TCP handshake?** 

О: Зависит от кэширования — если DNS уже закэширован (у браузера/резолвера), резолвинг практически мгновенный. Если нет — DNS-резолвинг может занять заметное время (несколько сетевых round-trip'ов через корневые/TLD/авторитетные серверы), после чего только начинается TCP handshake. 

В сумме первое обращение к новому домену всегда медленнее последующих именно из-за некэшированного DNS.

>**В: Почему TLS handshake использует и асимметричное, и симметричное шифрование одновременно?** 

О: Асимметричное шифрование (с парой публичный/приватный ключ) надёжно для обмена ключами, но **медленное** для шифрования больших объёмов данных. 

Симметричное — быстрое, но требует, чтобы обе стороны заранее знали один и тот же секретный ключ. Решение: асимметричным шифрованием **безопасно передают** симметричный ключ, а дальше всю **реальную** передачу данных шифруют быстрым симметричным алгоритмом.

>**В: Может ли reverse proxy делать одновременно и балансировку нагрузки, и SSL termination?** 

О: Да, это стандартная практика — один и тот же nginx/HAProxy на входе в инфраструктуру часто одновременно расшифровывает HTTPS-трафик **и** распределяет расшифрованные запросы между несколькими внутренними серверами приложения.

>**В: Почему нельзя просто всегда использовать WebSocket вместо HTTP, если он "мощнее"?** 

О: WebSocket-соединение **постоянно открыто** и требует ресурсов сервера на поддержание (память на каждое соединение) — при большом количестве пользователей это дороже, чем короткоживущие HTTP-запросы. 

Для большинства обычных запросов (загрузка страницы, обычный CRUD через API) простой HTTP эффективнее и проще — WebSocket оправдан именно там, где нужна частая, двусторонняя, низколатентная связь, а не как универсальная замена HTTP.
