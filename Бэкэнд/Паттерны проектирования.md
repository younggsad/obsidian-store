>Паттерны проектирования делятся на три основные категории: 
>**порождающие (creational)** — как создавать объекты
>**структурные (structural)** — как компоновать объекты и классы
>**поведенческие (behavioral)** — как объекты взаимодействуют и распределяют обязанности.

## Порождающие паттерны

### Singleton

>Singleton — паттерн, гарантирующий что у класса есть только один экземпляр и предоставляет глобальную точку доступа к нему.

```js
class Database {
  static #instance;

  constructor() {
    if (Database.#instance) {
      return Database.#instance; // если экземпляр уже есть — вернуть его, не создавать новый
    }
    Database.#instance = this;
  }
}

const db1 = new Database();
const db2 = new Database();
console.log(db1 === db2); // true — это один и тот же объект
```

**Применение:** подключение к базе данных, конфигурация приложения — вещи, которых логически должно быть ровно **одно** на всё приложение.

**Осторожно:** Singleton часто критикуют как антипаттерн при злоупотреблении — он создаёт **глобальное состояние**, что усложняет тестирование (сложно подменить единственный экземпляр на mock в тестах) и создаёт скрытые зависимости между частями кода.

### Factory (фабрика)

>Factory — это паттерн, который централизует и инкапсулирует создание объектов, скрывая детали их создания от клиентского кода.

```js
class Dog { speak() { return 'Woof'; } }
class Cat { speak() { return 'Meow'; } }

function animalFactory(type) {
  if (type === 'dog') return new Dog();
  if (type === 'cat') return new Cat();
  throw new Error('Unknown animal type');
}

const pet = animalFactory('dog'); // клиентский код не знает деталей создания, просто просит нужный тип
```

**Применение:** когда логика создания объекта сложная или зависит от условий, и не хочется, чтобы клиентский код знал все детали инстанцирования конкретных классов.

### Builder (строитель)

>Builder — это порождающий паттерн, который позволяет создавать сложные объекты пошагово, отделяя процесс их построения от конечного представления объекта.

```js
class PizzaBuilder {
  constructor() {
    this.toppings = [];
  }
  addCheese() { this.toppings.push('cheese'); return this; } // возвращает this для цепочки вызовов
  addPepperoni() { this.toppings.push('pepperoni'); return this; }
  build() { return { toppings: this.toppings }; }
}

const pizza = new PizzaBuilder()
  .addCheese()
  .addPepperoni()
  .build(); // "method chaining" — цепочка вызовов
```

## Структурные паттерны

### Adapter (адаптер)

>Adapter — структурный паттерн, который позволяет объектам с несовместимыми интерфейсами взаимодействовать друг с другом путем преобразования одного интерфейса в другой, который ожидает клиент.

```js
// Старый API возвращает данные в одном формате
class OldPaymentAPI {
  makePayment(amountInCents) { console.log(`Paid ${amountInCents} cents`); }
}

// Новый код ожидает другой интерфейс (доллары, не центы)
class PaymentAdapter {
  constructor(oldApi) { this.oldApi = oldApi; }
  pay(amountInDollars) {
    this.oldApi.makePayment(amountInDollars * 100); // адаптирует вызов под старый API
  }
}

const adapter = new PaymentAdapter(new OldPaymentAPI());
adapter.pay(10); // "Paid 1000 cents" — новый код работает через привычный интерфейс
```

**Применение:** интеграция стороннего/legacy кода, интерфейс которого не соответствует ожиданиям текущей системы, без изменения самого стороннего кода.

### Decorator (декоратор)

>Decorator — структурный паттерн, который позволяет динамически добавлять объекту новые обязанности, оборачивая его в объекты с тем же интерфейсом, не изменяя исходный класс.

```js
function withLogging(fn) {
  return function(...args) {
    console.log(`Calling with args: ${args}`);
    return fn(...args);
  };
}

function add(a, b) { return a + b; }
const loggedAdd = withLogging(add); // "декорируем" функцию дополнительным поведением
loggedAdd(2, 3); // логирует вызов, потом возвращает 5
```

Это тот же паттерн, что лежит в основе **HOC в React** (уже разобранных подробно в отдельном конспекте) — HOC буквально является реализацией паттерна Decorator применительно к React-компонентам.

### Facade (фасад)

>Facade — структурный паттерн, который предоставляет простой интерфейс для работы со сложной подсистемой, скрывая внутреннюю реализацию и уменьшая связанность клиента с большим количеством объектов.

```js
// Сложная подсистема с множеством классов
class CPU { start() { /* ... */ } }
class Memory { load() { /* ... */ } }
class HardDrive { read() { /* ... */ } }

// Фасад скрывает сложность за одним простым методом
class Computer {
  constructor() {
    this.cpu = new CPU();
    this.memory = new Memory();
    this.hardDrive = new HardDrive();
  }
  start() { // клиенту не нужно знать про CPU/Memory/HardDrive по отдельности
    this.cpu.start();
    this.memory.load();
    this.hardDrive.read();
  }
}

new Computer().start(); // один простой вызов вместо ручного управления тремя подсистемами
```

### Repository 

>**Repository Pattern** — это архитектурный паттерн, который создает отдельный слой между бизнес-логикой приложения и источником данных.

Главная идея:

> **Бизнес-логика не должна напрямую работать с базой данных. Она должна обращаться к Repository, который отвечает за получение и сохранение данных.**

Repository выступает как абстракция над источником данных.

### Проблема без Repository

Типичная плохая архитектура:

```
Controller
    |
    ↓
Service
    |
    ↓
Database
```

Например:

```TypeScript
class UserService {

  constructor(
    private prisma: PrismaClient
  ) {}

  createUser(data) {
    return this.prisma.user.create({
      data
    });
  }

}
```

На первый взгляд всё работает.

Но `UserService` теперь знает:

- какой ORM используется;
- как устроена база данных;
- какие методы предоставляет Prisma;
- как формируются запросы.

Получается сильная связанность.

### Что происходит при изменении технологии

Допустим, раньше использовали:

```
Prisma + PostgreSQL
```

А потом решили перейти:

```
TypeORM + PostgreSQL
```

Без Repository:

```
UserService
    |
    ↓
Prisma
```

Нужно менять все сервисы, где используются Prisma-запросы.

### Архитектура с Repository

Правильнее:

```
Controller
      |
      ↓
Service
      |
      ↓
Repository
      |
      ↓
Database
```

Теперь:

- Controller отвечает за HTTP;
- Service отвечает за бизнес-логику;
- Repository отвечает за работу с данными.

### Пример

Repository:

```typescript
class UserRepository {

  constructor(
    private prisma: PrismaClient
  ) {}

  create(data) {
    return this.prisma.user.create({
      data
    });
  }

  findById(id:string) {
    return this.prisma.user.findUnique({
      where:{
        id
      }
    });
  }

}
```

Service:

```typescript
class UserService {

  constructor(
    private repository: UserRepository
  ) {}

  register(data) {
    return this.repository.create(data);
  }

}
```

Теперь Service не знает, как именно сохраняются данные.

### Ответственность Repository

Repository отвечает за:

- получение данных;
- сохранение данных;
- обновление данных;
- удаление данных;
- построение запросов.

Например:

```typescript
findById()

findAll()

create()

update()

delete()
```

### Что НЕ должен делать Repository

Repository не должен содержать бизнес-логику.

### Repository и SOLID

Repository особенно связан с DIP (Dependency Inversion Principle).

Без Repository:

```
UserService
      ↓
Prisma
```

Сервис зависит от конкретной реализации.

С Repository:

```
UserService
      ↓
UserRepository(interface)
      ↓
PrismaRepository
```

Теперь Service зависит от абстракции.

---
### Repository и тестирование

Без Repository:

```
UserService
      |
      ↓
Real Database
```

Для теста нужен настоящий PostgreSQL.

С Repository:

Можно передать Mock:

```typescript
class FakeUserRepository {

 save(){
    return user;
 }

}
```

Тестируем бизнес-логику без базы.

## Поведенческие паттерны

### Observer

>Observer - это паттерн, определяющий зависимость "один ко многим" между объектами: когда один объект (subject/publisher) меняет состояние, **все** зависимые от него объекты (observers/subscribers) автоматически уведомляются.

```js
class EventEmitter {
  #listeners = {};

  on(event, callback) {
    if (!this.#listeners[event]) this.#listeners[event] = [];
    this.#listeners[event].push(callback);
  }

  emit(event, data) {
    (this.#listeners[event] || []).forEach(callback => callback(data));
  }
}

const emitter = new EventEmitter();
emitter.on('userCreated', user => console.log(`Send welcome email to ${user.name}`));
emitter.on('userCreated', user => console.log(`Log: user ${user.name} created`));

emitter.emit('userCreated', { name: 'Alice' }); // оба подписчика получат уведомление
```

**Применение:** повсеместно — DOM-события (`addEventListener` — реализация Observer), Node.js `EventEmitter`, React (через изменение state и повторный рендер подписанных компонентов концептуально похоже), реактивное программирование (RxJS).

### Strategy (стратегия)

>Strategy - это паттерн, определяющий семейство **взаимозаменяемых** алгоритмов, инкапсулируя каждый в отдельный класс, позволяя выбирать нужный алгоритм во время выполнения. Он уменьшает количество условных операторов, повышает расширяемость и помогает соблюдать OCP и DIP.

```js
const strategies = {
  bubbleSort: (arr) => { /* ... */ },
  quickSort: (arr) => { /* ... */ },
  mergeSort: (arr) => { /* ... */ }
};

function sortArray(arr, strategyName) {
  return strategies[strategyName](arr); // выбираем алгоритм динамически
}
```

**Применение:** когда есть несколько способов выполнить одну задачу (разные алгоритмы сортировки, разные способы валидации, разные способы расчёта скидки), и выбор конкретного способа должен быть гибким, определяться снаружи, а не жёстко "зашит" в код.

### Middleware (частный случай Chain of Responsibility) — актуально для backend

Хотя формально это реализация паттерна **Chain of Responsibility** (цепочка обязанностей), стоит упомянуть отдельно, так как это крайне часто встречается на практике в backend-разработке (Express.js и подобные фреймворки):

```js
function loggerMiddleware(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next(); // передаёт управление следующему звену цепочки
}

function authMiddleware(req, res, next) {
  if (!req.headers.authorization) {
    return res.status(401).send('Unauthorized'); // прерывает цепочку, дальше не идёт
  }
  next();
}

app.use(loggerMiddleware);
app.use(authMiddleware);
app.get('/profile', (req, res) => { /* обработчик выполнится только если ВСЕ middleware вызвали next() */ });
```

Каждый обработчик в цепочке решает: либо передать управление **дальше** (`next()`), либо **прервать** цепочку (отправить ответ самому, не вызывая `next()`) — классическая реализация Chain of Responsibility, где каждое звено может обработать запрос само или передать его дальше по цепочке.
