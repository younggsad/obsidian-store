## 1.1 Session (сессии)

>**Идея:** HTTP — протокол без состояния (stateless), сервер сам по себе не помнит, кто ты, между запросами. Сессия — способ "симулировать" память о пользователе.

**Как работает:**

1. Пользователь логинится → сервер создаёт запись в своём хранилище сессий (в памяти, Redis, базе данных) — обычно вида `{ sessionId: "abc123", userId: 42, ... }`.
2. Сервер отправляет `sessionId` клиенту через `Set-Cookie`.
3. Браузер автоматически прикрепляет эту cookie к каждому следующему запросу.
4. Сервер по `sessionId` находит запись в своём хранилище и понимает, кто пользователь.

```js
// Express + express-session, иллюстративно
app.post('/login', (req, res) => {
  req.session.userId = user.id; // сервер сохраняет данные в хранилище сессий
});

app.get('/profile', (req, res) => {
  const userId = req.session.userId; // сервер читает сессию по cookie
});
```

**Ключевая характеристика:** состояние хранится **на сервере** (stateful) — сервер обязан где-то держать все активные сессии. Это упрощает **отзыв доступа** (просто удалить запись сессии — пользователь мгновенно "разлогинен"), но усложняет горизонтальное масштабирование — если у тебя несколько серверов за балансировщиком нагрузки, все они должны иметь доступ к **общему** хранилищу сессий (обычно решается через Redis), иначе пользователь будет "терять" сессию, попадая на разные серверы при разных запросах.

## 1.2 JWT (JSON Web Token)

>**Идея:** вместо того чтобы сервер хранил состояние, вся нужная информация закодирована **прямо в токене**, который хранится у клиента.

**Структура:** `header.payload.signature` (три части, разделённые точками, каждая закодирована в Base64URL).

```js
// header (алгоритм подписи)
{ "alg": "HS256", "typ": "JWT" }

// payload (сами данные — НЕ зашифрованы, просто закодированы, любой может прочитать)
{ "userId": 42, "role": "admin", "exp": 1735689600 }

// signature — вычисляется сервером: HMACSHA256(base64(header) + "." + base64(payload), secretKey)
```

**Проверка на сервере:** при получении токена сервер пересчитывает подпись, используя свой секретный ключ, и сравнивает с подписью в токене. Если совпадает — токен не подделан. Это **не требует** обращения к базе данных — вся проверка происходит локально, криптографически (**stateless**).

**Access token + Refresh token** — стандартная практика:

- **Access token** — короткоживущий (обычно 15 минут), используется для авторизации запросов.
- **Refresh token** — долгоживущий, хранится более защищённо (например, `HttpOnly` cookie), используется **только** для получения нового access token, когда старый истёк, без необходимости заново вводить логин/пароль.

## 1.3 CORS (Cross-Origin Resource Sharing)

>**Проблема, которую решает CORS:** браузер по умолчанию блокирует запросы с **одного источника (origin)** к **другому**, если сервер явно не разрешил это — это называется **Same-Origin Policy (политика единого источника)**, защита от вредоносных сайтов, которые могли бы втихую делать запросы к другим сайтам от имени залогиненного пользователя.

>**Origin** — комбинация протокола + домена + порта: `https://example.com:443`. Запрос с `https://myapp.com` на `https://api.example.com` — это **cross-origin** запрос (разные домены).

**Как работает CORS:**

1. Браузер отправляет запрос к другому origin.
2. Сервер должен явно ответить заголовком, разрешающим этот origin:

```
Access-Control-Allow-Origin: https://myapp.com
```

3. Если заголовка нет (или он не совпадает с origin запроса) — браузер **блокирует** доступ к ответу для JavaScript-кода страницы (важно: сам запрос **может** дойти до сервера и выполниться, но браузер не даст JS прочитать ответ — это заблуждение, что CORS блокирует сам запрос).

>**Preflight-запрос (предварительный запрос):** для "непростых" запросов (например, с методом `PUT`/`DELETE`, кастомными заголовками, `Content-Type: application/json`) браузер **сначала** сам, автоматически, отправляет `OPTIONS`-запрос — спрашивает у сервера "а разрешено ли мне вообще это делать?" — и только если сервер ответит разрешением, браузер отправляет реальный запрос.

```
Access-Control-Allow-Origin: https://myapp.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
```

**Практический вывод:** CORS — это **браузерный** механизм защиты (настраивается на сервере, но применяется браузером) — он не защищает сервер от прямых запросов (curl, Postman, сервер-сервер), потому что эти инструменты не подчиняются политике same-origin — CORS защищает именно **пользователя браузера** от того, чтобы вредоносный сайт втихую делал запросы от его имени к другим сайтам.

## 1.4 CSP (Content Security Policy)

>**Проблема, которую решает CSP:** защита от **XSS-атак** (Cross-Site Scripting) — когда злоумышленник каким-то образом внедряет вредоносный JS-код на страницу (например, через незаэкранированный пользовательский ввод), и этот код выполняется в браузере жертвы.

**Как работает:** сервер отправляет заголовок, явно указывающий, **откуда разрешено** загружать различные типы ресурсов (скрипты, стили, изображения):

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted-cdn.com; img-src *;
```

- `default-src 'self'` — по умолчанию разрешены ресурсы только с того же origin.
- `script-src 'self' https://trusted-cdn.com` — скрипты разрешены только с текущего сайта и указанного CDN.
- `img-src *` — изображения разрешены с любого источника.

Если злоумышленник внедрит `<script>alert('hacked')</script>` через уязвимость — браузер **откажется** выполнять этот инлайн-скрипт (если CSP не разрешает `unsafe-inline`), даже если код физически оказался на странице — это защита **на уровне браузера**, дополнительный барьер поверх правильной санитизации ввода на сервере.

**Практический вывод:** CSP — это "defense in depth" (эшелонированная защита) — даже если где-то в коде проскочила XSS-уязвимость, правильно настроенный CSP может **предотвратить** реальный вред от неё, не давая браузеру выполнить вредоносный код.

## 1.5 Cache (кэширование)

>**Идея:** избежать повторного выполнения дорогой операции (сетевой запрос, вычисление, запрос к базе данных), сохранив результат для повторного использования.

### HTTP-кэширование

```
Cache-Control: max-age=3600 — ответ можно кэшировать на 3600 секунд, не переспрашивая сервер

Cache-Control: no-cache — можно кэшировать, но ОБЯЗАТЕЛЬНО перепроверить актуальность у сервера перед использованием

Cache-Control: no-store — вообще не кэшировать (для чувствительных данных)
```

**ETag** — механизм проверки актуальности без повторной передачи всего содержимого:

1. Сервер отправляет `ETag: "abc123"` (хэш содержимого) вместе с ответом.
2. При следующем запросе браузер отправляет `If-None-Match: "abc123"`.
3. Если содержимое не изменилось — сервер отвечает `304 Not Modified` **без тела ответа** (экономит трафик) — браузер использует уже сохранённую у себя копию.

### Кэширование на уровне приложения/базы данных

>**Redis** как кэш перед базой данных — частый паттерн:

```js
async function getUser(id) {
  const cached = await redis.get(`user:${id}`);
  if (cached) return JSON.parse(cached); // быстрый ответ из кэша, без похода в БД

  const user = await db.query('SELECT * FROM users WHERE id = $1', [id]);
  await redis.set(`user:${id}`, JSON.stringify(user), 'EX', 3600); // кэшируем на час
  return user;
}
```

**Проблема инвалидации кэша** — классическая, часто цитируемая сложность в разработке ("в информатике есть только 2 сложные вещи: инвалидация кэша и придумывание имён"): когда данные в базе меняются, нужно не забыть **обновить или удалить** устаревшую версию в кэше — иначе пользователь увидит устаревшие данные (stale data).

**Основные стратегии кэширования:**

- **Cache-aside (Lazy loading)** — приложение само проверяет кэш, и если данных нет — идёт в базу и кладёт результат в кэш (пример выше).
- **Write-through** — при записи данные сразу пишутся и в базу, и в кэш одновременно.
- **Write-behind** — данные сначала пишутся в кэш, а в базу данных попадают позже, асинхронно (быстрее, но есть риск потери данных при сбое до записи в базу).

## 1.6 Idempotency (идемпотентность)

_(Уже разобрано в backend-конспекте применительно к HTTP-методам — здесь дополнительный практический аспект.)_

>**Напоминание определения:** операция идемпотентна, если повторное её выполнение с теми же параметрами даёт **тот же результат**, что и однократное выполнение — не создаёт дополнительных побочных эффектов при повторении.

**Практическая проблема, где это важно — двойная отправка формы/платежа:** Пользователь нажал "Оплатить", запрос ушёл, но ответ не пришёл (плохая сеть) — пользователь в панике нажимает "Оплатить" ещё раз. Без защиты от повтора — спишутся деньги **дважды**.

**Решение — Idempotency Key:**

```
POST /payments
Idempotency-Key: unique-client-generated-id-abc123
```

Клиент генерирует **уникальный** ключ для конкретной попытки операции (обычно UUID) и передаёт его в заголовке. Сервер **запоминает**, что запрос с таким ключом уже был обработан, и при **повторном** запросе с тем же ключом — просто возвращает **сохранённый результат** первого выполнения, **не выполняя** операцию повторно (не списывает деньги второй раз).

**Практический вывод:** это стандартная практика в платёжных API (Stripe, например, требует именно такой подход) — критично для любых операций, где повторное выполнение имеет реальную денежную/бизнес-цену.
