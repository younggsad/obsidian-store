### Что такое Node.js

>**Node.js** — это среда выполнения (runtime) JavaScript **вне браузера**. До Node.js JavaScript мог работать только внутри браузера. Node.js взял движок V8 (тот же, что используется в Chrome для выполнения JS) и добавил к нему возможность работать с файловой системой, сетью, процессами — то есть всё то, что нужно для backend-разработки, но чего в браузере по соображениям безопасности нет.

**Ключевая особенность:** Node.js — **однопоточный** (single-threaded) в плане выполнения JS-кода, но при этом умеет обрабатывать **тысячи** одновременных соединений эффективно — благодаря **асинхронной, неблокирующей модели ввода-вывода** (non-blocking I/O). Это одна из главных тем, которую спрашивают на собеседованиях, и мы разберём её подробно ниже.

### Синхронный vs асинхронный код — база

**Синхронный код** выполняется строго последовательно, одна операция за другой — каждая следующая строка ждёт, пока закончится предыдущая.

```js
console.log("1");
console.log("2");
console.log("3");
// Вывод строго по порядку: 1, 2, 3
```

**Проблема с синхронным подходом на сервере:** представим, что сервер должен прочитать файл с диска, и это занимает, скажем, 2 секунды.

```js
const fs = require('fs');

const data = fs.readFileSync('bigfile.txt'); // блокирует ВЕСЬ поток на 2 секунды
console.log('Файл прочитан');
console.log('Эта строка выполнится только после чтения файла');
```

Пока идёт чтение файла **синхронно** (`readFileSync`), весь Node.js-процесс **заблокирован** — не может обрабатывать никакие другие запросы от других пользователей в это время. Если у тебя сервер, который одновременно обслуживает тысячи пользователей, а один запрос "подвесил" единственный поток на 2 секунды — все остальные пользователи будут просто ждать в очереди, даже если их запросы вообще не связаны с чтением файла.

**Асинхронный подход** решает эту проблему:

```js
const fs = require('fs');

fs.readFile('bigfile.txt', (err, data) => {
  console.log('Файл прочитан');
});

console.log('Эта строка выполнится СРАЗУ, не дожидаясь чтения файла');
```

Node.js **запускает** операцию чтения файла (делегируя её операционной системе / отдельному внутреннему пулу потоков), и **сразу же** продолжает выполнять остальной код, не дожидаясь результата. Когда чтение файла завершится — вызовется колбэк с результатом, но это произойдёт **позже**, не блокируя выполнение остального кода в данный момент.

### Event Loop в Node.js

>Событийный цикл (event loop) — это механизм, который позволяет Node.js оставаться однопоточным для выполнения JS-кода, но при этом не "зависать" на долгих операциях (сеть, диск, таймеры) — вместо этого такие операции делегируются "наружу" (операционной системе или внутреннему пулу потоков Node.js — **libuv**), а event loop следит за тем, когда они завершатся, и в нужный момент выполняет связанный с ними JS-код (колбэки).

**Важное отличие от браузерного event loop** (который мы разбирали для JS в целом) — в Node.js event loop состоит из **нескольких фаз**, выполняющихся по кругу:

1. **Timers** — выполняются колбэки `setTimeout` и `setInterval`, у которых истекло время ожидания.
2. **Pending callbacks** — выполняются некоторые системные колбэки, отложенные с предыдущего цикла.
3. **Poll** — самая важная фаза: здесь Node.js получает новые I/O-события (например, "файл дочитан", "пришли данные по сети") и выполняет их колбэки. Если очередь пуста, Node.js может "подождать" здесь новых событий.
4. **Check** — выполняются колбэки `setImmediate`.
5. **Close callbacks** — колбэки закрытия (например, `socket.on('close', ...)`).

Между **каждой** фазой (и даже между отдельными колбэками внутри одной фазы) Node.js **опустошает очередь микрозадач** — `process.nextTick()` (у него даже более высокий приоритет, чем у обычных микрозадач) и `Promise.then()`.

```js
console.log('start');

setTimeout(() => console.log('setTimeout'), 0);

setImmediate(() => console.log('setImmediate'));

Promise.resolve().then(() => console.log('promise'));

process.nextTick(() => console.log('nextTick'));

console.log('end');
```

**Порядок вывода:**

```
start
end
nextTick     // process.nextTick — наивысший приоритет среди асинхронных                                                                       задач
promise      // затем обычные микрозадачи (Promise)
setTimeout   // затем макрозадачи — порядок setTimeout/setImmediate может                                                      зависеть от контекста
setImmediate
```

**Практический вывод:** `process.nextTick()` выполняется **раньше всего остального асинхронного кода**, даже раньше промисов — это специфика именно Node.js (в браузере такого метода нет вообще). Из-за этого приоритета `process.nextTick` стоит использовать осторожно — если постоянно добавлять в него новые вызовы, можно вообще "заблокировать" event loop, не давая ему перейти к I/O-операциям (это называется "starvation").

### Callback, Promise, Async/Await — три способа писать асинхронный код

**1. Callbacks (колбэки)** — исторически первый способ в Node.js:

```js
const fs = require('fs');

fs.readFile('file1.txt', (err, data1) => {
  if (err) return console.error(err);
  fs.readFile('file2.txt', (err, data2) => {
    if (err) return console.error(err);
    fs.readFile('file3.txt', (err, data3) => {
      if (err) return console.error(err);
      console.log('Все файлы прочитаны');
    });
  });
});
```

**Проблема** — "callback hell" (ад колбэков): при последовательных асинхронных операциях код "разрастается вправо", становится трудночитаемым, обработка ошибок дублируется в каждом уровне.

**2. Promises** — решают проблему вложенности через цепочки `.then()`:

```js
const fs = require('fs').promises; // fs с промис-версиями методов

fs.readFile('file1.txt')
  .then(data1 => fs.readFile('file2.txt'))
  .then(data2 => fs.readFile('file3.txt'))
  .then(data3 => console.log('Все файлы прочитаны'))
  .catch(err => console.error(err)); // одна точка обработки ошибок для всей цепочки
```

**3. Async/await** — синтаксический сахар поверх промисов, делает асинхронный код похожим на синхронный по читаемости:

```js
async function readFiles() {
  try {
    const data1 = await fs.readFile('file1.txt');
    const data2 = await fs.readFile('file2.txt');
    const data3 = await fs.readFile('file3.txt');
    console.log('Все файлы прочитаны');
  } catch (err) {
    console.error(err); // try/catch вместо .catch()
  }
}
```

**Важно понимать:** `async/await` не заменяет промисы — это способ **писать** код с промисами более читаемо. Под капотом всё равно работают промисы, `await` просто "приостанавливает" выполнение функции до того, как промис зарезолвится, не блокируя при этом весь event loop (другие операции в это время продолжают выполняться).

### Параллельное выполнение асинхронных операций

Частая ошибка новичков — писать независимые `await` последовательно, хотя они могли бы выполняться параллельно:

```js
// Плохо — операции НЕ зависят друг от друга, но выполняются последовательно (медленно)
async function getData() {
  const users = await fetchUsers();     // ждём 1 секунду
  const products = await fetchProducts(); // ждём ещё 1 секунду
  return { users, products }; // итого 2 секунды
}

// Хорошо — запускаем параллельно, ждём оба сразу
async function getData() {
  const [users, products] = await Promise.all([
    fetchUsers(),
    fetchProducts()
  ]); // обе операции идут одновременно, итого ~1 секунда
  return { users, products };
}
```

### Streams (потоки)

**Streams** — это механизм для работы с данными **порциями (chunks)**, а не загружая всё сразу в память целиком. Критично важно для работы с большими файлами или данными, объём которых заранее неизвестен (например, видео, большие датасеты, сетевые ответы).

**Проблема без streams:**

```js
const fs = require('fs');

// Загружает ВЕСЬ файл в память целиком, прежде чем что-то делать дальше
fs.readFile('huge-video.mp4', (err, data) => {
  response.end(data); // если файл 10 ГБ — в памяти сервера окажется 10 ГБ данных
});
```

Если файл большой (видео, архив), а сервер одновременно обрабатывает много таких запросов — память сервера быстро закончится.

**Решение через streams:**

```js
const fs = require('fs');

const readStream = fs.createReadStream('huge-video.mp4');
readStream.pipe(response); // данные передаются небольшими порциями (chunks), не загружая всё в память сразу
```

**Типы streams в Node.js:**

- **Readable** — источник данных, можно читать (например, чтение файла, HTTP-запрос от клиента).
- **Writable** — приёмник данных, можно писать (например, запись в файл, HTTP-ответ клиенту).
- **Duplex** — одновременно и читаемый, и записываемый (например, TCP-сокет).
- **Transform** — Duplex-поток, который **преобразует** данные при прохождении через себя (например, сжатие файла на лету через `gzip`).

**Метод `.pipe()`** — соединяет Readable-поток с Writable-потоком, автоматически управляя скоростью передачи данных (backpressure — если приёмник не успевает обрабатывать данные так быстро, как их поставляет источник, `.pipe()` сам приостанавливает чтение, чтобы не переполнить память).

```js
const fs = require('fs');
const zlib = require('zlib');

// Пример реальной цепочки: читаем файл → сжимаем → записываем сжатую версию
fs.createReadStream('input.txt')
  .pipe(zlib.createGzip())
  .pipe(fs.createWriteStream('input.txt.gz'));
```

**Практическое применение streams:**

- Отдача больших файлов клиенту (видео, изображения) без загрузки их целиком в память сервера.
- Обработка загружаемых пользователем файлов (upload) по мере поступления, не дожидаясь полной загрузки.
- Построчная обработка огромных CSV/лог-файлов, которые не поместятся в памяти целиком.

### Многопоточность в Node.js — как однопоточный JS справляется с нагрузкой

Важный момент, который часто путают: **сам JS-код выполняется в одном потоке**, но Node.js (через библиотеку **libuv**) использует **пул потоков (thread pool)** под капотом для операций, которые нельзя сделать неблокирующими на уровне операционной системы напрямую — например, некоторые файловые операции, DNS-запросы, работа с криптографией (`crypto.pbkdf2`).

Сетевые операции (HTTP-запросы, работа с базами данных через сокеты) обычно **не используют** пул потоков вообще — они полагаются на асинхронные механизмы самой операционной системы (epoll в Linux, kqueue в macOS, IOCP в Windows), что ещё эффективнее.

**Для настоящих тяжёлых вычислений** (не I/O, а именно CPU-нагрузка — например, обработка изображений, сложные вычисления), которые **блокируют** единственный поток JS, в Node.js есть:

- **Worker Threads** — реальные отдельные потоки с собственным V8-инстансом, для CPU-интенсивных задач.
- **Child Processes** (`child_process.fork()`) — запуск полностью отдельного Node.js-процесса.
- **Кластеризация (`cluster` модуль)** — запуск нескольких процессов Node.js (обычно по числу ядер процессора), которые вместе обрабатывают входящие запросы, распределяя нагрузку между собой — стандартный способ горизонтально масштабировать Node.js-приложение на одной машине.

**Практический вывод, важный для собеса:** Node.js **отлично** подходит для I/O-интенсивных задач (много одновременных сетевых запросов, работа с базами данных, файлами) именно благодаря неблокирующей модели — но **плохо** подходит "из коробки" для CPU-интенсивных задач (сложные вычисления, обработка изображений/видео), потому что такая задача заблокирует единственный поток, и **все** остальные пользователи будут ждать, пока она не закончится — если не использовать Worker Threads/кластеризацию для таких случаев.

## Модульные системы — CommonJS vs ES Modules

### CommonJS (исторический стандарт Node.js)

```javascript
// math.js
function add(a, b) { return a + b; }
module.exports = { add };
// или: exports.add = add;

// main.js
const { add } = require('./math.js');
console.log(add(2, 3));
```

**Особенности:**

- `require()` — **синхронный**, выполняется в момент вызова.
- Можно вызывать `require()` **условно**, внутри `if`, циклов — в отличие от статических `import`.
- Не поддерживает нативный **tree shaking** (разбирали в конспекте про бандлеры) — весь модуль загружается целиком, потому что `require` не анализируется статически до выполнения.

### ES Modules (современный стандарт)

```javascript
// math.mjs (или .js с "type": "module" в package.json)
export function add(a, b) { return a + b; }

// main.mjs
import { add } from './math.mjs';
console.log(add(2, 3));
```

```json
// package.json
{
  "type": "module"  // включает ESM по умолчанию для всех .js файлов проекта
}
```

**Особенности:** статический анализ (позволяет tree shaking), `import` не может быть условным на верхнем уровне (хотя есть `import()` — динамический, асинхронный, возвращающий промис, аналог того, что разбирали в теме бандлеров).

## Модуль `fs` — работа с файловой системой

```javascript
const fs = require('fs');
const fsPromises = require('fs/promises'); // promise-based API — предпочтительнее

// Синхронно (БЛОКИРУЕТ event loop — избегать в серверном коде!)
const data = fs.readFileSync('file.txt', 'utf-8');

// Callback-based (старый стиль)
fs.readFile('file.txt', 'utf-8', (err, data) => {
  if (err) throw err;
  console.log(data);
});

// Promise-based (современный, предпочтительный способ)
async function readFile() {
  const data = await fsPromises.readFile('file.txt', 'utf-8');
  console.log(data);
}

await fsPromises.writeFile('output.txt', 'Новое содержимое');
await fsPromises.mkdir('new-folder', { recursive: true });
await fsPromises.unlink('file.txt'); // удалить файл
```

⚠️ **Критически важно:** `fs.readFileSync` **блокирует весь event loop** до завершения операции — на сервере, обрабатывающем множество одновременных запросов, это означает, что **все** остальные запросы "замирают", пока читается файл. В серверном коде почти всегда нужно использовать асинхронные версии (`fs.promises` или callback-based).

## Модуль `http` — базовый веб-сервер без фреймворка

```javascript
const http = require('http');

const server = http.createServer((req, res) => {
  if (req.url === '/api/users' && req.method === 'GET') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    res.end(JSON.stringify([{ id: 1, name: 'Аня' }]));
  } else {
    res.writeHead(404, { 'Content-Type': 'text/plain' });
    res.end('Not Found');
  }
});

server.listen(3000, () => {
  console.log('Сервер запущен на порту 3000');
});
```

На практике почти всегда используют фреймворк поверх этого низкоуровневого API — **Express**, **Fastify**, **NestJS** — они убирают необходимость вручную парсить URL, методы, тело запроса.

## Express — самый популярный минималистичный фреймворк

```javascript
const express = require('express');
const app = express();

app.use(express.json()); // middleware — парсит JSON-тело запроса в req.body

app.get('/api/users', (req, res) => {
  res.json([{ id: 1, name: 'Аня' }]);
});

app.get('/api/users/:id', (req, res) => {
  const id = req.params.id; // параметры из URL-пути
  res.json({ id, name: 'Аня' });
});

app.post('/api/users', (req, res) => {
  const { name, email } = req.body; // данные из тела запроса
  res.status(201).json({ id: 2, name, email });
});

app.listen(3000);
```

### Middleware — центральная концепция Express

```javascript
function logger(req, res, next) {
  console.log(`${req.method} ${req.url}`);
  next(); // ОБЯЗАТЕЛЬНО вызвать next(), иначе запрос "зависнет" навсегда
}

app.use(logger); // применяется ко ВСЕМ маршрутам

function authMiddleware(req, res, next) {
  const token = req.headers.authorization;
  if (!token) {
    return res.status(401).json({ error: 'Не авторизован' }); // прерываем цепочку, НЕ вызываем next()
  }
  req.user = verifyToken(token); // добавляем данные в req для следующих обработчиков
  next();
}

app.get('/api/profile', authMiddleware, (req, res) => {
  res.json(req.user); // req.user доступен благодаря предыдущему middleware
});
```

**Middleware** — функция, получающая `(req, res, next)`, выполняющаяся **до** основного обработчика маршрута — может модифицировать `req`/`res`, завершить запрос досрочно, или передать управление дальше через `next()`. Цепочка middleware — базовый механизм для аутентификации, логирования, валидации, обработки ошибок в Express-подобных фреймворках.

### Обработка ошибок — специальный middleware с 4 аргументами

```javascript
app.use((err, req, res, next) => { // 4 параметра — Express распознаёт это как error-handler
  console.error(err.stack);
  res.status(500).json({ error: 'Внутренняя ошибка сервера' });
});
```

## npm/package.json — управление зависимостями

```json
{
  "name": "my-app",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node index.js",
    "dev": "nodemon index.js"
  },
  "dependencies": {
    "express": "^4.18.0"
  },
  "devDependencies": {
    "nodemon": "^3.0.0"
  }
}
```

- `dependencies` — нужны и в production (сама работа приложения).
- `devDependencies` — нужны только для разработки (тестирование, сборка, линтинг) — не попадают в production-окружение при `npm install --production`.
- `^4.18.0` — совместимость с любой версией `4.x.x` (кроме major-изменений); `~4.18.0` — только patch-обновления в пределах `4.18.x`.

## Асинхронность в Node.js — практический пример полного цикла

```javascript
import express from 'express';
import fs from 'fs/promises';

const app = express();
app.use(express.json());

app.get('/api/users/:id', async (req, res) => {
  try {
    const raw = await fs.readFile('./users.json', 'utf-8');
    const users = JSON.parse(raw);
    const user = users.find((u) => u.id === Number(req.params.id));

    if (!user) {
      return res.status(404).json({ error: 'Пользователь не найден' });
    }

    res.json(user);
  } catch (error) {
    console.error(error);
    res.status(500).json({ error: 'Ошибка сервера' });
  }
});

app.listen(3000);
```

Все асинхронные операции внутри Express-обработчика (`async (req, res) => {...}`) оборачиваются в `try/catch` — сам Express **не ловит** отклонённые промисы автоматически (в версиях до Express 5) — если не обернуть в `try/catch`, необработанная ошибка внутри `async`-обработчика "потеряется", запрос может зависнуть без ответа.

## Частые вопросы на собеседовании (Node.js)

**В: Почему Node.js однопоточный, но при этом быстрый для веб-серверов?** О: Потому что большинство операций веб-сервера — это I/O (ожидание базы данных, сети, диска), а не вычисления. Пока идёт ожидание, event loop свободен и может обрабатывать другие запросы — не нужно создавать отдельный поток на каждого пользователя (как в некоторых других языках/фреймворках), что экономит память и накладные расходы на переключение контекста между потоками.

**В: Что произойдёт, если в Node.js выполнить тяжёлое синхронное вычисление (например, огромный цикл)?** О: Весь сервер "зависнет" на время этого вычисления — event loop заблокирован, никакие другие запросы не обрабатываются, пока цикл не закончится. Это одна из главных опасностей в Node.js — легко случайно заблокировать весь сервер одной неаккуратной синхронной операцией.

**В: В чём разница между `process.nextTick()` и `setImmediate()`?** О: `process.nextTick()` выполняется **сразу** после текущей операции, до перехода к следующей фазе event loop (даже раньше промисов). `setImmediate()` выполняется в фазе **check**, после фазы poll (после обработки I/O-событий) — то есть позже, чем `nextTick`, и обычно позже, чем `setTimeout(fn, 0)`.
