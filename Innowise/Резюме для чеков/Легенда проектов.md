# Legend 1 DrupalJira

## Context

DrupalJira is an internal project and issue tracking system built on Drupal 11 and PHP 8.4. The business problem was that teams tracked tasks in spreadsheets and chats, so nobody had a clear view of statuses, sprints and time spent. We needed a Jira-like tool that fits our processes, has no license costs and is easy to extend with custom logic.

## Responsibilities
 
I was a backend-oriented full-stack developer. I owned the custom modules for the Kanban board, task status changes, modal views and sprint management. I designed the `time_log` custom content entity with its own forms, access control and list builder. I also implemented the task lifecycle with Workflows and Content Moderation, and the project statistics service. Besides coding, I took part in code reviews, set up code quality tools (PHPCS, PHPStan, GrumPHP) and wrote Playwright tests.

## Features and way of working

The main features I built were these:
 
- I built a Kanban board where cards move between columns, and the server decides which transitions are allowed.
- I built sprints, so the team can create them, fill them with tasks, close them and move unfinished tasks back to the backlog.
- I implemented time tracking through the `time_log` entity.
- I created project statistics that show tasks per status, hours spent and team velocity.
- I imported legacy tasks from CSV files with the Migrate API.
- I added attachments with Media Library and Paragraphs.
 
 My way of working was simple. I took a ticket, clarified the acceptance criteria with the analyst and briefly described my approach in the ticket. If a decision affected the architecture, for example a new entity or service, I discussed it with the tech lead before coding. I kept my pull requests small so that reviews were fast, and I shipped tests together with each feature.

## Gamechanger feature
 
It was the Kanban board that feels like a single-page app but is built with standard Drupal tools. When a user drops a card, an AJAX request goes to the server. The server checks through Workflows and Content Moderation whether the transition is allowed, and then only the necessary part of the page is refreshed. This gave the business two benefits. First, people actually started using the system because it was fast. Second, nobody could move a task to "Done" without a review, because the rule lives on the server and not in the UI. The second strong feature was time statistics, because managers could see the real effort per project for the first time.

## Uniqueness

 The project would not have collapsed, but there would probably be more logic in forms and JavaScript, fewer services and tests, and the Kanban board would refresh with a full page reload. My uniqueness is that I combine deep knowledge of the Drupal API (Entity, Plugin, Queue, Batch, Access) with a solid frontend background in TypeScript and React. This means I can take a feature from the database schema to the user interface. I also actively use AI assistants like Claude Code and Codex, but I always verify the results with tests and static analysis. This makes me faster without losing quality.

## Initiative

 When the tech lead was on vacation, I took over part of their duties. I ran the sprint planning and cleared the code review queue so that pull requests did not stall. I also discussed priorities with the product owner. Some requests did not fit into the sprint, so I explained what we could do now, what we should postpone and why. When an urgent production bug appeared, I coordinated the work myself. I reproduced the bug, prepared a hotfix, agreed the release with QA and told the business what would be fixed and when. After the tech lead came back, I wrote a short summary of the decisions I had made.

## Deployment

Locally we worked in DDEV, and the Drupal configuration was stored in Git (config sync). On every pull request, GitHub Actions ran PHPCS, PHPStan, PHPUnit and Playwright. After a merge to main, the CI built a Docker image (PHP-FPM and Nginx, tagged with the commit SHA) and pushed it to ECR using OIDC, so we had no static keys.
 
The application ran on ECS Fargate behind an ALB, in at least two availability zones. We used MariaDB on RDS (Multi-AZ), Redis on ElastiCache, files on S3 through `s3fs` and CloudFront, and secrets in Secrets Manager.
 
The release had two steps. First, we ran a one-off `drush deploy` task (updatedb, config:import, cache:rebuild). Then we updated the service. Staging was deployed automatically, and production needed a manual approval. Production used the same image and had an RDS snapshot before the migrations. If the new tasks failed the health check, the circuit breaker rolled the release back on its own. We could also return to the previous revision manually. Logs went to CloudWatch, and cron and queues ran as separate EventBridge tasks.

> [!question] Why does `drush deploy` run as a separate task and not on container start?
> 
> If it ran on container start, every task in the service would run the migration at the same time, and they would interfere with each other. A separate one-off task runs exactly once. If it fails, the release stops before the service is updated, so users stay on the working version.

> [!question] Fargate has no persistent disk. How did you handle uploaded files?
> 
> Public and private files are stored in S3 through `s3fs`, and public files are served through CloudFront. Sessions and cache are stored in Redis. The container keeps only data that we can afford to lose, such as temporary files and compiled Twig templates.

> [!question] How do you handle config and content during a release?
> 
> Configuration, such as entity types, workflows, views and permissions, travels through Git and `config:import`. Content, such as tasks, sprints and time records, lives only in the database, and a release never overwrites it. Differences between environments, for example debug modules or URLs, are handled with Config Split and environment variables.

> [!question] What was your personal part in the deployment?
> 
> I wrote and maintained the Dockerfile and the GitHub Actions workflows for checks, build and release. I also set up the `drush deploy` step and the smoke test on staging, and I moved the settings in `settings.php` to environment variables. I created the AWS resources (VPC, RDS, ECS) together with a DevOps engineer or the tech lead. I described the requirements of the application, such as versions, PHP extensions, the health check and S3, and they were responsible for networking and permissions.

## Most interesting task
 
It was updating parts of the page through AJAX on the Kanban board. When a status changed or a modal window opened, only the needed block had to refresh. I used Drupal AJAX and Drupal behaviors, so JavaScript attached correctly to the new DOM after every update. I kept the business logic on the server.

> [!question] Why not React for the board?
> 
> We wanted to stay inside standard Drupal because it is easier to maintain. Server-side cache, access control and rendering work out of the box, and we did not need a separate API.

> [!question] What if two users move the same card?
> 
> The server checks the current status before the transition. The second request gets an error together with the updated state.

## Most interesting bug

After several card moves, one click started to fire twice, then three times, and duplicate status change requests were sent. The cause was that a behavior runs after every AJAX response, so the handlers were attached again and again to the same elements. I found the problem in the Network tab, where the number of requests kept growing, and by debugging the behaviors.

I fixed it with `once()` from Drupal core, so a handler is attached only once per element, and I added `detach` for cleanup. Then I wrote a Playwright test that moves several cards in a row and checks that exactly one request is sent for each action. The lesson is that in Drupal any JavaScript must be idempotent.

## High load and fault tolerance
 
Our load was moderate, with hundreds of active users, but we still applied several measures.

**Caching.** We used render cache with cache tags and contexts, Dynamic Page Cache and Redis. The statistics were cached and invalidated only when the tasks of the project changed.

**Heavy operations.** We ran heavy work, such as recalculating statistics and imports, through the Queue API and Batch API, so no HTTP request was blocked.
 
**Horizontal scaling.** The containers were stateless and sat behind a load balancer. Sessions and cache were in Redis, and files were in S3.
 
**Database.** We used indexes, a read replica when needed, and the slow query log.
 
**Fault tolerance.** We ran at least two instances in different availability zones and used Multi-AZ for RDS. We also had health checks, automatic container restarts, backups with restore tests, and logs with alerts.
 
**Graceful degradation.** If an external dependency like email failed, the operation went into a queue and was retried, so the user did not see an error.

## Database
 
**Normalization.** `time_log` is a separate entity with entity references to the task and the user, and it is not an array inside the task. One task has many time records, and this makes reporting easy.
 
**Denormalization.** Calculating `SUM(minutes)` over all `time_log` records on every card render is expensive. So the task stores an aggregated "minutes spent" field, and a service updates it when a `time_log` is saved or deleted. The trade-off is that the data can drift. To handle this, I added a drush command for recalculation and a consistency test.
 
**N+1.** The board rendered 50 cards, and the assignee, status and attachments were loaded separately for each card. This produced hundreds of queries, and I found the problem with Webprofiler and Devel (the query counter). To fix it, I used EntityQuery to get the IDs and then `loadMultiple()` to load the entities in one batch. I also preloaded related entities, such as users, in bulk. I used Views with relationships instead of loops, and I cached the result with cache tags. After this, we had dozens of queries instead of hundreds (use your own numbers if you measured them).
 
**Indexes.** The main queries were tasks of a project by status, and time records by task and by user for a period. I added composite indexes, for example `(task_id, logged_at)`, in the schema of the custom entity, and I checked query plans with `EXPLAIN`. My rule is that an index should serve a real query and not exist "just in case", because every index slows down writes.

## Layers
 
The application has five layers.

1. **Presentation.** It contains routes, controllers, forms, Twig and behaviors. It has no business logic, and it only receives the request and renders the response.
2. **Application and service.** It contains services with dependency injection, for example for changing a task status and for statistics. All business logic lives here, and it is easy to cover with unit tests.
3. **Domain.** It contains the entities (task, sprint, time_log), Workflows and Content Moderation, and the transition rules.
4. **Data access.** It contains entity storage, EntityQuery and migrations. Controllers never write SQL directly.
5. **Cross-cutting.** It contains access handlers, event subscribers, caching and logging.

 The benefit is that we can replace a controller, for example to add a JSON:API endpoint, and the service stays the same. Our tests are also split by layer. We used unit tests for services, kernel tests for entities and Playwright for user scenarios.

## Team
 
The team had about six people. We had a tech lead who was also the architect, two Drupal backend developers (me and a colleague), a frontend and theming developer, a QA engineer and an analyst who was also the product owner.
 
We used Scrum with two-week sprints, which included planning, a daily stand-up, a demo and a retrospective. We tracked tasks in Jira or Trello for external customers.
 
The process was like this. The analyst writes the requirements, and the tech lead helps with estimation and architecture. A developer takes a ticket into a branch and opens a pull request. The pull request must pass the CI and a review by at least one colleague. Then QA tests it on staging, and after that we release.

With the frontend developer, we agreed in advance on a contract, which means what data the server provides and which render arrays and templates the theme uses. With QA, we discussed the test scenarios before the work started, and I added automated tests for the critical ones.

# Legend 2 Live Voting App

## Context

Live Voting App is a polling application with real-time results. The idea is to run a vote quickly at a meeting, a lecture or in a team, without registration, and to see the result on the screen immediately. It is a monorepo. The frontend uses React 19, TypeScript and Vite, and the backend uses Express.js and PostgreSQL with Prisma.

## Responsibilities, features and way of working
 
There were two developers, and we also got feedback from the customer, who was an event organizer. I led the backend and the architecture. I designed the database schema and the API contracts, and I built the poll and voting APIs and the duplicate vote protection. I also implemented the security layer (Helmet, CORS, secure cookies, rate limiting), the unified validation and error handling, and the live results over WebSocket or SSE. In addition, I set up the CI, Docker Compose and the deployment.
 
The second developer mostly owned the frontend. They built poll creation, the voting page, the result charts and the responsive layout. The boundaries were not strict. I also worked on the frontend, for example on the live results integration and TanStack Query, and my colleague also worked on the backend, for example on pagination and part of the tests.
 
The main features were poll creation, single and multiple choice, anonymous voting, poll expiration, real-time results and management of your own polls.
 
We started with the data model and the API contracts, using Zod schemas shared between the frontend and the backend. Then we built vertical slices from the endpoint to the UI and the tests. We did not block each other. While I built an endpoint, my colleague worked with MSW mocks based on the agreed contract.

## Gamechanger and uniqueness
 
It was the real-time results. The organizer shows the screen, the participants vote from their phones, and the bars grow instantly. This makes a poll a live event, and it is what separates the product from ordinary forms. The server pushes updates to the clients through WebSocket or SSE, so the API is not loaded by constant polling.
 
I think about security and data integrity, and not only about making things work. For example, I care about duplicate vote protection, rate limiting, secure cookies, Helmet and unified validation. I also cover the code with tests (Vitest, RTL, MSW, Supertest), so the project is easy to change without fear of breaking something.

## Most interesting task: duplicate vote protection
 
We needed to keep voting anonymous and still prevent double votes. I created a layered solution. It uses a session token in a cookie, with a database unique constraint on the pair "poll and session". It also uses a server-side IP check and rate limiting on the API.

The client and the API run on different origins, so I configured CORS with credentials and set the cookie with `HttpOnly`, `Secure` and `SameSite`. 

I am also honest about the limits. A user can clear cookies or change the network, so this protection reduces abuse but does not give an absolute guarantee. Strict voting would require authentication.

## Bug: race condition on votes
 
During a load test, two simultaneous requests from the same session sometimes both passed the check "has not voted yet", and the vote was stored twice. A check in the code does not protect against a race condition. So I moved the guarantee into the database. I added a unique index on `(poll_id, session_id)` and handled the uniqueness violation as "already voted". I also counted votes inside a transaction. The lesson is that invariants must be enforced by the database, and not only by the application.

## High load and fault tolerance

The main risk is many simultaneous connections to the live results and sudden bursts of votes. To handle this, I used aggregated counters instead of `COUNT(*)` on every update. I pushed updates in batches with a small interval (throttling) and did not send an event for every vote. I also added indexes on `poll_id`, a connection pool for PostgreSQL and rate limiting.
 
To scale to several Node instances, we need a shared broker such as Redis pub/sub. This way, an event reaches the clients that are connected to other instances.
 
For fault tolerance, we used health checks, container restarts, logging and error monitoring, and database backups. The client also reconnects automatically.

## Database
 
**Normalization.** The schema is normalized: `Poll` has `Option`, and `Option` has `Vote`, with a unique vote per session.

**Denormalization.** The vote counter is stored on the option and is updated in the same transaction as the vote insert. This way, the results request does not need to calculate an aggregate every time.

**N+1.** A typical Prisma trap is a loop over polls with a separate query for the options of each poll. I used `include` and `select` to load the relations in one query, and I watched the Prisma query logs.
 
**Indexes.** I added indexes on `poll_id` in `Option` and `Vote`, a unique composite index for votes, and an index on `expires_at` to select active polls.

## Layers
 
On the backend, Express has these layers. Routes contain the routing and middleware. Controllers parse the request and send the response. Services contain the business logic, such as voting rules and expiration. The data access layer uses Prisma. Finally, shared layers handle Zod validation, a unified error handler, logging and security middleware.
 
On the frontend, we have routing with TanStack Router, a data layer with TanStack Query and the API client, and UI components.

## Deployment

Locally, everything runs in Docker Compose, which includes the frontend, the API and PostgreSQL. For the cloud, GitHub Actions builds the images. The API runs in a container on ECS or EC2, and PostgreSQL runs on RDS. The frontend static files are stored on S3 and served through CloudFront. In front of the API, there is a load balancer with health checks. Prisma migrations run as a separate step during the release.
 
In the CI, we run ESLint, Prettier, Husky (pre-commit hooks) and unit and integration tests. In production, we have logs, a health check endpoint and error monitoring.

## Team
 
The team had two developers. I worked on the backend, the architecture and DevOps, and my colleague worked on the frontend and the UI. The customer, who was an event organizer, gave us the requirements and attended the demos.
 
We worked in Kanban with short iterations and a weekly demo. Every task was in a tracker and had its own branch. Every pull request had to pass the automated CI checks (ESLint, Prettier, tests) and a mandatory review by the other developer.
 
We fixed the API contract in advance in Zod schemas, so the frontend could work in parallel with MSW mocks. We discussed debatable architecture decisions, for example WebSocket or SSE and how to protect against duplicate votes, in a short call. Then we wrote the decision down in the README or in an ADR. For QA, we used automated tests and a manual check before each demo.
