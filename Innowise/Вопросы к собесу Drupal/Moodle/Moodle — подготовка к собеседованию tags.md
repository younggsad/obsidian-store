# ЧАСТЬ 1. ТЕОРИЯ

## 1.1 Что такое Moodle

Moodle — открытая система дистанционного обучения (LMS) на PHP. В ней есть курсы, активности (форумы, тесты, задания), записи пользователей на курсы, роли и права, журнал оценок, отчёты, уведомления. Лицензия GPL v3. Работает с MySQL/MariaDB, PostgreSQL, MS SQL Server.

Главная архитектурная идея: ядро не правят, всё расширяется плагинами. Даже форум и тест в самом Moodle — это плагины. Плагин кладётся в нужную папку, подчиняется соглашениям об именах и файлах, и Moodle сам его находит, устанавливает, создаёт таблицы, права, строки.

Код исторически процедурный, со множеством глобальных объектов. Постепенно в него приходят классы, пространства имён, автозагрузка, Mustache-шаблоны, hooks, типизированные API.

## 1.2 Из чего состоит установка

Три части. Код (каталог с исходниками). База данных. Каталог moodledata — внешняя папка, куда пишутся загруженные файлы, кэши, сессии (если файловые), временные данные. Moodledata не должна быть доступна из веба напрямую.

Конфигурация лежит в config.php: параметры БД, wwwroot, dataroot. Последней строкой config.php подключает lib/setup.php — это точка, где Moodle «оживает».

Начиная с Moodle 5.0 веб-доступный код переехал в подпапку public/, а в корне остались конфигурация и всё, что не должно быть видно из веба. Принципы разработки те же, меняются пути.

## 1.3 Как обрабатывается запрос

Moodle «много-входной»: у каждой страницы свой php-файл. Типичный скрипт начинается с подключения config.php. Дальше lib/setup.php подключается к БД, поднимает сессию, загружает кэши, определяет пользователя, создаёт глобальные объекты. Потом скрипт проверяет вход и права, настраивает страницу через $PAGE и выводит шапку, содержимое и подвал через $OUTPUT.

Глобальные объекты: $CFG (настройки), $DB (база), $USER (текущий пользователь), $PAGE (описание страницы), $OUTPUT (вывод), $COURSE (текущий курс), $SITE (курс-сайт), $SESSION (сессия). В функциях их надо объявлять через global.

## 1.4 Предметная область

Сайт содержит категории курсов, в категориях курсы, в курсах разделы, в разделах активности. Экземпляр активности привязан к курсу через course module (cm). Важно различать id экземпляра (в таблице самой активности, например forum) и id course module (в таблице course_modules). Это два разных числа.

Пользователь записывается на курс через плагин записи (enrol). Ему назначается роль (студент, преподаватель и т.д.).

## 1.5 Контексты, роли, права

Контекст — область, в которой действует право. Иерархия: система, категория, курс, модуль (активность), блок. Отдельно стоит контекст пользователя. Роль назначается в контексте, права наследуются вниз и могут быть переопределены.

Capability — конкретное право вида компонент/путь:имя, например mod/forum:replypost. Объявляется в db/access.php плагина. У права есть тип (read или write), уровень контекста, архетипы (какие стандартные роли получают его по умолчанию), битовая маска риска (например, RISK_XSS, RISK_PERSONAL).

В коде проверяют право, а не роль. has_capability возвращает true/false, require_capability выбрасывает исключение. Для курсов и активностей перед этим вызывают require_login с курсом и cm: он проверяет вход, запись на курс, видимость.

## 1.6 Плагины и frankenstyle

У каждого плагина есть тип и имя. Вместе они дают frankenstyle-имя: local_hello, mod_forum, block_html. Это же имя называется component и используется везде: в строках, правах, событиях, кэшах, таблицах, пространствах имён.

Типы: mod (активности), block (блоки), local (универсальный, для всего, что не подходит под другие), theme, auth, enrol, filter, format (форматы курсов), report, tool (админ-утилиты, в admin/tool), qtype (типы вопросов), repository, и много других. Для новых страниц, интеграций, обработчиков событий и веб-сервисов обычно берут local.

Минимальный плагин: version.php, языковой файл lang/en/компонент.php с ключом pluginname, и (в современных версиях обязательно для каталога) privacy provider.

## 1.7 version.php и обновления

В version.php задают component, version (формат ГГГГММДДNN), requires (минимальная версия Moodle), maturity, release, при необходимости dependencies. Moodle сравнивает version из файла с версией, записанной в БД. Если в файле число больше, запускается обновление: выполняется db/upgrade.php. Поэтому после любого изменения схемы или прав версию повышают и запускают php admin/cli/upgrade.php.

## 1.8 База данных

Всё обращение к БД идёт через $DB. Имена таблиц пишутся без префикса. В SQL таблицы берут в фигурные скобки {таблица}, Moodle сам добавит префикс. Значения подставляются через плейсхолдеры, знак вопроса или :имя, смешивать их нельзя.

Основные методы: get_record, get_records, get_field, get_records_sql, get_recordset, insert_record, update_record, delete_records, record_exists, count_records, get_in_or_equal. Для разных СУБД есть хелперы sql_like, sql_concat и т.д.

Схема таблиц описывается в db/install.xml (создаётся при первой установке). Изменения для уже существующих сайтов оформляются в db/upgrade.php через XMLDB API с обязательным upgrade_plugin_savepoint. Генерировать XML удобнее в админском XMLDB-редакторе. Поле id в таблице обязательно. Название таблицы вместе с именем без префикса не должно превышать 28 символов.

## 1.9 Безопасность

Входные данные берутся через required_param и optional_param с типом PARAM_*, прямой доступ к $_GET и $_POST не используется. Защита от XSS: format_string для заголовков, format_text для HTML из редактора, s() для произвольных строк, автоэкранирование в Mustache. Защита от SQL-инъекций: только плейсхолдеры. Защита от CSRF: sesskey. Формы moodleform проверяют его сами, для ссылок с действиями используют sesskey() и require_sesskey().

## 1.10 Вывод страницы

На странице обязательно задать URL и контекст ($PAGE->set_url, $PAGE->set_context), затем заголовки. Дальше header, содержимое, footer.

Современный подход: данные готовит PHP-класс (renderable/templatable с методом export_for_template), а HTML делает Mustache-шаблон из templates/. Mustache не содержит логики: всё, что нужно (флаги, отформатированные даты), готовится в PHP. Один и тот же шаблон можно отрисовать и на сервере, и в JavaScript через core/templates.

Формы делаются на классе moodleform: определение полей в definition(), типы данных через setType, валидация в validation(), обработка через is_cancelled() и get_data().

## 1.11 Языковые строки

Все тексты интерфейса лежат в lang/<язык>/<компонент>.php и получаются через get_string('ключ', 'компонент', $a). Английская версия обязательна. Строки не склеивают из кусков, а используют плейсхолдеры. Ключи расположены по алфавиту. Строки кэшируются, поэтому после правок сбрасывают кэш.

## 1.12 Подсистемы, на которые плагины опираются

События (Events API). Ядро и плагины бросают события, другие плагины на них подписываются через db/events.php. События пишутся в журнал.

Задачи (Task API). Scheduled-задачи выполняются по расписанию из db/tasks.php, adhoc-задачи ставятся в очередь для разового фонового выполнения. Всё выполняет cron Moodle.

Веб-сервисы и external functions. Функция описывается в db/services.php и реализуется классом с методами execute_parameters, execute, execute_returns. Одна функция работает и через REST для внешних клиентов, и как AJAX-вызов из JS страницы (флаг ajax).

Hooks и callbacks. Старый способ расширения: функции с особым именем в lib.php плагина. Новый способ (с 4.3): типизированные hooks, подписка в db/hooks.php. Старые callbacks постепенно объявляются устаревшими.

Cache API (MUC). Определения кэшей в db/caches.php, режимы application, session, request, настраиваемые хранилища (файлы, Redis, Memcached).

Files API. Файл определяется набором: contextid, component, filearea, itemid, filepath, filename. Отдача файлов идёт через callback pluginfile, где обязательно проверять права.

Message API. Отправка уведомлений по каналам (email, push и др.), типы сообщений объявляются в db/messages.php.

Privacy API. Каждый плагин обязан описать, хранит ли он персональные данные, и уметь экспортировать и удалять их.

## 1.13 JavaScript

JS пишется модулями. Исходники лежат в amd/src (можно писать на ES6), собираются Grunt-ом в amd/build, собранные файлы коммитят. Подключение со страницы: $PAGE->requires->js_call_amd('компонент/модуль', 'функция', [параметры]). Серверные вызовы идут через core/ajax к external functions, строки через core/str, шаблоны через core/templates, уведомления через core/notification.

## 1.14 Активности и блоки

Активность (mod) состоит из таблицы экземпляров, lib.php с функциями hello_add_instance, hello_update_instance, hello_delete_instance, hello_supports, формы mod_form.php, страницы view.php и index.php, прав addinstance и view. Для полноценной интеграции добавляют резервное копирование (backup/moodle2), журнал оценок, отслеживание завершения.

Блок — класс block_имя, наследует block_base, методы init, get_content, applicable_formats. Для добавления блока нужны права addinstance и myaddinstance.

## 1.15 Тестирование и отладка

PHPUnit для PHP: тесты в tests/, класс наследует advanced_testcase, resetAfterTest откатывает БД, генераторы создают пользователей, курсы, активности. Behat для сценариев в браузере на Gherkin.

Отладка: режим DEVELOPER в настройках или в config.php, отладка через Xdebug, сброс кэшей командой admin/cli/purge_caches.php, режим дизайнера темы и выключение кэша JS для разработки. Для проверки качества плагина: moodle-plugin-ci (phpcs, phpdoc, phpunit, behat, grunt, mustache lint).

## 1.16 Золотые правила

Ядро не трогаем. Всё делаем через API. Права проверяем всегда, в правильном контексте. Весь вывод экранируем, весь SQL через плейсхолдеры. Изменил схему или права — поднял version. Пишем Privacy provider, тесты и документацию с первого дня.

# ЧАСТЬ 2. ВОПРОСЫ И ОТВЕТЫ

## Блок A. Общие вопросы

### 1. Что такое Moodle и из чего он состоит?

**Коротко.** Это открытая LMS на PHP: курсы, активности, пользователи, роли, оценки. Состоит из ядра и плагинов, причём даже форум и тесты — это плагины. Данные хранятся в SQL-базе, файлы в каталоге moodledata.

**Развёрнуто.** Три части установки: код, база данных, moodledata. Расширение только через плагины разных типов (mod, block, local, theme, auth, enrol и т.д.). Ядро предоставляет API: база ($DB), права (capabilities), вывод ($OUTPUT, Mustache), формы, события, задачи, веб-сервисы, кэш, файлы, сообщения.

**Подвох.** Не говори «это CMS». Moodle — LMS, у него предметная область обучения (курсы, записи, оценки), а не универсальное управление контентом.

### 2. Чем Moodle отличается от обычной CMS (например, Drupal или WordPress) с точки зрения разработчика?

**Коротко.** В Moodle предметная область уже зашита: курсы, записи на курс, роли в контекстах, журнал оценок. Расширение идёт плагинами по строгим соглашениям о папках и именах, а код ближе к процедурному стилю с глобальными объектами.

**Развёрнуто.** У Moodle собственный слой БД ($DB) вместо ORM или сущностей, собственная система прав на контекстах (более гибкая и привязанная к курсам, чем простые роли), своя форма-библиотека moodleform, свои Mustache-шаблоны. Нет единого роутера, у каждой страницы свой скрипт (в 4.5/5.0 появился новый routing для части маршрутов). В Drupal больше опоры на Symfony, внедрение зависимостей, конфигурацию в YAML и сущности. Принцип «ядро не правим, пишем плагин» общий.

**Подвох.** Не критикуй Moodle как «старый». Скажи нейтрально: стиль исторически сложился, но современные версии активно движутся к классам, hooks и типизированным API.

### 3. Что такое moodledata и зачем она нужна?

**Коротко.** Это каталог вне веб-корня, куда Moodle пишет загруженные файлы, кэши, временные данные, иногда сессии. Путь задаётся в $CFG->dataroot.

**Развёрнуто.** Файлы пользователей хранятся там в виде хэшированных имён (дедупликация по содержимому), а метаданные лежат в таблице files. Каталог должен быть доступен на запись веб-серверу и недоступен из веба, иначе утекут приватные файлы. В кластере moodledata делают общей (NFS и аналоги), а кэши и сессии выносят в Redis/Memcached.

**Подвох.** Нельзя «просто скопировать БД», нужно переносить и moodledata, иначе файлы пропадут.

### 4. Какова структура каталогов Moodle и что изменилось в 5.0?

**Коротко.** В корне ядра папки по типам плагинов: mod, blocks, local, theme, auth, enrol, admin/tool, lib и т.д. В 5.0 веб-доступный код переехал в public/, в корне остались конфигурация и непубличные файлы.

**Развёрнуто.** Плагины ставятся в папку по типу: local/имя, mod/имя, blocks/имя, admin/tool/имя, course/format/имя, question/type/имя. В 5.x те же папки лежат внутри public/. Это сделано для безопасности (в веб-корне только то, что должно быть доступно) и для будущего routing. Для разработчика плагина внутренняя структура плагина не меняется.

**Подвох.** Если не уверен в деталях конкретного релиза, скажи это прямо и укажи, где проверишь (moodledev.io, notes релиза).

### 5. Как Moodle обрабатывает запрос? Что делает config.php?

**Коротко.** Скрипт подключает config.php, тот читает настройки и подключает lib/setup.php. Setup подключается к БД, создаёт сессию, загружает кэши, определяет пользователя и создаёт глобальные объекты. После этого выполняется код страницы.

**Развёрнуто.** Дальше типичный скрипт вызывает require_login, require_capability, настраивает $PAGE (URL, контекст, заголовок), выводит header, содержимое и footer. Setup — это «точка загрузки ядра», поэтому require lib/setup.php должен быть последней строкой config.php.

**Подвох.** Забытый $PAGE->set_url вызывает ошибку кодирования, а забытый require_login оставляет страницу открытой всем.

### 6. Какие глобальные объекты есть в Moodle и зачем?

**Коротко.** $CFG конфигурация, $DB база, $USER текущий пользователь, $PAGE описание страницы, $OUTPUT вывод, $COURSE текущий курс, $SITE курс сайта, $SESSION сессия.

**Развёрнуто.** $COURSE заполняется после require_login с курсом. $SITE — запись курса с id=1. Внутри функций их объявляют через global. В современном коде их стараются не использовать глубоко внутри классов: передают нужные данные параметрами, чтобы код было проще тестировать.

**Подвох.** $USER хранит данные сессии, а не всегда свежие данные из БД. Для актуальных данных пользователя берут запись из таблицы user.

## Блок B. Плагины

### 7. Какие типы плагинов бывают и как выбрать тип?

**Коротко.** Основные: mod, block, local, theme, auth, enrol, filter, format, report, tool, qtype, repository. Если нужна новая активность в курсе — mod, блок на странице — block, остальное чаще всего local.

**Развёрнуто.** Local — универсальный тип для новых страниц, обработчиков событий, веб-сервисов, интеграций. Tool — для административных утилит. Report — для отчётов. Theme — для оформления. Auth и enrol — для способов входа и записи на курс. Выбор типа определяет папку и набор обязательных файлов.

**Подвох.** Не используй mod там, где достаточно local: mod тянет за собой резервное копирование, оценки, завершение, права на экземпляр, это много работы.

### 8. Что такое frankenstyle?

**Коротко.** Это схема именования компонента: тип_имя, например local_hello, mod_forum. Это имя используется в строках, правах, событиях, кэшах, названиях таблиц и пространствах имён.

**Развёрнуто.** Таблицы называются с префиксом компонента (local_hello_msg), функции в lib.php тоже (local_hello_extend_navigation), для mod функции начинаются с имени без mod_ (hello_add_instance). Пространство имён классов совпадает с компонентом, поэтому автозагрузка находит класс по пути внутри classes/.

**Подвох.** Имя плагина без подчёркиваний в самой части «имя», иначе Moodle не сможет разобрать компонент.

### 9. Какие файлы обязательны в плагине?

**Коротко.** version.php и языковой файл lang/en/компонент.php с ключом pluginname. Для публикации также Privacy provider. Остальное по необходимости.

**Развёрнуто.** Дальше добавляются: db/install.xml и upgrade.php (таблицы), db/access.php (права), settings.php (настройки), lib.php (callbacks), classes/ (код), templates/ (шаблоны), amd/ (JS), tests/ (тесты). У mod обязательны ещё mod_form.php, view.php, функции add/update/delete instance.

**Подвох.** Если имя папки не совпадает с component в version.php, Moodle откажется устанавливать плагин.

### 10. Как Moodle узнаёт, что плагин нужно установить или обновить?

**Коротко.** Сравнивает version из version.php с версией в БД. Нет записи — установка, число больше — обновление. Проверка выполняется при заходе админа в админку или через php admin/cli/upgrade.php.

**Развёрнуто.** При установке выполняется db/install.xml и (для некоторых типов) install.php. При обновлении выполняется db/upgrade.php. Параллельно регистрируются права из access.php, события, задачи, веб-сервисы, кэши. Поэтому после изменения любого из этих файлов повышают version.

**Подвох.** Поменял db/access.php, но не поднял version — новое право не появится.

### 11. Как менять схему БД у уже установленного плагина?

**Коротко.** Через db/upgrade.php: блок if ($oldversion < НОВАЯ_ВЕРСИЯ), внутри изменения через XMLDB API, затем upgrade_plugin_savepoint, и такая же версия в version.php. Параллельно обновляют install.xml, чтобы новые установки получали актуальную схему.

**Развёрнуто.** Пример: создать xmldb_table и xmldb_field, проверить field_exists, вызвать add_field. Проверки существования делают миграции идемпотентными. Для переименования, удаления полей, индексов, ключей есть соответствующие методы менеджера схемы ($DB->get_manager()). XMLDB-редактор в админке генерирует код для upgrade.php.

**Подвох.** Менять только install.xml недостаточно: он выполняется лишь при первой установке.

### 12. Как работает автозагрузка классов?

**Коротко.** Классы лежат в classes/, пространство имён начинается с компонента, остальное повторяет путь. \local_hello\form\message_form находится в local/hello/classes/form/message_form.php.

**Развёрнуто.** Карта классов кэшируется, поэтому после добавления нового класса нужно сбросить кэши. Файл с классом не подключают через require вручную, кроме случаев с устаревшими библиотеками (например, formslib для moodleform).

**Подвох.** «Class not found» после добавления класса почти всегда лечится сбросом кэшей или исправлением namespace.

### 13. В чём разница между local, mod и block на практике?

**Коротко.** Mod — активность внутри курса (со своими экземплярами, оценками, резервными копиями). Block — виджет на странице. Local — всё остальное, без привязки к курсу как к контейнеру.

**Развёрнуто.** Экземпляр mod создаёт преподаватель, он попадает в course_modules, участвует в резервном копировании и доступе. Блок добавляется на страницу и показывает контент. Local не имеет собственного UI-контейнера: сам решает, какие страницы, пункты навигации и обработчики добавить.

**Подвох.** Для небольшой функции «страница + таблица + право» хватит local, не усложняй.

## Блок C. База данных

### 14. Почему в Moodle нельзя использовать PDO или mysqli напрямую?

**Коротко.** Moodle поддерживает несколько СУБД, и $DB скрывает различия, добавляет префиксы, плейсхолдеры, профилирование, транзакции и работу с тестовой БД.

**Развёрнуто.** Прямой доступ ломает переносимость (разный SQL), обход префиксов, тесты (PHPUnit использует отдельный префикс и откат), безопасность (единые плейсхолдеры). Для кроссплатформенных конструкций есть хелперы: sql_like, sql_concat, sql_compare_text, sql_cast_char2int.

**Подвох.** На проверке кода прямое обращение к БД почти всегда отклоняют.

### 15. get_record, get_records, get_recordset: в чём разница?

**Коротко.** get_record возвращает одну запись, get_records — массив записей с ключом по первому полю, get_recordset — итератор, который не грузит всё в память.

**Развёрнуто.** Для больших выборок используют recordset и обязательно закрывают его ($rs->close()), иначе утечка соединения. У get_record есть режимы: IGNORE_MISSING (вернуть false), IGNORE_MULTIPLE (взять первую), MUST_EXIST (выбросить исключение, если нет).

**Подвох.** В get_records первое поле выборки становится ключом массива. Если оно не уникально, строки «перезапишут» друг друга. Поэтому в запросах с JOIN первым полем ставят уникальный id.

### 16. Как безопасно подставлять значения в SQL и как делать IN?

**Коротко.** Только плейсхолдеры: ? или :имя, без смешивания. Для IN используют get_in_or_equal.

**Развёрнуто.** Пример: [$insql, $params] = $DB->get_in_or_equal($ids, SQL_PARAMS_NAMED); дальше "WHERE id $insql". Таблицы в SQL пишутся как {имя}, чтобы Moodle подставил префикс. Динамические имена колонок или сортировку по пользовательскому вводу сверяют по белому списку.

**Подвох.** Конкатенация пользовательских данных в SQL недопустима, даже «очищенных».

### 17. Как работают транзакции в Moodle?

**Коротко.** $transaction = $DB->start_delegated_transaction(); внутри операции; в конце $transaction->allow_commit(). При исключении вызывают rollback($e). Транзакции вложенные: реальная фиксация происходит на самом внешнем уровне.

**Развёрнуто.** Делегированная транзакция позволяет вызывать функции, которые сами открывают транзакции, не ломая внешнюю. Если внутренний код сделал rollback, внешний уровень тоже будет откачен. Это связано и с событиями: наблюдатели с internal=false откладываются до фиксации транзакции.

**Подвох.** Не оставляй транзакцию «висеть» без allow_commit или rollback.

### 18. Как создаётся таблица и как её менять?

**Коротко.** Схема описывается в db/install.xml (удобно через XMLDB-редактор), изменения идут через db/upgrade.php с повышением version.

**Развёрнуто.** Обязательны поле id и первичный ключ. Для внешних ключей объявляют KEY type=foreign. Индексы описывают в INDEXES. Имя таблицы не длиннее 28 символов без префикса. Для запросов, по которым часто фильтруют, добавляют индексы.

**Подвох.** Забытый индекс по полю фильтрации — самая частая причина медленных страниц на больших данных.

## Блок D. Безопасность и права

### 19. Как устроена система ролей и прав?

**Коротко.** Права (capabilities) объявляются в db/access.php. Роли получают их в контекстах (система, категория, курс, модуль, блок), права наследуются вниз и могут быть переопределены. В коде проверяют право, а не роль.

**Развёрнуто.** Значения: CAP_ALLOW, CAP_PREVENT, CAP_PROHIBIT (жёсткий запрет, не переопределяется ниже), CAP_INHERIT. Архетипы в access.php задают, какие стандартные роли получают право по умолчанию. Админ может менять и переопределять права через интерфейс.

**Подвох.** Проверка вида «если у пользователя роль teacher» — плохая практика: роли переименовывают и создают новые.

### 20. В чём разница между require_login и require_capability?

**Коротко.** require_login проверяет, что пользователь вошёл (и при передаче курса и cm — что он имеет доступ к курсу и активности). require_capability проверяет конкретное право в контексте.

**Развёрнуто.** Правильный порядок для страницы активности: require_login($course, true, $cm), затем require_capability('mod/x:view', context_module::instance($cm->id)). Для функций, которые должны возвращать результат, а не прерываться исключением, используют has_capability.

**Подвох.** require_login без права даёт доступ любому вошедшему, включая гостя или студента без нужной роли.

### 21. Как получать параметры запроса?

**Коротко.** Через required_param и optional_param с типом PARAM_*, например PARAM_INT. Прямое чтение $_GET и $_POST не используется.

**Развёрнуто.** Тип выполняет очистку: PARAM_INT оставит число, PARAM_ALPHANUMEXT буквы, цифры, подчёркивание и дефис, PARAM_TEXT уберёт теги. PARAM_RAW не очищает, поэтому с ним нужна отдельная валидация и аккуратный вывод.

**Подвох.** В moodleform забывают setType для полей, из-за чего значение не очищается и Moodle выдаёт предупреждение при отладке.

### 22. Как в Moodle защититься от XSS, CSRF и SQL-инъекций?

**Коротко.** XSS: format_string, format_text, s(), автоэкранирование Mustache. CSRF: sesskey (moodleform делает сам, для ссылок require_sesskey). SQL: плейсхолдеры.

**Развёрнуто.** В Mustache {{var}} экранирует, {{{var}}} нет, поэтому тройные скобки допустимы только для уже безопасного HTML. Права проверяют на сервере всегда, даже если кнопку «не показали». Для данных, чувствительных к XSS, у права ставят riskbitmask (например, RISK_XSS), чтобы админ видел риск при выдаче.

**Подвох.** Скрыть кнопку в интерфейсе — не защита. Проверка должна быть на сервере.

### 23. Как проверить доступ пользователя к конкретной активности?

**Коротко.** Получить cm, вызвать require_login($course, true, $cm), затем проверить право в context_module::instance($cm->id).

**Развёрнуто.** get_course_and_cm_from_cmid или get_fast_modinfo дают курс и cm. require_login учитывает запись на курс, видимость, ограничения доступа и режим гостя. Дальше проверяется конкретное право (view, submit и т.д.).

**Подвох.** Нужно различать id экземпляра и id course module. В URL обычно приходит id cm, а в таблице активности ищут по instance.

## Блок E. Вывод и интерфейс

### 24. Как выводить HTML: renderer, renderable, Mustache?

**Коротко.** PHP-класс (renderable/templatable) готовит данные в export_for_template, Mustache-шаблон из templates/ делает HTML, renderer связывает их. Для простых случаев достаточно $OUTPUT->render_from_template.

**Развёрнуто.** Mustache не содержит логики. Всё, что нужно шаблону (флаги hasmessages, отформатированные даты, готовые строки), считается в PHP. В шаблоне обязателен docblock с @template и примером контекста в JSON. Тот же шаблон можно отрисовать из JavaScript через core/templates, что упрощает AJAX-обновления.

**Подвох.** Тройные фигурные скобки отключают экранирование. Используй их только для заведомо безопасного HTML.

### 25. Как делать формы?

**Коротко.** Через moodleform: определить поля в definition(), указать типы setType, добавить правила и validation(). На странице: is_cancelled(), get_data(), display().

**Развёрнуто.** Форма сама проверяет sesskey, очищает данные по setType, показывает ошибки. Есть элементы для файлов (filemanager), редактора, дат, автодополнения. Для предзаполнения используют set_data. Для форм активностей (mod) наследуются от moodleform_mod, которая добавляет стандартные блоки (описание, доступность, завершение).

**Подвох.** Форма, не обрабатывающая случай «данные не пришли», показывает пустую страницу после сохранения. Всегда делай redirect после успешного сохранения (паттерн Post/Redirect/Get).

### 26. Как работают языковые строки?

**Коротко.** Строки лежат в lang/<язык>/<компонент>.php, получаются через get_string('ключ', 'компонент', $a). Английский файл обязателен, остальные языки добавляются по желанию.

**Развёрнуто.** Параметры подставляются плейсхолдерами {$a} или {$a->поле}. Строки не склеивают из кусков, потому что в других языках другой порядок слов. Ключи сортируются по алфавиту. В JS используют core/str. После правки строк сбрасывают кэш, иначе увидишь старое значение или [[ключ]].

**Подвох.** Название права ($string['hello:view']) и описание события тоже живут в языковом файле. Забытая строка показывает [[ключ]] в интерфейсе.

### 27. Как подключить JavaScript и как он собирается?

**Коротко.** Исходники в amd/src, сборка Grunt-ом в amd/build, подключение $PAGE->requires->js_call_amd('компонент/модуль', 'функция', [параметры]).

**Развёрнуто.** Модуль можно писать на ES6 (import/export). Собранные .min.js и .map коммитят в репозиторий, потому что на сервере сборки нет. Серверные вызовы идут через core/ajax к external functions с флагом ajax. Обновления интерфейса делают через core/templates.

**Подвох.** «Не обновляется JS» обычно означает, что не выполнен grunt amd или не сброшены кэши.

## Блок F. Подсистемы

### 28. Что такое Events API и как им пользоваться?

**Коротко.** Ядро и плагины бросают события (класс наследует \core\event\base, вызывается ->trigger()), другие плагины подписываются через db/events.php, а обработчик — метод класса. События пишутся в журнал.

**Развёрнуто.** В событии задают crud (c, r, u, d), edulevel, objecttable, имя и описание. Наблюдатель получает объект события с данными (userid, relateduserid, objectid, contextid, other). По умолчанию наблюдатели выполняются сразу, но можно отложить до фиксации транзакции (internal=false).

**Подвох.** Тяжёлую работу в наблюдателе делать не нужно: поставь adhoc-задачу в очередь.

### 29. Какие бывают задачи cron и когда что использовать?

**Коротко.** Scheduled task выполняется по расписанию (db/tasks.php), adhoc task ставится в очередь для разового фонового выполнения. Всё запускает cron Moodle.

**Развёрнуто.** Scheduled — для регулярных операций (очистка, синхронизация). Adhoc — для тяжёлых действий по требованию (рассылка, пересчёт), данные передаются через set_custom_data. Класс scheduled-задачи наследует \core\task\scheduled_task, задаёт get_name() и execute(). Cron должен быть настроен в ОС каждую минуту.

**Подвох.** Задача должна быть идемпотентной: при сбое её могут запустить повторно.

### 30. Как сделать API, чтобы внешний клиент и мой JS могли вызывать код плагина?

**Коротко.** External function: объявить в db/services.php, реализовать класс с execute_parameters, execute, execute_returns. Флаг ajax даёт вызов из JS, для внешних клиентов настраивают сервис и токен.

**Развёрнуто.** Внутри execute: validate_parameters, validate_context, require_capability, затем логика. Возвращаемая структура описывается через external_single_structure и external_multiple_structure. Начиная с Moodle 4.2 классы находятся в пространстве core_external. Внешний клиент вызывает /webservice/rest/server.php с wstoken и wsfunction.

**Подвох.** Валидация параметров и проверка прав обязательны: функцию можно вызвать напрямую, минуя интерфейс.

### 31. Hooks и callbacks в lib.php: в чём разница?

**Коротко.** Callbacks — старый способ, функции с особым именем в lib.php. Hooks (с 4.3) — типизированные классы, подписка в db/hooks.php, обработчик в классе. Новое — hooks, старые callbacks постепенно помечаются устаревшими.

**Развёрнуто.** Hook-подход даёт явные типы, приоритеты, возможность тестирования и документацию. Если для нужной точки расширения в твоей версии есть hook, используют его. Свои hooks можно объявлять для расширения собственного плагина другими.

**Подвох.** Не все точки ядра уже переведены на hooks. Смотри документацию своей версии.

### 32. Как работает кэширование (MUC)?

**Коротко.** Cache API: определение в db/caches.php, использование через \cache::make(компонент, определение), методы get, set, delete, purge. Режимы application, session, request, хранилище настраивается админом.

**Развёрнуто.** Ключи можно делать простыми (simplekeys), задавать ttl, статическое ускорение, версионирование. На проде кэш выносят в Redis или Memcached. Отдельно кэшируются строки, шаблоны, JS, CSS темы.

**Подвох.** Кэшируя данные пользователя, не забывай учитывать контекст и права: общий кэш не должен «подсовывать» одному пользователю чужие данные.

### 33. Как Moodle хранит и отдаёт файлы?

**Коротко.** Через Files API: файл задаётся contextid, component, filearea, itemid, filepath и filename. Метаданные в таблице files, содержимое в moodledata. Отдача идёт через callback pluginfile.

**Развёрнуто.** Из формы файлы приходят в черновую область (draft), их переносят в постоянную через file_save_draft_area_files. В callback local_xxx_pluginfile обязательно проверяют вход и права, затем send_stored_file. Ссылку строят через moodle_url::make_pluginfile_url.

**Подвох.** Отдача файла без проверки прав — классическая дыра.

### 34. Зачем нужен Privacy API?

**Коротко.** Для соответствия GDPR: каждый плагин обязан описать, какие персональные данные он хранит, и уметь их экспортировать и удалять. Если данных нет, используется null_provider.

**Развёрнуто.** Реализуются интерфейсы metadata\provider и plugin\provider: описание хранимых данных, поиск контекстов пользователя, экспорт, удаление для пользователя и для контекста. Строки с описанием лежат в языковом файле (privacy:metadata:...).

**Подвох.** Плагин без provider не пройдёт проверку каталога и вызовет проблемы на сайтах с запросами на удаление данных.

### 35. Как отправить пользователю уведомление?

**Коротко.** Message API: объявить провайдер в db/messages.php, собрать \core\message\message (component, name, userfrom, userto, subject, fullmessage...) и вызвать message_send.

**Развёрнуто.** Доставка идёт по каналам, настроенным у пользователя (email, push, внутреннее сообщение). Для разовых баннеров на странице используют \core\notification::success() или redirect с типом уведомления.

**Подвох.** Для имени провайдера нужна строка messageprovider:имя в языковом файле.

## Блок G. Активности, блоки, оценки

### 36. Из чего состоит модуль активности?

**Коротко.** version.php, lib.php (hello_add_instance, update_instance, delete_instance, supports), mod_form.php, view.php, index.php, db/install.xml (таблица экземпляров), db/access.php (права), языковой файл.

**Развёрнуто.** Таблица экземпляров называется как модуль (hello), с полями id, course, name, intro, introformat, timemodified. hello_supports объявляет возможности (описание, резервное копирование, оценки, завершение). Для полноты добавляют backup/moodle2 (резервное копирование и восстановление), интеграцию с журналом оценок (grade_update) и правила завершения активности.

**Подвох.** Файл языковых строк mod-плагина называется hello.php, без префикса mod_.

### 37. В чём разница между id экземпляра и id course module?

**Коротко.** Course module — привязка активности к курсу и разделу (таблица course_modules). Instance — запись самой активности (например, в таблице forum). Это разные числа.

**Развёрнуто.** В URL обычно приходит id cm (view.php?id=...). Экземпляр получают как $cm->instance. Контекст модуля строится от cm: context_module::instance($cm->id), а не от instance.

**Подвох.** Попытка искать запись в таблице активности по cm id даёт чужую или пустую запись.

### 38. Как устроен блок?

**Коротко.** Класс block_имя extends block_base в файле blocks/имя/block_имя.php. Методы: init (заголовок), get_content (содержимое), applicable_formats (где можно добавлять). Права addinstance и myaddinstance в access.php.

**Развёрнуто.** has_config() включает settings.php, instance_allow_multiple разрешает несколько экземпляров. Для сложного контента используют renderer и Mustache.

**Подвох.** Без права addinstance блок нельзя добавить на страницу.

### 39. Как активность интегрируется с оценками и завершением?

**Коротко.** Оценки через grade_update и функции hello_grade_item_update, завершение через стандартные правила и FEATURE_COMPLETION_* в supports, а пользовательские правила через классы custom_completion.

**Развёрнуто.** Активность объявляет, что поддерживает оценку (FEATURE_GRADE_HAS_GRADE), создаёт grade item при создании экземпляра и обновляет оценки пользователей. Для завершения указывают, отслеживает ли она просмотр, оценку и свои условия. Это попадает в журнал оценок и отчёты завершения курса.

**Подвох.** Для таких деталей на собеседовании честно говори, какие функции помнишь, и что точные сигнатуры смотришь в документации.

## Блок H. Практика и инженерия

### 40. Как тестировать плагины?

**Коротко.** PHPUnit для PHP (класс наследует advanced_testcase, resetAfterTest, генераторы данных), Behat для сценариев в браузере. CI на базе moodle-plugin-ci.

**Развёрнуто.** PHPUnit использует отдельную БД и dataroot, настраиваемые в config.php, и инициализируется командой admin/tool/phpunit/cli/init.php. Генераторы создают пользователей, курсы, записи, активности. Behat описывает сценарии на Gherkin и запускает их в браузере (Selenium/Chrome).

**Подвох.** Забытый resetAfterTest приводит к «протеканию» данных между тестами.

### 41. Как отлаживать и что делать, если «ничего не обновляется»?

**Коротко.** Включить режим DEVELOPER, смотреть логи, подключить Xdebug. Для «не обновляется»: purge_caches, поднять version при изменении db/, пересобрать JS.

**Развёрнуто.** В разработке отключают кэш JS и строк, включают режим дизайнера темы. Чек-лист: изменил PHP — обнови страницу; изменил строки, шаблоны, классы или db/*.php — сбрось кэши; изменил схему или права — подними version и запусти upgrade; изменил JS — grunt amd.

**Подвох.** Правка файла на сервере без сброса кэша — причина большинства «Moodle не видит мои изменения».

### 42. Как оптимизировать медленную страницу?

**Коротко.** Найти узкое место (профилирование, perfdebug), убрать запросы в цикле (N+1), добавить индексы, кэшировать дорогие данные, вынести тяжёлое в adhoc-задачи.

**Развёрнуто.** Использовать JOIN вместо запросов в цикле, get_fast_modinfo вместо отдельных запросов по активностям, recordset для больших выборок, постраничность вместо загрузки всего. Выносить кэши в Redis, сессии в Redis или БД, включать OPcache. Для тяжёлых отчётов — предрасчёт по cron.

**Подвох.** Оптимизировать «вслепую» не стоит: сначала измерения, потом правки.

### 43. Почему нельзя править ядро и как обновлять сайт с плагинами?

**Коротко.** Правки ядра ломаются при обновлении и делают поддержку невозможной. Все изменения делают плагином, а перед обновлением Moodle проверяют совместимость плагинов и тестируют на копии.

**Развёрнуто.** Каждый релиз Moodle может менять API и помечать устаревшее. Плагин указывает minimum requires и при необходимости supported-версии. Перед апгрейдом: резервная копия БД и moodledata, тест на копии, проверка плагинов, затем php admin/cli/upgrade.php в режиме обслуживания (admin/cli/maintenance.php).

**Подвох.** Правки темы тоже делают через дочернюю тему, а не правкой Boost.

### 44. Как бы вы реализовали: при завершении курса отправлять пользователю письмо и записывать факт в свою таблицу?

**Коротко.** Local-плагин с наблюдателем на \core\event\course_completed в db/events.php. В обработчике — запись в свою таблицу и постановка adhoc-задачи на отправку письма через Message API.

**Развёрнуто.** Таблица описывается в install.xml, право и privacy provider добавляются сразу. Обработчик делает минимум (insert и queue_adhoc_task), письмо отправляется в задаче через message_send. Для настроек (включить, текст письма) добавляют settings.php. Пишут PHPUnit-тест на наблюдатель.

**Подвох.** Не отправляй письмо прямо в наблюдателе: это замедлит запрос пользователя и усложнит повтор при ошибке.

### 45. Как бы вы сделали страницу отчёта, доступную только преподавателям курса?

**Коротко.** Плагин типа report (или local) со страницей, где require_login($course), контекст курса и require_capability с собственным правом, которое по архетипу получает editingteacher и teacher.

**Развёрнуто.** Право объявляется в access.php (captype read, contextlevel CONTEXT_COURSE). Страница получает id курса через required_param, строит SQL по записанным пользователям с учётом групп, выводит через Mustache, добавляет пункт в навигацию курса через callback или hook. Большие отчёты нужно разбивать на страницы.

**Подвох.** Не забыть учесть режим групп и то, что преподаватель должен видеть только своих студентов.

### 46. Как реализовать AJAX-кнопку, которая меняет данные без перезагрузки страницы?

**Коротко.** External function с флагом ajax в db/services.php, JS-модуль вызывает её через core/ajax, затем обновляет интерфейс (через core/templates). На сервере — проверка параметров и права.

**Развёрнуто.** JS: Ajax.call с methodname и args, обработка ошибок через Notification.exception. На сервере: validate_parameters, validate_context, require_capability, изменение данных, возврат структуры. Сборка JS обязательна (grunt amd).

**Подвох.** Нельзя полагаться на проверку на клиенте: функцию можно вызвать напрямую.

### 47. Какие самые частые ошибки новичков в Moodle?

**Коротко.** Забывают require_login и require_capability, обращаются к $_GET, склеивают SQL, не поднимают version, не сбрасывают кэши, путают id cm и instance, не пишут Privacy provider.

**Развёрнуто.** Ещё: не задают $PAGE->set_url, выводят HTML без экранирования, используют PARAM_RAW везде, не закрывают recordset, не собирают JS, пишут тексты в коде вместо языковых строк, правят ядро.

**Подвох.** На собеседовании полезно сказать не только «как правильно», но и «как это обычно ломается» — это показывает практический опыт.

## Блок I. Как отвечать, если опыта мало

### 48. Что говорить, если вы чего-то не знаете или не помните деталей API?

**Коротко.** Честно обозначить границу и показать, как ты это решаешь: назвать подсистему и принцип, сказать, что точную сигнатуру проверишь на moodledev.io или по исходникам ядра.

**Развёрнуто.** Хороший шаблон: «Принцип такой... Точное имя метода в этой версии я бы проверил в документации. Если нужно, посмотрю, как это сделано в ядре, например в mod_forum». Ссылка на исходники ядра как образец показывает правильный рабочий процесс.

**Подвох.** Не выдумывай названия функций. Лучше сказать «не помню точно», чем назвать несуществующее.

### 49. Какие вопросы задать интервьюеру?

**Коротко.** Спросить про версию Moodle и процесс обновления, про то, какие плагины свои, а какие сторонние, про тесты и CI, про инфраструктуру (кэши, cron, масштабирование) и про code review.

**Развёрнуто.** Примеры: «Какая версия Moodle в проде и как часто обновляетесь?», «Есть ли у вас PHPUnit и Behat в CI?», «Как организована отладка и деплой плагинов?», «Есть ли форки ядра?» (хороший признак, если нет).

**Подвох.** Вопрос про зарплату и графики оставь на конец или на отдельный этап.

# ПРИЛОЖЕНИЕ. БЫСТРАЯ ПАМЯТКА ПЕРЕД СОБЕСЕДОВАНИЕМ

## Где что объявляется

- Версия и зависимости: version.php
- Таблицы: db/install.xml, миграции db/upgrade.php
- Права: db/access.php
- Строки: lang/en/компонент.php
- Настройки: settings.php
- События (подписка): db/events.php
- Задачи: db/tasks.php и classes/task/
- Веб-сервисы: db/services.php и classes/external/
- Кэши: db/caches.php
- Сообщения: db/messages.php
- Hooks: db/hooks.php
- Шаблоны: templates/*.mustache
- JS: amd/src → amd/build
- Privacy: classes/privacy/provider.php

## Скелет страницы

```php
require_once(__DIR__ . '/../../config.php');
require_login();
$context = context_system::instance();
require_capability('local/xxx:view', $context);
$PAGE->set_url(new moodle_url('/local/xxx/index.php'));
$PAGE->set_context($context);
$PAGE->set_title('...');
$PAGE->set_heading('...');
echo $OUTPUT->header();
// содержимое
echo $OUTPUT->footer();
```

## Цикл разработки

Правка кода, затем при изменении db, lang, классов, шаблонов сброс кэшей, при изменении version или db запуск upgrade, затем проверка в браузере.

## Пять фраз, которые стоит произнести в ответах

1. «Ядро не правим, расширяем плагином».
2. «Права проверяем на сервере, в нужном контексте, через capability, а не через роль».
3. «Весь SQL через $DB и плейсхолдеры, вывод экранируем».
4. «Изменил схему или права — поднимаю version и делаю upgrade».
5. «Тяжёлое выношу в adhoc-задачи, часто читаемое кэширую».
