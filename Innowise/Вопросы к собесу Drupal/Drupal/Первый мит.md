## 1. Переопределение меток и изменение чужих сущностей

### Главное правило

Код Drupal Core и чужих модулей не правят. Если его отредактировать, изменения пропадут при обновлении, а сайт сломается. Вместо этого в Drupal есть «точки расширения»: специальные хуки, подписчики на события, подмена сервисов, настройки, темизация.

### Как изменить название (label) и другие свойства чужой сущности

Описание. Тип сущности (например, node) описан в PHP-коде, в блоке `#[ContentEntityType]` или `#[ConfigEntityType]`. Это «паспорт» типа: название, таблица, классы формы и списка. Через админку его не изменить. Менять нужно из своего модуля с помощью хука `hook_entity_type_alter()`. Drupal собирает паспорта всех типов сущностей в один список и передаёт его в этот хук. Ключ списка это id типа (`node`, `user`), значение это объект с описанием. Берёшь нужный объект и меняешь его методами `setLabel()`, `setClass()` и подобными.

После изменения нужно очистить кеш (`drush cr`), потому что определения типов сущностей кешируются.

Пример.

```php
function mymodule_entity_type_alter(array &$entity_types) {
  $entity_types['node']->setLabel(t('Материал'));
}
```

Описание. `hook_entity_bundle_info_alter()` делает то же самое для bundle (подтипов, например «Статья» или «Страница» у node). Через него можно поменять название bundle и некоторые другие данные.

Пример.

```php
function mymodule_entity_bundle_info_alter(array &$bundles) {
  $bundles['node']['article']['label'] = t('Новость');
}
```

Описание. Для полей есть свои хуки. `hook_entity_base_field_info_alter()` меняет базовые поля чужой сущности (например, подпись поля title). `hook_entity_bundle_field_info_alter()` меняет поля, привязанные к bundle. Подписи полей, которые созданы через интерфейс (Field UI), хранятся в конфигурации, и менять их нужно там, а не кодом.

Пример.

```php
function mymodule_entity_base_field_info_alter(array &$fields, EntityTypeInterface $entity_type) {
  if ($entity_type->id() === 'node') {
    $fields['title']->setLabel(t('Название задачи'));
  }
}
```

### Чем отличается изменение конфигурации от изменения определения сущности

Описание. Есть два места, где лежат названия и настройки.

- Конфигурация (config): настройки сайта, которые хранятся в базе и выгружаются в YAML-файлы. Например, название типа материала `node.type.article` и подпись поля `field.field.node.article.field_x`. Меняются через админку, через `drush config:set` или импортом config. Переносятся между окружениями.
- Определение сущности: то, что записано в PHP-коде в атрибуте. Меняется только кодом (хук alter). В YAML не выгружается.

Правило: если значение лежит в config, меняй config. Если оно написано в коде, используй alter-хук.

### Как изменить метки форм, действий и ссылок

Описание.

- Подписи и элементы формы: `hook_form_alter()` и его варианты (разобраны ниже).
- Ссылки операций в списках (Edit, Delete): `hook_entity_operation_alter()`.
- Вкладки на странице (local tasks) и кнопки вида «Добавить ...» (local actions): `hook_menu_local_tasks_alter()` и `hook_menu_local_actions_alter()`.
- Пункты меню: `hook_menu_links_discovered_alter()`.
- Отдельные ссылки: `hook_link_alter()`.
- Адреса, заголовки и права маршрутов: класс RouteSubscriber, метод `alterRoutes()`.
- Простая замена текста интерфейса: перевод строки (locale) или `$settings['locale_custom_strings_en']` в settings.php.

Пример.

```php
// Меняем подпись кнопки в форме
$form['actions']['submit']['#value'] = t('Сохранить задачу');
```

### Когда использовать три вида form_alter

Описание. Все три хука позволяют изменить уже существующую форму. Разница в том, на какие формы они срабатывают.

- `hook_form_alter()` срабатывает на все формы сайта. Внутри надо проверять `$form_id`. Подходит, когда нужно изменить много разных форм одинаково.
- `hook_form_BASE_FORM_ID_alter()` срабатывает на семейство форм с одним базовым id. Например, `hook_form_node_form_alter()` сработает на формы создания и редактирования материалов любого типа.
- `hook_form_FORM_ID_alter()` срабатывает на одну конкретную форму. Это самый точный вариант и обычно лучший. Выбирай как можно более узкий хук.

Общие хуки вызываются раньше, конкретные позже.

Пример.

```php
// Только форма редактирования материала типа task
function mymodule_form_node_task_edit_form_alter(&$form, FormStateInterface $form_state) {
  $form['title']['widget'][0]['value']['#title'] = t('Название задачи');
}
```

### Когда нужны hook_theme(), preprocess и переопределение Twig

Описание. Это три разных инструмента для изменения HTML.

- `hook_theme()`: твой модуль регистрирует собственный шаблон. Нужен, когда создаёшь новый вывод, которого ещё нет.
- Preprocess-функция (`hook_preprocess_HOOK()`): меняет или добавляет переменные перед тем, как они попадут в шаблон. Шаблон остаётся прежним. Подходит, когда нужно добавить в шаблон новые данные или изменить имеющиеся.
- Переопределение Twig-шаблона: копируешь шаблон в свою тему и меняешь разметку. Подходит, когда нужно изменить сам HTML. Включи режим Twig debug, и Drupal покажет в HTML-комментариях имена шаблонов, которые он ищет.

Ещё два хука: `hook_theme_suggestions_HOOK_alter()` добавляет свои имена шаблонов, `hook_theme_registry_alter()` меняет то, как зарегистрирован чужой theme hook.

Пример.

```php
// Добавляем переменную в шаблон node
function mymodule_preprocess_node(array &$variables) {
  $variables['is_overdue'] = FALSE;
}
```

```
Шаблон в теме: templates/node--task--full.html.twig
```

### Как менять чужую функциональность без правки кода

Описание. Выбирай способы в таком порядке (от лучшего к худшему):

1. Настройки (config).
2. Alter-хуки.
3. Подписчик на события (event subscriber).
4. Подмена или декорирование сервиса.
5. Подмена класса обработчика или плагина через alter.
6. Тема (preprocess, Twig).
7. Патч через composer-patches. Это крайняя мера, и причину нужно записывать.

### Что запомнить

- Подпись поля: config (если поле из админки) или `hook_entity_base_field_info_alter()` (если базовое).
- Название типа сущности: `hook_entity_type_alter()`, `hook_entity_bundle_info_alter()` или config.
- Форма: `hook_form_FORM_ID_alter()`.
- HTML: preprocess и Twig.

## 2. Entity Handlers (обработчики сущностей)

### Что такое handler и зачем он нужен

Описание. Handler это класс, который выполняет одну роль для конкретного типа сущности. Одна роль: построить список, показать форму, проверить права, создать адреса страниц. Сам тип сущности только перечисляет, какой класс за что отвечает. Благодаря этому логика не свалена в одну кучу, и любую часть можно заменить отдельно.

Получить handler можно через EntityTypeManager: `getListBuilder()`, `getAccessControlHandler()`, `getFormObject($type, 'edit')`, `getStorage()`, `getViewBuilder()`.

### Основные handlers

Описание.

- storage: загружает и сохраняет сущности. По умолчанию подходит стандартный (SqlContentEntityStorage для контента).
- list_builder (EntityListBuilder): строит страницу со списком сущностей. Основные методы: `buildHeader()` (заголовки колонок), `buildRow($entity)` (одна строка), `getDefaultOperations()` (ссылки действий).
- form: формы для операций default, add, edit, delete. Базовые классы: ContentEntityForm, EntityForm, ContentEntityDeleteForm.
- access (EntityAccessControlHandler): отвечает на вопрос «можно ли пользователю сделать это с сущностью». Методы `checkAccess($entity, $operation, $account)` и `checkCreateAccess()` возвращают объект AccessResult (разрешено, запрещено, нет мнения). Операции: view, update, delete, create.
- views_data (EntityViewsData): рассказывает модулю Views, какие поля сущности можно использовать в отчётах и списках.
- route_provider: автоматически создаёт адреса (маршруты) для сущности по её `links`. Стандартные классы: DefaultHtmlRouteProvider и AdminHtmlRouteProvider (страницы в админской теме). Создаются маршруты canonical, add_form, edit_form, delete_form, collection.
- view_builder (EntityViewBuilder): показывает сущность на странице.

### Как подключить свой handler в #[ContentEntityType]

Описание. Handlers перечисляются в параметре `handlers` атрибута. Если handler не указан, соответствующей возможности у сущности нет. Например, без `route_provider` страницы сущности автоматически не появятся.

Пример (имена условные).

```php
#[ContentEntityType(
  id: 'time_log',
  label: new TranslatableMarkup('Time log'),
  handlers: [
    'list_builder' => TimeLogListBuilder::class,
    'form' => [
      'default' => TimeLogForm::class,
      'delete' => ContentEntityDeleteForm::class,
    ],
    'access' => TimeLogAccessControlHandler::class,
    'views_data' => EntityViewsData::class,
    'route_provider' => ['html' => AdminHtmlRouteProvider::class],
  ],
  base_table: 'time_log',
  admin_permission: 'administer time_log',
  entity_keys: ['id' => 'id', 'uuid' => 'uuid'],
  links: [
    'collection' => '/admin/content/time-log',
    'add-form' => '/admin/content/time-log/add',
    'edit-form' => '/admin/content/time-log/{time_log}/edit',
    'delete-form' => '/admin/content/time-log/{time_log}/delete',
  ],
)]
```

### Как создать класс handler и когда наследоваться от стандартного

Описание. Почти всегда наследуйся от стандартного класса и переопределяй только нужные методы. Писать handler с нуля почти не нужно. Если handler требует сервисы, у него вместо `create()` используется метод `createInstance(ContainerInterface $container, EntityTypeInterface $entity_type)`. Стандартные классы (например, EntityListBuilder) его уже содержат.

Пример.

```php
class TimeLogListBuilder extends EntityListBuilder {
  public function buildHeader() {
    $header['id'] = $this->t('ID');
    return $header + parent::buildHeader();
  }
  public function buildRow(EntityInterface $entity) {
    $row['id'] = $entity->id();
    return $row + parent::buildRow($entity);
  }
}
```

### Чем handler отличается от сервиса, плагина и контроллера

Описание.

- Сервис: один объект на весь сайт, объявлен в services.yml, не привязан к типу сущности.
- Handler: класс для одной роли конкретного типа сущности. Указан в описании типа сущности, создаётся менеджером сущностей.
- Плагин: один из многих вариантов одного вида (например, один из блоков). Drupal находит его сам по атрибуту.
- Контроллер: класс, привязанный к адресу (маршруту), который возвращает содержимое страницы.

### Что запомнить

Drupal узнаёт, какой класс отвечает за список, форму, права или адреса сущности, прочитав параметр `handlers` в описании типа. EntityTypeManager по id типа и названию роли находит этот класс и создаёт его.

## 3. Form API (формы)

### Базовые классы

Описание.

- FormBase: для обычной формы.
- ConfigFormBase: для формы настроек. Значения сохраняются в конфигурацию. Нужен метод `getEditableConfigNames()`, который возвращает список конфигураций, которые форма может менять.
- EntityForm и ContentEntityForm: для формы создания или редактирования сущности. Поля строятся автоматически, сущность сохраняется методом `save()`.

Форма подключается через маршрут: в routing.yml пишется `_form: '\Drupal\mymodule\Form\MyForm'`. Для сущностей форма подключается через `handlers` (см. раздел 2).

### Четыре основных метода

Описание.

- `getFormId()`: возвращает уникальное имя формы. По нему работает `hook_form_FORM_ID_alter()`.
- `buildForm()`: строит массив с описанием формы (поля, кнопки).
- `validateForm()`: проверяет введённые значения.
- `submitForm()`: выполняется, когда проверка пройдена. Здесь значения сохраняются.

Пример.

```php
class HoursForm extends FormBase {
  public function getFormId() {
    return 'mymodule_hours_form';
  }
  public function buildForm(array $form, FormStateInterface $form_state) {
    $form['hours'] = [
      '#type' => 'number',
      '#title' => $this->t('Часы'),
      '#required' => TRUE,
    ];
    $form['actions']['submit'] = ['#type' => 'submit', '#value' => $this->t('Сохранить')];
    return $form;
  }
  public function validateForm(array &$form, FormStateInterface $form_state) {
    if ($form_state->getValue('hours') <= 0) {
      $form_state->setErrorByName('hours', $this->t('Часы должны быть больше нуля.'));
    }
  }
  public function submitForm(array &$form, FormStateInterface $form_state) {
    $this->messenger()->addStatus($this->t('Сохранено: @h ч.', ['@h' => $form_state->getValue('hours')]));
  }
}
```

### Свойства элементов формы

Описание.

- `#type`: вид элемента (textfield, textarea, number, select, checkbox, checkboxes, radios, entity_autocomplete, submit, details, container).
- `#title`: подпись.
- `#default_value`: значение по умолчанию.
- `#required`: поле обязательно, Drupal сам покажет ошибку.
- `#options`: список вариантов для select, radios, checkboxes (ключ => подпись).
- `#states`: показывать, скрывать или блокировать поле в зависимости от другого поля, без написания JavaScript.

Пример.

```php
$form['reason'] = [
  '#type' => 'textfield',
  '#title' => t('Причина'),
  '#states' => [
    'visible' => [':input[name="status"]' => ['value' => 'blocked']],
  ],
];
```

### Валидация и submit-обработчики

Описание.

- Ошибка ставится вызовом `$form_state->setErrorByName('поле', 'текст')`. Если есть ошибки, `submitForm()` не вызывается и форма показывается снова с сообщениями.
- Проверки пиши в `validateForm()`, сохранение в `submitForm()`.
- Дополнительные обработчики добавляются в `$form['#validate'][]` и `$form['#submit'][]` (или на конкретную кнопку).
- Перенаправление после сохранения: `$form_state->setRedirect('имя.маршрута')`.

### Как получать и сохранять значения

Описание.

- Получить значение: `$form_state->getValue('имя')`. Все значения: `getValues()`.
- Если у формы стоит `'#tree' => TRUE`, вложенное значение берётся так: `getValue(['группа', 'поле'])`.
- Временные данные между шагами формы: `$form_state->set()` и `get()`.
- Сохранить в конфигурацию: `->set('ключ', $значение)->save()`.
- Сохранить в сущность: `$entity->set('поле', $значение)->save()`.

### Dependency Injection в формах

Описание. Форме часто нужны сервисы (например, EntityTypeManager). Их не берут из глобального `\Drupal::service()`. Вместо этого форма описывает их в конструкторе, а статический метод `create()` достаёт сервисы из контейнера и передаёт в конструктор. Drupal вызывает `create()` сам.

Пример.

```php
class MyForm extends FormBase {
  public function __construct(protected EntityTypeManagerInterface $entityTypeManager) {}

  public static function create(ContainerInterface $container) {
    return new static($container->get('entity_type.manager'));
  }
}
```

### hook_form_alter() и изменение существующих форм

Описание. Через `hook_form_FORM_ID_alter()` можно добавить поле в чужую форму, изменить подпись, скрыть элемент (`#access => FALSE`), добавить свою проверку и свой submit. Важно: добавленное поле само нигде не сохранится. Нужен свой submit-обработчик, который запишет значение.

Пример.

```php
function mymodule_form_node_task_edit_form_alter(&$form, FormStateInterface $form_state) {
  $form['my_note'] = ['#type' => 'textfield', '#title' => t('Заметка')];
  $form['#validate'][] = 'mymodule_task_validate';
  $form['actions']['submit']['#submit'][] = 'mymodule_task_submit';
}
```

### AJAX в формах

Описание. AJAX обновляет часть формы без перезагрузки страницы. Нужно три вещи.

1. В элементе указать `#ajax` с методом-обработчиком (`callback`), id блока для замены (`wrapper`) и событием (`event`).
2. Оформить обновляемый блок формы контейнером с этим id.
3. В методе-обработчике вернуть либо часть формы, либо объект AjaxResponse с командами. Команды: ReplaceCommand (заменить разметку), HtmlCommand (заменить содержимое), AppendCommand, InvokeCommand, CssCommand, MessageCommand, RedirectCommand.

Пример (зависимый список: при выборе проекта обновляются задачи).

```php
$form['project'] = [
  '#type' => 'select',
  '#title' => t('Проект'),
  '#options' => $projects,
  '#ajax' => [
    'callback' => '::updateTasks',
    'wrapper' => 'tasks-wrapper',
    'event' => 'change',
  ],
];
$form['tasks'] = [
  '#type' => 'select',
  '#title' => t('Задача'),
  '#options' => $tasks,
  '#prefix' => '<div id="tasks-wrapper">',
  '#suffix' => '</div>',
];

public function updateTasks(array &$form, FormStateInterface $form_state) {
  return $form['tasks'];
}
```

### Форма настроек и форма сущности

Описание.

- Форма настроек: класс на основе ConfigFormBase. В `buildForm()` значения берутся из `$this->config('mymodule.settings')`. В `submitForm()` они записываются в ту же конфигурацию и вызывается `parent::submitForm()`.
- Форма сущности: класс на основе ContentEntityForm, подключается через `handlers`. Доступна переменная `$this->entity`. Поля берутся из Form Display.

Пример (форма настроек).

```php
class SettingsForm extends ConfigFormBase {
  protected function getEditableConfigNames() {
    return ['mymodule.settings'];
  }
  public function getFormId() {
    return 'mymodule_settings';
  }
  public function buildForm(array $form, FormStateInterface $form_state) {
    $form['limit'] = [
      '#type' => 'number',
      '#title' => $this->t('Лимит часов'),
      '#default_value' => $this->config('mymodule.settings')->get('limit'),
    ];
    return parent::buildForm($form, $form_state);
  }
  public function submitForm(array &$form, FormStateInterface $form_state) {
    $this->config('mymodule.settings')->set('limit', $form_state->getValue('limit'))->save();
    parent::submitForm($form, $form_state);
  }
}
```

### Что запомнить

Нужно уметь: создать класс формы и маршрут, добавить поля с `#type`, проверить значения в `validateForm()`, сохранить их в `submitForm()` (в конфигурацию или в сущность) и добавить поле в уже существующую форму через `hook_form_FORM_ID_alter()`.

## 4. Services и Dependency Injection

### Что такое сервис и Service Container

Описание. Сервис это объект, который выполняет одну задачу и доступен по имени: работа с базой, доступ к сущностям, отправка почты, твоя бизнес-логика. Service Container это «склад и фабрика» сервисов. Он создаёт объекты по описанию и сам подставляет им нужные зависимости. Каждый сервис создаётся один раз и используется повторно.

### Как Drupal находит и создаёт сервисы

Описание. Drupal собирает файлы `MODULE.services.yml` всех включённых модулей и ядра, строит из них контейнер и кеширует его. Сервис создаётся только при первом обращении. Если ты изменил services.yml, нужно очистить кеш (`drush cr`), чтобы контейнер собрался заново.

### Собственный сервис в MODULE.services.yml

Описание. В файле указывается имя сервиса, его класс и аргументы (другие сервисы, имя которых начинается с `@`). Имя принято начинать с имени модуля. Дополнительные ключи: `tags` (например, event_subscriber), `calls` (вызвать метод после создания), `decorates` (обернуть чужой сервис), `autowire` (подставить зависимости автоматически по типам).

Пример.

```yaml
services:
  mymodule.task_stat:
    class: Drupal\mymodule\Service\TaskStatService
    arguments: ['@entity_type.manager', '@database']
```

### Внедрение зависимостей через конструктор

Описание. Все нужные сервисы класс получает в конструкторе и сохраняет в свойствах. Так сразу видно, от чего зависит класс, и в тестах эти зависимости легко заменить заглушками.

Пример.

```php
class TaskStatService {
  public function __construct(
    protected EntityTypeManagerInterface $entityTypeManager,
    protected Connection $database,
  ) {}
}
```

### Интерфейсы сервисов

Описание. Зависимость лучше указывать по интерфейсу (`EntityTypeManagerInterface`), а не по конкретному классу. Тогда реализацию можно заменить (декоратором или заглушкой в тесте), и остальной код менять не придётся. Для своих сервисов тоже стоит писать интерфейс.

### ContainerInterface, create() и фабричное создание

Описание. Некоторые классы создаёт не контейнер напрямую, а Drupal (формы, контроллеры, плагины, handlers). Чтобы такие классы получили сервисы, у них есть статический метод-фабрика:

- Контроллеры и формы: `create(ContainerInterface $container)`.
- Плагины: `create(ContainerInterface $container, array $configuration, $plugin_id, $plugin_definition)` (интерфейс ContainerFactoryPluginInterface).
- Handlers сущностей: `createInstance(ContainerInterface $container, EntityTypeInterface $entity_type)`. Внутри везде одно и то же: достать сервисы из контейнера и вернуть `new static(...)`.

Пример (контроллер).

```php
class StatController extends ControllerBase {
  public function __construct(protected TaskStatService $stat) {}

  public static function create(ContainerInterface $container) {
    return new static($container->get('mymodule.task_stat'));
  }
}
```

### Как передавать сервисы в разные классы

Описание.

- В другой сервис: список `arguments` в services.yml.
- В контроллер и форму: метод `create()` и конструктор.
- В плагин: ContainerFactoryPluginInterface.
- В handler: `createInstance()`.

### \Drupal::service() и когда его можно использовать

Описание. Это прямое обращение к контейнеру из любого места кода. Его можно использовать только там, где внедрить зависимость нельзя: в процедурном коде (файлы .module и .install, реализации хуков, update-хуки). В классах (сервисы, формы, контроллеры, плагины) его использовать не надо: зависимости становятся скрытыми, и класс сложно тестировать.

Пример.

```php
// В .install или .module допустимо
$stat = \Drupal::service('mymodule.task_stat');
```

### Сервис, плагин и обычный PHP-класс

Описание.

- Сервис: один зарегистрированный объект с постоянной ролью. Берётся по имени.
- Плагин: один из многих вариантов одного вида. Выбирается по id или настройкам.
- Обычный класс: создаётся через `new`. Подходит для простых объектов с данными или утилит без зависимостей.

### Тестирование классов с внедрёнными зависимостями

Описание.

- Unit-тесты (UnitTestCase): зависимости заменяются заглушками (mock) и передаются в конструктор. Именно ради этого и нужно внедрение зависимостей.
- Kernel-тесты: запускается настоящий контейнер с нужными модулями, сервис берётся через `$this->container->get()`.
- Functional-тесты: полноценный сайт с браузером.

### Что запомнить

Бизнес-логику (например, расчёт статистики по задачам) выносят в сервис, описывают в services.yml и используют в контроллере, форме, блоке или Drush-команде без копирования кода.

## 5. Plugin API (плагины)

### Что такое плагин и зачем Drupal его использует

Описание. Плагин это небольшой класс, который добавляет один вариант какой-то функциональности: блок, способ вывода поля, обработчик очереди. Модули добавляют такие варианты, не меняя код ядра: достаточно положить класс в нужную папку и описать его атрибутом. Drupal найдёт его сам.

### Plugin Manager, discovery и definition

Описание.

- Тип плагина: вид, например Block, FieldFormatter, QueueWorker.
- Plugin Manager: сервис, который управляет одним типом плагинов. Он знает, в какой папке искать (например, `Plugin/Block`), какой интерфейс должен быть у плагина, и кеширует найденное. Создаёт экземпляр методом `createInstance('id', $config)`.
- Discovery (обнаружение): способ найти плагины. Современный сканирует классы с атрибутами. Старый читает аннотации в комментариях. Для некоторых типов (пункты меню, вкладки) плагины описываются в YAML-файлах.
- Definition (определение): набор данных о плагине (id, название, класс, модуль), собранный из его атрибута.

Порядок работы: менеджер сканирует папку `Plugin/<Тип>/` во всех модулях, читает атрибуты, собирает определения, и по id создаёт нужный экземпляр.

### Атрибуты плагинов и старые аннотации

Описание. В современном Drupal (10.x и 11) данные плагина записываются PHP-атрибутом над классом. Раньше это делали аннотацией в комментарии (`@Block(...)`). Аннотации сейчас считаются устаревшими. В старом коде они встречаются, в новом пиши атрибуты.

Пример.

```php
#[Block(
  id: 'mymodule_task_stat',
  admin_label: new TranslatableMarkup('Статистика задач'),
  category: new TranslatableMarkup('DrupalJira'),
)]
class TaskStatBlock extends BlockBase {
  public function build() {
    return ['#markup' => $this->t('Статистика')];
  }
}
```

### Примеры типов плагинов

Описание.

- Block (BlockBase): блок на странице. Методы: `build()` (содержимое), `blockForm()` и `blockSubmit()` (настройки блока), `blockAccess()` (доступ).
- Field Formatter (FormatterBase): определяет, как значение поля показывается. Основной метод: `viewElements()`.
- Field Widget (WidgetBase): определяет, как значение поля вводится в форме. Основной метод: `formElement()`.
- Queue Worker: обрабатывает элементы очереди, в том числе по cron. Основной метод: `processItem($data)`.
- Другие: Field Type, Condition, Action, плагины Views и Migrate, фильтры текста. Сами типы сущностей тоже обнаруживаются как плагины.

Пример (Queue Worker).

```php
#[QueueWorker(
  id: 'mymodule_recalc',
  title: new TranslatableMarkup('Пересчёт статистики'),
  cron: ['time' => 60],
)]
class RecalcWorker extends QueueWorkerBase {
  public function processItem($data) {
    // обработать один элемент очереди
  }
}
```

### Как создать свой тип плагина и его реализацию

Описание. Для нового типа плагина нужны четыре части.

1. Интерфейс и базовый класс плагина.
2. Класс атрибута (наследует `Drupal\Component\Plugin\Attribute\Plugin`), в котором перечислены поля описания (id, label).
3. Plugin Manager (наследует DefaultPluginManager). В конструкторе указывается папка, интерфейс и класс атрибута.
4. Регистрация менеджера в services.yml. Реализация плагина: класс в папке `src/Plugin/<Тип>/` с твоим атрибутом.

Пример.

```php
// Менеджер
class ReportManager extends DefaultPluginManager {
  public function __construct(\Traversable $namespaces, CacheBackendInterface $cache_backend, ModuleHandlerInterface $module_handler) {
    parent::__construct('Plugin/Report', $namespaces, $module_handler, ReportInterface::class, Report::class);
    $this->alterInfo('report_info');
    $this->setCacheBackend($cache_backend, 'report_plugins');
  }
}
```

```yaml
services:
  plugin.manager.report:
    class: Drupal\mymodule\ReportManager
    parent: default_plugin_manager
```

### Плагин, сервис и handler: в чём разница

Описание.

- Плагин: выбирается из набора вариантов по id.
- Сервис: единственный объект с постоянной ролью.
- Handler: исполнитель одной роли для конкретного типа сущности, указан в описании сущности.

### Что запомнить

Плагин нужен, когда у функциональности много взаимозаменяемых вариантов, которые должны подключаться отдельными классами (блоки, форматтеры, виджеты). Drupal находит их по атрибутам в папке `Plugin/`. Чтобы написать свой плагин, нужны класс и атрибут в правильной папке.

## 6. Entity API (сущности)

Это одна из самых важных тем.

### Content Entity и Configuration Entity

Описание.

- Content Entity: данные сайта в базе. Например, материалы (node), пользователи, комментарии, термины, твой time_log. У них есть поля, ревизии, переводы. Класс наследует ContentEntityBase.
- Configuration Entity: настройки сайта. Например, тип материала (node_type), роль, словарь, view. Хранятся как config и выгружаются в YAML. Полей нет. Класс наследует ConfigEntityBase.

Как выбрать. Если это настройка, которую нужно переносить между окружениями, это Config Entity. Если это данные, которые создают пользователи или процессы, это Content Entity.

### Entity Type, Bundle и экземпляр

Описание.

- Entity Type (тип сущности): вид данных, например node.
- Bundle: подтип внутри типа, например «Статья» или «Задача» у node. У каждого bundle могут быть свои поля. Если подтипов нет, bundle совпадает с id типа.
- Экземпляр: одна конкретная запись, например материал с id 5.

Bundles часто сами являются Config Entity (для node это node_type). Это указывается параметром `bundle_entity_type`.

### Основные классы и интерфейсы

Описание. ContentEntityBase и ConfigEntityBase это базовые классы. Интерфейсы EntityInterface и ContentEntityInterface общие. Дополнительные возможности подключаются интерфейсами и трейтами: EntityChangedInterface (дата изменения), EntityOwnerInterface (автор), EntityPublishedInterface (опубликовано). EntityTypeManagerInterface (сервис `entity_type.manager`) это главная точка доступа ко всем частям системы сущностей.

### Создание собственного Content Entity Type

Описание. Нужно сделать:

1. Класс сущности в `src/Entity/` с атрибутом `#[ContentEntityType]`.
2. Интерфейс сущности.
3. Метод `baseFieldDefinitions()` с описанием полей.
4. Handlers (список, форма, доступ, адреса).
5. Права (`admin_permission` или файл permissions.yml).
6. Ссылки (`links`) и пункты меню или кнопки. После включения модуля Drupal сам создаёт нужные таблицы по описанию.

### Атрибут #[ContentEntityType] и его параметры

Описание.

- `id`: машинное имя типа.
- `label`, `label_collection`, `label_singular`, `label_plural`: названия для интерфейса.
- `handlers`: обработчики (см. раздел 2).
- `base_table`: основная таблица. `data_table` для данных по языкам. `revision_table` для ревизий.
- `admin_permission`: право «администрировать» этот тип.
- `entity_keys`: какое поле за что отвечает (см. ниже).
- `links`: шаблоны адресов (canonical, add-form, edit-form, delete-form, collection).
- `field_ui_base_route`: маршрут страницы настроек. К нему Field UI прикрепляет вкладки «Управление полями» и «Управление отображением». Без этого параметра интерфейс управления полями не появится.
- Прочее: `translatable`, `bundle_entity_type`, `bundle_label`, `show_revision_ui`, `constraints`.

### Entity keys

Описание. Entity keys это соответствие «роль => имя поля». Благодаря им код вроде `$entity->id()` или `$entity->label()` работает одинаково для любой сущности, какие бы имена колонок в ней ни были.

- `id`: первичный ключ.
- `uuid`: уникальный идентификатор, одинаковый на разных окружениях.
- `label`: поле, которое считается заголовком.
- `langcode`: язык.
- `bundle`: поле с типом (bundle).
- `uid` или `owner`: автор.
- `status` или `published`: опубликовано ли.
- `revision`: id ревизии. Набор зависит от типа сущности.

Пример.

```php
entity_keys: [
  'id' => 'id',
  'uuid' => 'uuid',
  'label' => 'title',
  'owner' => 'uid',
],
```

### Base fields через BaseFieldDefinition

Описание. Базовые поля описываются в коде, в статическом методе `baseFieldDefinitions()`. Они одинаковы для всех bundles этого типа и не настраиваются через Field UI.

Пример.

```php
public static function baseFieldDefinitions(EntityTypeInterface $entity_type) {
  $fields = parent::baseFieldDefinitions($entity_type);

  $fields['hours'] = BaseFieldDefinition::create('decimal')
    ->setLabel(t('Часы'))
    ->setRequired(TRUE)
    ->setDisplayOptions('form', ['type' => 'number', 'weight' => 0])
    ->setDisplayConfigurable('form', TRUE)
    ->setDisplayConfigurable('view', TRUE);

  $fields['task'] = BaseFieldDefinition::create('entity_reference')
    ->setLabel(t('Задача'))
    ->setSetting('target_type', 'node')
    ->setRequired(TRUE);

  return $fields;
}
```

### CRUD: создание, чтение, изменение, удаление

Описание.

- Создать: `Node::create([...])` или `$storage->create([...])`, затем `->save()`.
- Загрузить: `Node::load($id)`, `$storage->load($id)`, `$storage->loadMultiple($ids)`.
- Сохранить: `$entity->save()`. Для новой сущности это вставка, для существующей обновление.
- Удалить: `$entity->delete()` или `$storage->delete($entities)`.
- Читать и писать поля: `$entity->get('поле')->value`, `$entity->set('поле', $значение)`. У ссылки `->target_id` это id, `->entity` это загруженная сущность.

Пример.

```php
$storage = \Drupal::entityTypeManager()->getStorage('time_log');
$log = $storage->create(['hours' => 2, 'task' => 15]);
$log->save();

$log = $storage->load($log->id());
$log->set('hours', 3)->save();
$log->delete();
```

### Entity Storage, Entity Query и EntityTypeManager

Описание.

- EntityTypeManager: даёт доступ к storage (`getStorage()`), определениям (`getDefinition()`), handlers (`getListBuilder()`, `getAccessControlHandler()`, `getFormObject()`).
- Storage: загружает, сохраняет, удаляет сущности и создаёт запросы.
- Entity Query: поиск сущностей по условиям. Возвращает массив id, а сами сущности загружаются отдельно. Вызов `accessCheck()` обязателен: `TRUE` учитывает права текущего пользователя, `FALSE` используется для системных операций.

Пример.

```php
$ids = $storage->getQuery()
  ->accessCheck(TRUE)
  ->condition('type', 'task')
  ->condition('field_status', 'done')
  ->sort('created', 'DESC')
  ->range(0, 10)
  ->execute();
$tasks = $storage->loadMultiple($ids);
```

### Entity access и permissions

Описание.

- Проверка: `$entity->access('view', $account)` (операции view, update, delete). Для создания: `getAccessControlHandler(...)->createAccess()`.
- Источники решения: access handler сущности, хуки `hook_entity_access()` и `hook_ENTITY_TYPE_access()`, для node ещё права доступа к материалам (node grants).
- Permissions (права): описываются в файле permissions.yml или функцией (`permission_callbacks`). Роли получают права через настройки (config). Параметр `admin_permission` в атрибуте задаёт право администратора типа.
- Результат проверки это объект AccessResult с данными для кеша.

Пример.

```php
if ($log->access('update', $account)) {
  // можно редактировать
}
```

### Entity references и связи

Описание. Связь между сущностями делается полем типа `entity_reference`. Настройки: `target_type` (на какой тип сущности ссылка), `handler` (например, `default:node`), `handler_settings` (например, `target_bundles`). В базе хранится id (`target_id`), а загруженную сущность возвращает `->entity`. Обратную связь (какие задачи принадлежат проекту) находят запросом по полю ссылки.

Пример.

```php
$task = $log->get('task')->entity;   // загруженная задача
$task_id = $log->get('task')->target_id;
```

### Как определяются формы и handlers в Entity Type

Описание. Формы и handlers перечисляются в параметре `handlers` атрибута (раздел 2), а адреса в `links`. Handler `route_provider` строит маршруты на основе `links`.

### Как Drupal хранит сущности и их поля

Описание.

- `base_table`: основная запись (id, uuid, bundle, язык). Простые базовые поля тоже хранятся здесь.
- `data_table`: данные по языкам, если сущность переводимая.
- `revision_table` и `revision_data_table`: ревизии.
- Поля, созданные через Field UI, хранятся в отдельных таблицах вида `тип__имя_поля` (например, `node__field_status`) и `тип_revision__имя_поля`. Колонки называются `имя_value`, `имя_target_id` и так далее.
- Многозначные базовые поля тоже получают отдельные таблицы.

Если после установки модуля меняется описание полей, нужен update-хук, который обновит схему. Иначе на странице статуса появится предупреждение «Mismatched entity and/or field definitions».

### Хуки жизненного цикла сущности

Описание. `hook_entity_presave()`, `hook_entity_insert()`, `hook_entity_update()`, `hook_entity_delete()` и варианты для конкретного типа (`hook_ENTITY_TYPE_presave()`). Те же действия можно перехватить в самом классе сущности: `preSave()`, `postSave()`, `preDelete()`.

### Что запомнить

Путь целиком: описание типа (атрибут, базовые поля, handlers) → установка модуля (создаются таблицы) → `create()` и `save()` (запись) → `load()` или запрос (чтение) → редактирование через форму → проверка доступа (access handler и права).

## 7. Field API и Computed Fields (поля)

### Base fields и configurable fields

Описание.

- Base field (базовое поле): описано в коде, есть у всех bundles типа, не меняется через Field UI.
- Configurable field (настраиваемое поле): создаётся через Field UI или конфигурацию, привязывается к конкретным bundles, выгружается в YAML.

### BaseFieldDefinition, FieldStorageConfig, FieldConfig

Описание.

- BaseFieldDefinition: описание базового поля в коде.
- FieldStorageConfig (`field.storage.node.field_x`): «хранилище» настраиваемого поля. Содержит имя, тип, количество значений, настройки хранения. После появления данных часть настроек менять нельзя (например, на какой тип сущности ведёт ссылка).
- FieldConfig (`field.field.node.task.field_x`): настройки поля для конкретного bundle. Подпись, описание, обязательность, значение по умолчанию. Одно хранилище можно использовать в разных bundles, для каждого будет свой FieldConfig.

### Field type, Field Widget и Field Formatter

Описание.

- Field type (тип поля): какие данные хранятся (string, integer, decimal, entity_reference, text_long, datetime). Класс наследует FieldItemBase и описывает свойства, схему таблицы и проверку на пустоту (`isEmpty()`).
- Field Widget (виджет): как значение вводят в форме (текстовое поле, список, автодополнение).
- Field Formatter (форматтер): как значение показывают (текст, ссылка, название связанной сущности).

### FieldItemList, FieldItemBase и структура значений

Описание.

- FieldItemBase: один элемент поля, то есть одно значение (с его свойствами: `value`, `target_id`, `format`).
- FieldItemList: список всех элементов поля у конкретной сущности. Это то, что возвращает `$entity->get('поле')`.
- Полезные методы: `first()`, `get($delta)`, `getValue()`, `setValue()`, `isEmpty()`. Свойство `->value` сразу читает значение первого элемента.

Структура значения: массив элементов, каждый элемент это массив свойств.

Пример.

```php
// Многозначное поле-ссылка
[
  ['target_id' => 5],
  ['target_id' => 7],
]

$first = $entity->get('field_tags')->first()->target_id;
```

### Cardinality, required, translatable, revisionable

Описание.

- Cardinality (количество значений): 1, или число N, или без ограничений (`FieldStorageDefinitionInterface::CARDINALITY_UNLIMITED`, значение -1).
- required: поле обязательно.
- translatable: у значения есть версии для разных языков.
- revisionable: значение сохраняется в ревизиях.

Пример (базовое поле).

```php
$fields['note'] = BaseFieldDefinition::create('string')
  ->setLabel(t('Заметка'))
  ->setCardinality(3)
  ->setRequired(FALSE)
  ->setTranslatable(TRUE)
  ->setRevisionable(TRUE);
```

### Entity Reference и таксономия

Описание. Поле типа `entity_reference` может вести на термины таксономии или другие сущности. Ключевые настройки: `target_type` (например, `taxonomy_term`), `handler` (`default:taxonomy_term`), `handler_settings` с `target_bundles` (какие словари допустимы) и `auto_create` (создавать новые термины на лету). Термин это Content Entity, словарь это Config Entity.

### Form Display и View Display

Описание.

- Form Display (`core.entity_form_display.{тип}.{bundle}.{режим}`): какие виджеты показываются в форме и в каком порядке.
- View Display (`core.entity_view_display.{тип}.{bundle}.{режим}`): какие форматтеры используются при выводе, в каком порядке (режимы full, teaser и другие). Это конфигурация, поэтому отображение полей выгружается в YAML. Для базовых полей нужно вызвать `setDisplayConfigurable('form', TRUE)` или `setDisplayOptions()`, иначе поле не попадёт в эти настройки.

### Computed Fields (вычисляемые поля)

Описание. Вычисляемое поле не хранится в базе. Его значение считается в момент обращения. Реализация состоит из двух частей: описания поля с флагом `setComputed(TRUE)` и класса списка значений, где метод `computeValue()` считает значение. Признак `isComputed()` на описании поля сообщает Drupal, что для поля не нужны таблицы и сохранение. Чужим сущностям такое поле добавляют через `hook_entity_base_field_info()` или `hook_entity_bundle_field_info()`.

Пример.

```php
$fields['logged_hours'] = BaseFieldDefinition::create('float')
  ->setLabel(t('Залогировано часов'))
  ->setComputed(TRUE)
  ->setReadOnly(TRUE)
  ->setClass(LoggedHoursItemList::class)
  ->setDisplayConfigurable('view', TRUE);
```

```php
class LoggedHoursItemList extends FieldItemList {
  use ComputedItemListTrait;

  protected function computeValue() {
    $value = 0; // здесь расчёт, например через сервис
    $this->list[0] = $this->createItem(0, $value);
  }
}
```

### Вычисляемое поле и обычное сохранённое поле

Описание.

- Сохранённое поле: значение записано в базу. По нему можно искать и сортировать (Entity Query, Views). Читается без расчётов.
- Вычисляемое поле: значения в базе нет. Всегда актуально, но по нему нельзя просто искать и сортировать, и оно не создаёт таблиц.

### Когда что использовать

Описание.

- Вычисляемое поле: значение производное, но нужно как «поле» сущности (для вывода, API, шаблона `$entity->logged_hours`).
- Сервис: сложные расчёты, суммы по многим сущностям, переиспользование в разных местах. В DrupalJira для статистики по задачам для этого есть TaskStatService.
- Метод сущности: простое вычисление по данным самой сущности.
- Обычное поле: значение нужно хранить, искать, сортировать или вводить вручную.

### Производительность и кеширование

Описание.

- Значение считается при первом обращении. Но если вывести список из многих сущностей, для каждой будет свой расчёт и свои запросы к базе (проблема N+1).
- Как смягчить: один общий запрос сразу для всех id в сервисе, статический кеш внутри сервиса. Если по значению нужны фильтры и сортировка, лучше хранить его в обычном поле.
- Вывод должен учитывать кеш: нужны cache tags (например, на сущности time_log, от которых зависит значение), cache contexts и max-age. Тогда при изменении данных кеш сбросится.

### Что запомнить

Нужно уметь объяснить: как объявляются поля (в коде или через настройки), как значения хранятся (таблицы, FieldItemList и элементы), как управляется отображение (Form Display, View Display, виджеты, форматтеры) и как сделать вычисляемое значение.

## 8. Configuration Management (конфигурация)

### Активная и экспортируемая конфигурация

Описание.

- Активная конфигурация: текущие настройки сайта. Хранятся в базе (таблица `config`).
- Экспортируемая конфигурация: те же настройки в виде YAML-файлов в папке синхронизации (`config/sync`). Эта папка лежит в Git. Путь к ней задаётся в settings.php: `$settings['config_sync_directory']`. Экспорт и импорт переносят настройки между этими двумя состояниями.

### YAML-файлы и config/sync

Описание. Каждая запись конфигурации это отдельный файл. Имя файла равно имени записи плюс `.yml`. Примеры: `system.site.yml` (общие настройки сайта), `node.type.task.yml` (тип материала), `field.storage.node.field_status.yml` (хранилище поля), `core.extension.yml` (список включённых модулей), `views.view.*.yml` (отчёты Views).

### ConfigFactoryInterface, Config, ImmutableConfig и EditableConfig

Описание.

- ConfigFactoryInterface (сервис `config.factory`): выдаёт объекты настроек.
- `get('имя')`: возвращает ImmutableConfig. Только для чтения, значения с учётом подмен (overrides) из settings.php.
- `getEditable('имя')`: возвращает изменяемый объект. Подмен в нём нет. Используется для записи.
- Методы: `get('ключ')`, `set('ключ', $значение)`, `save()`, `clear('ключ')`, `delete()`.
- В классах с ConfigFormBase и ControllerBase для чтения есть короткая запись `$this->config('имя')`.

Пример.

```php
// Чтение
$limit = $factory->get('mymodule.settings')->get('hours_limit');

// Запись
$factory->getEditable('mymodule.settings')
  ->set('hours_limit', 8)
  ->save();
```

### ConfigFormBase и пользовательские настройки

Описание. В форме на основе ConfigFormBase три шага: метод `getEditableConfigNames()` называет настройки, которые форма меняет. В `buildForm()` значения читаются из настроек. В `submitForm()` они записываются через `->set()->save()` и вызывается `parent::submitForm()`. Пример см. в разделе 3. Для настроек модуля должна быть описана схема (см. ниже).

### drush config:export и drush config:import

Описание.

- `drush config:export` (`cex`): из активной конфигурации в YAML-файлы.
- `drush config:import` (`cim`): из YAML-файлов в активную конфигурацию. Перед применением показывает различия.
- Полезные команды: `drush config:status` (чем отличаются файлы и база), `drush config:get`, `drush config:set`, `drush config:delete`.
- Обычный порядок деплоя: `drush updb`, затем `drush cim`, затем `drush cr`. Команда `drush deploy` выполняет это сама.

### Simple configuration и configuration entities

Описание.

- Simple configuration: одна запись настроек, например `mymodule.settings`. Структуру описывает схема типа `config_object`. Подходит для общих настроек модуля.
- Configuration entity: много однотипных записей (типы материалов, роли, views). Есть свой класс (ConfigEntityBase), id и название. Имя записи строится так: `модуль.тип.id`.

Пример (simple config).

```yaml
# config/install/mymodule.settings.yml
hours_limit: 8
```

### config/install, config/optional, config/schema

Описание.

- `config/install`: YAML, который применяется при установке модуля. Если нужные зависимости не выполнены, установка модуля не пройдёт.
- `config/optional`: ставится только если все зависимости есть (например, view, которой нужен другой модуль).
- `config/schema/MODULE.schema.yml`: описание структуры настроек (какие ключи и типы значений). Нужно для проверки, перевода и корректной выгрузки.

Пример.

```yaml
# config/schema/mymodule.schema.yml
mymodule.settings:
  type: config_object
  label: 'Настройки DrupalJira'
  mapping:
    hours_limit:
      type: integer
      label: 'Лимит часов'
```

### config_dependencies (зависимости конфигурации)

Описание. В YAML может быть блок `dependencies`: от каких других настроек (`config`), модулей (`module`), тем (`theme`), контента (`content`) зависит запись. Для Config Entity зависимости вычисляются автоматически методом `calculateDependencies()`, а жёсткие задаются в `enforced`. Благодаря этому Drupal импортирует записи в правильном порядке и не даёт удалить модуль или сущность, от которых что-то зависит.

Пример.

```yaml
dependencies:
  config:
    - field.storage.node.field_status
    - node.type.task
  module:
    - mymodule
```

### Default configuration и configuration overrides

Описание.

- Default configuration (настройки по умолчанию): то, что лежит в `config/install` и применяется один раз при установке модуля. Дальше это обычные активные настройки.
- Overrides (подмены): значения, которые подставляются «на лету» и не сохраняются в базу. Например, в settings.php: `$config['system.site']['name'] = 'Dev site'`. Через `get()` подмена видна, через `getEditable()` нет. Для разных окружений есть ещё модуль config_split.

Пример.

```php
// settings.php (только на этом окружении)
$config['system.site']['name'] = 'DrupalJira (dev)';
```

### Update hooks и изменение структуры настроек

Описание. Если модуль меняет структуру настроек (новый ключ, переименование, новая сущность), на уже установленных сайтах файл из `config/install` повторно не применится. Нужен update-хук `hook_update_N()` в файле .install (например, `mymodule_update_10001`). В нём настройки правятся программно. После этого новую конфигурацию выгружают (`drush cex`) и коммитят. Drupal запоминает версию схемы модуля, и `drush updb` выполняет те обновления, которых ещё не было.

Пример.

```php
function mymodule_update_10002() {
  \Drupal::configFactory()->getEditable('mymodule.settings')
    ->set('hours_limit', 8)
    ->save();
}
```

### Перенос конфигурации между окружениями через Git

Описание. Порядок такой:

1. Изменил настройку на dev (через админку или код).
2. `drush cex`.
3. `git add config/sync`, коммит, push.
4. На другом окружении `git pull`.
5. `drush updb`, `drush cim`, `drush cr`. Условие: у сайтов должен совпадать UUID сайта (запись `system.site`). Обычно этого достигают тем, что окружение создают из копии базы. Иначе импорт откажется работать.

### Почему импорт конфигурации не переносит обычный контент

Описание. Импорт переносит настройки (структуру сайта), но не данные. В YAML не попадают материалы, пользователи, комментарии, термины таксономии (термины это контент, а словарь это конфигурация), файлы, записи time_log. Контент переносят миграциями, модулями вроде default_content или копией базы. Нужно учитывать и обратное: если в конфигурации удалили тип материала, существующие записи этого типа придётся удалять отдельно.

### Как диагностировать ошибки импорта и несовпадения

Описание.

- `drush config:status` показывает, какие записи есть только в базе, только в файлах или отличаются.
- `drush cim --preview=diff` показывает различия перед применением.
- В интерфейсе: страница `/admin/config/development/configuration`. Ошибки смотри в `/admin/reports/dblog` и в выводе drush.
- Частые причины: разный UUID сайта; не включён модуль, указанный в `core.extension`; не выполнена зависимость записи; запись не соответствует схеме; конфликт при слиянии веток в Git; забыли выполнить `drush updb`; часть настроек исключена из синхронизации (config_split или `config_exclude_modules`).

### Что запомнить

Полный цикл: создать настройку, сохранить её (форма настроек), `drush cex`, YAML в `config/sync`, коммит в Git, на другом окружении `git pull`, `drush cim`. Настройка применена.

## 9. Database credentials и settings.php

### Роль settings.php и settings.local.php

Описание.

- `sites/default/settings.php`: главный файл настроек сайта на уровне PHP. В нём: подключение к базе, `hash_salt`, путь к config sync, разрешённые домены (trusted hosts), путь к private-файлам, подмены настроек. Читается в самом начале запуска Drupal.
- `settings.local.php`: настройки только для этого окружения (обычно для разработки). В конце settings.php стоит блок, который подключает этот файл, если он существует. В Git его не кладут (добавляют в `.gitignore`). Могут быть и другие файлы окружения: `settings.ddev.php`, `settings.lando.php`. Они создаются автоматически средой разработки.

### Как задаётся подключение к БД: $databases

Описание. Структура: `$databases[ключ][цель]`. Ключ `default` это основная база. Цель `default` это основное подключение, `replica` это копия для чтения. Параметры подключения:

- `driver`: тип базы (mysql, pgsql, sqlite).
- `database`: имя базы.
- `username` и `password`: логин и пароль.
- `host` и `port`: адрес и порт (или `unix_socket`).
- `prefix`: префикс имён таблиц.
- `namespace` и `autoload`: данные драйвера базы.

Пример.

```php
$databases['default']['default'] = [
  'driver' => 'mysql',
  'database' => 'drupaljira',
  'username' => 'db_user',
  'password' => getenv('DB_PASSWORD'),
  'host' => 'db',
  'port' => '3306',
  'prefix' => '',
  'namespace' => 'Drupal\\mysql\\Driver\\Database\\mysql',
  'autoload' => 'core/modules/mysql/src/Driver/Database/mysql/',
];
```

### Настройки подключения и конфигурация Drupal: в чём разница

Описание.

- Настройки подключения к базе: параметры окружения. Лежат в PHP-файле settings.php. В базе не хранятся и в YAML не выгружаются.
- Конфигурация Drupal: настройки сайта. Хранятся в базе и выгружаются в YAML (раздел 8).

Почему подключение нельзя хранить в конфигурации. Конфигурация лежит в базе. Чтобы её прочитать, нужно сначала подключиться к базе. Получается замкнутый круг, поэтому пароль к базе должен быть в файле. Кроме того, на каждом окружении своя база и свой пароль.

### Как Drupal выбирает настройки для сайта

Описание. Drupal определяет папку сайта в каталоге `sites/` по домену, порту и пути запроса. Соответствия можно задать в файле `sites/sites.php`. Если подходящей папки нет, используется `sites/default`. Затем читается файл settings.php из выбранной папки.

### Multisite

Описание. Один код Drupal может обслуживать несколько сайтов. У каждого своя папка: `sites/site1.example.com/settings.php`, `sites/site2.example.com/settings.php`. У каждого сайта свои база, файлы и папка config sync. Файл `sites/sites.php` связывает домены с папками. Drush выбирает сайт параметром `--uri` или по текущей папке.

Пример.

```php
// sites/sites.php
$sites['site2.example.com'] = 'site2.example.com';
```

### Переменные окружения и безопасное хранение секретов

Описание. Пароли и ключи берут из окружения, а не пишут в файл: `getenv('DB_PASSWORD')`. Источники: переменные сервера или контейнера, файл `.env` (не в Git), секреты CI, Docker или Kubernetes. Так один и тот же settings.php работает везде, а значения у окружений разные. На продакшене файл settings.php лучше сделать доступным только для чтения (`chmod 444`). Это касается не только базы, но и `hash_salt`, ключей API, паролей SMTP.

Пример.

```php
$settings['hash_salt'] = getenv('DRUPAL_HASH_SALT');
```

### Почему пароли и ключи нельзя коммитить в Git

Описание. Git хранит всю историю. Даже если удалить пароль из последнего коммита, он останется в старых, и его увидит каждый, у кого есть доступ к репозиторию. Утечка пароля это доступ к базе данных. Как делать правильно: `settings.local.php` и `.env` в `.gitignore`, общий settings.php без секретов, секреты берутся из окружения. Если пароль всё же попал в Git, его нужно сразу менять.

Конфигурация в `config/sync` тоже лежит в Git, поэтому секреты в неё попадать не должны. Для них используют подмены (overrides) в settings.php или модули Key и Encrypt.

### Overrides в settings.php

Описание.

- `$config['имя.настройки']['ключ'] = значение`: подмена значения конфигурации во время работы. В базу не пишется.
- `$settings['config_sync_directory'] = '../config/sync'`: папка с YAML-конфигурацией.
- `$settings['hash_salt']`, `$settings['trusted_host_patterns']`, `$settings['file_private_path']`, `$settings['file_temp_path']`.
- `$settings['config_exclude_modules']`: исключить модули из синхронизации конфигурации. Применяется для значений, которые отличаются на разных окружениях, без изменения общей конфигурации.

### Как не путать настройки БД с YAML-настройками

Описание.

- settings.php: PHP-массивы `$databases`, `$settings`, `$config`. Окружение, секреты, пути. В config sync не попадают.
- YAML-конфигурация (`config/sync`, `config/install`): настройки сайта и модулей. Переносятся через Git.

Правило: если значение разное на каждом окружении или секретное, оно идёт в settings.php. Если значение общее для сайта, оно идёт в конфигурацию.

### Как проверить подключение и найти ошибку

Описание. Проверка подключения:

- `drush status`: в строке Database видно, подключена ли база.
- `drush sql:cli` открывает консоль базы, `drush sql:connect` показывает команду подключения, `drush sqlq "SELECT 1"` выполняет запрос.
- Страница `/admin/reports/status`: отчёт о состоянии сайта.
- Если подключение не работает или settings.php пустой, Drupal открывает установщик (`install.php`).

Типичные ошибки MySQL:

- 1045 Access denied: неверные логин или пароль, либо у пользователя нет прав на эту базу.
- 1049 Unknown database: базы с таким именем нет или имя указано неверно.
- 2002 Connection refused: неверный host или port, сервер базы не запущен. В Docker и DDEV хост это имя контейнера (например, `db`), а не `localhost`.
- Driver not found: нет расширения PHP `pdo_mysql` или неверные `namespace` и `autoload`.

Что проверить: подключиться к базе вручную клиентом mysql с теми же данными, проверить значения переменных окружения, проверить, какой файл настроек реально подключился (например, подхватился ли `settings.local.php`), и права пользователя базы.

### Что запомнить

Drupal берёт параметры подключения из `$databases` в settings.php выбранного сайта (и файлов окружения, которые он подключает). На каждом окружении они свои. Секреты приходят из окружения, а не из Git. В экспортируемой конфигурации паролей нет, потому что конфигурация лежит в Git, а подключение к базе нужно до того, как конфигурацию можно прочитать.

## Шпаргалка: какой механизм выбрать

- Поменять подпись поля: поле из админки, значит config; базовое поле, значит `hook_entity_base_field_info_alter()`.
- Поменять название типа сущности или bundle: `hook_entity_type_alter()`, `hook_entity_bundle_info_alter()` или config (для типов материалов).
- Поменять форму: `hook_form_FORM_ID_alter()` (одна форма), `hook_form_BASE_FORM_ID_alter()` (семейство), `hook_form_alter()` (все формы).
- Поменять HTML: preprocess-функция и переопределение Twig в теме.
- Нужен свой список, форма, права или адреса сущности: handler.
- Нужна общая логика, которую используют в нескольких местах: сервис и Dependency Injection.
- Нужны взаимозаменяемые варианты (блоки, виджеты, форматтеры): плагин.
- Настройка, которую нужно переносить между окружениями: config (simple config или config entity).
- Секрет или значение, свойственное одному окружению: settings.php и переменные окружения.
