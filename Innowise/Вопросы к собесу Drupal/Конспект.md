## Блок 1. Мультиязычность (Multilingual)

> [!abstract] Кратко 
> Мультиязычность состоит из трёх независимых слоёв: язык интерфейса (системные строки), язык контента (переводы сущностей и полей) и язык конфигурации (метки полей, названия типов материалов). Язык запроса определяет language negotiation: префикс URL, домен, настройки пользователя, заголовок `Accept-Language`. Часть полей может быть общей для всех переводов. Кеш обязан учитывать язык.

### 1.1. Общая концепция

- **Interface language** — кнопки, сообщения, системные надписи.
- **Content language** — материалы, пользовательские сущности, переводимые поля.
- **Configuration language** — переводимые значения конфигурации (метки и описания полей, заголовки блоков и Views).

Модули ядра:

|Модуль|Назначение|
|---|---|
|`Language`|управление языками, определение языкового контекста|
|`Interface Translation` (`locale`)|перевод интерфейсных строк|
|`Content Translation`|перевод содержимого|
|`Configuration Translation`|перевод поддерживаемых значений конфигурации|

Минимальная настройка: включить четыре модуля → добавить языки → настроить language negotiation → включить перевод для нужных entity types и bundles (_Content language and translation_) и отметить переводимые поля. Само включение модулей ничего не делает без этих шагов.

### 1.2. Language negotiation

Механизм определения языка запроса. Источники: префикс URL (`/en/about`), домен (`en.example.com`), предпочтения пользователя, `Accept-Language`, язык по умолчанию. Методы и приоритет настраиваются отдельно для каждого типа языка, поэтому язык интерфейса и язык содержимого могут различаться. Выбор языка запроса не создаёт перевод и не гарантирует, что он существует.

```php
$lm = \Drupal::languageManager();
$ui = $lm->getCurrentLanguage(LanguageInterface::TYPE_INTERFACE)->getId();
$content = $lm->getCurrentLanguage(LanguageInterface::TYPE_CONTENT)->getId();
```

В классах `language_manager` внедряют через DI.

### 1.3. Перевод сущностей

Перевод живёт на уровне сущности и полей: это не отдельные материалы, а языковые версии одной сущности с общим ID. Переводимость задаётся на поле (`translatable`); значение непереводимого поля общее для всех переводов. Alias пути может быть свой у каждого языка.

```php
if ($node && $node->hasTranslation('en')) {
  $en = $node->getTranslation('en');
  $title = $en->label();
}
if ($node && !$node->hasTranslation('en')) {
  $node->addTranslation('en', ['title' => 'Implement task workflow']);
  $node->save();
}
```

Методы: `isTranslatable()`, `isDefaultTranslation()`, `hasTranslation()`, `getTranslation()` (не создаёт перевод, бросает исключение, если его нет), `addTranslation()`.

Не путать: язык запроса, язык исходной сущности, язык конкретного перевода, переводимость поля.

### 1.4. Перевод интерфейса

Переводимые строки оформляют через `$this->t()` (`StringTranslationTrait`):

```php
$this->t('Task @title has been saved.', ['@title' => $title]);
```

Плейсхолдеры: `@value` — экранирование; `%value` — экранирование + выделение (`<em>`); `:value` — URL для `href`/`src`. Множественное число: `formatPlural($count, '1 task', '@count tasks')`. В Twig: `{{ 'Text'|t }}` и `{% trans %}...{% endtrans %}`.

Строки не склеивают из кусочков: переводчик должен менять порядок слов. `t()` не заменяет экранирование. Вызов `t()` лишь помечает строку переводимой; сам перевод берётся из языковых пакетов, `.po`-файлов или UI.

### 1.4а. Перевод конфигурации

Переводятся не все значения: **label** поля переводится, **machine name** нет. Что переводимо, определяет config schema (тип `label`, `text` и т.п. переводимы, `integer` нет). Не путать: Configuration Management переносит настройки между окружениями, Configuration Translation переводит значения настроек.

### 1.5. Language fallback

Выбор альтернативного значения, когда нужного перевода нет. Поведение зависит от типа данных и API; нельзя считать, что всегда подставится язык по умолчанию. Отдельно учитывают отсутствие перевода сущности и отсутствие перевода поля.

### 1.6. Мультиязычность и кеш

Результат рендеринга зависит от языка, поэтому нужны cache contexts `languages:language_interface` и `languages:language_content`. Выбирают по реальной зависимости, а не добавляют все подряд. Контекст добавляется в `#cache` или всплывает (bubbling) из вложенных элементов.

> [!example] Практика 
> Включить четыре модуля, настроить negotiation, отметить переводимые bundles и поля. В коде все видимые строки идут через `t()`, а компонентам, зависящим от языка, задают языковые cache contexts. Значения вроде статусов хранят машинными (`in_progress`, `done`), подписи переводят.

> [!warning] Типичные ошибки
> 
> - Смешивать язык интерфейса и язык содержимого.
> - Не проверять `hasTranslation()` перед `getTranslation()`.
> - Ждать отдельные значения у непереводимого поля.
> - Оставлять сообщения без `t()` или склеивать переводимые строки.
> - Забывать языковые cache contexts.
> - Переводить machine names.
> - Создавать отдельные независимые материалы вместо перевода одной сущности.
> - Считать, что перевод интерфейса переведёт контент.

> [!question] Вопросы на собеседовании **Interface language и content language?** 
> Первый — язык системных строк и UI, второй — язык содержимого сущностей. Определяются отдельно и могут различаться.
> 
> **Что будет при `getTranslation()` для несуществующего перевода?** Исключение, перевод не создаётся. Сначала `hasTranslation()`, для создания `addTranslation()`.
> 
> **Переводимое и непереводимое поле?** Переводимость задаётся на уровне поля. Значение непереводимого общее для всех переводов (внешний ID, дата).
> 
> **Configuration Translation и Configuration Management?** Первый переводит значения настроек, второй переносит настройки между окружениями.
> 
> **Зачем языковые cache contexts?** Чтобы пользователь не получил из кеша страницу на чужом языке.

## Блок 2. REST API и JSON:API

> [!abstract] Кратко 
> REST в Drupal — не просто «вернуть JSON». Три пути: REST-модуль ядра с плагинами ресурсов, JSON:API для стандартных операций с сущностями и собственные маршруты с контроллерами. В любом случае нужны аутентификация, авторизация, валидация, корректные HTTP-коды и метаданные кеша.

### 2.1. Ресурсы и HTTP

REST — стиль, где клиент работает с ресурсами через HTTP (например, React-фронтенд получает задачи и меняет статус).

|Метод|Назначение|
|---|---|
|`GET`|получить ресурс|
|`POST`|создать ресурс или выполнить операцию|
|`PATCH`|частично изменить|
|`PUT`|создать или полностью заменить|
|`DELETE`|удалить|

|Код|Значение|
|---|---|
|200 / 201 / 204|успех / создан / без тела|
|400|некорректный запрос|
|401|нет подходящей аутентификации|
|403|доступ запрещён|
|404|не найден или не раскрывается клиенту|
|405|метод не поддерживается|
|409|конфликт состояния|
|422|не прошла валидация|

### 2.2. Способы построить API

- **REST-модуль ядра** (REST Resource plugins).
- **JSON:API** (ядро) — отдельная реализация спецификации, не путать с REST Resource.
- **Собственные маршруты** с `JsonResponse` / `CacheableJsonResponse`.
- **Views REST export** — список в JSON/XML без кода.
- contrib: GraphQL.

Инфраструктура REST: Resource plugins, Serialization API, Authentication API, Access API.

### 2.3. JSON:API

```http
GET /jsonapi/node/task?filter[field_status]=in_progress&include=field_project&page[limit]=20
Accept: application/vnd.api+json
```

Ресурс идентифицируется **UUID**, а не числовым ID. Ответ: `type` (`node--task`), `id`, `attributes`, `relationships`. Поддержка фильтров зависит от полей. Включённый JSON:API по умолчанию допускает запись: для read-only API его настраивают отдельно. Права и доступ к связанным сущностям проверяются как обычно.

### 2.4. REST Resource plugin

Плагин наследует `ResourceBase`:

```php
#[RestResource(id: 'example_tasks', label: new TranslatableMarkup('Example tasks'),
  uri_paths: ['canonical' => '/api/tasks'])]
final class TasksResource extends ResourceBase {
  public function get(): ResourceResponse {
    return new ResourceResponse(['data' => [['id' => 1, 'title' => 'Prepare notes']]]);
  }
}
```

(в старых версиях вместо атрибута аннотация `@RestResource`). Класс сам endpoint не открывает: ресурс нужно **включить** конфигурацией `rest.resource.*` (methods, formats, authentication) и выдать permissions вида `restful get example_tasks`. Ответ `ResourceResponse` кешируемый: добавляют `addCacheableDependency()`.

### 2.5. REST Resource и JSON:API

|REST Resource|JSON:API|
|---|---|
|собственные плагины|стандартизированный API сущностей|
|структуру определяет разработчик|структура по спецификации|
|для специальных операций|для типовых операций с сущностями|

Для стандартных данных сначала оценивают JSON:API, для особой бизнес-операции — REST Resource или собственный маршрут (контроллер координирует запрос/ответ, расчёты в сервисе).

### 2.6. Serialization

- **Normalization** — объект → массив.
- **Encoding** — массив → формат (JSON, XML).

Порядок: запрос → маршрут → аутентификация и доступ → обработка → сериализация → ответ.

### 2.7. Аутентификация, авторизация, CSRF

Authentication — кто, Authorization — можно ли ему, CSRF — защита от подделки запросов через сессию. При cookie-аутентификации токен берут на `/session/token` и передают в `X-CSRF-Token`. HTTPS не заменяет авторизацию и CSRF.

### 2.8. Валидация и ошибки

Проверяют формат и типы, обязательность, допустимые значения (статус должен быть разрешённым, а переход допустимым), существование связанных сущностей, права, бизнес-ограничения. Ошибки возвращают в согласованном формате, без stack traces и секретов.

### 2.9. Кеширование и CORS

Учитывают query-параметры, заголовки, язык, права, персональные данные. Персонализированное не кладут в общий кеш без контекстов. Для другого домена фронтенда — `cors.config` в `services.yml` (`enabled`, `allowedOrigins`, `allowedMethods`, `allowedHeaders`, `supportsCredentials`). CORS не заменяет аутентификацию и CSRF.

> [!example] Практика 
> Для стандартных данных берут JSON:API (ядро, спецификация, фильтры, include, пагинация). Для спецоперации — REST Resource или маршрут. Списки без кода — Views REST export. Для отдельного фронтенда: аутентификация, проверка доступа к каждой сущности, CORS, CSRF для cookie. Пример DrupalJira: `/jsonapi/node/task` с фильтром для React-клиента.

> [!warning] Типичные ошибки
> 
> - Операции без проверки доступа; считать аутентификацию достаточной.
> - Игнорировать CSRF при cookie.
> - Не валидировать вход.
> - Путать REST Resource и JSON:API.
> - Отдавать внутренние ошибки.
> - `GET` для изменения данных.
> - Кешировать персональные ответы без контекстов.
> - Считать, что маршрут с `_entity_access: node.view` сам проверит bundle.

> [!question] Вопросы на собеседовании **JSON:API и REST-модуль?** 
> JSON:API — готовый стандартизированный API сущностей; REST строится на плагинах, структуру и логику задаёт разработчик.
> 
> **Что нужно, чтобы свой REST Resource заработал?** Плагин, включённый ресурс `rest.resource.*` и выданные permissions.
> 
> **Когда 401, 403, 404?** 401 — нет подходящей аутентификации, 403 — пользователь известен, но доступ запрещён, 404 — ресурса нет или он скрыт.
> 
> **Как защитить cookie-запросы от CSRF?** Токен с `/session/token` в заголовке `X-CSRF-Token`, плюс обязательная проверка прав.
> 
> **Чем идентифицируется сущность в JSON:API?** UUID.

## Блок 3. Configuration Management

> [!abstract] Кратко 
> Настройки и устройство сайта хранятся в YAML и переносятся между окружениями через Git. В конфигурацию входят типы материалов, поля, Views, роли и разрешения. Контент (задачи, проекты, записи времени) не входит. Секреты и параметры инфраструктуры задаются на каждом окружении отдельно.

### 3.1. Конфигурация, контент, код

- **Код** — PHP, Twig, CSS, JS.
- **Конфигурация** — типы материалов, поля, Views, роли, workflows, настройки модулей и отображения.
- **Контент** — статья, задача, проект, запись времени.

|Что|Где|Переносится через CM?|
|---|---|---|
|Config|active config в БД + YAML|да|
|Content|таблицы сущностей|нет (миграции, `default_content`, копия БД)|
|State|сервис `state` (время последнего cron)|нет|
|Settings|`settings.php`, секреты, пути|нет, задаются на окружении|

Классификация зависит от типа сущности: термин таксономии — контент, словарь — конфигурация.

### 3.2. Active configuration и sync storage

**Active configuration** — настройки работающего сайта (таблица `config`). 
**Sync storage** — каталог YAML (`$settings['config_sync_directory']`), обычно в Git. 
Процесс: изменить → экспорт → проверить YAML → коммит → развернуть → импорт.

Имена файлов: `system.site.yml`, `node.type.task.yml`, `field.storage.node.field_status.yml`, `field.field.node.task.field_status.yml`, `core.extension.yml`, `views.view.*.yml`.

### 3.3. Drush

```bash
drush config:export   # cex
drush config:import   # cim
drush config:status   # cst: различия active и sync
drush config:get system.site
drush config:set system.site name 'DrupalJira'
drush cim --preview=diff
```

Деплой: `drush updb` → `drush cim` → `drush cr` (или `drush deploy`). Перед импортом смотрят различия: импорт создаёт, меняет и **удаляет** объекты.

### 3.4. Machine name, label, UUID

Machine name (`field_status`) используется в коде и зависимостях, label (`Status`) — отображаемое имя, UUID — уникальный идентификатор. UUID **сайта** в sync должен совпадать с целевым, иначе полный импорт отклоняется (сайты должны происходить от одной установки; обычно окружение создают из копии БД).

### 3.5. Config API: Config, Immutable, Editable

- `config.factory` (`ConfigFactoryInterface`): `get('name')` → `ImmutableConfig` (чтение, с учётом overrides из settings.php); `getEditable('name')` → изменяемый объект без overrides.
- Методы: `get('key')`, `set('key', $v)`, `save()`, `clear('key')`, `delete()`.
- В `ConfigFormBase`/`ControllerBase` короткая запись `$this->config('name')`.

```php
$limit = $factory->get('mymodule.settings')->get('hours_limit');
$factory->getEditable('mymodule.settings')->set('hours_limit', 8)->save();
```

### 3.6. Simple config и config entities

- **Simple configuration** — одна запись (`mymodule.settings`), схема `config_object`.
- **Configuration entity** — много однотипных записей (типы материалов, роли, views), класс `ConfigEntityBase`, имя `модуль.тип.id`.

### 3.7. config schema

Описывает структуру и типы значений: помогает валидации, переводу и корректному экспорту. Отсутствие или неверные типы дают ошибки схемы в тестах.

```yaml
# config/schema/example.schema.yml
example.settings:
  type: config_object
  label: 'Example settings'
  mapping:
    api_endpoint: { type: uri, label: 'API endpoint' }
    timeout: { type: integer, label: 'Timeout' }
    enabled: { type: boolean, label: 'Enabled' }
```

### 3.8. `config/install` и `config/optional`

- `config/install` — ставится при установке модуля; если зависимости не выполнены, установка не пройдёт.
- `config/optional` — ставится, только если все зависимости есть.

Файл в `config/install` **не обновляет** уже существующие сайты. Для них нужны импорт конфигурации или update hook.

### 3.9. Зависимости конфигурации

В YAML блок `dependencies` (`config`, `module`, `theme`, `content`). У config entity вычисляются автоматически (`calculateDependencies()`), жёсткие задаются в `enforced`. Drupal импортирует в правильном порядке и не даёт удалить то, от чего что-то зависит.

```yaml
dependencies:
  config: [field.storage.node.field_status, node.type.task]
  module: [mymodule]
```

Проверяют: включены ли модули, существуют ли объекты, корректны ли machine names и схемы, не удаляется ли объект, на который ссылаются.

### 3.10. CM и update hooks

CM — декларативный перенос настроек. Update hook — программное преобразование существующей установки (данные, структура). Новая структура на старых сайтах: `hook_update_N()` + `drush cex` + коммит.

```php
function example_update_10001(): void {
  \Drupal::configFactory()->getEditable('example.settings')->set('enabled', TRUE)->save();
}
```

### 3.11. Окружения, overrides, Config Split

Приложение — в конфигурацию, секреты и параметры инфраструктуры — в окружение (`settings.php`, переменные окружения, secret management).

- **Overrides**: `$config['system.site']['name'] = 'Dev';` — подмена «на лету», в экспорт не попадает.
- **Config Split** — разные наборы конфигурации по окружениям (dev-модули только локально).
- **Config Ignore** — исключает объекты из импорта/экспорта.
- `$settings['config_exclude_modules']` — исключить модули из синхронизации.

### 3.12. Почему импорт не переносит контент

Не попадают материалы, пользователи, комментарии, термины, файлы, записи `time_log`. Контент переносят миграциями, `default_content` или копией БД. Обратное: если удалить тип материала из конфигурации, существующие записи удаляются отдельно.

### 3.13. Диагностика ошибок

`drush config:status`, `drush cim --preview=diff`, страница `/admin/config/development/configuration`, логи `/admin/reports/dblog`. Частые причины: разный UUID сайта, не включён модуль из `core.extension`, нарушена зависимость записи, запись не соответствует схеме, конфликт слияния в Git, не выполнен `updb`, часть настроек исключена из синхронизации.

> [!example] Практика 
> Правка локально → `drush cex` → YAML в Git → на другом окружении деплой кода, `updb`, `cim`, `cr`. Перед импортом `cst`. В DrupalJira в Git идут типы Project и Task, поля, роли, Views; сами задачи — контент и в экспорт не входят.

> [!warning] Типичные ошибки
> 
> - Менять конфигурацию на production без переноса в Git.
> - Считать, что `config/install` обновляет существующие сайты.
> - Игнорировать зависимости, удалять объекты без проверки ссылок.
> - Путать контент с конфигурацией.
> - Заменять экспорт/импорт update hook'ами без причины.
> - Импортировать без `drush cst`.
> - Хранить секреты в репозитории (и в `config/sync`).
> - Не добавить update hook, когда существующие данные требуют преобразования.

> [!question] Вопросы на собеседовании **Конфигурация и контент?** 
> Конфигурация описывает устройство и настройки сайта и переносится через YAML; контент — рабочие данные, через CM не переносится.
> 
> **UUID сайта не совпадает?** Полный импорт отклоняется: сайты должны происходить от одной установки.
> 
> **Разные настройки для окружений?** `$config` overrides и секреты в `settings.php`, Config Split.
> 
> **Обновит ли `config/install` существующие сайты?** Нет, только при установке модуля. Нужны импорт или update hook.
> 
> **`get()` и `getEditable()`?** Первый возвращает неизменяемый объект с учётом overrides, второй — изменяемый без overrides, для записи.

## Блок 4. Services и Dependency Injection

> [!abstract] Кратко 
> Service — объект с определённой задачей, зарегистрированный в service container. DI — класс получает зависимости извне (обычно через конструктор), а не создаёт их сам. Код становится переиспользуемым, слабо связанным и тестируемым.

### 4.1. Сервис и контейнер

Примеры сервисов: `entity_type.manager`, `current_user`, `logger.factory`, `database`, `cache.default`, `language_manager`, `config.factory`, `http_client`, `request_stack`, `event_dispatcher`, `queue`.

Service Container (Symfony DependencyInjection) хранит определения, создаёт объекты и подставляет зависимости. Drupal собирает все `MODULE.services.yml`, строит контейнер и кеширует; сервис создаётся при первом обращении, обычно один раз за жизненный цикл контейнера (но не всякий сервис — глобальный singleton). После правки `services.yml` нужен `drush cr`.

### 4.2. DI

Без DI: `\Drupal::entityTypeManager()->getStorage('node')` — скрытая зависимость от глобального состояния, сложно тестировать. С DI:

```php
final class TaskManager {
  public function __construct(private readonly EntityTypeManagerInterface $entityTypeManager) {}
  public function loadTask(int $id): ?NodeInterface {
    $e = $this->entityTypeManager->getStorage('node')->load($id);
    return $e instanceof NodeInterface && $e->bundle() === 'task' ? $e : NULL;
  }
}
```

Зависимость лучше указывать **интерфейсом**, а не конкретным классом: реализацию можно заменить (декоратор, mock в тесте).

### 4.3. Регистрация сервиса

```yaml
services:
  example.task_manager:
    class: Drupal\example\TaskManager
    arguments: ['@entity_type.manager']
```

`@` — ссылка на сервис. Дополнительно: `tags` (`event_subscriber`, `access_check`, `normalizer`, `authentication_provider`, `cache.bin`), `calls` (вызвать метод после создания), `decorates` (подмена/обёртка сервиса), `parent`, `lazy`, `public`, `autowire`.

```yaml
  example.task_manager.logged:
    class: Drupal\example\LoggedTaskManager
    decorates: example.task_manager
    arguments: ['@example.task_manager.logged.inner', '@logger.factory']
```

Autowiring в Drupal зависит от версии и требует alias'ов интерфейсов; явная регистрация предпочтительнее.

### 4.4. Как получают сервисы разные классы

|Где|Как|
|---|---|
|другой сервис|`arguments` в `services.yml`|
|контроллер, форма|`create(ContainerInterface $container)` + конструктор|
|плагин|`ContainerFactoryPluginInterface`, `create($container, $configuration, $plugin_id, $plugin_definition)`|
|handler сущности|`createInstance($container, $entity_type)`|

Плагины создаёт Plugin Manager, поэтому просто добавить аргумент в конструктор нельзя.

```php
final class TaskController extends ControllerBase {
  public function __construct(private readonly EntityTypeManagerInterface $entityTypeManager) {}
  public static function create(ContainerInterface $container): static {
    return new static($container->get('entity_type.manager'));
  }
}
```

### 4.5. `\Drupal::service()`

Допустим там, где DI недоступен: `.module`, `.install`, процедурные хуки, update hooks. В классах (сервисы, формы, контроллеры, плагины) его избегают: зависимости скрыты, тестировать сложнее.

### 4.6. Сервис, плагин, handler, обычный класс

- **Сервис** — один объект с постоянной ролью, берётся по имени.
- **Плагин** — один из многих взаимозаменяемых вариантов, выбирается по id.
- **Handler** — исполнитель одной роли для типа сущности.
- **Обычный класс** — `new`, для данных и утилит без зависимостей.

### 4.7. Тестируемость

Unit-тест: зависимости заменяются mock/stub в конструкторе. Но для проверки реальной интеграции с Drupal лучше Kernel/Functional. Если класс сам ходит в `\Drupal::service()`, изолировать его трудно.

### 4.8. Когда сервис не нужен

Сервис оправдан, когда логика используется в нескольких местах, имеет самостоятельную ответственность, требует DI или изолированного теста, является отдельной бизнес-операцией. Для маленькой локальной операции он лишний.

> [!example] Практика 
> Бизнес-логику (расчёт статистики) выносят в сервис, описывают в `services.yml` и используют в контроллере, форме, блоке, Drush-команде. В DrupalJira: `TaskStatService` используют блок, контроллер и update hook.

> [!warning] Типичные ошибки
> 
> - `\Drupal::service()` повсюду.
> - «Божественные» сервисы.
> - Забыть зарегистрировать сервис или сбросить кеш.
> - Порядок/число `arguments` не совпадает с конструктором, опечатка в имени сервиса.
> - Неверное внедрение в плагины.
> - Зависимость от конкретных классов вместо интерфейсов.
> - Считать, что все объекты Drupal создаются одинаково.

> [!question] Вопросы на собеседовании **Что такое service container?** 
> Компонент Symfony DI: хранит определения, создаёт объекты, подставляет зависимости.
> 
> **Почему DI лучше `\Drupal::service()`?** Зависимости явные, связанность ниже, в тестах можно подменять.
> 
> **Как внедрить сервис в плагин?** `ContainerFactoryPluginInterface` и `create()`, потому что плагин создаёт менеджер, а не контейнер.
> 
> **Теги и декораторы?** Тег помечает сервис для обнаружения подсистемой (`event_subscriber`), декоратор подменяет или расширяет сервис без правки его кода.
> 
> **Где `\Drupal::service()` допустим?** В процедурном коде: `.module`, `.install`, хуки, update hooks.

## Блок 5. Производительность и масштабирование

> [!abstract] Кратко 
> Performance — скорость при данной нагрузке, scalability — способность расти вместе с нагрузкой. Основа — кеширование: cache contexts (от чего зависит результат), cache tags (от каких данных), max-age (сколько живёт). Вторая группа проблем — лишние запросы к БД (N+1) и тяжёлая работа в HTTP-запросе. Начинают с измерений.

### 5.1. Источники проблем и измерение

Избыточные запросы к БД, повторная загрузка сущностей, неправильный кеш, тяжёлые операции в каждом запросе, большие render arrays, внешние API, плохие индексы, долгие фоновые операции в синхронном режиме. Инструменты: Webprofiler (Devel), Xdebug, Blackfire/XHProf, лог медленных SQL, APM. Профилирование не включают на production без понимания нагрузки.

### 5.2. Уровни кеша

- **Internal Page Cache** — целые ответы для анонимных запросов.
- **Dynamic Page Cache** — страницы с динамическими частями, учитывает контексты, полезен и для авторизованных.
- **Render Cache** — результаты рендеринга компонентов.

Для данных вне render-системы — Cache API (`cache.default`, `cache.data`, свои cache bins). Кеш-бэкенд (БД, Redis) определяет хранение, но не исправляет неверные метаданные.

### 5.3. Cache contexts

Определяют, при каких условиях нужен отдельный вариант результата: `user`, `user.roles`, `user.permissions`, `languages:language_interface`, `languages:language_content`, `url.path`, `url.query_args`.

```php
return ['#markup' => $message,
  '#cache' => ['contexts' => ['user.roles', 'languages:language_interface']]];
```

Лишние контексты множат варианты кеша и снижают его эффективность.

### 5.4. Cache tags

Описывают, от каких данных зависит результат; при изменении сущности Drupal инвалидирует кеш по её тегам.

```php
'#cache' => ['tags' => $task->getCacheTags()]   // node:123
```

Для списков — `node_list`, `node_list:task` или собственные. Теги отвечают за зависимость от данных, а не за вариации по пользователю или языку.

### 5.5. Max-age

Время жизни в секундах. `0` — не кешировать; `Cache::PERMANENT` — без ограничения (инвалидация по тегам остаётся). Внимание: `max-age: 0` во вложенном элементе всплывает и отключает кеш всей страницы.

|Механизм|Вопрос|
|---|---|
|contexts|для кого или при каких условиях нужен отдельный вариант?|
|tags|какие изменения данных делают результат устаревшим?|
|max-age|как долго результат действителен?|

### 5.6. Cache bubbling

Метаданные вложенных элементов переходят к родителям: contexts и tags объединяются, max-age берётся наименьший. Метаданные задают на уровне компонентов, а не пересчитывают вручную. Объекты доступа тоже несут cacheability (`AccessResult::allowedIf(...)->addCacheContexts([...])`).

### 5.7. N+1 и загрузка сущностей

N+1: список сущностей, затем отдельный запрос на каждую (100 задач и отдельная загрузка проекта для каждой). Решения: Entity Query для ID, `loadMultiple()` вместо цикла `load()`, предзагрузка связанных, Views, кеширование повторно используемых данных, агрегирующие SQL для статистики (суммы часов). Для подсчёта используют `->count()`, а не загрузку всех сущностей. Реальные SQL измеряют: не каждая последовательность обращений — проблема (есть static cache хранилища).

### 5.8. Индексы

Ускоряют фильтрацию, сортировку, joins; но занимают место, замедляют запись и не гарантируют ускорение. Анализируют `EXPLAIN`, а не добавляют наугад.

### 5.9. BigPipe, placeholders, lazy builders

BigPipe отправляет часть HTML раньше, динамическое досылает позже. Placeholders откладывают рендеринг элементов. Персонализированные части — lazy builders:

```php
$build['summary'] = [
  '#lazy_builder' => ['drupaljira_timelog.task_stat:buildSummary', [$task_id]],
  '#create_placeholder' => TRUE,
];
```

Callback должен быть доверенным (`TrustedCallbackInterface`). Это не заменяет кеш и оптимизацию запросов.

### 5.10. Инфраструктура

OPcache (байткод PHP), Redis/Memcache (внешний кеш), CDN, reverse proxy (Varnish, Nginx). Само наличие не ускоряет без правильной настройки и инвалидации (tags → purge). На production: агрегация CSS/JS, image styles, отключённые dev-модули.

### 5.11. Масштабирование

Вертикальное — больше ресурсов одного сервера. Горизонтальное — несколько экземпляров: общая БД, общие файлы (shared storage/S3), общие кеши и locks, согласованная конфигурация, cron и очереди выполняются один раз, хранение сессий, лимиты БД и внешних API. Очереди убирают тяжёлое из запроса, но работу всё равно нужно выполнить.

> [!example] Практика 
> Правильные метаданные в render arrays: contexts для вариаций, tags для инвалидации, max-age для ограничения по времени. Медленные персонализированные части — lazy builders и BigPipe. Для запросов: `loadMultiple`, агрегаты, индексы по `EXPLAIN`, тяжёлое в очередь. Страница проекта в DrupalJira считает сумму часов одним запросом, а не загружает записи по одной.

> [!warning] Типичные ошибки
> 
> - Отключать кеш вместо исправления настройки.
> - Забывать tags и contexts; `max-age` как единственная инвалидация.
> - N+1; индексы без анализа.
> - Тяжёлая обработка в HTTP-запросе.
> - Масштабировать PHP, игнорируя БД.
> - Кешировать персональные данные без контекстов.
> - Тяжёлые Views без пагинации и индексов.

> [!question] Вопросы на собеседовании **Из чего состоит cacheability?** 
> Contexts, tags, max-age.
> 
> **Что такое cache bubbling?** Передача метаданных кеша от вложенных элементов к родителям. Поэтому `max-age: 0` в одном элементе отключает кеш всей страницы.
> 
> **Как избежать N+1?** Пакетная загрузка (`loadMultiple`), связанные данные одним запросом или Views, агрегирующие запросы.
> 
> **Internal Page Cache и Dynamic Page Cache?** Первый кеширует целые ответы для анонимов, второй — страницы с динамическими частями с учётом контекстов, в том числе для авторизованных.
> 
> **Чем `Cache::PERMANENT` отличается от «никогда не обновляется»?** Нет лимита по времени, но инвалидация по tags работает.

## Блок 6. Тестирование

> [!abstract] Кратко 
> Четыре уровня: Unit (изолированная логика), Kernel (ядро и тестовая БД), Functional (HTTP, `BrowserTestBase`), FunctionalJavascript (браузер с JS). Проверяют на самом простом уровне, который подтверждает корректность. Всегда тестируют права доступа, не только успешный сценарий.

### 6.1. Зачем

Модули тесно связаны с Entity API, сервисами, маршрутизацией, конфигурацией, доступом, рендерингом. Тесты ловят ошибки бизнес-логики, нарушения доступа, проблемы с БД и конфигурацией, ошибки маршрутов и форм, регрессии.

### 6.2. Виды тестов

|Тип|База|Что проверяет|
|---|---|---|
|Unit|`UnitTestCase`|логику без Drupal, зависимости — mocks/stubs|
|Kernel|`KernelTestBase`|сервисы, сущности, конфигурацию, hooks на тестовой БД|
|Functional|`BrowserTestBase`|маршруты, формы, права через HTTP|
|FunctionalJavascript|`WebDriverTestBase`|поведение, зависящее от клиентского JS|
|E2E (Playwright, Cypress/Nightwatch)|внешние|сквозные сценарии|

Kernel-тесты требуют явно подключить модули и схемы:

```php
protected static $modules = ['system', 'user', 'node', 'field', 'text', 'drupaljira_timelog'];
protected function setUp(): void {
  parent::setUp();
  $this->installEntitySchema('user');
  $this->installEntitySchema('node');
  $this->installConfig(['node', 'drupaljira_timelog']);
}
```

Functional: `$modules` и обязательный `$defaultTheme` (например, `stark`).

```php
public function testAnonymousCannotEdit(): void {
  $this->drupalGet('/node/1/edit');
  $this->assertSession()->statusCodeEquals(403);
}
```

### 6.3. Пирамида

Много быстрых unit, достаточно kernel для интеграции, functional для важных сценариев, мало тяжёлых browser-тестов. Это ориентир, не жёсткое правило.

### 6.4. Mocks и stubs

Mock задаёт ожидаемые вызовы и проверяет взаимодействие, stub возвращает заранее заданные значения. Избыток моков даёт тесты деталей реализации. Для реальной интеграции с Drupal API — kernel/functional.

### 6.5. Тестирование доступа

Проверять и разрешённого, и запрещённого пользователя, а также route access и entity access. Для DrupalJira: администратор редактирует; менеджер проекта делает разрешённое; обычный пользователь не меняет чужие задачи; аноним не получает закрытое; недоступная сущность не раскрывается через API.

### 6.6. Тестовые данные

Создаются в самом тесте; детерминированные, независимые от состояния окружения, минимальные, изолированные между тестами.

### 6.7. Регрессии

Особенно при изменении permissions и access handlers, workflow, entity definitions, конфигурации, API, миграций, кеширования. Запускают в CI перед слиянием. Тесты миграций проверяют число записей, преобразования, связи, повторный запуск; тесты очередей — идемпотентность и отсутствие дублей побочных эффектов.

### 6.8. Запуск и статический анализ

```bash
./vendor/bin/phpunit -c web/core web/modules/custom/drupaljira_timelog/tests
./vendor/bin/phpunit -c web/core --filter testLoggedHours web/modules/custom/drupaljira_timelog
```

Нужны `phpunit.xml` и переменные `SIMPLETEST_DB`, `SIMPLETEST_BASE_URL`. Дополнительно: PHPCS/PHPCBF (стандарт `Drupal`/`DrupalPractice`), PHPStan (`phpstan-drupal`).

> [!example] Практика 
> Unit для логики без Drupal, Kernel для сервисов и сущностей, Functional для маршрутов, форм и прав, FunctionalJavascript только когда нужен JS. Данные создают в тесте, кодстайл и анализ — в CI. Для статистики DrupalJira подходит Kernel-тест, для доступа к записям времени — Functional.

> [!warning] Типичные ошибки
> 
> - Только успешный сценарий.
> - Слишком много mocks.
> - Тесты, зависящие от данных сайта.
> - Не проверять права доступа.
> - Functional-тест на каждую мелочь.
> - Игнорировать нестабильные тесты.
> - Проверять реализацию, а не поведение.
> - Не запускать тесты после изменения конфигурации или схемы.

> [!question] Вопросы на собеседовании **Какие типы тестов есть?** 
> Unit, Kernel, Functional (`BrowserTestBase`), FunctionalJavascript. Выбирают самый простой подходящий уровень.
> 
> **Kernel и Functional?** Kernel поднимает ядро и БД без браузера, модули и схемы подключают вручную; Functional работает через HTTP на полноценно установленном сайте.
> 
> **Как тестировать доступ?** И разрешённого, и запрещённого пользователя, аноним, чужая сущность; route access и entity access.
> 
> **Зачем `$modules` и `$defaultTheme`?** `$modules` — включаемые для теста модули, `$defaultTheme` обязателен для `BrowserTestBase`.

## Блок 7. Безопасность

> [!abstract] Кратко 
> Безопасность многоуровневая: аутентификация, авторизация, контроль доступа, валидация входа, экранирование вывода, CSRF, защита от SQL-инъекций. Не доверять данным и проверять доступ на сервере, а не в интерфейсе. Permission не означает доступ к любой сущности: доступ к конкретной задаче проверяется отдельно.

### 7.1. Принципы

Authentication — кто; Authorization — разрешено ли действие; Access control — доступ к сущностям, маршрутам, операциям; Validation — проверка входа; Output escaping — защита от XSS; CSRF; SQL injection protection. Валидные данные не означают права их менять, и наоборот.

### 7.2. Permissions и роли

Permission — разрешённое действие, Role — набор разрешений, у пользователя может быть несколько ролей. В DrupalJira: Project Manager, Authenticated User, Administrator.

```yaml
# drupaljira_timelog.permissions.yml
manage project tasks:
  title: 'Manage project tasks'
  restrict access: true
```

Объявление не выдаёт право: роли назначают его отдельно. Проверка: `$account->hasPermission('manage project tasks')` (в классах — через DI `current_user`).

### 7.3. Доступ к маршрутам

```yaml
requirements:
  _permission: 'access content'     # или _role, _user_is_logged_in, _entity_access: 'node.update', _custom_access, _csrf_token
```

Сложные проверки — `_custom_access` или сервис с тегом `access_check`. Скрытая кнопка не защита: проверка всегда на сервере.

### 7.4. Доступ к сущностям (Entity Access API)

```php
$access = $node->access('update', NULL, TRUE);
if ($access->isAllowed()) { /* ... */ }
```

Третий аргумент `TRUE` возвращает `AccessResultInterface` с cacheability. Результат трёхзначный: Allowed, Forbidden, Neutral; Neutral не равен разрешению. Доступ проверяется отдельно для каждой операции (`view`, `update`, `delete`). Запросы к данным учитывают `accessCheck`. Если доступ зависит от пользователя, ролей или состояния сущности, это отражают в cache contexts результата (`cachePerPermissions()`, `cachePerUser()`).

### 7.5. CSRF

Form API защищает формы автоматически (form token). Для своего изменяющего маршрута:

```yaml
requirements:
  _entity_access: 'node.update'
  _csrf_token: 'TRUE'
methods: [POST]
```

Токен ожидается в параметре `token`; для REST/JSON:API с cookie — `/session/token` и заголовок `X-CSRF-Token`. CSRF-токен не заменяет проверку прав. Изменяющие действия не делают через `GET`.

### 7.6. XSS

Twig экранирует автоматически; `|raw` — только для доверенного HTML. В PHP: `Html::escape()`. В Render API: `#plain_text` экранируется полностью, `#markup` фильтруется по белому списку (`Xss::filterAdmin`). Пользовательский HTML — через text formats с фильтрами. Фильтрация не равна экранированию: экранирование делает данные безопасными для контекста вывода.

### 7.7. SQL injection

Database API с параметрами:

```php
$uid = $connection->select('users_field_data', 'u')->fields('u', ['uid'])
  ->condition('name', $username)->execute()->fetchField();
// или $connection->query('... WHERE name = :name', [':name' => $username]);
```

Для сущностей лучше Entity API. Динамические имена таблиц и столбцов требуют отдельного контроля; безопасный SQL не заменяет проверку доступа к данным.

### 7.8. Валидация

Уровни: ограничения полей и сущностей (Entity Validation API, constraints `NotBlank`, `Range`, `Length`), валидация формы, проверки в сервисах, проверка структуры API-запросов. Клиентская проверка удобство, серверная обязательна. Нарушения (violations) показывают пользователю или возвращают в API (422).

### 7.9. Файлы

Проверять расширения и размер, использовать безопасные схемы (public/private), не доверять имени и MIME от клиента, не исполнять загруженное, проверять доступ при выдаче файла (private-схема сама права не проверяет).

### 7.10. Практики

Наименьшие привилегии; доступ к каждой сущности и операции; не доверять URL, формам, API, JS; Entity и Database API вместо ручного SQL; HTTPS и `trusted_host_patterns`; секреты и `hash_salt` вне репозитория; не оставлять debug в production; обновлять core и contrib (`composer audit`, security advisories); flood control; тесты на разрешённое и запрещённое.

### 7.11. Пример: смена статуса чужой задачи

Безопасная реализация `/task/123/status` проверяет: метод (`POST`), CSRF-токен, авторизацию, право менять **именно эту** задачу, допустимость нового статуса и перехода, сохранение через API Drupal. Запрос не безопасен только потому, что кнопка видна менеджеру.

> [!example] Практика 
> Штатные API: Twig, Render API, Entity и Database API с параметрами, Form API с токенами, route requirements, Entity Access API. Следить за обновлениями, давать минимум прав, тестировать запрещённые сценарии. Смена статуса задачи DrupalJira идёт через CSRF, entity access и проверку workflow.

> [!warning] Типичные ошибки
> 
> - Скрывать кнопку вместо серверной проверки.
> - Проверять только permission, а не доступ к сущности.
> - `|raw` и непроверенный `#markup` для пользовательского ввода.
> - Конкатенация в SQL.
> - Игнорировать CSRF; лишние права «для удобства».
> - Секреты и debug-вывод в production.
> - Считать Neutral разрешением.

> [!question] Вопросы на собеседовании **Как Drupal защищает от XSS?** 
> Twig экранирует автоматически, `#plain_text` экранируется полностью, `#markup` фильтруется по списку тегов. `raw` — только для доверенного HTML.
> 
> **Как безопасно работать с БД?** Entity API или Database API с параметрами, без подстановки значений в строку SQL.
> 
> **Как защитить маршрут от CSRF?** `_csrf_token: 'TRUE'` и ограничение методов; права при этом проверяют отдельно.
> 
> **Permission и entity access?** Permission — общее право на тип действия; entity access решает по конкретной сущности и зависит от владельца, состояния и других условий.
> 
> **Что значит Neutral в AccessResult?** Проверка не дала ни разрешения, ни запрета; разрешением не считается.

## Блок 8. Multisite

> [!abstract] Кратко 
> Несколько сайтов на одной кодовой базе: общие core, модули и темы. У каждого свой каталог в `sites/`, свой `settings.php`, обычно своя БД, конфигурация и файлы. Удобно для похожих сайтов, но ошибка или обновление в общем коде затрагивает все сайты.

### 8.1. Структура

```text
web/
  core/  modules/  themes/
  sites/
    sites.php                 # сопоставление доменов и каталогов (необязательно)
    default/settings.php
    docs.example.com/settings.php
    support.example.com/settings.php
```

Drupal выбирает каталог по домену, порту и пути запроса; если подходящего нет — `sites/default`. Если имя каталога не совпадает с доменом: `$sites['docs.localhost'] = 'docs.example.com';` в `sites.php`. Multisite не означает общую БД или общих пользователей автоматически.

### 8.2. Общее и отдельное

|Компонент|Как|
|---|---|
|core, файлы модулей и тем|обычно общие|
|конфигурация, контент (при разных БД)|отдельные|
|пользователи|зависит от хранения и подключения|
|файлы|`sites/<site>/files`|
|кеш|зависит от инфраструктуры|

### 8.3. Настройка

Установить код → создать каталоги → настроить `settings.php` и подключение к БД → направить домены на общий document root → установить каждый сайт. Drush: `drush --uri=docs.example.com status|cr|cim`. Cron, очереди и `updb` выполняются **отдельно для каждого сайта**; у каждого свой sync-каталог (`config_sync_directory`).

### 8.4. Плюсы и риски

Плюсы: одна кодовая база, меньше дублирования, централизованное обновление. Риски: обновление затрагивает все сайты, нужно тестировать совместимость на каждом, конфликты требований, отдельные бэкапы, большой радиус поражения, изоляция данных зависит от настройки.

### 8.5. Когда выбирать

Когда сайты похожи и поддерживаются вместе. Если нужны независимые обновления, разные версии модулей или процессы — отдельные установки (можно с общим Composer-шаблоном). Альтернатива: один сайт с contrib-модулем **Domain** (несколько доменов, одна БД).

> [!example] Практика 
> Каталог в `sites/` с `settings.php`, при необходимости запись в `sites.php`, Drush с `--uri`. Cron, `updb` и импорт конфигурации по каждому сайту отдельно.

> [!warning] Типичные ошибки
> 
> - Считать БД и пользователей общими.
> - Обновлять общий код без тестов на каждом сайте.
> - Забывать `updb`/cron для каждого сайта.
> - Один sync-каталог для разных сайтов.
> - Секреты `settings.php` в репозитории.
> - Multisite для сайтов с разными жизненными циклами.

> [!question] Вопросы на собеседовании **Как Drupal выбирает сайт?** 
> Сопоставляет домен и путь с каталогом в `sites/` (имя или запись в `sites.php`) и загружает его `settings.php`.
> 
> **Что общее, что отдельное?** Общие core, модули, темы; отдельные `settings.php`, БД, конфигурация, файлы.
> 
> **Главные риски?** Общий код влияет на все сайты; тестировать каждый, `updb` и cron отдельно.
> 
> **Команда Drush для конкретного сайта?** `drush --uri=docs.example.com cr`.

## Блок 9. Events API

> [!abstract] Кратко 
> Один компонент сообщает о событии, другие реагируют, не зная друг о друге. Событие — объект, отправляемый через `event_dispatcher`; обработчики — event subscribers, сервисы с тегом `event_subscriber`. Подписчик объявляет события и приоритеты в `getSubscribedEvents()`. Это уменьшает связанность.

### 9.1. Понятия

- **Event** — объект с данными о событии.
- **Event dispatcher** — рассылает событие обработчикам (Symfony EventDispatcher).
- **Event subscriber** — класс, подписанный на события.
- **Event listener** — обработчик конкретного события.
- **Event name** — идентификатор (строка или класс).

События ядра: `KernelEvents::REQUEST`, `RESPONSE`, `EXCEPTION`, `TERMINATE`, `VIEW`, `ConfigEvents::SAVE`, `RoutingEvents::ALTER`. Список: `drush debug:event`. Не на всё в Drupal есть событие Symfony: жизненный цикл сущности чаще перехватывают хуками и методами сущности.

### 9.2. Подписчик

```php
final class ExampleSubscriber implements EventSubscriberInterface {
  public static function getSubscribedEvents(): array {
    return [KernelEvents::REQUEST => ['onRequest', 30]];   // больше приоритет — раньше
  }
  public function onRequest(RequestEvent $event): void { /* ... */ }
}
```

Значение — имя метода, пара `[метод, приоритет]` или список пар. Событие можно остановить: `$event->stopPropagation()`.

```yaml
services:
  drupaljira_timelog.example_subscriber:
    class: Drupal\drupaljira_timelog\EventSubscriber\ExampleSubscriber
    arguments: ['@current_user']
    tags: [{ name: event_subscriber }]
```

После добавления — `drush cr`.

### 9.3. Собственное событие

```php
final class TaskEvents { public const STATUS_CHANGED = 'drupaljira_timelog.task_status_changed'; }

final class TaskStatusChangedEvent extends Event {
  public function __construct(private readonly NodeInterface $task,
    private readonly string $oldStatus, private readonly string $newStatus) {}
  // геттеры getTask(), getOldStatus(), getNewStatus()
}

// отправка (EventDispatcherInterface через DI), после реального сохранения
$task->set('field_status', $new)->save();
$this->eventDispatcher->dispatch(new TaskStatusChangedEvent($task, $old, $new), TaskEvents::STATUS_CHANGED);
```

Имя в `dispatch()` должно совпадать с ключом в `getSubscribedEvents()`. Событие не отправляют до того, как изменение действительно произошло.

### 9.4. Events и Hooks

|Events API|Hooks|
|---|---|
|диспетчеризация событий, объект-событие|именованные точки расширения Drupal|
|сервисы-подписчики с тегом|функции `hook_*` или OOP-хуки `#[Hook]` (Drupal 11.1+)|
|подходит для событийной архитектуры|широко используется в API Drupal|

Не заменяют все хуки событиями: используют то, что предоставлено в нужной точке расширения.

### 9.5. Events и Queue

Вызов dispatcher синхронный: медленный подписчик задерживает запрос. Схема: сохранить статус → отправить событие → подписчик ставит уведомление в очередь → worker отправляет позже. Событие не даёт асинхронности, гарантии доставки и транзакционной согласованности.

### 9.6. Когда применять

Когда несколько компонентов реагируют на одно действие, а основной код не должен зависеть от них: уведомления, аудит, интеграции. Не создавать событие на каждый тривиальный вызов.

> [!example] Практика 
> Событие смены статуса задачи в DrupalJira запускает аудит и постановку уведомления в очередь. Подписчик — сервис с тегом `event_subscriber`, зависимости через конструктор.

> [!warning] Типичные ошибки
> 
> - Забыть тег `event_subscriber` или сбросить кеш.
> - Несовпадение имени события или сигнатуры.
> - Отправлять событие до сохранения.
> - Тяжёлая работа в подписчике (лучше Queue).
> - Заменять событиями все хуки; событие без реальной точки расширения.
> - Перепутать приоритеты (больший выполняется раньше).

> [!question] Вопросы на собеседовании **События и хуки?** 
> События — объекты, их обрабатывают сервисы-подписчики; хуки — именованные точки расширения Drupal, реализуемые функциями или OOP-методами.
> 
> **Как создать подписчика?** Класс с `EventSubscriberInterface` и `getSubscribedEvents()`, сервис с тегом `event_subscriber`, затем сброс кеша.
> 
> **Что значит приоритет?** Чем выше, тем раньше вызов; событие можно остановить `stopPropagation()`.
> 
> **Как отправить своё событие?** Класс события и `dispatch()` у `event_dispatcher` (через DI) после реального изменения.

## Блок 10. Entity API

> [!abstract] Кратко 
> Entity — единица данных Drupal. Entity type (`node`, `user`, `taxonomy_term`) задаёт общее поведение, bundle (`task`, `project`) — подтип со своими полями. Сущности бывают контентные (рабочие данные) и конфигурационные (настройки). Entity API — стандартный способ создавать, загружать, искать, удалять и проверять доступ без прямого SQL.

### 10.1. Content и Configuration Entity

- **Content Entity** — данные сайта: Node, User, Comment, Term, Media, File, свой `time_log`. Поля, ревизии, переводы; класс наследует `ContentEntityBase`.
- **Configuration Entity** — настройки: тип материала, роль, словарь, View. Хранятся как config, выгружаются в YAML, полей нет; `ConfigEntityBase`.

Выбор: переносится между окружениями как настройка — Config Entity; создаётся пользователями и процессами — Content Entity.

### 10.2. Entity Type, Bundle, экземпляр

Entity type — вид (`node`), bundle — подтип (`article`, `task`) со своими полями, экземпляр — конкретная запись. Bundles часто сами config entities (для node — `node_type`, параметр `bundle_entity_type`). Если подтипов нет, bundle совпадает с id типа. В DrupalJira project и task — bundles node, `time_log` — отдельная сущность.

### 10.3. Загрузка и сохранение

```php
$storage = $this->entityTypeManager->getStorage('node');
$node = $storage->load(123);                 // NULL, если нет
$nodes = $storage->loadMultiple($ids);
$node = $storage->create(['type' => 'task', 'title' => 'Implement workflow', 'status' => 1]);
$node->save();                               // вставка или обновление
$node->delete();
```

Здесь `status` — статус **публикации**, не пользовательское `field_status` и не moderation state. Перед сохранением проверяют обязательные поля, права, бизнес-правила; `$node->validate()` для ограничений. Прямой SQL к таблицам сущностей обходит поля, ревизии, хуки: не используют.

### 10.4. Работа с полями

```php
$status = $node->get('field_status')->value;
$node->set('field_status', 'in_progress')->save();
$project = $node->get('field_project')->entity;     // NULL, если нет
$id = $node->get('field_project')->target_id;
```

Значение должно соответствовать настройкам поля. Многозначные поля — Блок 14.

### 10.5. Entity Query

```php
$ids = $storage->getQuery()
  ->accessCheck(TRUE)
  ->condition('type', 'task')->condition('field_status', 'in_progress')
  ->sort('created', 'DESC')->range(0, 10)->execute();
$tasks = $storage->loadMultiple($ids);
```

Возвращает ID, не объекты. `accessCheck()` обязателен в Drupal 10/11: `TRUE` учитывает права, `FALSE` — только для системных операций с обоснованием. `->count()` для подсчёта.

### 10.6. Entity Access

`$node->access('view')`, `$node->access('update', NULL, TRUE)` → `AccessResultInterface`. Решает access control handler сущности, хуки `hook_entity_access()`/`hook_ENTITY_TYPE_access()`, для node — node grants. Доступ к отдельным полям — `hook_entity_field_access`. Для создания — `createAccess()` у handler. Permissions — в `permissions.yml` или `permission_callbacks`; `admin_permission` в описании типа.

### 10.7. Entity Reference

Поле `entity_reference`: `target_type`, `handler` (`default:node`), `handler_settings` (`target_bundles`). В БД хранится `target_id`, `->entity` возвращает объект. Обратную связь (задачи проекта) находят запросом по полю ссылки. Проверяют существование, доступность, допустимые типы цели.

### 10.8. Revisions

Отдельные версии объекта: история и откат.

```php
$node->setNewRevision(TRUE);
$node->setRevisionLogMessage('Status changed to in_progress');
$node->save();
```

Поддержка зависит от типа сущности, конфигурации и модулей (Content Moderation).

### 10.9. Entity API и Render API

Entity API — данные, Render API — отображение. Для вывода используют view builders и режимы: `$viewBuilder->view($node, 'teaser')`. Непроверенные пользовательские данные в HTML не вставляют.

### 10.10. Собственная Content Entity

Когда node не подходит (своя структура, много записей, отдельная таблица), создают custom content entity (`time_log`). Составные части:

1. Класс в `src/Entity/` (`ContentEntityBase`) с атрибутом `#[ContentEntityType]` (в старых версиях аннотация), интерфейс.
2. `baseFieldDefinitions()`.
3. Handlers (Блок 16).
4. Права и ссылки (`links`), пункты меню/кнопки.
5. Таблицы создаются при установке модуля; изменение структуры существующей сущности — update hook (`EntityDefinitionUpdateManager`).

Параметры `#[ContentEntityType]`:

- `id`, `label`, `label_collection`, `label_singular`, `label_plural`;
- `handlers`;
- `base_table`, `data_table` (по языкам), `revision_table`;
- `admin_permission`;
- `entity_keys`;
- `links` (canonical, add-form, edit-form, delete-form, collection);
- `field_ui_base_route` (к нему Field UI цепляет «Управление полями» и «Управление отображением»; без него интерфейса полей не будет);
- `translatable`, `bundle_entity_type`, `bundle_label`, `show_revision_ui`, `constraints`.

Доп. возможности подключают интерфейсами: `EntityChangedInterface` (дата изменения), `EntityOwnerInterface` (автор), `EntityPublishedInterface`.

### 10.11. Entity keys

Соответствие «роль → имя поля», чтобы `$entity->id()`, `label()` работали единообразно: `id`, `uuid`, `label`, `langcode`, `bundle`, `uid`/`owner`, `status`/`published`, `revision`.

```php
entity_keys: ['id' => 'id', 'uuid' => 'uuid', 'label' => 'title', 'owner' => 'uid'],
```

### 10.12. Base fields

```php
public static function baseFieldDefinitions(EntityTypeInterface $entity_type) {
  $fields = parent::baseFieldDefinitions($entity_type);
  $fields['hours'] = BaseFieldDefinition::create('decimal')
    ->setLabel(t('Часы'))->setRequired(TRUE)
    ->setDisplayOptions('form', ['type' => 'number', 'weight' => 0])
    ->setDisplayConfigurable('form', TRUE)->setDisplayConfigurable('view', TRUE);
  $fields['task'] = BaseFieldDefinition::create('entity_reference')
    ->setLabel(t('Задача'))->setSetting('target_type', 'node')->setRequired(TRUE);
  return $fields;
}
```

Base fields одинаковы для всех bundles типа; configurable fields создаются через Field UI для конкретных bundles и хранятся в конфигурации.

### 10.13. Как хранятся сущности

- `base_table` — основная запись (id, uuid, bundle, язык, простые базовые поля).
- `data_table` — данные по языкам, `revision_table` и `revision_data_table` — ревизии.
- Поля из Field UI — отдельные таблицы `тип__имя_поля` (`node__field_status`) и `тип_revision__имя_поля`, колонки `имя_value`, `имя_target_id`.

Если описание полей изменилось после установки, нужен update hook; иначе в статусе предупреждение «Mismatched entity and/or field definitions».

### 10.14. Хуки жизненного цикла

`hook_entity_presave()`, `hook_entity_insert()`, `hook_entity_update()`, `hook_entity_delete()` и варианты `hook_ENTITY_TYPE_presave()`. То же в классе сущности: `preSave()`, `postSave()`, `preDelete()`.

> [!example] Практика 
> Загрузка и сохранение через storage, поиск через Entity Query с явным `accessCheck`, проверка `access()`, поля и revisions. SQL к таблицам сущностей не пишут. Когда node не подходит — собственная content entity: в DrupalJira project и task — bundles node, записи времени — `time_log`.

> [!warning] Типичные ошибки
> 
> - Путать entity type и bundle.
> - Путать `status` (публикация), `field_status` и moderation state.
> - Забывать `accessCheck()`.
> - Не проверять `NULL` после `load()` и у ссылок.
> - Загружать в цикле (N+1).
> - SQL вместо Entity API.
> - Менять схему custom entity без update hook.
> - Не задать `field_ui_base_route` и удивляться, что нет Field UI.

> [!question] Вопросы на собеседовании **Entity type и bundle?** 
> Тип задаёт общий вид (node, user), bundle — подтип со своим набором полей (article, page).
> 
> **Content entity и configuration entity?** Первая хранит рабочие данные, вторая описывает настройки и экспортируется в YAML.
> 
> **Зачем `accessCheck` в Entity Query?** Учитывать ли права при выборке; в Drupal 10/11 указывается явно, `FALSE` только осознанно.
> 
> **Base fields и configurable fields?** Первые объявлены в коде и есть у всех bundles, вторые создаются через UI или конфигурацию для конкретных bundles.
> 
> **Что такое entity keys?** Соответствие ролей (id, uuid, label, bundle, owner) именам полей.
> 
> **Где хранятся поля из Field UI?** В отдельных таблицах `тип__имя_поля`.

## Блок 11. Plugin API

> [!abstract] Кратко 
> Плагин — взаимозаменяемая реализация известного контракта: блок, виджет поля, queue worker, process-плагин миграции. Plugin Manager находит плагины (по атрибутам или аннотациям), хранит определения и создаёт экземпляры. Плагин нужен для интеграции с подсистемой Drupal, бизнес-логику лучше выносить в сервис.

### 11.1. Основные понятия

- **Plugin type** — вид (Block, FieldFormatter, QueueWorker).
- **Plugin Manager** — сервис `plugin.manager.<type>`: знает каталог (`Plugin/Block`), интерфейс, кеширует определения, создаёт `createInstance('id', $config)`.
- **Plugin ID** — уникален в рамках типа.
- **Plugin Definition** — метаданные: id, название, категория, класс.
- **Конфигурация экземпляра** — настройки конкретного использования (отличается от определения).

Плагины применяются для блоков, способов аутентификации, источников миграции, виджетов и форматтеров, обработчиков очередей, Actions, условий, фильтров текста, эффектов изображений, плагинов Views. Типы сущностей тоже обнаруживаются как плагины.

### 11.2. Discovery

- **Attribute discovery** — PHP-атрибуты `#[Block(...)]` (10.2/10.3+, предпочтительны в 11).
- **Annotation discovery** — аннотации в docblock (`@Block(...)`), устаревают, в старом коде встречаются.
- **YAML discovery** — меню, local tasks, `*.migrate_drupal.yml`.
- **Hook discovery** — `hook_*_info`.

Порядок: менеджер сканирует `src/Plugin/<Тип>/` во всех модулях, читает атрибуты, собирает определения. После добавления плагина — `drush cr` (кеш определений). Конкретный механизм зависит от типа плагина.

### 11.3. Block Plugin

```php
#[Block(
  id: 'task_summary',
  admin_label: new TranslatableMarkup('Task Summary'),
  category: new TranslatableMarkup('DrupalJira'),
)]
final class TaskSummaryBlock extends BlockBase {
  public function build(): array {
    return ['#theme' => 'item_list', '#items' => [$this->t('Backlog')],
      '#cache' => ['tags' => ['node_list:task']]];
  }
}
```

`build()` возвращает render array, а не HTML-строку: так Drupal обработает вложенные элементы, библиотеки, cache metadata и доступ. Методы блока: `blockForm()`, `blockSubmit()` (настройки), `blockAccess()`, `defaultConfiguration()`.

### 11.4. Другие типы

- Field Formatter (`FormatterBase`): `viewElements()`.
- Field Widget (`WidgetBase`): `formElement()`.
- Queue Worker (`QueueWorkerBase`): `processItem($data)`, `cron: ['time' => 60]`.
- Field Type (`FieldItemBase`).

### 11.5. DI в плагинах

```php
final class TaskSummaryBlock extends BlockBase implements ContainerFactoryPluginInterface {
  public function __construct(array $configuration, $plugin_id, $plugin_definition,
    private readonly EntityTypeManagerInterface $entityTypeManager) {
    parent::__construct($configuration, $plugin_id, $plugin_definition);
  }
  public static function create(ContainerInterface $container, array $configuration, $plugin_id, $plugin_definition): static {
    return new static($configuration, $plugin_id, $plugin_definition, $container->get('entity_type.manager'));
  }
}
```

Сигнатуры базовых классов зависят от версии Drupal.

### 11.6. Свой тип плагина

1. Интерфейс и базовый класс.
2. Класс атрибута (наследует `Drupal\Component\Plugin\Attribute\Plugin`) с полями описания.
3. Plugin Manager (`DefaultPluginManager`): в конструкторе папка, интерфейс, класс атрибута; `alterInfo()`, `setCacheBackend()`.
4. Сервис `plugin.manager.<type>` (`parent: default_plugin_manager`) и реализации в `src/Plugin/<Тип>/`.

Для вариантов, порождаемых данными (один блок на проект), — **derivatives**.

### 11.7. Plugin и hook, сервис, handler

Хук вмешивается в существующую точку расширения; плагин — отдельная реализация известного типа. Не всякое расширение должно быть плагином. Сервис — один объект с постоянной ролью, `plugin.manager.block` — сервис, управляющий плагинами блоков.

> [!example] Практика 
> Плагины там, где Drupal ожидает взаимозаменяемые реализации. Тонкий плагин интегрируется с подсистемой, сервис содержит логику. Блок статистики в DrupalJira строит render array, а считает данные сервис.

> [!warning] Типичные ошибки
> 
> - Аргументы в конструктор плагина без `ContainerFactoryPluginInterface`.
> - Не сбросить кеш; неверный namespace/каталог.
> - Бизнес-логика в плагине.
> - Возвращать HTML-строку вместо render array.
> - Путать определение и конфигурацию экземпляра.
> - Плагин там, где хватает hook или сервиса.
> - Один и тот же ID у двух плагинов одного типа.

> [!question] Вопросы на собеседовании **Что такое Plugin Manager?** 
> Сервис, который находит плагины типа, хранит определения и создаёт экземпляры.
> 
> **Annotation и attribute discovery?** Определение в docblock или в PHP-атрибуте; в новых версиях (10.2/10.3+, 11) предпочтительны атрибуты.
> 
> **Как получить сервисы в плагине?** `ContainerFactoryPluginInterface` и `create()`.
> 
> **Когда плагин, когда hook?** Плагин — отдельная конфигурируемая реализация известного типа; hook — вмешательство в существующую точку.
> 
> **Из чего состоит свой тип плагина?** Интерфейс, атрибут, менеджер, регистрация сервисом, реализации в `Plugin/<Тип>`.

## Блок 12. Batch API, Cron и Queue API

> [!abstract] Кратко 
> Долгие операции нельзя выполнять одним HTTP-запросом. Batch API делит работу на шаги с прогрессом (запускает пользователь). Cron выполняет периодические задачи. Queue API хранит отдельные задания, которые обрабатывают воркеры. Их часто комбинируют.

### 12.1. Зачем

Импорт тысяч записей, массовая обработка, рассылки, удаление устаревшего, синхронизация: в одном запросе возможны лимиты PHP, тайм-ауты и перегрузка.

### 12.2. Batch API

```php
$builder = (new BatchBuilder())
  ->setTitle(t('Updating tasks'))
  ->setFinishCallback(['\Drupal\drupaljira_timelog\Batch\TaskBatch', 'finished'])
  ->addOperation(['\Drupal\drupaljira_timelog\Batch\TaskBatch', 'process'], [$ids]);
batch_set($builder->toArray());
```

(старый вариант — массив `$batch = ['title', 'operations', 'finished']`). Операция:

```php
public static function process(array $ids, array &$context): void {
  if (!isset($context['sandbox']['progress'])) {
    $context['sandbox']['progress'] = 0;
    $context['sandbox']['max'] = count($ids);
  }
  $chunk = array_slice($ids, $context['sandbox']['progress'], 50);
  // обработать $chunk
  $context['sandbox']['progress'] += count($chunk);
  $context['finished'] = $context['sandbox']['max'] ? $context['sandbox']['progress'] / $context['sandbox']['max'] : 1;
}
```

- `$context['sandbox']` — состояние между вызовами одной операции;
- `$context['results']` — результаты для следующих шагов и finish callback;
- `$context['message']` — текст прогресса;
- `$context['finished']` — доля 0…1, операция повторяется, пока не достигнет 1.

В update hook то же: `hook_update_N(&$sandbox)` и `$sandbox['#finished']`. Batch не делает операцию безопасной автоматически и не является полноценным фоновым заданием, независимым от браузера: для такого лучше Queue.

### 12.3. Cron API

Периодические задачи: очистка временных данных, обработка очередей, обслуживание модулей, синхронизация. Запуск: Automated Cron, Drush, системный планировщик.

```php
function drupaljira_timelog_cron(): void { /* небольшие задачи или постановка в очередь */ }
```

```bash
drush cron
*/15 * * * * cd /var/www/html && vendor/bin/drush cron
```

В `hook_cron()` не делают тяжёлую обработку тысяч записей без ограничений. Системный cron лишь запускает Drupal Cron; на production лучше внешний планировщик. Время последнего запуска собственных задач — в `State`.

### 12.4. Queue API

Понятия: queue, item, worker, claim, delete, backend.

```php
$this->queueFactory->get('drupaljira_notifications')->createItem(['task_id' => 123, 'recipient_uid' => 45]);
```

Worker:

```php
#[QueueWorker(id: 'drupaljira_notifications', title: new TranslatableMarkup('Task notifications'), cron: ['time' => 30])]
final class TaskNotificationWorker extends QueueWorkerBase {
  public function processItem($data): void { /* проверить данные, найти задачу и получателя, отправить */ }
}
```

`cron time` — бюджет времени обработки в cron, а не гарантия. Задача или пользователь могли быть удалены. Исключения: `RequeueException` (повторить позже), `SuspendQueueException` (остановить очередь, например при недоступности внешней системы). Ручной запуск: `drush queue:run <имя>`, список — `drush queue:list`. Очередь можно обрабатывать не только cron, но и отдельным CLI-воркером.

### 12.5. Надёжность очередей

- Повторная обработка возможна: воркер **идемпотентен** (повтор не даёт дублей: повторное списание, повторные письма).
- Данные задания валидируются; в очередь кладут минимум (ID и параметры), актуальное состояние загружают в воркере.
- Временные сбои не удаляют элемент; ошибки логируются.
- Конкурентные воркеры учитывают гонки.
- Чувствительные данные и большие объекты в очередь не кладут.

### 12.6. Сравнение и выбор

|API|Назначение|Сценарий|
|---|---|---|
|Batch|длительная операция шагами с прогрессом|админ обновляет тысячи задач|
|Cron|периодический запуск|очистка старых данных|
|Queue|отложенная обработка отдельных заданий|уведомления после изменения задачи|

Комбинация: Batch импортирует набор задач → для каждой создаётся задание уведомления → cron запускает воркеры. Для короткой операции очередь не нужна.

> [!example] Практика 
> Batch — когда пользователь запускает долгое действие и ждёт прогресс; Cron — регулярное обслуживание; Queue — отложенные независимые задания. В update hook большие объёмы идут порциями через `$sandbox`. В DrupalJira update hook `10001` обрабатывает существующие задачи порциями, а уведомления логично отправлять через очередь.

> [!warning] Типичные ошибки
> 
> - Тяжёлая обработка в `hook_cron()`.
> - Batch без ограничения порции и без `$context['finished']`.
> - Не идемпотентный воркер.
> - Удалять элемент очереди при временной ошибке.
> - Не настроить системный cron.
> - Чувствительные данные и огромные объекты в очереди.
> - Очередь для коротких мгновенных операций.

> [!question] Вопросы на собеседовании **Когда Batch, Queue, Cron?** 
> Batch — запуск пользователем с прогрессом, Queue — отложенные отдельные задания, Cron — расписание.
> 
> **Что такое идемпотентность воркера?** Повторная обработка элемента не даёт дублей; важна, потому что элементы могут выполняться повторно.
> 
> **Большой объём в `hook_update_N()`?** `&$sandbox`, порция за вызов, `$sandbox['#finished']` от 0 до 1.
> 
> **Как вручную запустить очередь?** `drush queue:run <имя очереди>`, список — `drush queue:list`.
> 
> **`RequeueException` и `SuspendQueueException`?** Первое возвращает элемент в очередь на повтор, второе останавливает обработку всей очереди.

## Блок 13. Migration API

> [!abstract] Кратко 
> Данные переносятся из источника в Drupal по схеме Source → Process → Destination. Source читает строки, process-плагины преобразуют значения, destination создаёт сущности. Соответствие старых и новых записей хранится в ID map, поэтому миграции можно перезапускать, обновлять и откатывать. Связи между миграциями задаются зависимостями и `migration_lookup`.

### 13.1. Назначение

Перенос из старой версии Drupal, CSV, XML/JSON, другой CMS, внешней БД, устаревшей структуры полей. Используются Migrate (ядро), **Migrate Plus** и **Migrate Tools**. Пример: старая система хранит статус `working`, новая — `in_progress`: Source отдаёт `working`, Process преобразует, Destination сохраняет в поле.

### 13.2. Компоненты

- **Source** — откуда: SQL, CSV, XML, JSON API, Drupal; строки с уникальными `ids`.
- **Process** — как преобразовать: переименовать, формат даты, статус, найти сущность, ссылка, объединить.
- **Destination** — куда: материалы (`entity:node`), пользователи, термины.
- **ID map** — таблица соответствия исходных и целевых идентификаторов.

### 13.3. Пример

```yaml
id: legacy_tasks
label: 'Import legacy tasks'
migration_group: legacy
source:
  plugin: embedded_data
  data_rows:
    - { id: 1, title: 'Fix login', old_status: working }
  ids: { id: { type: integer } }
process:
  type: { plugin: default_value, default_value: task }
  title: title
  field_status:
    plugin: static_map
    source: old_status
    map: { todo: backlog, working: in_progress, qa: review, completed: done }
destination:
  plugin: 'entity:node'
```

`embedded_data` — демонстрационный источник. Файлы миграций лежат в `migrations/` модуля (или как config entity при Migrate Plus). Если значения нет в `static_map`, поведение определяется настройками (`default_value`, `bypass`): неизвестные значения нужно обработать явно.

### 13.4. Process plugins

|Плагин|Назначение|
|---|---|
|`get`|получить значение|
|`default_value`|значение по умолчанию|
|`static_map`|преобразование по карте|
|`concat`|объединение|
|`skip_on_empty`|пропуск при пустом|
|`migration_lookup`|результат другой миграции|
|`entity_lookup`|поиск сущности (Migrate Plus)|
|`callback`, `format_date`, `explode`, `sub_process`|вспомогательные|

Цепочка плагинов (pipeline) выполняется последовательно. Собственное преобразование — custom process plugin (`transform()`).

### 13.5. Зависимости и lookup

Сначала проекты, затем задачи:

```yaml
migration_dependencies:
  required: [legacy_projects]
process:
  field_project:
    plugin: migration_lookup
    migration: legacy_projects
    source: legacy_project_id
```

Если проект не найден, решают: пропустить задачу, импортировать без связи или завершить ошибкой.

### 13.6. ID map

Исходная задача `42` → материал `137`. Нужна для повторного запуска, обновления, связей между миграциями, учёта обработанных записей. Map не заменяет бэкап; изменение исходных данных не обязательно обновит целевые сущности автоматически.

### 13.7. Запуск

```bash
drush migrate:status
drush migrate:import legacy_tasks
drush migrate:import legacy_tasks --update     # обновить импортированные
drush migrate:import legacy_tasks --limit=10   # пробный запуск
drush migrate:messages legacy_tasks
drush migrate:rollback legacy_tasks            # может удалять созданные сущности
```

Инкрементальные импорты — `track_changes` и `high_water_property`. Изменение YAML не всегда обновляет уже импортированное: определяют, какие записи обработать повторно, нужен ли `--update` или откат, нужно ли импортировать обновлённое определение (если config entity). Сначала проверяют на тестовой копии.

### 13.8. Миграция и update hook

Миграция переносит данные **из внешнего источника**; update hook преобразует **существующую** установку при обновлении кода (например, инициализация `field_project_type` у существующих задач).

> [!example] Практика 
> Миграции описывают в YAML, запускают через Migrate Tools и Drush, зависимости задают в `migration_dependencies`, связи — через `migration_lookup`, значения — `static_map`. Перед реальным запуском — копия данных, `--limit`, `migrate:messages`. В DrupalJira при миграции статусов нужно согласовать и moderation state.

> [!warning] Типичные ошибки
> 
> - Не указать `migration_dependencies`, запускать задачи раньше проектов.
> - Менять YAML и ждать автообновления импортированного.
> - `rollback` без понимания последствий.
> - Не обработать значения вне `static_map`.
> - Мигрировать только `field_status`, забыв moderation state и публикацию.
> - Не проверить на тестовой копии.
> - Использовать плагины Migrate Plus без установки модуля.

> [!question] Вопросы на собеседовании **Из чего состоит миграция?** 
> Source (чтение), process (преобразование), destination (сохранение).
> 
> **Что такое ID map?** Таблица соответствия исходных записей и созданных сущностей; позволяет перезапускать, обновлять и откатывать.
> 
> **Как связать две миграции?** `migration_dependencies` и плагин `migration_lookup`.
> 
> **Какие команды Drush?** `migrate:status`, `migrate:import` (`--update`, `--limit`), `migrate:messages`, `migrate:rollback`.

## Блок 14. Field API

> [!abstract] Кратко 
> Field API добавляет сущностям структурированные данные. Различают Field Type (тип данных), Field Storage (как и где хранится, cardinality) и Field Configuration (использование на конкретном bundle). Ввод обеспечивает widget, вывод — formatter. Поля бывают базовыми (в коде сущности) и конфигурируемыми (UI/конфигурация). Бывают также вычисляемые (computed) поля.

### 14.1. Field Type, Storage, Configuration

|Тип|Назначение|
|---|---|
|`string`, `text_long`, `text`|короткий текст, длинный, форматированный|
|`integer`, `decimal`, `float`, `boolean`|числа, логика|
|`entity_reference`|ссылка на сущность|
|`datetime`|дата и время|
|`list_string`|список допустимых значений (статусы)|
|`image`, `file`|файлы|

- **Field Storage** (`field.storage.node.field_x`, `FieldStorageConfig`) — тип, cardinality, настройки хранения; привязан к entity type и имени поля. После появления данных часть настроек менять нельзя (например, целевой тип ссылки).
- **Field Configuration** (`field.field.node.task.field_x`, `FieldConfig`) — использование на bundle: подпись, описание, обязательность, значение по умолчанию. Одно хранилище можно использовать в нескольких bundles, у каждого свой FieldConfig.

`field_estimate` — decimal, одно значение, добавлено к `task`, но отсутствует у `project`.

### 14.2. Base fields и configurable fields

- **Base fields** — в коде (`baseFieldDefinitions()`, `BaseFieldDefinition`), есть у всех bundles (`title`, `uid`, `status` у node); меняются кодом и update hooks.
- **Configurable fields** — через UI/конфигурацию для конкретных bundles (`field_status` у `task`); меняются через UI и Configuration Management.

Для custom entity вроде `time_log` поля обычно base. Для базовых полей нужен `setDisplayConfigurable('form'|'view', TRUE)` или `setDisplayOptions()`, иначе поле не попадёт в настройки отображения.

### 14.3. Создание поля

Через UI: тип материала → управление полями → добавить → тип → cardinality, обязательность → форма и отображение → **экспорт конфигурации**. Через YAML: пишут на основе экспорта рабочей конфигурации, а не «наугад»; привязка к bundle хранится отдельно.

### 14.4. Чтение и запись значений

```php
$estimate = $node->get('field_estimate')->value;      // decimal — обычно строка
$node->hasField('field_estimate');
$assignee = $node->get('field_assignee')->entity;     // может быть NULL
foreach ($node->get('field_attachments') as $item) { $id = $item->target_id; }
$node->get('field_x')->isEmpty();
$node->get('field_x')->getValue();                    // массив значений
$node->get('field_project')->referencedEntities();
```

`->value` читает только первый элемент. **FieldItemList** — список значений поля у сущности (`first()`, `get($delta)`, `getValue()`, `setValue()`, `isEmpty()`), **FieldItemBase** — одно значение со свойствами (`value`, `target_id`, `format`). У разных типов разные свойства: нельзя считать, что всегда есть `value`.

```php
[['target_id' => 5], ['target_id' => 7]]   // структура многозначной ссылки
```

### 14.5. Cardinality и атрибуты

- Cardinality: `1`, число N, `-1` (`CARDINALITY_UNLIMITED`).
- `required`, `translatable`, `revisionable`.

```php
BaseFieldDefinition::create('string')->setLabel(t('Заметка'))
  ->setCardinality(3)->setRequired(FALSE)->setTranslatable(TRUE)->setRevisionable(TRUE);
```

### 14.6. Entity Reference и таксономия

Настройки: `target_type` (`taxonomy_term`), `handler` (`default:taxonomy_term`), `handler_settings` с `target_bundles` и `auto_create`. Термин — Content Entity, словарь — Config Entity. Учитывают существование и доступность цели, допустимые типы, поведение при удалении.

### 14.7. Widget и Formatter

**Widget** — как значение вводится (текстовое поле, список, автодополнение; настраивается в _Manage form display_). **Formatter** — как отображается (текст, ссылка, дата, название связанной сущности; _Manage display_). Один тип поля может иметь несколько виджетов и форматтеров. Это плагины (Блок 11): собственный тип поля — три плагина: FieldType, FieldWidget, FieldFormatter. Widget не заменяет серверную валидацию.

### 14.8. Form Display и View Display

- Form Display (`core.entity_form_display.{тип}.{bundle}.{режим}`) — виджеты и порядок в форме.
- View Display (`core.entity_view_display.{тип}.{bundle}.{режим}`) — форматтеры при выводе (full, teaser и др.).

Это конфигурация, поэтому выгружается в YAML.

### 14.9. Computed fields (вычисляемые поля)

Значение не хранится в БД, считается при обращении. Два элемента: определение поля с `setComputed(TRUE)` (таблицы и сохранение не нужны) и класс списка с `computeValue()`. Чужой сущности добавляют через `hook_entity_base_field_info()` или `hook_entity_bundle_field_info()`.

```php
$fields['logged_hours'] = BaseFieldDefinition::create('float')
  ->setLabel(t('Залогировано часов'))->setComputed(TRUE)->setReadOnly(TRUE)
  ->setClass(LoggedHoursItemList::class)->setDisplayConfigurable('view', TRUE);

class LoggedHoursItemList extends FieldItemList {
  use ComputedItemListTrait;
  protected function computeValue() {
    $value = 0;   // расчёт, например через сервис
    $this->list[0] = $this->createItem(0, $value);
  }
}
```

|Сохранённое поле|Вычисляемое поле|
|---|---|
|значение в БД, можно искать и сортировать (Entity Query, Views)|значения в БД нет, всегда актуально|
|читается без расчётов|по нему нельзя просто искать и сортировать, таблиц не создаёт|

Когда что: вычисляемое поле — значение производное, но нужно как поле сущности (вывод, API, шаблон); сервис — сложные расчёты, суммы по многим сущностям, переиспользование (в DrupalJira — `TaskStatService`); метод сущности — простое вычисление по данным самой сущности; обычное поле — значение нужно хранить, искать, сортировать, вводить.

Производительность: в списке из многих сущностей расчёт и запросы для каждой — N+1. Смягчение: один запрос для всех ID в сервисе, static cache. Если нужны фильтры и сортировка — хранимое поле. Вывод должен нести cache tags (на сущности `time_log`, от которых зависит значение), contexts и max-age.

### 14.10. Поля, Views, Configuration Management

Views выводит поля без ручных запросов. Определения полей — конфигурация: при переносе учитывают модуль типа поля, entity type и bundle, цели ссылок, виджеты, форматтеры, display-конфигурации. Если чего-то нет, импорт может упасть. Экспорт структуры не переносит значения полей существующих материалов.

### 14.11. Изменение схемы

Новая схема не применяется к существующей БД автоматически: нужны update hooks, обновление конфигурации или миграция данных. Особенно осторожно менять тип поля и структуру хранения, если есть данные.

> [!example] Практика 
> Создать поле через UI или конфигурацию, проверить виджет и форматтер, экспортировать конфигурацию, читать значения через Entity API. Для существующих данных любые изменения storage — update hook или миграция. Для собственной сущности поля base, для nodes — configurable. В DrupalJira у задачи список статусов, decimal-оценка и ссылка на проект.

> [!warning] Типичные ошибки
> 
> - Путать field storage и field configuration.
> - Читать только `->value` у многозначного поля или у ссылки.
> - Не проверять `NULL` у Entity Reference.
> - Менять storage поля с данными без update hook или миграции.
> - Писать YAML полей вручную без экспорта; забыть экспорт после UI.
> - Менять `field_status`, забыв moderation state.
> - Считать widget механизмом безопасности.
> - Ждать, что по вычисляемому полю можно фильтровать.

> [!question] Вопросы на собеседовании **Field storage и field configuration?** 
> Storage описывает тип, cardinality и хранение для entity type; configuration (`field.field.*`) — использование на конкретном bundle.
> 
> **Widget и formatter?** Widget отвечает за ввод, formatter за отображение.
> 
> **Как прочитать многозначное поле?** Итерацией по элементам или `getValue()`; `->value` даёт только первый элемент.
> 
> **Что делать при изменении storage поля с данными?** Update hook или миграция: схема автоматически не применяется.
> 
> **Что такое computed field?** Поле без хранения, значение считается при обращении (`setComputed(TRUE)` и `computeValue()`); искать и сортировать по нему нельзя.

## Блок 15. Authentication API

> [!abstract] Кратко 
> Аутентификация отвечает на «кто делает запрос», авторизация — «что ему разрешено». За аутентификацию отвечают authentication providers: cookie-сессия, HTTP Basic, токены и OAuth (contrib). После определения пользователя Drupal всё равно проверяет доступ к маршруту, сущности и бизнес-правила.

### 15.1. Сессия и провайдеры

После входа Drupal использует сессию в cookie. Для внешних клиентов — токен или иной способ. **Authentication Provider** — компонент, определяющий, может ли механизм аутентифицировать запрос (`applies()`, `authenticate()`). Выбираются по типу запроса, модулям, конфигурации маршрута (`options: _auth: [...]`) и должны быть включены и настроены.

|Механизм|Принцип|
|---|---|
|Session/Cookie|cookie с id сессии, обычный сайт|
|HTTP Basic (`basic_auth`)|логин и пароль в `Authorization`, интеграции|
|Bearer/OAuth/JWT|токен; contrib (`simple_oauth`, key-auth и др.)|
|внешняя идентификация|SSO|

Не все механизмы входят в ядро; наличие заголовка Bearer само по себе поддержку не включает.

### 15.2. REST и аутентификация

Для REST настраивают ресурс, методы, форматы, аутентификацию (`authentication: [cookie, basic_auth]` в `rest.resource.*`), разрешения и доступ к сущностям. Даже при подтверждённой личности проверяется право на операцию.

### 15.3. Basic Authentication

```http
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

Base64 — кодирование, а не шифрование, поэтому только через HTTPS. Подходит для отдельных интеграций; учитывают хранение секретов в клиенте и ограничения доступа. Если возможен механизм с ограниченными токенами, его предпочитают.

### 15.4. Cookie и CSRF

Браузер отправляет cookie автоматически, что создаёт риск CSRF для изменяющих операций. Проверяют метод, CSRF-токен (для REST/JSON:API с cookie — `X-CSRF-Token` из `/session/token`), разрешения, доступ к сущности, допустимость операции. При Bearer-токене в заголовке модель угроз иная, но API не защищён автоматически: учитывают хранение токена, XSS, CORS, HTTPS, срок жизни, отзыв, права.

### 15.5. Токены

Срок действия, отзыв, безопасное хранение, scopes, HTTPS, защита от утечки через логи и URL; секретные токены не передают в query string. Для интеграций — отдельная учётная запись с минимальными правами.

### 15.6. Последовательность и сравнение

Запрос → аутентификация → доступ к маршруту → доступ к сущности → бизнес-правила → изменение → ответ.

|Authentication|Authorization|
|---|---|
|определяет личность|определяет доступные действия|
|учётные данные или токен|permissions и access rules|
|«Кто ты?»|«Что тебе разрешено?»|

### 15.7. Собственный провайдер

Нужен, когда стандартных механизмов недостаточно. Сервис с тегом `authentication_provider` и `AuthenticationProviderInterface`:

```yaml
services:
  authentication.example_token:
    class: Drupal\example\Authentication\Provider\TokenAuth
    arguments: ['@entity_type.manager']
    tags:
      - { name: authentication_provider, provider_id: 'example_token', priority: 100 }
```

```php
final class TokenAuth implements AuthenticationProviderInterface {
  public function applies(Request $request): bool { return $request->headers->has('X-Api-Token'); }
  public function authenticate(Request $request) { /* проверить токен; вернуть аккаунт или NULL */ }
}
```

Нужно продумать порядок нескольких провайдеров, обработку невалидных данных, безопасность токенов, тесты позитивных и негативных сценариев. Для одного маршрута свой механизм не создают; не принимают «user id» из запроса без проверки подлинности.

### 15.8. Безопасность API

HTTPS, минимальные права, доступ к каждой сущности, валидация входа, ограничение методов, секреты не в логах, правильные ошибки, тесты без аутентификации и с недостаточными правами, flood control. Пользователь не должен получать чужую задачу простой сменой ID в URL.

> [!example] Практика 
> Для внешней интеграции выбирают провайдер: cookie для браузера, Basic через HTTPS для простых случаев, OAuth/токены из contrib для API. Указывают в `rest.resource.*` или `_auth` маршрута. Система, читающая задачи DrupalJira, получает отдельного пользователя только с правом чтения.

> [!warning] Типичные ошибки
> 
> - Путать аутентификацию и авторизацию.
> - Считать, что токен или сессия дают право на всё.
> - Basic Auth без HTTPS; токены в URL или логах.
> - Не включить провайдер для маршрута.
> - Игнорировать CSRF для cookie-запросов.
> - Свой провайдер там, где хватает готового.
> - Права администратора технической учётной записи.

> [!question] Вопросы на собеседовании **Authentication и authorization?** 
> Первое определяет, кто делает запрос, второе — что ему разрешено.
> 
> **Что такое Authentication Provider?** Сервис с тегом `authentication_provider` и `AuthenticationProviderInterface`: `applies()` — подходит ли к запросу, `authenticate()` — возвращает пользователя.
> 
> **Как включить Basic Auth для REST-ресурса?** Включить `basic_auth` и добавить `basic_auth` в `authentication` конфигурации `rest.resource.*`.
> 
> **Почему Basic Auth без HTTPS нельзя?** Base64 не шифрует: логин и пароль читаются при перехвате.

## Блок 16. Entity Handlers

> [!abstract] Кратко 
> Handler — класс, который выполняет одну роль для типа сущности: список, форма, проверка прав, маршруты. Тип сущности лишь перечисляет в параметре `handlers`, какой класс за что отвечает. Любую роль можно заменить отдельно. Если handler не указан, этой возможности у сущности нет (без `route_provider` страниц не появится).

### 16.1. Основные handlers

|Handler|Роль|
|---|---|
|`storage`|загрузка и сохранение (по умолчанию `SqlContentEntityStorage`)|
|`list_builder` (`EntityListBuilder`)|страница списка: `buildHeader()`, `buildRow($entity)`, `getDefaultOperations()`|
|`form`|формы `default`, `add`, `edit`, `delete`; базовые `ContentEntityForm`, `EntityForm`, `ContentEntityDeleteForm`|
|`access` (`EntityAccessControlHandler`)|`checkAccess($entity, $operation, $account)`, `checkCreateAccess()` → `AccessResult`|
|`views_data` (`EntityViewsData`)|поля сущности для Views|
|`route_provider`|автоматически создаёт маршруты по `links`: `DefaultHtmlRouteProvider`, `AdminHtmlRouteProvider` (canonical, add_form, edit_form, delete_form, collection)|
|`view_builder` (`EntityViewBuilder`)|отображение сущности|

Получить handler: `getListBuilder()`, `getAccessControlHandler()`, `getFormObject($type, 'edit')`, `getStorage()`, `getViewBuilder()` у `EntityTypeManager`.

### 16.2. Подключение в атрибуте

```php
#[ContentEntityType(
  id: 'time_log',
  label: new TranslatableMarkup('Time log'),
  handlers: [
    'list_builder' => TimeLogListBuilder::class,
    'form' => ['default' => TimeLogForm::class, 'delete' => ContentEntityDeleteForm::class],
    'access' => TimeLogAccessControlHandler::class,
    'views_data' => EntityViewsData::class,
    'route_provider' => ['html' => AdminHtmlRouteProvider::class],
  ],
  base_table: 'time_log',
  admin_permission: 'administer time_log',
  entity_keys: ['id' => 'id', 'uuid' => 'uuid'],
  links: [
    'collection' => '/admin/content/time-log',
    'add-form' => '/admin/content/time-log/add',
    'edit-form' => '/admin/content/time-log/{time_log}/edit',
    'delete-form' => '/admin/content/time-log/{time_log}/delete',
  ],
)]
```

### 16.3. Свой handler

Почти всегда наследуются от стандартного класса и переопределяют нужные методы.

```php
class TimeLogListBuilder extends EntityListBuilder {
  public function buildHeader() { $h['id'] = $this->t('ID'); return $h + parent::buildHeader(); }
  public function buildRow(EntityInterface $entity) { $r['id'] = $entity->id(); return $r + parent::buildRow($entity); }
}
```

Если нужны сервисы — `createInstance(ContainerInterface $container, EntityTypeInterface $entity_type)` (в стандартных классах уже есть).

### 16.4. Handler, сервис, плагин, контроллер

- Сервис — один объект на сайт, объявлен в `services.yml`, не привязан к типу сущности.
- Handler — роль конкретного типа сущности, указан в описании сущности, создаётся менеджером сущностей.
- Плагин — один из вариантов вида, Drupal находит по атрибуту.
- Контроллер — класс маршрута, возвращает содержимое страницы.

> [!warning] Типичные ошибки
> 
> - Нет `route_provider` или `links`: страниц нет.
> - Писать handler с нуля вместо наследования.
> - Забыть `drush cr` после изменения определения.

> [!question] Вопросы на собеседовании **Как Drupal узнаёт, какой класс отвечает за список, форму, права?** 
> Читает `handlers` в описании типа; `EntityTypeManager` по id типа и роли находит и создаёт класс.
> 
> **Handler и сервис?** Handler — роль конкретного типа сущности, сервис — один общий объект с постоянной ролью.

## Блок 17. Form API

> [!abstract] Кратко 
> Формы строят на `FormBase` (обычная), `ConfigFormBase` (настройки модуля) и `EntityForm`/`ContentEntityForm` (создание и редактирование сущности). Четыре метода: `getFormId()`, `buildForm()`, `validateForm()`, `submitForm()`. Form API автоматически защищает формы CSRF-токеном и поддерживает AJAX.

### 17.1. Подключение

Обычная форма — маршрут с `_form: '\Drupal\mymodule\Form\MyForm'`. Форма сущности — через `handlers` (Блок 16).

### 17.2. Методы

- `getFormId()` — уникальное имя (по нему работает `hook_form_FORM_ID_alter()`).
- `buildForm()` — массив с описанием формы.
- `validateForm()` — проверка; ошибка: `$form_state->setErrorByName('hours', $this->t('...'))`. Если есть ошибки, `submitForm()` не вызывается.
- `submitForm()` — сохранение; перенаправление `$form_state->setRedirect('имя.маршрута')`.

```php
class HoursForm extends FormBase {
  public function getFormId() { return 'mymodule_hours_form'; }
  public function buildForm(array $form, FormStateInterface $form_state) {
    $form['hours'] = ['#type' => 'number', '#title' => $this->t('Часы'), '#required' => TRUE];
    $form['actions']['submit'] = ['#type' => 'submit', '#value' => $this->t('Сохранить')];
    return $form;
  }
  public function validateForm(array &$form, FormStateInterface $form_state) {
    if ($form_state->getValue('hours') <= 0) {
      $form_state->setErrorByName('hours', $this->t('Часы должны быть больше нуля.'));
    }
  }
  public function submitForm(array &$form, FormStateInterface $form_state) { /* сохранить */ }
}
```

### 17.3. Свойства элементов

`#type` (`textfield`, `textarea`, `number`, `select`, `checkbox`, `checkboxes`, `radios`, `entity_autocomplete`, `submit`, `details`, `container`), `#title`, `#default_value`, `#required`, `#options` (для select/radios/checkboxes), `#states` (показать/скрыть/заблокировать по другому полю без JS).

```php
$form['reason'] = ['#type' => 'textfield', '#title' => t('Причина'),
  '#states' => ['visible' => [':input[name="status"]' => ['value' => 'blocked']]]];
```

### 17.4. Значения и хранение

`$form_state->getValue('имя')`, `getValues()`; при `'#tree' => TRUE` — `getValue(['группа', 'поле'])`. Данные между шагами — `$form_state->set()`/`get()`. Сохранение: в конфигурацию `->set('ключ', $v)->save()`, в сущность `$entity->set('поле', $v)->save()`. Дополнительные обработчики — `$form['#validate'][]`, `$form['#submit'][]` (или на конкретную кнопку).

### 17.5. DI в формах

```php
class MyForm extends FormBase {
  public function __construct(protected EntityTypeManagerInterface $entityTypeManager) {}
  public static function create(ContainerInterface $container) {
    return new static($container->get('entity_type.manager'));
  }
}
```

### 17.6. Форма настроек

```php
class SettingsForm extends ConfigFormBase {
  protected function getEditableConfigNames() { return ['mymodule.settings']; }
  public function getFormId() { return 'mymodule_settings'; }
  public function buildForm(array $form, FormStateInterface $form_state) {
    $form['limit'] = ['#type' => 'number', '#title' => $this->t('Лимит часов'),
      '#default_value' => $this->config('mymodule.settings')->get('limit')];
    return parent::buildForm($form, $form_state);
  }
  public function submitForm(array &$form, FormStateInterface $form_state) {
    $this->config('mymodule.settings')->set('limit', $form_state->getValue('limit'))->save();
    parent::submitForm($form, $form_state);
  }
}
```

Для настроек модуля описывают config schema.

### 17.7. Форма сущности

`ContentEntityForm`, подключается через `handlers`, доступна `$this->entity`, поля строятся из Form Display, сохранение `save()`.

### 17.8. AJAX

Три шага: у элемента `#ajax` (`callback`, `wrapper`, `event`); обновляемый блок оформлен контейнером с этим id; callback возвращает часть формы или `AjaxResponse` с командами (`ReplaceCommand`, `HtmlCommand`, `AppendCommand`, `InvokeCommand`, `CssCommand`, `MessageCommand`, `RedirectCommand`).

```php
$form['project'] = ['#type' => 'select', '#options' => $projects,
  '#ajax' => ['callback' => '::updateTasks', 'wrapper' => 'tasks-wrapper', 'event' => 'change']];
$form['tasks'] = ['#type' => 'select', '#options' => $tasks,
  '#prefix' => '<div id="tasks-wrapper">', '#suffix' => '</div>'];

public function updateTasks(array &$form, FormStateInterface $form_state) { return $form['tasks']; }
```

### 17.9. Изменение чужих форм

`hook_form_FORM_ID_alter()` позволяет добавить поле, изменить подпись, скрыть элемент (`#access => FALSE`), добавить проверку и submit. Добавленное поле само нигде не сохранится: нужен свой submit-обработчик.

```php
function mymodule_form_node_task_edit_form_alter(&$form, FormStateInterface $form_state) {
  $form['my_note'] = ['#type' => 'textfield', '#title' => t('Заметка')];
  $form['#validate'][] = 'mymodule_task_validate';
  $form['actions']['submit']['#submit'][] = 'mymodule_task_submit';
}
```

> [!warning] Типичные ошибки
> 
> - Сохранять значения в `validateForm()`.
> - Не вызвать `parent::buildForm()`/`parent::submitForm()` в `ConfigFormBase`.
> - Забыть `getEditableConfigNames()`.
> - Нет контейнера с id для AJAX.
> - Добавить поле в чужую форму без submit-обработчика.
> - Вручную собирать HTML-форму вместо Form API (теряется CSRF-защита).

> [!question] Вопросы на собеседовании **Основные методы формы?** 
> `getFormId()`, `buildForm()`, `validateForm()`, `submitForm()`.
> 
> **Чем `ConfigFormBase` отличается от `FormBase`?** Предназначен для настроек: значения сохраняются в конфигурацию, нужен `getEditableConfigNames()`.
> 
> **Как получить сервисы в форме?** `create()` достаёт их из контейнера и передаёт в конструктор.
> 
> **Как работает AJAX в форме?** `#ajax` с callback и wrapper; callback возвращает часть формы или `AjaxResponse` с командами.

## Блок 18. Изменение чужого кода и сущностей без правки

> [!abstract] Кратко 
> Core и чужие модули не правят: изменения пропадут при обновлении. Вместо этого используют точки расширения: alter-хуки, подписчики на события, подмену сервисов, настройки, темизацию. Значение, лежащее в config, меняют через config; значение, записанное в PHP-атрибуте, меняют через alter-хук.

### 18.1. Метки и определения сущностей

Тип сущности описан в PHP (`#[ContentEntityType]`, `#[ConfigEntityType]`) — его «паспорт». Через UI он не меняется; из своего модуля — хуками. После изменения определений `drush cr`.

```php
function mymodule_entity_type_alter(array &$entity_types) {
  $entity_types['node']->setLabel(t('Материал'));        // также setClass() и т.п.
}
function mymodule_entity_bundle_info_alter(array &$bundles) {
  $bundles['node']['article']['label'] = t('Новость');
}
function mymodule_entity_base_field_info_alter(array &$fields, EntityTypeInterface $entity_type) {
  if ($entity_type->id() === 'node') { $fields['title']->setLabel(t('Название задачи')); }
}
```

`hook_entity_bundle_field_info_alter()` меняет поля, привязанные к bundle. Подписи полей из Field UI хранятся в конфигурации: меняют там, а не кодом.

### 18.2. Config или определение сущности

- **Config** — настройки в БД и YAML (`node.type.article`, `field.field.node.article.field_x`); меняются через админку, `drush config:set`, импорт; переносятся между окружениями.
- **Определение сущности** — в PHP-атрибуте; меняется только кодом (alter-хук), в YAML не выгружается.

### 18.3. Формы, действия, ссылки, маршруты

|Что менять|Чем|
|---|---|
|элементы формы|`hook_form_alter()` и варианты|
|ссылки операций (Edit, Delete)|`hook_entity_operation_alter()`|
|вкладки и кнопки «Добавить»|`hook_menu_local_tasks_alter()`, `hook_menu_local_actions_alter()`|
|пункты меню|`hook_menu_links_discovered_alter()`|
|отдельные ссылки|`hook_link_alter()`|
|адреса, заголовки, права маршрутов|`RouteSubscriber`, метод `alterRoutes()`|
|простая замена текста|перевод строки (locale) или `$settings['locale_custom_strings_en']`|

### 18.4. Три варианта form_alter

- `hook_form_alter()` — на все формы, внутри проверять `$form_id`.
- `hook_form_BASE_FORM_ID_alter()` — на семейство форм (`hook_form_node_form_alter()` — все формы материалов).
- `hook_form_FORM_ID_alter()` — на одну форму; самый точный, обычно лучший.

Общие хуки вызываются раньше конкретных.

### 18.5. HTML

- `hook_theme()` — модуль регистрирует собственный шаблон (новый вывод).
- `hook_preprocess_HOOK()` — меняет или добавляет переменные до шаблона.
- Переопределение Twig в теме — меняет разметку; включают Twig debug, чтобы увидеть имена шаблонов.
- `hook_theme_suggestions_HOOK_alter()` — свои имена шаблонов, `hook_theme_registry_alter()` — изменение регистрации чужого theme hook.

```php
function mymodule_preprocess_node(array &$variables) { $variables['is_overdue'] = FALSE; }
// шаблон в теме: templates/node--task--full.html.twig
```

### 18.6. Порядок предпочтения способов

1. Настройки (config).
2. Alter-хуки.
3. Подписчик на события.
4. Подмена или декорирование сервиса.
5. Подмена класса handler или плагина через alter.
6. Тема (preprocess, Twig).
7. Патч через composer-patches — крайняя мера, причину записывают.

> [!question] Вопросы на собеседовании **Как изменить подпись поля?** 
> Поле из админки — через config; базовое — `hook_entity_base_field_info_alter()`.
> 
> **Как изменить название типа сущности или bundle?** `hook_entity_type_alter()`, `hook_entity_bundle_info_alter()` или config (для типов материалов).
> 
> **Какой form_alter выбрать?** Самый узкий: `hook_form_FORM_ID_alter()`.
> 
> **Как менять чужую функциональность без правки кода?** Config → alter-хуки → события → подмена сервиса → тема → патч.

## Блок 19. settings.php и подключение к БД

> [!abstract] Кратко 
> Параметры подключения к БД лежат в `settings.php` выбранного сайта (и файлах окружения), а не в конфигурации: конфигурация хранится в БД, и чтобы её прочитать, нужно сначала подключиться. На каждом окружении они свои, секреты приходят из окружения, а не из Git.

### 19.1. settings.php и settings.local.php

- `sites/default/settings.php` — главный PHP-файл настроек сайта: подключение к БД, `hash_salt`, `config_sync_directory`, `trusted_host_patterns`, путь private-файлов, overrides. Читается в самом начале запуска.
- `settings.local.php` — настройки только этого окружения, подключается блоком в конце `settings.php`, если файл существует; в Git не кладут (`.gitignore`). Также `settings.ddev.php`, `settings.lando.php` создаются средой.

### 19.2. $databases

Структура `$databases[ключ][цель]`: `default` — основная БД, `replica` — копия для чтения.

```php
$databases['default']['default'] = [
  'driver' => 'mysql', 'database' => 'drupaljira',
  'username' => 'db_user', 'password' => getenv('DB_PASSWORD'),
  'host' => 'db', 'port' => '3306', 'prefix' => '',
  'namespace' => 'Drupal\\mysql\\Driver\\Database\\mysql',
  'autoload' => 'core/modules/mysql/src/Driver/Database/mysql/',
];
```

Параметры: `driver`, `database`, `username`, `password`, `host`/`port` (или `unix_socket`), `prefix`, `namespace`, `autoload`.

### 19.3. Настройки подключения и конфигурация

|settings.php|YAML-конфигурация|
|---|---|
|PHP-массивы `$databases`, `$settings`, `$config`|`config/sync`, `config/install`|
|окружение, секреты, пути|настройки сайта и модулей|
|в config sync не попадает|переносится через Git|

Правило: значение разное на каждом окружении или секретное — в `settings.php`; общее для сайта — в конфигурацию.

### 19.4. Как Drupal выбирает настройки

По домену, порту и пути ищется папка в `sites/` (соответствия — `sites/sites.php`); если нет — `sites/default`. Затем читается `settings.php` этой папки. В multisite у каждого сайта свои БД, файлы и config sync (Блок 8).

### 19.5. Секреты

Пароли и ключи берут из окружения: `getenv('DB_PASSWORD')`, `$settings['hash_salt'] = getenv('DRUPAL_HASH_SALT');`. Источники: переменные сервера или контейнера, `.env` (не в Git), секреты CI, Docker, Kubernetes. На production `settings.php` делают только для чтения (`chmod 444`). Относится и к `hash_salt`, ключам API, паролям SMTP.

Почему не в Git: Git хранит историю, удалённый пароль остаётся в старых коммитах; утечка пароля — доступ к БД. `settings.local.php` и `.env` в `.gitignore`, общий `settings.php` без секретов; если пароль попал в Git — сразу менять. `config/sync` тоже в Git, секреты в нём не хранят: используют overrides или модули Key и Encrypt.

### 19.6. Overrides

- `$config['имя.настройки']['ключ'] = значение;` — подмена во время работы, в БД не пишется (через `get()` видна, через `getEditable()` нет).
- `$settings['config_sync_directory'] = '../config/sync';`
- `$settings['hash_salt']`, `trusted_host_patterns`, `file_private_path`, `file_temp_path`.
- `$settings['config_exclude_modules']` — исключить модули из синхронизации.

### 19.7. Диагностика подключения

`drush status` (строка Database), `drush sql:cli`, `drush sql:connect`, `drush sqlq "SELECT 1"`, страница `/admin/reports/status`. Пустой `settings.php` или отсутствие подключения — открывается установщик (`install.php`).

Типичные ошибки MySQL:

- 1045 Access denied — неверные логин/пароль или нет прав на БД;
- 1049 Unknown database — БД нет или неверное имя;
- 2002 Connection refused — неверный host/port, сервер БД не запущен; в Docker и DDEV хост — имя контейнера (`db`), а не `localhost`;
- Driver not found — нет расширения `pdo_mysql` или неверные `namespace`/`autoload`.

Проверить: подключиться клиентом `mysql` с теми же данными, значения переменных окружения, какой файл настроек реально подключился (подхватился ли `settings.local.php`), права пользователя БД.

> [!warning] Типичные ошибки
> 
> - Пароль к БД в Git.
> - Путать `$databases` в `settings.php` с YAML-конфигурацией.
> - В Docker указывать `localhost` вместо имени контейнера.
> - Забыть, что `settings.local.php` не попадает на другие окружения.

> [!question] Вопросы на собеседовании **Откуда Drupal берёт параметры подключения к БД?** 
> Из `$databases` в `settings.php` выбранного сайта и подключаемых файлов окружения.
> 
> **Почему их нельзя хранить в конфигурации?** Конфигурация лежит в БД: чтобы её прочитать, нужно подключиться. К тому же у каждого окружения свои база и пароль, а конфигурация лежит в Git.
> 
> **Как не коммитить секреты?** `getenv()`, `.env` и `settings.local.php` в `.gitignore`, секреты CI/контейнера.
> 
> **Что делать, если пароль попал в Git?** Немедленно сменить.

## Блок 20. Практические flow: создать через админку и в коде, переопределить, нюансы

> [!abstract] Кратко 
> Любой объект Drupal можно создать тремя путями: **админка** (результат лежит в активной конфигурации/БД), **конфигурация в коде** (YAML в `config/install` модуля) и **PHP-код** (классы, плагины, сервисы). Разница определяет, переносится ли объект между окружениями и можно ли его изменить после установки. Общий приём: сделать в админке → `drush cex` → перенести нужные YAML в модуль.

### 20.0. Админка: адреса, которые нужно знать

|Что|Путь|
|---|---|
|Модули (включить/выключить)|`/admin/modules`|
|Типы материалов|`/admin/structure/types`|
|Поля типа `task`|`/admin/structure/types/manage/task/fields`|
|Форма редактирования (виджеты)|`/admin/structure/types/manage/task/form-display`|
|Отображение (форматтеры)|`/admin/structure/types/manage/task/display`|
|Роли и права|`/admin/people/roles`, `/admin/people/permissions`|
|Views|`/admin/structure/views`|
|Размещение блоков|`/admin/structure/block`|
|Меню|`/admin/structure/menu`|
|Таксономия|`/admin/structure/taxonomy`|
|Текстовые форматы|`/admin/config/content/formats`|
|Языки / перевод контента|`/admin/config/regional/language`, `/admin/config/regional/content-language`|
|Синхронизация конфигурации|`/admin/config/development/configuration`|
|Логи / статус|`/admin/reports/dblog`, `/admin/reports/status`|

### 20.1. Создание модуля (основа всего)

Структура:

```text
web/modules/custom/drupaljira_timelog/
  drupaljira_timelog.info.yml
  drupaljira_timelog.module            # хуки в процедурном стиле
  drupaljira_timelog.install           # hook_install, hook_schema, hook_update_N
  drupaljira_timelog.services.yml
  drupaljira_timelog.routing.yml
  drupaljira_timelog.permissions.yml
  drupaljira_timelog.links.menu.yml / .links.task.yml / .links.action.yml
  config/install/  config/optional/  config/schema/
  src/ (Controller, Form, Entity, Plugin/..., EventSubscriber, Service)
  templates/
```

```yaml
# drupaljira_timelog.info.yml
name: 'DrupalJira TimeLog'
type: module
description: 'Учёт времени по задачам.'
package: DrupalJira
core_version_requirement: ^10.3 || ^11
dependencies:
  - drupal:node
  - drupal:views
```

Flow: создать папку и `info.yml` → в админке `/admin/modules` или `drush en drupaljira_timelog` → `drush cr`. Дальше код подхватывается: autoload PSR-4 для `Drupal\drupaljira_timelog\` → `src/`.

Нюансы:

- namespace должен совпадать с путём (`src/Plugin/Block/X.php` ↔ `Drupal\модуль\Plugin\Block`), иначе плагин/класс не найдётся;
- `dependencies` в `info.yml` и в YAML-конфигурации должны быть согласованы, иначе модуль не установится;
- имя модуля = префикс всех хуков (`drupaljira_timelog_cron`) и сервисов (`drupaljira_timelog.task_stat`);
- генерация каркаса: `drush generate module`, `drush generate controller|form|plugin:block|service`.

### 20.2. Тип материала (content type)

**Через админку.** Структура → Типы материалов → Добавить → название (machine name `task`), настройки: «Создавать новую ревизию», «Отображать информацию об авторе», превью → сохранить. Затем поля, форма, отображение (20.3). Права: `/admin/people/permissions` → «Task: Create new content» и т.д.

**В коде (config).** Файл `config/install/node.type.task.yml`:

```yaml
langcode: en
status: true
dependencies: {}
name: Task
type: task
description: 'Work item for a project.'
help: ''
new_revision: true
preview_mode: 1
display_submitted: false
```

Установка модуля создаст тип автоматически.

**Как делают на практике:** создать в админке → `drush cex` → скопировать нужные файлы `node.type.task.yml`, `field.storage.*`, `field.field.*`, `core.entity_form_display.*`, `core.entity_view_display.*` в `config/install` модуля → **удалить из них ключи `uuid` и `_core`** (иначе конфликт UUID при установке на другом сайте).

Нюансы:

- по тому же принципу создаются роли, Views, vocabularies, text formats: «сделал в UI → экспортировал → положил в модуль»;
- файлы в `config/install` применяются **только при установке модуля**; на уже установленном сайте нужен update hook или обычный `config:import` (Блок 3);
- если у типа есть поля, их storage и instance должны ставиться раньше/вместе: зависимости (`dependencies.config`) проставляют порядок;
- права на тип материала (`create task content`, `edit own task content`, `edit any task content`, `delete ...`) создаются автоматически при появлении типа.

### 20.3. Поле

**Через админку.** Тип материала → Управление полями → Добавить поле → тип (число decimal, список list_string, ссылка entity reference) → machine name `field_estimate` → настройки хранилища (cardinality, precision/scale, допустимые значения списка) → настройки поля (label, required, default, допустимые bundles для ссылки) → Управление формой (виджет, порядок) → Управление отображением (форматтер, label above/hidden, порядок). Не забыть `drush cex`.

**В коде — конфигурацией.** Четыре файла:

```yaml
# field.storage.node.field_estimate.yml
langcode: en
status: true
dependencies:
  module: [node]
id: node.field_estimate
field_name: field_estimate
entity_type: node
type: decimal
settings: { precision: 10, scale: 2 }
module: core
locked: false
cardinality: 1
translatable: true
indexes: {}
persist_with_no_fallback: false
custom_storage: false
```

```yaml
# field.field.node.task.field_estimate.yml
langcode: en
status: true
dependencies:
  config: [field.storage.node.field_estimate, node.type.task]
id: node.task.field_estimate
field_name: field_estimate
entity_type: node
bundle: task
label: 'Оценка (часы)'
description: ''
required: false
translatable: false
default_value: {  }
default_value_callback: ''
settings: { min: 0, max: null, prefix: '', suffix: '' }
field_type: decimal
```

Плюс `core.entity_form_display.node.task.default.yml` (виджет `number`) и `core.entity_view_display.node.task.default.yml` (форматтер `number_decimal`). Без display-файлов поле существует, но **не видно** ни в форме, ни при выводе.

**В коде — PHP.** Для существующего сайта (update hook):

```php
FieldStorageConfig::create([
  'field_name' => 'field_estimate', 'entity_type' => 'node', 'type' => 'decimal',
  'settings' => ['precision' => 10, 'scale' => 2],
])->save();
FieldConfig::create([
  'field_name' => 'field_estimate', 'entity_type' => 'node', 'bundle' => 'task', 'label' => 'Оценка',
])->save();
\Drupal::service('entity_display.repository')
  ->getFormDisplay('node', 'task')->setComponent('field_estimate', ['type' => 'number'])->save();
\Drupal::service('entity_display.repository')
  ->getViewDisplay('node', 'task')->setComponent('field_estimate', ['type' => 'number_decimal'])->save();
```

**Базовое поле** — только кодом (`baseFieldDefinitions()` своей сущности; к чужой — `hook_entity_base_field_info()`; после добавления в существующую сущность нужен update hook с `EntityDefinitionUpdateManager::installFieldStorageDefinition()`).

Нюансы:

- configurable field: после появления данных менять тип и часть настроек storage нельзя;
- `list_string`: допустимые значения хранятся в storage; **менять ключи (machine values) нельзя без миграции данных**, меняют подписи;
- для отображения базового поля нужен `setDisplayConfigurable()`/`setDisplayOptions()`;
- перевод: у поля флаг `translatable` в storage и отдельная галочка для bundle в `/admin/config/regional/content-language`.

### 20.4. Роль и права

**Админка.** Люди → Роли → Добавить роль → `/admin/people/permissions` (по роли или общая матрица) → отметить права.

**Код.**

1. Объявить права: `drupaljira_timelog.permissions.yml` (Блок 7). Динамические права — `permission_callbacks: ['\Drupal\mod\Class::method']`.
2. Выдать роли: в `config/install/user.role.project_manager.yml` с блоком `permissions`, либо программно:

```php
user_role_grant_permissions('authenticated', ['access content']);   // в hook_install / update hook
Role::load('project_manager')->grantPermission('manage project tasks')->save();
```

3. Назначить роль пользователю: `$user->addRole('project_manager'); $user->save();`.

Нюансы:

- объявить право ≠ выдать его: без выдачи его нет ни у кого, кроме администратора (роль администратора получает все права автоматически, `is_admin`);
- `user.role.*` в `config/install` должна иметь `dependencies` на модули, объявляющие права, иначе ошибка при установке;
- права и роли — конфигурация, переносятся через `cex`/`cim`; назначение роли пользователю — контент, не переносится.

### 20.5. Маршрут, страница, меню

**Админка.** Маршруты создаёт только код (или Views — страница/блок). Пункт меню: Структура → Меню → добавить ссылку (хранится как контент `menu_link_content`, не как конфигурация).

**Код.**

```yaml
# drupaljira_timelog.routing.yml
drupaljira_timelog.task_list:
  path: '/tasks'
  defaults:
    _controller: '\Drupal\drupaljira_timelog\Controller\TaskController::list'
    _title: 'Tasks'
  requirements:
    _permission: 'access content'
```

```yaml
# drupaljira_timelog.links.menu.yml — пункт меню
drupaljira_timelog.tasks:
  title: 'Tasks'
  route_name: drupaljira_timelog.task_list
  parent: system.admin_content
  weight: 10
```

```yaml
# drupaljira_timelog.links.task.yml — вкладка
drupaljira_timelog.tab_list:
  title: 'List'
  route_name: drupaljira_timelog.task_list
  base_route: drupaljira_timelog.task_list
```

```yaml
# drupaljira_timelog.links.action.yml — кнопка «Добавить»
drupaljira_timelog.add:
  title: 'Add task'
  route_name: drupaljira_timelog.task_add
  appears_on: [drupaljira_timelog.task_list]
```

Нюансы:

- после добавления маршрута/ссылки — `drush cr` (кеш маршрутов и меню);
- ссылки меню из `*.links.menu.yml` — плагины (меняются alter-хуками), ссылки из админки — контент;
- параметр `{node}` + `options.parameters.node.type: entity:node` даёт upcasting, но **не проверяет bundle** — проверяйте вручную;
- `_title_callback` нужен для динамического заголовка.

### 20.6. Блок

**Админка.** Структура → Размещение блоков → «Разместить блок» в нужном регионе темы → выбрать блок (системный или от модуля) → заголовок, видимость (страницы, типы материалов, роли), регион → сохранить. Для редактируемого контента: Контент → Блоки → «Добавить блок» (custom block, это content entity), затем разместить.

**Код.** Плагин `src/Plugin/Block/TaskSummaryBlock.php` (Блок 11) → после `drush cr` он появляется в списке «Разместить блок». Само **размещение** — конфигурация `block.block.<id>.yml` (тема, регион, плагин, visibility); в коде:

```php
Block::create(['id' => 'task_summary', 'theme' => 'olivero', 'region' => 'sidebar',
  'plugin' => 'task_summary', 'settings' => ['label' => 'Summary']])->save();
```

Нюансы:

- плагин блока и размещение блока — **две разные вещи**: плагин один, размещений может быть много, у каждого свои настройки и видимость;
- блок размещается **в теме** (размещение привязано к теме); при смене темы блоки нужно разместить заново;
- кеш блока: `getCacheContexts()`, `getCacheTags()`, `getCacheMaxAge()` или `#cache` в `build()`;
- права доступа блока: `blockAccess()`.

### 20.7. View

**Админка.** Структура → Views → Добавить View → показать «Материалы» типа `task`, сортировка → формат (таблица/список/сетка), поля, фильтры, сортировки, relationships, contextual filters, пейджер → дополнительно: страница (путь, меню), блок или REST export → сохранить → `drush cex`.

**Код.** Файл `config/install/views.view.task_list.yml` (экспортированный). Расширение: плагины Views (field/filter/sort/argument handlers), `hook_views_data()` (подключить свою таблицу/сущность), `hook_views_data_alter()` (добавить поле к чужим данным), `hook_views_query_alter()`, `hook_views_pre_render()`.

Нюансы:

- у Views свой кеш (по tags/time), настраивается в «Расширенные → Кеширование»;
- выбранный в Views формат «Поля» vs «Материал» (отображение через view mode) влияет на производительность;
- view с контекстным фильтром требует корректного значения аргумента по умолчанию.

### 20.8. Собственная сущность: полный flow

1. Интерфейс и класс `src/Entity/TimeLog.php` (`#[ContentEntityType]`, Блок 10/16).
2. `baseFieldDefinitions()` (поля) + entity keys.
3. Handlers: list_builder, form, access, views_data, route_provider (Блок 16).
4. `links` (адреса) + `admin_permission` / `permissions.yml`.
5. Меню/кнопка: `links.menu.yml`, `links.action.yml`, `links.task.yml`.
6. Включить модуль: таблицы создаются автоматически (`drush en`); `drush cr`.
7. Поля через Field UI — только если задан `field_ui_base_route` (и сущность «fieldable»).
8. Проверка: `/admin/content/time-log`, права, форма добавления, удаление.
9. Тесты: Kernel (CRUD, access) и Functional (страницы).

**Изменение уже установленной сущности:** добавили/изменили базовое поле → на `/admin/reports/status` появится «Mismatched entity and/or field definitions» → нужен update hook:

```php
function drupaljira_timelog_update_10002() {
  $definition = BaseFieldDefinition::create('string')->setLabel(t('Comment'));
  \Drupal::entityDefinitionUpdateManager()
    ->installFieldStorageDefinition('comment', 'time_log', 'drupaljira_timelog', $definition);
}
```

Если данные уже есть, а тип меняется — миграция данных в batch (`$sandbox`).

### 20.9. Сервис, форма, событие, плагин: краткие flow «создать»

|Что|Файлы|Дальше|
|---|---|---|
|Сервис|класс в `src/Service`, запись в `services.yml`|внедрить через `arguments`/`create()` → `drush cr`|
|Форма|класс в `src/Form`, маршрут с `_form`|`drush cr`|
|Подписчик|класс в `src/EventSubscriber` + сервис с тегом `event_subscriber`|`drush cr`|
|Плагин (блок, worker, formatter)|класс в `src/Plugin/<Тип>` с атрибутом|`drush cr`|
|Права|`permissions.yml`|выдать роли|
|Update hook|`.install`, `hook_update_N()`|`drush updb`|
|Хук|функция в `.module` (или OOP `#[Hook]`)|`drush cr`|

### 20.10. Как переопределять (шпаргалка по объектам)

|Что переопределить|Как|
|---|---|
|**Сервис** (заменить класс)|`ServiceProvider`: класс `Drupal\mod\ModServiceProvider extends ServiceProviderBase`, `alter(ContainerBuilder $c) { $c->getDefinition('x')->setClass(Y::class); }`. Или декоратор `decorates:` в `services.yml`|
|**Маршрут** (путь, права, контроллер)|`RouteSubscriber extends RouteSubscriberBase`, `alterRoutes(RouteCollection $c)`: `$c->get('entity.node.canonical')->setRequirement('_permission', '...')`, `->setDefault('_controller', ...)`; сервис с тегом `event_subscriber`|
|**Контроллер**|заменить `_controller` у маршрута (см. выше)|
|**Класс сущности**|`hook_entity_type_alter()`: `$entity_types['node']->setClass(MyNode::class)`; для bundle — bundle classes (`hook_entity_bundle_info_alter`, ключ `class`)|
|**Handler сущности** (список, форма, доступ)|`hook_entity_type_alter()`: `->setHandlerClass('list_builder', X::class)`, `setFormClass('default', X::class)`, `setAccessClass(X::class)`|
|**Плагин** (блок, форматтер, виджет…)|`hook_block_alter()`, `hook_field_formatter_info_alter()`, `hook_field_widget_info_alter()`, в общем виде `hook_<тип>_info_alter()` — поменять `class` в определении|
|**Форму**|`hook_form_FORM_ID_alter()`; `hook_form_BASE_FORM_ID_alter()`; либо подмена класса формы через `hook_entity_type_alter()`|
|**Виджет/форматтер поля**|`hook_field_widget_single_element_form_alter()`, `hook_field_formatter_third_party_settings_form`; либо свой плагин и выбор в Manage display|
|**Вывод сущности**|`hook_entity_view_alter()`, `hook_ENTITY_TYPE_view_alter()`, `hook_entity_display_build_alter()`, preprocess|
|**Шаблон**|копия `*.html.twig` в теме; `hook_theme_suggestions_HOOK_alter()` для новых имён; preprocess для переменных|
|**CSS/JS библиотеку**|в теме `libraries-override` / `libraries-extend` (`theme.info.yml`), в модуле `hook_library_info_alter()`; страница целиком: `hook_page_attachments_alter()`|
|**Права доступа к сущности**|`hook_entity_access()`, `hook_ENTITY_TYPE_access()`, `hook_node_access()`, `hook_entity_field_access()`, `hook_entity_create_access()`; `AccessResult::forbidden()` перебивает allowed|
|**Права на маршрут**|`RouteSubscriber` + `setRequirement()`; свой `access_check` сервис|
|**Запрос к БД/сущностям**|`hook_query_alter()`, `hook_query_TAG_alter()` (теги вроде `node_access`), `hook_views_query_alter()`|
|**Конфигурацию**|UI/`config:set`/импорт (постоянно); `$config[...]` в `settings.php` или `ConfigFactoryOverrideInterface` (подмена на лету, не сохраняется)|
|**Текст интерфейса**|перевод строки (`/admin/config/regional/translate`), `locale_custom_strings_<lang>`|
|**Определения сущностей/полей/bundle**|`hook_entity_type_alter()`, `hook_entity_bundle_info_alter()`, `hook_entity_base_field_info_alter()`, `hook_entity_bundle_field_info_alter()`|
|**Меню/вкладки/действия**|`hook_menu_links_discovered_alter()`, `hook_menu_local_tasks_alter()`, `hook_menu_local_actions_alter()`, `hook_link_alter()`, `hook_entity_operation_alter()`|
|**Права (объявления)**|чужие права из `permissions.yml` не меняют; их выдают/забирают у ролей|
|**Письма**|`hook_mail_alter()`|
|**Ответ/заголовки**|подписчик на `KernelEvents::RESPONSE`|

Порядок выбора: config → alter-хук → событие → декоратор/ServiceProvider → тема → патч.

### 20.11. Нюансы и ловушки (сводка)

**Кеш и обновление определений**

- после `services.yml`, routing, plugin, hook, entity definition — `drush cr`; изменения Twig в dev требуют `twig.config` (debug, auto_reload) или сброса кеша;
- определения плагинов/сущностей/полей кешируются отдельно, `cr` их сбрасывает.

**Конфигурация**

- `config/install` работает только при установке; `config/optional` — если есть зависимости;
- при переносе файлов из `cex` в модуль удаляют `uuid` и `_core`;
- синхронизация меняет только конфигурацию; контент (материалы, термины, меню-ссылки `menu_link_content`, custom blocks) — нет.

**Сущности и поля**

- `status` ≠ `field_status` ≠ moderation state;
- изменение схемы после установки — update hook; иначе «Mismatched definitions»;
- у настраиваемого поля нельзя после появления данных менять тип и часть storage-настроек;
- удаление поля запускает фоновую очистку данных (по cron), не мгновенную.

**Доступ**

- permission ≠ доступ к сущности; route access ≠ entity access;
- `accessCheck(FALSE)` в запросе обходит права — только осознанно;
- `AccessResult::forbidden()` сильнее `allowed()`; `neutral` не разрешает.

**Блоки, формы, темы**

- плагин блока и его размещение — разные объекты; размещение привязано к теме;
- в alter формы добавленное поле нужно самим сохранять в submit;
- Twig-шаблон в теме перекрывает шаблон модуля; сначала включите Twig debug и найдите имя файла.

**Окружения**

- `settings.php` — окружение и секреты, config — общее; overrides не попадают в экспорт;
- `drush cim` без `cst` может удалить объекты; UUID сайта должен совпадать.

**Безопасность и надёжность**

- не хранить секреты в YAML и коде; `getenv()`;
- CSRF для изменяющих маршрутов; `|raw` только для доверенного;
- очереди и cron-логика идемпотентны; batch и update hooks порционные.

> [!question] Вопросы на собеседовании 
> **Как создать тип материала и поле, чтобы они переносились между окружениями?** 
> Создать в админке, выгрузить `drush cex`, положить YAML в `config/install` модуля (убрав `uuid` и `_core`) или переносить через `config/sync`; для существующих сайтов — `cim` или update hook.
> 
> **Чем настраиваемое поле создаётся в коде?** 
> Файлами `field.storage.*`, `field.field.*`, плюс `core.entity_form_display.*` и `core.entity_view_display.*`; без display-файлов поле не видно.
> 
> **Как переопределить сервис?** 
> Декоратор (`decorates`) или `ServiceProvider` с `alter(ContainerBuilder)`.
> 
> **Как поменять права или контроллер чужого маршрута?** 
> `RouteSubscriber::alterRoutes()`.
> 
> **Как заменить класс чужой сущности или её handler?** 
> `hook_entity_type_alter()` (`setClass`, `setHandlerClass`, `setFormClass`).
> 
> **Как заменить реализацию чужого плагина?** 
> `hook_<тип>_info_alter()` (например, `hook_block_alter()`): поменять `class` в определении.
> 
> **Чем отличается плагин блока от размещённого блока?** 
> Плагин — код блока, размещение — конфигурация (`block.block.*`) с темой, регионом и видимостью; размещений у одного плагина может быть много.
> 
> **Почему после изменения routing/services/плагина «ничего не происходит»?** 
> Закешированы определения: нужен `drush cr`.

## Приложение. Базовые темы, на которые опираются блоки

### A. Routing и Controllers

```yaml
drupaljira_timelog.task_view:
  path: '/task/{node}'
  defaults:
    _controller: '\Drupal\drupaljira_timelog\Controller\TaskController::view'
    _title: 'Task'
  requirements:
    _permission: 'access content'
    node: \d+
  options:
    parameters:
      node: { type: entity:node }
```

- `{node}` + `type: entity:node` — параметрический конвертер (upcasting): контроллер получает `NodeInterface`, а не ID;
- `requirements` — `_permission`, `_entity_access`, `_custom_access`, `_csrf_token`, `_role`;
- `methods: [POST]` — ограничение методов;
- контроллер возвращает render array или `Response`, наследует `ControllerBase`, зависимости — `create()`.

### B. Render API, Twig и Theme layer

Вывод строится из render arrays (`#theme`, `#markup`, `#type`, `#cache`, `#attached`); Drupal собирает метаданные кеша (bubbling) и библиотеки. Шаблоны — Twig (`*.html.twig`), переменные готовят в preprocess, темы регистрирует `hook_theme()`. Библиотеки CSS/JS — `*.libraries.yml` и `#attached['library']`. Автоэкранирование Twig — основа защиты от XSS.

### C. Hooks: процедурные и OOP

Хуки — именованные точки расширения (`hook_entity_presave()`, `hook_form_alter()`, `hook_cron()`, `hook_theme()`). Традиционно функции в `.module`; в Drupal 11.1+ OOP-хуки — методы с атрибутом `#[Hook('entity_presave')]` (с DI через конструктор). В `.install`: `hook_install()`, `hook_uninstall()`, `hook_schema()`, `hook_update_N()` (номер, например `10001`, определяет порядок), `hook_post_update_NAME()` (когда доступны все сервисы и сущности). Запуск: `drush updb`.

### D. Views

Конфигурируемый конструктор выборок: поля, фильтры, сортировки, relationships (JOIN), contextual filters, режимы, форматы (таблица, список, JSON через REST export). Views — config entities (YAML), расширяются плагинами и `hook_views_data()` (для собственных сущностей вроде `time_log`). Кешируются по tags и времени.

### E. Content Moderation и Workflows

Модули `workflows` и `content_moderation` добавляют состояния (draft, published) и переходы, учитывают роли и revisions. **Moderation state** хранится отдельно от поля публикации `status` и пользовательского `field_status`: при миграциях и update hooks (`10001`) все три согласуют.

### F. Инструменты

- **Composer**: `composer require drupal/module`, `composer update`, `composer audit`.
- **Drush**: `cr`, `updb`, `cex`/`cim`, `cron`, `queue:run`, `migrate:*`, `watchdog:show`, `sql:cli`, `php:eval`, `uli`.
- **Логи**: `logger.factory` (`$this->getLogger('drupaljira_timelog')->error(...)`), модули `dblog`/`syslog`.
- **Окружение**: DDEV/Lando, `settings.local.php`, `development.services.yml` (отключение кеша для разработки).
