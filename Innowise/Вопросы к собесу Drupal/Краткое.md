# Часть 2. Полная теория

## 1. Multilingual — мультиязычность

### 1.1. Что это такое

Мультиязычность в Drupal позволяет одному сайту работать с несколькими языками. При этом переводиться могут как элементы интерфейса, так и содержимое сайта, отдельные поля и конфигурационные объекты.

Drupal разделяет мультиязычность на несколько механизмов.

|Механизм|Назначение|
|---|---|
|Language|Определяет доступные языки сайта|
|Interface Translation|Перевод системных строк и интерфейса|
|Content Translation|Перевод сущностей и их полей|
|Configuration Translation|Перевод конфигурационных объектов|
|Language Negotiation|Определение языка текущего запроса|

### 1.2. Interface Translation

Отвечает за перевод интерфейса Drupal и модулей: кнопок, системных сообщений, подписей и других строк, зарегистрированных для перевода.

Для перевода используются функции и методы API перевода, например:

```php
$message = $this->t('Welcome to the website');
```

Метод `t()` возвращает перевод строки на текущий язык интерфейса, если перевод доступен.

Важно: переводимые строки должны быть статическими литералами в коде, а не произвольными строками, собранными из пользовательских данных.

### 1.3. Content Translation

Позволяет переводить содержимое, представленное сущностями: например, узлами (`node`), терминами таксономии (`taxonomy_term`) и пользовательскими блоками (`block_content`), если для них включён перевод.

В переводимой сущности Drupal хранит общий идентификатор сущности, а для каждого перевода — соответствующий языковой вариант.

Например, статья может иметь английский и русский переводы. Это не обязательно две независимые статьи: обычно это одна логическая сущность с несколькими переводами.

Переводимость полей настраивается отдельно. Поле с названием статьи можно переводить, а внутренний идентификатор или другое общее значение — оставить одинаковым для всех языков.

Пример получения перевода сущности:

```php
$node = \Drupal\node\Entity\Node::load(1);

if ($node && $node->hasTranslation('ru')) {
  $translated_node = $node->getTranslation('ru');
  $title = $translated_node->label();
}
```

Здесь `hasTranslation()` проверяет наличие перевода, а `getTranslation()` возвращает языковой вариант сущности. Перед получением перевода нужно учитывать, что целевой язык может отсутствовать.

### 1.4. Language Negotiation

Drupal должен определить, какой язык использовать для конкретного запроса. Для этого существует механизм Language Negotiation.

Язык может определяться по:

- URL-префиксу, например `/en/about` или `/ru/about`;
    
- домену, например `example.com` и `example.fr`;
    
- языку, выбранному пользователем;
    
- языку браузера;
    
- другим включённым механизмам определения языка.
    

Если активны несколько методов, Drupal применяет их в заданном порядке.

### 1.5. Конфигурация

Языки сайта и параметры перевода управляются через настройки Drupal. Конфигурационные объекты также могут быть переводимыми.

Например, переводимая конфигурация может содержать название блока, подпись или описание, которые отличаются в зависимости от языка.

Когда применять: когда сайт должен обслуживать пользователей на нескольких языках, поддерживать перевод контента и интерфейса или показывать разные языковые варианты в зависимости от URL и настроек пользователя.

Типичная ошибка: считать, что включение Content Translation автоматически переводит все поля и системные строки. Настройки переводимости полей и интерфейса нужно проверять отдельно.

## 2. REST API

### 2.1. Что такое REST

REST — архитектурный стиль построения взаимодействия между системами через HTTP. В Drupal REST API позволяет внешним приложениям получать и изменять данные сайта, если соответствующие ресурсы и операции настроены и доступны.

REST обычно использует следующие HTTP-методы:

|Метод|Назначение|
|---|---|
|GET|Получение ресурса|
|POST|Создание ресурса или выполнение операции|
|PATCH|Частичное изменение ресурса|
|DELETE|Удаление ресурса|
|PUT|Замена ресурса целиком или создание по известному адресу, если это поддерживает API|

Фактическое поведение определяется контрактом конкретного endpoint. Не следует считать, что любой метод автоматически доступен для каждой сущности Drupal.

### 2.2. Как работает REST в Drupal

REST API в Drupal строится из нескольких частей:

1. Маршрут определяет URL и способ обработки HTTP-запроса.
    
2. REST resource предоставляет конкретную операцию или тип ресурса.
    
3. Serialization преобразует данные между внутренним представлением и форматом обмена.
    
4. Authentication определяет, кто выполняет запрос.
    
5. Authorization и access checks проверяют, разрешена ли операция.
    
6. REST configuration определяет доступные методы, форматы и способы аутентификации для REST-ресурсов.
    

Для работы со стандартными REST-ресурсами обычно используется модуль `rest`, а для сериализации — `serialization`.

### 2.3. Форматы данных

Наиболее распространённый формат обмена — JSON.

Пример ответа:

```
{
  "id": 42,
  "title": "Introduction to Drupal",
  "status": true
}
```

Это условный пример структуры ответа, а не гарантированный формат Drupal entity REST resource. Реальная структура зависит от ресурса, сериализатора и конфигурации полей.

### 2.4. Настройка REST

REST-ресурсы настраиваются через конфигурацию Drupal. Для каждого ресурса определяются поддерживаемые методы, форматы и механизмы аутентификации.

Важно различать:

- REST resource — предоставляет операцию над ресурсом;
    
- route — связывает URL с обработчиком;
    
- serializer — преобразует данные;
    
- authentication provider — устанавливает личность пользователя;
    
- access control — решает, разрешено ли действие.
    

Для стандартных сущностей Drupal нужно отдельно проверять разрешения и доступ к конкретной сущности. Сам факт доступности endpoint не означает, что любой пользователь может получить или изменить любые данные.

### 2.5. REST и JSON:API

В Drupal есть несколько способов предоставлять данные внешним приложениям.

|REST|JSON:API|
|---|---|
|Позволяет настраивать конкретные REST-ресурсы и методы|Предоставляет стандартизированный API для сущностей|
|Требует настройки поддерживаемых ресурсов и операций|Для стандартных entity-операций часто требует меньше ручной настройки|
|Удобен для специализированных операций и интеграций|Удобен для типовых CRUD-операций над сущностями|

JSON:API — отдельный API, а не просто другой формат сериализации REST. В Drupal он реализован отдельным модулем `jsonapi`.

Когда применять: REST подходит для интеграций, когда требуется явно определить доступные ресурсы и операции. JSON:API часто удобнее для headless-приложений, которым нужно читать и изменять сущности Drupal по стандартным правилам.

Типичная ошибка: включить endpoint, но не проверить права доступа, CSRF-защиту для соответствующих способов аутентификации и доступность изменяющих операций.

## 3. Configuration Management

### 3.1. Что такое конфигурация Drupal

Configuration Management — механизм управления настройками сайта и переноса их между окружениями.

Конфигурация описывает, как Drupal должен работать, а контент описывает, какие данные содержит сайт.

Примеры конфигурации:

- типы материалов и поля;
    
- Views;
    
- типы блоков;
    
- настройки ролей и разрешений;
    
- настройки модулей;
    
- форматы текстового ввода;
    
- настройки отображения сущностей.
    

Примеры контента:

- конкретная статья;
    
- пользовательский комментарий;
    
- запись пользователя;
    
- конкретный термин таксономии.
    

Это общее правило, но существуют пограничные случаи: некоторые данные хранятся в конфигурации, хотя визуально напоминают контент.

### 3.2. Где хранится конфигурация

Drupal хранит активную конфигурацию в системе конфигурационного хранилища. В типичном окружении используется база данных.

Для переноса конфигурации между окружениями применяется экспорт в YAML-файлы.

Обычно структура выглядит так:

```php
config/
  sync/
    system.site.yml
    node.type.article.yml
    views.view.content.yml
```

Это пример структуры, а не обязательный путь для каждого проекта. Каталог синхронизации задаётся конфигурацией Drupal.

### 3.3. Export и Import

Основной рабочий процесс:

1. Разработчик изменяет настройки на локальном сайте.
    
2. Экспортирует активную конфигурацию.
    
3. Добавляет YAML-файлы в систему контроля версий.
    
4. Переносит изменения в другое окружение.
    
5. Импортирует конфигурацию.
    
6. Drupal проверяет зависимости и применяет изменения.
    

В Drush обычно используются команды:

```php
drush config:export
drush config:import
```

В зависимости от установленной версии Drush доступны и сокращённые варианты команд.

### 3.4. Configuration entities и simple configuration

Configuration entities — конфигурационные объекты, имеющие структуру сущностей и собственные определения. Примеры: типы материалов, словари таксономии и Views.

Simple configuration — конфигурационные объекты, содержащие произвольную структуру настроек. Пример — некоторые настройки модуля или сайта.

Для работы с простой конфигурацией используется Config API:

```php
$config = \Drupal::config('system.site');
$site_name = $config->get('name');
```

Этот пример показывает чтение конфигурации. В сервисах предпочтительнее получать необходимые зависимости через Dependency Injection, а не обращаться к глобальному контейнеру напрямую.

Для изменения настроек программно используется изменяемая конфигурация:

```php
$config = \Drupal::configFactory()->getEditable('system.site');
$config->set('name', 'Example Site');
$config->save();
```

Программное изменение конфигурации требует осторожности: изменение активной конфигурации на работающем сайте не заменяет полноценный процесс конфигурационного управления.

### 3.5. Конфигурационные зависимости

Один конфигурационный объект может зависеть от других.

Например, отображение поля зависит от существования самого поля и типа сущности. Drupal отслеживает многие такие зависимости и может сообщать об ошибках, если зависимая конфигурация отсутствует.

Когда применять: при разработке модулей, переносе настроек между окружениями, командной работе и автоматизированном развёртывании.

Типичные ошибки:

- хранить настройки окружения, например секреты, в репозитории;
    
- забывать экспортировать конфигурацию после изменений;
    
- переносить конфигурацию без зависимостей;
    
- считать конфигурационный импорт способом переноса контента.
    

## 4. Services and Dependency Injection (DI)

### 4.1. Что такое Service

Service — объект, предоставляющий определённую функциональность, которую можно повторно использовать в разных частях Drupal.

Примеры сервисов Drupal:

- `current_user` — текущий пользователь;
    
- `entity_type.manager` — управление типами сущностей;
    
- `database` — доступ к базе данных;
    
- `logger.factory` — создание логгеров;
    
- `http_client` — HTTP-клиент.
    

Сервисы регистрируются в контейнере зависимостей и могут получать другие сервисы.

### 4.2. Dependency Injection

Dependency Injection — принцип, при котором объект получает необходимые зависимости извне, вместо того чтобы создавать их самостоятельно.

Без DI класс может напрямую обращаться к глобальному контейнеру:

```php
$current_user = \Drupal::currentUser();
```

Такой код работает в подходящем контексте, но создаёт скрытую зависимость от глобального состояния Drupal и усложняет изолированное тестирование.

Предпочтительный подход — передать сервис через конструктор:

```php
use Drupal\Core\Session\AccountProxyInterface;

class GreetingService {

  public function __construct(
    protected AccountProxyInterface $currentUser,
  ) {}

  public function getGreeting(): string {
    return 'Hello, ' . $this->currentUser->getDisplayName();
  }

}
```

В этом примере класс не ищет текущего пользователя самостоятельно. Он получает готовую зависимость.

### 4.3. Регистрация собственного сервиса

В модуле создаётся файл `example.services.yml`:

```php
services:
  example.greeting:
    class: Drupal\example\Service\GreetingService
    arguments: ['@current_user']
```

Drupal создаёт сервис и передаёт ему зависимость `current_user`.

Получение сервиса через контейнер возможно, например, из подходящего интеграционного кода:

```php
$greeting = \Drupal::service('example.greeting');
```

Однако внутри обычного сервиса не стоит использовать глобальный контейнер для получения каждой зависимости. Лучше передавать зависимости через конструктор.

### 4.4. DI в контроллерах и плагинах

Разные типы классов Drupal имеют разные способы создания.

- Контроллеры могут реализовывать `ContainerInjectionInterface` или использовать базовые классы с поддержкой внедрения зависимостей.
    
- Плагины часто используют `ContainerFactoryPluginInterface`, когда им нужны сервисы.
    
- Формы и блоки также имеют собственные механизмы создания объектов и внедрения зависимостей.
    

Не любой класс Drupal автоматически создаётся контейнером. Поэтому способ DI зависит от типа класса и его фабрики.

Когда применять: практически всегда, когда класс использует сервисы Drupal. DI повышает тестируемость, снижает связанность и делает зависимости явными.

Типичная ошибка: передавать в класс весь контейнер вместо нескольких необходимых интерфейсов. Это скрывает реальные зависимости и затрудняет поддержку.

## 5. Drupal Performance & Scalability

### 5.1. Performance и Scalability

Performance — насколько быстро система выполняет отдельную операцию или обрабатывает запрос.

Scalability — способность системы обслуживать растущую нагрузку за счёт ресурсов и архитектурных решений.

Например, страница может загружаться быстро при десяти пользователях, но медленно при десяти тысячах. Это указывает на проблему масштабирования, хотя исходная производительность могла быть приемлемой.

### 5.2. Cache API

Кеширование позволяет повторно использовать результат вычислений или подготовленные данные, чтобы не выполнять дорогие операции при каждом запросе.

В Drupal важно различать три ключевых свойства кеша:

|Свойство|Назначение|
|---|---|
|Cache contexts|Определяют, для каких вариантов запроса кеш действителен|
|Cache tags|Позволяют инвалидировать кеш при изменении зависимых данных|
|Max-age|Определяет максимальное время жизни кешированного результата|

Например, содержимое блока может зависеть от роли пользователя. Тогда кеш должен учитывать соответствующий контекст доступа. Если блок зависит от конкретной статьи, изменение статьи должно приводить к инвалидированию связанных данных через теги.

Пример:

```php
$build['#cache'] = [
  'contexts' => ['user.roles'],
  'tags' => ['node:42'],
  'max-age' => 3600,
];
```

Здесь:

- `user.roles` разделяет варианты кеша по ролям;
    
- `node:42` связывает кеш с конкретной сущностью;
    
- `3600` задаёт максимальный возраст в секундах.
    

Это пример объявления кешируемости. Само по себе наличие тега не гарантирует правильную инвалидизацию, если зависимость не зарегистрирована корректно.

### 5.3. Render Cache, Dynamic Page Cache и Internal Page Cache

В Drupal существуют разные уровни кеширования.

- Render Cache — кеширует результаты рендеринга отдельных элементов.
    
- Dynamic Page Cache — кеширует готовые страницы с учётом контекстов, позволяя обслуживать многие динамические страницы.
    
- Internal Page Cache — кеширует страницы для анонимных пользователей.
    
- Persistent cache bins — хранилища кеша для разных типов данных.
    
- Reverse proxy и CDN — внешние уровни кеширования, которые могут обслуживать запросы без обращения к Drupal.
    

Эти механизмы дополняют друг друга, но не являются взаимозаменяемыми.

### 5.4. База данных

Для производительности важны:

- правильные индексы;
    
- ограничение количества запросов;
    
- отсутствие N+1 queries;
    
- пагинация больших выборок;
    
- оптимизация Views;
    
- измерение медленных запросов.
    

Проблема N+1 возникает, когда приложение делает один запрос для получения списка объектов, а затем выполняет дополнительный запрос для каждого объекта. Для десятков записей это может быть незаметно, но на больших наборах становится дорого.

### 5.5. Масштабирование

Для масштабирования Drupal используют:

- несколько PHP-приложений за балансировщиком нагрузки;
    
- общую базу данных или правильно спроектированную схему работы с БД;
    
- Redis или другое подходящее кеш-хранилище;
    
- CDN и reverse proxy;
    
- фоновые очереди;
    
- мониторинг ошибок, времени ответа и потребления ресурсов.
    

При горизонтальном масштабировании важно учитывать общие файлы, сессии, кеш, блокировки и синхронизацию конфигурации. Простого запуска нескольких копий приложения недостаточно.

Когда применять: при высокой посещаемости, медленных страницах, больших объёмах контента, тяжёлых операциях и росте инфраструктуры.

Типичная ошибка: отключать кеширование ради исправления некорректной страницы. Правильнее найти отсутствующие cache contexts, tags или другие причины неправильной инвалидации.

## 6. Testing — тестирование

### 6.1. Зачем нужны тесты

Тесты проверяют ожидаемое поведение кода и помогают обнаруживать регрессии после изменений.

В Drupal используются несколько видов тестирования.

|Тип|Что проверяет|
|---|---|
|Unit tests|Логику отдельных классов без полноценной загрузки Drupal|
|Kernel tests|Компоненты Drupal с частью ядра, контейнером и необходимой инфраструктурой|
|Functional tests|Поведение сайта через HTTP, маршруты, формы и браузерные сценарии|
|Functional JavaScript tests|Сценарии, для которых требуется выполнение JavaScript в браузере|
|Browser/E2E tests|Полный пользовательский сценарий через реальный браузер и приложение|
|Static analysis|Типы, контракты и потенциальные ошибки без выполнения приложения|

В стандартном Drupal PHPUnit используется для основных типов тестов, а статический анализ может выполняться отдельными инструментами.

### 6.2. Unit tests

Unit test проверяет небольшую часть логики изолированно.

Например, если класс вычисляет итоговую стоимость на основе количества и цены, можно проверить формулу без запуска базы данных и Drupal.

Преимущество — скорость и точная локализация ошибки. Недостаток — тест не доказывает, что класс корректно интегрирован с Drupal.

### 6.3. Kernel tests

Kernel tests подходят для проверки сервисов, Entity API, полей и других компонентов, которым нужна часть инфраструктуры Drupal, но не требуется полный браузерный сценарий.

В зависимости от теста необходимо включить соответствующие модули и настроить схему базы данных.

### 6.4. Functional tests

Функциональные тесты позволяют проверять маршруты, формы, разрешения, ответы и взаимодействие с системой в более полном окружении.

Например, тест может подтвердить, что пользователь с определённой ролью получает доступ к странице, а пользователь без необходимых разрешений — нет.

### 6.5. Принципы хороших тестов

- Один тест должен проверять конкретное ожидаемое поведение.
    
- Тесты должны быть повторяемыми.
    
- Тестовые данные должны создаваться предсказуемо.
    
- Тесты не должны зависеть от порядка выполнения.
    
- Важные сценарии ошибок и отказа в доступе нужно проверять отдельно.
    
- Тест должен падать, если проверяемое поведение нарушено.
    

Когда применять: при разработке модулей, изменении API, работе с доступами, миграциями и интеграциями.

Типичная ошибка: тестировать только успешный сценарий. Для Drupal особенно важно проверять права доступа, кеширование, отсутствие сущностей и некорректный пользовательский ввод.

## 7. Drupal Security

### 7.1. Основные принципы

Безопасность Drupal строится на нескольких независимых механизмах:

- аутентификация пользователя;
    
- авторизация действий;
    
- проверка доступа к сущностям и маршрутам;
    
- защита от CSRF;
    
- безопасная обработка ввода;
    
- безопасный вывод;
    
- управление зависимостями и обновлениями.
    

Authentication отвечает на вопрос «кто пользователь?», а Authorization — «что ему разрешено?».

### 7.2. Permissions и roles

Роль объединяет набор разрешений (`permissions`). Пользователю назначаются роли, а Drupal проверяет соответствующие разрешения при выполнении операций.

Примеры разрешений — просмотр опубликованного контента, редактирование материалов или администрирование определённой функциональности.

Нельзя считать, что проверка наличия сессии автоматически даёт право на действие.

### 7.3. Access checks

Drupal поддерживает проверки доступа на уровне маршрутов, сущностей и операций.

В маршруте можно указать требование к разрешению:

```php
example.admin:
  path: '/admin/example'
  defaults:
    _controller: '\Drupal\example\Controller\ExampleController::content'
  requirements:
    _permission: 'administer site configuration'
```

Такой маршрут доступен только пользователям, которым предоставлено соответствующее разрешение.

Для операций над сущностями нужно учитывать доступ к конкретной сущности и тип операции. Например, право редактировать один материал не обязательно означает право редактировать все материалы.

### 7.4. CSRF

Cross-Site Request Forgery — атака, при которой браузер пользователя пытаются заставить выполнить нежелательное действие на сайте, где пользователь уже аутентифицирован.

Drupal предоставляет механизмы CSRF-защиты для форм и маршрутов. При разработке изменяющих операций нужно использовать подходящую защиту с учётом способа аутентификации и типа endpoint.

GET-запросы не следует использовать для действий, которые изменяют состояние системы.

### 7.5. XSS и безопасный вывод

Cross-Site Scripting возникает, когда недоверенные данные интерпретируются браузером как исполняемый код.

Для защиты необходимо:

- избегать конкатенации пользовательских данных в HTML;
    
- использовать безопасные механизмы рендеринга Drupal;
    
- экранировать вывод в зависимости от контекста;
    
- корректно обрабатывать разрешённый HTML;
    
- не считать входные данные безопасными только потому, что они пришли из базы данных.
    

Например, при выводе текста в Twig следует учитывать автоматическое экранирование и не использовать `|raw` для недоверенного содержимого.

### 7.6. SQL Injection и другие риски

При работе с базой данных нужно использовать Database API и параметризованные запросы, а не собирать SQL из пользовательских строк.

Дополнительно необходимо:

- обновлять Drupal core и contrib-модули;
    
- не хранить секреты в публичном репозитории;
    
- ограничивать доступ к административным функциям;
    
- проверять загружаемые файлы;
    
- валидировать ввод;
    
- учитывать права доступа к связанным сущностям;
    
- не отключать проверки доступа ради удобства разработки.
    

Когда применять: безопасность требуется на каждом уровне приложения, а не только в административной части.

Типичная ошибка: проверять только роль пользователя, но не доступ к конкретной сущности, или полагаться на скрытие кнопки в интерфейсе вместо серверной проверки доступа.

## 8. Multisite — несколько сайтов на одной кодовой базе

### 8.1. Что такое Multisite

Drupal Multisite позволяет обслуживать несколько отдельных сайтов, используя одну кодовую базу Drupal.

У каждого сайта могут быть собственные:

- база данных;
    
- активная конфигурация;
    
- пользователи и контент;
    
- включённые модули и темы;
    
- файловое хранилище.
    

Типичная структура:

```php
web/
  index.php
  sites/
    example.com/
      settings.php
    second.example.com/
      settings.php
```

Это упрощённый пример структуры. Конкретное расположение каталогов зависит от проекта и способа организации окружений.

### 8.2. Как выбирается сайт

Drupal использует механизм определения сайта на основе запрошенного hostname и настроек в каталоге `sites/`.

Файл `settings.php` содержит параметры подключения к базе данных и другие настройки конкретного сайта.

Общая кодовая база означает, что обновление Drupal core может затронуть все сайты, которые используют эту кодовую базу.

### 8.3. Преимущества и недостатки

Преимущества:

- общая кодовая база;
    
- централизованное обновление модулей;
    
- повторное использование общей функциональности.
    

Недостатки:

- обновления могут затронуть все сайты;
    
- появляется необходимость согласовывать зависимости;
    
- ошибки в общем коде могут затронуть несколько сайтов;
    
- требуется аккуратно управлять конфигурацией и окружениями.
    

Multisite не означает автоматическое совместное использование контента. Если сайтам требуется общий контент, это отдельная архитектурная задача.

### 8.4. Когда использовать

Multisite подходит, когда нескольким сайтам действительно полезно иметь общую кодовую базу и согласованный цикл обновления.

Если сайты должны независимо развиваться, использовать разные версии модулей или иметь разные процессы релизов, отдельные установки могут быть удобнее.

Типичная ошибка: выбирать Multisite только потому, что несколько сайтов принадлежат одной организации. Общая кодовая база создаёт и общие риски.

## 9. Events API

### 9.1. Что такое Events API

Events API позволяет одному компоненту Drupal сообщать о произошедшем событии, а другим компонентам — реагировать на него без прямой зависимости от конкретного класса, который это событие вызвал.

Например, один компонент выполняет операцию, после чего публикует событие. Другой компонент подписывается на него и запускает дополнительную логику.

Основные понятия:

- Event — объект, содержащий информацию о произошедшем событии.
    
- Event dispatcher — механизм отправки события подписчикам.
    
- Event subscriber — класс, который подписывается на определённые события.
    
- Event name — идентификатор события.
    

### 9.2. Event Subscriber

В Drupal подписчики обычно реализуют интерфейс `EventSubscriberInterface`.

Пример:

```php
namespace Drupal\example\EventSubscriber;

use Symfony\Component\EventDispatcher\EventSubscriberInterface;
use Symfony\Component\HttpKernel\KernelEvents;
use Symfony\Component\HttpKernel\Event\RequestEvent;

class RequestSubscriber implements EventSubscriberInterface {

  public static function getSubscribedEvents(): array {
    return [
      KernelEvents::REQUEST => ['onRequest', 0],
    ];
  }

  public function onRequest(RequestEvent $event): void {
    // React to the request event.
  }

}
```

Этот класс подписывается на событие `KernelEvents::REQUEST`. Обработчик получает объект события и может анализировать текущий запрос.

Регистрация в `example.services.yml`:

```php
services:
  example.request_subscriber:
    class: Drupal\example\EventSubscriber\RequestSubscriber
    tags:
      - { name: event_subscriber }
```

Тег `event_subscriber` сообщает контейнеру Drupal, что сервис является подписчиком событий.

### 9.3. Приоритеты и распространение событий

Подписчики могут иметь разные приоритеты. Обычно обработчики с более высоким приоритетом вызываются раньше.

Некоторые события допускают изменение данных или остановку дальнейшего распространения. Возможность этого зависит от конкретного события и его класса.

Не каждое событие предназначено для изменения состояния системы. Всегда нужно изучать контракт конкретного события.

### 9.4. Events API и Hooks

|Hooks|Events API|
|---|---|
|Традиционный механизм расширения Drupal|Механизм событийной коммуникации|
|Часто используется для изменения или дополнения поведения Drupal|Позволяет подписчикам реагировать на определённое событие|
|Расширяется через хуки и их реализации|Расширяется через подписчиков и dispatcher|

Оба механизма продолжают использоваться в современном Drupal. Не все хуки имеют соответствующие события, а события не заменяют хуки целиком.

Когда применять: когда нужно реагировать на существующее событие и не связывать обработчик напрямую с вызывающим компонентом.

Типичная ошибка: создавать подписчик на событие, которое не гарантирует нужного момента выполнения, или размещать в подписчике слишком много несвязанной логики.

## 10. Entity API

### 10.1. Что такое Entity

Entity — структурированный объект Drupal, который представляет данные определённого типа.

Например:

- `node` — материал;
    
- `user` — пользователь;
    
- `taxonomy_term` — термин таксономии;
    
- `media` — медиаобъект;
    
- `block_content` — пользовательский блок.
    

Существуют также конфигурационные сущности: например, типы материалов, словари таксономии и некоторые настройки отображения.

### 10.2. Content entities и configuration entities

|Content entities|Configuration entities|
|---|---|
|Представляют контентные или предметные данные|Представляют настраиваемые объекты Drupal|
|Часто содержат пользовательский контент|Обычно определяют структуру и поведение сайта|
|Примеры: Node, User, Media|Примеры: тип материала, View, словарь таксономии|

Это концептуальное разделение. Конкретный тип сущности определяется её реализацией в Drupal.

### 10.3. Entity Type Manager

`entity_type.manager` — центральный сервис для работы с типами сущностей и их хранилищами.

Он позволяет получать storage handler, создавать сущности и загружать существующие объекты.

Пример загрузки:

```php
$storage = \Drupal::entityTypeManager()->getStorage('node');
$node = $storage->load(1);

if ($node) {
  $title = $node->label();
}
```

В обычном сервисе зависимость `entity_type.manager` лучше внедрять через DI.

### 10.4. Создание и сохранение сущности

```php
$node = \Drupal\node\Entity\Node::create([
  'type' => 'article',
  'title' => 'Introduction to Drupal',
  'status' => 1,
]);

$node->save();
```

Пример создаёт опубликованный материал типа `article`. На практике создание зависит от обязательных полей, доступности типа материала и требований бизнес-логики.

Объект сущности предоставляет методы для чтения и изменения полей. `save()` сохраняет изменения через механизм хранения сущностей Drupal.

### 10.5. Entity lifecycle

Типичный жизненный цикл:

1. Создание или загрузка сущности.
    
2. Чтение и изменение полей.
    
3. Выполнение проверок и обработки, предусмотренных механизмом сохранения.
    
4. Сохранение через storage handler.
    
5. Обновление зависимых механизмов, включая кеширование, если это предусмотрено реализацией.
    

Для отдельных типов сущностей могут существовать специфические правила и обработчики.

### 10.6. Access API

Наличие сущности в базе данных не означает, что текущему пользователю разрешено её просматривать или редактировать.

Drupal предоставляет проверки доступа к сущностям и отдельным операциям. При разработке необходимо учитывать права пользователя, состояние публикации и особенности конкретной сущности.

Когда применять: практически в любой работе с контентом Drupal, конфигурационными объектами и типизированными данными.

Типичная ошибка: обращаться к таблицам сущностей напрямую вместо Entity API, игнорируя проверки доступа, поля, переводы и жизненный цикл сущности.

## 11. Plugin API

### 11.1. Что такое Plugin API

Plugin API позволяет Drupal находить, создавать и использовать разные реализации определённой функциональности по общему контракту.

Вместо того чтобы жёстко привязывать систему к одному классу, Drupal может выбирать подходящий плагин по идентификатору и определению.

Примеры плагинов:

- блоки;
    
- форматтеры полей;
    
- виджеты полей;
    
- обработчики Views;
    
- плагины миграций;
    
- плагины действий.
    

### 11.2. Plugin Manager

Plugin Manager отвечает за обнаружение и создание плагинов определённого типа.

Обычно он:

- обнаруживает определения плагинов;
    
- хранит или использует их определения;
    
- предоставляет методы поиска;
    
- создаёт экземпляры плагинов через соответствующую фабрику.
    

Для разных типов плагинов используются разные менеджеры и базовые классы.

### 11.3. Пример Block plugin

```php
namespace Drupal\example\Plugin\Block;

use Drupal\Core\Block\BlockBase;

/**
 * Provides an example block.
 *
 * @Block(
 *   id = "example_message",
 *   admin_label = @Translation("Example message")
 * )
 */
class ExampleMessageBlock extends BlockBase {

  public function build(): array {
    return [
      '#markup' => $this->t('Hello from Drupal'),
    ];
  }

}
```

Этот класс определяет блок с идентификатором `example_message`. Метод `build()` возвращает render array, который Drupal использует для построения вывода.

Это минимальный пример: реальный блок может получать данные через DI, объявлять кешируемость и выполнять дополнительные проверки доступа.

### 11.4. Plugin discovery

Drupal поддерживает несколько способов обнаружения плагинов. Конкретный способ зависит от типа плагина.

В частности, в Drupal используются:

- PHP-атрибуты для типов плагинов, поддерживающих attribute-based discovery;
    
- аннотации в существующих системах плагинов;
    
- другие механизмы определения, предусмотренные конкретным API.
    

Нельзя утверждать, что все плагины Drupal нужно объявлять только через атрибуты или что все старые аннотации уже можно заменить одинаковым способом. Следует проверять требования конкретного Plugin Manager и версии Drupal.

### 11.5. Plugins и Services

Service предоставляет функциональность через контейнер зависимостей. Plugin представляет подключаемую реализацию определённого типа функциональности.

Например, сервис может отправлять HTTP-запросы, а разные плагины могут определять, какие именно HTTP-операции поддерживает система.

Когда применять: когда система должна поддерживать несколько взаимозаменяемых реализаций одной функциональности.

Типичная ошибка: создавать собственную систему плагинов там, где достаточно обычного сервиса, либо помещать бизнес-логику в плагин, который должен отвечать только за конкретную реализацию.

## 12. Batch API, Cron и Queue API

Эти три механизма решают разные задачи: Batch API обрабатывает длительные операции в рамках пользовательского процесса, Cron выполняет периодические задачи, а Queue API позволяет организовывать обработку отложенной работы.

### 12.1. Batch API

Batch API предназначен для выполнения больших операций небольшими порциями.

Например, если необходимо обработать тысячи записей, выполнение всей операции в одном запросе может привести к тайм-ауту. Batch API разбивает работу на последовательные операции и позволяет показывать пользователю прогресс.

Упрощённый пример определения batch:

```php
$batch = [
  'title' => t('Processing items'),
  'operations' => [
    ['\Drupal\example\Batch\ExampleBatch::process', []],
  ],
  'finished' => '\Drupal\example\Batch\ExampleBatch::finished',
];

batch_set($batch);
```

Для реального использования нужно реализовать callback обработки и callback завершения, а также учитывать передачу состояния между итерациями. Обычно обработчик должен завершать ограниченный объём работы за один проход.

### 12.2. Cron API

Cron — механизм периодического выполнения фоновых задач Drupal.

Он используется для:

- очистки временных данных;
    
- выполнения периодических проверок;
    
- обработки задач, запланированных модулями;
    
- других операций, которые не должны выполняться при каждом пользовательском запросе.
    

Модули могут реализовывать обработчики cron. Сам по себе cron не гарантирует выполнение строго в заданную секунду: фактическая периодичность зависит от способа запуска и настроек окружения.

В производственной системе cron обычно запускают через системный планировщик или подходящий механизм инфраструктуры.

### 12.3. Queue API

Queue API позволяет помещать задания в очередь и обрабатывать их отдельно от исходного запроса.

Типичная схема:

1. Создать queue worker.
    
2. Добавить задания в очередь.
    
3. Запустить обработчик очереди.
    
4. Обработать задание.
    
5. Удалить его из очереди после успешной обработки согласно используемому механизму.
    

Пример добавления задания:

```php
$queue = \Drupal::queue('example_tasks');
$queue->createItem([
  'item_id' => 42,
]);
```

Это добавляет элемент в очередь с именем `example_tasks`. Чтобы очередь реально обрабатывалась, нужен соответствующий обработчик и механизм её запуска.

### 12.4. Queue Worker

Queue Worker определяет, как обрабатывать отдельный элемент очереди.

В Drupal для этого используется Plugin API. Обработчик обычно реализует интерфейс `QueueWorkerInterface` или наследуется от подходящего базового класса.

Очередь может использоваться для отправки уведомлений, обработки изображений, синхронизации с внешними системами и других длительных операций.

### 12.5. Сравнение

|Механизм|Основная задача|
|---|---|
|Batch API|Длительная операция, часто инициированная пользователем|
|Cron|Периодический запуск задач|
|Queue API|Отложенная обработка отдельных заданий|
|Queue Worker|Реализация обработки элемента очереди|

Когда применять: Batch — для больших пользовательских операций; Cron — для периодических процессов; Queue — для отложенной, распределённой или повторяемой обработки заданий.

Типичные ошибки: помещать тяжёлую работу в обычный HTTP-запрос, предполагать, что задания очереди выполнятся без запущенного обработчика, или делать обработку неустойчивой к повторным попыткам.

## 13. Migration API

### 13.1. Что такое Migration API

Migration API предназначен для переноса данных из источника в Drupal с возможностью преобразования данных и управления процессом миграции.

Источником могут быть:

- CSV-файл;
    
- другая база данных;
    
- старый сайт;
    
- предыдущая версия Drupal;
    
- внешняя система;
    
- другие источники, для которых существует подходящий source plugin.
    

Миграция обычно состоит из трёх основных этапов: Source → Process → Destination.

### 13.2. Source

Source определяет, откуда поступают данные и как их читать.

Он предоставляет записи в формате, с которым может работать процесс миграции.

Например, источник может вернуть поля `old_title`, `old_status` и `old_author`.

### 13.3. Process

Process описывает преобразование исходных данных в значения, необходимые целевой системе.

Пример:

```php
process:
  title: old_title
  status:
    plugin: static_map
    source: old_status
    map:
      draft: 0
      published: 1
```

В этом примере значение `old_title` переносится в `title`, а статус преобразуется через `static_map`.

Если исходное значение отсутствует в карте, поведение зависит от настроек process plugin. Для реальной миграции необходимо явно определить обработку неизвестных значений.

### 13.4. Destination

Destination определяет, куда будут записаны преобразованные данные.

Примеры назначений:

- `entity:node` — создание или обновление материалов;
    
- `entity:user` — работа с пользователями;
    
- другие доступные destination plugins.
    

Назначение должно соответствовать структуре целевой сущности и требованиям Drupal.

### 13.5. Migration plugins

Migration API использует плагины для источников, преобразований и назначений.

В стандартной экосистеме миграций важную роль играют:

- Migrate API;
    
- Migrate Drupal;
    
- Migrate Plus и другие расширения, если они необходимы для конкретной задачи.
    

Набор доступных плагинов зависит от установленных модулей.

### 13.6. Migration map и повторный запуск

Drupal сохраняет информацию о соответствии исходных идентификаторов целевым сущностям. Это позволяет отслеживать перенесённые записи и выполнять обновления при повторном запуске миграции.

На практике нужно учитывать:

- уникальность идентификаторов источника;
    
- зависимости между миграциями;
    
- обработку удалённых и изменённых данных;
    
- повторяемость миграции;
    
- проверку корректности результата.
    

Например, при миграции материалов, ссылающихся на пользователей, сначала может потребоваться перенести пользователей, чтобы затем корректно установить связи.

Когда применять: при переходе на Drupal, обновлении структуры данных, импорте из внешних систем и регулярной синхронизации данных.

Типичная ошибка: переносить данные без проверки ссылок между сущностями, без карты идентификаторов и без тестового запуска на копии данных.

## 14. Field API

### 14.1. Что такое Field API

Field API позволяет определять поля для сущностей Drupal и управлять их хранением, настройками, отображением и вводом.

Например, материал может содержать поля:

- текст;
    
- число;
    
- дату;
    
- ссылку;
    
- изображение;
    
- ссылку на другую сущность;
    
- список значений.
    

Field API отделяет определение поля от конкретного значения, которое хранится в сущности.

### 14.2. Основные понятия

|Понятие|Назначение|
|---|---|
|Field type|Определяет тип значения и его структуру|
|Field storage|Определяет правила хранения данных поля|
|Field instance / field configuration|Связывает поле с конкретным типом сущности и задаёт его настройки|
|Field widget|Определяет элемент ввода в форме|
|Field formatter|Определяет отображение значения|
|Typed Data API|Предоставляет типизированное представление данных|

В современном Drupal конфигурация полей разделена на storage и field configuration. Это позволяет использовать одно поле в нескольких подходящих контекстах, если его настройки совместимы.

### 14.3. Field type

Field type определяет структуру данных. Например, числовое поле хранит числовое значение, а entity reference — ссылку на другую сущность.

Тип поля определяет не только формат хранения, но и то, какие операции над значением имеют смысл.

### 14.4. Field widget

Widget отвечает за ввод значения пользователем через форму.

Например, ссылка на сущность может вводиться через autocomplete widget, а дата — через соответствующий элемент выбора даты.

Widget не определяет окончательное представление поля на странице просмотра.

### 14.5. Field formatter

Formatter отвечает за отображение сохранённого значения.

Например, поле с датой можно показывать в разных форматах, а ссылку на сущность — выводить в виде ссылки на связанный объект.

Одно поле может иметь разные formatter в разных режимах отображения.

### 14.6. Работа с полями в коде

```php
$node = \Drupal\node\Entity\Node::load(1);

if ($node && $node->hasField('field_summary')) {
  $summary = $node->get('field_summary')->value;
}
```

`hasField()` проверяет наличие поля на сущности, а `get()` возвращает объект поля.

Для многозначного поля нужно учитывать, что оно может содержать несколько элементов. В таком случае нельзя считать, что обращение к первому значению охватывает все данные.

### 14.7. Field API и Entity API

Entity API отвечает за сущность как объект, а Field API — за систему полей, связанных с сущностью.

При этом поля не являются отдельными сущностями в том же смысле, что материалы или пользователи. Поля представлены специализированными определениями, объектами данных и механизмами хранения.

Когда применять: при проектировании структуры данных, создании собственных типов полей, настройке форм ввода и отображения.

Типичная ошибка: путать widget и formatter либо пытаться решить задачу изменения структуры данных исключительно через шаблон отображения.

## 15. Authentication API

### 15.1. Authentication и Authorization

Authentication API отвечает за установление личности пользователя или клиента, выполняющего запрос.

Authorization определяет, разрешено ли этой личности выполнять конкретное действие.

Например, корректная аутентификация через токен подтверждает, кто отправил запрос, но сама по себе не разрешает редактировать все материалы сайта.

### 15.2. Основные способы аутентификации

В Drupal используются разные способы аутентификации в зависимости от типа приложения и архитектуры.

- Session-based authentication — пользователь работает через браузерную сессию.
    
- HTTP Basic authentication — учётные данные передаются в HTTP-заголовке; использовать следует только через HTTPS и при наличии подходящих ограничений.
    
- Token-based authentication — клиент предъявляет токен, который проверяется соответствующим механизмом.
    
- Cookie-based authentication — аутентификация опирается на cookie и связанные механизмы сессии.
    
- OAuth 2.0 / OpenID Connect — могут предоставляться соответствующими модулями или внешними системами.
    

Не все способы включены по умолчанию. Их доступность зависит от модулей, конфигурации и архитектуры интеграции.

### 15.3. Authentication Provider

Authentication provider — компонент, который определяет, может ли запрос быть аутентифицирован определённым способом.

Например, provider может анализировать заголовок запроса, извлекать учётные данные или токен и устанавливать пользователя, от имени которого выполняется запрос.

После установления личности Drupal всё равно должен проверить доступ к запрашиваемому ресурсу.

### 15.4. Аутентификация REST-запросов

Для REST-запроса обычно необходимо определить:

1. Как клиент передаёт учётные данные.
    
2. Как Drupal проверяет их.
    
3. Как устанавливается пользователь.
    
4. Какие разрешения есть у пользователя.
    
5. Разрешена ли операция над конкретной сущностью.
    
6. Требуется ли дополнительная CSRF-защита.
    

В браузерных сценариях с cookie и сессиями CSRF имеет особое значение, поскольку браузер может автоматически прикладывать cookies к запросам. При токенах, передаваемых явно в заголовке, модель угроз отличается, но безопасность всё равно зависит от способа выдачи, хранения и проверки токена.

### 15.5. Authentication API и User API

User API управляет пользователями Drupal: их данными, ролями и другими свойствами.

Authentication API решает другую задачу — устанавливает личность, связанную с текущим запросом.

Поэтому наличие объекта пользователя в базе данных не означает, что любой запрос от его имени уже аутентифицирован.

### 15.6. Безопасность учётных данных

Основные правила:

- использовать HTTPS;
    
- не передавать секреты в URL;
    
- не хранить токены в публичном репозитории;
    
- ограничивать срок жизни и область действия токенов, если механизм это поддерживает;
    
- корректно обрабатывать истечение и отзыв учётных данных;
    
- не путать проверку токена с проверкой разрешений;
    
- избегать самостоятельной реализации криптографических механизмов.
    

Когда применять: при разработке REST-интеграций, мобильных приложений, headless Drupal и систем с внешними клиентами.

Типичная ошибка: считать, что наличие валидного токена даёт полный доступ к API. Токен устанавливает личность, а права и доступ проверяются отдельно.

# Часть 3. Как связаны технологии между собой

Чтобы действительно понимать Drupal, важно видеть не только отдельные API, но и их взаимодействие.

## 1. Entity API + Field API

Entity API управляет сущностями, а Field API определяет, какие поля могут содержать эти сущности.

Например, Entity API загружает материал, а Field API позволяет получить его текстовое поле, дату или ссылку на другую сущность.

## 2. Services + Dependency Injection + Plugin API

Service предоставляет функциональность, DI передаёт необходимые зависимости, а Plugin API позволяет использовать различные реализации определённого типа.

Эти механизмы не конкурируют друг с другом. Они решают разные архитектурные задачи.

## 3. REST API + Authentication API + Security

REST определяет способ взаимодействия по HTTP. Authentication API устанавливает личность клиента. Security-механизмы определяют, можно ли выполнять запрошенную операцию.

Для безопасного endpoint нужны все соответствующие уровни, а не только включённый REST-ресурс.

## 4. Configuration Management + Multisite

Configuration Management переносит настройки между окружениями. Multisite позволяет обслуживать несколько сайтов на одной кодовой базе.

При Multisite конфигурация должна управляться с учётом каждого сайта: общая кодовая база не означает, что все сайты имеют одинаковые активные настройки.

## 5. Migration API + Entity API + Field API

Migration API получает данные из источника и преобразует их. Destination plugin может создавать или обновлять сущности через механизмы Drupal, а Field API предоставляет структуру полей, в которые записываются значения.

## 6. Events API + Services + DI

Event subscriber обычно регистрируется как сервис. Если ему нужны другие сервисы, они передаются через DI. После возникновения события subscriber выполняет необходимую логику.

## 7. Cache API + Entity API + Performance

Entity API предоставляет данные, а Cache API помогает повторно использовать результаты вычислений и рендеринга. Корректные cache contexts, tags и max-age необходимы, чтобы кеш был быстрым и не возвращал неправильные данные.

## 8. Batch API + Cron + Queue API

Batch API предназначен для порционной обработки длительных операций, Cron — для периодического запуска задач, а Queue API — для отложенной обработки заданий. В одной системе они могут использоваться совместно, но не заменяют друг друга.
