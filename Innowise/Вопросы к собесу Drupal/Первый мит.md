Как всё связано (общая картина): Entity Type объявляется в коде (атрибут) и получает handlers (list_builder, form, access, route_provider, views_data). Поля entity задаются через Field API. Формы строятся через Form API. Логика выносится в сервисы, которые приходят через Dependency Injection. Расширяемые куски (блоки, виджеты, форматтеры) — плагины. Настройки сайта живут в Configuration Management, а подключение к БД — в settings.php.

## 1. Переопределение меток и изменение чужих сущностей

### Что это / What it is

Главный принцип Drupal: никогда не править код Core или чужого модуля. Вместо этого используются «точки расширения»: alter-хуки, event subscribers, декораторы сервисов, конфигурация, темизация. Нужно уметь выбрать правильный механизм под задачу.

EN: Never hack Core or contrib. Drupal gives extension points: alter hooks, event subscribers, service decorators, configuration and theming. The skill is picking the right one.

### Как менять label и другие свойства чужой сущности

Определение entity type (то, что объявлено атрибутом #[ContentEntityType] или #[ConfigEntityType]) — это код. Его можно поправить из своего модуля через hook_entity_type_alter(array &$entity_types). В хук приходит массив объектов EntityTypeInterface по id.

Пример:

```php
function mymodule_entity_type_alter(array &$entity_types) {
  $entity_types['node']->setLabel(t('Материал'));
  // можно подменить и класс, и handler:
  // $entity_types['node']->setClass(MyNode::class);
  // $entity_types['node']->setListBuilderClass(MyListBuilder::class);
  // $entity_types['node']->setFormClass('edit', MyNodeForm::class);
}
```

Что можно менять: label, label_collection, класс сущности, handler-классы, form-классы, links, и т.д. Эти данные кешируются, поэтому после изменения нужен drush cr.

hook_entity_bundle_info_alter(array &$bundles) — меняет информацию о bundles (подтипах): label, класс bundle (bundle class), другие метаданные.

php

```php
function mymodule_entity_bundle_info_alter(array &$bundles) {
  $bundles['node']['article']['label'] = t('Новость');
}
```

Важно: у node bundle label на самом деле хранится в config (node.type.article), поэтому «правильно» его менять через UI или config. Alter-хук нужен, когда надо переопределить программно, независимо от конфигурации.

Смежные хуки для полей:

- hook_entity_base_field_info_alter(&$fields, EntityTypeInterface $entity_type) — менять base fields чужой сущности (например, $fields['title']->setLabel(t('Название'))).
- hook_entity_bundle_field_info_alter() — менять поля, привязанные к bundle.
- Метки configurable fields (созданных через Field UI) хранятся в FieldConfig (config), их меняют через UI/config, а не через код.

### Разница: изменение конфигурации vs изменение определения сущности

- Конфигурация (config): данные в YAML/БД, меняются через UI, drush config:set, импорт config. Примеры: label типа материала node.type.article, label поля field.field.node.article.field_x, настройки displays. Переносится между окружениями через config sync.
- Определение сущности (entity definition): код, объявление класса. Меняется только кодом (атрибут, alter-хук). Не экспортируется в YAML. Правило: если значение лежит в config — меняй config; если задано в коде — используй alter-хук.

EN: Config = data you export/import; entity definition = code, altered via hooks.

### Как менять метки форм, действий, ссылок

- Метки и элементы формы: hook_form_alter() и варианты (см. ниже). Например, $form['actions']['submit']['#value'] = t('Сохранить задачу').
- Operations (ссылки Edit/Delete в списках): hook_entity_operation_alter().
- Local tasks (вкладки) и local actions (кнопки «Add ...»): hook_menu_local_tasks_alter(), hook_menu_local_actions_alter(); либо hook_local_tasks_alter() / hook_local_actions_alter() для определений.
- Пункты меню (menu links): hook_menu_links_discovered_alter().
- Отдельные ссылки: hook_link_alter().
- Маршруты (routes): RouteSubscriber на событие маршрутизации, метод alterRoutes(), можно менять title, права, контроллер.
- Простая замена строки интерфейса: перевод (locale), config_translation или $settings['locale_custom_strings_en'] в settings.php.
- Plugin definitions: hook_PLUGIN_TYPE_alter (например, hook_block_alter, hook_field_formatter_info_alter).

### hook_form_alter(), hook_form_BASE_FORM_ID_alter(), hook_form_FORM_ID_alter()

- hook_form_alter(&$form, FormStateInterface $form_state, $form_id) — вызывается для ВСЕХ форм. Использовать, когда логика общая (проверить $form_id внутри).
- hook_form_BASE_FORM_ID_alter() — для семейства форм с общим base form id. Пример: hook_form_node_form_alter() сработает для форм создания/редактирования всех типов node.
- hook_form_FORM_ID_alter() — для одной конкретной формы. Пример: hook_form_node_task_edit_form_alter() — только форма редактирования Task. Это самый точный и предпочтительный вариант. Общие хуки вызываются раньше, конкретные позже (порядок между модулями задаётся весом модулей). Правило выбора: чем уже, тем лучше.

### hook_theme(), preprocess, Twig

- hook_theme() — модуль регистрирует свои theme hooks (render arrays с '#theme' => 'my_hook' и шаблон my-hook.html.twig). Нужен, когда создаёшь собственную разметку.
- hook_preprocess_HOOK(&$variables) — подготовка/изменение переменных перед рендером шаблона, в том числе чужого (hook_preprocess_node, hook_preprocess_block). Подходит, если надо добавить/изменить данные для шаблона, не трогая сам шаблон.
- Переопределение Twig-шаблона: копируешь шаблон в свою тему (templates/), при необходимости называешь по suggestion (node--task--full.html.twig) и правишь разметку. Включить twig debug, чтобы видеть имена подходящих шаблонов.
- hook_theme_suggestions_HOOK_alter() — добавить свои suggestions.
- hook_theme_registry_alter() — изменить регистрацию theme hook (например, подменить шаблон/путь из модуля).

### Как менять чужую функциональность без правки кода

По убыванию «правильности»: 1) конфигурация; 2) alter-хуки; 3) event subscribers; 4) декорирование/подмена сервиса (ServiceProvider::alter() или decorates в services.yml); 5) подмена класса handler/plugin через alter; 6) тема (Twig, preprocess); 7) патч через composer-patches — крайняя мера и только с задокументированной причиной.

### Результат / Outcome

Если нужно изменить подпись поля — смотри, где она хранится: config (FieldConfig) или base field (hook_entity_base_field_info_alter). Название типа сущности — hook_entity_type_alter / bundle info alter / config. Форма — hook_form_FORM_ID_alter. HTML — preprocess + Twig.

EN summary: Don't edit foreign code. Entity definitions are code → hook_entity_type_alter, hook_entity_bundle_info_alter, base-field alter hooks. Field/bundle labels created in UI are config. Forms → hook_form_FORM_ID_alter (most specific wins). Markup → hook_theme, preprocess, Twig overrides.

## 2. Entity Handlers

### Что такое handler и зачем он нужен

Handler (обработчик сущности) — класс, который отвечает за одну «роль» для конкретного entity type: построить список, показать форму, проверить доступ, сгенерировать маршруты, описать данные для Views. Entity type — это декларация; handlers — исполнители. Благодаря handlers логика не лежит в самой сущности, и её можно подменить по частям.

EN: A handler is a class that performs one role for an entity type. The entity type declaration says which class does what.

Handlers объявляются в ключе handlers атрибута entity type. Получить handler можно через EntityTypeManager: getHandler($entity_type_id, 'list_builder'), getListBuilder(), getAccessControlHandler(), getFormObject($entity_type_id, 'edit'), getStorage(), getViewBuilder().

### Основные handlers

- storage — загрузка/сохранение (по умолчанию SqlContentEntityStorage для content, ConfigEntityStorage для config). Также storage_schema.
- list_builder (EntityListBuilder) — построение страницы-списка сущностей: методы buildHeader(), buildRow(EntityInterface $entity), getDefaultOperations(), render(), load().
- form — формы по операциям: default, add, edit, delete. Типичный набор: 'default' => MyEntityForm::class, 'delete' => ContentEntityDeleteForm::class. Базовые классы: ContentEntityForm, EntityForm, ContentEntityDeleteForm.
- access (EntityAccessControlHandler) — проверка доступа: checkAccess(EntityInterface $entity, $operation, AccountInterface $account) и checkCreateAccess(). Возвращает AccessResult (allowed/forbidden/neutral) с кешируемостью. Операции: view, update, delete, create.
- views_data (EntityViewsData) — интеграция с Views: описывает таблицы и поля для Views. Базовый класс сам выводит base fields; для вычисляемых данных расширяется getViewsData().
- route_provider — генерация маршрутов сущности на основе links. Базовые классы: DefaultHtmlRouteProvider, AdminHtmlRouteProvider (маршруты в админ-теме). Строит entity.{type}.canonical, add_form, edit_form, delete_form, collection.
- view_builder (EntityViewBuilder) — рендер сущности в режимах отображения.
- translation — для мультиязычности.

### Как подключить свой handler в #[ContentEntityType]

php

```php
#[ContentEntityType(
  id: 'time_log',
  label: new TranslatableMarkup('Time log'),
  handlers: [
    'list_builder' => TimeLogListBuilder::class,
    'form' => [
      'default' => TimeLogForm::class,
      'delete' => ContentEntityDeleteForm::class,
    ],
    'access' => TimeLogAccessControlHandler::class,
    'views_data' => EntityViewsData::class,
    'route_provider' => ['html' => AdminHtmlRouteProvider::class],
  ],
  base_table: 'time_log',
  admin_permission: 'administer time_log',
  entity_keys: ['id' => 'id', 'label' => 'id', 'uuid' => 'uuid'],
  links: [
    'canonical' => '/admin/content/time-log/{time_log}',
    'collection' => '/admin/content/time-log',
    'add-form' => '/admin/content/time-log/add',
    'edit-form' => '/admin/content/time-log/{time_log}/edit',
    'delete-form' => '/admin/content/time-log/{time_log}/delete',
  ],
)]
```

(пример иллюстративный; имена подставь свои.) Если handler не указан, Drupal использует значение по умолчанию либо функциональность недоступна (например, нет route_provider — нет автоматических маршрутов).

### Как создать класс handler и когда наследоваться от стандартного

Правило: почти всегда наследуйся от стандартного класса (EntityListBuilder, EntityAccessControlHandler, ContentEntityForm), переопредели только нужные методы. Писать с нуля нужно очень редко. Если handler нужны зависимости, реализуй EntityHandlerInterface::createInstance(ContainerInterface $container, EntityTypeInterface $entity_type) — у handlers именно createInstance(), а не create(); в базовых классах (EntityListBuilder) уже есть реализация, которую можно расширить.

### Handler vs сервис vs плагин vs контроллер

- Сервис: один экземпляр на весь контейнер, регистрируется в services.yml, не привязан к entity type.
- Handler: класс, привязанный к конкретному entity type, создаётся entity type manager’ом, получает $entity_type, указывается в определении сущности.
- Плагин: одна из многих взаимозаменяемых реализаций типа, обнаруживается plugin manager’ом по атрибуту/аннотации в каталоге Plugin/.
- Контроллер: класс, привязанный к маршруту (_controller в routing.yml), принимает Request и возвращает render array/Response. Заметка: сам entity type — тоже плагин (обнаруживается через атрибут), а его handlers — отдельные классы.

### Результат / Outcome

Drupal узнаёт, какой класс использовать, читая handlers из определения entity type: EntityTypeManager по id типа и роли возвращает нужный класс и создаёт его.

EN summary: Handlers are per-entity-type role classes (list_builder, form, access, views_data, route_provider, storage, view_builder) declared in the entity type attribute and obtained via EntityTypeManager. Extend core base classes. Don't confuse with services (singletons), plugins (discovered implementations) and controllers (route targets).

## 3. Form API

### Базовые классы

- FormBase — простая форма (абстрактный базовый класс, даёт доступ к config(), messenger(), t(), currentUser() и пр.).
- ConfigFormBase — форма настроек, сохраняющая значения в config. Обязателен метод getEditableConfigNames() (список config names, которые можно править). В submitForm сохраняет значения и вызывает parent::submitForm() для сообщения «Конфигурация сохранена».
- EntityForm / ContentEntityForm — форма сущности: сама строит поля (для content entity из Form Display), в save() сохраняет сущность, имеет actions(). Форма подключается маршрутом: defaults: _form: '\Drupal\mymodule\Form\MyForm' (для сущностей — через handlers form).

### Методы FormInterface

- getFormId(): string — уникальный id формы (используется в hook_form_FORM_ID_alter).
- buildForm(array $form, FormStateInterface $form_state): array — строит render array формы.
- validateForm(array &$form, FormStateInterface $form_state): void — проверка значений.
- submitForm(array &$form, FormStateInterface $form_state): void — обработка после успешной валидации.

### Свойства элементов

- #type: textfield, textarea, number, select, checkbox, checkboxes, radios, entity_autocomplete, date, submit, hidden, container, details, fieldset, и др.
- #title — подпись; #description — подсказка.
- #default_value — значение по умолчанию.
- #required — обязательное поле (Drupal сам проверит и покажет ошибку).
- #options — варианты для select/radios/checkboxes (массив ключ => метка).
- #states — клиентская логика показа/скрытия/блокировки без JS:

php

```php
$form['reason'] = [
  '#type' => 'textfield',
  '#title' => t('Причина'),
  '#states' => [
    'visible' => [':input[name="status"]' => ['value' => 'blocked']],
  ],
];
```

Также полезны: #maxlength, #attributes, #weight, #access, #tree (вложенность значений), #ajax.

### Валидация и submit

- Валидация: $form_state->setErrorByName('hours', t('Часы должны быть больше нуля.')); если есть ошибки — submit не вызывается, форма перерисуется с сообщениями.
- Submit handlers: по умолчанию метод submitForm; можно добавить свои в $form['#submit'][] и на кнопке $form['actions']['submit']['#submit'][]. Аналогично #validate.
- Редирект после submit: $form_state->setRedirect('route.name', ['param' => $id]).
- Для проверки лучше использовать валидацию в validateForm, а не в submitForm.

### Получение и сохранение значений

- $form_state->getValue('field_name'), getValues(), cleanValues() (убирает служебные form_token, form_id, op).
- Для вложенных значений ('#tree' => TRUE) getValue(['group', 'field']).
- Хранение между шагами: $form_state->set()/get() или setStorage(); для многошаговых — $form_state->setRebuild().
- Сохранение: в config через $this->config('mod.settings')->set('key', $value)->save(); в сущность через $entity->set()->save().
- Защита от CSRF встроена (form_token).

### Dependency Injection в формах

Форма — ContainerInjectionInterface (FormBase его уже реализует). Схема:

php

```php
class MyForm extends FormBase {
  public function __construct(protected EntityTypeManagerInterface $entityTypeManager) {}

  public static function create(ContainerInterface $container) {
    return new static($container->get('entity_type.manager'));
  }
}
```

create() вызывается Drupal, достаёт сервисы из контейнера и передаёт в конструктор. Не используй \Drupal::service() внутри форм.

### hook_form_alter и изменение существующих форм

Через hook_form_FORM_ID_alter() добавляешь поля, меняешь метки, прячешь элементы (#access => FALSE), добавляешь свой валидатор/submit:

php

```php
function mymodule_form_node_task_edit_form_alter(&$form, FormStateInterface $form_state) {
  $form['my_note'] = ['#type' => 'textfield', '#title' => t('Заметка')];
  $form['#validate'][] = 'mymodule_task_validate';
  $form['actions']['submit']['#submit'][] = 'mymodule_task_submit';
}
```

Помни: добавленное в форму поле не сохранится само — нужен submit-обработчик, который запишет значение.

### AJAX

- В элементе: '#ajax' => ['callback' => '::updateOptions', 'wrapper' => 'my-wrapper', 'event' => 'change', 'progress' => [...]].
- Целевой контейнер в форме: '#prefix' => '<div id="my-wrapper">', '#suffix' => '</div>' (или '#type' => 'container' с '#attributes' => ['id' => ...]).
- Callback возвращает либо часть render array формы, либо AjaxResponse с командами: ReplaceCommand, HtmlCommand, AppendCommand, InvokeCommand, CssCommand, MessageCommand, RedirectCommand.
- При AJAX форма пересобирается; значения читаются из $form_state->getValue() / getTriggeringElement().
- Используется для зависимых селектов, динамических подсказок и т.д.

### Формы конфигурации и формы сущности

- Config form: ConfigFormBase + getEditableConfigNames() + buildForm (с $config = $this->config('mod.settings')) + submitForm (save).
- Entity form: ContentEntityForm (handlers → form) + route из route_provider. Поля берутся из Form Display, save() сохраняет сущность, $this->entity доступен в форме.

### Результат / Outcome

Умеешь создать форму: класс + маршрут; поля с #type; validateForm; submitForm (сохранение в config или сущность); добавить поле в чужую форму через hook_form_FORM_ID_alter.

EN summary: FormBase for custom forms, ConfigFormBase for settings, EntityForm for entities. Four core methods: getFormId, buildForm, validateForm, submitForm. Use form_state for values/errors/redirect, inject services via create(), alter other forms with hook_form_FORM_ID_alter, use #ajax with AjaxResponse commands for dynamic parts.

## 4. Services и Dependency Injection

### Что такое сервис и Service Container

Сервис — PHP-объект, выполняющий одну задачу (работа с БД, отправка почты, доступ к сущностям, ваша бизнес-логика) и доступный через контейнер по имени. Service Container (Symfony DependencyInjection) — «фабрика и реестр» сервисов: создаёт объекты по определению и подставляет их зависимости. По умолчанию сервис создаётся один раз и переиспользуется (shared).

EN: A service is a reusable object registered in the container by name; the container builds it and wires dependencies; shared by default.

### Как Drupal находит и создаёт сервисы

При сборке контейнера Drupal собирает MODULE.services.yml всех включённых модулей, ядра и ServiceProvider-классов, компилирует контейнер и кеширует. Сервис создаётся лениво — при первом запросе. Изменили services.yml — нужен drush cr, чтобы контейнер пересобрался.

### Собственный сервис в MODULE.services.yml

yaml

```yaml
services:
  mymodule.task_stat:
    class: Drupal\mymodule\Service\TaskStatService
    arguments: ['@entity_type.manager', '@database', '@datetime.time']
  # или с autowire:
  # mymodule.task_stat:
  #   class: Drupal\mymodule\Service\TaskStatService
  #   autowire: true
```

Ключи определения: class, arguments, calls (вызов методов после создания), tags (например event_subscriber, twig.extension), decorates (декорирование чужого сервиса), factory, public, autowire, parent. Имя принято начинать с имени модуля: module.name.

### Constructor injection

Зависимости передаются в конструктор и хранятся в свойствах (promoted properties в PHP 8):

php

```php
class TaskStatService {
  public function __construct(
    protected EntityTypeManagerInterface $entityTypeManager,
    protected Connection $database,
  ) {}
}
```

Преимущества: явные зависимости, легко подменять в тестах, нет глобального состояния.

### Интерфейсы сервисов

Зависимость лучше типизировать интерфейсом (EntityTypeManagerInterface, а не EntityTypeManager). Тогда можно подменить реализацию (декоратор, mock в тестах) без изменения клиентского кода. Свой сервис тоже стоит сопровождать интерфейсом.

### ContainerInterface, create(), фабричное создание

Классы, которые создаёт не контейнер напрямую (формы, контроллеры, плагины, handlers), получают сервисы через статический фабричный метод:

- ContainerInjectionInterface::create(ContainerInterface $container) — контроллеры, формы, блоки-классы без конфигурации.
- ContainerFactoryPluginInterface::create(ContainerInterface $container, array $configuration, $plugin_id, $plugin_definition) — плагины.
- EntityHandlerInterface::createInstance(ContainerInterface $container, EntityTypeInterface $entity_type) — entity handlers. Внутри: return new static($container->get('service.id'), ...). Заметка: в Drupal 11 появляются и OOP hooks с атрибутом #[Hook] и внедрением зависимостей в конструктор.

### Как передавать сервисы

- Контроллер: ControllerBase + create(), сервисы в конструктор.
- Форма: см. раздел 3.
- Плагин: ContainerFactoryPluginInterface.
- Другой сервис: через arguments в services.yml.
- Handler: createInstance().

### \Drupal::service()

Статический доступ к контейнеру. Допустим только там, где DI невозможен: процедурный код (.module, .install, hook-реализации, update hooks), быстрые отладочные вещи. В классах (сервисы, формы, контроллеры, плагины) — не использовать: прячет зависимости и мешает тестам.

### Сервис vs плагин vs обычный класс

- Сервис: один зарегистрированный объект, фиксированная роль, берётся по id.
- Плагин: много реализаций одного типа, выбирается по id/конфигурации, обнаруживается по атрибутам.
- Обычный PHP-класс: создаётся через new (value object, DTO, простая утилита без зависимостей), контейнер не нужен.

### Тестирование

- Unit-тесты (UnitTestCase): зависимости подменяются mock-объектами через конструктор — именно поэтому DI удобен.
- Kernel-тесты: реальный контейнер с подключёнными модулями, можно получить сервис через $this->container->get().
- Functional-тесты: полноценный сайт и браузер.

### Результат / Outcome

Бизнес-логику (например, расчёт статистики по задачам) выносишь в сервис, регистрируешь в services.yml и используешь в контроллере, форме, блоке, Drush-команде — без дублирования.

EN summary: Services are shared objects defined in MODULE.services.yml and built by the Symfony container; use constructor injection and interfaces; classes not built by the container use create()/createInstance(); \Drupal::service() only in procedural code; test with mocks (unit) or the real container (kernel).

## 5. Plugin API

### Что такое плагин и зачем он нужен

Плагин — небольшой класс, реализующий конкретный вариант какого-то типа функциональности (например, блок, форматтер поля, queue worker). Plugin API позволяет модулям добавлять новые реализации без изменения кода ядра: достаточно положить класс в нужный каталог с нужным атрибутом.

EN: Plugins are swappable implementations of a plugin type, discovered automatically by metadata (attribute/annotation) in a known directory.

### Plugin Manager, discovery, definition

- Plugin type = «семейство» (Block, FieldFormatter, QueueWorker, Condition, Action, ...).
- Plugin Manager — сервис (plugin.manager.block и т.п.), расширяет DefaultPluginManager: знает каталог (Plugin/Block), интерфейс, класс атрибута; кеширует определения; создаёт экземпляры createInstance($plugin_id, $configuration).
- Discovery — поиск реализаций: AttributeDiscovery (современный), AnnotatedClassDiscovery (старый), YamlDiscovery (для YAML-плагинов вроде menu links, local tasks), плюс derivatives (производные плагины из одного класса).
- Definition — массив метаданных плагина (id, label, class, provider и т.д.), собранный из атрибута/аннотации. Процесс: manager сканирует Plugin/<Type>/ в namespace’ах модулей → читает атрибуты → строит definitions → по id создаёт экземпляр через фабрику (ContainerFactory для DI).

### Атрибуты плагинов

В современном Drupal (10.x/11) метаданные задаются PHP-атрибутом:

php

```php
#[Block(
  id: 'mymodule_task_stat',
  admin_label: new TranslatableMarkup('Task statistics'),
  category: new TranslatableMarkup('DrupalJira'),
)]
class TaskStatBlock extends BlockBase { ... }
```

Класс атрибута (Drupal\Core\Block\Attribute\Block) расширяет базовый атрибут плагина (Drupal\Component\Plugin\Attribute\Plugin).

### Аннотации vs атрибуты

Раньше использовались докблоки @Block(...) (Doctrine annotations). Сейчас они объявлены устаревшими (deprecated) в пользу атрибутов; в старом коде встретишь аннотации, в новом пиши атрибуты.

### Примеры плагинов

- Block: класс в src/Plugin/Block/, расширяет BlockBase; методы build() (render array), blockForm()/blockSubmit() (настройки), blockAccess(), getCacheTags/Contexts/MaxAge().
- Field Formatter: #[FieldFormatter(id, label, field_types)], расширяет FormatterBase, метод viewElements(FieldItemListInterface $items, $langcode) — как показать значение поля.
- Field Widget: #[FieldWidget], расширяет WidgetBase, метод formElement() — как вводить значение поля.
- Queue Worker: #[QueueWorker(id, title, cron: ['time' => 60])], метод processItem($data) — обработка элементов очереди (в том числе по cron).
- Другие: Field Type, Condition, Action, Views plugins, Migrate plugins, Image effect, Filter, Menu link (YAML), и даже сами entity types.

### Как создать собственный тип плагина и реализацию

Тип плагина:

1. Интерфейс (MyPluginInterface) и базовый класс (MyPluginBase) для общей логики.
2. Класс атрибута (#[MyPlugin(id: ..., label: ...)]), расширяет Drupal\Component\Plugin\Attribute\Plugin.
3. Plugin Manager (расширяет DefaultPluginManager): в конструкторе parent::__construct('Plugin/MyPlugin', $namespaces, $module_handler, MyPluginInterface::class, MyPlugin::class); alterInfo('my_plugin_info'); setCacheBackend($cache_backend, 'my_plugin_plugins').
4. Регистрация менеджера в services.yml (plugin.manager.my_plugin, arguments: ['@container.namespaces', '@cache.discovery', '@module_handler']). Реализация: класс в src/Plugin/MyPlugin/ с атрибутом и реализацией интерфейса. Использование: $manager->getDefinitions(), $manager->createInstance('id', $config).

### Плагин vs сервис vs handler

- Плагин: выбирается из набора вариантов по id (многие реализации одного интерфейса).
- Сервис: единственный экземпляр с фиксированной ролью.
- Handler: класс-исполнитель роли для конкретного entity type, объявляется в определении сущности.

### Результат / Outcome

Плагин нужен, когда у функциональности есть множество взаимозаменяемых вариантов, которые должны подключаться извне (например, разные блоки/форматтеры). Drupal находит реализации через discovery атрибутов в каталоге Plugin/; создаёшь собственный плагин — класс + атрибут в правильном каталоге.

EN summary: Plugin type = manager + interface + attribute class + directory; plugins are discovered by attributes (annotations are legacy), definitions are cached, instances are created via createInstance. Typical plugins: Block, FieldFormatter, FieldWidget, QueueWorker. Difference: service = singleton, handler = per entity type, plugin = one of many selectable implementations.

## 6. Entity API

### Content Entity vs Configuration Entity

- Content Entity: данные сайта в БД (node, user, comment, taxonomy_term, ваш time_log). Есть поля (fields), revisions, translations, валидация, access. Класс расширяет ContentEntityBase.
- Configuration Entity: конфигурация сайта, хранится как config (YAML при экспорте): node_type, view, user_role, taxonomy_vocabulary, field_storage_config. Класс расширяет ConfigEntityBase. Нет полей, переносится через config sync. Критерий: нужно переносить между окружениями как настройку → config entity; создаётся пользователями/процессами как данные → content entity.

### Entity Type, Bundle, экземпляр

- Entity type — «вид» сущностей (node).
- Bundle — подтип внутри entity type (article, page, task); у bundle могут быть свои поля. Если bundle нет, id bundle совпадает с id entity type.
- Entity — конкретный экземпляр (node 5). Bundles часто сами config entities (node_type), указываются через bundle_entity_type.

### Базовые классы и интерфейсы

ContentEntityBase, ConfigEntityBase, EntityInterface, ContentEntityInterface; дополнительные интерфейсы и трейты: EntityChangedInterface (+EntityChangedTrait), EntityOwnerInterface (+EntityOwnerTrait), EntityPublishedInterface (+EntityPublishedTrait), RevisionLogInterface. EntityTypeManagerInterface — главный сервис (entity_type.manager) для доступа к storage, handlers, определениям.

### Создание собственного Content Entity Type

Нужно: 1) класс сущности в src/Entity/ с атрибутом; 2) интерфейс; 3) baseFieldDefinitions(); 4) handlers (list_builder, form, access, route_provider, views_data); 5) permissions (admin_permission или permissions.yml); 6) links и маршруты; 7) при необходимости menu/local actions/tasks. После включения модуля Drupal создаёт таблицы по определению.

### Атрибут #[ContentEntityType] — основные параметры

- id — машинное имя типа.
- label (+ label_collection, label_singular, label_plural, label_count) — человеческие названия.
- handlers — классы-обработчики (см. раздел 2).
- base_table — основная таблица. data_table — для переводимых данных, revision_table / revision_data_table — для ревизий.
- admin_permission — право «администрировать» тип сущности.
- entity_keys — карта ролей полей (см. ниже).
- links — шаблоны URL (canonical, add-form, edit-form, delete-form, collection).
- field_ui_base_route — маршрут страницы настроек bundle, к которому Field UI привязывает вкладки «Manage fields/display». Без него Field UI не появится.
- Также: translatable, bundle_entity_type, bundle_label, show_revision_ui, constraints, common_reference_target, internal.

### Entity keys

Связь «роль → имя поля»: id (первичный ключ), uuid (универсальный идентификатор), label (поле заголовка), langcode (язык), bundle (поле с типом bundle), uid/owner (автор), status/published (опубликовано), revision (id ревизии). Набор зависит от типа сущности. Благодаря keys, код вроде $entity->label() и $entity->id() работает единообразно для любых сущностей.

### Base fields через BaseFieldDefinition

php

```php
public static function baseFieldDefinitions(EntityTypeInterface $entity_type) {
  $fields = parent::baseFieldDefinitions($entity_type);
  $fields['hours'] = BaseFieldDefinition::create('decimal')
    ->setLabel(t('Hours'))
    ->setRequired(TRUE)
    ->setDisplayOptions('form', ['type' => 'number', 'weight' => 0])
    ->setDisplayConfigurable('form', TRUE)
    ->setDisplayConfigurable('view', TRUE);
  $fields['task'] = BaseFieldDefinition::create('entity_reference')
    ->setLabel(t('Task'))
    ->setSetting('target_type', 'node')
    ->setRequired(TRUE);
  return $fields;
}
```

Base fields определены в коде, одинаковы для всех bundles, не экспортируются как config.

### CRUD

- Create: $entity = Node::create([...]) или $storage->create([...]); затем ->save().
- Load: Node::load($id) или $storage->load($id); loadMultiple($ids); loadByProperties([...]).
- Save: $entity->save() — для нового вставляет, для существующего обновляет (isNew()).
- Delete: $entity->delete() или $storage->delete($entities).
- Чтение/запись полей: $entity->get('field')->value, $entity->set('field', $value), $entity->field_x->target_id, ->entity для ссылок.

### Entity Storage, Entity Query, EntityTypeManager

- EntityTypeManager: $manager->getStorage('node'), getDefinition(), getDefinitions(), getAccessControlHandler(), getListBuilder(), getViewBuilder(), getFormObject().
- Storage: загрузка/сохранение/удаление, создаёт запросы.
- Entity Query: $storage->getQuery()->accessCheck(TRUE)->condition('type', 'task')->condition('field_status', 'done')->sort('created', 'DESC')->range(0, 10)->execute() — возвращает массив id. accessCheck() обязателен: TRUE учитывает права текущего пользователя, FALSE — для системных операций. Затем loadMultiple($ids).

### Entity access и permissions

- Доступ проверяется через $entity->access('view|update|delete', $account) и $manager->getAccessControlHandler(...)->createAccess().
- Источники: access handler сущности, hook_entity_access(), hook_ENTITY_TYPE_access(), hook_entity_create_access(); для node ещё node access grants.
- Permissions: permissions.yml (права как данные), permission_callbacks (динамические), admin_permission в атрибуте. Роли получают права через config (user.role.*).
- Результат — объект AccessResult с кешируемостью (cache tags/contexts).

### Entity references и связи

Поле типа entity_reference: настройка target_type, handler (default:node), handler_settings (target_bundles). Значение — target_id; ->entity даёт загруженную сущность. Обратные связи ищутся запросом по полю. Для Project→Task связь реализуется ссылкой с Task на Project (например, field_project).

### Хуки жизненного цикла

hook_entity_presave/insert/update/delete и hook_ENTITY_TYPE_*; методы самого класса: preSave(), postSave(), preDelete(), postDelete(). Валидация — constraints (validate()).

### Определение форм и handlers в Entity Type

Форм и handlers указываются в ключе handlers атрибута (раздел 2), а URL — в links; route_provider строит маршруты по links.

### Как Drupal хранит сущности и поля

SqlContentEntityStorage создаёт таблицы:

- base_table — основная запись (id, uuid, bundle, langcode...), сюда же попадают простые base fields.
- data_table — данные по языкам (если translatable).
- revision_table / revision_data_table — ревизии.
- Для configurable fields — отдельные таблицы entity_type__field_name (и *_revision), столбцы вида field_name_value / field_name_target_id.
- Многозначные base fields — в отдельных таблицах. При изменении определения (новое поле, смена схемы) нужны обновления через update hook и entity definition update manager (например, installFieldStorageDefinition), иначе будет предупреждение «Mismatched entity and/or field definitions».

### Результат / Outcome

Путь: объявление типа (атрибут + base fields + handlers) → установка модуля (создаются таблицы) → create()+save() (запись) → load()/query (чтение) → редактирование через форму/сохранение → проверка доступа (access handler, permissions).

EN summary: Content entities (DB data, fields, revisions) vs config entities (exportable settings). Entity type → bundle → entity. Declare type with #[ContentEntityType] (id, label, handlers, base_table, admin_permission, entity_keys, links, field_ui_base_route), define base fields with BaseFieldDefinition. CRUD via storage; query via entity query with accessCheck; access via handler/permissions; storage uses base/data/revision tables plus per-field tables for configurable fields.

## 7. Field API и Computed Fields

### Base fields и configurable fields

- Base field: определено в коде (baseFieldDefinitions), есть у всех bundles типа сущности, не настраивается через config и Field UI (хотя display можно сделать configurable).
- Configurable field: создаётся через Field UI или config, привязывается к конкретным bundles, экспортируется в YAML.

### BaseFieldDefinition, FieldStorageConfig, FieldConfig

- BaseFieldDefinition — определение base field в коде.
- FieldStorageConfig (field.storage.node.field_x) — «хранилище» configurable field: имя, тип, cardinality, translatable, настройки хранилища (нельзя менять после появления данных, напр. target_type у ссылки).
- FieldConfig (field.field.node.task.field_x) — настройки поля для конкретного bundle: label, description, required, default value, настройки (handler, target_bundles). Одно хранилище может использоваться в нескольких bundles через несколько FieldConfig.

### Field type, Widget, Formatter

- Field type (плагин FieldType): что за данные (string, integer, decimal, entity_reference, text_long, datetime). Класс расширяет FieldItemBase; методы propertyDefinitions(), schema(), isEmpty(), настройки по умолчанию.
- Field widget: как вводить значение (текстовое поле, select, autocomplete).
- Field formatter: как выводить значение (plain text, ссылка, label).

### FieldItemList, FieldItemBase, структура значений

- FieldItemBase — один элемент (одно значение, delta) со свойствами (value, target_id, format, processed...).
- FieldItemList — список элементов поля у конкретной сущности: first(), get($delta), getValue(), setValue(), isEmpty(), ->value (быстрый доступ к первому элементу). $entity->get('field') возвращает FieldItemList. Структура значения: массив элементов; каждый элемент — массив свойств, например [['target_id' => 5], ['target_id' => 7]].

### Cardinality, required, translatable, revisionable

- Cardinality: 1 — одно значение, N — максимум N, -1 (FieldStorageDefinitionInterface::CARDINALITY_UNLIMITED) — без ограничения.
- required: поле обязательно.
- translatable: значения переводятся по языкам.
- revisionable: значения хранятся по ревизиям. Для base field: ->setCardinality(), ->setRequired(), ->setTranslatable(TRUE), ->setRevisionable(TRUE).

### Entity Reference и таксономия

Тип entity_reference: target_type (taxonomy_term, node, user), handler (default:taxonomy_term), handler_settings (target_bundles — словари/типы, auto_create — создавать термины на лету). Термин — content entity, словарь — config entity.

### Form Display и View Display

- Form Display (core.entity_form_display.{type}.{bundle}.{mode}) — какие виджеты и в каком порядке показываются в форме.
- View Display (core.entity_view_display.{type}.{bundle}.{mode}) — форматтеры и порядок при выводе (режимы full, teaser и т.д.). Это config entities, поэтому отображение полей экспортируется. Для base fields нужно setDisplayConfigurable('form'/'view', TRUE) или setDisplayOptions().

### Computed Fields

Вычисляемое поле — поле, значение которого не хранится в БД, а считается при обращении. Реализация (идея):

php

```php
$fields['logged_hours'] = BaseFieldDefinition::create('float')
  ->setLabel(t('Logged hours'))
  ->setComputed(TRUE)
  ->setReadOnly(TRUE)
  ->setClass(LoggedHoursItemList::class)
  ->setDisplayConfigurable('view', TRUE);

class LoggedHoursItemList extends FieldItemList {
  use ComputedItemListTrait;
  protected function computeValue() {
    $value = /* посчитать, например через сервис */ 0;
    $this->list[0] = $this->createItem(0, $value);
  }
}
```

isComputed() — признак на определении поля (FieldDefinition/FieldStorageDefinitionInterface), по которому Drupal понимает, что поле не нужно хранить и создавать для него таблицу. Для чужих сущностей поле добавляют через hook_entity_base_field_info() / hook_entity_bundle_field_info().

### Computed vs обычное сохранённое поле

- Сохранённое: значение записано в БД, участвует в entity query, Views, сортировках, переносится при загрузке без вычислений.
- Вычисляемое: значение считается «на лету», в БД нет, по нему нельзя (просто) искать/сортировать в entity query и Views, не создаёт таблиц, всегда актуально.

### Когда что использовать

- Computed field: значение производное и нужно как поле сущности (отображение, API, вывод в Twig как $entity->logged_hours).
- Сервис: сложная логика, агрегаты по многим сущностям, переиспользование в разных местах, пакетные расчёты, запросы с агрегацией. В проекте DrupalJira для статистики по задачам это ближе к TaskStatService.
- Метод сущности: простое вычисление по уже загруженным данным этой же сущности.
- Обычное поле: значение надо хранить, фильтровать, сортировать, или оно вводится вручную.

### Производительность и кеширование

- Computed value считается лениво при первом обращении к полю, но при выводе списка сущностей может привести к проблеме N+1 запросов.
- Решения: агрегатные запросы в сервисе сразу по всем id, статический кеш внутри сервиса, хранение рассчитанных данных (денормализация) если нужны фильтры/сортировки.
- Кеширование рендера: вывод должен иметь cache tags (например, зависимость от сущностей time_log), cache contexts и max-age, чтобы при изменении источника данных кеш сбрасывался.

### Результат / Outcome

Ты можешь объяснить: как объявляются поля (base vs configurable), как значения хранятся (таблицы, FieldItemList/FieldItem), как управляется отображение (Form/View Display, widgets/formatters) и как сделать вычисляемое значение.

EN summary: Base fields (code) vs configurable fields (config: FieldStorageConfig + FieldConfig). Field type defines data, widget handles input, formatter handles output; FieldItemList holds items for an entity field. Cardinality/required/translatable/revisionable are field properties. Displays are config. Computed fields use setComputed(TRUE) + a FieldItemList with computeValue(); they're not stored, not queryable by default; watch N+1 queries and cache tags.

## 8. Configuration Management

### Активная и экспортируемая конфигурация

- Active configuration: текущая конфигурация сайта, хранится в БД (таблица config).
- Exported configuration: YAML-файлы в каталоге синхронизации (config/sync), под контролем Git. Каталог задаётся $settings['config_sync_directory'] в settings.php. Это два состояния одной и той же конфигурации; export/import переносят между ними.

### YAML и config/sync

Каждая запись config — отдельный файл: system.site.yml, node.type.task.yml, field.storage.node.field_status.yml, core.extension.yml (список включённых модулей), views.view.*.yml и т.д. Имя файла = config name + .yml.

### ConfigFactoryInterface, Config, ImmutableConfig, EditableConfig

- ConfigFactoryInterface (сервис config.factory) — выдаёт объекты config.
- $factory->get('mymodule.settings') — возвращает ImmutableConfig (только чтение, применены overrides, например из settings.php).
- $factory->getEditable('mymodule.settings') — возвращает изменяемый Config без overrides — для записи.
- Методы: get('key'), set('key', $value), save(), clear('key'), delete(), getRawData(), getOriginal().
- В классах с ConfigFormBase/ControllerBase: $this->config('mymodule.settings') (чтение) и $this->configFactory()->getEditable(...) (запись). Запись: $config = $factory->getEditable('mymodule.settings'); $config->set('hours_limit', 8)->save();

### ConfigFormBase и пользовательские настройки

ConfigFormBase: getEditableConfigNames() возвращает ['mymodule.settings']; в buildForm значения берутся из $this->config('mymodule.settings'); в submitForm значения записываются через $this->config('mymodule.settings')->set(...)->save() и вызывается parent::submitForm(). Для корректной работы нужна schema.

### drush config:export / config:import

- drush config:export (cex) — из активной в файлы.
- drush config:import (cim) — из файлов в активную; показывает diff (--preview=diff) и применяет.
- Также: drush config:status (cst) — различия, config:get, config:set, config:delete.
- Типичный деплой: drush updb → drush cim → drush cr (или drush deploy, который выполняет это в правильном порядке).

### Simple configuration vs configuration entities

- Simple config: один объект настроек (mymodule.settings), одна запись, структура описана schema типа config_object. Подходит для общих настроек модуля.
- Config entity: множество однотипных экземпляров (node types, views, роли), имеет класс на основе ConfigEntityBase, id, label, handlers, схему вида mapping. Имя: module.entity_type.id.

### config/install, config/optional, config/schema

- config/install — YAML, который импортируется при установке модуля; все его зависимости должны быть выполнены, иначе установка не пройдёт.
- config/optional — ставится, только если выполнены зависимости (например, view, нужный другому модулю).
- config/schema/MODULE.schema.yml — описание структуры (типы значений) config: нужно для валидации, перевода, корректного экспорта и для тестов со strict schema.

### config_dependencies

Конфигурация хранит в YAML ключ dependencies: config (другая config), module, theme, content. Для config entities зависимости вычисляются автоматически методом calculateDependencies(); enforced — задаются жёстко. Зависит от этого: порядок импорта, запрет удалить модуль/сущность, на которых держится config, автоматическое каскадное удаление.

### Default configuration и overrides

- Default configuration — то, что лежит в config/install и подхватывается при установке модуля. Далее живёт как обычная активная config.
- Overrides: значения, подменяемые в рантайме без сохранения в config: $config['system.site']['name'] = 'Dev site' в settings.php; сервисы ConfigFactoryOverrideInterface (language overrides и др.). Через get() видны, через getEditable() — нет. Для разных окружений есть config_split.

### Update hooks и изменение структуры

Если модуль меняет структуру своей config (новый ключ, переименование, добавление entity), у уже установленных сайтов default config из config/install не обновится сам. Нужен hook_update_N() в .install (например, mymodule_update_10001), где config правится программно; затем новый вариант экспортируется (cex) и коммитится. Версия схемы модуля хранится в системе (key_value), drush updb выполняет недостающие обновления.

### Перенос между окружениями через Git

1. Изменил настройку на dev (UI/код) → 2) drush cex → 3) git add/commit/push config/sync → 4) на целевом окружении git pull → 5) drush updb, drush cim, drush cr. Условие: у сайтов должен совпадать site UUID (system.site), иначе import откажется (работает с клонированной БД).

### Почему config import не для обычного контента

Config import переносит настройки сайта (структуры), но не данные: nodes, users, comments, terms (термины — content, словарь — config), файлы, time_log записи не входят в экспорт. Для контента используют миграции, default_content/Content Sync, дампы БД. При импорте config контент не переносится, а удалённая в config сущность (например, bundle) может потребовать очистки данных.

### Диагностика ошибок импорта и несовпадений

- drush config:status — какие записи различаются (Only in DB / Only in sync dir / Different).
- drush cim --preview=diff — посмотреть diff.
- Частые причины: несовпадающий site UUID; отсутствующие модули (core.extension требует их включить); неудовлетворённые зависимости; нарушение schema; конфликт разных веток Git; забыли updb; config исключена (config_exclude_modules / config_split).
- UI: /admin/config/development/configuration — отчёт и diff; логи — /admin/reports/dblog; ошибки сообщает сам drush.

### Результат / Outcome

Полный цикл: создать настройку (config form → save) → drush cex → YAML в config/sync → commit в Git → на другом окружении git pull → drush cim → настройка применена.

EN summary: Active config lives in DB, exported config in YAML in config/sync. Read with config.factory->get() (immutable, with overrides), write with getEditable()->set()->save(). Simple config vs config entities; config/install, optional, schema; dependencies control order. Use update hooks to migrate structure, config import for settings only (not content), drush cex/cim + Git for environments; diagnose with config:status and diffs.

## 9. Database credentials и settings.php

### Роль settings.php и settings.local.php

- sites/default/settings.php — главный файл настройки сайта на уровне PHP: подключение к БД, hash_salt, путь config sync, trusted hosts, private files path, overrides. Читается на раннем этапе bootstrap.
- settings.local.php — локальные настройки окружения (dev). В конце settings.php обычно есть блок «if (file_exists(.../settings.local.php)) include ...». Файл не коммитится (в .gitignore). Также бывают settings.ddev.php, settings.lando.php и подобные автогенерируемые файлы среды.

### $databases

php

```php
$databases['default']['default'] = [
  'driver' => 'mysql',
  'database' => 'drupaljira',
  'username' => 'db_user',
  'password' => getenv('DB_PASSWORD'),
  'host' => 'db',
  'port' => '3306',
  'prefix' => '',
  'namespace' => 'Drupal\\mysql\\Driver\\Database\\mysql',
  'autoload' => 'core/modules/mysql/src/Driver/Database/mysql/',
];
```

Структура: $databases[ключ][цель]. Ключ 'default' — основная база, цель 'default' — основное подключение, 'replica' — реплика для чтения. Параметры: driver (mysql, pgsql, sqlite), database, username, password, host (или unix_socket), port, prefix, collation, namespace/autoload (для драйвера), init_commands, pdo options.

### Конфигурация подключения vs конфигурация Drupal

- Подключение к БД — настройка среды (PHP, settings.php). Не хранится в БД и не экспортируется.
- Конфигурация Drupal — настройки сайта (config), хранится в БД и экспортируется в YAML. Почему так: Drupal хранит config в БД, а чтобы прочитать config, надо сначала подключиться к БД, поэтому параметры подключения не могут лежать в config (проблема курицы и яйца). Кроме того, у каждого окружения свои credentials.

### Как Drupal выбирает настройки для сайта

Drupal определяет каталог сайта в sites/ по домену/порту/пути (DrupalKernel::findSitePath). Сопоставления можно задать в sites/sites.php; иначе используется sites/default. Внутри выбранного каталога читается его settings.php.

### Multisite

Один код Drupal обслуживает несколько сайтов: sites/site1.example.com/settings.php, sites/site2.example.com/settings.php, у каждого свои БД, файлы, config sync. sites/sites.php связывает домены с каталогами. Drush выбирает сайт через --uri или текущий каталог.

### Переменные окружения и безопасное хранение секретов

Секреты берутся из окружения: getenv('DB_PASSWORD'), $_ENV, .env (читается phpdotenv/сервером, не коммитится), секреты хостинга/CI/Docker/Kubernetes secrets. Так одинаковый settings.php работает на всех окружениях, а значения различаются. Файл settings.php желательно делать read-only (chmod 444) на проде. Не только DB: hash_salt, API ключи, SMTP-пароли.

### Почему пароли нельзя коммитить в Git

История Git хранит всё навсегда и доступна всем с доступом к репозиторию; удаление из последнего коммита не помогает. Утечка credentials = доступ к БД. Решение: .gitignore для settings.local.php и .env, шаблон settings.php без секретов (или settings.php из default.settings.php), секреты в окружении; при утечке — немедленно менять пароль. Config в config/sync публикуется в Git, поэтому секреты не должны попадать в config (используй overrides из settings.php/окружения или модули Key/Encrypt).

### Overrides в settings.php

- $config['system.site']['name'] = '...' — подмена значений config на рантайме (не сохраняется в БД и не попадает в экспорт при cex, если брать getEditable).
- $settings['config_sync_directory'] = '../config/sync';
- $settings['hash_salt'], $settings['trusted_host_patterns'], $settings['file_private_path'], $settings['file_temp_path'] и др.
- $settings['config_exclude_modules'] — исключить модули из синхронизации. Применение: окружение-специфичные значения (отладка, ключи API) без изменения общей config.

### Не путать БД-настройки с YAML-настройками

- settings.php: PHP-массивы $databases, $settings, $config — окружение, секреты, пути. Не в config sync.
- YAML config (config/sync, config/install): настройки сайта и модулей. Переносятся по Git. Правило: если значение разное на каждом окружении или секретное — settings.php (окружение). Если значение общее для сайта — config.

### Проверка подключения и диагностика

- drush status — строка Database: Connected / не подключена и параметры.
- drush sql:cli, drush sql:connect, drush sqlq "SELECT 1".
- /admin/reports/status — отчёт о состоянии (Database connection).
- Если settings.php/БД неверны — открывается install.php. Типичные ошибки MySQL: 1045 Access denied (неверные username/password или права), 1049 Unknown database (БД не создана/неверное имя), 2002 Connection refused / No such file (host/port/сокет, сервис БД не запущен; в Docker/DDEV хост — имя контейнера, например db), «Driver not found» (нет PHP-расширения pdo_mysql, неверный namespace/autoload). Проверяй: логины вручную через клиент mysql, env-переменные, какой settings-файл реально подключился (включается ли settings.local.php), права пользователя БД.

### Результат / Outcome

Drupal берёт параметры подключения из $databases в settings.php выбранного сайта (и подключаемых к нему файлов окружения); на каждом окружении они свои, секреты приходят из окружения, а не из Git; в экспортируемой конфигурации credentials нет, потому что config хранится в БД и публикуется в репозитории, а подключение нужно до чтения config.

EN summary: DB credentials live in $databases in sites/<site>/settings.php (plus settings.local.php/env-specific files), because config is stored in the DB itself and the connection is needed to read it. Secrets come from environment variables, not Git. Site selection uses sites/ directory and sites.php (multisite). Overrides ($config, $settings) change runtime values per environment. Diagnose with drush status, drush sql:cli, and the status report.

## Быстрая шпаргалка выбора механизма / Quick decision guide

- Изменить подпись поля: configurable field → FieldConfig (config/UI); base field → hook_entity_base_field_info_alter.
- Изменить название типа сущности или bundle: hook_entity_type_alter / hook_entity_bundle_info_alter (или config для node type).
- Изменить форму: hook_form_FORM_ID_alter (узко), BASE_FORM_ID (семейство), form_alter (все).
- Изменить HTML: preprocess + Twig override в теме.
- Нужен свой список/форма/доступ/маршруты сущности: entity handler.
- Нужна общая логика: сервис + DI.
- Нужны взаимозаменяемые реализации: плагин.
- Настройка, которую надо переносить между окружениями: config (simple config или config entity).
- Секрет или значение конкретного окружения: settings.php / переменные окружения.
