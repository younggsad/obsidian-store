## 📖 Базовые понятия (глоссарий)

> [!abstract]+ Ядро методологии
> 
> - **Spec Kit** — открытый (open source) тулкит от GitHub для **Spec-Driven Development**: набор CLI (`specify`), шаблонов, скриптов и слэш-команд, которые подключаются к любому ИИ-агенту для программирования (Claude Code, GitHub Copilot, Gemini CLI, Cursor, Codex и др.).
> - **Spec-Driven Development (SDD)** — методология, при которой спецификация становится **исполняемым** артефактом: не просто описанием "для галочки", а документом, из которого агент напрямую генерирует рабочую реализацию. Спецификация определяет "_что_" и "_зачем_" до того, как определяется "_как_".
> - **`specify` CLI** — командная строка, управляющая жизненным циклом Spec Kit-проекта: инициализация, интеграции, расширения, пресеты, воркфлоу, бандлы.
> - **Интент-ориентированный харнесс (intent-driven harness)** — актуальное самоопределение Spec Kit: инструмент, который выходит за рамки просто кода и может направлять агента через весь SDLC или любой бизнес-процесс.
> - **Constitution (конституция проекта)** — файл `constitution.md`, задающий неизменные принципы проекта (архитектурный стиль, стандарты тестирования, требования безопасности). Это "высший закон", с которым сверяется каждая последующая фаза.
> - **Feature (фича)** — единица работы Spec Kit: пронумерованная директория (`001-feature-name`) со своими `spec.md`, `plan.md`, `tasks.md`. Обычно привязана к git-ветке того же имени.

> [!abstract]+ Артефакты SDD-процесса
> 
> - **`spec.md`** — спецификация фичи: пользовательские сценарии, требования, критерии приёмки. Фокус на "что и зачем", без технологий.
> - **`plan.md`** — технический план: архитектура, стек, структура реализации, выведенные из спецификации и конституции.
> - **`tasks.md`** — пошаговый, зависимо-упорядоченный список задач, сгенерированный из `plan.md`, разбитый на фазы.
> - **Checklist ("юнит-тесты для требований")** — сгенерированный чек-лист, проверяющий не код, а саму спецификацию: полноту, ясность, отсутствие противоречий.
> - **Cross-artifact analysis** — сверка согласованности между `spec.md`, `plan.md` и `tasks.md` перед началом реализации.

> [!abstract]+ Расширяемость
> 
> - **Integration (интеграция)** — привязка Spec Kit к конкретному ИИ-агенту (30+ поддерживаемых); задаёт нужные файлы команд и структуру директорий. Активна только одна интеграция на проект одновременно.
> - **Extension (расширение)** — добавляет новые возможности сверх базового SDD-воркфлоу: доменные команды, интеграции с внешними инструментами, quality gates. Несколько расширений могут сосуществовать в проекте.
> - **Preset (пресет)** — переопределяет файлы команд, шаблонов и скриптов **без изменения инструментария** — способ применить организационные стандарты или адаптировать методологию.
> - **Workflow (воркфлоу)** — автоматизация многошаговых SDD-процессов: цепочки команд, промптов, shell-шагов и точек ручной проверки, с условной логикой, циклами и возможностью паузы/возобновления.
> - **Bundle (бандл)** — версионированный, устанавливаемый в один шаг набор из расширений, пресетов и воркфлоу — всё, что нужно команде или роли.
> - **Catalog (каталог)** — источник, откуда `specify` ищет и устанавливает расширения/пресеты (встроенные официальный + community, либо кастомный каталог организации).

## 🧭 Что такое Spec-Driven Development

> [!quote] Определение 
> Spec-Driven Development **переворачивает** традиционный процесс разработки. Десятилетиями код был королём, а спецификации — вспомогательными лесами, которые выбрасывались, как только начиналась "настоящая работа". SDD меняет это: **спецификации становятся исполняемыми**, напрямую порождая рабочую реализацию, а не просто направляя её.

### Ядро философии

- **Intent-driven development** — спецификации определяют "_что_" до того, как определяется "_как_"
- **Rich specification creation** — создание спецификации с использованием guardrails и организационных принципов
- **Multi-step refinement** — многошаговое уточнение вместо one-shot генерации кода по одному промпту
- **Опора на продвинутые способности ИИ** — модель должна уметь интерпретировать спецификацию, а не только генерировать код по ней

> [!tip] Кому это подходит 
> Spec Kit особенно полезен в трёх сценариях: **Greenfield** (разработка с нуля), **Creative exploration** (параллельное исследование разных реализаций/архитектур) и **Iterative enhancement / Brownfield** (модернизация существующей системы, итеративное добавление фич).

### Фазы разработки

|Фаза|Фокус|Ключевые действия|
|---|---|---|
|**0-to-1 Development** ("Greenfield")|Генерация с нуля|Начать с высокоуровневых требований → сгенерировать спецификации → спланировать шаги реализации → построить production-ready приложение|
|**Creative Exploration**|Параллельные реализации|Исследовать разные решения, поддерживать разные стеки и архитектуры, экспериментировать с UX|
|**Iterative Enhancement** ("Brownfield")|Модернизация legacy|Добавлять фичи итеративно, модернизировать устаревшие системы, адаптировать процессы|

### Экспериментальные цели проекта

- **Технологическая независимость** — SDD не привязан к конкретному стеку, языку или фреймворку
- **Enterprise-ограничения** — поддержка mission-critical разработки с организационными ограничениями (облачные провайдеры, дизайн-системы, комплаенс)
- **User-centric разработка** — от vibe-coding до AI-native подходов, для разных пользовательских когорт
- **Творческие и итеративные процессы** — параллельное исследование реализаций, устойчивые воркфлоу для upgrade и модернизации

> [!note] Spec Kit не диктует, как хранить спецификации 
> Spec Kit не предписывает, как команда должна сохранять или изменять `spec.md`, `plan.md` и `tasks.md` после изменения требований — это описано отдельно в концепции **Spec Persistence Models** и руководстве **Evolving Specs in Existing Projects** (для brownfield-проектов).

## ⚙️ Установка и структура проекта

### Установка `specify` CLI

```bash
# Создать новый проект
uvx --from git+https://github.com/github/spec-kit.git specify init <PROJECT_NAME>

# Или инициализировать в текущей директории
uvx --from git+https://github.com/github/spec-kit.git specify init .

# Постоянная установка через pipx
pipx install git+https://github.com/github/spec-kit.git
specify init <PROJECT_NAME>
```

> [!warning] Только официальный источник 
> Единственный официальный пакет Spec Kit публикуется напрямую из репозитория GitHub.

### Команда `specify init`

|Опция|Назначение|
|---|---|
|`--integration <key>`|ИИ-агент для интеграции (`copilot`, `claude`, `gemini` и др.)|
|`--integration-options`|Доп. опции интеграции (например, кастомная директория команд)|
|`--script sh\|ps\|py`|Тип скриптов: bash/zsh, PowerShell или Python|
|`--here`|Инициализация в текущей директории вместо создания новой|
|`--force`|Принудительное слияние/перезапись при инициализации в непустой директории|
|`--ignore-agent-tools`|Пропустить проверку наличия CLI ИИ-агента|
|`--preset <id>`|Установить пресет сразу при инициализации|

```bash
specify init my-project --integration copilot
specify init --here --integration copilot
specify init my-project --integration copilot --script ps
specify init my-project --integration copilot --preset compliance
```

> [!note] Интеграция по умолчанию 
> Если `--integration` не указан: в интерактивном терминале Spec Kit спросит явно, а в неинтерактивных сессиях (CI, пайпах) по умолчанию используется **GitHub Copilot** — если не задать `SPECKIT_INTEGRATION_DEFAULT`.

### Другие базовые команды

```bash
specify check              # проверка наличия нужных CLI-агентов (офлайн)
specify version             # версия CLI, Python, платформа, архитектура
specify version --features  # список поддерживаемых возможностей CLI
```

### Структура проекта после инициализации

```text
my-project/
├── .github/                      # (для интеграции Copilot — свои файлы у каждого агента)
│   └── prompts/
│       ├── specify.prompt.md
│       ├── plan.prompt.md
│       └── tasks.prompt.md
└── .specify/
    ├── memory/
    │   └── constitution.md       # конституция проекта
    ├── scripts/                  # bash (.sh) и/или PowerShell (.ps1) скрипты автоматизации
    ├── specs/
    │   └── 001-feature-name/     # директория конкретной фичи
    │       ├── spec.md
    │       ├── plan.md
    │       └── tasks.md
    ├── templates/                # шаблоны spec/plan/tasks/agent-context
    ├── extensions/                # конфигурация установленных расширений
    └── extension-catalogs.yml     # список подключённых каталогов расширений
```

> [!tip] Определение активной фичи 
> Команды Spec Kit автоматически определяют активную фичу по текущей **git-ветке** (например, `001-feature-name`). Чтобы переключиться между спецификациями, просто переключите ветку. Для нестандартных случаев есть `.specify/feature.json` и переменные `SPECIFY_FEATURE` / `SPECIFY_FEATURE_DIRECTORY`.

> [!warning] Git не входит в базовую поставку 
> Инициализация git-репозитория и работа с ветками управляются отдельным **git-расширением**, которое не устанавливается по умолчанию. Установите его: `specify extension add git`.

### Важные переменные окружения

|Переменная|Назначение|
|---|---|
|`SPECKIT_INTEGRATION_DEFAULT`|Переопределяет интеграцию по умолчанию для `specify init`|
|`SPECIFY_INIT_DIR`|Указывает корень проекта (директорию с `.specify/`) для работы вне её, например в монорепо/CI|
|`SPECIFY_FEATURE_DIRECTORY`|Переопределяет активную директорию фичи внутри проекта|
|`SPECIFY_FEATURE`|Переопределяет определение фичи для проектов без Git|

### Интеграции с агентами

Spec Kit поддерживает **30+ интеграций** — Copilot, Claude Code, Gemini CLI, Codex, Windsurf, Cursor, Forge, Kiro и др. Активна только одна интеграция на проект одновременно, но переключаться между ними можно в любой момент одной командой. Если нужного агента нет в списке — есть универсальная интеграция **`generic`**.

> [!note] Skills-режим 
> Для интеграций, поддерживающих режим скиллов (например, Claude Code, Codex CLI, Kimi Code), можно установить команды как **скиллы** вместо слэш-команд-промптов: `specify init --integration claude --integration-options="--skills"`.

### Работа в монорепозитории

Каждый под-проект монорепо может иметь собственную `.specify/` директорию (свою конституцию и нумерацию фич):

```text
my-monorepo/
├── .git/
├── apps/
│   ├── web/
│   │   └── .specify/     # проект Spec Kit "web"
│   └── api/
│       └── .specify/     # проект Spec Kit "api"
└── packages/
    └── ui/
        └── .specify/     # проект Spec Kit "ui"
```

Команды запускаются из директории соответствующего под-проекта (`cd apps/web`), либо через `SPECIFY_INIT_DIR` для неинтерактивных/CI-сценариев.

## 📜 Constitution (конституция проекта)

> [!quote] Определение 
> Конституция (`.specify/memory/constitution.md`) — **"высший закон"** проекта: неизменные принципы (архитектурный стиль, стандарты тестирования, требования к дизайн-системе, security-требования), с которыми сверяется каждая последующая фаза SDD. Это "живая документация" — агент активно читает её перед каждой задачей, что предотвращает архитектурный дрейф.

### Как создать и редактировать

```text
/speckit.constitution This project follows a "Library-First" approach.
All features must be implemented as standalone libraries first.
We use TDD strictly. We prefer functional programming patterns.
```

Команда создаёт или обновляет конституцию и синхронизирует зависимые от неё шаблоны. Запускается один раз в начале и повторно — при изменении принципов проекта.

### Версионирование

Конституция использует семантическое версионирование (`CONSTITUTION_VERSION`):

- **MAJOR** — обратно несовместимые удаления/переопределения принципов управления
- **MINOR** — добавление новых принципов
- **PATCH** — уточнения формулировок без изменения смысла

Также фиксируются `RATIFICATION_DATE` (дата первого принятия) и `LAST_AMENDED_DATE` (дата последнего изменения).

> [!tip] Практический совет 
> Файл конституции — обычный markdown, ничем не защищённый технически. После генерации стоит вручную просмотреть его и удалить всё, что не соответствует вашему подходу — шаблонная разметка не обязательна к сохранению.

## 🔄 Рабочий процесс — команды speckit

> [!quote] Общий порядок
> 
> text
> 
> ```text
> /speckit.constitution → /speckit.specify → /speckit.clarify → /speckit.checklist → /speckit.plan → /speckit.tasks → /speckit.analyze → /speckit.implement → /speckit.converge
> ```
> 
> Команды рассчитаны на выполнение по порядку, но строго обязателен перед `/speckit.plan` только `/speckit.specify`. `clarify`, `checklist` и `analyze` — это **quality gates**, которые стоит добавлять для всего, что содержит существенную неоднозначность.

> [!note] Разная форма вызова 
> Точный синтаксис зависит от агента: некоторые skills-based агенты используют `$speckit-*` (Codex, ZCode) или `/skill:speckit-*` (Kimi) вместо `/speckit.*`.

### `/speckit.constitution`

Создаёт/обновляет конституцию проекта — см. [[#📜 Constitution (конституция проекта)]].

### `/speckit.specify`

Создаёт или обновляет **спецификацию фичи** из описания на естественном языке. Фокус на **что и зачем** — пользовательском поведении и целях, не на стеке технологий (это относится к `/speckit.plan`).

```text
/speckit.specify Build an application that helps me organize photos into
albums grouped by date, re-orderable by drag-and-drop, with a tile preview.
```

### `/speckit.clarify`

Задаёт до **пяти** целевых вопросов о недоопределённых местах текущей спецификации и вписывает ответы обратно в `spec.md`. Можно запускать многократно, каждый раз фокусируясь на новой области. Опционально принимает область фокуса аргументом.

```text
/speckit.clarify Focus on the task card behavior: status changes, comment limits, and who can be assigned.
```

> [!tip] Зачем уточнять до планирования 
> Уточнение до планирования не даёт проектировать поверх неоднозначности. Если `/speckit.analyze` позже выявит пробелы в требованиях — вернитесь и снова запустите `/speckit.clarify` (или `/speckit.specify`).

### `/speckit.checklist`

Генерирует чек-лист качества фичи — **"юнит-тесты для требований"**. Проверяет не код, а саму спецификацию: полна ли она, ясна, непротиворечива ("определены ли правила drag-and-drop для каждой колонки?", "описано ли поведение при удалении назначенного пользователя?").

```text
/speckit.checklist
/speckit.checklist Focus on the Kanban board interactions and comment permissions.
```

Если чек-лист выявляет пробелы — вернитесь к `/speckit.clarify` или `/speckit.specify`, прежде чем разбивать работу на задачи.

### `/speckit.plan`

Запускает процесс планирования, генерируя проектные артефакты из спецификации. Именно сюда идут технические детали — стек, архитектура, ограничения.

```text
/speckit.plan Use .NET Aspire with Postgres. The frontend is Blazor Server
with drag-and-drop boards and real-time updates. Expose REST APIs for
projects, tasks, and notifications.
```

### `/speckit.tasks`

Генерирует практичный, зависимо-упорядоченный `tasks.md` из проектных артефактов. Задачи организованы по фазам: **Setup** → **Foundational** (блокирующие предпосылки) → **по одной фазе на каждую user story** в порядке приоритета → финальная фаза **Polish** (сквозные вопросы). Тесты генерируются внутри фазы соответствующей user story, а не отдельной фазой; задачи помечаются для параллельного выполнения там, где это возможно.

```text
/speckit.tasks
```

### `/speckit.analyze`

Выполняет **read-only** кросс-артефактный анализ согласованности и качества между `spec.md`, `plan.md` и `tasks.md`: находит конфликты, пробелы, неоднозначности (например, задачу без соответствующего требования или решение в плане, противоречащее спецификации). **Никогда не редактирует файлы** — только выдаёт отчёт и опционально предлагает исправления на ваше усмотрение.

```text
/speckit.analyze
```

> [!warning] Куда возвращаться при найденных проблемах 
> Возвращайтесь к **шагу, которому принадлежит проблема**: `/speckit.specify` или `/speckit.clarify` — для проблем с требованиями, `/speckit.plan` — для проблем дизайна, `/speckit.tasks` — чтобы перегенерировать список задач. Затем повторяйте `/speckit.analyze`, пока отчёт не станет чистым. Можно запустить `/speckit.analyze` повторно уже после реализации как дополнительную проверку.

### `/speckit.implement`

Выполняет задачи из `tasks.md` по фазам в порядке зависимостей, учитывая маркеры параллельности.

```text
/speckit.implement
```

Для больших фич — фазовая реализация, чтобы не перегружать контекст агента:

```text
/speckit.implement Implement only the Setup and Foundational phases:
project scaffolding and the project/task data model with basic CRUD.
Stop before the user-story features.
```

```text
/speckit.implement Now implement the Kanban board user story: drag-and-drop between columns.
```

### `/speckit.converge`

Оценивает кодовую базу на соответствие спецификации, плану и задачам фичи, чтобы убедиться, что ничего не упущено. Работает **только на дозапись (append-only)**: никогда не редактирует и не удаляет код, единственная возможная запись — добавление задач в `tasks.md`. Запускается **после** того, как `/speckit.implement` уже отработал по текущему `tasks.md`.

```text
/speckit.converge
```

Сначала выводит сводку находок по степени серьёзности, затем приходит к одному из двух исходов:

|Исход|Что происходит|
|---|---|
|**✅ Converged**|Пробелов нет. `tasks.md` остаётся неизменным побайтово. Можно переходить к ревью/PR|
|**Tasks appended**|Найдены пробелы — добавлены как новые задачи в раздел Convergence `tasks.md`. Нужно снова запустить `/speckit.implement`, затем `/speckit.converge` — повторять, пока не будет достигнута конвергенция|

## 🧰 Extensions, Presets, Workflows, Bundles

> [!tip] Как это соотносится 
> **Extension** добавляет новое поведение (команды). **Preset** переопределяет существующие файлы (шаблоны/команды/скрипты) без нового поведения. **Workflow** автоматизирует последовательность шагов. **Bundle** упаковывает всё вышеперечисленное вместе для установки в один шаг.

### Extensions (расширения)

Добавляют доменные команды, интеграции с внешними инструментами, quality gates. Несколько расширений могут сосуществовать в проекте.

```bash
specify extension search [query]         # поиск в каталогах
specify extension add <name>             # установка
specify extension remove <name>          # удаление
specify extension list                   # список установленных
specify extension enable/disable <name>  # включить/выключить без удаления
specify extension set-priority <name> <N> # приоритет разрешения конфликтов
```

Пример: встроенное расширение **bug** добавляет трёхшаговый процесс триажа багов (assess → fix → validate), каждый баг отслеживается в своей директории `.specify/bugs/`:

```bash
specify extension add bug
```

Проектная регистрация расширений и хуков хранится в `.specify/extensions.yml`, включая хуки вида `before_implement` / `after_implement`, которые можно привязать к командам расширений.

### Presets (пресеты)

Переопределяют шаблоны команд, файлы шаблонов и скрипты **без изменения инструментария** — способ применить организационные стандарты или адаптировать методологию. Несколько пресетов можно комбинировать с приоритетами.

```bash
specify preset search [query]
specify preset add <preset_id> --priority <N>
specify preset remove <preset_id>
specify preset resolve <name>       # какой файл реально используется
```

Стратегии применения файла: **replace** (первое совпадение в стеке приоритетов побеждает целиком), **prepend/append** (контент пресета до/после контента более низкого приоритета), **wrap** (замена плейсхолдера `{CORE_TEMPLATE}` на контент из более низкого уровня).

**Стек разрешения** (от высшего приоритета к низшему):

1. Project-local overrides — `.specify/templates/overrides/`
2. Installed presets — по приоритету
3. Installed extensions — по приоритету
4. Spec Kit core — `.specify/templates/`

### Workflows (воркфлоу)

Автоматизируют многошаговые SDD-процессы в повторяемые последовательности: цепочки команд, промптов, shell-шагов и человеческих контрольных точек, с условной логикой, циклами, fan-out/fan-in и возможностью поставить на паузу и возобновить с точного места прерывания.

### Bundles (бандлы)

Компонуют существующие расширения, пресеты и воркфлоу в единую версионированную устанавливаемую единицу — не добавляют новое поведение, а курируют стек примитивов (всё, что нужно команде или роли), устанавливая их через собственные механизмы каждого компонента, с фиксацией версий, проверкой конфликтов и отслеживанием происхождения.

### Community-экосистема

На момент написания: **106K+ звёзд на GitHub**, **200+ контрибьюторов**, **30 интеграций**, **105 расширений (60+ авторов)**, **22 пресета**, **4 проекта-"друга"**. Среди альтернативных SDD-процессов сообщества: **AIDE** (7-шаговый жизненный цикл), **Canon** (baseline-driven workflows), **Product Forge** (продукт-менеджерский SDD), **FX→.NET** (миграция .NET Framework), **MAQA** (мультиагентная оркестрация с quality gates).

> [!warning] Ответственность за сторонний контент 
> Мейнтейнеры Spec Kit **не проверяют, не аудируют и не поддерживают** код расширений и пресетов сообщества — их создают и поддерживают независимые авторы. Проверяйте исходный код перед установкой.

## 🏗️ Сквозной пример — Taskify

Полный проход по воркфлоу на примере командной платформы для управления задачами (канбан-доска).

**1. Конституция:**

```text
/speckit.constitution Taskify is a "Security-First" application.
All user inputs must be validated. We use a microservices architecture.
Code must be fully documented.
```

**2. Спецификация:**

```text
/speckit.specify Develop Taskify, a team productivity platform. It should
allow users to create projects, add team members, assign tasks, comment
and move tasks between boards in Kanban style. [...] I want five users
in two different categories, one product manager and four engineers. [...]
```

**3. Уточнение (можно вызывать несколько раз подряд):**

```text
/speckit.clarify I want to clarify the task card details. For each task
in the UI [...] you should be able to change the current status of the
task between the different columns [...]
```

**4. Валидация чек-листом:**

```text
/speckit.checklist
```

**5. Технический план:**

```text
/speckit.plan We are going to generate this using .NET Aspire, using
Postgres as the database. The frontend should use Blazor server with
drag-and-drop task boards, real-time updates. [...]
```

**6. Задачи:**

```text
/speckit.tasks
```

**7. Анализ согласованности перед реализацией:**

```text
/speckit.analyze
```

**8. Реализация:**

```text
/speckit.implement
```

> [!tip] Фазовая реализация для крупных проектов 
> Для больших проектов вроде Taskify реализуйте по фазам (например: Phase 1 — базовая структура проектов/задач, Phase 2 — канбан-функциональность, Phase 3 — комментарии и назначения). Это предотвращает насыщение контекста агента и позволяет валидировать каждый этап отдельно.

### Ключевые принципы (из официального Quick Start)

- **Будьте явными** насчёт того, что вы строите и зачем
- **Не фокусируйтесь на стеке технологий** на этапе спецификации
- **Итерируйте и уточняйте** спецификации до начала реализации
- **Валидируйте** требования и план до того, как начнётся написание кода
- **Дайте агенту разобраться** с деталями реализации самому
