# 1. Введение в AI-Assisted Development

## 1.1. Определение

**AI-Assisted Development** — разработка программного обеспечения, в которой AI-инструменты помогают выполнять инженерные задачи: изучать кодовую базу, писать и изменять код, создавать тесты, искать причины ошибок, читать документацию, собирать прототипы и поддерживать delivery-процесс.

AI в этом подходе — не замена разработчика, а средство ускорения. Разработчик по-прежнему отвечает за понимание требований, архитектурные решения, безопасность, качество и конечный результат.

AI может помогать:

- писать новый код и изменять существующий;
- изучать незнакомые библиотеки и языки;
- исследовать репозиторий;
- отлаживать ошибки;
- создавать тесты и документацию;
- уточнять требования и декомпозировать задачи;
- анализировать CI/CD;
- собирать прототипы и помогать с deployment.

## 1.2. Chatbot и coding agent

**Chatbot** в основном отвечает на сообщения. Пользователь часто сам переносит код и команды между чатом и рабочей средой.

**Coding agent** может исследовать репозиторий, читать файлы, искать определения, редактировать код и запускать команды — если соответствующие инструменты и разрешения доступны.

Общий цикл агента:

1. Получить цель и ограничения.
2. Собрать релевантный контекст.
3. Составить план действий.
4. Выполнить действия с помощью инструментов.
5. Проверить результат тестами и другими проверками.
6. Исправить найденные проблемы.
7. Сообщить, что сделано и что осталось.

Это общая модель, а не гарантия, что любой инструмент всегда выполнит все этапы правильно.

## 1.3. Роль разработчика

Разработчик формулирует задачу, определяет критерии готовности, выбирает подход, предоставляет контекст, контролирует изменения и проверяет результат. Знание программирования остаётся важным: без него трудно отличить правильное решение от убедительно выглядящего ошибочного.

## 1.4. Ограничения AI

Модель может неправильно понять требование, придумать несуществующий API, использовать устаревшие примеры, изменить лишние файлы, пропустить edge cases или заявить об успехе без фактической проверки. Поэтому принцип работы — **делегировать выполнение, но не ответственность**.

Материалы курса описывают инструментарий примерно на июнь 2026 года. Цены, лимиты, модели и функции меняются быстро. Устойчивее всего навыки постановки задач, работы с контекстом, спецификации, декомпозиции и проверки.

# 2. Современные инструменты

## 2.1. Claude Code

**Claude Code** — coding agent от Anthropic для работы с кодовой базой через терминал и интеграции с редакторами и другими workflow. Типичные задачи: исследование проекта, реализация функций, рефакторинг, исправление ошибок, тестирование, работа с Git и анализ изменений.

## 2.2. OpenAI Codex

**Codex** — инструментальная линейка OpenAI для AI-assisted coding. Конкретные возможности зависят от версии и среды. При сравнении важно смотреть не только на модель, но и на доступ к репозиторию, запуск команд, проверку тестов, работу с Git, подтверждение действий, изоляцию и ограничения тарифа.

## 2.3. Google Antigravity

Google Antigravity упоминается в курсе как ещё один вариант AI-assisted development environment. Доступность и набор функций нужно проверять по актуальным материалам продукта.

## 2.4. Как выбирать инструмент

Учитывайте стек, размер репозитория, приватность, стоимость, доступные интеграции, требования команды и качество проверки результата. Не следует считать один инструмент лучшим для всех задач или запоминать текущие цены как постоянные факты.

Работать можно в терминале, через расширение редактора, в отдельной IDE или в удалённой среде. Важно понимать, где агент выполняет команды и к каким данным имеет доступ.

## 2.5. Безопасный старт с агентом

1. Открыть правильный репозиторий и ветку.
2. Проверить состояние Git.
3. Для нетривиальной задачи попросить сначала исследовать проект.
4. Уточнить scope и критерии готовности.
5. Разрешить реализацию.
6. Просмотреть diff.
7. Запустить проверки.
8. Проверить фактическое поведение.

Пример запроса:

```text
Изучи структуру проекта и найди, где реализована авторизация.
Пока не изменяй файлы. Опиши текущий flow, важные зависимости
и тесты, которые покрывают это поведение.
```

# 3. Claude Code: модель работы

Claude Code получает задачу, собирает контекст, использует разрешённые инструменты и сообщает результат. Качество зависит от трёх составляющих: **инструкции, контекста и доступных инструментов/разрешений**.

В незнакомом проекте сначала попросите агента определить стек, структуру, entry points, команды запуска и тестирования, существующие паттерны и связанные файлы. Это снижает риск преждевременных изменений.

Для сложной задачи попросите план с предполагаемыми файлами, изменениями, зависимостями, тестами и рисками. План — это ранняя проверка того, правильно ли агент понял задачу.

Не считайте фразу «готово» доказательством успеха. Проверьте список изменённых файлов, тесты, lint/typecheck/build, runtime-сценарий, ограничения и нежелательные изменения.

Агент может выполнять опасные команды или взаимодействовать с внешними системами. Не выдавайте избыточные разрешения, проверяйте удаление и массовую перезапись, не помещайте секреты в промпты и используйте изолированное окружение для рискованных экспериментов.

Большие задачи лучше делить на этапы, если они затрагивают много файлов, архитектуру, миграции, безопасность или внешние API.

# 4. Prompt Engineering

## 4.1. Определение

**Prompt Engineering** — проектирование инструкций модели, чтобы получить результат, соответствующий задаче. В coding workflows важнее передать цель, контекст, ограничения и способ проверки, чем делать каждый запрос максимально длинным.

## 4.2. Структура промпта

Полезные части для средней или сложной задачи:

- **Task** — что сделать;
- **Context/Input** — контекст, файлы и исходные данные;
- **Requirements** — обязательное поведение;
- **Constraints/Rules** — ограничения;
- **Output format** — формат результата;
- **Definition of Done** — как проверить завершённость.

Пример:

```xml
<task>Добавить отображение количества элементов в списке.</task>
<context>Использовать существующий компонент и систему стилей.</context>
<requirements>
- Показывать актуальное количество.
- Корректно обрабатывать пустой список.
- Сохранять адаптивность.
</requirements>
<rules>
- Не добавлять библиотеку без необходимости.
- Не менять несвязанные компоненты.
</rules>
<definition_of_done>
- Добавлены или обновлены тесты.
- Тесты проходят.
- Изменения кратко объяснены.
</definition_of_done>
```

XML-теги — лишь способ визуально разделить части. Можно использовать Markdown или обычный текст.

## 4.3. Инструкции и данные

Текст документа, лога или страницы может содержать фразы, похожие на инструкции. Агент должен анализировать их как данные, а не автоматически выполнять. Для недоверенного содержимого полезно явно указать, что его нельзя считать источником команд.

## 4.4. Definition of Done

«Сделай качественно» — слабый критерий. Более проверяемый вариант: «Добавь тесты на успешный и отказной сценарии; оба должны проходить». Для маленькой правки достаточно короткого промпта. Структура должна соответствовать сложности и риску задачи.

# 5. Meta Prompting и context-aware prompt enhancement

**Meta prompting** — использование AI для создания, уточнения или улучшения другого промпта.

```text
Краткая идея → prompt enhancer → уточнённый промпт
→ проверка разработчиком → coding agent → тесты
```

Краткий запрос обычно описывает желаемый результат, но не говорит, где находится код, какие интерфейсы уже существуют и какие тесты нужно обновить. Meta prompting помогает добавить конкретику.

**Context-aware prompt enhancement** использует знания о конкретном репозитории. Система может индексировать workspace, находить релевантные файлы, компоненты и соглашения и на этой основе формировать проектно-ориентированную инструкцию. Это отличается от обычного enhancer, который улучшает формулировку по общим правилам.

Пример исходного запроса: «Добавь отображение расхода токенов». Уточнённый промпт может определить интерфейс, где доступны данные, какие файлы отвечают за отображение, как различаются input/output tokens и какие тесты нужно изменить.

Не принимайте такой промпт автоматически: проверьте выбранные файлы, scope, требования, архитектурные предположения и ограничения. Качество retrieval может быть недостаточным.

**One-shot coding** — попытка выполнить задачу за один достаточно полный запрос. Хороший контекст повышает шанс удачной первой реализации, но не отменяет тестирования и отладки.

В материалах курса упоминаются готовые meta-prompts и репозиторий `snarktank/ai-dev-tasks`, включая шаблон наподобие `create-prd.md`. Общая идея: описание идеи → генерация PRD → проверка требований → декомпозиция → выполнение задач. Точные файлы и команды зависят от версии инструмента.

# 6. Context Engineering

## 6.1. Определение

**Context Engineering** — управление информацией, доступной модели для выполнения задачи: какие инструкции, файлы, примеры, требования, результаты команд и инструменты предоставить и когда.

Prompt Engineering фокусируется на формулировке запроса; Context Engineering охватывает более широкую систему подготовки контекста.

## 6.2. Почему больше не всегда лучше

Большой объём нерелевантных файлов расходует context window, может повышать стоимость и задержки, затрудняет выделение важных требований и увеличивает шум. Цель — дать релевантную информацию в нужный момент, а не передать всё подряд.

## 6.3. Практики

1. Кратко описать проект и задачу.
2. Найти связанные реализации и тесты.
3. Передать актуальные требования и ограничения.
4. Не вставлять целый репозиторий без необходимости.
5. Использовать поиск, индексацию или retrieval, если они доступны.
6. Поддерживать проектные инструкции актуальными.
7. Разделять большие задачи на этапы.
8. Проверять предположения агента.
9. Убирать устаревшие и противоречивые сведения.

## 6.4. Файлы инструкций

В Claude Code часто используется `CLAUDE.md`; другие инструменты могут использовать собственные файлы. В них полезно хранить обзор архитектуры, команды запуска и тестов, conventions, ограничения, важные директории и требования к отчёту.

Пример:

```markdown
# Project instructions
## Overview
Краткое описание архитектуры.
## Development commands
- Запуск: ...
- Тесты: ...
- Линтер: ...
## Code conventions
- Следовать существующим паттернам.
- Не добавлять зависимости без причины.
## Verification
- Запускать релевантные тесты.
- Указывать непроверенные сценарии.
```

Инструкции должны быть короткими и применимыми. Слишком длинный файл сам становится источником шума.

## 6.5. RAG и индексирование

**RAG (Retrieval-Augmented Generation)** — сначала извлечь релевантную информацию из внешнего источника, затем передать её модели для ответа или реализации. В кодовой базе поиск может использовать текст, символы, связи файлов, embeddings или семантическое сходство.

```text
Запрос → поиск фрагментов → сбор контекста → модель → результат
```

RAG не гарантирует, что найдёт правильные файлы. Нужно проверять, на каких данных основано решение.

## 6.6. Context window, caching и сессии

**Context window** — объём токенов, учитываемых моделью в конкретном запросе или сессии. История, инструкции, файлы и результаты инструментов могут занимать значительную часть окна.

Некоторые платформы поддерживают **context caching**, которое может сделать повторное использование стабильного контекста эффективнее. Точные условия зависят от продукта и тарифа.

Статусная строка (statusline), если инструмент её поддерживает, может показывать модель, состояние и использование контекста. Это помогает заметить, когда сессия стала слишком длинной.

Для большой задачи удобно выделять отдельные сессии под исследование, планирование, реализацию и review. При переходе передавайте короткое резюме: цель, изменения, важные файлы, принятые решения, команды проверок и оставшиеся проблемы.

## 6.7. Актуальные знания

Встроенные знания модели могут не соответствовать текущим версиям библиотек. Для быстро меняющихся API используйте официальную документацию и проверенные источники. Не следует полагаться исключительно на training data модели.

# 7. Model Context Protocol (MCP)

## 7.1. Определение

**Model Context Protocol (MCP)** — протокол стандартизированного взаимодействия AI-приложений с внешними инструментами и источниками данных. MCP-сервер может предоставлять tools, resources и другие возможности, доступные клиентскому приложению.

Упрощённо:

- **Host/client** — приложение с AI-агентом, подключающееся к серверу;
- **MCP server** — компонент, предоставляющий инструменты или данные;
- **Tools** — операции, которые агент может вызывать;
- **Resources/context** — доступные сведения, если сервер их поддерживает.

MCP стандартизирует взаимодействие, но не гарантирует безопасность сервера или правильность его действий.

## 7.2. Примеры

В материалах курса упоминаются GitHub MCP, Microsoft Playwright MCP, Context7, Figma и Supabase. Применение зависит от реализации и выданных разрешений.

**Context7** может помогать получать актуальную документацию. Типовой процесс: определить библиотеку, найти её документацию, извлечь текущие API-примеры и использовать их при реализации. Это снижает риск устаревших рекомендаций, но результат всё равно нужно проверять.

## 7.3. Безопасность MCP

Проверьте происхождение сервера, набор доступных действий, права на чтение/запись, работу с credentials и возможность ограничить доступ. Предпочтительны официальные или одобренные организацией серверы, если они подходят задаче.

Риски: чрезмерные разрешения, утечка секретов, нежелательные внешние действия, недоверенный сервер и prompt injection в получаемом содержимом.

Используйте минимальные привилегии, ограниченный набор серверов, отдельные credentials с минимальными правами, подтверждение опасных действий и аудит, где он доступен.

## 7.4. Почему не подключать всё подряд

Множество серверов может расходовать контекст, усложнять настройку и увеличивать поверхность атаки. Это не означает, что MCP устарел: он полезен там, где интеграция действительно улучшает workflow. Подключайте серверы осознанно.

# 8. Spec-Driven Development

**Spec-Driven Development (SDD)** — подход, в котором спецификация становится центральным артефактом разработки и направляет проектирование, декомпозицию, реализацию и проверку.

Обычная упрощённая схема:

```text
Идея → Код → Тесты → Документация
```

SDD:

```text
Intent → Specification → Plan → Tasks → Implementation → Verification
```

AI может правильно реализовать неправильно понятое требование. Например, запрос «добавь голосование» не уточняет, можно ли выбирать несколько вариантов, менять голос, голосовать повторно или голосовать после завершения. Спецификация превращает это в проверяемое поведение.

Основные артефакты:

| Артефакт | На какой вопрос отвечает |
|---|---|
| Constitution | Какие постоянные правила действуют? |
| Specification | Что и зачем строим? |
| Clarifications | Что было неоднозначно? |
| Plan | Как реализовать технически? |
| Tasks | Какие конкретные действия выполнить? |
| Verification | Как проверить правильность результата? |

Преимущества SDD: меньше неоднозначности, проще обнаружить пробелы, легче согласовать scope и проверить результат, проще передавать работу людям и агентам.

Ограничения: плохая спецификация формализует плохую идею; требования могут измениться; процесс требует времени. Для маленькой правки полный SDD-процесс может быть избыточным.

# 9. GitHub Spec Kit

**GitHub Spec Kit** — набор инструментов, шаблонов и команд для организации Spec-Driven Development с AI coding agents. Это не framework приложения вроде React. Он организует процесс через связанные артефакты и проверки.

Концептуальная последовательность:

```text
Constitution → Specify → Clarify → Plan → Tasks
→ Analyze / Checklists → Implement → Tests / Review
```

Точные команды зависят от версии Spec Kit и выбранного агента; сверяйте их с актуальной документацией.

Обычный промпт просит «реализовать функцию». Spec Kit помогает сначала зафиксировать требования, затем план, конкретные задачи и критерии проверки. Он особенно полезен для больших функций, командной работы, повторяемости и задач с большим количеством edge cases.

# 10. Установка Spec Kit

Команды установки меняются, поэтому используйте официальный Quick Start. Общая схема:

1. Подготовить репозиторий и окружение.
2. Проверить runtime-инструменты, которые требует текущая версия.
3. Установить или запустить CLI по официальной инструкции.
4. Инициализировать Spec Kit в проекте.
5. Выбрать поддерживаемого coding agent.
6. Проверить созданные шаблоны и команды.
7. Адаптировать правила под реальный проект.
8. Проверить workflow на небольшой задаче.

**Greenfield** — проект с нуля; правила и архитектуру можно определить заранее.

**Brownfield** — существующий проект; нужно учитывать архитектуру, conventions, зависимости, ограничения и технический долг. До изменений полезно исследовать кодовую базу и не предполагать, что её можно свободно перестроить.

После установки проверьте структуру файлов, интеграцию с агентом, корень репозитория, сохранность существующих инструкций, применимость шаблонов и путь от spec к verification.

# 11. Constitution

**Constitution** — документ с постоянными инженерными принципами и ограничениями проекта. В отличие от spec конкретной функции, constitution задаёт общие правила.

В него могут входить архитектурные принципы, требования к качеству кода и тестам, форматирование, безопасность, доступность, ограничения зависимостей, обратная совместимость и критерии CI.

Пример:

```markdown
# Project Constitution
## Code Quality
- Следовать существующим conventions.
- Избегать ненужных абстракций.
- Не добавлять зависимости без обоснования.
## Testing
- Добавлять тесты для нового поведения.
- Проверять успешные и отказные сценарии.
## Security
- Не хранить секреты в исходниках.
- Проверять авторизацию на серверной стороне.
- Использовать минимальные привилегии.
```

**Interactive**-создание задаёт вопросы и формирует правила через диалог. **Non-interactive** использует заранее заданные параметры или инструкции. Точный синтаксис зависит от версии инструмента.

Для brownfield-проекта сначала изучите реальную архитектуру, команды, соглашения и ограничения. Отделите существующие правила от желаемых улучшений. Constitution не заменяет проверку: если в нём сказано добавлять тесты, нужно убедиться, что тесты действительно появились и проходят.

# 12. Specify, Clarify, Plan, Tasks, Implement

## 12.1. Specify

Цель — описать желаемое поведение и причины, не погружаясь преждевременно в технические детали. Зафиксируйте проблему пользователя, цель, сценарии, функциональные и нефункциональные требования, ограничения и acceptance criteria.

Пример: «Пользователь может сбросить счётчик к нулю. После нажатия Reset отображается 0 независимо от текущего значения».

## 12.2. PRD

**PRD (Product Requirements Document)** — документ продуктовых требований. Типовая структура: проблема, пользователи, цели и метрики, scope/out of scope, пользовательские сценарии, функциональные требования, нефункциональные требования, ограничения, зависимости, критерии приёмки и открытые вопросы.

PRD объясняет, что и зачем нужно продукту. Технические детали обычно раскрываются на этапе Plan.

## 12.3. Clarify

Нужно устранить неоднозначности: что происходит при пустом вводе, какие роли имеют доступ, можно ли повторить операцию, как обрабатывается ошибка, каковы правила для дубликатов и что происходит с существующими данными.

Не заполняйте важные пробелы догадками. Если неоднозначность влияет на безопасность, архитектуру или пользовательское поведение, её нужно уточнить.

## 12.4. Plan

Plan описывает технический подход в конкретной кодовой базе: модули и файлы, интерфейсы, модель данных, интеграции, обработку ошибок, тестовую стратегию, миграции и риски. План должен основываться на реальном исследовании проекта.

## 12.5. Tasks

Tasks — конкретные действия для выполнения плана. Хорошая задача имеет понятный результат, ограниченный scope, критерии проверки и зависимости, если они важны.

Пример:

```text
1. Добавить функцию расчёта итогового значения.
2. Написать тесты на обычный и граничный случаи.
3. Подключить функцию к UI.
4. Добавить состояние пустого списка.
5. Запустить тесты, lint и typecheck.
```

Проверьте, что все требования покрыты задачами, нет противоречий, дубликатов и пропущенных крайних сценариев.

## 12.6. Implement и Verification

На этапе Implement агент выполняет утверждённые задачи, соблюдает constitution и существующие conventions, добавляет тесты и сообщает о блокерах. После этого выполняются подходящие unit/integration/e2e tests, typecheck, lint, build, ручная проверка и проверка доступа/данных — в зависимости от задачи.

# 13. Post-MVP

**MVP (Minimum Viable Product)** — минимальная версия, позволяющая проверить ключевую гипотезу и дать базовую ценность пользователю. Это не означает, что продукт должен быть некачественным.

После MVP обычно появляются обратная связь, ошибки UX, новые требования, потребности в аналитике, производительности, безопасности и масштабировании.

Workflow post-MVP:

1. Собрать обратную связь и данные.
2. Выбрать проблему или улучшение.
3. Оценить ценность, риски и стоимость.
4. Обновить PRD/spec.
5. Уточнить требования.
6. Подготовить plan и tasks.
7. Реализовать небольшими шагами.
8. Проверить регрессии.
9. Выпустить изменение и оценить эффект.

Не следует постоянно добавлять функции без приоритизации: это раздувает продукт и усложняет поддержку, не обязательно увеличивая ценность.

# 14. Agent Skills

**Agent Skill** — переиспользуемый набор инструкций и материалов для определённого класса задач. Он может содержать условия использования, workflow, входные данные, правила, примеры, ссылки и ожидаемый результат. Формат зависит от платформы.

Skill отличается от разового промпта тем, что сохраняет повторяемый процесс. Например, code-review skill может предписывать изучить diff, проверить edge cases, безопасность и тесты, а затем выдать замечания с приоритетами.

Создавайте Skill, если workflow регулярно повторяется, его можно описать однозначно и команда выигрывает от стандартизации. Не стоит делать Skill для каждой мелочи: слишком много похожих навыков затрудняет выбор и поддержку.

Хороший Skill имеет ясное название, условия применения, конкретные шаги, проверяемые критерии и актуальные примеры. Длинные справочные материалы лучше хранить отдельно и подключать по необходимости.

# 15. Sub-Agents

**Sub-agent** — отдельный агент, которому делегируется ограниченная подзадача. Например, один исследует архитектуру, другой анализирует тесты, третий изучает документацию, а основной агент объединяет результаты.

Делегирование полезно, если задачи независимы, границы ясны и результат можно проверить отдельно. Оно может быть неэффективным, если задача маленькая, подзадачи тесно связаны или агенты одновременно меняют одни и те же файлы.

В поручении задайте цель, контекст, границы ответственности, разрешённые действия, формат ответа и критерии завершения.

Пример:

```text
Исследуй покрытие тестами модуля оплаты. Не изменяй файлы.
Перечисли основные сценарии, существующие тесты, пробелы и риски.
Укажи пути к важным файлам и обоснуй рекомендации.
```

Основной агент должен проверять выводы sub-agent, разрешать противоречия и запускать интеграционные проверки. Отчёт другого агента не является доказательством качества.

# 16. Claude Code Agent Teams

**Agent Teams** — подход к координации нескольких агентов над общей задачей. Он может дать параллелизм и разные точки зрения. Реальная доступность и команды зависят от текущей версии Claude Code.

Подходящая декомпозиция: исследование архитектуры, анализ требований и edge cases, тестовая стратегия, реализация независимого модуля, review. Не следует отдавать нескольким агентам одни и те же файлы без правил владения и интеграции.

Риски: конфликтующие изменения, дублирование, разные предположения, рост затрат на координацию и противоречивые рекомендации. Оценивайте не количество агентов, а качество и скорость проверенного результата.

# 17. Frameworks и Task-Master AI

Слово **framework** может означать framework приложения, framework для coding agents или **agent harness** — среду, соединяющую модель, инструменты, контекст, ограничения и цикл выполнения. В разговоре уточняйте значение.

Agent frameworks могут стандартизировать постановку задач, планирование, доступ к инструментам, обработку ошибок, проверку, состояние, делегирование и журналирование. Они не отменяют тестирование и не исправляют плохие требования автоматически.

**Task-Master AI** упоминается в программе как инструмент/подход для организации задач с AI. Общая модель task-management: передать PRD, получить иерархию задач, проверить зависимости, уточнить критерии готовности, выполнять задачи и отслеживать статус.

Автоматически сгенерированный список задач нужно проверять: он должен покрывать требования, не дублировать работу и учитывать порядок зависимостей.

Spec Kit делает акцент на связи между specification, plan, tasks и implementation. Task-management-инструмент может больше фокусироваться на декомпозиции и отслеживании задач. Функции конкретных продуктов зависят от версии.

# 18. NotebookLM

**NotebookLM** в материалах курса предлагается использовать для работы с учебными источниками и создания summary, audio overview, slide deck и mind map, если соответствующие функции доступны.

Workflow:

1. Собрать материалы: текст урока, документы и поддерживаемые ссылки.
2. Добавить источники в NotebookLM.
3. Попросить summary.
4. Проверить выводы по исходным материалам.
5. При необходимости создать аудиообзор, слайды или карту понятий.
6. Использовать их как вспомогательные материалы, а не замену оригиналам.

Инструмент подходит для конспектов, сопоставления документов, списков терминов и вопросов для самопроверки. Ограничения: резюме может опустить детали, слайды могут чрезмерно упростить материал, а точность зависит от источников. Не загружайте конфиденциальные данные в неразрешённые сервисы.

# 19. Проверка качества

AI-код может выглядеть убедительно, но содержать логические ошибки, неверные предположения или несоответствие архитектуре.

Основные уровни проверки:

- **Unit tests** — небольшие единицы логики;
- **Integration tests** — взаимодействие компонентов;
- **End-to-end tests** — пользовательский сценарий целиком;
- **Lint** — определённые проблемы стиля и качества;
- **Typecheck** — типовая корректность, если применимо;
- **Build** — возможность собрать проект;
- **Manual verification** — проверка поведения вручную.

Definition of Done может включать реализованные требования, обработку ошибок и edge cases, тесты, lint/typecheck/build, чистый diff, обновлённую документацию и список оставшихся ограничений.

AI может помочь с code review: объяснить diff, найти подозрительные участки, проверить требования и предложить тесты. Но AI-review не гарантирует обнаружения всех ошибок.

Хороший итоговый отчёт агента указывает, что изменено, какие файлы затронуты, какие проверки запускались и каков результат, какие сценарии не проверялись и какие риски остались.

# 20. Self-healing CI/CD

**CI (Continuous Integration)** — автоматизированная проверка изменений: тесты, lint, typecheck, build и другие quality gates. **CD (Continuous Delivery/Deployment)** — автоматизация подготовки релиза и/или развёртывания.

**Self-healing CI/CD** — workflow, который обнаруживает сбой, собирает диагностику и использует автоматизацию, в том числе AI-агента, чтобы предложить или выполнить исправление.

Традиционный сценарий: CI падает → разработчик читает лог → копирует ошибку в чат → получает совет → меняет код → запускает CI повторно.

Агентный сценарий:

```text
CI падает → workflow собирает логи и контекст → агент анализирует
→ готовит исправление → проверки → PR/review/разрешённое слияние
```

Безопасный дизайн:

1. Запускать анализ для подходящих ошибок.
2. Передавать минимально необходимый лог и контекст.
3. Не передавать секреты.
4. Ограничить доступ агента.
5. Генерировать diff или PR вместо прямого изменения защищённой ветки.
6. Запускать тесты, lint, typecheck и build после исправления.
7. Требовать review для существенных изменений.
8. Ограничивать число автоматических попыток.
9. Сохранять журнал действий и причину исправления.

Лучше подходят ограниченные воспроизводимые ошибки: lint, typecheck, тестовые fixtures, команда сборки. Опаснее автоматически менять production-данные, security policy, авторизацию, инфраструктуру и критические зависимости.

Оценивайте долю корректных исправлений, ложные срабатывания, время восстановления, повторные падения, стоимость и долю ручного вмешательства. Цель — безопасно сокращать время восстановления, а не максимизировать автономность.

# 21. Deployment Lovable-прототипа в Google Cloud

Инструменты вроде Lovable или Replit помогают быстро создать прототип. Для демонстрации, интеграции или большего контроля его можно развернуть в облаке. Курс рассматривает Google Cloud как один из возможных вариантов; это не означает, что он всегда дешевле или проще других облаков.

Общий процесс:

1. Получить исходный код.
2. Изучить стек и структуру.
3. Определить команды сборки и запуска.
4. Найти переменные окружения и зависимости.
5. Проверить локальный запуск.
6. Выбрать способ deployment.
7. Настроить runtime, build и environment variables.
8. Настроить доступ к БД и внешним сервисам.
9. При необходимости настроить домен и HTTPS.
10. Выполнить deployment.
11. Проверить логи, health checks и пользовательский сценарий.
12. Проверить, что секреты не попали в репозиторий или клиентский bundle.

До deployment выясните, frontend-only ли это приложение, есть ли backend и БД, какие API keys нужны, как выполняются миграции, какие требования к доступности и какие данные чувствительны.

Прототип может зависеть от платформы-генератора, содержать тестовые данные, небезопасные настройки CORS, отсутствие мониторинга или секреты в клиентском коде. Облачное размещение улучшает доступность демонстрации, но не делает приложение production-ready автоматически.

# 22. Мультиагентные системы, open-source модели и harness

**Multi-agent orchestration** — координация нескольких AI-агентов, инструментов и этапов workflow: кому назначается задача, какие контексты передаются, что можно выполнять параллельно, как объединять результаты и проверять итог.

**Agent harness** — окружающая система исполнения, управляющая моделью, контекстом, инструментами, разрешениями, циклом действий и проверками.

```text
Задача → harness/orchestration
  ├─ контекст и инструкции
  ├─ модель
  ├─ инструменты
  ├─ разрешения
  ├─ проверка результата
  └─ журналирование
→ итог
```

Модель — только один компонент. Надёжность зависит от контекста, инструментов, прав доступа, тестов и правил исполнения.

Open-source модели или модели для самостоятельного развёртывания могут быть полезны для контроля инфраструктуры, приватности, локальной обработки данных и настройки. Но нужно учитывать качество, скорость, hardware, лицензии, обслуживание и полную стоимость. Open-source не означает автоматически бесплатность, безопасность или превосходство.

Custom harness может ограничивать набор инструментов, маршрутизировать задачи, использовать локальную модель для классификации или суммаризации и передавать сложные задачи более сильной модели или человеку. Это требует инженерных усилий и не всегда выгоднее готового решения.

В программе упоминаются OpenCode, pythagora.dev и OpenClaw как примеры экосистемы. Их текущие функции и статус нужно проверять по официальным источникам.

# 23. Безопасность

## 23.1. Минимальные привилегии

Предоставляйте агенту только права, необходимые для текущей задачи. Для исследования обычно достаточно чтения; для реализации нужны права на изменение файлов; публикация и управление облаком требуют дополнительных разрешений.

## 23.2. Секреты

Не помещайте в промпты, логи и репозитории API keys, пароли, access tokens, приватные ключи и конфиденциальные данные. Используйте секрет-хранилища и контролируйте, какие инструменты видят credentials.

## 23.3. Prompt injection

**Prompt injection** — попытка повлиять на поведение модели через прочитанный ею внешний контент: документ, issue, страницу, лог или README. Риск возникает, когда модель воспринимает данные как инструкции.

Меры защиты: разделять инструкции и данные, ограничивать разрешения, проверять действия с внешними эффектами и не выполнять автоматически команды, найденные в документах.

## 23.4. Высокорисковые изменения

Особого контроля требуют удаление данных, миграции БД, изменения авторизации, обновления критических зависимостей, deployment и инфраструктура. Для таких задач нужны план, тестовая среда, rollback strategy и review.

Перед принятием AI-изменений проверьте diff, секреты, зависимости, права доступа, edge cases, тесты, способ отката и существование используемых API.

| Ситуация | Подход |
|---|---|
| Маленькая локальная правка | Короткий промпт, небольшой diff, целевая проверка |
| Неясная задача | Исследование и уточнение требований |
| Средняя функция | План, контекст, реализация и тесты |
| Большая функция | SDD, PRD/spec, plan, tasks и verification |
| Незнакомая кодовая база | Исследование контекста до изменений |
| Повторяемый процесс | Agent Skill или стандартизированный workflow |
| Независимые подзадачи | Sub-agents/agent team, если оправдана координация |
| Падающий CI | Анализ логов, ограниченное исправление и повторные проверки |
| Прототип для демонстрации | Проверка стека и секретов, затем контролируемый deployment |

# Шпаргалка

- **AI-Assisted Development** — AI ускоряет инженерную работу, но разработчик отвечает за результат.
- **Coding agent** — может выполнять действия через инструменты, а не только генерировать текст.
- **Prompt Engineering** — как сформулировать инструкцию.
- **Meta Prompting** — улучшение или создание промпта с помощью AI.
- **Context Engineering** — какие данные, инструкции и инструменты предоставить модели.
- **RAG** — поиск релевантных данных с последующим использованием в генерации.
- **MCP** — стандартизированное подключение AI-приложений к инструментам и источникам.
- **SDD** — разработка вокруг явной спецификации.
- **Constitution** — постоянные правила проекта.
- **PRD** — продуктовые требования.
- **Plan** — технический способ реализации.
- **Tasks** — конкретные действия.
- **Agent Skill** — переиспользуемый workflow для агента.
- **Sub-Agent** — агент с ограниченной делегированной задачей.
- **Agent Team** — группа агентов, координируемых для общей задачи.
- **Agent harness** — система исполнения модели, инструментов, контекста и контроля.
- **Self-healing CI/CD** — автоматизированный анализ и исправление сбоев с проверкой результата.

Ключевые различия:

- Prompt Engineering — формулировка; Context Engineering — подготовка информационной среды.
- Specification — что и зачем; Plan — как; Tasks — какие действия.
- Constitution — общие правила; spec — требования функции.
- MCP — интеграционный протокол, но не гарантия безопасности.
- MVP — минимальная версия для проверки ценности; Post-MVP — развитие по обратной связи.
- Успешная сборка — не доказательство правильного поведения или безопасности.

```text
Ясная цель + релевантный контекст + ограниченный scope + проверяемые критерии + безопасные инструменты + независимая проверка = более надёжный AI-assisted workflow
```
