## 1. Artificial Intelligence (AI)

**Artificial Intelligence (AI)** — искусственный интеллект, область компьютерных наук, в которой создаются системы, способные выполнять задачи, обычно требующие человеческого интеллекта: анализировать информацию, распознавать закономерности, генерировать текст и код, принимать решения.

В разработке AI используют для:

- генерации и рефакторинга кода;
    
- поиска и исправления ошибок;
    
- анализа существующего проекта;
    
- написания тестов и документации;
    
- автоматизации повторяющихся задач.
    

## 2. Machine Learning и Deep Learning

**Machine Learning (ML)** — машинное обучение, подход, при котором система обучается закономерностям на данных вместо того, чтобы программист вручную описывал каждое правило.

**Deep Learning (DL)** — направление машинного обучения, основанное на многослойных нейронных сетях.

**LLM** — один из видов моделей, построенных с использованием глубокого обучения.

Упрощённая связь:

AI → Machine Learning → Deep Learning → современные LLM.

## 3. LLM — Large Language Model

**LLM (Large Language Model)** — большая языковая модель, обученная обрабатывать язык и генерировать последовательности токенов на основе контекста.

Примеры семейств моделей:

- GPT от OpenAI;
    
- Claude от Anthropic;
    
- Gemini от Google.
    

LLM может:

- понимать и генерировать текст;
    
- объяснять концепции;
    
- анализировать код;
    
- предлагать решения;
    
- находить закономерности и ошибки;
    
- генерировать структурированные ответы.
    

### Как работает LLM

Упрощённый процесс:

1. Модель получает входные данные.
    
2. Текст преобразуется в последовательность токенов.
    
3. Модель обрабатывает вход с учётом контекста.
    
4. Модель вычисляет вероятности возможных следующих токенов.
    
5. Токены генерируются последовательно, формируя ответ.
    

Модель не просто ищет готовый ответ в базе данных. Она генерирует результат на основе выученных закономерностей и текущего контекста.

**Важно:** LLM может ошибаться, придумывать несуществующие API и выдавать убедительный, но неверный ответ. Поэтому результаты нужно проверять.

## 4. Token — токен

**Токен** — единица текста, которую модель использует при обработке входных данных и генерации ответа.

Токеном может быть:

- целое слово;
    
- часть слова;
    
- знак препинания;
    
- другой фрагмент текста.
    

Например, слово может разбиваться на несколько токенов. Конкретное разбиение зависит от токенизатора модели.

Токены используются для измерения:

- размера входного контекста;
    
- объёма сгенерированного ответа;
    
- использования контекстного окна;
    
- расхода ресурсов и, в некоторых тарифах, стоимости API-запросов.
    

В AI-assisted Development токены расходуются не только на промпт, но и на код, инструкции, историю диалога, результаты инструментов и ответы модели.

## 5. Context Window — контекстное окно

**Context Window** — максимальный объём токенов, который модель может учитывать в рамках одного контекстного окна.

В контекст могут входить:

- системные инструкции;
    
- сообщения пользователя;
    
- предыдущие ответы;
    
- код и документация;
    
- результаты вызовов инструментов;
    
- другая информация, переданная модели.
    

Чем больше нерелевантной информации, тем больше ресурсов может расходоваться впустую.

Большое контекстное окно не означает, что модель всегда одинаково хорошо использует всю находящуюся в нём информацию.

### Как управлять контекстом

- Передавать только необходимые файлы и сведения.
    
- Использовать инструкции проекта.
    
- Сохранять важные решения и прогресс.
    
- Сжимать историю, если это необходимо.
    
- Делегировать независимые исследования субагентам.
    

## 6. Prompt и Prompt Engineering

**Prompt** — запрос или инструкция, переданная модели.

Пример:

> Изучи компонент TaskCard, найди причину ошибки и предложи минимальное исправление. Не меняй другие компоненты без необходимости.

**Prompt Engineering** — процесс проектирования и улучшения промптов для получения более точных и предсказуемых результатов.

Хороший промпт обычно определяет:

- цель;
    
- контекст задачи;
    
- ограничения;
    
- ожидаемый формат результата;
    
- критерии успешного выполнения.
    

Плохой промпт:

> Сделай страницу лучше.

Хороший промпт:

> Реализуй страницу проекта по указанному макету Figma. Используй существующую дизайн-систему, сохрани адаптивность, не добавляй новые зависимости без необходимости и проверь результат через Playwright.

## 7. Context Engineering

**Context Engineering** — организация информации, доступной модели, для решения конкретной задачи.

В контекст могут входить:

- инструкции;
    
- структура проекта;
    
- исходный код;
    
- документация;
    
- правила разработки;
    
- история принятых решений;
    
- результаты тестов;
    
- данные, полученные через инструменты.
    

Пример: вместо того чтобы просить агента написать страницу с нуля, разработчик предоставляет ему существующие компоненты, файл с правилами проекта, нужный макет Figma и команды для запуска тестов.

Это позволяет уменьшить количество предположений и повысить вероятность того, что решение будет соответствовать архитектуре проекта.

**Разница:**

- Prompt Engineering отвечает за формулирование задачи.
    
- Context Engineering отвечает за организацию информации, необходимой для её решения.
    

## 8. AI Assistant и AI Agent

### AI Assistant

**AI Assistant** — помощник, который отвечает на запросы, объясняет концепции, генерирует идеи или код.

Обычно пользователь сам переносит предложенный код в проект и запускает его.

### AI Agent

**AI Agent** — система на основе модели, которая может выбирать действия, использовать инструменты, наблюдать за результатами и продолжать работу для достижения цели.

Например, агент разработки может:

1. Изучить репозиторий.
    
2. Найти нужный компонент.
    
3. Изменить код.
    
4. Запустить тесты.
    
5. Проанализировать ошибки.
    
6. Исправить найденные проблемы.
    
7. Проверить итоговый результат.
    

Разница не только в качестве ответа, но и в возможности выполнять последовательность действий с использованием инструментов.

## 9. Agent Loop

**Agent Loop** — повторяющийся цикл работы агента, в котором он анализирует задачу, выполняет действия, получает результаты и определяет следующие шаги.

Упрощённая схема:

1. **Analyze** — анализ задачи и контекста.
    
2. **Plan** — выбор следующего шага.
    
3. **Act** — выполнение действия.
    
4. **Observe** — получение результата.
    
5. **Evaluate** — оценка результата и выбор дальнейшего действия.
    

Цикл продолжается, пока агент не достигнет цели, не столкнётся с препятствием или не выполнится условие остановки.

Пример: агент запускает тест, получает ошибку, изучает сообщение, исправляет код и повторяет тест.

Agent Loop не гарантирует правильного результата. Агент может зациклиться, неверно интерпретировать ошибку или принять неудачную реализацию за успешную.

## 10. Tools — инструменты агента

**Tools** — инструменты, с помощью которых агент взаимодействует с внешней средой.

В разработке это могут быть:

- чтение и изменение файлов;
    
- поиск по проекту;
    
- выполнение команд в терминале;
    
- запуск тестов;
    
- работа с Git;
    
- взаимодействие с браузером;
    
- получение данных из внешних сервисов.
    

Пример: модель сама по себе не обязательно может открыть сайт или выполнить тесты. Но если агенту доступен инструмент терминала или браузера, он может запросить выполнение соответствующего действия и использовать полученный результат.

Модель выбирает действие, инструмент выполняет его в разрешённой среде, а результат возвращается модели.

## 11. MCP — Model Context Protocol

**MCP (Model Context Protocol)** — протокол, позволяющий AI-приложениям взаимодействовать с внешними источниками данных и инструментами через стандартизированный интерфейс.

MCP-сервер может предоставлять:

- **Tools** — выполняемые действия;
    
- **Resources** — доступные данные и ресурсы;
    
- **Prompts** — шаблоны запросов, если они реализованы сервером.
    

Примеры в разработке:

- Figma MCP — получение данных о дизайне;
    
- Playwright MCP — управление браузером и проверка интерфейса;
    
- MCP для документации — получение справочной информации.
    

MCP предоставляет возможность взаимодействия, но сам по себе не гарантирует правильного использования инструментов или качества результата.

## 12. Skills

**Skill** — переиспользуемый набор инструкций и, в зависимости от реализации, вспомогательных материалов или сценариев для выполнения определённого типа задач.

Пример Skill для Claude Code:

1. Изучить структуру проекта.
    
2. Получить данные нужного фрейма Figma.
    
3. Найти существующие компоненты и стили.
    
4. Реализовать страницу.
    
5. Проверить её в браузере.
    
6. Исправить визуальные расхождения.
    
7. Запустить необходимые тесты.
    

Skills помогают стандартизировать повторяющиеся рабочие процессы.

Skill и MCP решают разные задачи:

- MCP предоставляет интерфейс для доступа к инструментам и данным.
    
- Skill описывает, как выполнять определённую работу.
    

Они могут использоваться независимо друг от друга.

## 13. Инструкции проекта: CLAUDE.md и AGENTS.md

Файлы `CLAUDE.md` и `AGENTS.md` используются соответствующими AI-инструментами для передачи инструкций проекта.

В них можно описать:

- архитектуру проекта;
    
- правила написания кода;
    
- структуру каталогов;
    
- команды сборки и тестирования;
    
- ограничения;
    
- соглашения команды;
    
- требования к проверке изменений.
    

Например:

- Используй существующие компоненты.
    
- Не добавляй зависимости без необходимости.
    
- Перед завершением запускай тесты.
    
- Соблюдай принятый в проекте стиль кода.
    

Эти файлы не являются взаимозаменяемыми во всех инструментах: нужно учитывать, какой файл и какой формат инструкций поддерживает конкретный агент.

## 14. Skills, инструкции и промпт — различия

|Механизм|Для чего нужен|
|---|---|
|Prompt|Поставить конкретную задачу|
|Context|Предоставить необходимую информацию|
|`CLAUDE.md` / `AGENTS.md`|Задать инструкции проекта|
|Skill|Описать переиспользуемый процесс|
|MCP|Предоставить стандартизированный доступ к внешним инструментам и данным|

Пример:

Промпт говорит: «Реализуй страницу профиля».

Инструкции проекта определяют правила разработки.

Контекст предоставляет код, макет и документацию.

Skill описывает порядок реализации и проверки интерфейса.

MCP предоставляет доступ к Figma и браузеру.

## 15. Subagents — субагенты

**Субагент** — отдельный агент, которому делегируется часть общей задачи.

Примеры:

- исследовать архитектуру проекта;
    
- изучить макет Figma;
    
- проверить тестовое покрытие;
    
- выполнить независимый анализ кода.
    

Субагенты полезны, когда задачи можно разделить на относительно независимые части.

Преимущества:

- разделение контекста;
    
- возможность параллельной работы;
    
- специализация на конкретной задаче;
    
- передача главному агенту кратких результатов вместо всей истории исследования.
    

Ограничения:

- дополнительные расходы токенов;
    
- необходимость координации;
    
- риск конфликтующих изменений;
    
- возможная потеря деталей при передаче краткого результата.
    

Субагенты не всегда экономят ресурсы. Для небольшой последовательной задачи их использование может быть избыточным.

## 16. Plan Mode

**Plan Mode** — режим предварительного планирования, в котором агент исследует задачу и предлагает последовательность действий до начала реализации.

План обычно включает:

- цель;
    
- файлы и компоненты, которые нужно изучить или изменить;
    
- последовательность шагов;
    
- зависимости;
    
- проверки и критерии завершения.
    

План позволяет выявить неверное понимание задачи до внесения изменений.

Перед реализацией разработчик оценивает:

- соответствие цели;
    
- обоснованность изменений;
    
- соблюдение архитектуры;
    
- возможные риски;
    
- достаточность проверок.
    

Большой план не обязательно плохой, а маленький не обязательно хороший. Важны обоснованность и масштаб изменений относительно задачи.

## 17. Code Review и ответственность разработчика

Даже если агент успешно выполнил задачу и тесты прошли, код необходимо проверить.

Review должен учитывать:

- корректность логики;
    
- читаемость и сопровождаемость;
    
- соответствие архитектуре;
    
- отсутствие ненужных зависимостей;
    
- обработку ошибок;
    
- безопасность;
    
- побочные эффекты;
    
- достаточность тестов.
    

**Ответственность за итоговый код остаётся у разработчика**, который проверяет и принимает изменения.

Успешные тесты подтверждают только то, что проверяют сами тесты. Они не доказывают автоматически правильность всей архитектуры, отсутствие уязвимостей или полное соответствие требованиям.

## 18. Как организовать работу AI-агента

Типовой процесс разработки:

1. **Задача** — сформулировать цель и критерии приёмки.
    
2. **Контекст** — предоставить необходимые инструкции, файлы и документацию.
    
3. **Исследование** — изучить проект и существующие решения.
    
4. **План** — согласовать последовательность действий.
    
5. **Реализация** — внести минимально необходимые изменения.
    
6. **Проверка** — запустить тесты, линтеры и браузерные проверки.
    
7. **Review** — проверить код, архитектуру и риски.
    
8. **Исправления** — устранить найденные проблемы.
    
9. **Приёмка** — убедиться, что критерии выполнены и результат воспроизводим.
    

## 19. Основные принципы AI-assisted Development

- AI-агент ускоряет разработку, но не заменяет ответственность разработчика.
    
- Качество результата зависит от задачи, контекста, инструментов и проверки.
    
- Большой объём контекста не всегда лучше тщательно подобранного.
    
- Планирование помогает обнаружить ошибки понимания до реализации.
    
- Skills стандартизируют повторяющиеся процессы.
    
- MCP предоставляет доступ к внешним возможностям.
    
- Субагенты полезны для независимых задач, но требуют координации.
    
- Автоматические тесты и Code Review дополняют друг друга.
    
- Критерии приёмки должны быть проверяемыми.
    
- Автономность агента должна соответствовать риску выполняемых действий.

- **MCP** — протокол взаимодействия с инструментами и данными.
