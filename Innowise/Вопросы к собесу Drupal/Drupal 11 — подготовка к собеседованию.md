## Блок 1. Multilingual — мультиязычность

### 1.1. Общая концепция

Drupal поддерживает мультиязычные сайты, на которых интерфейс, содержимое и конфигурация могут существовать на нескольких языках.

Например, сайт может иметь русский и английский интерфейс, а одна статья — русскую и английскую версии. При этом не весь контент обязательно должен иметь перевод.

В Drupal различают три основных аспекта мультиязычности:

- **Interface language** — язык интерфейса: кнопок, сообщений, системных надписей и других переводимых строк.
    
- **Content language** — язык содержимого: материалов, пользовательских сущностей и переводимых полей.
    
- **Configuration language** — язык переводимых значений конфигурации, например меток и описаний полей.
    

Основные модули ядра:

- `Language` — управление языками и определение языкового контекста.
    
- `Interface Translation` — перевод интерфейсных строк.
    
- `Content Translation` — перевод содержимого.
    
- `Configuration Translation` — перевод поддерживаемых конфигурационных значений.
    

Эти модули работают совместно, но решают разные задачи.

### 1.2. Language negotiation

Language negotiation — механизм определения языка для текущего запроса.

Drupal может выбирать язык на основании:

- Языкового префикса URL: `/en/about`.
    
- Домена или поддомена: `en.example.com`.
    
- Предпочтений пользователя.
    
- Заголовка браузера `Accept-Language`.
    
- Языка по умолчанию.
    

Методы и их приоритет настраиваются в административном интерфейсе. Результат зависит от выбранных методов и типа языка, который определяется.

Язык интерфейса и язык содержимого могут отличаться. Например, пользователь видит английские системные сообщения, но открывает русскую статью.

Для работы с языками используется сервис `language_manager`.

```php
$language_manager = \Drupal::languageManager();

$interface_language = $language_manager
  ->getCurrentLanguage(
    \Drupal\Core\Language\LanguageInterface::TYPE_INTERFACE
  );

$content_language = $language_manager
  ->getCurrentLanguage(
    \Drupal\Core\Language\LanguageInterface::TYPE_CONTENT
  );

$interface_code = $interface_language->getId();
$content_code = $content_language->getId();
```

Результатом могут быть языковые коды `ru`, `en` и другие.

В классах приложения предпочтительно получать `language_manager` через Dependency Injection, а не использовать статический вызов `\Drupal::languageManager()`.

### 1.3. Перевод сущностей

В Drupal перевод может существовать на уровне сущности и отдельных полей.

Например, сущность `Article` содержит:

- `title` — заголовок;
    
- `body` — текст статьи;
    
- `field_publish_date` — дату публикации;
    
- `field_external_id` — внешний идентификатор.
    

Заголовок и текст можно сделать переводимыми, а дату и внешний идентификатор оставить общими для всех переводов.

Переводимость полей настраивается отдельно. Если поле непереводимое, его значение используется совместно переводами сущности.

Пример получения перевода материала:

```php
$node = \Drupal\node\Entity\Node::load($nid);

if ($node && $node->hasTranslation('en')) {
  $english_node = $node->getTranslation('en');

  $title = $english_node->label();
  $body = $english_node->get('body')->value;
}
```

Основные методы:

- `isTranslatable()` — проверяет, поддерживает ли тип сущности переводы.
    
- `isDefaultTranslation()` — определяет, является ли перевод основным.
    
- `hasTranslation($langcode)` — проверяет наличие перевода.
    
- `getTranslation($langcode)` — получает существующий перевод.
    
- `addTranslation($langcode, $values)` — создаёт перевод с переданными значениями в соответствии с API сущностей.
    

`getTranslation()` не создаёт перевод автоматически. Перед обращением к переводу необходимо проверить его наличие либо корректно обработать отсутствие.

Переводы используют общую сущность и её идентификатор. Это не отдельные независимые материалы, хотя отдельные значения полей могут различаться.

### 1.4. Перевод интерфейса

Строки пользовательского интерфейса должны быть доступны для перевода.

В классах Drupal обычно применяется `$this->t()`:

```php
$message = $this->t('Task has been saved.');
```

Для динамических значений используется подстановка:

```php
$message = $this->t(
  'Task @title has been saved.',
  ['@title' => $title]
);
```

Основные маркеры подстановки:

- `@value` — текстовая подстановка с экранированием.
    
- `%value` — экранированная подстановка, обычно предназначенная для визуального выделения.
    
- `:value` — специальная подстановка URL; использовать её нужно согласно правилам API перевода и требованиям к URL.
    

Не следует собирать переводимую фразу из множества отдельных строк. Лучше передавать целую фразу в функцию перевода, чтобы переводчик мог изменять порядок слов.

Например, вместо конкатенации имени и статического текста лучше использовать:

```php
$message = $this->t(
  'The task @title has been updated.',
  ['@title' => $title]
);
```

Функция перевода не заменяет все остальные меры безопасности. При выводе данных необходимо учитывать контекст, экранирование и способ дальнейшей обработки.

### 1.5. Перевод конфигурации

Конфигурация хранит настройки Drupal: определения полей, типы материалов, Views, настройки модулей и другие параметры.

Часть конфигурации поддерживает перевод. Например, административная метка поля может переводиться, а его машинное имя — нет.

Configuration Translation API позволяет переводить поддерживаемые текстовые значения конфигурации.

Нужно различать:

- **Configuration Management** — перенос настроек между окружениями.
    
- **Configuration Translation** — перевод значений настроек.
    

Это разные механизмы. Экспорт конфигурации не является переводом, а перевод конфигурации не заменяет процесс её развёртывания.

### 1.6. Language fallback

Language fallback — механизм выбора альтернативного языка или значения, когда запрошенный перевод недоступен.

Например, сайт может не иметь перевода определённого элемента на французский язык. В зависимости от используемого механизма и настроек Drupal может выбрать альтернативное значение либо не предоставить ожидаемый перевод.

Нельзя предполагать, что любой отсутствующий перевод автоматически заменится значением языка по умолчанию. Поведение зависит от типа данных и используемого API.

При разработке нужно отдельно учитывать отсутствие перевода сущности и отсутствие перевода конкретного поля.

### 1.7. Мультиязычность и кеширование

Язык может влиять на результат рендеринга. Поэтому кеширование должно учитывать языковой контекст, когда он изменяет результат.

Drupal использует Cache Contexts, в том числе контексты языка интерфейса и языка содержимого.

Например, если компонент выводит заголовок переведённой статьи, кеш не должен ошибочно использовать английский вариант для русского запроса.

Языковой контекст может добавляться непосредственно при формировании render array либо передаваться через другие кешируемые объекты.

### 1.8. Типичные ошибки

- Смешивать язык интерфейса и язык содержимого.
    
- Не проверять наличие перевода перед его получением.
    
- Ожидать отдельные значения для непереводимого поля.
    
- Оставлять пользовательские сообщения непереводимыми.
    
- Забывать про языковые контексты кеширования.
    
- Пытаться переводить машинные имена полей и конфигурационных объектов.
    
- Предполагать одинаковое поведение fallback для всех типов данных.

## Блок 2. REST API

### 2.1. Что такое REST

REST (Representational State Transfer) — архитектурный стиль построения систем, взаимодействующих с ресурсами через HTTP.

REST API позволяет внешним приложениям получать данные и выполнять операции над ресурсами. Например, frontend на React может запрашивать список задач из Drupal и отправлять запросы на изменение их статусов.

REST API — это не просто возврат JSON. Важны также структура ресурсов, HTTP-методы, коды ответов, аутентификация, проверка доступа, валидация и обработка ошибок.

### 2.2. Ресурсы и HTTP-методы

Ресурс — объект или представление данных, с которым работает клиент. Например, задача или коллекция задач.

URI идентифицирует ресурс или коллекцию ресурсов.

Основные HTTP-методы:

- `GET` — получение представления ресурса.
    
- `POST` — создание ресурса или выполнение операции.
    
- `PATCH` — частичное изменение ресурса.
    
- `PUT` — создание или полная замена ресурса согласно контракту API.
    
- `DELETE` — удаление ресурса.
    

Пример запроса к JSON в Drupal:

```php
GET /jsonapi/node/task
Accept: application/vnd.api+json
```

Он обращается к коллекции сущностей типа `task` в bundle `node`.

Основные HTTP-коды:

- `200 OK` — запрос успешно выполнен.
    
- `201 Created` — ресурс создан.
    
- `204 No Content` — операция выполнена без тела ответа.
    
- `400 Bad Request` — запрос некорректен.
    
- `401 Unauthorized` — отсутствует подходящая аутентификация.
    
- `403 Forbidden` — доступ запрещён.
    
- `404 Not Found` — ресурс не найден или не предоставляется клиенту.
    
- `405 Method Not Allowed` — HTTP-метод не поддерживается для данного ресурса.
    

Конкретный ответ зависит от реализации endpoint и настроек безопасности.

### 2.3. REST в Drupal

Drupal предоставляет несколько механизмов построения API:

- REST-модуль ядра.
    
- JSON.
    
- Собственные маршруты и контроллеры.
    
- Дополнительные модули для специализированных API, например GraphQL.
    

REST-модуль ядра позволяет настраивать REST-ресурсы, HTTP-методы, форматы и способы аутентификации.

Основные компоненты REST-инфраструктуры:

- REST Resource plugins — реализация операций над ресурсами.
    
- Serialization API — нормализация и сериализация данных.
    
- Authentication API — определение контекста аутентификации.
    
- Access API — проверка разрешения операции.
    

JSON является отдельной реализацией API, ориентированной на спецификацию JSON. Его не следует путать с REST Resource plugins.

### 2.4. REST Resource plugins

Собственный REST Resource обычно реализуется как плагин, наследующий `ResourceBase`.

Плагин определяет идентификатор, название, URI и поддерживаемые методы.

Пример структуры:

```php
<?php

namespace Drupal\example\Plugin\rest\resource;

use Drupal\rest\Plugin\ResourceBase;
use Drupal\rest\ResourceResponse;

/**
 * Provides a simple tasks resource.
 *
 * @RestResource(
 *   id = "example_tasks",
 *   label = @Translation("Example tasks"),
 *   uri_paths = {
 *     "canonical" = "/api/tasks"
 *   }
 * )
 */
final class TasksResource extends ResourceBase {

  public function get() {
    return new ResourceResponse([
      'data' => [
        ['id' => 1, 'title' => 'Prepare notes'],
      ],
    ]);
  }

}
```

Это упрощённый пример, который демонстрирует структуру ресурса. Для production-реализации нужно учитывать контракт API, проверки доступа, сериализацию, обработку ошибок и актуальные требования используемой версии Drupal.

В приведённом примере данные статические. В реальном приложении они обычно получаются через Entity API, сервис или специализированный слой доступа к данным.

REST-ресурсы должны быть включены и настроены в конфигурации Drupal. Наличие PHP-класса само по себе не гарантирует, что endpoint доступен.

### 2.5. REST и JSON

REST Resource подходит для реализации специализированных операций и нестандартных ресурсов.

JSON особенно полезен, когда frontend должен работать со стандартными сущностями Drupal: материалами, пользователями и их полями.

Различия:

|REST Resource|JSON|
|---|---|
|Реализуется через собственные REST-плагины|Предоставляет стандартизированный API сущностей|
|Структуру ответа определяет разработчик|Структура соответствует спецификации JSON|
|Подходит для специализированных операций|Подходит для стандартных операций с сущностями|
|Требует реализации собственной логики|Многие типовые операции уже реализованы|

Если задача состоит в предоставлении стандартных данных сущностей, сначала стоит оценить JSON. Если требуется специализированная бизнес-операция, можно реализовать REST Resource или собственный маршрут.

### 2.6. Serialization API

Serialization API преобразует данные между PHP-представлением и внешним форматом, например JSON.

Основные понятия:

- **Normalization** — преобразование объекта в структурированное представление.
    
- **Encoding** — преобразование нормализованных данных в конкретный формат.
    

Упрощённый процесс обработки API-запроса:

1. Drupal получает HTTP-запрос.
    
2. Определяет маршрут и обработчик.
    
3. Выполняет необходимые проверки аутентификации и доступа.
    
4. Обрабатывает запрос и получает данные.
    
5. Подготавливает ответ.
    
6. Сериализует данные, если это предусмотрено механизмом.
    
7. Возвращает HTTP-ответ.
    

Точный порядок и распределение обязанностей зависят от реализации endpoint и используемых компонентов Drupal.

### 2.7. Authentication, Authorization и CSRF

Эти механизмы выполняют разные задачи.

**Authentication** определяет, кто выполняет запрос или какой клиент его отправляет.

**Authorization** определяет, разрешена ли конкретная операция этому субъекту.

**CSRF protection** защищает от подделки запросов, выполняемых от имени пользователя через его браузерную сессию.

Аутентифицированный пользователь не обязательно имеет право изменять конкретную сущность.

Например, пользователь может войти в Drupal, но не иметь права менять статус задачи. Проверка должна выполняться на сервере.

Для запросов, использующих cookie-based session authentication, особенно важна CSRF-защита. Требования зависят от способа аутентификации и типа endpoint.

HTTPS защищает транспортный канал, но не заменяет авторизацию и CSRF-защиту.

### 2.8. Валидация и обработка ошибок

Входные данные API необходимо проверять перед использованием.

Проверяются:

- Формат и типы значений.
    
- Обязательные поля.
    
- Допустимые значения перечислений.
    
- Существование связанных сущностей.
    
- Права пользователя на выполнение операции.
    
- Бизнес-ограничения.
    

Например, если API принимает новый статус задачи, недостаточно проверить, что значение является строкой. Нужно убедиться, что статус разрешён и соответствующий переход допустим.

Ошибки должны возвращаться в согласованном формате. Нельзя раскрывать клиенту внутренние stack traces, секреты или чувствительные данные.

### 2.9. Кеширование API

Ответы API могут кешироваться, если это безопасно и оправдано.

При этом необходимо учитывать:

- Query parameters.
    
- Заголовки запроса, влияющие на ответ.
    
- Язык.
    
- Права доступа.
    
- Аутентификацию.
    
- Персональные данные.
    

Персонализированные ответы нельзя бездумно помещать в общий кеш. Неправильная конфигурация может привести к выдаче данных одного пользователя другому.

### 2.10. Типичные ошибки

- Разрешать операции без полноценной проверки доступа.
    
- Считать аутентификацию достаточным условием для изменения данных.
    
- Игнорировать CSRF-защиту.
    
- Не валидировать входные данные.
    
- Путать REST Resource и JSON.
    
- Возвращать внутренние ошибки и чувствительные сведения.
    
- Использовать неподходящие HTTP-методы.
    
- Кешировать персональные ответы без необходимых ограничений.

## Блок 3. Configuration Management

### 3.1. Назначение

Configuration Management — механизм хранения, экспорта, импорта и переноса конфигурации Drupal между окружениями.

Например, разработчик создаёт тип материала `Task`, добавляет поля, настраивает Views и permissions. Эти изменения должны быть перенесены на тестовый сервер и затем в production.

Вместо повторного создания настроек вручную конфигурация экспортируется в YAML-файлы, сохраняется в Git и импортируется на целевом окружении.

Главный принцип: конфигурация описывает настройки и устройство сайта, а контент содержит рабочие данные сайта.

Примеры конфигурации:

- Типы материалов.
    
- Определения полей.
    
- Views.
    
- Настройки модулей.
    
- Роли и разрешения.
    
- Настройки workflow.
    
- Настройки отображения форм и полей.
    

Примеры контента:

- Конкретная статья.
    
- Задача в DrupalJira.
    
- Проект.
    
- Запись времени, затраченного на задачу.
    

Не каждый объект, хранящийся в базе данных, является контентом. Классификация зависит от типа сущности и её назначения.

### 3.2. Active configuration и synchronization storage

**Active configuration** — активная конфигурация, используемая работающим сайтом. Обычно она хранится в базе данных.

**Synchronization storage** — хранилище конфигурации для синхронизации. Оно содержит экспортированные файлы, которые используются для переноса изменений.

Путь к sync-каталогу обычно определяется настройками окружения, в том числе в `settings.php`.

Рабочий процесс:

1. Разработчик изменяет настройки сайта.
    
2. Экспортирует активную конфигурацию.
    
3. Проверяет YAML-файлы.
    
4. Сохраняет изменения в Git.
    
5. Развёртывает код и конфигурацию на другом окружении.
    
6. Импортирует конфигурацию.
    

### 3.3. Команды Drush

Основные команды:

```php
# Экспорт активной конфигурации.
drush config:export

# Импорт конфигурации из sync-каталога.
drush config:import

# Просмотр различий конфигурации.
drush config:status
```

Распространённые сокращения:

```php
drush cex
drush cim
drush cst
```

Перед импортом важно проверить изменения и убедиться, что целевое окружение готово к обновлению.

Импорт может создавать, изменять и удалять конфигурационные объекты. Это не безусловно безопасная операция, особенно на production.

### 3.4. YAML и machine names

Конфигурация Drupal обычно представлена YAML-файлами.

Например, настройки типа материала могут находиться в `node.type.task.yml`.

Упрощённый пример:

```php
langcode: en
status: true
name: Task
type: task
description: 'Work item for a project.'
new_revision: true
```

Это иллюстративный фрагмент. Реальная конфигурация может содержать дополнительные поля и зависимости.

Основные понятия:

- **Machine name** — технический идентификатор объекта.
    
- **Label** — название, предназначенное для отображения пользователю.
    
- **UUID** — уникальный идентификатор конфигурационного объекта.
    

Например, `field_status` — машинное имя поля, а `Status` — его метка.

Machine names используются в коде и зависимостях, поэтому их изменение требует анализа связанных объектов.

### 3.5. Config schema

Config schema описывает структуру и типы значений конфигурации. Она помогает Drupal интерпретировать конфигурационные данные, проверять их структуру и определять переводимые значения.

Например, собственный модуль хранит настройки:

```php
api_endpoint: 'https://api.example.com'
timeout: 30
enabled: true
```

Для этих настроек может быть объявлена схема:

```php
example.settings:
  type: config_object
  label: 'Example settings'
  mapping:
    api_endpoint:
      type: uri
      label: 'API endpoint'
    timeout:
      type: integer
      label: 'Timeout'
    enabled:
      type: boolean
      label: 'Enabled'
```

Файл схемы должен соответствовать реальной структуре конфигурации и правилам Drupal Config Schema API.

Отсутствие схемы или неправильные типы могут осложнить проверку конфигурации, её перевод и обслуживание.

### 3.6. `config/install` и `config/optional`

Модули могут поставлять конфигурационные файлы в собственных каталогах.

`config/install` содержит конфигурацию, предназначенную для установки при установке модуля, если выполнены необходимые условия.

`config/optional` содержит конфигурацию, которая может быть установлена при наличии необходимых зависимостей.

Например, модуль может поставлять настройки по умолчанию или подготовленное представление.

Важно: добавление нового файла в `config/install` не означает, что он автоматически обновит конфигурацию на всех уже существующих сайтах.

Для обновления существующих инсталляций используют управляемый импорт конфигурации или update hooks, в зависимости от характера изменения.

### 3.7. Dependencies

Конфигурационные объекты часто зависят друг от друга.

Например, View может ссылаться на:

- Тип материала.
    
- Поля сущности.
    
- Форматтеры.
    
- Модули, предоставляющие плагины.
    

Если зависимый объект отсутствует, импорт может завершиться ошибкой.

При работе с конфигурацией необходимо учитывать:

- Включены ли требуемые модули.
    
- Существуют ли необходимые объекты.
    
- Корректны ли machine names.
    
- Совместимы ли схемы конфигурации.
    
- Не удаляется ли объект, на который ссылаются другие настройки.
    
- Соответствуют ли UUID и зависимости ожидаемому состоянию.
    

Зависимости должны быть согласованы между кодом и конфигурацией.

### 3.8. Configuration Management и update hooks

Configuration Management отвечает за декларативное описание и перенос настроек.

Update hooks позволяют выполнить программные изменения при обновлении существующей установки.

Например, update hook может добавить новое значение в существующую конфигурацию:

```php
/**
 * Adds a new configuration value.
 */
function example_update_10001(): void {
  $config = \Drupal::configFactory()
    ->getEditable('example.settings');

  $config
    ->set('enabled', TRUE)
    ->save();
}
```

Это упрощённый пример. Реальная логика должна учитывать существующие значения и состояние сайта.

Update hooks используют, когда существующая установка должна пройти контролируемое преобразование состояния. Они не должны без необходимости дублировать обычный процесс экспорта и импорта конфигурации.

### 3.9. Конфигурация между окружениями

Локальное окружение, тестовый сервер и production должны использовать согласованную конфигурацию, но могут отличаться настройками окружения.

Например, секреты, пароли, адреса баз данных и некоторые параметры окружения не следует хранить в публичном репозитории.

Для таких настроек применяют `settings.php`, переменные окружения и соответствующие механизмы управления секретами.

При этом нужно разделять:

- Настройки приложения, которые должны контролироваться через конфигурацию.
    
- Секреты и параметры инфраструктуры, которые должны задаваться безопасно на конкретном окружении.
    

### 3.10. Типичные ошибки

- Менять конфигурацию на production без переноса изменений в Git.
    
- Считать, что `config/install` обновляет существующие сайты.
    
- Игнорировать зависимости YAML-файлов.
    
- Удалять конфигурационные объекты без проверки ссылок.
    
- Путать контент с конфигурацией.
    
- Использовать update hooks вместо обычного экспорта там, где это не требуется.
    
- Импортировать конфигурацию без проверки изменений.
    
- Хранить секреты в репозитории вместе с обычной конфигурацией.

## Блок 4. Services and Dependency Injection

### 4.1. Что такое Service

Service — это объект, который предоставляет определённую функциональность и может использоваться разными компонентами Drupal.

Например, приложению может понадобиться отправить электронное письмо, загрузить сущность, получить текущего пользователя или записать сообщение в журнал. Вместо того чтобы реализовывать эту логику в каждом классе отдельно, Drupal предоставляет сервисы.

Примеры сервисов ядра:

- `entity_type.manager` — работа с типами сущностей и их хранилищами.
    
- `current_user` — информация о текущем пользователе и его правах.
    
- `logger.factory` — создание логгеров для записи сообщений.
    
- `database` — доступ к соединению с базой данных.
    
- `cache.default` — доступ к стандартному кеш-хранилищу.
    
- `language_manager` — работа с языками.
    
- `config.factory` — работа с конфигурацией.
    
- `http_client` — HTTP-запросы к внешним системам.
    
- `request_stack` — доступ к текущему HTTP-запросу и стеку запросов.
    

Сервисы обычно регистрируются в контейнере зависимостей и получают уникальные идентификаторы.

### 4.2. Service Container

Service Container — контейнер, который хранит определения сервисов и отвечает за их создание и предоставление зависимостей.

В Drupal используется компонент Dependency Injection Container из Symfony.

Когда классу требуется сервис, контейнер может создать нужный объект, передать ему необходимые зависимости и предоставить его вызывающему компоненту.

Например, контроллеру нужны менеджер сущностей и логгер. Вместо самостоятельного создания этих объектов контроллер получает их извне.

Основные преимущества:

- Повторное использование компонентов.
    
- Централизованное управление зависимостями.
    
- Упрощение тестирования.
    
- Снижение связанности классов.
    
- Возможность заменять реализации зависимостей.
    

Обычно сервисы используются повторно в пределах жизненного цикла контейнера. Однако не следует считать, что абсолютно каждый сервис является глобальным singleton на протяжении всей работы PHP-процесса: поведение зависит от определения сервиса и окружения.

### 4.3. Dependency Injection

Dependency Injection (DI) — принцип, при котором объект получает необходимые ему зависимости извне, а не создаёт их самостоятельно.

Без DI класс может напрямую обращаться к глобальному контейнеру:

```php
$storage = \Drupal::entityTypeManager()
  ->getStorage('node');
```

Такой код работает в подходящем контексте Drupal, но создаёт прямую зависимость класса от глобального статического API.

При использовании DI зависимость передаётся через конструктор:

```php
<?php

namespace Drupal\example;

use Drupal\Core\Entity\EntityTypeManagerInterface;

final class TaskManager {

  public function __construct(
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {}

  public function loadTask(int $id): ?\Drupal\node\NodeInterface {
    $entity = $this->entityTypeManager
      ->getStorage('node')
      ->load($id);

    return $entity instanceof \Drupal\node\NodeInterface
      && $entity->bundle() === 'task'
      ? $entity
      : NULL;
  }

}
```

В этом примере класс получает `EntityTypeManagerInterface` через конструктор. Он не должен самостоятельно создавать менеджер сущностей.

DI делает зависимости явными и позволяет в тестах передавать подменную реализацию интерфейса.

### 4.4. Регистрация собственного сервиса

Собственные сервисы регистрируются в файле `example.services.yml` внутри модуля.

Пример:

```php
services:
  example.task_manager:
    class: Drupal\example\TaskManager
    arguments:
      - '@entity_type.manager'
```

Здесь:

- `example.task_manager` — идентификатор сервиса.
    
- `class` — PHP-класс, реализующий сервис.
    
- `arguments` — зависимости, передаваемые конструктору.
    
- `@entity_type.manager` — ссылка на существующий сервис контейнера.
    

После регистрации сервис можно получить из контейнера, но в обычном коде приложения предпочтительно внедрять его в потребляющий класс.

Например, другой сервис может получить `example.task_manager` через собственный конструктор.

### 4.5. Dependency Injection в контроллерах

Контроллеры Drupal часто получают сервисы через статический метод `create()`.

Для этого используется `ContainerInjectionInterface` или соответствующая реализация в базовом классе контроллера.

Пример:

```php
<?php

namespace Drupal\example\Controller;

use Drupal\Core\Controller\ControllerBase;
use Drupal\Core\Entity\EntityTypeManagerInterface;
use Symfony\Component\DependencyInjection\ContainerInterface;

final class TaskController extends ControllerBase {

  public function __construct(
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {}

  public static function create(ContainerInterface $container): static {
    return new static(
      $container->get('entity_type.manager'),
    );
  }

  public function view(int $node): array {
    $task = $this->entityTypeManager
      ->getStorage('node')
      ->load($node);

    if (!$task || $task->bundle() !== 'task') {
      return [
        '#markup' => $this->t('Task not found.'),
      ];
    }

    return [
      '#type' => 'item',
      '#title' => $task->label(),
    ];
  }

}
```

Это демонстрация DI, а не законченный production-контроллер. В реальном маршруте предпочтительно использовать корректные требования доступа и параметрический конвертер сущностей, а не самостоятельно загружать сущность и возвращать сообщение об отсутствии.

Метод `create()` используется Drupal для создания экземпляра класса с необходимыми зависимостями.

### 4.6. Dependency Injection в плагинах

Плагины Drupal создаются через Plugin Manager. Поэтому их внедрение зависимостей отличается от обычных сервисов.

Многие плагины используют `ContainerFactoryPluginInterface`, который позволяет создавать экземпляры плагинов через контейнер.

Пример структуры:

```php
<?php

namespace Drupal\example\Plugin\Block;

use Drupal\Core\Block\BlockBase;
use Drupal\Core\Plugin\ContainerFactoryPluginInterface;
use Drupal\Core\Entity\EntityTypeManagerInterface;
use Symfony\Component\DependencyInjection\ContainerInterface;

/**
 * Provides a task summary block.
 *
 * @Block(
 *   id = "example_task_summary",
 *   admin_label = @Translation("Task summary")
 * )
 */
final class TaskSummaryBlock extends BlockBase implements ContainerFactoryPluginInterface {

  public function __construct(
    array $configuration,
    $plugin_id,
    $plugin_definition,
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {
    parent::__construct(
      $configuration,
      $plugin_id,
      $plugin_definition,
    );
  }

  public static function create(
    ContainerInterface $container,
    array $configuration,
    $plugin_id,
    $plugin_definition,
  ): static {
    return new static(
      $configuration,
      $plugin_id,
      $plugin_definition,
      $container->get('entity_type.manager'),
    );
  }

  public function build(): array {
    return [
      '#markup' => $this->t('Task summary'),
    ];
  }

}
```

Пример показывает структуру внедрения зависимости. Сам блок пока не загружает задачи, поэтому сервис в нём фактически не используется.

Важно: нельзя просто добавить произвольный параметр в конструктор плагина и ожидать, что Plugin Manager автоматически передаст сервис. Для соответствующего типа плагина нужно использовать предусмотренный механизм создания экземпляров.

### 4.7. Autowiring и явная регистрация

В современных PHP-приложениях, включая проекты на Symfony, часто применяется autowiring — автоматическое определение зависимостей по типам аргументов.

В Drupal поддержка и удобство autowiring зависят от способа регистрации сервиса и используемой инфраструктуры.

Явная регистрация через `services.yml` делает зависимости очевидными:

```php
services:
  example.task_manager:
    class: Drupal\example\TaskManager
    arguments:
      - '@entity_type.manager'
```

Преимущество явной регистрации — понятный контроль над тем, какие зависимости передаются объекту.

Не следует полагаться на автоматическое разрешение любой зависимости только потому, что она указана в type declaration конструктора. Необходимо учитывать правила контейнера Drupal.

### 4.8. Почему DI улучшает тестируемость

Если класс самостоятельно обращается к глобальному контейнеру, его сложнее изолированно тестировать.

Если зависимость передаётся через конструктор, в тест можно передать mock или stub.

Например, сервис, работающий с Entity Storage, можно тестировать с подменным `EntityTypeManagerInterface`, чтобы проверить логику без настоящей базы данных.

DI не означает, что тесты всегда должны использовать моки. Для проверки реального взаимодействия с Drupal API могут быть полезнее Kernel tests или Functional tests.

### 4.9. Когда не следует создавать сервис

Не каждую функцию нужно превращать в отдельный сервис.

Сервис оправдан, когда логика:

- Используется в нескольких местах.
    
- Имеет самостоятельную ответственность.
    
- Требует внедрения зависимостей.
    
- Должна быть изолированно протестирована.
    
- Представляет отдельную бизнес-операцию.
    

Для небольшой локальной операции отдельный сервис может только усложнить структуру проекта.

### 4.10. Типичные ошибки

- Использовать `\Drupal::service()` повсюду вместо DI.
    
- Создавать сервисы с чрезмерным количеством обязанностей.
    
- Передавать зависимости через сеттеры без необходимости.
    
- Забывать зарегистрировать собственный сервис.
    
- Неправильно передавать зависимости в конструкторы плагинов.
    
- Зависеть от конкретных реализаций там, где достаточно интерфейса.
    
- Считать, что все объекты Drupal создаются одинаковым способом.

## Блок 5. Drupal Performance & Scalability

### 5.1. Производительность и масштабирование

**Performance** — скорость выполнения операций и обработки запросов при определённой нагрузке.

**Scalability** — способность системы увеличивать пропускную способность и обрабатывать растущую нагрузку.

Сайт может быть быстрым при небольшом количестве посетителей, но работать медленно при одновременных запросах. Поэтому производительность и масштабирование связаны, но не являются одним и тем же.

Основные источники проблем производительности:

- Избыточные запросы к базе данных.
    
- Повторная загрузка одних и тех же сущностей.
    
- Неправильное кеширование.
    
- Тяжёлые операции при каждом HTTP-запросе.
    
- Большие render arrays и сложный рендеринг.
    
- Вызовы внешних API.
    
- Неэффективные индексы.
    
- Длительные фоновые операции, выполняемые синхронно.
    

Начинать оптимизацию нужно с измерений, а не с предположений.

### 5.2. Cache API

Drupal использует несколько уровней кеширования.

**Internal Page Cache** — кеширует полные ответы страниц для подходящих анонимных запросов.

**Dynamic Page Cache** — кеширует страницы и их динамические части с учётом контекста и правил кешируемости. Он полезен и для аутентифицированных пользователей.

**Render Cache** — кеширует результаты рендеринга отдельных компонентов, если они поддерживают кеширование.

Эти механизмы дополняют друг друга.

Кеширование уменьшает повторные вычисления, загрузки сущностей и рендеринг, но не исправляет архитектурные проблемы автоматически.

### 5.3. Cache contexts

Cache context описывает, от какого контекста зависит результат рендеринга.

Например, если блок отображает разный текст в зависимости от роли пользователя, его кеширование должно учитывать соответствующее различие.

Примеры контекстов:

- `user` — текущий пользователь.
    
- `user.roles` — роли пользователя.
    
- `languages:language_interface` — язык интерфейса.
    
- `languages:language_content` — язык содержимого.
    
- `url.path` — путь URL.
    
- `url.query_args` — параметры запроса.
    

Пример render array:

```php
return [
  '#markup' => $message,
  '#cache' => [
    'contexts' => [
      'user.roles',
      'languages:language_interface',
    ],
  ],
];
```

Этот пример подходит, если результат действительно зависит от ролей и языка интерфейса.

Не следует добавлять контексты без необходимости: большое количество вариантов кеша снижает его эффективность.

### 5.4. Cache tags

Cache tags описывают, какие данные влияют на кешируемый результат.

Например, блок отображает заголовок задачи. Если задача изменяется, соответствующий кеш должен быть инвалидирован.

Для этого используются теги кеширования, связанные с сущностями и другими кешируемыми объектами.

Упрощённый пример:

```php
return [
  '#markup' => $task->label(),
  '#cache' => [
    'tags' => $task->getCacheTags(),
  ],
];
```

Здесь кешируемый вывод связан с тегами сущности задачи.

При изменении или удалении сущности Drupal может инвалидировать кеш, связанный с её тегами.

Cache tags отвечают за зависимость от данных, а не за вариации результата по пользователю или языку.

### 5.5. Cache max-age

Cache max-age определяет максимальное время жизни кешируемого результата в секундах.

Например:

```php
return [
  '#markup' => $message,
  '#cache' => [
    'max-age' => 3600,
  ],
];
```

Здесь задан максимальный срок кеширования в один час.

Значение `0` означает, что результат не должен кешироваться. Значение `Cache::PERMANENT` обозначает отсутствие временного ограничения, но не запрещает инвалидацию по тегам.

Даже при большом max-age кеш может быть инвалидирован раньше, если изменятся данные, от которых зависит результат.

### 5.6. Cacheability и cache bubbling

Cacheability — свойства объекта, определяющие, как его можно кешировать.

Основные составляющие:

- Cache contexts.
    
- Cache tags.
    
- Cache max-age.
    

Cache bubbling — распространение свойств кешируемости от вложенных элементов к родительским элементам при построении результата рендеринга.

Например, блок включает данные задачи, которые зависят от текущего языка и имеют определённые cache tags. Эти свойства должны учитываться в итоговом рендеринге страницы.

Если компонент возвращает динамические данные без корректных метаданных кеша, возможна выдача устаревшей или персонализированной информации другому пользователю.

Для объектов доступа Drupal также предоставляет cacheability metadata. Если доступ к сущности зависит от определённых условий, кешируемость результата проверки доступа должна учитываться при построении ответа.

### 5.7. Entity loading и N+1

N+1 query problem возникает, когда приложение сначала получает список сущностей, а затем выполняет отдельный запрос для каждой сущности.

Например, код получает 100 задач, а затем отдельно загружает проект для каждой задачи. В результате число запросов может существенно увеличиться.

Проблему можно уменьшить с помощью:

- Entity queries для получения идентификаторов.
    
- Загрузки нескольких сущностей через подходящие методы storage.
    
- Предварительной загрузки связанных сущностей.
    
- Использования Views или других механизмов, подходящих для задачи.
    
- Кеширования повторно используемых данных.
    

Необходимо измерять реальные SQL-запросы и время их выполнения: не каждая последовательность обращений автоматически является серьёзной проблемой.

### 5.8. Database indexes

Индексы помогают базе данных находить строки без полного просмотра таблицы, если запрос может эффективно использовать соответствующий индекс.

Они особенно важны для часто используемых условий фильтрации, сортировки и соединения таблиц.

Однако индексы не являются бесплатными:

- Они занимают дополнительное место.
    
- Увеличивают стоимость операций записи.
    
- Требуют корректного выбора полей и порядка колонок.
    
- Не гарантируют ускорение любого запроса.
    

При проблемах производительности нужно анализировать SQL-запросы и планы выполнения, а не добавлять индексы случайным образом.

### 5.9. BigPipe и placeholders

BigPipe позволяет отправлять часть HTML-страницы раньше, а отдельные динамические участки доставлять позднее.

Например, основная часть страницы может быть готова быстро, тогда как персонализированный блок требует дополнительной обработки.

Placeholders позволяют отложить рендеринг отдельных элементов, что помогает уменьшить задержку до получения первой части страницы.

Эти механизмы не ускоряют автоматически каждую операцию и не заменяют кеширование или оптимизацию запросов. Их эффективность зависит от структуры страницы и того, какие части можно безопасно обрабатывать отдельно.

### 5.10. PHP OPcache, Redis и CDN

**OPcache** хранит скомпилированный байткод PHP, уменьшая необходимость повторной компиляции файлов.

**Redis** может использоваться как внешнее кеш-хранилище и для других задач, поддерживаемых соответствующей интеграцией.

**CDN** распределяет статические ресурсы и, при соответствующей конфигурации, кешируемые ответы ближе к посетителям.

**Reverse proxy** может кешировать HTTP-ответы перед приложением, уменьшая число запросов, доходящих до PHP.

Это разные уровни инфраструктуры. Установка Redis или CDN сама по себе не гарантирует ускорения: необходимо корректно настроить кеширование, инвалидацию, безопасность и поведение приложения.

### 5.11. Scalability

Горизонтальное масштабирование предполагает добавление нескольких экземпляров приложения для обработки нагрузки.

Для Drupal при этом важно учитывать:

- Общую или согласованную базу данных.
    
- Доступность файлов и загруженных ресурсов.
    
- Общие кеши и механизмы блокировок, если они необходимы.
    
- Согласованную конфигурацию на всех экземплярах.
    
- Выполнение cron и фоновых задач.
    
- Корректное хранение сессий.
    
- Ограничения внешних API и базы данных.
    

Если два экземпляра приложения независимо обрабатывают одну и ту же задачу, возможны дублирование операций и конфликты.

### 5.12. Типичные ошибки

- Отключать кеширование вместо устранения его неправильной настройки.
    
- Забывать cache tags и contexts.
    
- Использовать `max-age` как единственный механизм инвалидации.
    
- Создавать N+1 запросы при работе с сущностями.
    
- Добавлять индексы без анализа SQL.
    
- Выполнять тяжёлую обработку в HTTP-запросе.
    
- Масштабировать PHP-приложение, игнорируя ограничения базы данных.
    
- Кешировать персональные данные без корректных контекстов и правил доступа.

## Блок 6. Testing

### 6.1. Зачем нужны тесты

Тесты проверяют, что код выполняет ожидаемые действия и не ломает существующую функциональность после изменений.

В Drupal тестирование особенно важно, потому что модули тесно взаимодействуют с Entity API, сервисами, маршрутизацией, конфигурацией, доступом и рендерингом.

Тесты помогают обнаруживать:

- Ошибки бизнес-логики.
    
- Нарушения прав доступа.
    
- Проблемы интеграции с базой данных.
    
- Ошибки конфигурации.
    
- Неправильное поведение маршрутов и форм.
    
- Регрессии после обновления кода.
    

### 6.2. Unit tests

Unit tests проверяют небольшую часть кода изолированно от полноценной установки Drupal.

Обычно тестируется один класс или отдельный метод, а внешние зависимости заменяются mocks или stubs.

В Drupal unit tests часто наследуются от `UnitTestCase`.

Пример:

```php
<?php

namespace Drupal\Tests\example\Unit;

use Drupal\Tests\UnitTestCase;

final class TaskTitleTest extends UnitTestCase {

  public function testTitleIsFormatted(): void {
    $title = 'Prepare interview notes';

    self::assertSame(
      'Task: Prepare interview notes',
      'Task: ' . $title,
    );
  }

}
```

Это изолированный пример PHP-логики. Он не загружает Drupal и не проверяет Entity API.

Unit tests обычно быстрые и подходят для проверки преобразований, вычислений и логики, которую можно отделить от инфраструктуры.

### 6.3. Kernel tests

Kernel tests запускают значительную часть инфраструктуры Drupal, включая контейнер сервисов, систему сущностей и базу данных тестового окружения.

Они подходят для проверки взаимодействия нескольких компонентов без запуска полноценного браузерного сценария.

В Drupal такие тесты обычно наследуются от `KernelTestBase`.

Применение:

- Создание и загрузка сущностей.
    
- Работа с сервисами.
    
- Проверка hooks и событий.
    
- Проверка конфигурации.
    
- Тестирование интеграции с базой данных.
    

Для теста необходимо установить нужные модули и подготовить необходимые схемы и конфигурацию.

### 6.4. Functional tests

Functional tests проверяют поведение сайта через HTTP и браузероподобный механизм тестирования Drupal.

Они обычно наследуются от `BrowserTestBase`.

Такие тесты позволяют:

- Создавать пользователей и назначать роли.
    
- Входить в систему.
    
- Открывать страницы.
    
- Отправлять формы.
    
- Проверять редиректы и сообщения.
    
- Проверять доступ к маршрутам.
    
- Проверять результат пользовательских операций.
    

Functional tests полезны для проверки сценариев, которые затрагивают сразу несколько уровней приложения.

### 6.5. FunctionalJavascript tests

FunctionalJavascript tests предназначены для проверки поведения, требующего выполнения JavaScript в браузерном окружении.

Они нужны, если функциональность зависит от клиентского JavaScript, динамического взаимодействия или поведения браузера.

Такие тесты обычно сложнее и медленнее обычных functional tests.

Для обычной серверной логики нет необходимости использовать браузерный JavaScript-тест, если её можно проверить на более простом уровне.

### 6.6. Пирамида тестирования

В типичном проекте полезно иметь:

- Много быстрых unit tests.
    
- Достаточное количество kernel tests для интеграции компонентов.
    
- Functional tests для важных пользовательских сценариев.
    
- Ограниченное число более тяжёлых browser-based tests.
    

Это не жёсткое требование по количеству. Соотношение зависит от архитектуры проекта.

Главная цель — проверять каждую функциональность на самом простом уровне, который действительно подтверждает её корректность.

### 6.7. Mocks и stubs

Mock — тестовый объект, который позволяет задавать ожидаемые вызовы методов и проверять взаимодействие с зависимостью.

Stub — объект, который возвращает заранее заданные значения.

Например, сервис отправки уведомлений можно подменить, чтобы тест не отправлял настоящие письма.

Но чрезмерное использование моков может привести к тестам, которые проверяют только детали реализации, а не фактическое поведение приложения.

Если важно проверить интеграцию с Drupal API, лучше использовать kernel или functional test.

### 6.8. Тестирование доступа

Проверка доступа — одна из наиболее важных областей тестирования Drupal.

Недостаточно проверить, что администратор может выполнить операцию. Необходимо проверить также пользователя с ограниченными правами.

Например, для системы задач можно тестировать:

- Администратор может редактировать задачу.
    
- Менеджер проекта может выполнять разрешённые операции.
    
- Обычный пользователь не может изменять чужие задачи.
    
- Анонимный пользователь не может получить закрытые данные.
    
- Недоступная сущность не раскрывается через API.
    

Проверки должны учитывать как route access, так и entity access, когда оба уровня применимы.

### 6.9. Fixtures и тестовые данные

Fixtures — заранее подготовленные тестовые данные.

В Drupal тестовые сущности часто создаются непосредственно в тесте, чтобы не зависеть от содержимого конкретной базы данных.

Хорошие тестовые данные должны быть:

- Детерминированными.
    
- Независимыми от случайного состояния окружения.
    
- Минимальными, но достаточными.
    
- Понятными по назначению.
    
- Изолированными между тестами.
    

Например, для тестирования workflow задач нужно создать задачи с известными статусами, а не использовать случайные материалы, которые уже существуют на сайте.

### 6.10. Regression testing

Regression testing проверяет, что существующая функциональность продолжает работать после изменения кода.

Например, изменение доступа к TimeLog не должно случайно запретить менеджеру создавать записи времени, если это разрешено требованиями.

Регрессионные тесты особенно полезны при изменениях:

- Permissions и access handlers.
    
- Workflow.
    
- Entity definitions.
    
- Configuration.
    
- API endpoints.
    
- Миграций.
    
- Кеширования.
    

Автоматические тесты могут запускаться в CI перед слиянием изменений.

### 6.11. Типичные ошибки

- Проверять только успешный сценарий.
    
- Использовать слишком много mocks и не проверять интеграцию.
    
- Писать тесты, зависящие от существующих данных сайта.
    
- Не проверять права доступа.
    
- Делать functional tests для каждой мелкой функции.
    
- Игнорировать нестабильные тесты.
    
- Проверять внутренние детали реализации вместо наблюдаемого поведения.
    
- Не запускать тесты после изменения конфигурации или схемы сущностей.

# Block 7 — Drupal Security

## 1. Основные принципы безопасности в Drupal

Безопасность в Drupal строится на нескольких уровнях: проверке прав доступа, защите от CSRF и XSS, безопасной обработке пользовательского ввода, использовании подготовленных запросов и правильной настройке ролей.

Основное правило: **нельзя доверять пользовательским данным**, даже если они пришли из формы Drupal или от авторизованного пользователя.

Основные механизмы безопасности:

- **Authentication** — проверка личности пользователя.
    
- **Authorization** — проверка того, разрешено ли пользователю выполнять действие.
    
- **Access control** — управление доступом к сущностям, маршрутам и операциям.
    
- **Input validation** — проверка корректности входных данных.
    
- **Output escaping** — безопасный вывод данных, предотвращающий XSS.
    
- **CSRF protection** — защита от подделки межсайтовых запросов.
    
- **SQL injection protection** — защита от внедрения SQL-кода.
    

## 2. Permissions и Roles

Permission определяет, какое действие разрешено выполнять пользователю. Role — это набор разрешений.

Например, в DrupalJira можно создать роли:

- Project Manager — создание и редактирование проектов и задач.
    
- Authenticated User — просмотр доступных проектов и работа с собственными задачами.
    
- Administrator — управление всеми аспектами сайта.
    

Разрешения определяются в административном интерфейсе Drupal или в файле `*.permissions.yml`.

Пример `drupaljira_board.permissions.yml`:

```
manage project tasks:
  title: 'Manage project tasks'
  description: 'Create and manage tasks in projects.'
  restrict access: true
```

Проверить разрешение в коде можно через сервис `current_user`:

```
$current_user = \Drupal::currentUser();

if ($current_user->hasPermission('manage project tasks')) {
  // Пользователю разрешено управлять задачами.
}
```

В классе предпочтительнее использовать Dependency Injection, а не статический вызов `\Drupal`.

Важно: наличие разрешения на действие не означает автоматического доступа ко всем сущностям. Например, пользователь может иметь право редактировать задачи, но не иметь права редактировать конкретную задачу из чужого проекта.

## 3. Access Control

Drupal предоставляет несколько уровней проверки доступа.

### Доступ к маршрутам

Маршрут может требовать определённое разрешение:

```
drupaljira_board.task_list:
  path: '/tasks'
  defaults:
    _controller: '\Drupal\drupaljira_board\Controller\TaskController::list'
    _title: 'Tasks'
  requirements:
    _permission: 'access content'
```

Drupal проверяет разрешение до вызова контроллера.

Для более сложной проверки можно использовать собственный access checker или требование `_custom_access`.

### Доступ к сущностям

Entity Access API позволяет проверить, может ли пользователь просматривать, редактировать или удалять конкретную сущность.

```
$access = $node->access('update', NULL, TRUE);

if ($access->isAllowed()) {
  // Пользователю разрешено редактировать материал.
}
```

Третий аргумент `TRUE` просит вернуть объект `AccessResultInterface`, а не простое логическое значение. Такой объект может содержать информацию о cacheability.

Это важно, поскольку результат доступа иногда зависит от пользователя, ролей, состояния сущности или других условий.

### Почему нельзя полагаться только на интерфейс

Если кнопка редактирования скрыта в интерфейсе, это не гарантирует защиту. Пользователь может напрямую отправить HTTP-запрос на соответствующий маршрут.

Поэтому проверка должна выполняться на сервере — на уровне маршрута, сущности или бизнес-логики.

## 4. CSRF Protection

CSRF (Cross-Site Request Forgery) — атака, при которой злоумышленник пытается заставить браузер авторизованного пользователя отправить нежелательный запрос.

Drupal предоставляет механизмы защиты для форм и маршрутов.

Например, для пользовательского маршрута, изменяющего данные, можно потребовать CSRF-токен:

```
drupaljira_board.update_status:
  path: '/task/{node}/status'
  defaults:
    _controller: '\Drupal\drupaljira_board\Controller\TaskController::updateStatus'
  requirements:
    _permission: 'access content'
    _csrf_token: 'TRUE'
  methods: [POST]
  options:
    parameters:
      node:
        type: entity:node
```

При таком подходе клиент должен передать корректный токен в соответствии с механизмом Drupal для данного маршрута.

Для стандартных Drupal Form API-форм защита от CSRF обычно реализуется автоматически. Для пользовательских AJAX- и REST-подобных маршрутов необходимо отдельно проверить подходящий механизм защиты.

**Важно:** CSRF-токен не заменяет проверку разрешений. Нужно одновременно убедиться, что запрос легитимен и что пользователь имеет право выполнять действие.

## 5. XSS Protection

XSS (Cross-Site Scripting) возникает, когда пользовательские данные выводятся как исполняемый HTML или JavaScript.

Например, пользователь вводит:

```
<script>alert('XSS')</script>
```

Если вывести эту строку как доверенный HTML, браузер может выполнить скрипт.

В Twig нужно использовать автоматическое экранирование:

```
<div class="task-title">
  {{ task_title }}
</div>
```

Twig автоматически экранирует обычные строковые значения в HTML-контексте.

Не следует без необходимости отключать экранирование:

```
{{ task_title|raw }}
```

Фильтр `raw` допустим только для содержимого, безопасность которого гарантирована отдельным способом.

В PHP для обычного HTML-вывода можно использовать:

```
use Drupal\Component\Utility\Html;

$safe_title = Html::escape($title);
```

В Drupal предпочтительно использовать Render API и корректные render arrays, чтобы система могла правильно обработать вывод, экранирование и кэширование.

## 6. SQL Injection

SQL injection — внедрение SQL-кода через данные, которые приложение использует в запросе.

Опасный подход — конкатенация пользовательского значения в SQL:

```
// Не делайте так.
$query = "SELECT uid FROM users_field_data WHERE name = '$username'";
```

Безопасный подход — параметризованные запросы:

```
$connection = \Drupal::database();

$result = $connection->select('users_field_data', 'u')
  ->fields('u', ['uid'])
  ->condition('name', $username)
  ->execute()
  ->fetchField();
```

Значение передаётся как параметр условия, а не вставляется непосредственно в SQL-код.

В обычном Drupal-приложении для работы с контентом и пользователями следует по возможности использовать Entity API, а не обращаться напрямую к таблицам базы данных.

## 7. Security Best Practices

- Применять принцип наименьших привилегий: выдавать только необходимые permissions.
    
- Проверять доступ к каждой сущности и операции.
    
- Не доверять значениям из URL, форм, API и JavaScript.
    
- Использовать Entity API и Database API вместо ручной работы с SQL.
    
- Не выводить пользовательский ввод как доверенный HTML.
    
- Использовать HTTPS.
    
- Не хранить пароли в открытом виде.
    
- Не оставлять отладочные маршруты и диагностические данные в production.
    
- Регулярно обновлять Drupal core и contrib-модули.
    
- Добавлять тесты на разрешённые и запрещённые операции.
    

## 8. Когда это применяется в DrupalJira

Предположим, обычный пользователь пытается изменить статус чужой задачи через `/task/123/status`.

Безопасная реализация должна проверить:

1. Что HTTP-метод соответствует операции, например `POST`.
    
2. Что запрос прошёл требуемую CSRF-проверку.
    
3. Что пользователь авторизован.
    
4. Что пользователь имеет право изменять именно эту задачу.
    
5. Что новый статус допустим для текущего workflow.
    
6. Что изменение сохраняется через корректный API Drupal.
    

Нельзя считать запрос безопасным только потому, что кнопка смены статуса отображается в интерфейсе лишь для менеджера.

# Block 8 — Drupal Multisite

## 1. Что такое Multisite

Drupal Multisite — это архитектура, которая позволяет обслуживать несколько отдельных Drupal-сайтов из одной кодовой базы.

Например, компания может иметь:

- `company.example.com` — основной сайт;
    
- `docs.example.com` — документацию;
    
- `support.example.com` — поддержку.
    

Эти сайты могут использовать общие версии Drupal core и модулей, но иметь разные настройки, контент, пользователей и базу данных.

Multisite не означает, что все сайты автоматически используют одну базу данных или один набор пользователей. Это зависит от конфигурации.

## 2. Как устроена структура Multisite

Типичная структура проекта:

```
web/
  core/
  modules/
  themes/
  sites/
    default/
      settings.php
    company.example.com/
      settings.php
    docs.example.com/
      settings.php
    support.example.com/
      settings.php
```

Каждый каталог сайта может содержать собственный `settings.php`, настройки подключения к базе данных и другие специфичные параметры.

При обработке запроса Drupal определяет, к какому сайту он относится, и загружает соответствующие настройки.

Например, сайт `docs.example.com` может использовать базу данных `docs_db`, а `support.example.com` — `support_db`.

При этом оба сайта могут использовать одни и те же файлы Drupal core и общие модули.

## 3. Что может быть общим, а что отдельным

|Компонент|Возможность совместного использования|
|---|---|
|Drupal core|Обычно общий|
|Установленные модули|Файлы могут быть общими|
|Темы|Файлы могут быть общими|
|Конфигурация сайта|Обычно отдельная|
|Контент|Обычно отдельный при разных БД|
|Пользователи|Зависит от структуры хранения и подключения|
|Файлы и загрузки|Зависит от настроек|
|Кэш|Зависит от конфигурации инфраструктуры|

Общая кодовая база упрощает обновление зависимостей, но повышает требования к тестированию: изменение общего модуля может повлиять на все сайты.

## 4. Настройка Multisite

В общих чертах процесс выглядит так:

1. Установить общую кодовую базу Drupal.
    
2. Создать каталоги для отдельных сайтов в `sites/`.
    
3. Настроить для каждого сайта `settings.php`.
    
4. Указать корректные подключения к базам данных.
    
5. Настроить веб-сервер так, чтобы домены направляли запросы в общий Drupal document root.
    
6. Установить каждый сайт и проверить работу модулей, тем и конфигурации.
    

Пример фрагмента `settings.php`:

```
$databases['default']['default'] = [
  'database' => 'docs_db',
  'username' => 'drupal_user',
  'password' => 'secret',
  'host' => 'database',
  'driver' => 'mysql',
  'prefix' => '',
];
```

Это лишь пример структуры настройки. Реальные секреты подключения не следует хранить в публичном репозитории.

## 5. Преимущества Multisite

- Общая кодовая база.
    
- Меньше дублирования модулей и тем.
    
- Возможность централизованно обновлять Drupal core.
    
- Удобство для группы связанных сайтов с похожим функционалом.
    

## 6. Недостатки и риски

- Обновление общего кода может затронуть все сайты.
    
- Требуется тщательно тестировать совместимость модулей.
    
- Возможны конфликты требований разных сайтов.
    
- Нужно отдельно планировать резервное копирование и восстановление.
    
- Ошибки в общей кодовой базе могут иметь большой радиус воздействия.
    
- Изоляция данных зависит от конфигурации и инфраструктуры.
    

Multisite не всегда является лучшим выбором. Если сайты имеют совершенно разные жизненные циклы, зависимости и требования безопасности, отдельные установки могут оказаться проще в сопровождении.

## 7. Multisite и Configuration Management

Каждый сайт может иметь собственный активный набор конфигурации. Например, на одном сайте используется одна тема и определённые типы материалов, а на другом — другая тема и другие настройки.

Нельзя предполагать, что экспорт конфигурации одного сайта автоматически подходит для всех остальных.

Перед импортом конфигурации нужно учитывать:

- наличие необходимых модулей;
    
- соответствие UUID сайта и конфигурационных объектов;
    
- зависимости между конфигурационными сущностями;
    
- различия между окружениями и отдельными сайтами.
    

## 8. Когда выбирать Multisite

Multisite подходит, когда несколько сайтов используют общую кодовую базу и имеют похожие требования к поддержке.

Если сайты должны независимо обновляться, использовать несовместимые версии модулей или иметь существенно разные процессы разработки, отдельные установки часто удобнее.

# Block 9 — Events API

## 1. Что такое Events API

Events API — механизм, который позволяет одному компоненту Drupal сообщать о событии, а другим компонентам реагировать на него.

Например, приложение может сообщить, что:

- сущность была загружена;
    
- пользователь вошёл в систему;
    
- произошла операция, на которую подписан обработчик;
    
- система выполнила определённое действие.
    

Компонент, который сообщает о событии, не обязан знать, какие другие компоненты на него реагируют.

Это уменьшает связанность между компонентами.

## 2. Основные понятия

- **Event** — объект, содержащий информацию о произошедшем событии.
    
- **Event dispatcher** — механизм, который отправляет событие обработчикам.
    
- **Event subscriber** — класс, подписанный на одно или несколько событий.
    
- **Event listener** — обработчик конкретного события.
    
- **Event name** — идентификатор события, по которому Drupal находит подписчиков.
    

В Drupal обработчики событий часто реализуются через сервисы.

## 3. Создание Event Subscriber

Допустим, модуль `drupaljira_board` должен реагировать на определённое событие.

Создадим файл:

`web/modules/custom/drupaljira_board/src/EventSubscriber/ExampleSubscriber.php`

```
<?php

namespace Drupal\drupaljira_board\EventSubscriber;

use Symfony\Component\EventDispatcher\EventSubscriberInterface;

final class ExampleSubscriber implements EventSubscriberInterface {

  /**
   * {@inheritdoc}
   */
  public static function getSubscribedEvents(): array {
    return [
      'example.event' => 'onExampleEvent',
    ];
  }

  /**
   * Handles the example event.
   */
  public function onExampleEvent(): void {
    // Выполнить нужную логику.
  }

}
```

Метод `getSubscribedEvents()` сообщает диспетчеру, на какие события подписан класс и какие методы следует вызвать.

В реальном проекте сигнатура обработчика должна соответствовать объекту события, который отправляет соответствующий код.

## 4. Регистрация подписчика как сервиса

Drupal должен знать о классе-подписчике. Для этого добавим описание в файл `drupaljira_board.services.yml`:

```
services:
  drupaljira_board.example_subscriber:
    class: Drupal\drupaljira_board\EventSubscriber\ExampleSubscriber
    tags:
      - { name: event_subscriber }
```

Тег `event_subscriber` позволяет Drupal обнаружить подписчика при сборке контейнера сервисов.

После добавления нового сервиса необходимо обновить кэш Drupal, чтобы изменения в определениях сервисов были обнаружены.

## 5. Отправка собственного события

Чтобы подписчик сработал, кто-то должен отправить соответствующее событие.

Для этого используется сервис `event_dispatcher`.

Упрощённый пример:

```
use Drupal\Component\EventDispatcher\Event;

$event = new Event();

\Drupal::service('event_dispatcher')
  ->dispatch($event, 'example.event');
```

Этот пример иллюстрирует сам механизм, но в настоящем модуле обычно создают собственный класс события с нужными данными и используют Dependency Injection вместо глобального вызова `\Drupal`.

Например, собственное событие может содержать объект задачи, старый статус и новый статус.

## 6. Передача данных через объект события

Если обработчику нужны дополнительные данные, их можно передать через собственный класс события.

Упрощённая структура:

```
namespace Drupal\drupaljira_board\Event;

use Drupal\node\NodeInterface;
use Symfony\Contracts\EventDispatcher\Event;

final class TaskStatusChangedEvent extends Event {

  public function __construct(
    private readonly NodeInterface $task,
    private readonly string $oldStatus,
    private readonly string $newStatus,
  ) {}

  public function getTask(): NodeInterface {
    return $this->task;
  }

  public function getOldStatus(): string {
    return $this->oldStatus;
  }

  public function getNewStatus(): string {
    return $this->newStatus;
  }

}
```

Теперь подписчик может получить задачу и сравнить предыдущий и новый статусы.

При использовании событий важно выбрать правильный момент отправки. Например, событие об изменении статуса после успешного сохранения не должно отправляться до того, как изменение действительно состоялось.

## 7. Events API и Hooks

Events API и Hooks позволяют расширять поведение Drupal, но работают по-разному.

|Events API|Hooks|
|---|---|
|Использует диспетчеризацию событий|Использует систему хуков Drupal|
|Часто реализуется через сервисы и подписчиков|Часто реализуется функциями с именами `hook_*`|
|Удобен для событийно-ориентированной архитектуры|Широко используется в существующем API Drupal|
|Событие обычно представлено объектом|Передача данных определяется сигнатурой конкретного хука|

Например, `hook_entity_presave()` позволяет модулю реагировать перед сохранением сущности.

```
function example_entity_presave(
  \Drupal\Core\Entity\EntityInterface $entity,
): void {
  // Выполнить проверку или подготовку данных.
}
```

Не нужно заменять все хуки событиями. Следует использовать тот механизм, который предоставляет нужную точку расширения в Drupal.

## 8. Events API и Queue API

Events API подходит для реакции на событие в процессе выполнения приложения.

Queue API предназначен для постановки задач в очередь и их обработки отдельно, обычно через cron или другой worker.

Например, при изменении статуса задачи можно:

1. Сохранить новый статус.
    
2. Отправить событие об изменении.
    
3. Подписчику поставить в очередь задачу отправки уведомления.
    
4. Отдельный worker отправит уведомление позднее.
    

Так основной запрос не обязан выполнять всю тяжёлую работу синхронно.

## 9. Когда применять Events API

Events API полезен, когда несколько компонентов должны реагировать на одно действие, а основной код не должен напрямую зависеть от всех этих компонентов.

Например, при изменении задачи в DrupalJira можно уведомлять подписчиков, записывать аудит или инициировать интеграцию с внешней системой.

Однако не стоит создавать собственное событие для каждого простого вызова. События наиболее полезны, когда они создают понятную точку расширения и действительно уменьшают связанность кода.

# Block 10 — Entity API

## 1. Что такое Entity API

Entity API — это один из основных API Drupal для работы с данными сайта. Он предоставляет единый способ создавать, загружать, изменять, сохранять и удалять сущности.

**Entity (сущность)** — объект Drupal, представляющий определённую единицу данных.

Примеры сущностей:

- Node — материал, например проект или задача.
    
- User — пользователь.
    
- Taxonomy term — термин таксономии.
    
- Media — медиаобъект.
    
- File — файл.
    
- Custom content entity — собственная сущность, созданная разработчиком.
    

Например, в DrupalJira проект и задача могут быть материалами (`node`) разных типов. При этом сам тип материала — `project` или `task` — определяет структуру конкретного материала, но оба используют одну систему сущностей Node.

Entity API позволяет работать с этими объектами без необходимости самостоятельно писать SQL-запросы к таблицам Drupal.

## 2. Entity Type и Bundle

Важно различать два понятия.

**Entity Type** определяет общий вид сущности и доступные для неё операции.

Например:

- `node` — материалы;
    
- `user` — пользователи;
    
- `taxonomy_term` — термины таксономии;
    
- `media` — медиаобъекты.
    

**Bundle** — подтип сущности, определяющий её конкретную структуру и назначение.

Например, у сущности `node` могут быть следующие bundles:

- `article`;
    
- `page`;
    
- `project`;
    
- `task`.
    

В DrupalJira `project` и `task` — это bundles типа `node`.

У них могут быть разные поля. У проекта может быть поле типа проекта, а у задачи — статус, исполнитель и оценка трудозатрат.

## 3. Content Entity и Configuration Entity

Drupal различает два основных вида сущностей.

### Content Entity

Content Entity предназначена преимущественно для хранения содержательных данных, которые создаются и изменяются в ходе работы сайта.

Примеры:

- Node;
    
- User;
    
- Media;
    
- Taxonomy term.
    

Такие сущности часто имеют поля, могут участвовать в системе прав доступа и поддерживать revisions.

### Configuration Entity

Configuration Entity предназначена для хранения конфигурации сайта.

Примеры:

- типы материалов;
    
- определения полей;
    
- Views;
    
- типы текстовых форматов;
    
- роли пользователей.
    

Конфигурационные сущности обычно экспортируются в YAML-файлы и управляются через Configuration Management.

Основное отличие: Content Entity хранит рабочие данные сайта, а Configuration Entity описывает, как сайт должен работать.

## 4. Загрузка сущностей

Для загрузки сущностей можно использовать Entity Storage API.

Например, загрузим материал по ID:

```
$node = \Drupal::entityTypeManager()
  ->getStorage('node')
  ->load(123);

if ($node !== NULL) {
  $title = $node->label();
}
```

Здесь:

- `entityTypeManager()` получает менеджер типов сущностей;
    
- `getStorage('node')` получает хранилище материалов;
    
- `load(123)` загружает материал с ID `123`;
    
- `label()` возвращает отображаемое название сущности.
    

В сервисах и контроллерах предпочтительно использовать Dependency Injection.

Например, можно внедрить `entity_type.manager` в конструктор класса, чтобы не обращаться к глобальному контейнеру через `\Drupal`.

## 5. Создание и сохранение сущности

Для создания нового материала используется метод `create()` хранилища.

```
$node = \Drupal::entityTypeManager()
  ->getStorage('node')
  ->create([
    'type' => 'task',
    'title' => 'Implement task workflow',
    'status' => 1,
  ]);

$node->save();
```

В этом примере создаётся материал типа `task`.

Поле `status` здесь обозначает статус публикации материала, а не пользовательское поле workflow. В DrupalJira поле `field_status` и состояние moderation workflow — отдельные механизмы, которые не следует путать со статусом публикации.

Перед сохранением необходимо проверить обязательные поля, права доступа и бизнес-правила приложения.

## 6. Работа с полями

Поля сущностей предоставляют доступ к данным.

Например, прочитаем поле статуса задачи:

```
$status = $node->get('field_status')->value;
```

Если поле допускает несколько значений, обращаться только к `value` может быть недостаточно. Для получения всех элементов поля используют его список значений.

Пример изменения поля:

```
$node->set('field_status', 'in_progress');
$node->save();
```

Значение должно соответствовать настройке поля и допустимым значениям списка.

Для Entity Reference поле содержит ссылку на другую сущность. Например, `field_project` у задачи может ссылаться на материал проекта.

```
$project = $node->get('field_project')->entity;
```

Если ссылка не заполнена или связанная сущность недоступна, результат может быть `NULL`. Поэтому при дальнейшей работе необходимо учитывать возможность отсутствующей ссылки.

## 7. Entity Query

Entity Query позволяет искать сущности по условиям без написания SQL.

Например, найдём задачи со статусом `in_progress`:

```
$ids = \Drupal::entityQuery('node')
  ->condition('type', 'task')
  ->condition('field_status', 'in_progress')
  ->accessCheck(TRUE)
  ->execute();
```

Результатом будет массив ID подходящих материалов.

`accessCheck(TRUE)` указывает, что при выполнении запроса должна учитываться проверка доступа.

В Drupal 10.2 и более поздних версиях, включая Drupal 11, для Entity Query нужно явно указывать режим проверки доступа. Использовать `accessCheck(FALSE)` следует только тогда, когда обход проверки доступа обоснован задачей и безопасность обеспечена другим способом.

Entity Query возвращает идентификаторы, а не полностью загруженные объекты. При необходимости объекты загружают через соответствующее хранилище.

## 8. Entity Access API

Entity API связан с системой доступа Drupal.

Например:

```
if ($node->access('view')) {
  // Пользователь может просматривать материал.
}
```

Для получения более подробного результата доступа:

```
$access = $node->access('update', NULL, TRUE);

if ($access->isAllowed()) {
  // Пользователь может редактировать материал.
}
```

Второй вариант позволяет получить объект результата доступа, содержащий также информацию о cacheability.

Проверка доступа особенно важна, когда разработчик создаёт собственные контроллеры, API endpoints или операции изменения сущностей.

## 9. Entity API и Revisions

Некоторые сущности поддерживают revisions — сохранение отдельных версий объекта.

Это позволяет хранить историю изменений и при необходимости возвращаться к предыдущим версиям.

Например, при изменении задачи можно создать новую revision, содержащую новый статус и информацию об изменении.

Однако не все сущности поддерживают revisions одинаковым образом. Нужно учитывать возможности конкретного entity type, его конфигурацию и используемые модули, например Content Moderation.

## 10. Entity API и Render API

Entity API отвечает за работу с данными, а Render API — за подготовку данных к отображению.

Например, контроллер может загрузить материал через Entity API, а затем передать его для рендеринга через render array.

```
return [
  '#type' => 'markup',
  '#markup' => $node->label(),
];
```

Этот пример упрощён. Для реального вывода материалов лучше использовать render arrays, view builders и механизмы отображения сущностей Drupal. Нельзя без необходимости вставлять непроверенные пользовательские данные в HTML.

При рендеринге Drupal также может учитывать кеширование, доступ и вложенные элементы render array.

## 11. Когда применять Entity API

Entity API следует использовать, когда необходимо:

- создавать и изменять материалы;
    
- загружать пользователей и медиаобъекты;
    
- получать значения полей;
    
- работать со ссылками между сущностями;
    
- искать материалы по условиям;
    
- проверять доступ к объектам;
    
- управлять revisions.
    

Главное преимущество Entity API — работа с данными через стандартную абстракцию Drupal вместо прямого взаимодействия с таблицами базы данных.

# Block 11 — Plugin API

## 1. Что такое Plugin API

Plugin API — механизм Drupal, позволяющий создавать взаимозаменяемые компоненты с определённым назначением.

Плагин реализует общий контракт, а Drupal обнаруживает его, создаёт экземпляр и использует в соответствующем контексте.

Например, плагины используются для:

- блоков;
    
- способов аутентификации;
    
- источников миграции;
    
- форматов полей;
    
- способов отображения;
    
- обработчиков действий и других расширяемых компонентов.
    

Основная идея: система работает с общим интерфейсом, а конкретные реализации могут различаться.

## 2. Plugin Manager

Plugin Manager — компонент, который отвечает за обнаружение и управление плагинами определённого типа.

Например, менеджер блоков знает, какие block plugins доступны, и предоставляет их Drupal для размещения на странице.

Плагины одного типа обычно имеют общую структуру и интерфейс, но различаются поведением и конфигурацией.

Разработчик редко должен вручную создавать экземпляры плагинов. Обычно их жизненным циклом управляет соответствующий Plugin Manager.

## 3. Plugin ID и Plugin Definition

**Plugin ID** — уникальный идентификатор конкретного плагина в рамках его типа.

**Plugin Definition** — описание плагина: его ID, название, категория, класс и другие метаданные.

Например, плагин блока может иметь ID `task_summary` и название `Task Summary`.

Определение помогает Drupal обнаружить плагин и представить его в административном интерфейсе.

## 4. Создание собственного Block Plugin

Допустим, нам нужен блок, который показывает краткую статистику задач.

Создадим файл:

`web/modules/custom/drupaljira_board/src/Plugin/Block/TaskSummaryBlock.php`

```
<?php

namespace Drupal\drupaljira_board\Plugin\Block;

use Drupal\Core\Block\BlockBase;

/**
 * Provides a task summary block.
 *
 * @Block(
 *   id = "task_summary",
 *   admin_label = @Translation("Task Summary"),
 *   category = @Translation("DrupalJira")
 * )
 */
final class TaskSummaryBlock extends BlockBase {

  /**
   * {@inheritdoc}
   */
  public function build(): array {
    return [
      '#markup' => $this->t('Task summary'),
    ];
  }

}
```

В этом примере:

- `@Block` — аннотация, описывающая плагин блока;
    
- `id` — идентификатор плагина;
    
- `admin_label` — название в административном интерфейсе;
    
- `category` — категория, к которой относится блок;
    
- `build()` — метод, возвращающий render array для отображения.
    

После добавления плагина может потребоваться очистить кэш Drupal, чтобы система обнаружила его определение.

## 5. Почему используется Render Array

Метод `build()` обычно возвращает render array, а не готовую HTML-строку.

Render array позволяет Drupal корректно обрабатывать вывод, включая:

- рендеринг;
    
- вложенные элементы;
    
- библиотеки CSS и JavaScript;
    
- cache contexts, tags и max-age;
    
- доступ к отображаемым данным.
    

Пример блока с вложенными элементами:

```
public function build(): array {
  return [
    '#theme' => 'item_list',
    '#items' => [
      $this->t('Backlog'),
      $this->t('In progress'),
      $this->t('Done'),
    ],
  ];
}
```

Для реальной статистики значения следует получать из подходящего сервиса или Entity Query, а не оставлять статическими.

## 6. Dependency Injection в плагинах

Плагинам иногда требуются сервисы, например Entity Type Manager или Current User.

В Drupal нельзя бездумно добавлять обычный конструктор с дополнительными аргументами: система должна знать, как создать экземпляр плагина.

Для плагинов, которым нужны сервисы, обычно реализуют `ContainerFactoryPluginInterface` и метод `create()`.

Упрощённый пример:

```
use Drupal\Core\Block\BlockBase;
use Drupal\Core\Plugin\ContainerFactoryPluginInterface;
use Drupal\Core\Entity\EntityTypeManagerInterface;
use Symfony\Component\DependencyInjection\ContainerInterface;

final class TaskSummaryBlock extends BlockBase implements ContainerFactoryPluginInterface {

  public function __construct(
    array $configuration,
    $plugin_id,
    $plugin_definition,
    private readonly EntityTypeManagerInterface $entityTypeManager,
  ) {
    parent::__construct($configuration, $plugin_id, $plugin_definition);
  }

  public static function create(
    ContainerInterface $container,
    array $configuration,
    $plugin_id,
    $plugin_definition,
  ): static {
    return new static(
      $configuration,
      $plugin_id,
      $plugin_definition,
      $container->get('entity_type.manager'),
    );
  }

  public function build(): array {
    return [
      '#markup' => $this->t('Task summary'),
    ];
  }

}
```

Пример показывает основную идею: Drupal передаёт зависимости через контейнер сервисов.

При использовании в реальном модуле нужно также проверить соответствие сигнатур интерфейсам установленной версии Drupal и стандартам типизации проекта.

## 7. Plugin API и Hooks

Hooks и плагины решают разные задачи.

Hooks позволяют модулю вмешиваться в определённые точки расширения Drupal.

Plugins позволяют создавать отдельные реализации известного типа компонента, которыми управляет Plugin Manager.

Например:

- `hook_entity_presave()` — реакция на сохранение сущности;
    
- Block Plugin — отдельный блок с собственным поведением;
    
- Migration Plugin — реализация определённого источника или обработчика миграции.
    

Не всякое расширение Drupal должно быть плагином. Нужно использовать механизм, который соответствует задаче.

## 8. Plugins с конфигурацией

Некоторые плагины могут получать конфигурацию.

Например, блок может иметь настройку, определяющую, сколько задач показывать. Для этого плагин может переопределять методы конфигурации и форму настроек.

Сама конфигурация экземпляра плагина и определение плагина — не одно и то же:

- определение описывает доступный тип плагина;
    
- конфигурация экземпляра задаёт параметры конкретного использования.
    

## 9. Когда применять Plugin API

Plugin API полезен, когда требуется создать компонент, который Drupal сможет обнаруживать, конфигурировать и использовать как одну из нескольких возможных реализаций.

Например, собственный блок статистики задач логично оформить как Block Plugin, а общую логику подсчёта задач вынести в отдельный сервис.

Так разделяются обязанности: плагин отвечает за интеграцию с системой блоков, а сервис — за бизнес-логику.

# Block 12 — Batch API, Cron API и Queue API

## 1. Зачем нужны фоновые и длительные операции

Не все задачи должны выполняться целиком в рамках одного HTTP-запроса.

Например:

- импортировать тысячи записей;
    
- обработать большой набор материалов;
    
- отправить уведомления множеству пользователей;
    
- удалить устаревшие данные;
    
- синхронизировать контент с внешней системой.
    

Если выполнять всё за один запрос, операция может занять слишком много времени, превысить лимиты PHP или создать высокую нагрузку на сервер.

Drupal предоставляет несколько механизмов для таких сценариев: Batch API, Cron API и Queue API.

Они решают связанные, но разные задачи.

## 2. Batch API

Batch API позволяет разбить длительную операцию на несколько небольших шагов, выполняемых последовательно.

Например, администратор запускает массовое обновление задач. Вместо обработки всех материалов за один запрос Drupal выполняет операцию порциями и показывает прогресс.

Batch API часто используется для:

- массовых обновлений;
    
- обработки большого числа сущностей;
    
- административных операций;
    
- импорта данных с отображением прогресса.
    

### Пример Batch API

```
$batch = [
  'title' => t('Updating tasks'),
  'operations' => [
    [
      '\Drupal\drupaljira_board\Batch\TaskBatch::process',
      [],
    ],
  ],
  'finished' => '\Drupal\drupaljira_board\Batch\TaskBatch::finished',
];

batch_set($batch);
```

В реальном модуле функции и классы должны существовать, а операция должна обрабатывать ограниченную порцию данных.

Например, обработчик может за один вызов обновлять 50 задач, а затем сохранять прогресс, чтобы следующий шаг продолжил работу.

### Операция и завершение

Batch API использует операции и callback, который сообщает о завершении всей обработки.

Операция должна корректно обновлять контекст выполнения, если нужно передавать прогресс между итерациями.

Callback завершения позволяет показать итоговое сообщение, сообщить об ошибках или выполнить финальные действия.

Batch API не делает тяжёлую операцию автоматически безопасной: обработчики всё равно должны правильно работать с данными, правами доступа и ошибками.

## 3. Cron API

Cron — механизм для выполнения периодических задач.

Примеры:

- очистка временных данных;
    
- обработка очередей;
    
- обслуживание модулей;
    
- удаление просроченной информации;
    
- периодическая синхронизация данных.
    

Drupal может запускать cron через административный интерфейс, Drush или системный планировщик задач.

### Hook Cron

Модуль может реализовать `hook_cron()`.

```
/**
 * Implements hook_cron().
 */
function drupaljira_board_cron(): void {
  // Выполнить периодические действия.
}
```

Drupal вызывает этот хук при запуске cron.

Не следует помещать в `hook_cron()` тяжёлую обработку тысяч записей без ограничения. Лучше использовать его для запуска или координации небольших задач и работы с очередями.

### Cron и планировщик системы

Cron в Drupal — это логика приложения, которую нужно запускать.

Системный cron или другой планировщик — механизм, который запускает эту логику по расписанию.

Например, системный планировщик может периодически выполнять:

```
drush cron
```

Команду нужно запускать из корректного каталога проекта и в соответствующем окружении.

Если системный планировщик не настроен и никто не запускает cron другим способом, периодические задачи могут выполняться нерегулярно.

## 4. Queue API

Queue API позволяет складывать задачи в очередь и обрабатывать их отдельно.

Например, после создания задачи DrupalJira нужно отправить уведомления десяти пользователям. Вместо отправки всех уведомлений в основном HTTP-запросе можно поставить задания в очередь.

Основные понятия:

- **Queue** — очередь задач.
    
- **Queue item** — отдельный элемент очереди.
    
- **Queue worker** — обработчик элементов очереди.
    
- **Claim** — получение элемента очереди для обработки.
    
- **Delete** — удаление успешно обработанного элемента.
    

Queue API помогает отделить создание задания от его выполнения.

### Добавление задания в очередь

```
$queue = \Drupal::queue('drupaljira_notifications');

$queue->createItem([
  'task_id' => 123,
  'recipient_uid' => 45,
]);
```

Этот пример помещает данные задания в очередь. Он не отправляет уведомление сам по себе.

В рабочем коде предпочтительно получать очередь через сервис `queue` и внедрять необходимые зависимости.

### Создание Queue Worker

Пример класса обработчика:

```
namespace Drupal\drupaljira_board\Plugin\QueueWorker;

use Drupal\Core\Queue\QueueWorkerBase;

/**
 * Processes task notifications.
 *
 * @QueueWorker(
 *   id = "drupaljira_notifications",
 *   title = @Translation("Task notifications"),
 *   cron = {"time" = 30}
 * )
 */
final class TaskNotificationWorker extends QueueWorkerBase {

  /**
   * {@inheritdoc}
   */
  public function processItem($data): void {
    // Проверить данные задания.
    // Найти получателя и задачу.
    // Отправить уведомление.
  }

}
```

Свойство `cron` в определении плагина указывает, что обработчик может участвовать в cron-обработке очереди с заданным бюджетом времени.

Конкретная логика отправки уведомления зависит от приложения. Нужно также обрабатывать ситуацию, когда задача или пользователь уже удалены либо больше не доступны.

## 5. Надёжность Queue API

При работе с очередями важно учитывать ошибки и повторные попытки.

Например, внешняя почтовая система может временно оказаться недоступна. В таком случае обработчик не должен бездумно удалять задание, которое не удалось выполнить.

Также важно помнить:

- повторная обработка задания возможна;
    
- обработчик должен быть устойчивым к повторному запуску;
    
- данные задания следует валидировать;
    
- временные сбои должны обрабатываться предсказуемо;
    
- ошибки нужно логировать;
    
- чувствительные данные не следует помещать в очередь без необходимости.
    

Если повторная обработка одного задания приводит к повторному списанию денег или отправке множества дублирующих уведомлений, архитектуру необходимо изменить. Для критических операций часто требуется идемпотентность — возможность повторного выполнения без нежелательных повторных эффектов.

## 6. Сравнение Batch API, Cron API и Queue API

|API|Основное назначение|Типичный сценарий|
|---|---|---|
|Batch API|Длительная операция с последовательными шагами и прогрессом|Администратор обновляет тысячи задач|
|Cron API|Периодический запуск обслуживания|Регулярная очистка старых данных|
|Queue API|Отложенная обработка отдельных заданий|Отправка уведомлений после изменения задачи|

Эти механизмы можно комбинировать.

Например:

1. Batch API импортирует большой набор задач.
    
2. Для каждой задачи создаются задания уведомлений в Queue API.
    
3. Cron периодически запускает обработчики очереди.
    

## 7. Как выбрать подходящий механизм

Используй Batch API, если пользователь сам запускает длительную операцию и ему нужен прогресс выполнения.

Используй Cron API для регулярных задач, которые должны выполняться по расписанию.

Используй Queue API, когда работу нужно отложить, разбить на отдельные задания или обрабатывать независимо от основного HTTP-запроса.

Не нужно использовать очередь для каждого простого действия. Если операция короткая и должна завершиться сразу, обычный сервис или контроллер может быть достаточным.

## 8. Применение в DrupalJira

Предположим, менеджер импортирует большой список задач.

Возможная архитектура:

- Batch API разбивает импорт на небольшие порции.
    
- Entity API создаёт и сохраняет задачи.
    
- Queue API ставит уведомления об изменениях в очередь.
    
- Cron запускает обработку очереди и другие периодические задачи.
    

Такой подход снижает риск тайм-аутов и разделяет ответственность между разными компонентами Drupal.
