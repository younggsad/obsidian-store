# 24 — Архитектура приложений и SOLID

## 1. Теория

### Принципы SOLID
1. **S (Single Responsibility)**: У класса должна быть только одна причина для изменения (одна зона ответственности).
2. **O (Open/Closed)**: Программные сущности должны быть открыты для расширения, но закрыты для модификации.
3. **L (Liskov Substitution)**: Объекты в программе должны быть заменяемыми на экземпляры их подтипов без нарушения правильности работы программы.
4. **I (Interface Segregation)**: Много специализированных интерфейсов лучше, чем один универсальный «толстый» интерфейс.
5. **D (Dependency Inversion)**: Зависимости должны строиться на абстракциях, а не на конкретных реализациях. Модули верхних уровней не должны зависеть от модулей нижних уровней.

### Архитектурные паттерны
- **MVC (Model-View-Controller)**: Классическое разделение ответственности на данные (Model), интерфейс (View) и логику управления (Controller).
- **Clean Architecture / Layered Architecture**: Разделение на доменную логику (Domain), сервисный слой (Application), инфраструктуру (Infrastructure) и презентацию (Presentation).

## 2. Примеры кода

```php
<?php
declare(strict_types=1);

// Пример соблюдения Dependency Inversion Principle (DIP)
interface NotifierInterface {
    function send(string $message): void;
}

class EmailNotifier implements NotifierInterface {
    public function send(string $message): void {
        // Send email
    }
}

class OrderService {
    // Зависимость передается через абстракцию (интерфейс)
    public function __construct(private NotifierInterface $notifier) {}

    public function completeOrder(): void {
        // бизнес-логика
        $this->notifier->send("Order completed");
    }
}
```

## 3. Вопросы на собеседовании

1. **Опишите принцип подстановки Барбары Лисков (LSP) на примере.**
   *Ответ*: Класс-потомок должен корректно реализовывать контракт родительского класса, не сужая ожидания клиента и не выбрасывая неожиданных исключений. Если метод родителя принимает любой `Logger`, то потомок не должен падать, если ему передали специфичный логгер.
2. **В чем суть принципа инверсии зависимостей (DIP)?**
   *Ответ*: Модули верхнего уровня не должны зависеть от модулей нижнего уровня; оба должны зависеть от абстракций. Абстракции не должны зависеть от деталей; детали должны зависеть от абстракций (использование интерфейсов вместо жесткого `new Class()`).
3. **Какие преимущества дает разделение приложения на слои (Layers)?**
   *Ответ*: Улучшается тестируемость (легко мокать зависимости), поддерживаемость, слабая связанность (Loose coupling) и возможность независимого изменения бизнес-логики и инфраструктуры (например, смены базы данных или фреймворка).
