# 💧 Drupal — полный конспект

> [!info] О конспекте 
> Собрано на основе официальной документации Drupal.org (Drupal User Guide, Glossary, Core modules, Change Records) по состоянию на **2 сентября 2026 года**. Актуальная версия ядра — **Drupal 11** (ветка 11.4.x, релиз 11.4.0 — 1 июля 2026); Drupal 10 поддерживается до конца 2026 года.

---

## 📖 Базовые понятия (глоссарий)

> [!abstract]+ Что такое Drupal
> 
> - **Drupal** — CMS (Content Management System / система управления контентом) с открытым исходным кодом, написанная на PHP. Набор инструментов для создания, изменения, организации, поиска, получения и удаления информации на сайте.
> - **Drupal core (ядро)** — файлы, темы, профили установки и модули, входящие в стандартный дистрибутив Drupal при скачивании. Всё, что не входит в core, называется **contributed** (загружается отдельно с Drupal.org).
> - **CMS vs Framework** — Drupal одновременно и готовая CMS для сайтостроения через UI, и PHP-фреймворк (построен поверх компонентов **Symfony**: Drupal 10 работает на Symfony 6.x, Drupal 11 — на Symfony 7.x) для написания собственного кода.
> - **Distribution (дистрибутив)** — единый пакет для быстрой настройки сайта конкретного типа (например, для интернет-магазина). Содержит core плюс подобранные contributed-модули/темы, часто с преднастроенной конфигурацией. Пример: **Drupal CMS** — официальный дистрибутив на базе Drupal 11 с готовыми **Recipes**.
> - **Recipe (рецепт)** — готовый тематический набор модулей и настроек, который можно применить к сайту в один шаг (появились в Drupal 11).
> - **Composer** — менеджер PHP-зависимостей, используемый Drupal, Drush и Symfony; основной способ установки и обновления ядра и модулей.
> - **Drush** — интерфейс командной строки (CLI) для Drupal: установка сайта, обновления, экспорт/импорт конфигурации, кэш, cron и многое другое без веб-интерфейса.

> [!abstract]+ Модули, темы, расширение
> 
> - **Module (модуль)** — код (обычно PHP, JS и/или CSS), расширяющий возможности сайта и добавляющий функциональность. Делятся на **core** (в составе ядра) и **contributed** (скачиваются отдельно) — а также **custom** (написанные под конкретный проект).
> - **Theme (тема)** — файлы кода и ассетов (изображения, CSS, PHP, шаблоны Twig), определяющие внешний вид и раскладку сайта. Также делятся на core и contributed.
> - **Region (регион)** — заданная областью темы зона страницы, куда можно поместить контент (шапка, подвал, основная область, боковая панель). Содержимое региона состоит из **блоков**.
> - **Block (блок)** — фрагмент контента (текст, изображения, ссылки), который отображается в определённом регионе страницы.
> - **Contextual link** — ссылка на страницу администрирования для редактирования элемента прямо в контексте, где он отображается (например, при наведении на меню).

> [!abstract]+ Данные: Content, Configuration, State Drupal различает **три типа данных**, которые хранятся и обрабатываются по-разному:
> 
> - **Content (контент)** — информация для отображения на сайте: тексты, изображения, файлы. Хранится в базе данных как **сущности (entities)**.
> - **Configuration (конфигурация)** — информация о сайте, не являющаяся контентом и более постоянная, чем state: название сайта, определения типов контента, представления (views) и т.д. Управляется через **Configuration Management** — экспортируется в YAML-файлы и синхронизируется между окружениями (`drush config:export` / `config:import`).
> - **State (состояние)** — временная информация о текущем состоянии сайта (например, время последнего запуска cron). В отличие от конфигурации, не экспортируется в код.

> [!abstract]+ Сущности (Entities) — ядро модели данных
> 
> - **Entity (сущность)** — единица данных содержимого или конфигурации. В обиходе термин чаще относится к content-сущностям. Примеры: content items, пользовательские блоки, термины таксономии (все — content entities); определение типа контента — configuration entity.
> - **Entity type (тип сущности)** — общий тип сущности: content item, taxonomy term, custom block и т.д.
> - **Entity subtype / Bundle (подтип / бандл)** — группировка внутри типа сущности по общему набору полей. Синонимы: _entity subtype_, _bundle_, _field bundle_. Пример: внутри типа "content item" — подтипы (content types) "статья" и "страница", у каждого свои поля.
> - **Content type (тип контента)** — bundle для entity type "content item" (**node**). Каждый тип используется для конкретной цели и имеет собственный набор полей.
> - **Field (поле)** — данные определённого типа, прикреплённые к content-сущности (текст, изображение, ссылка на таксономию и т.д.).
> - **Reference field (поле-ссылка)** — поле, представляющее связь между сущностью и одной или несколькими другими сущностями (того же или другого типа). Поля таксономии — тоже reference fields.
> - **Revision (ревизия)** — запись о прошлом или текущем состоянии content-сущности по мере её редактирования во времени.
> - **View mode (режим отображения)** — набор конфигураций **field formatter** для всех полей сущности данного bundle; например, режимы _Full_ и _Teaser_ для типа контента.
> - **Field formatter / Field widget** — конфигурация отображения данных поля (formatter) и конфигурация формы ввода/редактирования данных поля (widget).

> [!abstract]+ Пользователи, таксономия, структура
> 
> - **User (пользователь)** — человек, взаимодействующий с сайтом: **Anonymous** (не вошёл) или **Authenticated** (вошёл).
> - **Role (роль)** — именованный набор **permissions (разрешений)**, применяемый к учётной записи пользователя.
> - **User 1** — первая учётная запись, создаваемая при установке сайта (ID = 1); автоматически имеет все разрешения, даже без назначенной административной роли.
> - **Taxonomy (таксономия)** — процесс классификации контента. **Vocabulary (словарь)** — группа **taxonomy terms (терминов)**, из которых выбирают при классификации; технически словарь — bundle для entity type "термин таксономии".
> - **View (представление)** — форматированный список данных, обычно построенный из content-сущностей средствами модуля **Views**. Может выводиться как страница, блок или лента (**Display**), с **Filter** (ограничение выборки), **Contextual filter** (ограничение по контексту URL) и **Relationship** (расширение данных через связанные сущности).
> - **Menu (меню)** — набор ссылок для навигации по сайту, может быть иерархическим.
> - **Path / Alias / URL** — **path** — внутренний уникальный "хвост" URL (например, `node/5`); **alias** — человекочитаемое имя, заменяющее внутренний path (`/about` вместо `/node/5`); **URL** — полный адрес страницы.

> [!abstract]+ Разработка: PHP-концепции ядра
> 
> - **Hook (хук)** — механизм, позволяющий модулям и темам "слушать" события системы или изменять поведение других модулей. Один из наиболее давних и определяющих механизмов Drupal (существует более 20 лет).
> - **OOP-хуки (Object-Oriented Hooks)** — начиная с **Drupal 11.1**, хуки можно реализовывать как методы классов с PHP-атрибутом `#[Hook]`, а не только как процедурные функции `hook_*()` в `.module`-файлах. Подробнее: [[#🪝 Hooks — процедурные и OOP]].
> - **Plugin (плагин)** — swappable-компонент с определённым интерфейсом, обнаруживаемый системой через **Plugin API** (используется для полей, форматтеров, виджетов, блоков и др.).
> - **Service / Dependency Injection (сервис / внедрение зависимостей)** — переиспользуемый объект, зарегистрированный в **service container** (контейнере служб) Symfony, доступный по строковому идентификатору и заменяемый другой реализацией без изменения кода, который его использует.
> - **Route / Controller (маршрут / контроллер)** — маршрут описывает соответствие URL-паттерна и требуемых прав доступа обработчику; контроллер — PHP-метод/класс, возвращающий ответ (страницу, JSON и т.д.).
> - **Render array (рендер-массив)** — вложенный PHP-массив, описывающий структуру и данные для вывода, который Drupal превращает в HTML через **render pipeline** и темизацию.
> - **Twig** — движок шаблонов PHP (от Symfony), используемый Drupal для тем — заменил PHPTemplate начиная с Drupal 8.

## 🏗️ Архитектура и типы данных

> [!quote] Определение 
> Drupal — CMS с открытым исходным кодом, известная гибкостью, надёжной безопасностью и масштабируемостью; используется от небольших блогов до крупных корпоративных порталов, университетов, НКО и госорганизаций.

### Три типа данных

Всё, что хранит и обрабатывает Drupal, относится к одной из трёх категорий — важно различать их, так как они хранятся и синхронизируются по-разному:

|Тип|Описание|Где хранится|
|---|---|---|
|**Content (контент)**|Информация для отображения на сайте — тексты, изображения, файлы|База данных, как сущности (entities)|
|**Configuration (конфигурация)**|Настройки сайта, более постоянные, чем state: название сайта, типы контента, views и т.д.|БД (активная) + YAML-файлы (для синхронизации между окружениями)|
|**State (состояние)**|Временная информация о текущем состоянии — например, время последнего запуска cron|Таблица `key_value` в БД, не экспортируется|

### Drupal как фреймворк

Начиная с Drupal 8, ядро построено на компонентах **Symfony** — это дало Drupal объектно-ориентированную архитектуру: service container, роутинг, events, HTTP kernel.

|Версия Drupal|Версия Symfony|PHP|
|---|---|---|
|Drupal 10|Symfony 6.x|8.1+|
|Drupal 11|Symfony 7.x|8.3+|

> [!tip] Изменение сервисов 
> Поскольку каждый сервис доступен по единому строковому ключу и имеет определённый интерфейс, его можно заменить другой реализацией. Для этого реализуют класс, расширяющий `ServiceProviderBase`, и метод `alter()` — работа идёт со скомпилированным Symfony-контейнером (алиасы, декорирование сервисов, теги, compiler passes).

## 📦 Сущности, поля и bundles

> [!quote] Определение 
> **Entity** — единица данных content или configuration. Именно вокруг Entity API строится вся модель данных Drupal.

### Иерархия: Entity type → Bundle → Field

|Термин|Значение|
|---|---|
|**Content item (node)**|Content-сущность, обычно предназначенная для отображения как основной контент страницы; сам является **entity type**|
|**Content type**|**Bundle** (подтип) для entity type "content item" — например, "Статья", "Страница", "Карточка вендора"|
|**Bundle / Entity subtype / Field bundle**|Синонимы: группировка сущностей внутри entity type, разделяющих общий набор полей|
|**Field**|Данные конкретного типа, прикреплённые к content-сущности (текст, изображение, дата, ссылка на другую сущность)|
|**Reference field**|Поле, задающее связь между сущностью и одной/несколькими другими сущностями (тот же или другой entity type); поля таксономии — тоже reference fields|
|**View mode**|Набор конфигураций field formatter для всех полей bundle (например, _Full_ и _Teaser_)|
|**Field formatter**|Конфигурация того, как данные поля отображаются (например, обрезка HTML-тегов в текстовом поле)|
|**Field widget**|Конфигурация того, как данные поля вводятся на форме (например, однострочное или многострочное поле ввода)|
|**Revision**|Запись о состоянии content-сущности на момент правки — история изменений во времени|

### Другие ключевые content-сущности

- **Taxonomy term / Vocabulary** — термин классификации и словарь терминов (vocabulary технически тоже bundle — для entity type "термин таксономии")
- **Custom block** — пользовательский блок как content-сущность
- **User** — учётная запись как content-сущность

### Views — построение списков из сущностей

**View** — форматированный список данных (обычно из content-сущностей), создаваемый модулем **Views** без кода, через UI:

|Часть View|Назначение|
|---|---|
|**Display**|Тип вывода: страница, блок, лента|
|**Filter**|Ограничение выборки по критериям (статус публикации, тип, значение поля)|
|**Contextual filter**|Ограничение по контексту отображения — например, по части URL|
|**Relationship**|Расширение данных через связанные сущности|

## 🧩 Модули и темы

> [!quote] Определение 
> **Module** — код, расширяющий возможности сайта. 
> **Theme** — файлы, определяющие внешний вид. 
> Оба делятся на **core** (в составе ядра) и **contributed** (отдельно с Drupal.org); к ним добавляется **custom** — написанный под конкретный проект.

### Regions и Blocks

- **Region** — заданная темой область страницы (шапка, подвал, сайдбар и т.д.)
- **Block** — фрагмент контента, размещаемый в регионе

### Distributions и Recipes

|Термин|Описание|
|---|---|
|**Distribution (дистрибутив)**|Единая сборка: core + подобранные contributed-модули/темы + преднастроенная конфигурация (иногда с примерами контента) для конкретного типа сайта|
|**Drupal CMS**|Официальный дистрибутив на базе Drupal 11, ориентированный на маркетологов, дизайнеров и контент-менеджеров — упрощает установку через готовые **Recipes**|
|**Recipe (рецепт)**|Готовый тематический набор модулей и настроек, применяемый к сайту в один шаг (`ddev composer drupal:recipe-unpack` при установке через DDEV)|

### Новшества Drupal 11 (в дополнение к рецептам)

- Экспериментальный модуль новой **навигации** — единое сворачиваемое вертикальное левое админ-меню на базе Layout Builder
- Модернизированные темы, обновлённые зависимости (PHP 8.3+, Symfony 7)
- Автоматические обновления для повышения безопасности

## 🪝 Hooks — процедурные и OOP

> [!quote] Определение 
> **Hook** — функции, следующие определённой конвенции именования и вызываемые в конкретных точках выполнения кода Drupal, позволяющие модулям расширять и изменять поведение системы. Один из старейших и наиболее характерных механизмов Drupal — практически неизменный на протяжении 24 лет, вплоть до Drupal 11.1.

### Классический (процедурный) способ

Функция `имя_модуля_hook_name()` в файле `имя_модуля.module`:

```php
function custom_module_form_alter(&$form, $form_state, $form_id) {
  // Изменение формы
}
```

Все `.module`-файлы загружались целиком при каждом запросе, даже если использовалась лишь малая часть хуков — это расходовало время на старте.

### Новый способ — OOP-хуки (с Drupal 11.1)

Хуки можно реализовать как **методы классов**, помеченные PHP-атрибутом `#[Hook]`:

```php
use Drupal\Core\Hook\Attribute\Hook;
use Drupal\Core\Entity\EntityInterface;

#[Hook('entity_insert')]
class EntityInsertHook {
  public function __invoke(EntityInterface $entity): void {
    // Логика хука
  }
}
```

Рекомендуемая директория — `src/Hook/`. Атрибут `#[Hook]` можно поставить на метод (рекомендуется) либо на класс с указанием метода вторым параметром.

### Преимущества OOP-хуков

|Преимущество|Пояснение|
|---|---|
|**Autoloading**|`.module`-файл больше не сканируется целиком — классы загружаются по PSR-4 только когда действительно используются, что ускоряет старт|
|**Dependency Injection**|Поскольку хуки теперь объектно-ориентированы, в них можно внедрять сервисы через конструктор|
|**Тестируемость**|Хуки в классах можно юнит-тестировать без полной загрузки Drupal|
|**Организация кода**|Хуки можно группировать по классам (например, все node-related хуки — в одном классе)|

### Обратная совместимость

Процедурные хуки продолжают работать — обе системы работают параллельно. Для модулей, которые должны поддерживать более старые версии (Drupal 10.3+), применяется **`#[LegacyHook]`** — процедурная функция-делегат в `.module`-файле, вызывающая сервис с OOP-хуком:

```php
use Drupal\Core\Hook\Attribute\LegacyHook;
use Drupal\custom_module\Hook\NodeHooks;

#[LegacyHook]
function custom_module_node_create(EntityInterface $entity) {
  return \Drupal::service(NodeHooks::class)->nodeCreate($entity);
}
```

> [!note] Hook Service Collector 
> Drupal добавил в ядро **Hook Service Collector**: при сборке контейнера служб он сканирует все сервисы на атрибут `#[Hook]`. Разработчику достаточно поместить класс в правильную директорию/namespace и использовать `autowire: true` — регистрировать хук вручную не требуется.

> [!warning] Не все хуки конвертируются 
> Некоторые старые или низкоуровневые хуки должны оставаться процедурными функциями. Preprocess-хуки в **модулях** поддерживают OOP-подход (начиная с Drupal 11.1.8/11.2), но preprocess-хуки в **темах** остаются процедурными.

## ⚙️ Configuration Management

> [!quote] Суть механизма 
> Конфигурация Drupal (типы контента, views, настройки модулей и т.д.) экспортируется в **YAML-файлы**, которые можно версионировать в Git и синхронизировать между окружениями (dev → staging → production).

Типовой рабочий процесс:

```bash
# Экспортировать активную конфигурацию сайта в YAML
drush config:export

# Импортировать конфигурацию из YAML в активное хранилище
drush config:import
```

YAML-файлы конфигурации обычно хранятся в директории `config/sync` (путь задаётся в `settings.php`). Это отделяет **конфигурацию** (versioned, деплоится вместе с кодом) от **контента** (живёт в базе данных production-сайта и обычно не деплоится через код).

## 🖥️ Установка и инструменты разработки

### Composer

**Composer** — предпочтительный способ установки Drupal и его зависимостей:

```bash
composer create-project drupal/recommended-project my-site
```

### Drush

**Drush** — командная строка и скриптовый интерфейс для Drupal. Частые команды:

```bash
drush site:install --account-name=admin --account-pass=admin -y   # установка сайта
drush uli                                                          # одноразовая ссылка входа
drush cache:rebuild                                                # сброс кэша
drush config:export / config:import                                # управление конфигурацией
drush updb                                                          # применение обновлений БД (update.php)
```

### Локальная разработка

Официальный **Local Development Guide** Drupal.org рекомендует контейнеризированные окружения — в частности **DDEV** — как основной способ локальной разработки на современном стеке (LAMP/LEMP без ручной настройки). Подробный разбор DDEV — в отдельном конспекте [[GitHub Spec Kit — конспект|(см. также конспект по GitHub Spec Kit)]].

> [!tip] Devel — модуль для разработки
>  **Devel** — contributed-модуль, помогающий в задачах разработки: отладка и инспекция кода, анализ запросов к БД, генерация тестового контента (dummy content).

## 🔒 Безопасность и жизненный цикл релизов

### Цикл релизов

Начиная с Drupal 11, действует более предсказуемый график: новая мажорная версия — **каждые два года**, с активной поддержкой около двух лет, затем ещё два года технической и security-поддержки.

|Версия|Релиз|Поддержка|
|---|---|---|
|Drupal 10|декабрь 2022|до конца 2026 (EOL ожидается с релизом Drupal 12)|
|Drupal 11|2 августа 2024|активная поддержка + продлённая security-поддержка|
|Drupal 12|ожидается 2-я половина 2026|—|

### Security advisories

> [!warning] Регулярные обновления — не опция 
> **Security update** — обновление, исправляющее уязвимость (например, дыру для взлома). Своевременное обновление ядра и contributed-модулей — базовая практика безопасности Drupal-сайта.
