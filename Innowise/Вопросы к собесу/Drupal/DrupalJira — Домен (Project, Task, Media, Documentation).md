## Задача 2.1 — Content types: Project и Task

### Суть

Базовый домен: два строго типизированных content type вместо «нод с произвольными текстовыми полями». Задача — сделать так, чтобы связь «задача → проект» и статус задачи были машиночитаемыми, а не текстом, который можно опечатать.

### Технологии и их роль

|Технология|За что отвечает|
|---|---|
|**Content type (Node type)** `project`, `task`|Базовые сущности домена — «Проект» и «Задача» как отдельные типы контента|
|**Core Field API** (через UI, без contrib)|Создание всех полей стандартными средствами ядра Drupal|
|**Entity reference field** (`field_project`)|Связь Task → Project. Тип поля — ссылка именно на **content type `project`**, а не текстовое поле с ID. Cardinality = 1, обязательное|
|**List (text) field** (`field_status`)|Статус задачи как **фиксированный список** значений (machine key → label): `backlog→Backlog`, `in_progress→In Progress`, `review→Review`, `done→Done`. Значение по умолчанию — `backlog`. Так исключается свободный ввод статуса|
|**Entity reference field** (`field_assignee`)|Ссылка на сущность **User** — исполнитель задачи, необязательное поле|
|**Number (decimal) field** (`field_estimate`)|Оценка трудозатрат в часах. Именно decimal, не integer и не текст — допускает дробные значения (например, 2.5 часа)|
|**Entity reference autocomplete widget**|Виджет формы для `field_project` — выбор существующей ноды Project через автодополнение, а не ручной ввод текста|
|**Configuration Management (CM)**|Экспорт всех YAML-конфигов типов и полей (`node.type.project.yml`, `field.field.node.task.field_project.yml` и т.д.) в `config/sync`, коммит в git. Проверяется через `/admin/config/development/configuration` — там не должно быть расхождений|

### Ключевая логика

- **Валидация на уровне поля**: `field_project` required → без выбора проекта форма Task не сохранится, будет понятная ошибка.
- **Значение по умолчанию** у `field_status` = Backlog — редактор видит его сразу при создании задачи, без явного выбора.
- **Отображение**: `field_estimate` показывается на full view только если заполнено; `field_project` рендерится как ссылка на ноду проекта.

> [!tip] Зачем так строго 
> Всё это (List вместо boolean/taxonomy/текста, Entity reference вместо текстового ID) нужно, чтобы дальше строить **Views, бизнес-логику и отчётность** поверх машиночитаемых данных, а не парсить строки.

## Задача 2.2 — Media Library для задач

### Суть

Вложения (скриншоты багов, файлы ТЗ) к задачам должны идти через **переиспользуемую медиатеку**, а не через одноразовую загрузку файла в каждую ноду.

### Технологии и их роль

|Технология|За что отвечает|
|---|---|
|**Модуль Media (ядро)**|Базовая сущность Media — обёртка над файлом с метаданными, переиспользуемая между нодами|
|**Модуль Media Library (ядро)**|UI-виджет: модальное окно с загрузкой нового файла **и** выбором уже существующего медиа-объекта из библиотеки|
|**Media bundle "Document"**|Отдельный тип медиа (аналог Image, но для файлов вроде PDF) — создаётся, если его ещё нет в проекте, с полем загрузки файла|
|**Media reference field** (`field_attachments` на Task)|Поле типа **Entity reference на Media entity** (НЕ File field!). Cardinality — unlimited, то есть можно прикрепить сколько угодно файлов|
|**Ограничение типов медиа на поле**|Настройка поля разрешает выбирать только бандлы **Image** и **Document** — остальные типы медиа для этого поля недоступны|
|**Media Library widget** (форма)|Именно этот виджет ставится на `field_attachments`, а не стандартный autocomplete entity reference — отсюда и модальное окно с загрузкой/выбором|

### Ключевая логика

- Разница между **File field** и **Media reference field**: File field хранит файл «намертво привязанным» к одной ноде; Media reference ссылается на переиспользуемую сущность Media, которую можно прикрепить к нескольким нодам.
- На full view задачи изображения и документы **визуально различаются**: картинка рендерится как `<img>`, документ — как ссылка/иконка на скачивание (не «голое» имя поля).
- Обратная совместимость: старые ноды Project/Task, созданные **до** добавления `field_attachments`, должны открываться и редактироваться без ошибок после появления нового поля.

> [!note] Зависимость от задачи 2.3 
> Media bundle **Image**, используемый здесь, — тот же самый, что переиспользуется в паб-типе `image` внутри Paragraphs (задача 2.3). Медиатека — сквозной слой для всего проекта.

## Задача 2.3 — Knowledge Base: Documentation + Paragraphs

### Суть

Документация к проекту (онбординг, примеры кода, предупреждения) должна собираться редактором как **конструктор из переиспользуемых блоков** произвольного порядка и количества — а не как один большой текстовый WYSIWYG-блок.

### Технологии и их роль

|Технология|За что отвечает|
|---|---|
|**Content type `documentation`**|Страница документации: `title`, `field_project` (обязательная связь с проектом), `field_content` (набор блоков)|
|**Модуль Paragraphs**|Даёт сущность Paragraph — вложенные, типизированные, переупорядочиваемые блоки контента внутри ноды|
|**Entity reference revisions field** (`field_content`)|Специальный тип поля именно для Paragraphs (в отличие от обычного entity reference — хранит **ревизии** параграфов). Unlimited cardinality, порядок задаёт редактор вручную (drag&drop)|
|**Paragraph type `text`**|Блок форматированного текста, поле `body`|
|**Paragraph type `code`**|Блок кода: `field_code` (plain text, без форматирования — важно, чтобы код не «портился» WYSIWYG-фильтрами) + `field_language` (List (text): php/twig/yaml/js, необязательное)|
|**Paragraph type `callout`**|Блок-акцент (типа alert/note): `field_callout_text` + `field_callout_type` (List (text): info/warning/success)|
|**Paragraph type `image`**|Блок картинки: `field_image` — **media reference на бандл Image** (переиспользует медиатеку из 2.2, отдельного файлового поля нет)|
|**Кастомные Twig-шаблоны** (`paragraph--text.html.twig`, `paragraph--code.html.twig`, `paragraph--callout.html.twig`, `paragraph--image.html.twig`)|Каждый тип параграфа рендерится своим шаблоном в кастомной теме/сабтеме → у типов разная HTML-разметка/классы, а не только стандартная Drupal-обёртка|
|**`hook_preprocess_paragraph()`** в `.theme` файле|PHP-хук темы: различает bundle параграфа и добавляет **вычисляемую** переменную (не введённую редактором как текст) — она пробрасывается в соответствующий Twig-шаблон и доступна там|
|**GrumPHP / PHPCS / PHPStan** (из задачи 1.3)|Статический анализ и код-стайл проверяют `.theme` файл перед коммитом — без прохождения проверки коммит блокируется|

### Ключевая логика — пример вычисляемой переменной

Для параграфа `code` с заполненным `field_language`:

- Хук `hook_preprocess_paragraph()` смотрит на bundle `= code` и на значение `field_language`.
- Формирует, например, CSS-класс вида `paragraph-code--lang-php` — **этот класс нигде не вводится редактором вручную**, он вычисляется в PHP.
- В Twig-шаблоне `paragraph--code.html.twig` этот класс используется в разметке.
- Если редактор меняет `field_language` (например, с `php` на `js`) — вычисляемый класс в выводе автоматически меняется соответственно.

Это доказывает, что переменная действительно **вычисляется на основе данных**, а не хардкодится/вводится вручную.

### Проверка результата

- Страница Documentation с проектом и минимум одним параграфом каждого из 4 типов сохраняется и рендерится **без PHP/Twig-ошибок** — проверяется в `/admin/reports/dblog`.
- Конфигурация content type `documentation`, всех paragraph types и полей — экспортирована и закоммичена без расхождений.

## Сквозные технологии по всем трём задачам

> [!abstract] Общие принципы, которые проверяются в каждой задаче
> 
> 1. **Только Core Field API**, без contrib-модулей для самих полей (кроме Media/Media Library/Paragraphs, которые — часть предусмотренного стека).
> 2. **List (text) вместо boolean/taxonomy/свободного текста** — везде, где нужен фиксированный набор значений (статус задачи, язык кода, тип колаута).
> 3. **Entity reference вместо текстовых ID** — связи между сущностями строятся типизированно (Task→Project, Task→Media, Documentation→Project, Paragraph→Media).
> 4. **Configuration Management (CM)**: любое изменение структуры (content type, поле, paragraph type) обязательно экспортируется в `config/sync` и коммитится; `/admin/config/development/configuration` должен показывать «нет расхождений» — это единый критерий приёмки во всех трёх задачах.
> 5. **Обратная совместимость**: добавление новых полей не должно ломать уже существующие ноды.

## Мини-глоссарий терминов Drupal, встретившихся в задачах

- **Content type (Node type)** — шаблон типа контента (Article, Page — в стандартной поставке; здесь: Project, Task, Documentation).
- **Field API** — механизм ядра Drupal для добавления полей к любым сущностям.
- **Entity reference** — тип поля-ссылки на другую сущность (ноду, пользователя, термин и т.д.).
- **Entity reference revisions** — вариант entity reference, который хранит ссылку на конкретную ревизию сущности; используется Paragraphs, чтобы у родительской ноды сохранялась история изменений вложенных блоков.
- **List (text)** — тип поля с фиксированным списком пар «машинное значение → человекочитаемая подпись».
- **Paragraphs (модуль)** — фреймворк вложенных типизированных блоков контента (page builder «изнутри» ноды).
- **Media / Media Library (модули ядра)** — единая переиспользуемая библиотека файлов/изображений с собственными «бандлами» (типами медиа).
- **hook_preprocess_HOOK()** — механизм темизации Drupal: PHP-функция, которая готовит/довычисляет переменные перед передачей их в Twig-шаблон.
- **Configuration Management (CM)** — система хранения конфигурации Drupal (content types, поля, view displays и т.д.) в виде YAML-файлов, синхронизируемых между окружениями через git.
