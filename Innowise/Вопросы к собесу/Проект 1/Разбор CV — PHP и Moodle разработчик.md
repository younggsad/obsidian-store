## 2. Moodle за 5 минут

**Moodle** — открытая LMS (система управления обучением) на PHP. Курсы, задания, тесты, форумы, оценки, пользователи, роли.

**Архитектура:**

- **Ядро** — не трогаем.
- **Плагины** — всё остальное. Расширяют систему через API.
- **Frankenstyle** — правило именования: `тип_имя`, например `local_deepl`, `mod_clinicalcase`, `theme_myboost`, `format_mycourse`.

**Основные типы плагинов (те, что есть в CV):**

|Тип|Папка|Для чего|
|---|---|---|
|`mod`|`/mod`|Модуль активности (элемент курса)|
|`local`|`/local`|Универсальные доработки, сервисы, интеграции|
|`theme`|`/theme`|Тема оформления|
|`format`|`/course/format`|Формат курса (как курс выглядит и устроен)|
|`block`|`/blocks`|Блок на страницах|
|`auth`|`/auth`|Способ входа (SAML, LDAP и т.д.)|
|`search`|`/search/engine`|Движок поиска (Solr)|

**Типовые файлы плагина:**

- `version.php` — версия и зависимости.
- `lib.php` — функции-колбэки для ядра.
- `settings.php` — страница настроек в админке.
- `db/install.xml` — схема таблиц.
- `db/upgrade.php` — миграции при обновлении версии.
- `db/access.php` — права (capabilities).
- `db/services.php` — внешние функции веб-сервисов.
- `db/tasks.php` — плановые задачи.
- `lang/en/…php` — строки интерфейса.
- `classes/` — классы с автозагрузкой.
- `templates/` — шаблоны Mustache.
- `amd/src/` — JavaScript-модули.

**Как данные идут на экран:** запрос → `require_login` → проверка прав → логика → renderer → шаблон Mustache → HTML.

## 3. Технологии из CV

> [!tip] Формат каждой технологии 
> **Что это** → **Зачем в проекте** → **Как использовал** → **Что сказать на собеседовании**.

### 3.1 Языки

#### PHP

- **Что это:** основной язык Moodle и твоего бэкенда.
- **Зачем:** плагины, веб-сервисы, задачи, формы.
- **Как:** классы с пространствами имён, работа с БД через Moodle API, соблюдение стандартов Moodle (PHPDoc, имена по Frankenstyle, `get_string`, проверки прав).
- **Сказать:** пишу по стандартам Moodle, не лезу в ядро, всё через API и колбэки.

#### JavaScript

- **Что это:** клиентская логика.
- **Зачем:** графики, динамика на страницах.
- **Как:** AMD-модули в `amd/src`, сборка в `amd/build` (Grunt), подключение через `$PAGE->requires->js_call_amd()`.
- **Сказать:** JS в Moodle — это модули с RequireJS, а не просто `<script>`.

### 3.2 Backend и инфраструктура

#### Moodle

- **Что это:** платформа, на которой построены оба проекта.
- **Зачем:** готовые курсы, роли, оценки, пользователи; мы расширяем под заказчика.
- **Как:** разработка плагинов всех нужных типов, настройка, отладка, обновления.

#### REST

- **Что это:** стиль API через HTTP, данные обычно в JSON.
- **Зачем:** обмен с внешними системами (синхронизация пользователей и записей на курсы, обмен с госсервисами).
- **Как:** Moodle предоставляет REST-протокол для веб-сервисов: `…/webservice/rest/server.php` с токеном, именем функции и форматом ответа. Твои функции регистрируются в `db/services.php`.

#### Composer

- **Что это:** менеджер PHP-зависимостей.
- **Зачем:** подключать сторонние библиотеки (например, SDK для Sentry), автозагрузка, разработческие инструменты.
- **Как:** `composer.json`, `composer install`. Для сторонних библиотек внутри плагина в Moodle принято описывать их в `thirdpartylibs.xml`.

#### Sentry

- **Что это:** сервис отслеживания ошибок.
- **Зачем:** видеть исключения и всплески ошибок в продакшене с трассировкой и контекстом.
- **Как:** SDK, отправка исключений и событий, группировка, оповещения.
- **Сказать:** узнаю об ошибках раньше пользователей.

#### Grafana

- **Что это:** дашборды и графики метрик.
- **Зачем:** время ответа страниц, нагрузка, очередь задач.
- **Как:** метрики в источник данных, графики и алерты. Нашёл медленные страницы — разобрал, почему (запросы к БД, тяжёлые операции) — исправил.

#### Apache Solr

- **Что это:** поисковый сервер с полнотекстовым индексом.
- **Зачем:** встроенный поиск Moodle по умолчанию на БД, он медленный на больших объёмах. Solr быстрее и умеет лучше ранжировать.
- **Как:** подключение через плагин движка `search_solr` в Moodle; настройка сервера (ядро, схема), индексация курсов, форумов, ресурсов по cron.

#### SAML

- **Что это:** протокол единого входа (SSO) между организациями.
- **Зачем:** слушатель входит через логин своей организации, без отдельного пароля на платформе.
- **Как:** Moodle выступает как поставщик услуги (Service Provider), организация — как поставщик идентификации (Identity Provider). Обмен метаданными, сопоставление атрибутов (логин, email, имя). Обычно используется плагин `auth_saml2`.

### 3.3 Технологии (API) Moodle

|API|Что делает|Где использовал|
|---|---|---|
|**Plugin API**|Правила создания плагинов, колбэки, события|Все плагины|
|**Web Services API**|Внешние функции для REST и других протоколов|Оба проекта|
|**DML API**|Работа с БД через `$DB`|Модуль активности, отчёты, синхронизации|
|**Form API**|Формы на классе `moodleform`|Настройки, форма самооценки|
|**Task API**|Плановые и разовые фоновые задачи|Массовый перевод, массовая запись на курсы|
|**Global Search API**|Поисковые области и индексация|Solr, поиск по курсам и форумам|

#### Plugin API

- Ядро знает, какие плагины есть, и вызывает их функции по заранее оговорённым именам (`pluginname_function`) или через классы и события.
- Зачем: чтобы **не править ядро**.

#### Web Services API

- Внешняя функция = класс с тремя методами: описание параметров, сама логика, описание возвращаемого.
- Обязательно: проверка параметров, контекст, права.
- Регистрация в `db/services.php`.
- Включение: функция добавляется в **сервис**, сервису выдаётся **токен**.

#### DML API

- `$DB->get_record()`, `get_records()`, `get_records_sql()`
- `insert_record()`, `update_record()`, `delete_records()`
- Плейсхолдеры вместо подстановки значений (защита от SQL-инъекций).
- Имена таблиц в SQL пишутся как `{tablename}` — префикс подставит Moodle.
- Один код работает на MySQL и PostgreSQL.

#### Form API

- Класс наследуется от `moodleform`, поля описываются в `definition()`.
- Типы параметров (`PARAM_INT`, `PARAM_TEXT`).
- Проверка в `validation()`, результат через `get_data()`.
- Защита от CSRF встроена (sesskey).

#### Task API

- **Плановая задача** (`scheduled_task`) — выполняется по расписанию cron.
- **Разовая задача** (`adhoc_task`) — ставится в очередь из кода с данными, выполняется при ближайшем запуске cron.
- Зачем: тяжёлую работу не делают в запросе пользователя.

#### Global Search API

- **Поисковая область** — класс, который знает, что и как индексировать (форумные посты, ресурсы, курсы).
- **Движок** — куда складывать (простой на БД или Solr).
- После выдачи Moodle проверяет права пользователя на каждый результат.

### 3.4 Фронтенд

#### HTML / CSS

- Вёрстка шаблонов и стилей темы. В Moodle стили часто через SCSS.

#### Mustache

- **Что это:** шаблонизатор без логики.
- **Зачем:** отделить HTML от PHP, дать возможность переопределять шаблоны в теме.
- **Как:** `{{name}}` — вывод с экранированием, `{{#items}}…{{/items}}` — цикл или условие, `{{> partial}}` — вложенный шаблон, `{{#str}}key, component{{/str}}` — строка перевода. Рендер: `$OUTPUT->render_from_template()`.

#### Chart.js

- **Что это:** JS-библиотека графиков.
- **Зачем:** графики результатов самооценки.
- **Как:** данные из PHP передаются в JS-модуль, строится диаграмма на `<canvas>`. В самом Moodle тоже есть встроенный API графиков (`core\chart_*`), который строится на Chart.js.

### 3.5 Базы данных

#### MySQL и PostgreSQL

- **Зачем два:** проект 1 на MySQL, проект 2 на PostgreSQL.
- **Различия, о которых полезно знать:** PostgreSQL строже к `GROUP BY` и типам, по-разному ведёт себя с регистром при `LIKE`.
- **Как сглаживает Moodle:** DML API и функции вроде `$DB->sql_like()`, `sql_concat()`.
- **Сказать:** пишу запросы через DML и переносимые функции, поэтому плагин работает на обеих БД.

### 3.6 Сторонние сервисы

#### DeepL

- **Что это:** сервис машинного перевода с API.
- **Зачем:** автоматический перевод материалов курсов на несколько языков.
- **Как:** HTTP-запрос с ключом и текстом на целевой язык; для HTML-контента включается режим сохранения тегов. Вызовы идут из фоновых задач.

### 3.7 DevOps

#### Docker и Docker Compose

- **Зачем:** одинаковое окружение у всех разработчиков и на стенде.
- **Как:** контейнеры веб-сервера и БД (и при необходимости Solr), описанные в `docker-compose.yml`; одна команда для запуска.

#### Linux

- **Зачем:** сервера и контейнеры на Linux.
- **Как:** работа в консоли, права на файлы, cron (для задач Moodle), логи.

### 3.8 Контроль версий

#### Git, GitLab, BitBucket

- **Git:** ветки, коммиты, слияния, разрешение конфликтов.
- **GitLab (проект 2) и BitBucket (проект 1):** репозитории, merge request / pull request, ревью кода.

## 4. Проект 1 — Платформа непрерывного медицинского образования

> [!abstract] Паспорт 
> **Период:** 04.2024 — по настоящее время 
> **Роль:** инженер-программист 
> **Что за платформа:** Moodle для сети медицинских и научных организаций. Курсы, аккредитованные программы повышения квалификации, научные материалы. 
> **Ключевая идея:** **одна установка Moodle на много организаций.** У каждой свои категории курсов, оформление, группы слушателей. Общее: управление контентом, многоязычность, безопасность. 
> **Окружение:** PHP, JS, Moodle, MySQL, Plugin / Web Services / Task / Form / DML / Global Search API, Mustache, HTML/CSS, Solr, SAML, Docker, Docker Compose, Linux, Grafana, Sentry, DeepL API, REST, Git / BitBucket.

### 4.1 Работа с партнёрами и дорожная карта

- **Задача:** организации хотят разного, а разработка ограничена по времени.
- **Что делал:** общался с представителями партнёров, приоритизировал, переводил потребности в конкретные задачи.
- **Как рассказать:** «Превращаю запрос вида "хотим, чтобы слушателям было удобнее" в задачи с понятным результатом и оценкой».
- **Почему важно:** показывает, что ты не только кодишь, но и понимаешь бизнес.

### 4.2 Языковые пакеты и многоязычный контент

- **Задача:** организации из разных регионов, нужен интерфейс и контент на разных языках.
- **Что делал:** настройка языковых пакетов, фильтров многоязычного контента, локализованные каталоги курсов.
- **Как сделано:**
    - Языковой пакет переводит **интерфейс** Moodle.
    - Фильтр многоязычности переводит **контент** курсов (один и тот же текст в нескольких языках, показывается нужный).
    - Каталоги курсов собраны под каждый регион.
- **Подводный камень:** интерфейс и контент — два разных механизма, их нельзя путать.

### 4.3 Local-плагин для DeepL

- **Задача:** переводить большие объёмы учебных материалов вручную долго и дорого.
- **Что делал:** local-плагин, который отправляет содержимое курсов и элементов в DeepL и получает перевод.
- **Как сделано (типично):**
    1. Настройки плагина: ключ API, языки (`settings.php`).
    2. Сбор переводимого контента: описания курсов и секций, страницы, подписи, элементы.
    3. Отправка в DeepL, режим сохранения HTML-тегов.
    4. Сохранение перевода в нужном виде (в мультиязычном формате или как отдельная версия).
    5. Тяжёлая часть вынесена в **adhoc-задачи** (см. 4.6).
- **Результат:** материалы переводятся автоматически на несколько языков.
- **Что уточнить у себя:** в каком виде хранится перевод; как обрабатываешь ошибки и лимиты API; как не переводить повторно то, что не менялось.

### 4.4 Global Search + Apache Solr

- **Задача:** встроенный поиск на БД медленный.
- **Что делал:** подключил глобальный поиск к Solr, настроил индексацию курсов, форумов, ресурсов.
- **Как сделано (типично):**
    1. Развёрнут Solr, создано ядро с нужной схемой.
    2. В Moodle выбран движок Solr, указаны адрес и имя индекса.
    3. Включены поисковые области (курсы, форумы, ресурсы).
    4. Первичная индексация, затем дополнительная по cron.
- **Результат:** сократилось время ответа поиска.
- **Подводный камень:** индекс надо поддерживать актуальным; права пользователя проверяются уже после поиска.

### 4.5 Тема на основе Boost

- **Задача:** у каждой организации должен быть свой фирменный стиль в одной установке.
- **Что делал:** дочерняя тема от Boost с переопределением шаблонов Mustache.
- **Как сделано (типично):**
    - Тема объявляет `Boost` родителем — берёт всё от него и меняет только нужное.
    - Шаблоны переопределяются копированием в папку темы.
    - Стили через SCSS.
- **Почему так:** обновления Boost не ломают тему, а свои правки собраны в одном месте.
- **Что уточнить:** как именно переключался стиль организации (настройки темы, категория, и т.д.).

### 4.6 Task API: плановые и разовые задачи

- **Задача:** массовый перевод и массовая запись на курсы — долго, запрос пользователя «упадёт» по тайм-ауту или заблокирует сайт.
- **Что делал:** вынес такие операции в плановые и ad-hoc задачи.
- **Как сделано:**
    - Пользователь (или код) ставит adhoc-задачу с данными: что обработать.
    - Cron выполняет её в фоне.
    - Плановые задачи — регулярные операции по расписанию (`db/tasks.php`).
- **Результат:** сайт не тормозит, большие объёмы обрабатываются спокойно.
- **Подводный камень:** задача должна быть **идемпотентной** (повторный запуск не ломает данные) и уметь продолжать после сбоя.

### 4.7 SAML SSO

- **Задача:** слушателям не нужен отдельный пароль, организации хотят вход через свою систему.
- **Что делал:** настроил аутентификацию SAML для провайдеров идентификации организаций-партнёров.
- **Как сделано (типично):** обмен метаданными SP ↔ IdP, соответствие атрибутов, создание пользователя при первом входе, сертификаты.
- **Что уточнить:** какой плагин (обычно `auth_saml2`); как решал вопрос нескольких IdP.

### 4.8 Свой модуль активности (разборы клинических случаев)

- **Задача:** стандартных элементов Moodle не хватает для учёта клинических случаев и научного прогресса.
- **Что делал:** собственный `mod`-плагин: свои таблицы, права, формы настроек.
- **Что входит в такой модуль:**
    - **Таблицы** — `db/install.xml`, миграции `db/upgrade.php`.
    - **Права** — `db/access.php`, проверка `require_capability`.
    - **Форма настроек** — `mod_form.php`.
    - **Функции для ядра** — `lib.php` (добавить, изменить, удалить экземпляр).
    - **Страница просмотра** — `view.php`, шаблоны.
    - **Для полноты** — Privacy API (персональные данные), Backup/Restore.
- **Как рассказать:** «Проектировал схему данных, права и интерфейс под процесс заказчика».

### 4.9 REST веб-сервисы

- **Задача:** учётные записи и записи на курсы должны синхронизироваться со сторонними системами в реальном времени.
- **Что делал:** проектировал и документировал внешние функции Moodle.
- **Как сделано:**
    - Класс внешней функции с описанием параметров и возвращаемого значения.
    - Проверка параметров, контекста и прав.
    - Регистрация в `db/services.php`, добавление в сервис, токен.

### 4.10 Мониторинг: Grafana и Sentry

### 5.4 Многошаговая форма самооценки (Form API + Chart.js)

- **Что делал:** многошаговая форма на Form API, мгновенный подсчёт, графики на Chart.js.
- **Как сделано (типично):**
    1. Форма делится на шаги; состояние сохраняется между шагами.
    2. Проверка ответов в `validation()`.
    3. Подсчёт баллов на сервере (и/или мгновенно на клиенте).
    4. Результаты передаются в JS-модуль, он строит график.
- **Подводный камень:** итоговый балл считай на сервере, клиенту не доверяй.

## 7. Вопросы и ответы по CV

> [!question] Расскажи о себе
> 
> **Ответ:** Инженер-программист, 4+ года на PHP, специализируюсь на Moodle. Пишу плагины, темы и интеграции для медицинских, научных и государственных организаций. Сейчас работаю над платформой непрерывного медицинского образования: DeepL, Solr, SAML, фоновые задачи, веб-сервисы, мониторинг. До этого делал обучающую платформу для европейских институтов.

> [!question] Какую самую сложную задачу решал?
> 
> **Ответ:** (выбери одну и расскажи по схеме «ситуация → что делал → результат»). Хорошие кандидаты: перенос правок ядра в плагины; многошаговая форма самооценки; интеграция DeepL с фоновой обработкой; подключение Solr.

> [!question] Почему не стоит править ядро Moodle?
> 
> **Ответ:** При обновлении правки пропадут или конфликтуют, сложно поддерживать. Moodle даёт плагины, колбэки, события, темы — через них можно расширить почти всё. Именно это я делал, когда переносил правки ядра в отдельные плагины.

> [!question] Чем `local`-плагин отличается от `mod`?
> 
> **Ответ:** `mod` — элемент курса, который добавляют в секцию (задание, форум, мой модуль клинических случаев). `local` — универсальный плагин для логики, которая не привязана к одному виду: интеграции, сервисы, доработки. Мой плагин DeepL — `local`, потому что это сервис, а не элемент курса.

> [!question] Зачем нужны Task API и в чём разница между плановой и разовой задачей?
> 
> **Ответ:** Тяжёлую работу нельзя делать в запросе пользователя — тайм-аут и тормоза. Плановая задача выполняется по расписанию (cron), разовая ставится в очередь из кода с данными. Я выносил в них массовый перевод и массовую запись на курсы.

> [!question] Как сделать задачу устойчивой к сбоям?
> 
> **Ответ:** Идемпотентность (повторный запуск безопасен), порционная обработка, логирование, понятные ошибки. Для разовых задач Moodle умеет повторять неудачные запуски.

> [!question] Как ты подключал Solr и чем он лучше стандартного поиска?
> 
> **Ответ:** Развернул Solr, подключил через плагин движка, включил поисковые области, настроил индексацию. Стандартный поиск работает на БД и на больших объёмах медленный; Solr — полнотекстовый индекс, быстрее и качественнее. После поиска Moodle всё равно проверяет права пользователя.

> [!question] Как работает SSO по SAML?
> 
> **Ответ:** Пользователь заходит на платформу (SP), его перенаправляют на систему организации (IdP), он входит там, IdP возвращает подписанное утверждение с атрибутами, платформа его проверяет и создаёт или находит пользователя. Настройка: обмен метаданными, сертификаты, сопоставление атрибутов.

> [!question] Как устроен веб-сервис Moodle?
> 
> **Ответ:** Внешняя функция — класс с описанием параметров, логикой и описанием ответа. Регистрируется в `db/services.php`, добавляется в сервис, вызывающему выдаётся токен. Внутри обязательно: проверка параметров, контекста и прав.

> [!question] Как защищаешь веб-сервис?
> 
> **Ответ:** Токен, сервисный пользователь с минимальными правами, проверка контекста и capabilities, валидация входных данных, ограничения по IP при необходимости, логирование.

> [!question] Как работает DML API и почему им, а не «голым» SQL?
> 
> **Ответ:** `$DB` — обёртка над БД: читает и пишет записи, использует плейсхолдеры (защита от инъекций), подставляет префикс таблиц и работает одинаково на MySQL и PostgreSQL. Это важно, потому что у меня были проекты на обеих БД.

> [!question] Как Moodle управляет схемой БД?
> 
> **Ответ:** Таблицы описаны в `db/install.xml`, изменения — в `db/upgrade.php` с повышением версии в `version.php`. Moodle сам применяет миграции при обновлении.

> [!question] Как переопределить шаблон в теме?
> 
> **Ответ:** Создать дочернюю тему с родителем Boost и положить свой Mustache-шаблон с тем же именем в `templates/` темы. Moodle возьмёт его вместо шаблона родителя.

> [!question] Что такое Mustache и почему без логики?
> 
> **Ответ:** Шаблонизатор, где в шаблоне только вывод и простые циклы и условия. Логика остаётся в PHP, шаблон — только вид. Это упрощает переопределение и тестирование.

> [!question] Как строится страница с графиком на Chart.js?
> 
> **Ответ:** PHP готовит данные, передаёт их в AMD-модуль через `js_call_amd`, модуль строит график на `<canvas>`. Вёрстка — шаблон Mustache.

> [!question] Что такое capabilities и зачем они?
> 
> **Ответ:** Права доступа. Описываются в `db/access.php`, проверяются в коде через `require_capability()` или `has_capability()`. Назначаются ролям. Я использовал их в модуле клинических случаев.

> [!question] Что такое подплагины и зачем они в анкетировании?
> 
> **Ответ:** Плагины внутри плагина. Основной модуль задаёт точку расширения, а каждый тип вопроса — отдельный подплагин. Новый тип добавляется без правки основного кода.

> [!question] Как обеспечить безопасность в Moodle-плагине?
> 
> **Ответ:** `require_login`, проверка прав, `required_param` с типами `PARAM_*`, плейсхолдеры в SQL, `sesskey` для изменяющих действий, экранирование вывода, не доверять данным с клиента.

> [!question] Как ты находил и исправлял медленные страницы?
> 
> **Ответ:** Grafana показывала проблемные страницы и время, Sentry — ошибки. Дальше профилирование: тяжёлые запросы к БД, лишние циклы, операции, которые нужно вынести в фон. Затем исправление и проверка по тем же графикам.

> [!question] Как организуешь код и работу в команде?
> 
> **Ответ:** Стандарты Moodle (PHPDoc, именование Frankenstyle), ветки в Git, merge request и ревью кода. Прошёл через GitLab и BitBucket.

> [!question] Как организовано окружение разработки?
> 
> **Ответ:** Docker и Docker Compose: контейнеры для веб-сервера и БД (и при необходимости Solr), единое окружение у всех, запуск одной командой.

> [!question] Как обновлять Moodle с кастомными плагинами?
> 
> **Ответ:** Проверить совместимость плагинов с новой версией (`version.php`, `requires`), прогнать на тестовом стенде, проверить миграции и задачи. Если нет правок ядра, обновление проходит намного легче.
