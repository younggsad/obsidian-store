# 1. LLM и AI-агенты

### 1. Что такое LLM?

**LLM (Large Language Model)** — большая языковая модель, обученная на большом объёме данных. Она обрабатывает текст и генерирует ответы, предсказывая следующие токены с учётом контекста.

### 2. Чем LLM отличается от AI-агента?

LLM генерирует ответы, а AI-агент использует модель для достижения цели: планирует действия, вызывает инструменты, анализирует результаты и при необходимости повторяет цикл.

### 3. Когда использовать LLM, а когда агента?

LLM подходит для генерации текста, объяснений и простых преобразований. Агент нужен для многошаговых задач, где требуется работать с файлами, запускать тесты, использовать API и проверять результаты.

### 4. Какие риски есть у AI-агентов?

Основные риски: prompt injection, утечка секретов, небезопасное выполнение команд, избыточные полномочия, ошибки в коде и неконтролируемые действия.

# 2. MCP

### 5. Что такое MCP?

**MCP (Model Context Protocol)** — протокол, позволяющий AI-приложениям стандартизированно подключаться к внешним инструментам и источникам данных.

### 6. Как работает MCP?

AI-клиент подключается к MCP-серверу, получает список доступных инструментов и при необходимости вызывает их. Сервер выполняет операцию и возвращает результат клиенту.

### 7. Что такое MCP Client и MCP Server?

- **MCP Client** — компонент внутри AI-приложения, который устанавливает соединение с MCP-сервером.
- **MCP Server** — предоставляет инструменты, ресурсы или шаблоны промптов для работы с внешней системой.

### 8. Где настраивается MCP?

В конфигурации MCP-клиента. Например, Claude Code поддерживает конфигурацию на уровне проекта и пользователя. Конкретный формат зависит от способа подключения и используемого инструмента.

### 9. Чем MCP отличается от прямого API?

Прямой API требует отдельной интеграции с конкретным сервисом. MCP предоставляет стандартизированный способ описания и вызова инструментов, упрощая подключение разных систем к AI-клиентам.

### 10. Когда нужен MCP?

Когда агенту необходимо работать с внешними системами: Figma, GitHub, базами данных, документацией или браузером. Для простой задачи без внешних интеграций MCP не обязателен.

# 3. Токены, контекст и память

### 11. Что такое токен?

**Token** — единица текста, которую обрабатывает языковая модель. Это может быть слово, часть слова, знак препинания или другой фрагмент текста.

### 12. Что такое context window?

**Context window** — максимальный объём токенов, доступных модели в рамках одного запроса. В него могут входить инструкции, история диалога, файлы и результаты инструментов.

### 13. Как контекст влияет на качество ответа?

Если контекст слишком большой, важная информация может потеряться среди второстепенных деталей. Противоречивые или устаревшие данные также могут ухудшить ответ.

### 14. Что такое context degradation?

Это снижение качества работы модели по мере усложнения или переполнения контекста. Модель может хуже учитывать важные детали, путать требования или повторять уже выполненную работу.

### 15. Что такое compaction?

**Compaction** — сжатие истории взаимодействия в более короткое представление с сохранением ключевых фактов, решений и текущего состояния задачи.

### 16. Когда нужно делать compaction?

Когда контекст становится слишком большим, а работа ещё не завершена. Перед сжатием желательно сохранить требования, принятые решения, изменённые файлы, результаты тестов и оставшиеся задачи.

### 17. Когда лучше начать новый чат?

Когда текущая история содержит много устаревшей информации, задача существенно изменилась или модель постоянно возвращается к прежним решениям. Перед переходом нужно сохранить актуальное состояние проекта.

### 18. Что такое prompt caching?

**Prompt caching** позволяет повторно использовать обработанное представление подходящей повторяющейся части промпта, чтобы уменьшить задержку и стоимость обработки. Он не заменяет контекст и не сохраняет автоматически состояние проекта.

### 19. Как реализовать собственное кэширование?

Можно сохранять результаты операций по ключу, сформированному из входных данных, с использованием TTL и механизма инвалидации. При изменении исходных данных кэш нужно обновлять.

### 20. Что такое Memory Bank?

**Memory Bank** — набор файлов, сохраняющих важный контекст проекта между сессиями: архитектуру, требования, решения и текущий прогресс.

### 21. Какие есть альтернативы Memory Bank?

`CLAUDE.md`, `AGENTS.md`, документация проекта, спецификации, планы, задачи в GitHub Issues и краткие файлы состояния. Главное — сохранять актуальные факты вне истории чата.

### 22. Чем статический контекст отличается от динамического?

- **Static context** — относительно постоянные инструкции и правила проекта.
- **Dynamic context** — текущая задача, выбранные файлы, результаты команд и изменения в процессе работы.

### 23. Что такое Context Engineering?

**Context Engineering** — организация информации, инструментов и инструкций, которые получает модель, для повышения качества и предсказуемости её работы.

### 24. Чем Context Engineering отличается от Prompt Engineering?

**Prompt Engineering** фокусируется на формулировке запроса. **Context Engineering** охватывает всю информацию, доступную модели: файлы, инструкции, историю, результаты инструментов и другие источники.

# 4. Модели и параметры

### 25. Что такое weights модели?

**Weights (веса)** — обученные числовые параметры нейронной сети, определяющие, как она преобразует входные данные в результат.

### 26. Что означает количество параметров модели?

Количество параметров показывает размер обученных числовых представлений модели. Большее количество может требовать больше памяти и вычислений, но само по себе не гарантирует лучшего качества.

### 27. Почему некоторые модели быстрее и дешевле?

Они могут быть меньше, использовать более эффективную архитектуру или оптимизированную инфраструктуру. Такие модели часто выгодны для простых и повторяющихся задач.

### 28. Когда использовать быструю модель, а когда сильную?

Быструю — для простых изменений, классификации и форматирования. Сильную — для сложной архитектуры, трудной отладки, анализа безопасности и многошагового планирования.

### 29. Что такое параметры генерации?

Это настройки, влияющие на формирование ответа, например `temperature` и ограничения длины вывода. Они управляют поведением генерации, а не изменяют обученные веса модели.

### 30. Один большой промпт или несколько маленьких?

Для сложной задачи лучше разделить работу на этапы: анализ, планирование, реализацию и проверку. Для простой задачи достаточно одного точного промпта.

# 5. Claude Code и инструкции проекта

### 31. Что такое `CLAUDE.md`?

Файл с инструкциями для Claude Code. В нём обычно описывают архитектуру проекта, команды запуска и тестирования, соглашения по коду и важные ограничения.

### 32. Что такое `AGENTS.md`?

Файл с инструкциями для AI-агентов, поддерживающих этот формат. Он может содержать правила разработки и команды проверки проекта. Поддержка зависит от конкретного инструмента.

### 33. Что нужно записывать в `CLAUDE.md`?

Только полезную и относительно постоянную информацию: структуру проекта, команды, стандарты кода, правила тестирования и важные ограничения. Не стоит помещать туда всю документацию или описание каждой задачи.

### 34. Когда обновлять `CLAUDE.md`?

Когда меняются архитектура, команды, соглашения или постоянные правила разработки. Временные детали отдельной задачи лучше хранить в её спецификации или плане.

### 35. Что такое Skills?

**Skills** — переиспользуемые инструкции, описывающие, как агенту выполнять определённый тип задач. Например, анализировать безопасность, писать тесты или проводить code review.

### 36. Что такое `SKILL.md`?

Файл с описанием Skill. Обычно он содержит YAML frontmatter с метаданными, такими как имя и назначение, а также основную инструкцию с последовательностью действий и ограничениями.

### 37. Лучше одна большая Skill или несколько маленьких?

Обычно лучше несколько специализированных Skills с чёткими задачами. Это упрощает поддержку и позволяет использовать нужные инструкции без загрузки всего материала сразу.

### 38. Что такое role prompting?

**Role prompting** — задание модели определённой роли, например «ты — senior backend developer» или «ты — security reviewer». Роль помогает направить анализ, но сама по себе не гарантирует компетентность или безопасность.

### 39. Что такое subagents?

**Subagents** — специализированные агенты, которым основной агент делегирует отдельные задачи. Они могут иметь собственные инструкции, контекст и ограничения инструментов.

### 40. Когда использовать subagents?

Когда задачу можно разделить на независимые части: один агент анализирует безопасность, другой изучает архитектуру, третий проверяет тесты. Результаты затем объединяются и проверяются основным агентом.

### 41. Что такое hooks?

**Hooks** — автоматические действия, запускаемые при определённых событиях рабочего процесса, например перед выполнением команды или после изменения файла. Они могут использоваться для проверок, логирования и автоматизации.

### 42. Что такое hook event?

**Hook event** — событие, которое запускает hook. Например, событие перед вызовом инструмента позволяет проверить операцию до её выполнения. Конкретные события зависят от инструмента.

### 43. Что такое custom commands?

**Custom commands** — пользовательские команды для повторяющихся сценариев. Они позволяют запускать стандартный процесс, например проверку кода или подготовку отчёта, без повторного написания длинного промпта.

# 6. Specs и SDD

### 44. Что такое спецификация?

**Specification (spec)** — документ, описывающий, что нужно сделать, зачем это нужно, какие требования существуют и по каким критериям проверяется результат.

### 45. Что такое SDD?

**SDD (Spec-Driven Development)** — подход, при котором разработка начинается со спецификации, а затем переходит к планированию, реализации и проверке соответствия требованиям.

### 46. Чем spec отличается от plan и tasks?

- **Spec** — что и зачем нужно сделать.
- **Plan** — как это реализовать.
- **Tasks** — конкретные шаги реализации, которые можно выполнять и проверять.

### 47. Когда использовать SDD?

Для сложных, неоднозначных или многоэтапных задач, особенно если затрагиваются несколько компонентов. Для небольшого очевидного исправления достаточно короткого промпта и проверки результата.

### 48. Что лучше: сначала писать код или сначала составлять план?

Для простой задачи можно сразу писать код. Для сложной лучше сначала изучить проект, уточнить требования, составить план, а затем реализовывать поэтапно.

### 49. Как выглядит рабочий процесс SDD?

**Specify → Clarify → Plan → Tasks → Implement → Test → Review.**

Сначала фиксируются требования, затем устраняются неоднозначности, составляется план, выполняются задачи и проверяется результат.

# 7. Безопасность AI-разработки

### 50. Какие данные нельзя отправлять в LLM без разрешения?

Пароли, API-ключи, токены доступа, приватные ключи, персональные данные и конфиденциальный код или документы. Перед использованием внешней модели нужно учитывать политику организации и условия обработки данных.

### 51. Что такое Prompt Injection?

**Prompt Injection** — попытка повлиять на поведение модели через недоверенные инструкции, например текст на веб-странице или в документе, который агент анализирует.

### 52. Как защититься от Prompt Injection?

Разделять доверенные инструкции и недоверенные данные, ограничивать полномочия инструментов, изолировать выполнение команд и требовать подтверждения опасных действий. Результаты инструментов нужно считать потенциально недоверенными.

### 53. Достаточно ли запретить опасные слова через regex?

Нет. Regex может обнаружить отдельные шаблоны, но не понимает смысл и легко обходится. Безопасность должна основываться на ограничении полномочий, проверке действий и изоляции среды.

### 54. Как задавать приоритет инструкций?

Нужно использовать предусмотренную инструментом иерархию инструкций и не считать содержимое файлов, сайтов или результатов инструментов более приоритетным, чем доверенные системные правила. Однако сама формулировка приоритетов не заменяет технических ограничений.

### 55. Что такое allowlist и denylist?

- **Allowlist** — список разрешённых действий или ресурсов.
- **Denylist** — список запрещённых действий или ресурсов.

Allowlist обычно обеспечивает более строгий контроль, если по умолчанию доступ запрещён.

### 56. Как ограничить доступ агента к файлам?

Использовать настройки разрешений, например `allow`, `ask` и `deny` в Claude Code, а для строгой изоляции — sandbox и системные ограничения доступа. Инструкции в промпте сами по себе доступ не блокируют.

### 57. Как определить, какие данные доступны модели в контексте?

Явно передавать нужные файлы и инструкции, использовать `CLAUDE.md`, path-specific rules и контекст задачи. Но ограничение контекста не означает запрета на чтение других файлов: для этого нужны отдельные ограничения доступа.

### 58. Какие уязвимости могут возникнуть при AI-assisted development?

Prompt injection, утечка секретов, небезопасное выполнение команд, обход авторизации, инъекции, небезопасная обработка вывода и использование уязвимых зависимостей.

### 59. Как проверять код, написанный AI?

Запускать тесты, линтеры и статический анализ, изучать diff, проверять авторизацию и обработку входных данных, а также проводить code review. Нельзя считать код безопасным только потому, что модель утверждает обратное.

### 60. Что такое принцип наименьших привилегий?

**Principle of Least Privilege** — предоставление агенту только тех прав и инструментов, которые необходимы для текущей задачи. Это уменьшает возможный ущерб от ошибки или атаки.

# 8. Практика: Skills, Subagents и Agent Teams

### 61. Как создать собственную Skill?

Создать каталог Skill и файл `SKILL.md`, описать её назначение, входные данные, шаги работы, ограничения и критерии результата. Затем проверить Skill на реальной задаче.

### 62. Как создать собственного subagent?

Создать файл определения агента, например в `.claude/agents/`, задать имя, описание, инструкции и необходимые инструменты. Агенту следует выдавать только необходимые полномочия.

### 63. Как выбрать инструменты для subagent?

В зависимости от задачи. Например, агенту для code review могут быть нужны инструменты чтения и поиска, но не редактирования. Агенту, который реализует функцию, могут понадобиться инструменты изменения файлов и запуска тестов.

### 64. Чем Skill отличается от subagent?

**Skill** описывает переиспользуемый процесс или набор инструкций. **Subagent** — отдельный исполнитель, которому можно делегировать работу со своим контекстом и набором инструментов.

### 65. Что такое Agent Teams?

**Agent Teams** — организация нескольких агентов, работающих над общей целью и координирующих результаты. Поддержка и механизм координации зависят от конкретной платформы.

### 66. Как эффективно распределить работу между несколькими агентами?

Разделить задачу на независимые части с чёткими результатами. Например, один агент анализирует требования, другой изучает безопасность, третий проверяет тесты. Нужно избегать одновременного изменения одних и тех же файлов и объединять результаты через проверку.

### 67. Какой главный принцип работы с AI-агентами?

**Не делегировать агенту больше полномочий, чем необходимо, и проверять результат каждого важного этапа.** Агент ускоряет работу, но ответственность за корректность и безопасность результата остаётся у разработчика.

## 10. Введение в AI-Assisted Development

### 68. Что такое AI-Assisted Development?

**AI-Assisted Development** — подход к разработке ПО, при котором разработчик использует AI для анализа требований, написания кода, тестирования, отладки и документирования. Разработчик контролирует процесс и отвечает за итоговое качество.

### 69. Чем AI-assisted development отличается от обычного программирования?

При обычном подходе разработчик преимущественно сам пишет и проверяет код. При AI-assisted development часть работы делегируется модели или агенту, а разработчик больше внимания уделяет постановке задач, архитектуре и проверке результата.

### 70. Что такое agentic coding?

**Agentic coding** — разработка, при которой AI-агент не только предлагает код, но и самостоятельно выполняет последовательность действий: изучает проект, редактирует файлы, запускает команды, анализирует ошибки и исправляет их.

### 71. Какова роль разработчика при работе с AI?

Разработчик определяет цель, задаёт ограничения, принимает архитектурные решения, контролирует доступы и проверяет результат. AI ускоряет работу, но не заменяет инженерную ответственность.

## 11. Современные инструменты

### 72. Какие современные инструменты используются для AI-assisted development?

Примеры:

- **Claude Code** — агент для работы с кодовой базой и терминалом.
- **OpenAI Codex** — инструмент для делегирования задач по разработке AI-агенту.
- **Google Antigravity** — среда разработки, ориентированная на работу с агентами.
- **GitHub Copilot** — AI-помощник для разработки и работы с репозиториями.
- **Cursor** — редактор кода с AI-функциями.
- **Figma MCP** — интеграция AI-инструментов с Figma через MCP.

### 73. Как выбрать инструмент для разработки?

Нужно учитывать сложность задач, качество работы с репозиторием, доступные модели, поддержку терминала и инструментов, безопасность, стоимость и интеграцию с существующим workflow.

### 74. Что важнее: модель или инструмент?

Оба компонента важны. Модель определяет возможности рассуждения и генерации, а инструмент обеспечивает контекст, доступ к файлам, вызов команд, управление разрешениями и проверку результата.

## 12. Prompt Engineering

### 75. Что такое Prompt Engineering?

**Prompt Engineering** — проектирование запросов к модели для получения более точных и полезных результатов. Оно включает постановку цели, предоставление контекста, ограничений, формата ответа и критериев качества.

### 76. Из чего состоит хороший промпт для программирования?

Обычно он включает:

1. **Goal** — цель.
2. **Context** — необходимая информация о проекте.
3. **Constraints** — ограничения.
4. **Expected output** — ожидаемый результат.
5. **Acceptance criteria** — условия успешного выполнения.

### 77. Как улучшить слабый промпт?

Убрать неоднозначность, указать конкретные файлы или компоненты, определить ограничения, описать ожидаемое поведение и попросить проверить результат.

### 78. Что лучше: описывать решение или желаемый результат?

Обычно лучше описывать желаемый результат и ограничения, позволяя агенту исследовать проект и выбрать подходящую реализацию. Если архитектура уже определена, необходимо явно указать технические требования.

### 79. Как просить AI исправить ошибку?

Предоставить сообщение об ошибке, шаги воспроизведения, ожидаемое и фактическое поведение. Попросить найти причину, предложить минимальное исправление и подтвердить его тестами.

## 13. Meta Prompting и Context-Aware Prompt Enhancement

### 80. Что такое Meta Prompting?

**Meta Prompting** — подход, при котором модель помогает создавать, улучшать или структурировать промпты для другой задачи.

Например, вместо немедленной реализации можно попросить AI сначала сформулировать уточняющие вопросы и подготовить качественный промпт для реализации.

### 81. Что такое Context-Aware Prompt Enhancement?

Это улучшение запроса с учётом доступного контекста: структуры проекта, используемых технологий, соглашений команды и конкретной задачи.

Например, агент изучает проект на React и TypeScript и уточняет промпт так, чтобы реализация использовала существующие компоненты и правила проекта.

### 82. Чем Meta Prompting отличается от Context-Aware Prompt Enhancement?

- **Meta Prompting** — работа над самим промптом: его структурой, инструкциями и формулировками.
- **Context-Aware Enhancement** — адаптация промпта к конкретной ситуации и имеющимся данным.

Эти подходы можно использовать вместе.

## 14. GitHub Spec Kit

### 83. Что такое GitHub Spec Kit?

**GitHub Spec Kit** — открытый инструментарий для организации разработки на основе спецификаций. Он предоставляет шаблоны, команды и последовательный workflow, который помогает агенту перейти от требований к реализации. [GitHub](https://github.com/github/spec-kit/blob/main/README.md?utm_source=chatgpt.com)

### 84. Для чего нужен Spec Kit, если можно написать промпт самостоятельно?

Он стандартизирует процесс разработки: сохраняет требования и план в файлах, помогает разбивать работу на задачи и проверять согласованность артефактов. Это особенно полезно для больших изменений и повторяемых процессов.

### 85. Какие артефакты создаёт Spec Kit?

В зависимости от процесса это могут быть:

- `constitution.md` — принципы проекта;
- `spec.md` — требования к функции;
- `plan.md` — технический план;
- `tasks.md` — список задач;
- чек-листы и результаты анализа согласованности.

Конкретная структура зависит от версии и выбранного процесса. [GitHub Docs](https://github.github.com/spec-kit/quickstart.html?utm_source=chatgpt.com)

### 86. Что делает команда `/speckit-specify`?

Создаёт спецификацию функции на основе описания задачи. Она должна объяснять, **что нужно реализовать и зачем**, не погружаясь преждевременно в детали реализации.

### 87. Что делает `/speckit-clarify`?

Выявляет неоднозначности и пробелы в требованиях, задаёт уточняющие вопросы и помогает обновить спецификацию до начала планирования.

### 88. Что делает `/speckit-plan`?

Подготавливает технический план реализации: архитектуру, технологии, структуру решения и другие технические детали.

### 89. Что делает `/speckit-tasks`?

Преобразует спецификацию и технический план в конкретные задачи, учитывая зависимости и порядок выполнения.

### 90. Что делает `/speckit-implement`?

Выполняет подготовленные задачи реализации. После этого разработчик должен проверить изменения и результаты тестирования.

### 91. Что делает `/speckit-analyze`?

Проверяет согласованность спецификации, плана и задач, выявляя противоречия, пробелы и несоответствия.

### 92. Что делает `/speckit-converge`?

Сверяет текущее состояние реализации с требованиями и другими артефактами. Если остаются пробелы, процесс может сформировать дополнительные задачи для устранения несоответствий. [GitHub Docs](https://github.github.com/spec-kit/quickstart.html?utm_source=chatgpt.com)

### 93. Все ли команды Spec Kit нужно запускать всегда?

Нет. Для небольшой функции можно использовать короткий workflow. Для сложной задачи полезно добавить уточнение требований, чек-листы и анализ согласованности.

### 94. Как установить GitHub Spec Kit?

Основной способ установки через `uv`:

```
uv tool install specify-cli
specify init my-project --integration codex
cd my-project
```

Затем открыть проект в выбранном AI-инструменте и запускать команды Spec Kit в чате агента. Название интеграции нужно выбирать из поддерживаемых текущей версией Spec Kit. [GitHub Docs](https://github.github.com/spec-kit/quickstart.html?utm_source=chatgpt.com)

### 95. Можно ли использовать Spec Kit в существующем проекте?

Да. Spec Kit можно подключить к существующей кодовой базе. Перед этим нужно изучить текущую архитектуру, определить существующие соглашения и убедиться, что новые спецификации не противоречат проекту.

## 15. Constitution

### 96. Что такое Constitution в Spec Kit?

**Constitution** — набор базовых принципов и ограничений проекта, которым должны соответствовать спецификации, планы и реализация.

Например:

- использовать TypeScript;
- соблюдать существующую архитектуру;
- писать тесты для бизнес-логики;
- не хранить секреты в коде;
- проверять права доступа.

### 97. Чем Constitution отличается от спецификации?

Constitution определяет **общие правила для проекта**, а спецификация описывает требования к конкретной функции. Constitution обычно создают в начале работы над проектом и меняют при изменении принципов разработки.

## 16. Post-MVP

### 98. Что такое MVP?

**MVP (Minimum Viable Product)** — минимальная версия продукта, которая реализует основные пользовательские сценарии и позволяет проверить гипотезу на практике.

### 99. Что такое Post-MVP?

**Post-MVP** — этап развития продукта после создания минимально жизнеспособной версии. На этом этапе улучшают функциональность, надёжность, безопасность, производительность и пользовательский опыт на основе обратной связи.

### 100. Как использовать AI для Post-MVP?

Собирать обратную связь, анализировать ошибки и метрики, составлять список улучшений, оценивать риски и приоритеты, а затем реализовывать изменения небольшими проверяемыми итерациями.

### 101. Нужно ли после MVP сразу добавлять все запланированные функции?

Нет. Следует оценивать пользовательскую ценность, стоимость реализации, риски и обратную связь. В первую очередь устраняют критические проблемы и реализуют наиболее полезные улучшения.

## 17. Frameworks и Task-Master AI

### 102. Что такое AI agent framework?

**AI agent framework** — программный фреймворк для создания агентов. Он может предоставлять управление циклом агента, вызов инструментов, передачу состояния, память, обработку ошибок и координацию нескольких агентов.

### 103. Зачем использовать framework, если уже есть LLM API?

LLM API предоставляет доступ к модели, а framework помогает организовать вокруг неё рабочий процесс: инструменты, состояние, последовательность действий, обработку ошибок и взаимодействие агентов.

### 104. Что такое Task Master AI?

**Task Master AI** — инструмент для управления задачами разработки с помощью AI. Он помогает преобразовывать требования и спецификации в структурированные задачи и подзадачи, организовывать их выполнение и отслеживать прогресс.

### 105. Чем Task Master AI отличается от Spec Kit?

Они могут использоваться вместе, но акценты различаются:

- **Spec Kit** структурирует путь от требований к плану, задачам, реализации и проверке соответствия спецификации.
- **Task Master AI** делает акцент на декомпозиции требований в управляемые задачи и организации их выполнения.

Конкретные возможности зависят от версии и интеграций. Ни один из инструментов сам по себе не гарантирует корректность реализации.

## 18. NotebookLM

### 106. Что такое NotebookLM?

**NotebookLM** — AI-инструмент Google для работы с предоставленными источниками. Он помогает анализировать документы, отвечать на вопросы по материалам, находить связи между идеями и создавать учебные обзоры.

### 107. Чем NotebookLM отличается от обычного чат-бота?

NotebookLM ориентирован на работу с конкретным набором источников, предоставленных пользователем. Это удобно, когда нужно изучить курс, документацию или набор статей, не смешивая их с произвольной информацией из разговора.

### 108. Как использовать NotebookLM для подготовки к собеседованию?

1. Добавить материалы курса и документацию.
2. Попросить составить структурированный конспект.
3. Создать вопросы и краткие ответы.
4. Проверить непонятные темы через вопросы по источникам.
5. Использовать Audio Overview для повторения материала на слух.

NotebookLM также поддерживает аудиообзоры в разных форматах, включая подробное обсуждение, краткое резюме и критический разбор. Сгенерированный материал всё равно необходимо проверять на точность. [Google Help](https://support.google.com/gemininotebook/answer/16212820?hl=en&utm_source=chatgpt.com)

## 19. Проверка качества AI-generated code

### 109. Что такое Quality Gates?

**Quality Gates** — обязательные проверки, которые должны пройти изменения перед переходом к следующему этапу разработки или слиянием в основную ветку.

Примеры: тесты, линтер, статический анализ, проверка безопасности и code review.

### 110. Что такое Verification Harness?

**Verification Harness** — набор автоматизированных механизмов, позволяющих объективно проверять результат работы агента: тесты, линтеры, анализаторы, проверки сборки и другие критерии приёмки.

Он помогает отличать реально работающий код от кода, который лишь выглядит правильным.

### 111. Как организовать проверку кода, созданного агентом?

Рекомендуемый порядок:

1. Проверить diff и убедиться, что изменения соответствуют задаче.
2. Запустить линтер и форматирование.
3. Запустить статический анализ.
4. Запустить unit- и integration-тесты.
5. Проверить критические сценарии и безопасность.
6. Выполнить code review.
7. Создать PR с описанием изменений и результатов проверок.

### 112. Почему недостаточно попросить AI проверить собственный код?

Модель может не заметить собственную ошибку или неверно интерпретировать результат. Поэтому нужны независимые проверки: автоматические тесты, статический анализ и проверка человеком.

## 20. Self-healing CI/CD

### 113. Что такое CI/CD?

- **CI (Continuous Integration)** — автоматическая проверка изменений при их интеграции в кодовую базу.
- **CD (Continuous Delivery/Deployment)** — автоматизация подготовки релиза или доставки изменений в окружение.

### 114. Что такое Self-healing CI/CD?

**Self-healing CI/CD** — подход, при котором AI-агент анализирует сбой в pipeline, пытается определить причину, предлагает или вносит исправление и повторно запускает проверки.

Это не означает, что pipeline всегда может исправить себя без участия разработчика.

### 115. Как выглядит self-healing workflow?

1. Разработчик создаёт commit или PR.
2. CI запускает тесты и анализаторы.
3. При ошибке агент получает логи и информацию об изменениях.
4. Агент анализирует причину и предлагает исправление.
5. Исправление проверяется повторным запуском pipeline.
6. Если проблема не устранена или изменение рискованное, подключается разработчик.

### 116. Какие риски есть у self-healing CI/CD?

Агент может скрыть настоящую проблему, изменить тест так, чтобы он перестал выявлять ошибку, или внести небезопасное исправление. Поэтому необходимо ограничивать права агента, сохранять логи и требовать проверки перед слиянием и деплоем.

## 21. Deployment Lovable-прототипа в Google Cloud

### 117. Что такое Lovable?

**Lovable** — инструмент для создания приложений с помощью AI по текстовому описанию. Он помогает быстро получить прототип интерфейса и приложения, после чего результат можно дорабатывать и подготавливать к развёртыванию.

### 118. Как перенести приложение из Lovable в Google Cloud?

Общий workflow:

1. Создать прототип в Lovable.
2. Подключить репозиторий GitHub и получить исходный код.
3. Проверить код локально, установить зависимости и запустить сборку.
4. Подготовить приложение к production.
5. Выбрать подходящий сервис Google Cloud.
6. Настроить переменные окружения, секреты и необходимые сервисы.
7. Развернуть приложение и проверить его работу.

Конкретный способ зависит от архитектуры приложения и используемых сервисов.

### 119. Какой сервис Google Cloud выбрать для развёртывания?

Зависит от приложения:

- **Cloud Run** — для контейнеризированных приложений и серверов; поддерживает масштабирование без самостоятельного управления серверами.
- **Cloud Storage с подходящим механизмом публикации** — для хранения статических файлов, но для полноценного публичного сайта могут потребоваться дополнительные настройки.
- Другие сервисы Google Cloud могут понадобиться для базы данных, хранения файлов, секретов или фоновых задач.

Cloud Run позволяет развернуть контейнер или поддерживаемое приложение из исходного кода. [Google Cloud Documentation](https://docs.cloud.google.com/run/docs/overview/what-is-cloud-run?utm_source=chatgpt.com)

### 120. Как развернуть приложение на Cloud Run?

Типичный процесс:

1. Проверить production-сборку.
2. Подготовить Dockerfile, если нужен собственный контейнер.
3. Собрать и разместить образ в реестре, например Artifact Registry.
4. Настроить права доступа и переменные окружения.
5. Выполнить развёртывание.
6. Проверить логи, доступность приложения и его основные сценарии.

Для образа контейнера используется, например:

```
gcloud run deploy SERVICE_NAME \
  --image IMAGE_URL \
  --region REGION
```

`SERVICE_NAME`, `IMAGE_URL` и `REGION` нужно заменить реальными значениями. Настройка публичного доступа должна соответствовать требованиям безопасности приложения. [Google Cloud Documentation](https://docs.cloud.google.com/run/docs/deploying?utm_source=chatgpt.com)

### 121. Что проверить перед production-деплоем Lovable-приложения?

Проверить сборку, обработку ошибок, адаптивность интерфейса, авторизацию, права доступа, хранение секретов, конфигурацию backend и базу данных. Также нужно убедиться, что тестовые данные и небезопасные настройки не попали в production.

## 22. Мультиагентные системы, open-source модели и harness

### 122. Что такое мультиагентная система?

**Multi-agent system** — система, в которой несколько AI-агентов выполняют разные задачи и взаимодействуют ради общей цели. Например, один анализирует требования, второй реализует код, третий проверяет безопасность.

### 123. Как организовать взаимодействие нескольких агентов?

Определить общую цель, разделить обязанности, установить формат передачи результатов и определить, кто принимает итоговые решения. Для параллельной работы необходимо контролировать конфликты файлов и зависимость задач друг от друга.

### 124. Какие проблемы возникают в мультиагентных системах?

Дублирование работы, противоречивые решения, увеличение стоимости и задержки, потеря контекста, конфликты при изменении файлов и распространение ошибок между агентами.

### 125. Всегда ли несколько агентов лучше одного?

Нет. Несколько агентов полезны, когда задачи можно разделить и параллельно исследовать. Для простой задачи один агент обычно дешевле, быстрее и проще в управлении.

### 126. Что такое open-source модель?

**Open-source model** — модель, доступная для использования и в определённой степени изучения, настройки или самостоятельного развёртывания. При этом важно проверять конкретную лицензию: доступность весов не означает автоматически неограниченных прав на использование.

### 127. Чем локальная модель отличается от облачной?

Локальная модель запускается на собственном компьютере или сервере, что может дать больший контроль над данными и инфраструктурой. Облачная модель обычно проще в использовании и может предоставлять больше вычислительных ресурсов без самостоятельного обслуживания оборудования.

### 128. Когда стоит использовать open-source модель?

Когда важны самостоятельное развёртывание, контроль над данными, настройка модели или снижение зависимости от внешнего поставщика. Нужно учитывать аппаратные требования, качество модели, стоимость обслуживания и лицензионные ограничения.

### 129. Что такое harness в AI-разработке?

**Agent harness** — программная среда, которая превращает языковую модель в работающего агента. Она управляет контекстом, инструментами, циклом выполнения, состоянием сессии, разрешениями и обработкой результатов. [Visual Studio Code](https://code.visualstudio.com/docs/agents/concepts/agent-harnesses?utm_source=chatgpt.com)

### 130. Чем harness отличается от модели?

Модель отвечает за генерацию и рассуждение. Harness организует её работу: передаёт контекст, предоставляет инструменты, обрабатывает вызовы, контролирует разрешения и сохраняет состояние процесса.

### 131. Из каких компонентов состоит типичный agent harness?

В зависимости от реализации он может включать:

- интерфейс взаимодействия с моделью;
- сбор и управление контекстом;
- вызов инструментов;
- цикл планирования и выполнения;
- состояние сессии и память;
- разрешения и подтверждение действий;
- логирование и обработку ошибок;
- проверки результата.

### 132. Почему harness важен для качества AI-разработки?

Даже сильная модель работает хуже, если не получает нужный контекст, не может использовать необходимые инструменты или не имеет механизма проверки результата. Хороший harness организует эти компоненты в управляемый процесс.

### 133. Что важнее для агента: модель, контекст или harness?

Они работают вместе. Модель обеспечивает возможности рассуждения, контекст даёт нужную информацию, а harness организует выполнение действий и контроль. Слабость любого из этих компонентов может ухудшить итоговый результат.
