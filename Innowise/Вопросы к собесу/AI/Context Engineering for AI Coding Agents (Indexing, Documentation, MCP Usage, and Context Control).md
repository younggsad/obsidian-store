## Почему context engineering важен

AI-агенты для программирования мощны, но их эффективность сильно зависит от **контекста**, который они получают: истории сообщений, файлов проекта, описаний инструментов, инструкций, документации, примеров и сгенерированного кода.

> [!tip] Ключевая идея 
> Качество контекста часто не менее важно, чем качество самой модели.

Причины сбоев агента:

- не знает, где реализован нужный код;
- полагается на устаревшие данные обучения;
- тратит токены на загрузку ненужных инструментов;
- переносит нерелевантную информацию из старых задач;
- становится медленнее и менее точным из-за разросшегося диалога.

**Context engineering** — практика управления тем, _что_ видит модель, _когда_ она это видит и _в каком объёме_. Цель — не «больше информации», а **нужная информация в нужный момент**.

Практики, разбираемые в конспекте:

1. Индексация большой кодовой базы для быстрого поиска релевантного кода.
2. Использование актуальной документации вместо только обучающих данных модели.
3. Сокращение избыточного использования MCP-серверов.
4. Правило «один чат — одна задача» во избежание конфликтов контекста.
5. Поддержание компактного окна контекста для лучшей стоимости и точности.
6. Мониторинг использования контекста через status-line и verbose-режимы.
7. Генерация постоянных инструкций проекта командами инициализации.

## Индексация кодовой базы

Крупные проекты сложно понять агенту простым «прямым» исследованием — при тысячах файлов и миллионах строк кода нельзя каждый раз перечитывать всё с нуля.

**Пример масштаба:** публичный репозиторий с GitHub — клонирование занимает несколько минут, ~900 000 объектов, ~21 900 файлов, ~17 млн строк кода.

Как агенту отвечать на вопросы о таком проекте, не тратя время и токены на сканирование файла за файлом?

> [!info] Решение 
> **Индексация кодовой базы** строит поисковое представление репозитория. Вместо прямого просмотра всего кода агент делает запрос к индексу и получает только релевантные части проекта.

### Augment Code и Auggie для индексации

Одно из практических решений — **Augment Code**, используемый через **Auggie CLI** и MCP-интеграцию. Решение платное и проприетарное, но демонстрирует общий подход к индексации.

- Augment Code применяется для контекстного улучшения промптов, а также как MCP-сервер.
- Индексация репозитория выполняется через Auggie CLI, а не через расширение VS Code — расширение не всегда корректно работает как MCP-сервер.
- После запуска Auggie в репозитории начинается индексация workspace: даже при ~17 млн строк кода она завершается примерно за **7 минут**.
- Сама индексация бесплатна в этом примере; платным является доступ к индексу и его использование.
- После завершения индексации разработчик может выйти из Auggie и использовать любимого агента (Codex, Claude Code), при условии, что MCP-сервер Auggie ему доступен — тогда агент может вызывать инструмент retrieval по кодовой базе.

### Вопросы к кодовой базе с индексом и без

Тестовый вопрос: _«Где в проекте реализован LLM provider?»_

|Режим|Результат|
|---|---|
|**С Auggie MCP**|Агент вызывает MCP codebase retrieval — по сути, просит другую AI-систему найти нужную часть кода. Ответ приходит **менее чем за минуту**|
|**Без индекса**|Агент использует встроенные инструменты чтения/поиска файлов, сканирует множество файлов. Заняло **~1 мин 30 сек** и потребовало **более 700 000 cache reads**|

> [!success] Вывод 
> Индекс кодовой базы помогает агенту быстрее и с меньшими затратами отвечать на структурные вопросы о крупном проекте. Встроенное исследование по-прежнему работает, но дороже и менее эффективно на больших проектах.
> 
> Можно использовать коммерческое решение, собственную реализацию или другого поставщика — суть одна: агенту не нужно каждый раз заново «открывать» всю кодовую базу.

## Актуальная документация

Осведомлённость о кодовой базе — лишь часть context engineering. Агентам также нужна **актуальная документация**, особенно при генерации кода, зависящего от внешних платформ, библиотек, облачных сервисов и API.

Внутренние знания модели ограничены датой отсечения обучающих данных:

- модель Claude Opus в демонстрации сообщает дату отсечения **январь 2026**;
- некоторые модели Gemini сообщают дату отсечения **январь 2025**, даже при более новых названиях моделей.

**Практический тест:** попросить модель создать пример Terraform-конфигурации для Kubernetes-кластера на AWS.

> [!warning] Проблема 
> При опоре только на внутренние знания модель сгенерировала конфигурацию с **Kubernetes 1.30** — версией, срок поддержки которой закончился **15 июля 2025 года**.

### Context7 для получения свежей документации

**Context7 MCP** даёт агенту прямой доступ к актуальной документации: агент может определить нужную библиотеку/источник документации и запросить самые свежие данные.

В примере с Kubernetes и Terraform: сессия перезапускается, включается Context7 MCP, промпт повторяется с явным указанием использовать Context7. Агент определяет ID библиотеки, проверяет доступные источники документации, оценивает их и генерирует более актуальную конфигурацию.

> [!success] Результат 
> Сгенерированная конфигурация использует **Kubernetes 1.33** вместо устаревшей 1.30 — заметное улучшение, так как код больше не основан на версии с истёкшим сроком поддержки.

Точная версия не будет «идеальной вечно» — версии Kubernetes продолжают устаревать. Главный вывод: получение документации повышает актуальность и качество генерируемого кода по сравнению с опорой только на данные обучения.

### Почему не просто использовать веб-поиск

Веб-поиск тоже может помочь найти актуальную документацию, но он не всегда доступен и бесплатен.

- Провайдеры моделей могут предлагать встроенный веб-поиск/веб-фетч, но это создаёт зависимость от их экосистемы инструментов.
- При работе с open-source моделями, другими агентскими «упряжками» (harness) или локальными настройками прямой веб-поиск может быть недоступен.
- **Web fetch** и **web search** — разные вещи: fetch работает, когда агент уже знает точную страницу; search — когда нужно сначала найти, какая страница релевантна.
- Многие агенты не имеют встроенного веб-поиска, если не подключены к провайдеру поиска.
- Поисковые API могут быть платными (например, Brave Search требует платной подписки и лимита запросов); DuckDuckGo может давать бесплатный доступ в некоторых конфигурациях, но веб-поиск не стоит считать гарантированным, универсальным или всегда бесплатным.

> [!info] Ценность 
> Context7 Даёт агенту выделенный путь получения документации: работает с open-source библиотеками, а в платных версиях — и с приватными репозиториями. Это ценно для организаций с внутренними микросервисами, приватными API и закрытой справочной документацией — вместо повторного вставления контрактов API в чат агент может получать нужную документацию по запросу, что снижает **галлюцинации** в использовании API (выдуманные эндпоинты, параметры, контракты).

## Сокращение количества MCP-серверов

MCP-серверы добавляют мощные возможности, но и **потребляют контекст**. Каждый подключённый сервер добавляет имена инструментов, схемы, описания, инструкции по использованию — всё это должно быть видимо модели.

Примеры потребления контекста:

- **Auggie MCP** — всего один инструмент, но с описанием **более 2000 символов**.
- **Context7 MCP** — инструмент для определения ID библиотеки (>1000 символов) и более короткий инструмент для запроса документации.
- **GitHub MCP** и **Atlassian MCP** — «богатые» серверы со множеством инструментов; каждый добавляет инструкции и схемы. При загрузке многих серверов они могут занять значительную часть контекстного окна ещё до первого реального вопроса пользователя.

> [!note] Про Claude Code 
> Встроенные системные инструменты Claude Code уже потребляют около **15 000 токенов**. Добавление множества MCP-серверов увеличивает нагрузку. Более новое поведение Claude Code улучшает это за счёт **загрузки MCP-инструментов по требованию** (on-demand), но не все инструменты поддерживают выборочную загрузку — в них особенно важно сокращать число подключённых серверов.

### MCPorter и CLI-инструменты вместо прямых MCP-подключений

Если нужно много MCP-возможностей, одна из стратегий — превратить MCP-серверы в **CLI-инструменты**.

- **MCPorter** — инструмент, конвертирующий настроенные MCP-серверы в инструменты командной строки.
- Вместо подключения агента напрямую к множеству серверов (и заполнения контекста полными описаниями инструментов) агент может использовать «скиллы» (skills) с минимальным frontmatter — сначала загружаются лишь несколько строк описания, а конкретная возможность вызывается через CLI при необходимости.
- У Context7 уже есть CLI-реализация — **CTX7**, позволяющая получать документацию без загрузки полного MCP-сервера в контекст.

> [!tip] Тренд 
> Часть рабочих процессов смещается от прямого использования MCP к CLI-инструментам. MCP по-прежнему полезен, CLI-инструменты тоже. Правильный выбор зависит от агента, workflow и допустимой нагрузки на контекст.

## Один чат — одна задача

Одна из простейших и сильнейших практик context engineering — **одна задача на один чат**.

Модель видит всю историю диалога и использует её при ответе на следующее сообщение. Это полезно, пока разговор сфокусирован, но вредно, когда в нём смешано много несвязанных задач.

> [!danger] Конфликт контекста (context clash)
> Если в одном чате смешаны маркетинг, программирование, юридические тексты и видеосценарии, модель может переносить сигналы из ранних задач в поздние — старые инструкции, цели или примеры могут вступать в конфликт с новой задачей.

Смешанные диалоги также вызывают **отвлечение контекста (context distraction)** — AI тратит внимание на уже неактуальную информацию, что может приводить к более медленным ответам, слабым рассуждениям и странным ошибкам.

Workflow с фоновыми агентами (background agents) естественно поощряет паттерн «одна задача — один чат»: задача назначается, агент выполняет её без постоянного взаимодействия, и каждая задача становится изолированной сессией.

**Практическое правило:** отдельная сессия для каждого проекта, темы или цели. Код — в одном чате, тексты — в другом, исследования — в третьем, документация — в четвёртом. Для новой задачи — новый чат с только нужными для неё деталями.

## Почему меньший контекст часто работает лучше

Большие контекстные окна полезны, но не означают, что их нужно заполнять целиком.

> [!example] Аналогия 
> Автомобиль может разгоняться до 250 км/ч, но это не значит, что нужно ездить на максимальной скорости постоянно. Обычные скорости безопаснее и легче для машины. Так же и с контекстным окном: оно доступно на случай необходимости, но AI обычно работает лучше при более компактном и сфокусированном контексте.

В одной рабочей сессии индикатор показывал лишь **13% использования контекста**, но в абсолютных цифрах это уже было **более 100 000 токенов**. Не так давно 200 000 токенов было максимальным размером контекста для многих моделей Anthropic — сессия, кажущаяся небольшой по проценту, может быть очень большой в абсолютных токенах.

Большой контекст может снижать производительность: модели приходится «перебирать» больше информации, важные детали могут теряться — особенно в середине длинного диалога или документа. Это явление часто называют **«потеря в середине» (lost in the middle)**: модель легче замечает информацию в начале и в конце, упуская ключевые факты, спрятанные в середине.

> [!tip] Цель — не меньше информации, а более сфокусированная информация 
> Хороший контекст ясен, релевантен и полон: включает то, что нужно модели, и исключает то, что уже не имеет значения.

Полезные практики:

- Убирать старые задачи из текущего контекста.
- Оставлять только релевантную историю.
- Помещать важные инструкции ближе к концу.
- Использовать короткие резюме вместо огромных логов диалога.
- Делиться только теми файлами/разделами, которые действительно нужны.

## Размер контекста, кэш и стоимость

Контекст также влияет на **цену**. В экране использования Claude Code сессия может показывать около **100 000 cache reads** и **200 000 cache writes**, с общей стоимостью чуть выше двух долларов.

- **Cache write** — система сохраняет переиспользуемые части диалога (инструкции, файлы, предыдущую историю сообщений).
- **Cache read** — система переиспользует сохранённый контекст вместо обработки всего с нуля.

> [!warning] Кэширование не делает длинные диалоги бесплатными 
> Очень длинный контекст всё равно может стоить дороже, работать медленнее и снижать фокус AI. Чем больше старой информации остаётся в контекстном окне, тем больше модели приходится учитывать — это увеличивает стоимость, снижает скорость и качество ответов, когда модель уделяет внимание устаревшим или нерелевантным деталям.

**Простое правило: держите контекст чистым.**

- Начинайте новый чат при смене темы.
- Удаляйте ненужные файлы.
- Используйте команды сжатия, например `/compact`, для резюмирования длинных обсуждений.
- Копируйте и вставляйте только то, что действительно важно.

## Мониторинг контекста

Context engineering требует **видимости**. Если разработчик не видит использование контекста, потребление токенов или выбор модели, управлять стоимостью и производительностью сложно.

**В Codex** status-line по умолчанию может показывать только процент оставшегося контекста. Этого недостаточно: если окно контекста — миллион токенов, и осталось 79%, это всё равно означает, что уже потрачено около **210 000 токенов**. Процент сам по себе может скрывать реальный масштаб сессии.

Полезная информация в status-line:

- выбранная модель;
- уровень «размышления» (reasoning level);
- текущая директория;
- текущая Git-ветка;
- объём использованного контекста;
- количество потраченных в сессии токенов.

**В Claude Code** соответствующая настройка менее очевидна: включение подробного (verbose) вывода в первую очередь не означает генерацию множества логов — важный эффект в том, что отображается потребление токенов во время сессии. Также доступна команда визуализации контекста `/context`, показывающая размер контекстного окна и текущее потребление токенов.

> [!note] Важно Каждый новый промпт обрабатывается вместе с уже существующим контекстом. 
> Если сессия уже содержит 70 000 токенов, а пользователь отправляет простое «привет», модель всё равно получает соответствующую историю диалога и контекст сессии — агент должен обработать этот контекст перед ответом или использованием инструментов.

Мониторинг использования контекста — первый шаг к управлению им.

## Инициализация инструкций проекта через init

AI-агенты работают лучше, когда у них есть **постоянные инструкции проекта**. Вместо объяснения структуры проекта, команд, конвенций и ожиданий каждый раз заново, разработчик может позволить агенту изучить репозиторий и создать файл инструкций.

- **В Codex** команда `/init` сканирует репозиторий и генерирует файл **AGENTS.md** — гид по проекту для агентов: описание проекта, важные команды, структура, рабочий процесс разработки, рекомендации по тестированию и другие заметки.
- **AGENTS.md** становится общей конвенцией для инструкций агентов, совместимой с несколькими инструментами (Codex, OpenCode, Replit и другими).
- Некоторые инструменты используют собственные файлы: Claude Code обычно использует **CLAUDE.md**, а Gemini/Antigravity-подобные workflow — **GEMINI.md**.

Та же идея инициализации применима и в Claude Code: команда `/init` позволяет агенту изучить проект и создать **CLAUDE.md**. В примере Codex создаёт около **30 строк** инструкций, а Claude — около **60 строк** (более развёрнутая версия), но обе служат одной цели: сохранить знания о проекте, чтобы агенту не приходилось каждый раз заново их «открывать».

> [!tip] Практический совет 
> Файлы инструкций можно редактировать вручную и переносить полезные части между ними. Можно держать **AGENTS.md** как единый источник истины, а остальные файлы (CLAUDE.md, GEMINI.md, replit.md) снабдить короткой инструкцией — читать AGENTS.md.

Эта практика особенно полезна для **brownfield**-проектов (с уже существующей кодовой базой). Для **greenfield**-проектов (с нуля) более подходящим может быть spec-first подход, например **GitHub Spec Kit**, — в зависимости от проекта и процесса команды.

## Итог

Эффективная разработка с помощью AI — это не только выбор мощной модели, а управление **информационным окружением** вокруг неё:

- Крупной кодовой базе нужна индексация для быстрого получения релевантного кода.
- Внешним платформам нужна актуальная документация, чтобы сгенерированный код не опирался на устаревшие данные обучения.
- MCP-серверы нужно использовать осторожно — каждый подключённый инструмент потребляет контекст.
- Длинных диалогов при смене задач стоит избегать.
- Контекстные окна должны оставаться сфокусированными, даже если модель поддерживает очень большие лимиты.
- Использование токенов должно быть видимым через status-line, verbose-вывод и визуализацию контекста.
- Инструкции проекта должны быть инициализированы и поддерживаться, чтобы агент начинал каждую задачу с правильными локальными знаниями.

> [!success] Итоговый эффект 
> Эти практики делают агентов более надёжными: снижают число галлюцинаций, уменьшают стоимость, повышают скорость и помогают AI сосредоточиться на задаче, которая действительно важна.
