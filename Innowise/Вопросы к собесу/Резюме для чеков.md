# **Projects**

**DrupalJira: Issue Tracking System**

DrupalJira is a project and issue tracking system built on Drupal 11. It is my main Drupal project, and I created it to practice backend development in a realistic scenario. The main idea is to manage projects and tasks with Kanban boards, Scrum sprints, time tracking and project statistics.

For the technologies, I used Drupal 11 and PHP 8.4 with MariaDB, and DDEV with Docker for the local environment. I worked with the Entity, Plugin, Form, Routing, Access and Migrate APIs, Workflows and Content Moderation, Twig, AJAX and Drupal behaviors.

I was responsible for the whole implementation. I developed custom modules for the Kanban board, task status updates, modal views and sprint management. I created time_log as a custom content entity with its own forms, access control and list builder. I implemented the task lifecycle with Workflows and Content Moderation, and I built project statistics in dependency-injected services with EntityQuery and AggregateQuery, using render arrays with cache tags. I also wrote event subscribers, a CSV migration, integrated Media Library and Paragraphs for task attachments, and added Playwright tests. To keep the code quality high, I used PHPCS, PHPStan and GrumPHP.

It is a personal project that I built during my internship. I used Git Flow on GitHub, with feature branches and pull requests.

**Live Voting App**

Live Voting App is a full-stack application where users create polls, collect votes and see the results update live. It is a monorepo with a React frontend and an Express.js REST API.

For the technologies, I used React 19, TypeScript, Vite, TanStack Router and TanStack Query on the frontend. On the backend, I used Node.js, Express.js, PostgreSQL with Prisma, and Zod for validation. The live results work through WebSocket/SSE, and the whole project runs in Docker Compose. For testing, I used Vitest, React Testing Library, MSW and Supertest.

I designed and built both parts of the application. I implemented the poll and voting APIs with flexible options, single and multiple choice, anonymous voting and poll expiration. I built protection against duplicate votes with sessions, IP checks and rate limiting, and I secured the API with Helmet, a CORS policy and secure cookies. I also created a unified validation and error-handling layer, implemented the live results, and covered the project with unit, integration and end-to-end tests. In addition, I set up CI with GitHub Actions, ESLint, Prettier and Husky, and deployed the application with logging, health checks and error monitoring.

It is a personal project, so I worked alone, using Git Flow on GitHub.

# **Интересная/сложная задача**

**DrupalJira: updating pages with AJAX**

One of the most interesting tasks for me in DrupalJira was to update parts of a page without a full reload. On the Kanban board, when a task changes its status or a modal view opens, only the necessary part of the page should be refreshed. I used the Drupal AJAX system together with custom JavaScript and Drupal behaviors, so the new content is attached correctly after every update. I kept the business logic on the server side: Workflows and Content Moderation decide which status changes are allowed. As a result, the board feels like a single-page application, but it is built with standard Drupal tools.

**DrupalJira: migrations and working with the database**

Another interesting part of DrupalJira was working with data. I implemented a CSV migration with the Migrate API and contributed migration plugins, so the data can be imported in a repeatable way. For time tracking, I created time_log as a custom content entity, and I used EntityQuery and AggregateQuery to calculate project statistics, so the database does the aggregation instead of PHP loops. The results are rendered through render arrays with cache tags, so they are cached and invalidated automatically when the data changes.

**Live Voting App: session, cookies and duplicate-vote protection**

The most interesting part of the Live Voting App for me was the backend security. I wanted every poll to be fair, so I had to prevent duplicate votes and still allow anonymous voting. I solved it with several layers: a session token in a cookie, an IP check on the server and rate limiting on the API. I also configured secure cookies and the CORS policy carefully, because the client and the API run on different origins, and cookies must be sent with credentials. In addition, I used Helmet and validated all input with Zod. As a result, every session can vote only once per poll, and each user manages only their own polls.

**Live Voting App: real-time results with WebSocket/SSE**

I also enjoyed implementing real-time results in the Live Voting App. When someone votes, every client that watches the poll should see the new numbers immediately, without refreshing the page. I used WebSocket/SSE: the server pushes updates to the connected clients, and the results page renders them instantly. I paid attention to the connection lifecycle and to keeping the pushed data consistent with the data in PostgreSQL. In the end, the results page works like a live dashboard, and the API is not loaded by constant polling.

**AI Analytics Platform: configuring a model for a specific task**

In the AI-Powered Analytics Platform, the most interesting task was to configure a language model for one specific job. I used OpenRouter with GPT-4o mini and defined a response schema, so the model always returns structured JSON: summaries, tables, code snippets, lists and chart data. I wrote the instructions for the model around the analytics use case. The frontend relies on this format and renders interactive Recharts line and bar charts directly from the response. As a result, the assistant is predictable: the interface does not parse text, and every response type has its own component.


# **Интересный баг**

One interesting bug that I fixed was connected with email notifications in the AI analytics application. The application sends emails for email verification and password recovery, and I used Resend as the email provider. At the beginning, the emails did not work as expected: the integration between the backend, the authentication layer and Resend needed a correct configuration, and the messages looked plain and unfinished.

Every email contains a unique URL with a token, so the link must lead to the correct frontend page and work only for the right user. I fixed the problem step by step. First, I configured the email delivery on the backend. Then I created a clean HTML template for the messages. Finally, I checked that every generated link opens the correct page in the frontend.

As a result, the emails are delivered reliably, they look professional, and the verification and password recovery flows work from start to finish. This bug taught me to test integrations with external services end to end, and not only in code.
