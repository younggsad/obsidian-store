# ЧАСТЬ 4. CRITICAL RENDERING PATH (CRP)

## 4.1 Общее определение

>**Critical Rendering Path** — последовательность шагов, которые браузер выполняет, чтобы преобразовать HTML, CSS и JavaScript в пиксели, отображаемые на экране. Понимание CRP критически важно для **оптимизации производительности** загрузки страницы — большинство техник ускорения сайта (что грузить раньше, что позже, что блокирует рендер) построены именно на знании этого процесса.

## 4.2 Пошаговый процесс

### Шаг 1 — Построение DOM (Document Object Model)

Браузер получает HTML-документ (обычно частями, по мере скачивания) и **парсит** его построчно, превращая теги в дерево объектов — DOM. Это происходит постепенно (streaming parsing) — браузер не ждёт полной загрузки файла, а начинает строить дерево по мере поступления данных.

```html
<html>
  <body>
    <p>Текст</p>
  </body>
</html>
```

→ превращается в дерево узлов: `html → body → p → "Текст"`

### Шаг 2 — Построение CSSOM (CSS Object Model)

Аналогично DOM, но для CSS — браузер парсит все стили (из `<link>`, `<style>`) и строит дерево, описывающее, какие стили применяются к каким узлам, с учётом каскада и специфичности.

⚠️ **Важная особенность: CSS — render-blocking (блокирует рендеринг) по умолчанию.** Браузер не начнёт отрисовку страницы, пока не построит **полный** CSSOM — потому что иначе пришлось бы сначала показать неоформленный контент, а потом резко "дёрнуть" его при применении стилей (это называлось бы FOUC — Flash of Unstyled Content, и браузеры намеренно этого избегают).

### Шаг 3 — Построение Render Tree (дерева рендеринга)

DOM и CSSOM объединяются в **Render Tree** — структуру, которая содержит только те узлы, которые реально будут **видимы** на странице (с учётом их вычисленных стилей).

Элементы с `display: none` **не попадают** в Render Tree вообще (в отличие от `visibility: hidden`, которая занимает место, но невидима — такой элемент в Render Tree присутствует, просто не отрисовывается).

### Шаг 4 — Layout (Reflow) — расчёт геометрии

Браузер вычисляет **точные координаты и размеры** каждого элемента на странице — где именно (в пикселях) должен находиться каждый узел Render Tree с учётом размеров экрана/окна.

### Шаг 5 — Paint (отрисовка)

Браузер закрашивает пиксели — фактически превращает геометрию из Layout в визуальные пиксели: цвета, тексты, изображения, тени, границы.

### Шаг 6 — Composite (композиция)

Если страница состоит из нескольких "слоёв" (например, элементы с `position: fixed`, CSS-анимации, `transform`, `opacity` часто создают отдельные композитные слои для оптимизации) — браузер собирает их в правильном порядке в финальное изображение, которое видит пользователь.

## 4.3 Схема CRP целиком

```
HTML  →  DOM  ─┐
                ├──→  Render Tree  →  Layout  →  Paint  →  Composite
CSS   →  CSSOM ─┘
```

## 4.4 Роль JavaScript в CRP — тоже render-blocking по умолчанию

**`<script>` без атрибутов `async`/`defer`, встреченный в HTML во время парсинга, полностью останавливает построение DOM**, пока скрипт не будет скачан (если внешний) и выполнен. Это потому, что JS может изменить сам DOM/CSSOM через `document.write()` или прямые манипуляции — браузер не может продолжать парсинг, не зная, не изменит ли скрипт то, что уже построено.

```html
<script src="app.js"></script>          <!-- блокирует парсинг HTML полностью -->
<script src="app.js" async></script>     <!-- скачивается параллельно с парсингом, выполняется СРАЗУ по готовности (может прервать парсинг в произвольный момент) -->
<script src="app.js" defer></script>      <!-- скачивается параллельно, но выполняется ТОЛЬКО после полного построения DOM, и строго в порядке следования скриптов -->
```

**Практическая рекомендация:** для скриптов, которым не нужен доступ к DOM немедленно (аналитика, независимые виджеты) — `async`. Для скриптов, зависящих от порядка и/или от готового DOM (большинство "обычных" приложений) — `defer`. Размещение `<script>` перед закрывающим `</body>` — более старая практика, дающая похожий эффект без использования атрибутов, но `defer` считается более современным и гибким решением.

## 4.5 Critical CSS — оптимизация под CRP

Так как CSS блокирует рендеринг **полностью**, пока не обработается весь CSSOM, одна из техник оптимизации — **Critical CSS**: встраивание стилей, необходимых для отображения видимой без прокрутки части страницы ("above the fold"), прямо в `<head>` через `<style>`, а остальной, менее срочный CSS — подгружать асинхронно.

```html
<head>
  <style>
    /* Критические стили для видимой сразу части страницы */
    header { ... }
    .hero { ... }
  </style>

  <link rel="preload" href="styles.css" as="style" onload="this.rel='stylesheet'">
  <!-- Остальные стили подгружаются асинхронно, не блокируя первый рендер -->
</head>
```

## 4.6 Reflow и Repaint — почему это важно для производительности JS-кода

- **Reflow (Layout)** — пересчёт геометрии (позиций, размеров) — самая "дорогая" операция.
- **Repaint** — перерисовка пикселей без изменения геометрии (например, смена цвета) — дешевле, чем reflow.
- **Composite** — самое дешёвое: не требует ни пересчёта геометрии, ни перерисовки пикселей, только сборка уже готовых слоёв (обычно задействуется для `transform`/`opacity`).

**Практический вывод для оптимизации анимаций:** анимировать `transform`/`opacity` — предпочтительнее (задействует только Composite), чем анимировать `width`/`height`/`top`/`left` (вызывает Layout на каждый кадр — гораздо тяжелее для производительности, может приводить к "дёрганой" анимации).

```javascript
// ❌ Дорого — вызывает Layout на каждом кадре
element.style.left = "100px";

// ✅ Дёшево — задействует только Composite
element.style.transform = "translateX(100px)";
```

**"Layout Thrashing"** — частая ошибка производительности: чередование чтения геометрии (`element.offsetHeight`) и записи стилей (`element.style.x = ...`) в цикле — каждое такое чтение после записи заставляет браузер выполнить принудительный синхронный Reflow, вместо того чтобы отложить и объединить все изменения.

```javascript
// ❌ Плохо — Layout Thrashing (чтение-запись чередуются в цикле)
elements.forEach((el) => {
  el.style.width = el.offsetWidth + 10 + "px"; // чтение ПОСЛЕ предыдущей записи форсирует reflow
});

// ✅ Хорошо — сначала все чтения, потом все записи
const widths = elements.map((el) => el.offsetWidth);
elements.forEach((el, i) => {
  el.style.width = widths[i] + 10 + "px";
});
```
